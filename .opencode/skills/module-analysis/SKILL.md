# 模块分析技能 (module-analysis)

当用户指定进行业务模块分析（如 `gateway`, `user` 等）时，加载此技能。

## 1. 核心行为准则
- **源码深度**：覆盖 98%+ 的关键业务逻辑、分支、异常处理、数据流和组件交互；对 WebFlux/响应式模块补充 Filter 顺序、线程模型、背压和上下文透传。
- **禁止源码翻译**：禁止逐行翻译代码。聚焦模块为什么这样设计、关键 API/组件为什么这样选、状态如何变化、异常如何传播以及它在业务链中的位置。
- **关注重点**：鉴权只做基础可用性和关键边界检查，不作为主要篇幅；主要深挖业务逻辑、数据一致性、Redis/MySQL/MQ/ES、分布式事务/锁/幂等、微服务调用、性能、工程质量和可观测性。
- **代码不可默认正确**：现有代码、注释、历史评审和设计文档都必须接受验证；发现 Bug、逻辑缺陷、架构风险或工程问题时，记录影响并可提出或实施修复。
- **事实优先级**：`当前代码实际逻辑` > `当前运行结果` > `当前分支改动` > `test-3/` 方法论与结果 > `test-2/` 历史文档。
- **文件覆盖对账**：分析完成后，必须对比 `project-directories/` 清单与实际模块文件，列出已覆盖、未覆盖、明确暂不分析的文件，并在报告中说明原因。

## 2. 标准产出结构
对于每个微服务模块，必须依次输出以下内容：

1. **当前模块定位**：职责、核心能力、在整条业务链的位置。
2. **当前代码事实**：基于真实目录、`pom.xml`、配置和启动入口确认事实。
3. **关键业务链路与源码流转**：
   - 使用逻辑图描述入口、服务、数据和异步流转
   - 以源码符号和行号为证据，分析关键决策，不做逐行翻译
   - 详细拆解状态机、边界条件、异常路径、重试和补偿
4. **数据流转与中间件参与点**：Redis/MySQL/MQ/ES 的 key、表、topic、索引、读写时机和一致性边界。
5. **跨模块与分布式行为**：Feign/RPC、超时/降级、事务消息、TCC、幂等、锁、分片、最终一致性。
6. **性能与工程质量**：线程池、连接池、缓存、限流、阻塞调用、资源释放、配置、构建、部署和恢复能力。
7. **鉴权基础检查**：只确认入口是否可用、关键边界是否失守，不把鉴权细节作为主要篇幅。
8. **当前分支/近期改动点**：明确区分现有基础功能、当前工作区改动、已修复问题和待修问题。
9. **风险与测试重点**：按代码 Bug、业务逻辑、分布式、微服务、性能、工程、可观测性分类。
10. **覆盖对账**：与 `project-directories/` 中该模块清单逐项对比，列出已覆盖、未覆盖和暂不分析文件。

## 3. 分析过程中的代码优化规则
- 分析过程中发现的明显问题（Bug、死代码、风险隐患），可直接提出修复方案。
- 禁止默认“现有代码即正确”，保持批判性视角。
- 修复前记录：问题说明、影响范围、修复理由。
- 修复后必须重新编译或执行对应验证，并记录验证结果。
- 不因已有注释、历史 review 或“当前能启动”而跳过源码与运行验证。

## 5. 运行环境恢复规则
- Docker 中间件容器配置了自动重启，机器重启后应先检查并确认容器健康状态。
- Java 微服务不是容器化自动恢复进程，机器重启或关机后不会自动启动。
- 每次重新开始测试或运行验证前，必须单独执行微服务启动流程，并逐项检查端口、健康状态和 Nacos 注册状态。
- 不能因为中间件已恢复，就假设微服务也已恢复；不能把上一次会话的微服务运行状态当作当前事实。

## 4. 模块分析工作流
1. 读取 `project-directories/<module>/inventory.md`，建立真实文件基线。
2. 扫描模块实际目录，补充 inventory 未展开的嵌套文件。
3. 阅读启动类、构建文件、配置、Controller、Service、Client、Consumer、Job、Mapper、关键工具类和测试入口。
4. 按业务链路分析同步调用、异步消息、数据写入、缓存和补偿。
5. 分类记录问题：代码 Bug、业务逻辑、分布式、微服务、性能、工程、可观测性、安全基础。
6. 分析完成后做文件覆盖对账；任何未读文件必须写明原因。
7. 只有在分析事实稳定后，才创建或更新对应测试文档；测试不得替代源码分析。
