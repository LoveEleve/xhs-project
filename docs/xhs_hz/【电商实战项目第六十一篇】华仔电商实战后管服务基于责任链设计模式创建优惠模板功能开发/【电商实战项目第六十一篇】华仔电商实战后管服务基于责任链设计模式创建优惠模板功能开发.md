## **2.3 基于责任链设计模式来创建优惠券模板**

### **2.3.1 什么是责任链设计模式**

先来看下什么是「**责任链设计模式**」。

「**责任链设计模式**」的英文翻译是 Chain Of Responsibility Design Pattern。在 GoF 的《设计模式》中，它是这么定义的：

Avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Chain the receiving objects and pass the request along the chain until an object handles it.

简单翻译如下：将请求的发送和接收解耦，让多个接收对象都有机会处理这个请求。将这些接收对象串成一条链，并沿着这条链传递这个请求，直到链上的某个接收对象能够处理它为止。

简单来说：在该设计模式中，多个处理器（也就是刚刚定义中说的“接收对象”）依次处理同一个请求。一个请求先经过 A 处理器处理，然后再把请求传递给 B 处理器，B 处理器处理完后再传递给 C 处理器，以此类推，形成一个链条。链条上的每个处理器各自承担各自的处理职责，因此叫作「**责任链模式**」，如下图所示：

  
![](images/FoPPLdw2EkyzHUAOYUD3CXwZis4Y.png)

![](images/FoPPLdw2EkyzHUAOYUD3CXwZis4Y.png)

如果还不理解的话，再给大家举个例子，SpringMvc 中可以定义拦截器，并且可以定义多个。当一个用户发起请求时，顺利的话请求会经过所有拦截器，最终到达业务代码逻辑，SpringMvc 拦截器设计就是使用了「**责任链设计模式**」。

为什么说顺利的话会经过所有拦截器？这是因为请求不满足拦截器自定义规则会被打回，但这并不是「**责任链设计模式**」的唯一处理方式，继续往下看。

在「**责任链设计模式**」中，多个处理器依次处理同一个请求。一个请求先经过 A 处理器处理，然后再把请求传递给 B 处理器，B 处理器处理完后再传递给 C 处理器，以此类推，形成一个链条，链条上的每个处理器「**各自承担各自的处理职责**」**。**

责任链模式中多个处理器形成的处理器链在进行处理请求时，有两种处理方式：

1.  请求会被**所有的处理器都处理一遍，不存在中途终止的情况**，可以参照 MyBatis 拦截器理解。
2.  处理器链执行请求中，某一处理器执行时，**如果不符合自定义规则的话，就会停止流程，并且生效的未执行处理器并不会执行了**，可以参照 SpringMvc 拦截器理解。

### **2.3.2 责任链业务场景设计及好处**

假设，当我们**系统处在一个下游系统**，因为业务需求系统中所使用的**基础数据需要从上游中台同步到系统数据库**。

基础数据包含了很多类型数据，**只要是人为录入就可能会存在问题，遵从对上游系统不信任原则**，需要对数据接收时进行一系列校验。

最初是要进行一系列验证原则才能入库的，从我们系统的接入数据规则而言，个人觉得需要支持以下几套规则：

1.  **必填项校验**：如果数据无法满足业务所必须字段要求，数据一旦落入库中就会产生一系列问题。
2.  **非法字符校验**：因为数据如何录入，上游系统的录入规则是什么样的我们都不清楚，这项规则也是必须的。
3.  **长度校验**：同上如果系统某字段长度限制 100，但是接入来的数据 200 长度，这也会造成问题。
4.  等等。

当然真实中不止这三套。**一旦将责任链设计模式嵌入数据同步流程**，就会**完全符合开闭原则，提高代码的扩展性**。

这里要再强调下，**设计模式的应用场景一定要灵活掌握**，只有这样才能在合适的业务场景合理运用对象的设计模式。

这里为什么要采用**责任链设计模式**来实现呢？

如果不使用责任链模式，上面说的真实同步场景面临两个问题：

1.  代码逻辑和校验规则需要写到一起，**那么这个类/方法会奇大无比**。减少代码复杂性一贯方法是：**将大块代码逻辑拆分成函数，将大类拆分成小类**，是应对代码复杂性的常用方法。这样拆分是能解决代码复杂性，但是还会面临第二个问题。
2.  **开闭原则**：添加一个新的功能应该是在已有代码基础上扩展代码，而非修改已有代码。大家设想一下，假设你写了三套校验规则，运行过一段时间，这时候领导让加第四套，是不是要在原有代码上改动。

/\*\*

\* 基于责任链设计模式创建优惠券模板

\* @param request CouponRequest 新增参数

\* @return

\*/

@Override

@Transactional(rollbackFor = Exception.class)

public boolean create(CouponTemplateRequest request) {

/\*\*

\* 获取责任链上下文

\*/

CouponTemplateContext context \= new CouponTemplateContext();

// 设置请求体

context.setRequest(request);

LoginUserVO loginUserVo \= SecurityUtil.getLoginUserVo();

// 设置操作人

context.setOperatorUid(loginUserVo.getUser().getId());

try {

// 初始化模板对象

initTemplate(context);

// 添加空检查

if (handlers == null || handlers.isEmpty()) {

log.error("责任链创建优惠券模板出现异常，处理器未配置");

throw new IllegalStateException("责任链处理器未配置");

}

// 按 Order 顺序执行责任链相关处理器，这里的顺序是基于 @Order(xxx) 来进行排序的

handlers.stream()

.sorted(AnnotationAwareOrderComparator.INSTANCE)

.forEach(handler -> {

if (!context.hasErrors()) {

handler.handle(context);

}

});

if (context.hasErrors()) {

log.error("责任链创建优惠券模板出现异常：{}", context.getErrors());

throw new CompositeException(context.getErrors());

}

return context.getTemplate().getId() > 0;

} catch (Exception e) {

log.error("责任链创建优惠券模板出现异常2：{}", e.toString());

// 清理幂等Key

if (context.getIdempotentKey() != null) {

redisCache.delete(context.getIdempotentKey());

}

// 异常转换

handleException(e);

return false;

}

}

/\*\*

\* 初始化优惠券模板

\* @param context

\*/

private void initTemplate(CouponTemplateContext context) {

CouponTemplateRequest template \= context.getRequest();

template.setCouponStatus(false);

template.setCouponDel(false);

template.setCouponAuditStatus(1);

CouponTemplateVO couponTemplateVO \= new CouponTemplateVO();

BeanUtils.copyProperties(template, couponTemplateVO);

log.info("初始化优惠券模板,请求：{}, VO：{}", template, couponTemplateVO);

context.setTemplate(couponTemplateVO);

}

/\*\*

\* 处理异常

\* @param e

\* @return

\*/

private ApiResult handleException(Exception e) {

if (e instanceof BizException) {

BizException be \= (BizException) e;

log.error("责任链创建优惠券模板出现异常3：{}", be.getMessage());

return ApiResult.doError(be.getCode(), be.getMessage());

}

return ApiResult.doResult(BizCodes.COMMON\_SERVER\_ERROR);

}
