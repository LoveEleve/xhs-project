# 08 · 商家搜索与事件同步

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：商家搜索 = **分片键只伺候买家 → 商家维度用 ES 异构索引（Canal→MQ→ES）+ 存量回填**；
> 点赞数/行为走事件同步——搜索只做"发现"，写操作以 DB 为准。
>
> **本篇带走**：① 为什么需要商家索引 ② 同步/回填/守卫 ③ 点赞数同步 ④ 行为上报。
> 前置：02。证据：`SellerOrderSearchService`、`SellerSubOrderIndexSyncConsumer`、
> `SellerSubOrderIndexBackfillJob`、`LikeCountSyncConsumer`、`BehaviorReportConsumer`、C-004。

---

## 0. 例子：三种"非搜索"的数据同步

```
① 商家按"状态=待发货 + 时间范围"搜子单
   → 订单按 user_id 分片，商家没有 user_id → 无法路由
   → ES seller_sub_order_index（Canal 根+存量回填）

② 用户点赞 → ES note_index.likeCount 要变
   → SOCIAL_TOPIC → LikeCountSyncConsumer → 读 analytics 权威 Set → partial update

③ 推荐行为上报
   → RECOMMEND_BEHAVIOR_TOPIC → BehaviorReportConsumer → t_user_behavior（INSERT IGNORE）
```

## 1. 生产环境怎么做（淘宝/行业常见）

| 问题 | 常见做法 |
|---|---|
| 分片键只伺候一个维度 | 为另一维度建**异构索引/读模型**（ES/数仓），不改分片键 |
| 索引供给 | CDC/binlog → MQ → 索引；存量用回填任务 |
| B 端查询 | 强制 sellerId 过滤；分页/筛选；ES 只做发现 |
| 计数同步 | 事件驱动 + 权威计数源；partial update |
| 行为流水 | MQ 异步落库 + 幂等键 |

## 2. 本项目的实现（代码证据）

### 2.1 问题：分片键只伺候买家

订单按 `user_id` 分片（`t_sub_order_0..3`）；商家手里只有 `sellerId/subOrderNo`：

- 按 `user_id` 路由 → 商家查不了；
- **候选解法对比**（C-004）：

| 方案 | 问题 |
|---|---|
| 全分片 scatter | 慢、放大 |
| 映射表 | 额外维护、热点 |
| 业务双写 | 一致性差 |
| 改分片键 | 买家查询崩 |
| 基因法 | 改造大 |
| **ES 异构索引** | ✅ 标准解（Canal+回填） |

- **ES 异构索引** → 商家维度读模型。

### 2.2 商家索引同步：Canal → MQ → ES

```
Canal order_instance（t_sub_order_0..3 binlog）
  → SUB_ORDER_INDEX_TOPIC
  → SellerSubOrderIndexSyncConsumer
  → seller_sub_order_index
```

```java
// doc id = subOrderNo；版本 = ts（缺失回退 es）+ ExternalGte
long version = canalMsg.getLongValue("ts", System.currentTimeMillis());
if (version == 0) version = canalMsg.getLongValue("es", System.currentTimeMillis());

if ("DELETE".equals(type) || row.getIntValue("deleted", 0) == 1) {
    indexWriter.softDelete(subOrderNo, version);   // 软删标记
} else {
    indexWriter.upsert(subOrderNo, documentBuilder.build(row), version);
}
```

- 同 id 重放幂等；乱序旧事件不覆盖；
- 失败单号进 `myxhs:es:sync:failed:seller-sub-order`（1h）+ MQ 重试；
- **ES 只做发现**：发货等写操作仍以 DB + CAS 为准。

### 2.3 存量回填 + 查询守卫

**存量回填**（Canal 只捕增量，存量必须回填；部署顺序：先回填后切流量）：

```java
R<List<Map<String, Object>>> resp =
        orderFeignClient.subOrderScan(cursor, effectiveLimit); // 上限 1000
// 成功一批 → 写 ES → 更新 Redis 断点 lastId；失败保留断点可重入
```

- `scheduledBackfill` + 手动 `/api/search/seller-order/backfill`；
- 游标分页，断点续传；批次上限 1000（防 order 侧误判收尾）。

**查询守卫**：

```java
@GetMapping("/list")
@RateLimit(windowSeconds = 1, maxRequests = 10, perUser = true, ...)
public R<SellerOrderPageVO> list(@RequestParam(required = false) Long sellerId, ...) {
    if (!accessTokenGuard.isAdminCall(adminCall)) return R.fail(403, "无权访问管理接口");
    if (sellerId == null || sellerId < 0) return R.fail(PARAM_INVALID, "sellerId 必填");
    return R.ok(service.search(sellerId, status, startTime, endTime, page, size));
}
```

- `sellerId` **必填**（不允许"查所有商家"，防全量泄漏）；
- `X-Admin-Call` 管理角色（真实商家身份体系是演进项）；
- 查询：`term(sellerId)` + `deleted=false` + 可选 status/时间范围（`createdAt`）+ `createdAt desc` + `from/size`（B 端，页大小上限 100）。

### 2.4 点赞数同步：读 analytics 权威 Set

```java
// SOCIAL_TOPIC LIKE/UNLIKE → LikeCountSyncConsumer
if (bizType != 1) return; // 只处理笔记点赞

Long likeSetSize = stringRedisTemplate.opsForSet()
        .size("myxhs:like:note:" + noteId);   // analytics 权威 Set（SCARD）
long likeCount = likeSetSize != null ? likeSetSize : 0L;

esClient.update(u -> u.index("note_index").id(noteId)
        .doc(Map.of("likeCount", likeCount)), Map.class);
```

**为什么不用 counter 的计数 key**（T-092）：search 与 counter **并行消费同一条 LIKE 消息**，
counter 写入前 search 可能读到旧值/0；analytics 的 Set 在 HTTP 响应前同步 SADD，无消费时序竞争。

### 2.5 行为上报：INSERT IGNORE 幂等

```java
// RECOMMEND_BEHAVIOR_TOPIC → BehaviorReportConsumer
INSERT IGNORE INTO t_user_behavior (id, user_id, note_id, behavior_type, duration)
VALUES (?, ?, ?, ?, ?)
```

- `id = eventId`：重投/重复消费被主键忽略，不产生毒丸；
- 上报接口先发 MQ；发送失败降级同步 INSERT IGNORE（同一 eventId）；
- 下游推荐用它算特征/兴趣标签（07）。

### 2.6 边界与一致性

| 关注点 | 归属 |
|---|---|
| 子单源数据/状态 | order（DB） |
| 商家订单索引 | search（ES） |
| 点赞计数权威 | analytics（Set） |
| 行为流水 | search 写入 content 库 `t_user_behavior` |
| 写操作（发货） | order DB + CAS，**不看 ES** |

- ES 最终一致：索引延迟不影响写操作/终态；
- 对账/强一致是演进项（C-004 非目标）。

## 4. 十二个坑

1. **用 user_id 分片查商家**：路由不到；必须异构索引。
2. **sellerId 不填**：变成"查所有商家"，数据泄漏；必须拒绝。
3. **先切流量后回填**：Canal 只捕增量，历史单搜不到；部署顺序=先回填。
4. **回填批次 >1000**：order 侧上限；误判收尾会漏单。
5. **doc id 用自增/随机**：重放不幂等；用 subOrderNo。
6. **删除直接物理删**：迟到旧事件复活；软删 + version，查询要带 `deleted=false`。
7. **把 ES 当写依据**：发货等必须 DB+CAS；ES 只是发现。
8. **点赞数读 counter key**：并行消费时序竞争；读 analytics Set（T-092）。
9. **行为不幂等**：重投变毒丸；eventId + INSERT IGNORE。
10. **时间范围不校验**：非法格式/时区；控制器/服务要兜底。
11. **索引失败静默**：失败单号进 Set + MQ 重试 + DLQ。
12. **强一致幻想**：C-004 明确最终一致；对账是演进项。

- **值得**：分片键维度的经典问题、异构索引、回填/守卫、点赞时序、行为幂等——B 端搜索与事件同步的核心；
- **一句话带过**：ES 字段、游标批次、Admin 令牌；
- **一句话**：**分片键只伺候买家 → 商家维度建 ES 异构索引（Canal+回填）；ES 只做发现，写操作以 DB 为准。**
- 索引一致性见 **02**；推荐见 **07**。

**面试口径**："订单按 user_id 分片，商家维度查不了——用 Canal→MQ→ES 建 seller_sub_order_index，存量用 order Feign 游标回填，部署先回填后切流量；sellerId 必填、ES 只做发现、写操作 DB+CAS；点赞数读 analytics 权威 Set 后 partial update，行为用 eventId + INSERT IGNORE 幂等。"
