# 01 · 数据源与边界

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：search 是**检索引擎 + 推荐引擎**，不是业务库——**没有自己的 MySQL 库**；
> 复用 content 数据源、跨库读 product、通过 Canal/MQ/Feign 取数、ES 承载索引。
>
> **本篇带走**：① 数据源地图 ② 契约（Canal/MQ/Feign）③ 跨库/派生表边界 ④ 为什么这么设计、坑在哪。
> 前置：00。证据：`06-搜索.md` §1/§3/§5、`feign/*`、`consumer/*`、`IndexRebuildJob`。

---

## 0. 例子：搜笔记 / 搜商品 / 商家搜订单

```
搜笔记   → ES note_index        ← Canal(content.t_note) → NOTE_INDEX_TOPIC
搜商品   → ES product_index     ← Canal(product.t_spu/t_sku) → PRODUCT_INDEX_TOPIC
商家搜单 → ES seller_sub_order_index ← Canal(order.t_sub_order) → SUB_ORDER_INDEX_TOPIC
                                     + order Feign 存量回填
热搜     → Redis 分钟桶 + 快照表（content 库 t_hot_search_snapshot）
联想     → ES suggest_index + Redis 缓存
历史     → Redis search:history:{userId}
```

三种搜索，数据来自三个不同的域；search 自己不拥有这些业务数据。

## 1. 生产环境怎么做（淘宝/行业常见）

| 关注点 | 常见做法 |
|---|---|
| 搜索服务定位 | 只拥有**索引/读模型**，不拥有业务源数据 |
| 数据供给 | CDC/binlog → MQ → 索引；或离线数仓/宽表 |
| 数据源 | 独立搜索库/特征库；避免直接跨业务库 JOIN |
| 一致性 | 最终一致；重建 + 别名切换；失败补偿/DLQ |
| 边界 | 业务域是源，搜索是派生；搜索不写业务源表 |

> 淘宝具体实现不公开；上面是搜索域的通用形态。

## 2. 本项目的实现（代码证据）

### 2.1 数据源地图

| 载体 | 内容 | 谁拥有 |
|---|---|---|
| **MySQL（content 库）** | 读 `t_note/t_comment`；读写 `t_item_feature`/`t_user_behavior`/`t_hot_search_snapshot` | content 域（search 复用连接） |
| **MySQL（product 库）** | 显式跨库读 `my_xhs_product.t_spu/t_sku` | product 域 |
| **ES** | `note_index` / `product_index` / `suggest_index` / `seller_sub_order_index` | **search 域** |
| **Redis** | 热搜分钟桶/榜、搜索历史、suggest 缓存、失败集合、重建进度、锁 | search 域 |
| **MQ** | `NOTE_INDEX_TOPIC` / `PRODUCT_INDEX_TOPIC` / `SUB_ORDER_INDEX_TOPIC` / `SOCIAL_TOPIC` / `RECOMMEND_BEHAVIOR_TOPIC` | 各源域生产，search 消费 |

**关键**：search **没有自己的业务库**；`spring.datasource.readwrite.enabled=true` 指向 content 库（读写分离）。

### 2.2 契约：Canal / MQ / Feign

**Canal（入）**：

```
note_instance   → NOTE_INDEX_TOPIC    → NoteIndexSyncConsumer
product_instance→ PRODUCT_INDEX_TOPIC → ProductIndexSyncConsumer（+ product 缓存失效）
order_instance  → SUB_ORDER_INDEX_TOPIC → SellerSubOrderIndexSyncConsumer
```

**MQ（入）**：

- `SOCIAL_TOPIC`（LIKE/UNLIKE）→ `LikeCountSyncConsumer` → 更新 `note_index.likeCount`；
- `RECOMMEND_BEHAVIOR_TOPIC` → `BehaviorReportConsumer` → `t_user_behavior`（INSERT IGNORE）。

**Feign（出）**：

```java
@FeignClient(name = "my-xhs-product")
public interface ProductFeignClient {
    @GetMapping("/api/product/spu/{spuId}")
    R<Map<String, Object>> getSpuDetail(@PathVariable Long spuId);
}

@FeignClient(name = "my-xhs-order", configuration = InternalCallFeignConfig.class)
public interface OrderFeignClient {
    @GetMapping("/api/order/internal/sub-order-scan")
    R<List<Map<String, Object>>> subOrderScan(@RequestParam("cursor") long cursor,
                                              @RequestParam("limit") int limit);
}
```

- product：索引补全（flat 消息/文档构建）；
- order：商家子单索引的**存量回填**（订单在分片库，search 无直连，必须经 order 域）。

### 2.3 跨库与派生表：边界在哪

**跨库读 product**：增量补偿/重建需要显式 `my_xhs_product.` 前缀：

```sql
SELECT s.id, s.name, ... FROM my_xhs_product.t_spu s
LEFT JOIN my_xhs_product.t_category c ...
LEFT JOIN my_xhs_product.t_sku k ...
```

P1-5 历史坑：search 默认数据源是 content 库，**不加库前缀 → 补偿必失败**。

**写 content 派生表**：

- `t_item_feature`（推荐特征）、`t_user_behavior`（行为）、`t_hot_search_snapshot`（热搜快照）；
- 这些表物理在 content 库，但由 search 读写——**"模块↔库"不是一对一**（结构事实，不是 bug）；
- 好处：不重复建库、不跨服务写；代价：边界模糊、content 库变更会波及 search。

**商家订单**：不直连分片库；增量走 `SUB_ORDER_INDEX_TOPIC`，存量走 `OrderFeignClient` 游标扫描。

**点赞数**：不读 counter 的计数 key（并行消费时序竞争），读 **analytics 权威 Set**：

```java
Long likeSetSize = stringRedisTemplate.opsForSet()
        .size("myxhs:like:note:" + noteId);
long likeCount = likeSetSize != null ? likeSetSize : 0L;
```

### 2.4 为什么 search 不建自己的库

| 理由 | 说明 |
|---|---|
| **源数据不在 search** | 笔记/商品/订单的源在 content/product/order；search 只做索引/读模型 |
| **索引可重建** | ES 索引是派生数据；全量重建 + 别名切换即可恢复 |
| **避免双写** | 业务写 DB 后由 Canal 供给，search 不做业务双写 |
| **代价** | 跨库耦合、派生表边界模糊、重建依赖源库 |

生产上更干净的做法是独立搜索库/特征库 + CDC；本项目选择"复用 content 库 + 跨库 product"是**范围取舍**。

## 3. 对照表：生产 vs 本项目

| 能力 | 生产环境 | 本项目 | 差异 |
|---|---|---|---|
| 搜索服务自有库 | 独立搜索/特征库 | ❌ 复用 content | 简化 |
| 数据供给 | CDC/MQ | ✅ Canal 双通道 + order 事件 | 对齐 |
| 跨库读 | 尽量避免 | ⚠️ 显式跨库 product | 取舍 |
| 派生表写入 | 独立特征库 | ⚠️ 写 content 派生表 | 边界模糊 |
| 搜索写业务源表 | 不写 | ✅ 不写 t_note/t_spu | 对齐 |
| 存量回填 | 离线/分页 | ✅ order Feign 游标扫描 | 对齐 |
| 索引重建 | 别名切换 | ✅ C-011 | 对齐 |

## 4. 十个坑

1. **以为 search 有自己的库**：没有；默认数据源是 content 库。
2. **跨库不加前缀**：`my_xhs_product.` 必须显式，否则补偿/重建必失败（P1-5）。
3. **search 写业务源表**：只能写派生表（feature/behavior/hot snapshot），不能写 t_note/t_spu。
4. **直连订单分片库**：search 无直连；增量走事件、存量走 order Feign。
5. **点赞数读 counter key**：并行消费时序竞争会读到旧值/0；读 analytics Set（T-092）。
6. **行为重复落库**：用 `INSERT IGNORE`（eventId 幂等），否则重投变毒丸。
7. **把 ES 当写操作依据**：商家索引只做"发现"；写操作/终态以 DB + CAS 为准。
8. **跨服务事务**：search 不做分布式事务；最终一致 + 补偿/重建。
9. **Feign 失败当数据不存在**：product/order 不可达要重试/补偿，不能静默丢索引。
10. **派生表当源表**：`t_item_feature`/`t_user_behavior` 可重建/可清空，不是权威业务数据。

## 5. 值不值得深挖 / 一句话

- **值得**：搜索服务的定位（索引不是业务库）、CDC 供给、跨库/派生表边界、Feign 回填——微服务边界核心；
- **一句话带过**：具体 topic 名、表字段；
- **一句话**：**search 拥有索引，不拥有源数据；Canal/MQ 供给、Feign 回填、ES 承载；跨库和派生表是取舍，不是"一模块一库"。**
- 索引一致性见 **02**；查询见 **03**。

**面试口径**："search 没有自己的业务库：笔记/商品/订单的源在各自域，search 通过 Canal/MQ 建 ES 索引，存量用 Feign 回填；content 库复用连接、跨库读 product；只写特征/行为/热搜快照这些派生表，不写业务源表。"
