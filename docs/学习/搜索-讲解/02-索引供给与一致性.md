# 02 · 索引供给与一致性

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：索引一致性 = **CDC 供给 + 版本防乱序 + 墓碑防复活 + 失败集收敛 + 重建别名切换**；
> 不靠"业务双写 ES"，靠"binlog 因果链 + 幂等/补偿"。
>
> **本篇带走**：① 双通道与文档构建 ② 版本域 ③ 墓碑 ④ 失败集/增量 ⑤ 全量重建/别名 ⑥ DLQ。
> 前置：01。证据：`NoteIndexSyncConsumer`、`ProductIndexSyncConsumer`、`IncrementalIndexSyncJob`、
> `IndexRebuildJob`、`IndexAliasManager`、C-011。

---

## 0. 例子：改标题 / 删笔记 / 全量重建

```
① 改标题（t_note UPDATE）
   → Canal note_instance → NOTE_INDEX_TOPIC → NoteIndexSyncConsumer
   → ES index(noteId, version=ts, ExternalGte)

② 删笔记（逻辑删/物理删）
   → 不物理删 ES 文档，写墓碑 status=-1 + deletedAt + version
   → 查询侧过滤 status=-1；7 天后重建任务清理超龄墓碑

③ 全量重建（mapping 变更/索引损坏）
   → 建 note_index_v2 → 全量灌数 → 清理墓碑 → 原子切别名 → 重放窗口 → 删 v1
```

## 1. 生产环境怎么做（淘宝/行业常见）

| 环节 | 常见做法 |
|---|---|
| 供给 | CDC/binlog → MQ → ES；不做业务双写 |
| 乱序 | external version（时间戳/序列号）；旧版本拒绝 |
| 删除 | 墓碑（status/deletedAt）而非直接物理删；超龄清理 |
| 失败 | 失败集 + 补偿 Job + DLQ；区分"可重试/确定性失败" |
| 全量重建 | 新索引 + 别名原子切换 + 窗口重放；失败不切 |
| 观测 | 同步延迟/失败数/重建进度/别名切换 |

## 2. 本项目的实现（代码证据）

### 2.1 双通道与文档构建

```
Canal note_instance    → NOTE_INDEX_TOPIC    → NoteIndexSyncConsumer
Canal product_instance → PRODUCT_INDEX_TOPIC → ProductIndexSyncConsumer
Canal order_instance   → SUB_ORDER_INDEX_TOPIC → SellerSubOrderIndexSyncConsumer（08）
```

- **笔记**：文档由 Canal 行数据直接构建（不查库）；
- **商品**：Canal 行提供 name/category/status，**再调 `ProductFeignClient.getSpuDetail` 补 categoryName/SKU 列表**；
  `flat` 消息同样走 Feign 补全——不是"完全不查"；
- `t_sku` 变更 → 按 `spu_id` 重新索引父 SPU（批量事件去重，RV32）。

### 2.2 版本域：`ts` 毫秒 + `ExternalGte`

```java
// NoteIndexSyncConsumer / ProductIndexSyncConsumer
long version = canalMsg.getLongValue("ts", System.currentTimeMillis());
if (version == 0) {
    version = canalMsg.getLongValue("es", System.currentTimeMillis());
}
...
.versionType(VersionType.ExternalGte)
.version(version)
```

**为什么不用 Canal 的 `es` 小整数**（P1-4/T-088/R3）：

- 增量补偿用 DB `updated_at`（毫秒 ~1.7e12）写过文档后，后续 Canal `es`（小整数）会被
  `ExternalGte` **永久拒绝** → 索引冻结在补偿快照；
- 统一到 **`ts` 毫秒域**，与补偿同域；
- `ts` 缺失才回退 `es`；同毫秒重复变更被 `ExternalGte` 接受（幂等覆盖）。

### 2.3 墓碑：删除不物理删

```java
private void deleteNote(Long noteId, long version) throws Exception {
    Map<String, Object> doc = new HashMap<>();
    doc.put("noteId", noteId);
    doc.put("status", -1);              // 墓碑：搜索侧过滤
    doc.put("deletedAt", System.currentTimeMillis());
    esClient.index(IndexRequest.of(idx -> idx
            .index(noteIndexName)
            .id(String.valueOf(noteId))
            .versionType(VersionType.ExternalGte)
            .version(version)
            .withJson(new StringReader(JSON.toJSONString(doc)))));
}
```

- **逻辑删**（deleted=1）→ 墓碑；
- **物理删**（Canal DELETE）→ 也写墓碑（C-011 R4）——直接物理删会被迟到旧 UPDATE 复活；
- 查询侧：笔记只搜 `status=2`、商品只搜 `status=1`，墓碑 `status=-1` 不返回；
- 清理：重建时 `delete_by_query(status=-1 && deletedAt < now-7d)`（7 天保留期）。

### 2.4 失败集 + 增量补偿：什么该重试

```
消费失败 → SADD myxhs:es:sync:failed:note|product（TTL 1h）
IncrementalIndexSyncJob（60s）→ 按失败集 + 时间窗回补
```

**C-011 R1/R5：补偿必须收敛**：

```java
// bulk 逐项判定
if ("version_conflict_engine_exception".equals(item.error().type())) {
    // ES 已是更新版本 = 幂等已应用 → 视为成功，不回填
    continue;
}
failedIds.add(Long.parseLong(item.id()));   // 仅真失败回填
```

- `version_conflict` ≠ 失败（旧消息被拒是预期）；
- **Canal 消费端**：`PRODUCT_NOT_FOUND` 是确定性失败 → 跳过；其他文档构建失败会抛错 → MQ 重试 + 失败集（有界）；
- **增量补偿 Job**：文档构建失败 → 丢弃 + `doc_build_failed` 指标，不回填（重试必然再失败）；
- 原实现把两类都回填 → 失败集每分钟重投 + re-SADD 续期**永久循环**。

### 2.5 全量重建：别名原子切换

`IndexRebuildJob`（每天 4:00 / 管理端 `POST /api/search/index/rebuild`）：

```
resolve alias → 当前实体 v1
→ 建 v2（mapping 复用）
→ 全量灌数（id 游标 + Bulk + 断点续传）
→ 清理墓碑/无效文档
→ 原子切别名（updateAliases remove+add 一次调用）
→ 重放窗口（updated_at >= rebuildStart）
→ 删 v1（best-effort）
```

```java
aliasManager.switchAlias(productIndexName, productTarget.currentIndex(), productWriteIndex);
replayWindowProducts(productIndexName, rebuildStart);
aliasManager.deleteIndex(productTarget.currentIndex());
```

- **切换前失败**：别名仍指 v1，重跑续传同一 v2；
- **切换后重放失败**：别名可能已指向新实体，日志提示人工确认（"失败不切换"只覆盖切换前）；
- **legacy 部署**（索引名=配置名、无别名）→ 原地重建 + 告警；
- **源表未就绪**（`t_note` 不可用）→ skip "data sync not ready"，不误删。

### 2.6 DLQ：5 组重放

`SearchDlqReplayConsumer` 监听 5 个 `%DLQ%`：

```
note-index-sync / product-index-sync / counter-es-sync / recommend-behavior / seller-sub-order-index-sync
→ 重投源 topic（保留 tag）
→ attempt ≤ 3；超限告警（防循环）
→ 重投失败不吞异常（进本组 DLQ，可见）
```

## 4. 十二个坑

1. **业务双写 ES**：事务成功、ES 失败 → 不一致；用 CDC。
2. **用 `es` 小整数做版本**：补偿毫秒版本写入后，Canal 小整数被永久拒绝（P1-4/T-088）。
3. **删除直接物理删**：迟到旧 UPDATE 会复活；用墓碑 + version。
4. **墓碑不清理**：7 天后重建清理；否则墓碑永久残留。
5. **version_conflict 当失败**：失败集永久循环（C-011 R1）。
6. **确定性失败回填**：增量 Job 里文档构建失败要丢弃 + 告警；Canal 消费端 `PRODUCT_NOT_FOUND` 跳过，其他失败仍有界重试。
7. **t_sku 批量只取 data[0]**：其余父 SPU 漏更新；按 spu_id 去重。
8. **t_sku DELETE 行镜像缺 spu_id**：MINIMAL 下定位不到父 SPU（需调行镜像/反查）。
9. **全量重建直接写线上索引**：半新半旧；用 v2 + 别名。
10. **切换后不重放窗口**：重建期间的更新丢失。
11. **源表未就绪仍重建**：可能清空/覆盖线上；先检查 `t_note`。
12. **DLQ 无限重放**：attempt 上限 + 告警，防"DLQ→重放→再 DLQ"。

## 5. 值不值得深挖 / 一句话

- **值得**：版本域、墓碑、失败集收敛、别名切换 + 窗口重放——索引一致性面试核心；
- **一句话带过**：Bulk 参数、Canal 配置、重试次数；
- **一句话**：**索引 = CDC 供给 + ts/ExternalGte 防乱序 + 墓碑防复活 + 失败集收敛 + 别名切换重建。**
- 查询路径见 **03**；商品侧索引见 04（商品篇）。

**面试口径**："索引走 Canal→MQ→ES；版本用 ts 毫秒 + ExternalGte，防旧消息覆盖；删除写墓碑 status=-1 + deletedAt，7 天清理；失败集只回填真失败（conflict 豁免、确定性失败丢弃）；全量重建建 v2、原子切别名、切换后重放窗口。"
