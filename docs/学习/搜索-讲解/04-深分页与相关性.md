# 04 · 深分页与相关性

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：深分页不能用 `from/size`（窗口上限 + 深页代价），要用 **Search After + 稳定排序 + 游标类型**；
> 相关性是 `_score` + tie-breaker，不是"关键词命中就算"。
>
> **本篇带走**：① from/size 的问题 ② Search After 序列化/解析 ③ 排序稳定性 ④ total 上限/游标安全/限流。
> 前置：03。证据：`AbstractSearchService`、`NoteSearchService`、`ProductSearchService`、C-011。

---

## 0. 例子：翻到第 100 页

```
GET /search/note?keyword=露营&size=20&searchAfter=[1.23,10086]
  → ES: sort(_score desc, noteId desc) + search_after([1.23,10086]) + size=21
  → 返回 20 条 + 新的 searchAfter（最后一条的 sort 值）
  → hasMore = 是否多取了第 21 条
```

如果用 `from=2000&size=20`：ES 默认 `max_result_window=10000`，深页要扫描/排序前 2020 条，越翻越慢；
本项目统一用 Search After。

## 1. 生产环境怎么做（淘宝/行业常见）

| 问题 | 常见做法 |
|---|---|
| 深分页 | Search After / PIT（Point-in-Time）+ 稳定排序 |
| 游标 | 不透明 token（服务端签名/编码），不暴露内部结构 |
| 排序 | 相关度 + 业务字段 + 唯一 tie-breaker |
| total | 默认上限（10000）或近似计数；不用于深分页 |
| 保护 | 限流、size 上限、游标校验 |

## 2. 本项目的实现（代码证据）

### 2.1 为什么不用 from/size

- ES `max_result_window` 默认 10000：`from+size > 10000` 直接报错；
- 深页要全局排序前 N 条，代价随页深增长；
- 本项目 `SearchRequest` 只设 `size(size+1)`，翻页靠 `searchAfter`，不传 `from`。

### 2.2 游标：带类型标签的序列化/解析

```java
// 序列化：每个排序值带类型标签（d/l/s/b/n），JSON 不丢类型
protected String serializeSearchAfter(List<FieldValue> sortValues) {
    List<Object> values = sortValues.stream()
            .map(this::encodeFieldValue)
            .collect(Collectors.toList());
    return JSON.toJSONString(values);   // [{"t":"d","v":1.0},{"t":"l","v":10086}]
}

private Object encodeFieldValue(FieldValue fv) {
    if (fv.isDouble())  return Map.of("t", "d", "v", fv.doubleValue());
    if (fv.isLong())    return Map.of("t", "l", "v", fv.longValue());
    if (fv.isBoolean()) return Map.of("t", "b", "v", fv.booleanValue());
    if (fv.isString())  return Map.of("t", "s", "v", fv.stringValue());
    return Map.of("t", "n");
}

// 解析：优先类型标签；旧格式裸数字走启发式（兼容历史游标）
private FieldValue decodeFieldValue(Object v) {
    if (v instanceof JSONObject obj && obj.containsKey("t")) {
        return switch (obj.getString("t")) {
            case "d" -> FieldValue.of(obj.getDoubleValue("v"));
            case "l" -> FieldValue.of(obj.getLongValue("v"));
            case "b" -> FieldValue.of(obj.getBooleanValue("v"));
            case "n" -> FieldValue.NULL;
            default  -> FieldValue.of(obj.getString("v"));
        };
    }
    // 旧格式：1.5→double、10086→long；整数值 double 仍有歧义
    ...
}
```

**为什么必须带类型标签**：JSON 不保留 double/long 类型，`1.0` 和 `1` 在裸数字里无法区分；
如果 `_score`/`price`（double）的游标被解析成 long，Search After 会类型不匹配，第二页异常/跳页。

> ✅ **已修复（C-019）**：整数值 double（1.0/100.0）现在按 `d` 编码；旧格式裸数字仍走启发式（历史游标兼容）。
> 单测 `SearchAfterCodecTest` 覆盖 double/long/string/boolean/null + 旧格式。

### 2.3 排序稳定性：tie-breaker 必须有

| 搜索 | 排序 |
|---|---|
| 笔记 relevance | `_score desc, noteId desc` |
| 笔记 time | `createdAt desc, noteId desc` |
| 笔记 hot | `likeCount desc, noteId desc` |
| 商品 relevance | `_score desc, spuId desc` |
| 商品 price | `price asc/desc, spuId asc/desc` |

- 没有 tie-breaker：排序值相同的文档顺序不稳定，Search After 会跳/重；
- `_score` 只在**同一查询**内可比；不同关键词的分数不可比；
- `sales` 无数据源 → 显式降级 relevance（03）。

### 2.4 total 上限：默认 10000

```java
long total = response.hits().total() != null ? response.hits().total().value() : 0;
```

- ES `track_total_hits` 默认 10000（代码未改）；
- `total` 只能当"约数"，不能用于深分页/全量统计；
- `hasMore` 用 `size+1` 判断，不依赖 total。

### 2.5 限流与游标安全

- 搜索端点 30 次/秒/用户（C-011）；
- `searchAfter` 是客户端传入的 JSON 数组：**未签名**，可被篡改；
- 篡改最多改变翻页位置/造成重复/跳过，不会越权（过滤条件仍在服务端）；
- 生产应使用不透明 token（签名/加密），避免暴露内部排序值。

### 2.6 相关性：BM25 + multiMatch boost

- 笔记：`multiMatch(title^3, content)`，`ik_smart`；标题权重 3 倍；
- 商品：`match(name)`；
- `_score` 由 ES BM25 计算；filter（status/分类/价格）不影响评分；
- 没有自定义 rerank/精排/学习排序（缺口）。

## 3. 对照表：生产 vs 本项目

| 能力 | 生产环境 | 本项目 | 差异 |
|---|---|---|---|
| 深分页 | Search After/PIT | ✅ Search After | 对齐（无 PIT） |
| 游标 | 不透明 token | ✅ 类型标签（旧格式兼容）；明文未签名 | 部分 |
| 稳定排序 | tie-breaker | ✅ noteId/spuId | 对齐 |
| total | 上限/近似 | ⚠️ 默认 10000 | 已知 |
| 相关性 | BM25 + boost/rerank | ✅ BM25 + title boost | 无 rerank |
| 限流 | 网关/接口 | ✅ 30/s | 对齐 |

## 4. 十个坑

1. **用 from/size 深翻**：10000 上限 + 深页代价；用 Search After。
2. **直接序列化 FieldValue**：会变成对象 JSON，解析不回来；必须提取实际值。
3. **旧格式游标类型歧义**：裸数字 `1.0/100.0` 仍被判 long；新格式带 `t` 标签已修复，历史游标仍可能翻页异常。
4. **没有 tie-breaker**：同分文档顺序不稳定，跳/重。
5. **total 当精确值**：默认 10000 上限；用 hasMore。
6. **游标明文**：可篡改；生产用签名/不透明 token。
7. **sort 字段缺失/null**：Search After 可能报错/跳；索引 mapping 要保证字段存在。
8. **size 不设上限**：大 size 打爆 ES；本项目 max 50。
9. **`_score` 跨查询比较**：不同关键词的分数不可比；只用于同查询排序。
10. **sales 排序无数据源**：必须降级，不能按缺失字段排序（03）。

## 5. 值不值得深挖 / 一句话

- **值得**：Search After 类型、tie-breaker、total 上限、游标安全——深分页面试核心；
- **一句话带过**：BM25 公式、PIT；
- **一句话**：**深分页 = Search After + 稳定排序 + 游标类型；total 只是约数，相关性是 _score + tie-breaker。**
- 读路径见 **03**；索引 mapping 见 **02**。

**面试口径**："深分页不用 from/size（10000 上限 + 深页代价），用 Search After；排序都带 noteId/spuId 次键保证稳定；游标是带类型标签的排序值数组（d/l/s/b/n，旧格式兼容）；total 默认 10000，只用 hasMore。"
