# 07 · 推荐

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：推荐 = **5 路召回 + 粗排（来源权重）+ 精排（四维加权）+ 重排（已看过/品类打散）**；
> 离线算特征/热门池/ItemCF，行为走 MQ 闭环。
>
> **本篇带走**：① 四层管线 ② 5 路召回 ③ 粗排/精排权重 ④ 重排/冷启动 ⑤ 离线与行为闭环。
> 前置：03。证据：`RecommendService`、`recommend/*RecallStrategy`、`RecommendComputeJob`、`BehaviorReportConsumer`。

---

## 0. 例子：打开推荐流

```
用户 A（有行为）打开推荐 Feed
  → 5 路召回并行（每路 100，2s 超时）→ 合并去重
  → 粗排：召回分 × 来源权重 → Top 100
  → 精排：来源 0.25 + 偏好 0.25 + 质量 0.30 + 时效 0.20 → Top 50
  → 重排：已看过过滤 + 同品类最多连续 2 个 → 20 条
  → 返回 noteId/score/source/reason

用户 B（无行为）→ 冷启动：热门 60 + 地理 30
```

## 1. 生产环境怎么做（淘宝/行业常见）

| 层 | 常见做法 |
|---|---|
| 召回 | 多路（CF/内容/热门/关注/地理/向量），并行 + 超时降级 |
| 粗排 | 轻量模型/规则，快速截断 |
| 精排 | 多特征加权/ML 模型 |
| 重排 | 去重/打散/多样性/业务规则 |
| 冷启动 | 热门/地理/人群/随机探索 |
| 闭环 | 曝光/点击/点赞/停留 → 特征/模型更新 |

## 2. 本项目的实现（代码证据）

### 2.1 四层管线

```java
public List<RecommendFeedVO> getRecommendFeed(Long userId) {
    boolean cold = isColdStartUser(userId);                  // 无行为 → 冷启动
    List<RecallItem> candidates = cold ? coldStartRecall(userId) : multiRecall(userId);
    List<RecallItem> rough = roughRank(candidates);          // 粗排 Top100
    List<RecallItem> fine = fineRank(rough, userId);          // 精排 Top50
    List<RecallItem> reRanked = reRank(fine, userId);         // 重排：过滤+打散 → 20
    return toVO(reRanked);
}
```

### 2.2 召回：5 路并行

| 策略 | 数据源 |
|---|---|
| Content | Redis 用户标签 + `t_item_feature.tags` |
| Following | `myxhs:recommend:following:latest:{userId}` ZSet |
| Geo | geohash 前缀 + `t_item_feature`；无 geohash → 降级热门 |
| Hot | `myxhs:recommend:hot:global` ZSet |
| ItemCF | `myxhs:recommend:itemcf:{noteId}` ZSet（离线相似矩阵） |

```java
List<CompletableFuture<List<RecallItem>>> futures = recallStrategies.stream()
    .map(s -> CompletableFuture.supplyAsync(
            () -> s.recall(userId, recallSizePerStrategy), recallInnerExecutor)
        .exceptionally(ex -> Collections.emptyList()))
    .toList();

CompletableFuture.allOf(...).get(recallTimeoutMs, TimeUnit.MILLISECONDS); // 2s 超时
// 按 noteId 合并去重，保留最高 recallScore
```

- 外层 `recallExecutor` 跑整请求、内层 `recallInnerExecutor` 跑 5 路召回（避免同池嵌套饿死）；
- 超时/异常 → 该路空列表，不拖垮整体；
- 每路默认 100 条。

### 2.3 粗排：召回分 × 来源权重

```java
double sourceWeight = SOURCE_WEIGHT.getOrDefault(item.getSource(), 0.5);
item.setRankScore(item.getRecallScore() * sourceWeight);
// Top 100
```

来源权重：`ITEM_CF 1.0 > FOLLOWING 0.9 > CONTENT 0.8 > HOT 0.6 > GEO 0.5`。

### 2.4 精排：四维加权（注意：权重在这一层，不在粗排）

```java
item.setRankScore(
        0.25 * sourceWeight +
        0.25 * userPreference +
        0.30 * quality +
        0.20 * timeDecay
);
// Top 50
```

- **用户偏好**：Redis Hash `recommend:user:tags:{userId}` 的品类权重（12h TTL）；
- **质量分**：`t_item_feature.quality_score`（缺失默认 0.3）；
- **时效**：`e^(-hours/24)`，24h≈0.37、48h≈0.14、7d≈0.001；
- 权重硬编码，可配化是演进项。

> 模块文档 §8 把 0.25/0.25/0.30/0.20 写在"粗排"里，**代码实际在 `fineRank`（精排）**；
> 粗排只做"召回分 × 来源权重"。这是阅读时最容易混的一处。

### 2.5 重排：已看过 + 品类打散

```java
// 1) 已看过过滤：Redis Set（不是 HyperLogLog）
if (isAlreadySeen(seenKey, noteId)) continue;

// 2) 品类打散：同品类连续最多 2 个
if (category.equals(lastCategory) && ++consecutive > 2) continue;

// 3) 记录曝光：SADD + 7 天 TTL；Set 超 5000 → TTL 收缩到 1 天
```

- 曝光用 **Set**（精确 `SISMEMBER`），不是注释里说的 HyperLogLog；
- 最终 `feedSize=20`；**Feed 固定 20 条、无分页/cursor**——刷新即重新召回，靠已看过过滤换内容。

### 2.6 冷启动：热门 60 + 地理 30

```java
boolean cold = jdbcTemplate.queryForObject(
    "SELECT EXISTS(SELECT 1 FROM t_user_behavior WHERE user_id = ? LIMIT 1)", Boolean.class, userId);
// 冷启动：HOT 60 + GEO 30，去重
```

> 代码注释写"热门 60% + 地理 30% + 随机 10%"，**实际没有随机 10%**（只召回 Hot/Geo）；是注释漂移。

### 2.7 离线与行为闭环

| 任务 | 职责 |
|---|---|
| `recommendItemCFJob` | 热门物品两两共现 → 相似矩阵 ZSet |
| `recommendFeatureJob` | 写 `t_item_feature`（质量分/标签/分类） |
| `recommendHotPoolJob` | 全局热门池 ZSet |

接口与防护：

- `/recommend/feed` 10 次/秒/用户；`/recommend/similar` 20 次/秒/用户；
- `/recommend/compute` 手动触发离线计算（管理端）；
- `/recommend/behavior` 上报行为。

行为上报：

```
/recommend/behavior → RECOMMEND_BEHAVIOR_TOPIC → t_user_behavior（INSERT IGNORE）
                   ↘ 正向行为（点赞/收藏/评论/分享/停留>10s）→ Redis 用户标签权重 +1（12h）
MQ 发送失败 → 降级同步 INSERT IGNORE（同 eventId）
相似推荐：/recommend/similar/{noteId} → ItemCF ZSet
```

## 4. 十三个坑

1. **把四维权重当粗排**：代码在 `fineRank`（精排）；粗排是"召回分 × 来源权重"。
2. **冷启动以为有随机 10%**：代码只有 Hot+Geo；注释漂移。
3. **已看过用 HyperLogLog**：`PFADD` 有副作用；本项目用 Set 精确判断。
4. **品类打散写成 ≥2 跳过**：会把第 2 个同品类也误伤；本项目允许连续 2 个。
5. **召回同池嵌套**：外层请求占满线程，内层召回排队 → 2s 超时；本项目内外池分离。
6. **超时不取消**：已完成结果仍可用；本项目超时后取消未完成 future。
7. **来源权重和精排权重混用**：两层各自一套，别叠加错。
8. **质量分默认值**：缺失默认 0.3；不要当 0 把新内容全压掉。
9. **用户标签 TTL**：12h；过期后偏好回落到 0.5。
10. **行为 MQ 失败**：必须降级同步写 + 同 eventId 幂等（INSERT IGNORE）。
11. **相似推荐为空**：ItemCF 矩阵未算/冷门笔记；返回空，不要报错。
12. **权重硬编码**：调权重要发版；可配化是演进项。
13. **Feed 无分页**：固定 20 条，刷新重新召回；没有 cursor/翻页，靠已看过过滤换内容。

## 5. 值不值得深挖 / 一句话

- **值得**：四层管线、5 路召回并行/超时、粗排 vs 精排权重、重排打散、冷启动——推荐面试核心；
- **一句话带过**：ItemCF 公式、线程池参数、权重数值；
- **一句话**：**推荐 = 多路召回 + 粗排（来源权重）+ 精排（四维）+ 重排（过滤/打散）；离线算特征，行为闭环。**
- 行为上报细节见 **08**；工程债见 **09**。

**面试口径**："推荐是四层：5 路召回并行（每路 100、2s 超时、按 noteId 合并）→ 粗排召回分×来源权重 Top100 → 精排四维加权（来源 0.25/偏好 0.25/质量 0.30/时效 0.20）Top50 → 重排已看过过滤 + 同品类连续最多 2 个 → 20 条；冷启动 Hot+Geo；离线三个 Job 算特征/热门/ItemCF。"
