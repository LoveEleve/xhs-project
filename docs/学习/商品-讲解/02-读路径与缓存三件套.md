# 02 · 读路径与缓存三件套

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
> QPS 数字是**设计假设**，不是本项目压测结论。
>
> **一句话**：详情读 = **布隆前置 → Redis 逻辑过期 → MySQL**；
> 三件套 = **逻辑过期、空值缓存、布隆过滤器**；再加防惊群、预热、读写分离。
>
> **本篇带走**：① 三级读路径 ② 逻辑过期 vs 物理过期 ③ 穿透/击穿/雪崩 ④ 防惊群/预热/读写分离。
> 前置：01。证据：`SpuService.getSpuDetail`、`RedisCacheData`、`ProductCacheWarmer`、C-005。

---

## 0. 例子：热点 SPU、不存在的 ID、冷 key

```
① 热点 SPU（10 万 QPS，假设）
   → Redis 命中且未逻辑过期 → 直接返回
   → 逻辑过期 → 返回旧值 + 异步刷新（只有一个线程刷）

② 不存在的 SPU ID（攻击/脏数据）
   → 布隆过滤器判定"一定不存在" → 直接返回 null（连 Redis 都不查）
   → 布隆误判"可能存在" → Redis 空值缓存 → 返回 null

③ 冷 key（刚上架/缓存被删）
   → 多个请求同时 miss → 分布式锁：一个查 DB 回填，其他短暂等待后重查
```

三个场景对应三种问题：**击穿（热点过期）、穿透（不存在）、惊群（冷 key 并发）**。

## 1. 生产环境怎么做（淘宝/行业常见）

| 层 | 常见做法 |
|---|---|
| L1 本地缓存 | Caffeine/本地 Map（热点 key，纳秒级；一致性靠失效广播） |
| L2 Redis | 逻辑过期/物理过期；空值缓存；布隆前置 |
| L3 DB | 只读库/读写分离；回源限流 |
| 防击穿 | 逻辑过期 + 异步刷新；或互斥重建 |
| 防穿透 | 布隆 + 空值缓存 |
| 防雪崩 | TTL 打散、多级缓存、降级限流 |
| 预热 | 启动/大促前预热热点与基础数据 |
| 观测 | 命中率、回源 QPS、刷新/失效指标 |

## 2. 本项目的实现（代码证据）

### 2.1 三级读路径

```java
public SpuDetailVO getSpuDetail(Long spuId) {
    // 1) 布隆前置：判定"一定不存在"直接返回；不可用则降级放行
    if (bloomFilterReady.get()) {
        try {
            if (!spuBloomFilter.contains(spuId)) {
                countCache("myxhs_product_bloom_block_total");
                return null;
            }
        } catch (Exception e) {
            // Redis/布隆不可用 → 降级放行
        }
    }

    // 2) Redis：统一 RedisCacheData 包装（含空值）
    String redisKey = RedisKeyConstants.PRODUCT_SPU + spuId;
    RedisCacheData<SpuDetailVO> cacheData = redisOperator.get(redisKey);
    if (cacheData != null) {
        if (!cacheData.isExpired()) {
            return cacheData.getData();       // 命中（含空值）
        }
        if (cacheData.getData() != null) {
            asyncRefreshCache(spuId, redisKey); // 逻辑过期：返回旧值 + 异步刷新
            return cacheData.getData();
        }
        // 空值过期 → 继续查 DB（数据可能已新增）
    }

    // 3) MySQL：冷 key 用分布式锁防惊群
    ...
}
```

- 布隆：`myxhs:product:bloom:spu`，容量 100 万 / 误判率 1%；
- Redis key：`myxhs:product:spu:{id}`，Value 是 `RedisCacheData`（数据 + 逻辑过期时间）；
- DB 回源只返回**上架** SPU + 上架 SKU（下架/删除 → null → 空值缓存）。

### 2.2 逻辑过期：用"秒级延迟"换"不打挂 DB"

```java
public class RedisCacheData<T> {
    private T data;
    private LocalDateTime logicExpire;

    public boolean isExpired() {
        return logicExpire != null && LocalDateTime.now().isAfter(logicExpire);
    }
}
```

| 类型 | 逻辑过期 | 物理 TTL | 为什么 |
|---|---|---|---|
| 正常数据 | **30 分钟** | **120 分钟** | 逻辑过期后返回旧值 + 异步刷新；物理 TTL 兜底清理 |
| 空值 | **2 分钟** | **5 分钟** | 新数据可能很快出现；空值不能缓存太久 |

**为什么不用物理过期**：物理过期到点删 key，高并发下大量请求同时穿透到 DB（击穿）；
逻辑过期让 key 一直在，过期后先返回旧值、后台单线程刷新——商品详情允许秒级延迟。

**刷新是异步且单线程**：`asyncRefreshCache` 用 Redisson 锁 + `CompletableFuture`，
拿不到锁直接跳过（别的线程在刷），不阻塞用户请求。

### 2.3 空值缓存：防穿透的第二道

DB 查不到时，缓存 `RedisCacheData(null, 2min)`，物理 TTL 5 分钟：

- 攻击者用大量不存在的 ID 打接口 → 布隆先挡；漏过的 → 空值缓存挡；
- 逻辑过期 2 分钟（新数据可能很快出现），物理 5 分钟（防 Redis 内存被垃圾 key 打爆）。

### 2.4 防惊群：冷 key 并发 miss

```java
String loadLockKey = CACHE_REFRESH_LOCK + "load:" + spuId;
RLock loadLock = redissonClient.getLock(loadLockKey);
if (loadLock.tryLock(1, 10, TimeUnit.SECONDS)) {
    // 双重检查：持锁期间可能已被其他线程回填
    // 查 DB → 回填缓存（正常数据 30min/120min；空值 2min/5min）
} else {
    // 有界等待：3 轮 × 100ms 重查缓存；仍没有才回源（避免无限等待）
}
```

**关键**：不是"拿不到锁就睡死"，而是**有界等待 + 兜底回源**；否则一个慢查询会把请求线程拖住。

### 2.5 预热、布隆重建、分类树

- **分类树**：`CategoryService` 缓存 2 小时；`POST /api/product/category/refresh` 主动刷新；
  `ProductCacheWarmer` 启动预热（`myxhs.cache-warmup.targets=product-category-tree`）；
- **布隆初始化**：启动时 `tryInit(1_000_000, 0.01)`；首次/为空时**异步分批**（5000/批）加载历史 SPU，
  分布式锁保证多实例只加载一次；加载期间 `bloomFilterReady=false` 降级放行；
- **布隆重建**：`POST /internal/bloom/rebuild` 异步触发（管理端用），避免阻塞请求。

### 2.6 读写分离与 N1/N2

- `spring.datasource.readwrite.enabled=true`：写主库、读从库；
- **主从延迟**风险：缓存回填可能读到旧值——写路径用 Canal binlog 失效兜底（03）；
- **N1/N2（C-005）**：`getSkuDetail`/`listSkusBySpuId` 复用已查 SPU，避免同一请求二次查 SPU；
  详情回源仍是"SPU + SKU 列表 + 类目名"三次查询（可接受）。

### 2.7 缓存指标

`myxhs_product_cache_hit_total` / `miss_total` / `null_hit_total` /
`bloom_block_total` / `refresh_total` / `evict_total`（source=write/canal）——
命中率、回源量、空值命中、布隆拦截、刷新/失效都能看。

## 4. 十个坑

1. **逻辑/物理混用**：同一 key 不能有时存裸对象、有时存 `RedisCacheData`；空值也要包装。
2. **空值 TTL 太长**：新数据出现会被空值挡住；本项目 2min/5min。
3. **布隆只增不减**：下架/删除的 ID 仍在布隆里，会多一次缓存查询（命中空值），不会返回错数据。
4. **布隆误判**：1% 误判会放行到 Redis/DB；不是"绝对不存在"。
5. **布隆不可用**：必须降级放行，不能把读请求打挂。
6. **Redis 不可用**：降级直查 DB；要有回源限流，否则 DB 被打爆。
7. **冷 key 惊群**：必须互斥回填 + 有界等待；别让所有线程都回源。
8. **逻辑过期数据旧**：商品详情允许秒级延迟；强一致场景不能用这套。
9. **主从延迟**：回填可能读旧值；靠 Canal 失效 + TTL 兜底。
10. **没有本地缓存**：单 key 热点全压 Redis；超大热点要 L1/热点探测（缺口）。

## 5. 值不值得深挖 / 一句话

- **值得**：逻辑过期 vs 物理过期、空值缓存、布隆、防惊群、主从延迟——缓存面试的核心；
- **一句话带过**：布隆容量/误判率、TTL 数值；
- **一句话**：**详情读 = 布隆挡不存在 + Redis 逻辑过期挡击穿 + 空值缓存挡穿透 + 分布式锁挡惊群；允许秒级延迟，换 DB 不被热点打挂。**
- 写路径/缓存失效见 **03**；索引供给见 **04**。

**面试口径**："商品详情是布隆 → Redis 逻辑过期 → MySQL；逻辑过期 30min、物理 TTL 2h，过期返回旧值异步刷新；空值缓存 2min/5min 防穿透；冷 key 用分布式锁 + 有界等待防惊群；读写分离，主从延迟靠 Canal 失效兜底。"
