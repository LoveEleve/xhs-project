# 01 · 商品模型：SPU / SKU / 类目 / 价格 / 状态

> **口径**：先讲**生产环境/淘宝公开形态**，再对照本项目；代码不代表应然标准。
>
> **一句话**：**SPU = 卖什么**（标准产品单元），**SKU = 具体哪一件**（可售最小单元）；
> 类目是树、属性是模板、价格有多口径、状态是 0/1——商品只存**静态描述**，库存不在这里。
>
> **本篇带走**：① SPU/SKU/类目/属性/价格/状态 ② 应然 vs 实然（哪些是简化）③ 本项目的校验与状态机。
> 前置：00。证据：`Spu`/`Sku`/`Category`、`ProductStatus`、`SkuService`、`SpuService`、C-005。

---

## 0. 例子：一件 T 恤（生产视角）

```
SPU：纯棉圆领 T 恤
  类目：服饰 > 男装 > T恤
  品牌：某品牌
  描述/图片：详情页内容（所有 SKU 共享）

SKU：
  白色 M  ¥79（原价 ¥99）
  白色 L  ¥79
  黑色 M  ¥79
  —— 价格、库存、规格在 SKU 上；库存真实值在 inventory
```

用户看到的是 **SPU 详情**；下单买的是 **SKU**；订单会**快照** SKU 的名称/价格——商品后续改价不影响已下单。

## 1. 生产环境的商品模型（淘宝/行业常见）

| 对象 | 生产环境常见做法 |
|---|---|
| **类目** | 多级类目树 + **类目属性模板**（属性因类目而异） |
| **品牌** | 品牌库（授权/审核），商品挂靠 |
| **SPU** | 基础/营销信息、店铺归属、详情富文本/视频 |
| **SKU** | **销售属性组合矩阵**（颜色×尺码自动生成）、编码/条码、重量体积 |
| **属性** | 关键属性/销售属性/参数属性 + 属性值库（结构化根基） |
| **价格** | 划线价/售价/活动价/会员价/阶梯价（多价格并存） |
| **状态机** | 草稿→待审核→上/下架→删除 + **定时上下架** |
| **商家** | 店铺/商家后台/权限 |
| **审核/留痕** | 图文合规、资质审核、编辑历史 |

> 淘宝具体实现不公开；上面是电商商品域的常见形态。

## 2. 本项目的实现（代码证据）

### 2.1 数据模型

```java
public class Spu extends BaseEntity {
    private String name;
    private Long categoryId;
    private Long brandId;
    private String description;
    private String images;      // JSON 数组
    private Integer status;     // 0 下架 / 1 上架
}

public class Sku extends BaseEntity {
    private Long spuId;
    private Long sellerId;      // 0=平台自营；下单按商家拆单
    private String name;
    private BigDecimal price;
    private BigDecimal originalPrice;
    private Integer stock;      // 冗余占位！真实库存在 inventory
    private String specs;       // 自由 JSON（颜色/尺码等）
    private Integer status;     // 0 下架 / 1 上架
}

public class Category extends BaseEntity {
    private String name;
    private Long parentId;      // 0=一级
    private Integer level;      // 1~3
    private Integer sort;
    private String icon;
    private Integer status;     // 0 禁用 / 1 启用
}
```

另外 `t_product_behavior` 记录商品浏览/行为埋点（append-only，供分析/搜索用）。

### 2.2 SPU 与 SKU 的职责

| 维度 | SPU | SKU |
|---|---|---|
| 是什么 | 标准产品单元（"卖什么"） | 可售最小单元（"哪一件"） |
| 共享信息 | 名称/类目/品牌/描述/图片 | —— |
| 独立信息 | —— | 价格/原价/规格/卖家/状态 |
| 库存 | 无 | `stock` 只是**占位**，真实库存在 inventory |
| 下单 | 详情页 | 订单快照 SKU 名称/价格 |

**为什么库存不在商品**：商品是"静态描述"，库存是"高频变化 + 强一致"的另一域；
`SkuVO` 已经把 `stock` 剔除，真实库存由 inventory 服务返回。

**建 SKU 后的库存初始化**（product→inventory 边界）：

```java
// SkuService.createSku：事务提交后初始化库存，失败进补偿队列（InventoryInitRepairJob）
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        spuService.evictSpuCache(spuId);
        initInventory(sku.getId(), sku.getStock());
    }
});
```

### 2.3 SKU 创建校验（C-005）

```java
// 1) SPU 必须存在（不要求已上架：正常流程是 建 SPU(下架) → 加 SKU → 上架）
Spu spu = spuMapper.selectById(request.getSpuId());
if (spu == null) throw new BizException(PRODUCT_NOT_FOUND);

// 2) 价格非负（0 元单合法——支付有零元单路径）
if (price < 0) throw ... "价格不能为负数";

// 3) 划线价不得低于售价
if (originalPrice < price) throw ... "划线价不能低于售价";

// 4) specs 必须是合法 JSON（脏 JSON 会沿购物车/订单快照放大）
objectMapper.readTree(specs); // 失败 → "规格属性必须是合法 JSON"
```

### 2.4 状态机：SPU 默认下架，SKU 默认上架

```java
public enum ProductStatus {
    OFF_SHELF(0, "下架"),
    ON_SHELF(1, "上架");
}
```

- **建 SPU 默认下架**（C-005）：原默认上架会产生"空商品在架"（无 SKU 可被搜到/详情为空）；
- **建 SKU 默认上架**：SKU 是在（通常下架的）SPU 下创建的；SPU 上架时要求至少一个上架 SKU；
- **上架校验**：

```java
if (ProductStatus.ON_SHELF.getCode() == status) {
    Long enabledSkuCount = skuMapper.selectCount(... eq(Sku::getStatus, ON_SHELF));
    if (enabledSkuCount == null || enabledSkuCount == 0) {
        throw new BizException(PARAM_INVALID, "商品至少需要一个上架中的 SKU 才能上架");
    }
}
```

- 没有"草稿/待审核/删除/定时上下架"；`deleted` 是逻辑删除字段；状态变更即时生效（缓存 afterCommit 失效）。

### 2.5 类目 / 品牌 / 价格 / 属性：本项目简化在哪

| 能力 | 本项目 | 差距/影响 |
|---|---|---|
| 类目 | 三级树；**只读**（改 DB 后靠缓存 TTL/refresh 接口） | 无类目管理后台 |
| 品牌 | 只有 `brandId` 字段 | **无品牌表/授权/审核** |
| 属性 | `specs` 自由 JSON | **无属性模板/规格矩阵**，不参与任何逻辑 |
| 价格 | `price` + `originalPrice` | 无活动价/会员价/阶梯价 |
| 商家 | SKU 有 `sellerId`（默认 0=平台自营）；SPU 无商家字段 | 无店铺/商家后台；下单按 sellerId 拆单 |
| 审核/留痕 | 无 | 无图文/资质审核、无编辑历史 |

> 这些是**范围取舍**：学习项目只保留"能支撑交易链路"的最小模型；
> 面试可以主动说"缺属性体系/多价格/审核，补的话怎么补"。

## 4. 十个坑

1. **SPU/SKU 混淆**：描述/图片在 SPU，价格/规格/库存在 SKU；别把价格放 SPU。
2. **拿 `t_sku.stock` 当库存**：它只是占位；真实库存在 inventory，扣减/回补都走库存域。
3. **建 SPU 默认上架**：会产生"空商品在架"；C-005 已改为默认下架。
4. **上架不校验 SKU**：没有上架 SKU 的商品可被搜到但无法下单。
5. **价格不校验**：负数、划线价低于售价都是数据错误；服务层要兜底。
6. **specs 脏 JSON**：会沿购物车/订单快照放大；入库前必须校验。
7. **类目当管理后台**：本项目类目只读；改类目要走 DB/refresh，不是 API。
8. **品牌当表**：只有 `brandId`，没有品牌表；别假设能查品牌详情。
9. **商品改价影响历史订单**：订单用快照；商品价格只影响新订单。
10. **多商家假设**：只有 SKU `sellerId`，没有店铺域；拆单按 sellerId，但商家后台/结算不在商品。

## 5. 值不值得深挖 / 一句话

- **值得**：SPU/SKU 职责、库存占位、默认状态机、价格/JSON 校验、订单快照——交易域的基础；
- **一句话带过**：类目字段、品牌字段、埋点字段；
- **一句话**：**SPU 卖什么、SKU 哪一件；价格/规格/库存在 SKU，库存真实值在 inventory；商品只存静态描述，订单用快照。**
- 读路径见 **02**；写路径/缓存一致性见 **03**。

**面试口径**："商品模型是 SPU + SKU：SPU 存共享描述/类目/品牌，SKU 存价格/规格/卖家/状态；库存不在商品，`t_sku.stock` 只是占位；建 SPU 默认下架、上架要求至少一个上架 SKU；订单用 SKU 快照。"
