# 03 · 写路径与缓存一致性

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：写路径 = **事务提交后立即删（快路径）+ 删失败 MQ 兜底 + Canal binlog 最终失效**；
> 不用"延迟双删"——它是**猜时间**，binlog 是**已提交数据的因果链**。
>
> **本篇带走**：① 为什么 afterCommit 删 ② 三层一致性 ③ 为什么弃用延迟双删
> ④ 外部直改/主从延迟/删失败 ⑤ 建 SKU 后的库存初始化边界。
> 前置：02。证据：`SpuService.updateSpu/evictSpuCache`、`CacheEvictConsumer`、`ProductCacheCanalEvictConsumer`、C-005。

---

## 0. 例子：改 SPU 名称/上下架后，详情多久可见

```
管理端 PUT /spu/{id}
  → DB 更新（事务）
  → afterCommit：立即删 myxhs:product:spu:{id}
  → 下一次读：缓存 miss → 查 DB → 回填新值

如果删缓存失败（Redis 抖动）
  → 发 CACHE_EVICT_TOPIC → 消费者重试删除

如果并发读在"删之前"把旧值回填了
  → Canal 抓到 binlog（已提交）→ PRODUCT_INDEX_TOPIC → 再删一次

如果是外部直改 DB（不经过应用）
  → 应用不知道 → 但 Canal 能抓到 → 最终失效
```

## 1. 生产环境怎么做（淘宝/行业常见）

| 策略 | 常见做法 |
|---|---|
| 更新顺序 | 先更新 DB，**提交后**删缓存（cache-aside） |
| 删失败 | MQ 兜底/重试；不能静默丢 |
| 最终一致 | **binlog/CDC 驱动失效**（Canal/Debezium），覆盖外部直改、并发回填、主从延迟 |
| 延迟双删 | 只在**没有 binlog 基建**时用；本质是"睡固定时间再删一次"，猜时间 |
| 降级 | Canal 宕机 → TTL 兜底；删缓存失败 → MQ/重试 |
| 观测 | 删缓存成功/失败/兜底/失效指标 |

## 2. 本项目的实现（代码证据）

### 2.1 写入口：事务后删缓存

`SpuService` 类注释写得很清楚（C-005）：

```java
/**
 * 【一致性策略（C-005：Canal 失效替代延迟双删）】
 * ① afterCommit 立即删（快路径，低延迟）
 * ② 删失败 → CACHE_EVICT_TOPIC MQ 兜底（写入侧）
 * ③ Canal（PRODUCT_INDEX_TOPIC → ProductCacheCanalEvictConsumer）→ 删缓存（最终保证）
 */
```

**更新 SPU**（字段级更新 + afterCommit）：

```java
LambdaUpdateWrapper<Spu> updateWrapper = new LambdaUpdateWrapper<>();
updateWrapper.eq(Spu::getId, spuId);
// 只 set 请求里出现的字段（避免 read-then-write 丢更新）
...
spuMapper.update(null, updateWrapper);

TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        evictSpuCache(spuId);
    }
});
```

**上下架**：同样 afterCommit 删；上架前校验"至少一个上架 SKU"。

**创建 SPU**（C-005）：

```java
spu.setStatus(ProductStatus.OFF_SHELF.getCode());   // 默认下架，避免"空商品在架"
spuMapper.insert(spu);

TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        spuBloomFilter.add(newSpuId);   // 提交后才加布隆；回滚不加
    }
});
```

**创建 SKU**：afterCommit 删 SPU 缓存 + 初始化库存（见 2.5）。

### 2.2 三层一致性

**第一层：afterCommit 立即删（快路径）**

```java
public void evictSpuCache(Long spuId) {
    String redisKey = RedisKeyConstants.PRODUCT_SPU + spuId;
    try {
        redisOperator.delete(redisKey);
    } catch (Exception e) {
        // Redis 抖动：发 MQ 兜底，DB 已提交不向客户端报 500
        rocketMQTemplate.syncSend(CacheEvictMessage.TOPIC, redisKey, 3000);
    }
}
```

**第二层：删失败 → MQ 兜底**

`CacheEvictConsumer` 消费 `CACHE_EVICT_TOPIC`，收到 key 后 `redisOperator.delete(key)`；
失败抛异常触发 MQ 重试；删除天然幂等。

**第三层：Canal binlog 最终失效**

```
Canal（my_xhs_product.t_spu/t_sku binlog）
  → PRODUCT_INDEX_TOPIC
  → ProductCacheCanalEvictConsumer（独立消费组）
  → 删 myxhs:product:spu:{id}
```

```java
if ("t_spu".equals(table)) {
    spuIds.add(data.getLong("id"));
} else if ("t_sku".equals(table)) {
    spuIds.add(data.getLong("spu_id"));   // SKU 变更 → 删父 SPU
}
for (Long spuId : spuIds) {
    redisOperator.delete(RedisKeyConstants.PRODUCT_SPU + spuId);
}
```

- `INSERT/UPDATE/DELETE`（含 `deleted=1` 逻辑删）一律失效；
- 同批多个 SKU 变更 → 父 SPU 去重后只删一次；
- 删除天然幂等；失败抛错触发 MQ 重试；
- **`t_sku` DELETE 在 `binlog_row_image=MINIMAL` 时只有主键、没有 `spu_id`** → 本项目 SKU 无删除路径，遇到仅告警（记录）。

### 2.3 为什么不用延迟双删

| 方案 | 本质 | 问题 |
|---|---|---|
| **延迟双删** | 更新后删一次，睡 N 秒再删一次 | **猜时间**：N 秒内并发读仍可能回填旧值；覆盖不了外部直改 DB；N 没有理论依据 |
| **Canal 失效** | 监听**已提交**的 binlog，删缓存 | 因果链确定；MQ 重试不丢；按主键分区保序；覆盖外部直改/并发回填/主从延迟 |

C-005 的决策：**移除延迟双删**（`SPU_DELAY_EVICT_SCHEDULER` 全仓零残留），
保留"立即删"做快路径，Canal 做最终保证。

### 2.4 外部直改、主从延迟、删失败

| 场景 | 谁兜底 |
|---|---|
| 外部直改 DB（不经过应用） | Canal（应用层根本不知道） |
| 并发读在删之前回填旧值 | Canal（提交后必发 binlog） |
| 删缓存失败 | MQ 兜底；MQ 也失败 → Canal/TTL |
| 主从延迟：从库读到旧值并回填 | Canal 最终删；逻辑过期 30min/物理 2h 兜底 |
| Canal 宕机 | 逻辑过期 30min + 物理 TTL 2h（基础设施降级，记录） |

### 2.5 建 SKU 后的库存初始化（product→inventory）

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        spuService.evictSpuCache(spuId);
        initInventory(sku.getId(), sku.getStock());
    }
});
```

- 远程调用放提交后，**不进事务**；
- 失败：ERROR + 指标 + 入 pending set；`InventoryInitRepairJob` 周期重试；
- "已初始化"响应视为成功（幂等）；
- 管理端也可手动重试。

## 3. 对照表：生产 vs 本项目

| 能力 | 生产环境 | 本项目 | 差异 |
|---|---|---|---|
| 更新顺序 | DB 提交后删 | ✅ afterCommit | 对齐 |
| 删失败兜底 | MQ/重试 | ✅ CACHE_EVICT_TOPIC | 对齐 |
| 最终一致 | binlog/CDC | ✅ Canal | 对齐 |
| 延迟双删 | 无 binlog 时的将就 | ❌ 已移除 | 对齐（更优） |
| 外部直改 | CDC 覆盖 | ✅ Canal | 对齐 |
| Canal 宕机 | TTL 兜底 | ✅ 30min/2h | 对齐（降级） |
| 库存初始化 | 事务后 + 补偿 | ✅ pending set + Job | 对齐 |

## 4. 十个坑

1. **先删缓存再更新 DB**：并发读会把旧值回填；本项目用"提交后删"。
2. **把延迟双删当主方案**：猜时间、覆盖不了外部直改；有 binlog 就用 binlog。
3. **删缓存失败静默**：必须 MQ 兜底/告警；否则脏到 TTL。
4. **只靠应用删**：外部直改 DB 不会触发；Canal 才能覆盖。
5. **Canal 宕机没兜底**：逻辑过期/物理 TTL 是最后防线。
6. **`t_sku` DELETE 行镜像缺 `spu_id`**：MINIMAL 模式下无法定位父 SPU；需调行镜像/反查（当前 SKU 无删除路径）。
7. **主从延迟回填旧值**：Canal 最终删；强一致读要主库（本项目未做）。
8. **布隆在事务内加**：回滚会留假阳性；本项目 afterCommit 加。
9. **库存初始化伪成功**：失败必须入补偿队列，不能只打日志。
10. **缓存 key 不统一**：写路径删的 key 必须和读路径一致（`myxhs:product:spu:{id}`）。

## 5. 值不值得深挖 / 一句话

- **值得**：afterCommit 删、MQ 兜底、Canal 因果链、为什么弃用延迟双删——缓存一致性面试核心；
- **一句话带过**：MQ 重试次数、Canal 配置；
- **一句话**：**写 DB 提交后立即删 + 删失败 MQ 兜底 + Canal binlog 最终失效；延迟双删是猜时间，binlog 才是确定性因果链。**
- 读路径见 **02**；索引供给见 **04**。

**面试口径**："商品写路径是 cache-aside：DB 提交后立即删缓存，删失败发 MQ 兜底，Canal 监听 binlog 做最终失效；不用延迟双删，因为那是猜时间，覆盖不了外部直改和主从延迟。Canal 宕机靠逻辑过期/物理 TTL 兜底。"
