# 05 · 热点与大促

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；所有 QPS/容量数字都是**设计假设**，
> 不是本项目压测结论（项目口径：编译+单测，无运行时）。
>
> **一句话**：大促热点 = **单 key + 单 DB 行**；靠逻辑过期 + 布隆 + 防惊群 + 预热 + 限流/降级扛；
> 本项目有前四项，**缺本地缓存、热点探测、SPU 预热、详情限流/自动降级**。
>
> **本篇带走**：① 热点识别 ② 击穿/雪崩/穿透 ③ 预热/降级/限流 ④ 本项目缺口与可讲口径。
> 前置：02/03。证据：`SpuService`、`ProductCacheWarmer`、`ProductController`、C-005。

---

## 0. 例子：大促爆款详情页（设计假设）

```
某个爆款 SPU：峰值 10 万 QPS（假设），全部打同一个 key myxhs:product:spu:{id}
  → Redis 命中（逻辑过期 30min）→ 直接返回
  → 逻辑过期 → 返回旧值 + 单线程异步刷新
  → Redis 挂了/被清空 → 全部穿透到 MySQL（没有 L1/限流 → DB 可能被打挂）
```

热点问题的本质：**流量集中在一个 key/一行数据上**，缓存和 DB 都会被单点放大。

## 1. 生产环境怎么做（淘宝/行业常见）

| 手段 | 做法 |
|---|---|
| 热点识别 | 按 key 统计 QPS/延迟；本地缓存命中；热点探测 |
| L1 本地缓存 | Caffeine/本地 Map，纳秒级；失效广播/短 TTL |
| 热点 key 拆分 | 同一商品多副本 key（随机后缀）/分片计数；读时随机 |
| 预热 | 大促前把 Top N 商品/类目灌进缓存 |
| 限流 | 网关/接口限流；热点接口单独配额 |
| 降级 | Redis 故障 → 本地缓存/静态兜底；DB 保护 |
| 容量 | 压测、容量规划、预案（扩容/切流/降级开关） |

## 2. 本项目的实现（代码证据）

### 2.1 热点在哪

- 详情缓存 key：`myxhs:product:spu:{id}`——**一个 SPU 一个 key**；
- 无 L1 本地缓存；无热点 key 拆分；无按 key 的热点统计；
- 详情读路径：布隆 → Redis（逻辑过期）→ MySQL（02）。

**结论**：单 key 热点上限就是单个 Redis slot 的上限；超大爆款需要 L1/拆分（本项目未做）。

### 2.2 三件事：击穿/穿透/雪崩

| 问题 | 本项目 | 说明 |
|---|---|---|
| **击穿** | ✅ 逻辑过期 + 异步刷新 | 热点 key 过期不删 key，返回旧值 + 单线程刷新；不会大量穿透 |
| **穿透** | ✅ 布隆 + 空值缓存 | 不存在的 ID 布隆挡；漏过的空值缓存 2min/5min |
| **雪崩** | ⚠️ 部分 | 逻辑过期避免"集中过期"；但 Redis 故障/清空 → 全部穿透 DB，**没有限流/降级** |

代码见 02：`RedisCacheData`、`asyncRefreshCache`、布隆、空值缓存。

### 2.3 预热：只预热了分类树

`ProductCacheWarmer` 只做一件事：预热分类树（`myxhs.cache-warmup.targets=product-category-tree`）。

- **SPU 详情没有批量预热**（没有 Top N 商品预热接口/Job）；
- 布隆启动时异步分批加载历史 SPU（5000/批），算"索引预热"，不是详情预热；
- 大促前要预热爆款详情 → 当前只能靠"用户访问自然回填"（缺口）。

### 2.4 限流与降级

**限流**（`ProductController`）：

```java
@RateLimit(prefix = "myxhs:product:list", maxRequests = 60, windowSeconds = 60, perUser = true)
```

- 列表/创建/更新/上下架有 `@RateLimit`；
- ⚠️ **详情 `GET /spu/{id}` 没有限流**——热点详情接口是裸奔的（缺口）。

**降级**：

- Redis 不可用 → 读路径降级直查 DB（02）；**没有回源限流/熔断**，DB 可能被打挂；
- 布隆不可用 → 降级放行（正确，但不能防穿透）；
- 没有"静态兜底/本地缓存兜底/降级开关"。

### 2.5 异步与可观测

浏览埋点走异步线程池：

```java
new ThreadPoolExecutor(
    2, 8, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100),
    daemonThreadFactory,
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

- 队列满时 **CallerRunsPolicy**：调用线程自己跑（会拖慢请求，但不会丢埋点）；
- `registerViewDropGauge` 把"丢弃"可见化（C-005）；
- 缓存指标：hit/miss/null/bloom/refresh/evict（02）；**没有按 key 的热点/QPS/延迟指标**。

### 2.6 价格延迟：详情缓存旧价，下单以 DB 为准

详情缓存最坏可能返回 30 分钟内的旧价格（逻辑过期；Canal 正常时秒级失效）；但**下单不走详情缓存**：

```
order → productFeignClient.batchGetSkuDetails(skuIds)
      → SkuService.batchGetSkuDetails → 查 DB（无缓存）
```

所以"详情展示旧价"是展示层延迟；**下单价格以 DB 为准**，不会按旧价成交。
（商品改价没有 API，只有改库；改库后详情靠 Canal 失效，03。）

| 能力 | 生产环境 | 本项目 | 差异 |
|---|---|---|---|
| 逻辑过期防击穿 | 常见 | ✅ | 对齐 |
| 布隆/空值防穿透 | 常见 | ✅ | 对齐 |
| L1 本地缓存 | 常见 | ❌ | 缺口 |
| 热点 key 拆分/探测 | 常见 | ❌ | 缺口 |
| SPU 预热 | 大促必备 | ❌ 只预热分类树 | 缺口 |
| 详情限流 | 必备 | ❌ | 缺口 |
| Redis 故障降级 | 本地/静态兜底 | ⚠️ 直查 DB，无限流 | 缺口 |

## 4. 十二个坑

1. **单 key 热点**：一个 SPU 一个 key；超大爆款要 L1/拆分。
2. **详情接口无限流**：`GET /spu/{id}` 没有 `@RateLimit`；热点时裸奔。
3. **SPU 未预热**：大促前只能自然回填；Top N 预热缺失。
4. **Redis 故障直查 DB**：没有回源限流/熔断，DB 可能被打挂。
5. **逻辑过期旧价**：详情可能展示旧价；下单以 DB 为准，别把详情价当成交价。
6. **布隆误判/只增**：误判放行；下架 ID 仍在布隆（多一次缓存查询）。
7. **主从延迟**：回填可能读旧值；Canal 失效 + TTL 兜底（03）。
8. **异步池 CallerRuns**：队列满会拖慢请求；埋点不能反压主流程。
9. **没有按 key 指标**：只能看总量，定位不到"哪个 SPU 热"。
10. **没有降级开关**：Redis/DB 故障只能硬扛。
11. **缓存清空/集群故障**：逻辑过期不防"key 全没了"；雪崩风险。
12. **没有压测**：QPS/容量都是设计假设，不能当实测结论。

## 5. 值不值得深挖 / 一句话

- **值得**：单 key 热点、L1/拆分、预热、详情限流、Redis 故障降级——大促面试核心；
- **一句话带过**：线程池参数、埋点指标；
- **一句话**：**大促热点 = 单 key + 单 DB 行；逻辑过期/布隆/防惊群解决"读"，预热/限流/降级解决"峰值"，L1/拆分解决"单 key 上限"。**
- 读路径见 **02**；写路径/失效见 **03**。

**面试口径**："商品详情用逻辑过期 + 布隆 + 空值 + 防惊群，能扛常规热点；但单 key 无 L1/拆分，详情接口也没限流，Redis 故障会直查 DB——这是大促缺口。下单价格走 SKU DB，不受详情缓存旧价影响。"
