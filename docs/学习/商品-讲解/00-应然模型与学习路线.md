> **口径**：先讲**生产环境/淘宝公开形态**，再对照本项目；代码只证明"我们这么做了"，不代表应然标准。

## 1. 例子：一件商品的三条路径

```
① 用户打开商品详情（高频读）
   布隆过滤 → Redis（逻辑过期）→ MySQL → 回填缓存
② 管理端改价/上下架（低频写）
   事务提交 → 立即删缓存 → 删失败 MQ 兜底 → Canal binlog 最终失效
③ 用户搜索（索引读）
   Canal 抓 t_spu/t_sku binlog → PRODUCT_INDEX_TOPIC → ES 索引
```

同一份商品数据，**三条路径对一致性的要求完全不同**：
详情页允许秒级延迟；管理端写完要尽快可见；搜索索引允许更长的最终一致。

## 2. 为什么需要它：三个核心问题

| # | 问题 | 真实场景 | 本项目的答案 |
|---|---|---|---|
| 1 | **读得准** | 详情页 QPS 高；缓存与 DB 不一致 | 逻辑过期 + 布隆 + 空值缓存 + Canal 失效 |
| 2 | **写得对** | 建 SPU 没 SKU 就上架；并发更新丢字段；价格负数/划线价倒挂；库存初始化失败 | 默认下架、上架校验 SKU、字段级更新、价格/JSON 校验、库存初始化补偿 |
| 3 | **查得快** | 热点商品打爆 DB；冷 key 穿透 | 多级缓存、布隆、分布式锁防惊群、读写分离、预热 |

**三个关键取舍**（面试要能解释）：

1. **逻辑过期 vs 物理过期**：物理过期到点删 key，高并发同时穿透（击穿）；逻辑过期返回旧值 + 异步刷新，
   用"秒级延迟"换"不打挂 DB"；
2. **Canal binlog 失效 vs 延迟双删**：延迟双删是"睡固定时间再删一次"的猜时间魔数；
   binlog 是"已提交数据"的因果链，确定性更强（C-005 用它替换了延迟双删）；
3. **单库 + 读写分离 vs 分库分表**：商品是"读多写少 + 量级可控"，单库 + 读写分离够用；
   分片留给订单/优惠券这种增长快的表。

## 3. 域边界：商品只存"静态描述"

```
product：SPU/SKU/类目/价格/状态（静态描述）
inventory：真实库存（product.t_sku.stock 只是冗余占位；建 SKU 后 afterCommit 初始化，失败进补偿 Job）
order：下单时快照商品价格/名称（不依赖商品实时状态）
search：索引（Canal 供给）
home：BFF 聚合详情
```

- **商品不扣库存**：真库存在 inventory；`t_sku.stock` 是占位，不能当库存用；
- **订单不实时读商品**：下单落快照，商品后续改价不影响已下单；
- **搜索不直连商品库**：Canal → MQ → ES，商品只负责"供给变更"。

## 4. 应然 vs 实然（本项目简化了什么）

| 能力 | 生产环境（淘宝/行业） | 本项目 | 影响 |
|---|---|---|---|
| SPU/SKU | 销售属性矩阵自动生成 SKU | `specs` 自由 JSON | 缺属性体系 |
| 类目/属性 | 多级类目 + 属性模板 | 三级类目只读 | 简化 |
| 品牌 | 品牌库/授权审核 | 裸 `brand_id` | 缺 |
| 价格 | 售价/划线价/活动价/会员价/阶梯价 | 售价 + 划线价 | 简化 |
| 状态机 | 草稿→审核→上下架→删除 + 定时 | SPU 建后默认下架；SKU 建后默认上架；0/1 即时上下架 | 简化 |
| 多商家 | 店铺归属 | 平台自营 | 缺 |
| 内容审核 | 图文/资质审核 | 无 | 缺 |
| 索引供给 | Canal/CDC → ES | ✅ Canal → MQ → ES | 对齐 |
| 缓存一致性 | 多级缓存 + binlog 失效 | ✅ 逻辑过期 + 布隆 + Canal | 对齐 |

> 这些差异是**范围取舍**，不是 bug；面试可以主动说"知道缺口，以及补的话怎么补"。

## 6. 面试开场（30 秒）

> "商品域我按三个问题讲：读得准、写得对、查得快。读路径是布隆 → Redis 逻辑过期 → MySQL，
> 空值缓存防穿透、分布式锁防惊群；写路径是事务后立即删 + MQ 兜底 + Canal binlog 最终失效，
> 不用延迟双删；索引走 Canal→MQ→ES。商品只存静态描述，库存和下单快照都不在它这里。"
