## 1. 先看一个例子：一笔 199 元的钱一生

```
用户下单 199 元 → 点"去支付"
  ① order 调 payment /pay
     → t_payment(status=0 待支付, payment_no=P20261019..., amount=19900分)
     → Redis myxhs:payment:paying:{orderId}（30min）
     → 渠道下单（Mock/支付宝）→ 返回二维码/跳转
  ② 用户付款 → 渠道异步通知（HTTP 回调，RSA2 验签 + 二次校验）
     → 三态解析：成功/明确失败/无法解析（-1 → 让渠道重试）
     → 乐观锁 WHERE status=0 → status=1 + paid_at
     → 四层通知 order（Feign → MQ → XXL 补偿 → 对账）
  ③ 30 分钟没付（另一条时间线）
     → paymentTimeoutCheckJob：DB 扫 status=0 AND created_at<now-30min → 乐观锁置 2
     → 若渠道此时才成功（迟到成功）→ 条件翻转 2→1 → 若订单已取消 → 业务拒绝 → 自动退款
  ④ 退款（用户退/订单取消）
     → t_refund(0 退款中) → 渠道退款 → 回调 → 1
     → 累计退款 = SUM(status=1)；全退：t_payment.status=3；部分退：保持 1 可续退
  ⑤ 日结
     → t_channel_flow（渠道对账文件）→ t_settlement_bill（日切账单）
     → 三方对账 → t_settlement_diff（三类差异挂账）→ 人工处理不覆盖
```

**这一圈里有六张表**：`t_payment`（支付单）/ `t_refund`（退款单）/ `t_payment_event`（事件流水，append-only）
/ `t_channel_flow`（渠道流水）/ `t_settlement_bill`（日切账单）/ `t_settlement_diff`（差异挂账）。
**支付域不是一个"调渠道接口"的模块，它自己就是一套账。**

## 2. 为什么需要支付域（两个身份）

1. **交易链路的资金执行者**：order 发起 pay/refund；支付/退款结果**主动回推 order**——而且用的是
   **四层通知**（Feign 主 → MQ 备 → XXL 补偿 → 对账），因为"钱付了但订单不知道"是资损级事故；
2. **独立资金账本**：支付单/退款单/事件/结算/对账自成一域——它可以脱离订单被审计、对账、结算。

> 一句话：**订单管"货"，支付管"钱"；两边各自是账本，靠状态机 + 补偿 + 对账咬合。**

## 3. 应然模型（真实支付域该有的样子）

| # | 能力 | 应然内容 |
|---|---|---|
| 1 | 支付单状态机 | 待支付→成功/失败/已关闭；**多渠道、多次尝试**（换渠道不是新订单） |
| 2 | 渠道契约层 | 通知/查单/关单/退款/验签是"渠道真实契约"；业务只依赖契约接口（换渠道=换实现） |
| 3 | 回调安全 | **先验签再进状态机**；二次校验（金额/单号/商户）；三态解析；ACK 控制渠道重试 |
| 4 | 结果通知可靠 | 至少一次：同步主路径 + MQ + 补偿 Job + 对账终线（四层） |
| 5 | 退款 | 部分退/多次退；累计可退；全退置终态；退款出金**幂等** |
| 6 | 对账与结算 | 渠道流水落库 → 日切账单（幂等重跑）→ 三类差异挂账 → 人工处理；结算=收款−退款−手续费 |

**三条铁律**（贯穿 8 篇）：
- **幂等**：渠道回调 at-least-once（重复/乱序/伪造）——唯一索引 + 乐观锁 + Redis 幂等键，**三层缺一不可**；
- **状态机**：所有状态变更用**条件 UPDATE**（WHERE status=当前态），影响行数=0 即幂等命中；
- **补偿**：通知/回调/退款都可能"半成功"——补偿窗口 + 上限 + 人工 + 对账兜底。

## 4. 实然对照（本项目，C-002/003 改造后）

| 能力 | 现状 | 说明 |
|---|---|---|
| 支付单状态机 | ✅ **单渠道单次尝试已升级**（C-002）：待支付单**复用**（同渠道返回同一 paymentNo）、**换渠道**（先查后决，关旧渠道→新单） | 终态含 4=已关闭（换渠道/订单终结关闭 pending） |

| 回调安全 | ✅ 验签 + 二次校验 + 三态解析（-1 让渠道重试）+ 迟到成功翻转（2→1） | 失败返回 fail + 告警，不误处理 |
| 四层通知 | ✅ Feign 主 → MQ 备（PAY_RESULT/REFUND_RESULT_TOPIC）→ XXL 补偿（5min 窗口）→ 对账 Job | `paymentNotifyCompensateJob` / `refundNotifyCompensateJob` / `paymentReconcileJob` |
| 退款 | ✅ 累计退款/可退金额/部分退可续退（T-076）；全退才通知订单（T-077）；C-002 出金幂等 | 退款回调模拟器 T-075 修复 |
| 对账结算 | ✅ 日切账单（uk 日期+渠道、run_no、force）+ 三方对账（游标 + 安全阀）+ 三类差异 + 演练扰动 | 结算与支付共库独立数据源 |

**已知边界（讲，不在本系列展开）**：真实渠道 SDK/网关联调（无商户资质，契约形态保真）；组合支付/余额/积分（未做）；退款域自身的 out 键缺口（订单侧"重试前查事实"兜底）。

## 5. 学习路线（8 篇）

| 篇 | 主题 | 核心问题 | 咬合 |
|---|---|---|---|
| 00 | 本篇 | 支付域是什么/为什么/怎么学 | — |
| 01 | 渠道契约层（支付宝） | 通知/查单/关单/退款/验签为什么要隔离成契约层；ACK 与重试 | gateway（回调免鉴权）、order（契约不变） |
| 02 | 支付回调与订单咬合 | 四层通知为什么是四层；回调幂等；业务拒绝=退款信号；撞车 | order（回调接口/状态机） |
| 03 | 退款链路 | 部分退/累计退/出金幂等；退款→库存/券/订单 | inventory（回补）、coupon（退券）、order（终结） |
| 04 | 对账体系 | 以谁为准；长款/短款/单边账；差异挂账与人工 | 全系统对账家族（99 §4-C） |
| 05 | 结算域 | 结算单/计费/分账/重跑；为什么结算独立 | order（交易额）、支付/退款流水 |
| 06 | 分布式问题专题 | 事务消息/Outbox/幂等矩阵/乱序/补偿自循环——用支付当样本 | 99 §4 家族横向对比 |
| 07 | 微服务与工程问题 | payment↔order 边界/超时/降级/回滚；Mock/演示密钥/死代码/注释漂移；参数校验/权限一嘴带过 | 99 §8.2 沉淀 |

**建议节奏**：01→02→03 按链路顺序读（渠道→回调→退款）；04/05 独立域；06/07 横切（面试差异化）。

## 6. 面试开场（30 秒版）

> "支付域我做成了**两本账 + 一条契约**：支付单/退款单/事件流水是交易账，渠道流水/结算/差异挂账是资金账；
> 渠道层按支付宝真实契约隔离（RSA2 验签、通知 ACK、先查后决），业务只依赖 `PayChannelStrategy`。
> 可靠性上三件套：**唯一索引 + 乐观锁 + Redis 幂等键**防重复；结果通知走**四层**（Feign→MQ→补偿 Job→对账）；
> 退款是全链路最绕的——累计可退、部分退可续退、全退才通知订单。"
>
> **危险信号（自检）**：只说"调通接口"、说不出幂等三层、把"通知失败重试"当兜底终线、回调不验签、退款不做累计校验。
