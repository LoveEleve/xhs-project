# 06 · 分布式问题专题（用支付当样本）

> **一句话**：支付链路的分布式问题只有五类——**不确定、重复、乱序、丢失、部分失败**；
> 五类问题对应五组模式，支付只是把这些模式用到了极致。
>
> **本篇带走 1 张地图 + 5 组模式**：
> 不确定 → **先查后决**；重复 → **幂等键 + 状态守卫**；乱序 → **状态机 + CAS**；
> 丢失 → **至少一次 + 四层收敛**；部分失败 → **补偿有边界 + 对账终线**。
>
> 前置：01–04（本篇只做抽象，不重复细节）。证据：`PaymentService` 全链路、四层通知、对账体系。

---

## 0. 一张地图：支付链路上的五类问题

```
下单 ──▶ 支付 ──▶ 渠道回调 ──▶ 通知订单 ──▶ 退款 ──▶ 对账/结算
 │        │          │            │           │         │
 │        │          │            │           │         └─ 丢失：账单/通知都可能缺
 │        │          │            │           └─ 部分失败：渠道成功、本地失败
 │        │          │            └─ 重复/乱序/丢失：Feign/MQ/Job 三层
 │        │          └─ 重复（重试）、乱序（迟到）、伪造（验签）
 │        └─ 不确定：超时/不可达，不知道付没付
 └─ 并发：重复建单/库存券争抢 → 由幂等键覆盖（§2）
```

**根因只有三个**：网络不可靠（超时/丢包）、进程会崩（本地成功、远端没收到）、调用方会重试（重复）。
所以不要问"怎么保证不丢不重"，要问"**丢了/重了之后怎么收敛**"。

## 1. 不确定 → 先查后决

**问题**：调用渠道超时/不可达时，结果是"不知道"——不是成功，也不是失败。

**模式**：任何"改变状态"的动作前，先查事实；**不可判定就不处置**。

| 场景 | 先查什么 | 三种结果 |
|---|---|---|
| 支付超时处置 | 渠道查单 | 已付→收敛成功；未付→关交易+置失败；**不可达→不处置** |
| 换渠道关旧单 | 查旧交易 | 已付→受理收敛；未付→close 后新开；不可达→不切换 |
| 退款重试 | 渠道退款结果 | 已退→同键返回；失败→重试；未知→**同键重试** |

**铁律**：`null`（不可判定）绝不能折叠成"未付/失败"——这是钱货两空的源头（见 01 §3、02 §2）。

## 2. 重复 → 幂等键 + 状态守卫

**问题**：至少一次投递意味着"同一件事会被处理多次"。

**模式**：幂等不是"去重表"，而是**找到每类操作的"业务唯一键 + 状态机当前位置"**。

| 操作 | 幂等键 | 守卫手段 | 为什么不用别的 |
|---|---|---|---|
| 创建支付单 | 订单 + 待支付态 | `uk_order_pending` 唯一索引 | 并发建单靠 DB 兜底，锁会过期 |
| 支付成功 | 支付单号 | `WHERE status=0` 条件更新 | 影响行数=0 即已处理，天然幂等 |
| 退款出金 | `out_refund_no` | 锁 + 唯一索引 + 渠道 `out_request_no` | 出金必须多道闸（03 §2） |
| 通知订单 | `orderId` + 订单状态 | 订单 `WHERE status=0` | 重复通知 harmless |
| 库存回补/券退还 | 订单/券 ID | 条件更新 / 幂等接口 | 重复回补会虚增 |

**判断标准**：幂等键要**贴近副作用**——出金的键必须能传给渠道（`out_request_no`），
不能只在本地"记一笔已处理"（进程崩了就丢）。

## 3. 乱序 → 状态机 + CAS

**问题**：重复之外，事件还会**迟到**（超时置失败后成功才到）、**交叉**（关单 vs 支付）、**并发**（两条通知同时到）。

**模式**：状态机只允许合法迁移；每次迁移用 **CAS（`WHERE status=旧值`）**；终态要有显式"翻转规则"。

```
0 待支付 ──成功──▶ 1 已成功 ──全退──▶ 3 已退款
   │ 失败                  └─ 部分退：保持 1（可续退）
   ▼
2 失败 ─┐
4 关闭 ─┴── 迟到成功（CAS 条件翻转）──▶ 1
```

```java
// 迟到成功：只有"还是旧状态"的行才翻转（CAS）
int flipped = paymentJdbcTemplate.update(
        "UPDATE t_payment SET status = 1, paid_at = ? WHERE id = ? AND status = ?",
        now, paymentId, previousStatus);
if (flipped > 0) {
    afterPaySuccess(...);   // 抢到翻转权，补跑成功副作用
}
```

**三个反例**（都是真实坑）：

- 用"先查再改"而不是条件更新 → 两条并发通知都读到 0，重复通知订单；
- 迟到成功直接 `return` → 用户已付、本地记失败、无退款通道；
- 关单先赢后支付成功，订单拒绝仍重试 → 退款后订单又被置成功（乱序资损）。

## 4. 丢失 → 至少一次 + 四层收敛

**问题**：同步调用会超时、MQ 会丢、消费会失败、进程会崩在"状态已改、消息未发"之间。

**模式**：端到端**没有 exactly-once**；工程上只有两条路：

- **at-most-once + 对账**（丢了靠事后发现，不自动收敛）；
- **at-least-once + 幂等消费**（支付选这条：重复比丢失便宜）。

四层收敛（02 §3）：

| 层 | 解决 | 边界 |
|---|---|---|
| Feign 同步 | 快、能拿业务结论 | 超时=未知，不判死 |
| MQ 备 | Feign 丢/超时的即时兜底 | 至少一次，靠幂等 |
| Job 兜底 | MQ 也失败（发送端崩） | 窗口 5min / 上限 10 次 / 告警 |
| 对账终线 | 前三层都假设"本地状态对" | 以渠道为准，天级延迟 |

**最关键的边界**：**ACK 的边界 = 支付单状态已提交**，不是"订单已通知"。
把下游失败翻译成 ACK fail → 重放会被状态守卫挡掉，形成"假重试"（02 §1.2）。

## 5. 部分失败 → 补偿有边界 + 对账终线

**问题**：本地成功、远端失败（支付成功但订单没收到；退款成功但订单没回补）。

**模式一：补偿不是回滚**。分布式里钱一旦动了，没有"回滚"，只有**新的正向动作**（退款/关单/回补），
它本身也必须幂等、可重试。

**模式二：补偿必须有边界**：

| 维度 | 本项目的值 | 为什么 |
|---|---|---|
| 窗口 | 支付/退款成功后 5 分钟 | 给正常链路留时间，避免"刚失败就补" |
| 次数 | 10 次 | 无限重试 = 掩盖问题 + 放大故障 |
| 告警 | 超限告警人工 | 机器解决不了的，必须有人接 |
| 终线 | 对账 | 补偿也不能保证 100%，最后以渠道为准 |

**模式三：对账是"两条真相"的交汇**：

- **资金真相**在渠道（钱的实际流水）；
- **业务真相**在本地（订单/支付状态）；
- 对账不是让一方覆盖另一方，而是**发现差异 → 挂账 → 人工裁决**（04 §4）。

## 6. 为什么不用分布式事务（2PC/XA）

| 方案 | 为什么不用 |
|---|---|
| 2PC/XA | 渠道（支付宝）不参与你的事务；长事务锁资源；协调者宕机=悬挂 |
| TCC | 要为每个参与方写 Try/Confirm/Cancel，渠道侧无法提供 Try |
| 本地消息表/事务消息 | ✅ 采用：order 终结=事务消息；order 状态通知=本地消息表（Outbox）；payment→order=Feign+MQ+Job |
| Saga | ✅ 本质就是"补偿链"：支付→退款、下单→取消，正是本项目在做的 |

支付的答案是：**本地事务 + 可靠事件 + 幂等消费 + 补偿 + 对账**——不追求强一致，追求**最终收敛**。

## 7. 与 99 §4 的家族对照（面试横向题）

| 问题家族 | 本项目的样本 | 通用模式 |
|---|---|---|
| A 幂等 | 支付单 `WHERE status=0`、退款 `out_request_no` | 幂等键 + 状态守卫 + 唯一索引 |
| B 乱序 | 迟到成功 2\|4→1、关单 vs 支付 | 状态机 + CAS + 翻转规则 |
| C 对账 | 渠道流水 vs 本地，差异挂账 | 以外部真相为准，检测与修正分离 |
| F 可靠消息 | 四层通知、Outbox、事务消息 | 至少一次 + 幂等消费 + 终线 |

## 8. 值不值得深挖 / 一句话

- **值得**：五类问题的**判断方式**（不确定/重复/乱序/丢失/部分失败）——换任何分布式业务都能套；
- **一句话带过**：具体组件的配置（MQ 重试次数、Job Cron、锁 TTL）；
- **一句话**：**分布式支付 = 接受"不可靠"，用"先查后决 + 幂等 + 状态机 + 至少一次 + 有界补偿 + 对账"换最终收敛。**
- 工程边界（payment↔order 谁拥有什么、Feign 降级语义）见 **07**。

**面试口径**："支付链路的分布式问题分五类：超时不确定、重复、乱序、丢失、部分失败；对应先查后决、幂等键+状态守卫、状态机+CAS、至少一次+四层收敛、有界补偿+对账终线；不用 2PC，走本地事务+可靠事件+补偿。"
