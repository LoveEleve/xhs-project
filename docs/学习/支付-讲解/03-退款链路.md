# 03 · 退款链路：部分退、累计校验、出金幂等

> **一句话**：退款不是"把支付单改成已退款"，而是"按**剩余可退金额**退、每次一张退款单、
> **同键只出金一次**；**只有全退才通知订单**（状态 5 + 库存/券回补）"。
>
> **本篇带走 4 条**：① 可退 = 支付额 − `SUM(成功退款)`，部分退可续退
> ② 出金幂等四道闸（锁 / out 键 / 唯一索引 / 渠道同号）
> ③ 同步返回三分支：成功 / 明确失败 / **异常=未知≠失败**
> ④ 全退才通知订单；退款失败不改订单状态
>
> 前置：`01-渠道契约层.md`、`02-支付回调与订单咬合.md`。
> 证据：`PaymentService.doRefund/handleRefundSuccessInternal`、`RefundNotifyCompensateJob`、
> `RefundTimeoutCheckJob`、order 侧 `onRefundSuccess`；T-071/075/076/077。

---

## 0. 场景：199 元分两次退

**第一幕：全退（正常）**

```
支付单 199 元（status=1）
→ 退款 199 → t_refund(0 处理中) → 渠道同步返回 fund_change=true
→ 退款单 1、支付单 3（已退款）
→ 通知订单：订单 1/2/3 → 5（已退款）+ 库存回补 + 退券 + 通知用户
```

**第二幕：部分退（最容易被写错）**

```
第一次退 100 → 支付单保持 1（还能再退 99），订单状态不变
第二次退 99  → 累计 199 = 支付额 → 支付单 3 → 才通知订单
```

**第三幕：三种异常**

| 场景 | 机制 | 在哪节 |
|---|---|---|
| 用户连点两次退款 | 锁 + out 键 + 唯一索引 + 渠道同号 | §2 |
| 调渠道超时（结果未知） | **不当失败**：回滚 → 同键重试 → 渠道幂等 | §3 |
| 渠道明确失败 | 退款单 2 + MQ 失败通知；订单状态不变 | §3/§4 |

## 1. 可退余额：退的是"剩余"，不是"支付单"

**公式**：`可退 = payment.amount − SUM(已成功退款)`。

```java
private BigDecimal getRefundedAmount(Long paymentId) {
    return paymentJdbcTemplate.query(
            "SELECT COALESCE(SUM(refund_amount), 0) FROM t_refund " +
                    "WHERE payment_id = ? AND status = 1 AND deleted = 0",
            rs -> {
                if (rs.next()) {
                    return rs.getBigDecimal(1);
                }
                return BigDecimal.ZERO;
            },
            paymentId
    );
}
```

两个关键点：

1. **只统计 `status=1`（成功）**：处理中/失败/关闭不算——否则一次失败会把可退额度"吃掉"；
2. **用 SQL 聚合，不拉明细**：可退额度是"累计值"，不是"最近一次退款"。

退款前校验：

```java
BigDecimal alreadyRefunded = getRefundedAmount(paymentId);
BigDecimal maxRefundable = payment.getAmount().subtract(alreadyRefunded);
if (refundAmount.compareTo(maxRefundable) > 0) {
    throw new BizException(ResultCode.PAYMENT_FAIL, "退款金额超过可退金额");
}
```

**T-076（原 bug）**：原实现每次退款成功都无条件把支付单置 3（已退款）——
部分退 100 之后支付单变 3，第二次退 99 直接被"支付单状态不允许退款"拒绝。
修复：**只有累计退款 ≥ 支付额才置 3**，否则保持 1 可续退：

```java
BigDecimal refundedTotal = getRefundedAmount(refund.getPaymentId());
BigDecimal paymentAmount = paymentJdbcTemplate.queryForObject(
        "SELECT amount FROM t_payment WHERE id = ? AND deleted = 0",
        BigDecimal.class, refund.getPaymentId());
if (paymentAmount != null && refundedTotal.compareTo(paymentAmount) >= 0) {
    paymentJdbcTemplate.update(
            "UPDATE t_payment SET status = ?, updated_at = ? WHERE id = ? AND deleted = 0",
            STATUS_REFUNDED, LocalDateTime.now(), refund.getPaymentId());
} else {
    log.info("[退款成功] 部分退款(累计{}<支付{}), 支付单保持已支付: paymentId={}",
            refundedTotal, paymentAmount, refund.getPaymentId());
}
```

**渠道兜底**：即使本地校验漏了，支付宝也会用 `ACQ.REFUND_AMT_NOT_EQUAL_TOTAL`
拒绝"累计超过交易金额"的退款——本地校验 + 渠道校验，双保险。

## 2. 出金幂等：四道闸

退款的本质是**出金**，重复一次就是资损。四道闸各管一段：

| 闸 | 防什么 | 失效时谁兜 |
|---|---|---|
| **① Redisson 锁**（per paymentId） | 同一支付单并发退款 | 串行化，后来的直接"请勿重复退款" |
| **② out_refund_no 业务键** | 重试/补偿重放（同一业务退款） | 同键直接返回既有退款单（含"处理中"） |
| **③ DB 唯一索引** `uk_out_refund_no` | 并发同键（锁覆盖不到的进程/实例） | `DuplicateKeyException` → 重查返回既有单 |
| **④ 渠道 `out_request_no`** | 网络超时后的同键重试 | 支付宝"同号只退一次" |

```java
// ① 锁：同一支付单串行
RLock refundLock = redissonClient.getLock("myxhs:lock:payment:refund:" + paymentId);
locked = refundLock.tryLock(3, 10, TimeUnit.SECONDS);
if (!locked) {
    throw new BizException(ResultCode.INTERNAL_ERROR, "系统繁忙，请稍后再试");
}

// ② 业务幂等键：同键返回既有退款单（含"处理中"——重试拿到的始终是同一 refundNo）
String outRefundNo = request.getOutRefundNo();
if (outRefundNo != null && !outRefundNo.isBlank()) {
    Refund existingRefund = findRefundByOutRefundNo(outRefundNo);
    if (existingRefund != null) {
        return R.ok(existingRefund.getRefundNo());
    }
}

// ②' Redis 退款中标记（锁后二次检查，防重复请求）
String existingStatus = stringRedisTemplate.opsForValue().get(refundingKey);
if (existingStatus != null) {
    throw new BizException(ResultCode.IDEMPOTENT_REJECT, "请勿重复退款");
}
stringRedisTemplate.opsForValue().set(refundingKey, String.valueOf(userId), REFUNDING_KEY_TTL);

// ③ 唯一索引兜底：并发同键插入冲突 → 重查返回既有单
try {
    paymentJdbcTemplate.update("INSERT INTO t_refund (...) VALUES (...)", ...);
} catch (DuplicateKeyException dup) {
    if (outRefundNo != null && !outRefundNo.isBlank()) {
        Refund existingRefund = findRefundByOutRefundNo(outRefundNo);
        if (existingRefund != null) {
            return R.ok(existingRefund.getRefundNo());
        }
    }
    throw dup;
}

// ④ 渠道幂等键：优先业务键 outRefundNo（重试稳定），缺省用 refundNo
String channelRequestNo = (outRefundNo != null && !outRefundNo.isBlank()) ? outRefundNo : refundNo;
RefundTradeResult result = strategy.refund(payment.getPaymentNo(), channelRequestNo, refundAmount, request.getReason());
```

**一个诚实的边界**：如果调用方**不传 `outRefundNo`**，渠道幂等键就退化成 `refundNo`（每次重试都是新号）。
一旦出现"渠道已出金、但响应超时 → 事务回滚 → 调用方重试"，就可能**再退一次**（只要还没超过可退余额）。
所以业务侧（售后单）必须传稳定的 `outRefundNo`——这是幂等的"业务锚点"，不能省。

## 3. 同步返回三分支：未知 ≠ 失败

C-003 对齐支付宝真实契约：退款**同步返回**（无退款回调）。结果的三种形态：

```java
RefundTradeResult result = strategy.refund(payment.getPaymentNo(), channelRequestNo, refundAmount, request.getReason());

if (result != null && result.isFundChange()) {
    // ① 成功：退款单 1 + 支付单（全退才 3）+ 通知订单
    handleRefundSuccessInternal(refundNo);
} else {
    // ② 明确失败：退款单 2 + MQ 失败通知（订单状态不变）
    handleRefundFailInternal(refundNo);
}
// ③ 调用抛异常（超时/网络）：走 catch → 事务回滚 → 调用方同 out 键重试
//    绝不当作"失败"——否则用户没收到钱，我们却把退款单记成失败
```

为什么异常必须上抛（而不是在方法里吞掉置失败）：

- 异常时渠道可能已经出金，只是响应没回来；
- 事务回滚后，退款单 INSERT 也撤销，调用方用**同一个 `outRefundNo`** 重试；
- 渠道按 `out_request_no` 幂等返回既有结果——不会重复出金；
- 如果吞掉置失败，就再也不会重试，用户的钱卡在渠道。

## 4. 退款成功后：订单只认"全退"

**T-077**：部分退款**不通知订单**——订单状态仍是"已支付"，库存/券都不动；
只有全退（累计 = 支付额）才通知：

```java
if (paymentAmount != null && refundedTotal.compareTo(paymentAmount) >= 0) {
    sendRefundResultMq(refund.getOrderId(), refund.getUserId(), true, refundNo);
    try {
        R<Void> nr = orderFeignClient.notifyRefundSuccess(refund.getOrderId(), refundNo);
        ...
    } catch (Exception e) { ... }
} else {
    log.info("[退款成功] 部分退款，不通知订单状态变更: orderId={}", refund.getOrderId());
}
```

订单侧 `onRefundSuccess`（全退时）：

```
订单 1/2/3 → 5（已退款）；子单全部 → 5（幂等）
→ confirmInventoryDeductSync（先清预扣，避免与回补叠加）
→ restoreStockOnRefund（库存回补）
→ returnCouponIfUsed（退券）
→ 通知用户"退款已到账"
```

**为什么全退才动订单**：订单状态是"整单"的；部分退之后订单还是"已支付"，
库存和券不能动。部分退的账在支付域（退款单）里，订单域不感知。

**退款失败**：`handleRefundFailInternal` 把退款单置 2 并发 MQ 失败通知；
订单侧 `refund-fail` 端点只记日志、**不改订单状态**——重试/取消由售后流程决定。

**通知订单失败怎么办**（与 02 对称）：

- MQ `REFUND_RESULT_TOPIC` 备用；
- `RefundNotifyCompensateJob`：扫 `t_refund status=1 AND t_payment.status=3 AND success_at < now-5min`，
  重发 Feign，10 次告警；
- 对账终线（04）。

## 5. 退款超时：15 天兜底

同步退款正常情况下是"秒级返回"，但进程崩溃/事务窗口可能留下 `status=0`（处理中）的退款单。
`RefundTimeoutCheckJob` 每 60 秒扫 `status=0 AND created_at < now-15d`：

```
→ 条件更新 0 → 3（退款关闭）
→ 清 Redis 退款中标记
→ 发 MQ 退款失败通知
```

15 天是给渠道/银行留的处理时间；它不是主链路，是"防止退款单永远卡在处理中"的兜底。

## 6. 坑清单

1. **部分退置 3（T-076）**：剩余金额再也退不了。修复 = 累计 ≥ 支付额才置 3。
2. **部分退通知订单（T-077）**：订单变 5、库存/券回补，但只退了一部分钱。修复 = 全退才通知。
3. **异常当失败**：用户没收到钱，退款单却记失败且不再重试。修复 = 未知上抛，同键重试。
4. **只靠 Redis 标记**：重启/过期就失效。必须配 DB 唯一索引 + 渠道幂等。
5. **不传 outRefundNo**：未知重试有双退风险（见 §2 边界）。
6. **金额比较用 `equals`**：`100.0` vs `100.00`；一律 `BigDecimal.compareTo`。
7. **退款补偿只扫全退**：这是设计——部分退本来就不通知订单，别把它当"漏补偿"。

## 7. 值不值得深挖 / 一句话

- **值得讲透**：可退余额的累计口径、T-076/T-077 两个 bug 的因果、出金幂等四道闸、未知≠失败；
- **一句话带过**：锁的 TTL、`refundType` 字段、补偿 Job 的 Redis 计数实现；
- **一句话**：**退款 = 按剩余可退金额退 + 同键只出金一次 + 全退才动订单。**
- 横向模式（幂等矩阵/补偿边界）见 **06 分布式专题**。

**面试口径**："退款按 `支付额 − SUM(成功退款)` 计算，部分退保持支付单可退；出金幂等靠锁 + out 键 + 唯一索引 + 渠道同号；渠道同步返回，异常视为未知并同键重试；只有全退才通知订单回补库存/券。"
