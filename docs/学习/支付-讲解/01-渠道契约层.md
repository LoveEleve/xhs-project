# 01 · 渠道契约层（支付宝）

> **一句话**：支付域不直接调渠道 SDK，而是把"和渠道打交道"收进一层契约。
> 本篇只回答一个问题：**为什么要有契约层、它长什么样**。
>
> **本篇带走 3 条**：① 契约层 = 策略模式（出站）+ 防腐层（入站）
> ② 五件事：创建/查单/关单/退款/通知 ③ 三值：1 已付 / 0 未付 / **不可判定**
>
> **留到后面**：通知三必答（二次校验/ACK·幂等）与 TRADE_CLOSED 双语义 → **02**；
> 先查后决（防双付）→ **06**；签名 → 一句话（本文 §6）。
>
> 前置：`00-应然模型与学习路线.md`。证据：`strategy/`、`config/PayStrategyConfig`、`alipay/`、C-003。

---

## 0. 场景：一笔 199 元的支付

**角色**：用户小王、商户系统（本项目）、支付宝。**三个单号**：

| 单号 | 谁生成 | 作用 |
|---|---|---|
| `out_trade_no`（= paymentNo，PAY 前缀） | **商户** | **支付单号**（不是订单号）；查单/关单/退款/通知都拿它找渠道 |
| `trade_no` | **支付宝** | 渠道交易号（对账/排查用） |
| `notify_id` | **支付宝** | 一条通知的 ID；重试时不变 |

> 一个订单可有多条支付单（换渠道/超时重建/并发复用），所以渠道商户单号标识的是"**一次支付尝试**"。

**正常流程（本篇只需要这个模型）**：

```
① 小王点"去支付"（订单 O1001，199.00 元）
② 商户 tradeCreate 登记渠道交易 → trade_no；本地签 app.pay orderStr = payParams
   → /pay 返回 PaymentVO{paymentNo, tradeNo, payParams} → 客户端拉起收银台
③ 小王付款 → 支付宝异步通知商户
④ 支付域处理通知 → 支付单 0→1 → 明文 ACK "success"
⑤ 支付成功后通知订单（Feign→MQ→补偿→对账，见 02）
```

本篇只回答：**②④ 之间，商户和渠道之间到底约定了几件事、业务层该看到什么。**

## 1. 没有契约层会怎样

反例：`PaymentService` 直接调 SDK、直接用渠道状态码。则"发起支付"里会出现
`if (payType == 1) alipayClient.tradeCreate(...) else if (payType == 2) ...`，
而且这套判断要在**发起/超时关单/退款/对账**四处各写一遍；业务到处出现 `TRADE_SUCCESS`/`TRADE_FINISHED`。

后果不是"代码丑"，是三件事：

1. **接新渠道 = 改支付主流程**（还要改 Job、对账、退款）；
2. **渠道状态码泄漏进状态机**（渠道改语义时全库搜着改）；
3. **没法测**（单测要么连真渠道，要么 mock 一堆 SDK 类）。

契约层做两个收口：

| 收口 | 内容 | 本质 |
|---|---|---|
| **交互面** | 和渠道只打 5 件交道（§2） | 变化点隔离（策略模式） |
| **语义面** | 渠道四态 → **三值**（§3） | 防腐/语义归一 |

> 所以严格说：**契约层 = 策略模式（出站）+ 防腐层（入站与翻译）**。
> 判断有没有契约层，不看有没有接口，看**业务层有没有出现渠道的状态码/字段名**。

## 2. 五件事（最小完备集）

| # | 契约 | 方向 | 没有它会怎样 |
|---|---|---|---|
| 1 | **创建** `tradeCreate` | 出站 | 渠道不知道这笔交易，收不了钱 |
| 2 | **查单** `tradeQuery` | 出站 | 通知丢了就永远不知道结果（通知会丢，查单不会） |
| 3 | **关单** `tradeClose` | 出站 | 换渠道/超时时渠道交易悬挂，可能被支付 |
| 4 | **退款** `tradeRefund` | 出站 | 出不了金 |
| 5 | **通知** `notify` 端点 | **入站** | 渠道推结果，你收不到/不会答 |

**为什么恰好五件**：这是让状态机可靠收敛的最小完备集——创建让钱能进，通知告诉你结果，
查单兜住通知丢失，关单防悬挂，退款能出。少一件，状态机就有一个"永远无法收敛"的分支。

注意第 5 件**不是策略接口的方法**：方向反了（渠道调我们），所以它落在
`AlipayNotifyController`，由控制器收口（验签/二次校验/ACK——细节见 02）。

## 3. 三值：1 / 0 / 不可判定

```
渠道四态                          契约三值（业务只认这个）
WAIT_BUYER_PAY   ─┐
TRADE_CLOSED     ─┴──────────────▶ 0   未付
TRADE_SUCCESS    ─┐
TRADE_FINISHED   ─┴──────────────▶ 1   已付
查单不可达/异常   ────────────────▶ null 不可判定
```

**为什么必须保留 `null`**（最容易被写错的地方）：

- 查单超时/网络异常时，渠道真实状态是"**不知道**"；
- 若把"不知道"映射成 `0`，超时 Job 就会置失败、关单——**而用户其实已付钱**（资损级 bug）；
- 契约规定：`null = 不可达/不可判定，绝不据此置失败`，调用方只能"本轮不处置，留给下一轮/对账"。

面试一句话：**"不知道 ≠ 没付"——渠道不可达必须显式表达为不可判定，不能折叠成未付。**

## 4. 代码：契约长什么样

```java
package com.myxhs.payment.strategy;

import com.myxhs.payment.alipay.RefundTradeResult;

import java.math.BigDecimal;

/**
 * 支付渠道策略接口
 * <p>
 * 策略模式：每种支付方式实现此接口，通过 {@link com.myxhs.payment.config.PayStrategyConfig}
 * 注册到 Map 中，由 {@link com.myxhs.payment.service.PaymentService} 按支付类型选择。
 * </p>
 * <p>
 * 渠道契约（C-003）：
 * <ul>
 *   <li>发起支付：异步渠道（支付宝）创建交易后由渠道通知驱动状态推进；Mock 为同步成功</li>
 *   <li>退款：<b>同步返回结果</b>（支付宝真实契约）——成功/失败由返回值表达，不再有退款回调</li>
 *   <li>查单：渠道事实来源（"不知道"≠"没付"：不可达返回 null）</li>
 *   <li>关单：抛异常 = 渠道未确认关闭（调用方按"先查后决"处理）</li>
 * </ul>
 * </p>
 */
public interface PayChannelStrategy {

    /**
     * 发起支付。
     *
     * @param orderId   订单 ID
     * @param amount    支付金额
     * @param paymentNo 支付流水号（= 渠道侧商户订单号 out_trade_no）
     * @return 渠道交易号（异步通知中回传）；Mock 模式返回 paymentNo
     */
    String pay(Long orderId, BigDecimal amount, String paymentNo);

    /**
     * 退款（<b>同步返回</b>）。
     * <p>
     * 支付宝真实契约：调用即得结果（fund_change）。失败重试必须携带同一个
     * {@code outRequestNo}（"同号只退一次"）。调用抛异常 = 结果未知——
     * 上层绝不当作失败（事务回滚后由调用方同键重试，渠道幂等兜底）。
     * </p>
     *
     * @param paymentNo    支付流水号（= 渠道侧 out_trade_no）
     * @param outRequestNo 退款请求号（渠道幂等键：优先业务键 outRefundNo，缺省用 refundNo）
     * @param refundAmount 退款金额
     * @param reason       退款原因
     * @return 同步退款结果（fundChange=true 表示退款成功）
     */
    RefundTradeResult refund(String paymentNo, String outRequestNo, BigDecimal refundAmount, String reason);

    /**
     * 构建客户端拉起支付所需参数（C-016）。
     * <p>
     * 真实契约：支付宝 APP 支付返回 {@code alipay.trade.app.pay} 的 orderStr（本地用应用私钥签名，
     * 客户端直接交给支付宝 SDK）；Mock 返回等价载荷（JSON）。
     * 复用既有支付单时同样重建（orderStr 带 timestamp，时间敏感——不能长期缓存）。
     * </p>
     *
     * @param orderId   订单 ID
     * @param amount    支付金额
     * @param paymentNo 支付流水号（= 渠道侧 out_trade_no）
     * @return 支付参数；null=该渠道不需要（如零元单）
     */
    default String buildPayParams(Long orderId, BigDecimal amount, String paymentNo) {
        return null;
    }

    /**
     * 查询支付状态（补偿/对账/超时处置/换渠道"先查"）。
     *
     * @param paymentNo 支付流水号
     * @return 0=渠道确认未支付 1=渠道已支付；{@code null}=不可达/不可判定（绝不据此置失败）
     */
    Integer queryPayStatus(String paymentNo);

    /**
     * 关闭渠道交易（换渠道关旧 / 超时处置 / 订单终结）。
     * <p>
     * 语义约定：调用方负责本地状态推进；本方法抛异常表示"渠道未确认关闭"——
     * 换渠道场景应中止切换（先查后决：复查渠道真相后决定受理或报错）。
     * </p>
     *
     * @param paymentNo 支付流水号
     */
    void close(String paymentNo);
}
```

支付宝实现是**薄适配**（唯一职责：四态 → 三值）：

```java
package com.myxhs.payment.strategy.impl;

import com.myxhs.payment.alipay.AlipayTradeClient;
import com.myxhs.payment.alipay.AlipayTradeQueryResult;
import com.myxhs.payment.alipay.RefundTradeResult;
import com.myxhs.payment.strategy.PayChannelStrategy;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;

import java.math.BigDecimal;

/**
 * 支付宝支付策略（渠道契约对齐 · C-003）
 * <p>
 * 本策略是<b>契约层之上</b>的薄适配：全部渠道交互委托 {@link AlipayTradeClient}
 * （真实场景 = 官方 SDK 封装；本地 = 模拟支付宝服务器 + 真实签名验签）。
 * </p>
 * <p>
 * 状态映射（四态 → 三值契约）：
 * <ul>
 *   <li>WAIT_BUYER_PAY → 0（未付）</li>
 *   <li>TRADE_SUCCESS / TRADE_FINISHED → 1（已付）</li>
 *   <li>TRADE_CLOSED → 0（对"本地 pending"单 = 未付款超时关闭；全退后关闭不可能出现在 pending 单）</li>
 *   <li>不可达/不可判定 → null（"不知道"≠"没付"）</li>
 * </ul>
 * </p>
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class AlipayPayStrategy implements PayChannelStrategy {

    private final AlipayTradeClient alipayTradeClient;

    @Override
    public String pay(Long orderId, BigDecimal amount, String paymentNo) {
        String tradeNo = alipayTradeClient.tradeCreate(orderId, amount, "订单支付", paymentNo);
        log.info("[支付宝] 发起支付: orderId={}, amount={}, paymentNo={}, tradeNo={}",
                orderId, amount, paymentNo, tradeNo);
        return tradeNo;
    }

    @Override
    public String buildPayParams(Long orderId, BigDecimal amount, String paymentNo) {
        // C-016：客户端拉起支付参数（alipay.trade.app.pay orderStr，本地应用私钥签名）
        return alipayTradeClient.buildAppPayOrderStr(orderId, amount, "订单支付", paymentNo);
    }

    @Override
    public RefundTradeResult refund(String paymentNo, String outRequestNo, BigDecimal refundAmount, String reason) {
        RefundTradeResult result = alipayTradeClient.tradeRefund(paymentNo, outRequestNo, refundAmount, reason);
        log.info("[支付宝] 同步退款: paymentNo={}, outRequestNo={}, fundChange={}, errorCode={}",
                paymentNo, outRequestNo, result.isFundChange(), result.getErrorCode());
        return result;
    }

    @Override
    public Integer queryPayStatus(String paymentNo) {
        AlipayTradeQueryResult result = alipayTradeClient.tradeQuery(paymentNo);
        if (result == null || result.getStatus() == null) {
            log.warn("[支付宝] 查单不可达/不可判定: paymentNo={}", paymentNo);
            return null;
        }
        Integer mapped = switch (result.getStatus()) {
            case TRADE_SUCCESS, TRADE_FINISHED -> 1;
            case WAIT_BUYER_PAY, TRADE_CLOSED -> 0;
        };
        log.info("[支付宝] 查单: paymentNo={}, tradeStatus={} → {}", paymentNo, result.getStatus(), mapped);
        return mapped;
    }

    @Override
    public void close(String paymentNo) {
        boolean closed = alipayTradeClient.tradeClose(paymentNo);
        if (!closed) {
            // 已支付交易不可关闭（官方 ACQ.TRADE_HAS_SUCCESS）→ 抛异常让调用方"先查后决"
            throw new IllegalStateException("渠道交易不可关闭（已支付或状态异常）: " + paymentNo);
        }
        log.info("[支付宝] 关闭渠道交易: paymentNo={}", paymentNo);
    }
}
```

```java
/** 查渠道（异常按"不可达"处理返回 null——"不知道"≠"没付"，绝不据此推进状态） */
private Integer queryChannelSafely(PayChannelStrategy strategy, String paymentNo) {
    try {
        return strategy.queryPayStatus(paymentNo);
    } catch (Exception e) {
        log.warn("[支付] 查渠道异常（按不可达处理）: paymentNo={}", paymentNo, e);
        return null;
    }
}
```

## 5. 三个坑（面试加分）

1. **不能用渠道方法名做契约**：接口里写 `alipayTradeCreate()` 就白抽象了——方法名必须是业务语言。
2. **返回值语义必须写进契约**：`null=不可判定`、`close 抛异常=未确认`、`refund 异常=结果未知≠失败`——不写清楚，每个调用方都会自己发明一套。
3. **契约会抹平渠道能力差异**：同步 vs 异步（支付宝异步通知、Mock 同步成功）、部分退款、免密支付——
   本项目的 `isMockMode(payType)` 就是"同步/异步差异"漏进 `PaymentService` 的痕迹；
   真实多渠道应把 capabilities 放进策略，而不是业务里判断（诚实的设计缺陷，可主动说改进方向）。

## 6. 后文指针 + 一句话

- 通知三必答（二次校验 / ACK·幂等 / TRADE_CLOSED 双语义）→ **02 支付回调与订单咬合**；
- 先查后决（换渠道防双付）→ **06 分布式专题**；
- 签名：RSA2 验签挡伪造；验签≠业务可信；必须原样参数——细节不展开。

**一句话**：契约层 = **把渠道差异收进实现类，把"不确定"显式化成 `null`**——业务只看到 1/0/不知道。

**面试口径**："支付域只依赖渠道契约层：创建/查单/关单/退款/通知五件事 + 三值状态；渠道不可达显式返回不可判定、绝不当未付；换渠道只换实现。"
