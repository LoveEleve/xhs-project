## 0. 场景：一笔 199 元的支付，卡在哪

**角色**：用户小王、商户系统（本项目）、支付宝。**三个单号**（记住用途即可）：

| 单号 | 谁生成 | 作用 |
|---|---|---|
| `out_trade_no`（= paymentNo，PAY 前缀） | **商户** | **支付单号**（不是订单号）；查单/关单/退款/通知都拿它找渠道 |
| `trade_no` | **支付宝** | 渠道交易号（对账/排查用） |
| `notify_id` | **支付宝** | 一条通知的 ID；重试时不变 |

> 一个订单可有多条支付单（换渠道/超时重建/并发复用），所以渠道商户单号标识的是"**一次支付尝试**"。

**第一幕：正常流程（建立模型）**

```
① 小王点"去支付"（订单 O1001，199.00 元）
② 商户：tradeCreate 登记渠道交易 → 得 trade_no；本地生成 app.pay orderStr（应用私钥签名）= payParams
   → /pay 返回 PaymentVO{paymentNo, tradeNo, payParams} 给客户端
   → 客户端把 payParams 交给支付宝 SDK 拉起收银台
③ 小王付款 → 支付宝记 TRADE_SUCCESS，并向商户异步通知
④ 商户 notify 端点：验签 → 二次校验 → 支付单 0→1 → 明文 ACK "success"
⑤ 支付成功之后：通知订单（Feign→MQ→补偿→对账，见 02）——本篇不展开
```

**第二幕：三个"如果"（本篇要解决的）**

| 如果…… | 后果 | 机制 | 在哪节 |
|---|---|---|---|
| 不二次校验 | 合法渠道的**错单/错金额/错商户**被当成自己的单 | 四查 | §2.1 |
| 不 ACK / ACK 错 | 渠道一直重试（重复）；或一次抖动丢通知 | 明文 `success` + 重试 | §2.2 |
| 重复通知 | 同一笔成功被处理两次 | 状态守卫幂等 | §2.2 |
| （衍生）关闭语义 | 关闭态与成功态互相覆盖 | 按本地状态分流 | §2.3 |
| （衍生）换渠道 | 旧单其实已付，又开新单=双付 | 先查后决 | §3 |

> 伪造由验签解决——**必要，但只值一句话**（§4）。

## 1. 契约层是什么：业务只认"三值"

对一个商户，和支付宝的全部交互只有 **五件事**（`AlipayTradeClient`）：

| # | 契约 | 用途 | 备注 |
|---|---|---|---|
| 1 | `tradeCreate` | 创建渠道交易 | 返回 `trade_no` |
| 2 | `tradeQuery` | 查单（通知的"双保险"） | `null`=不可达（"不知道"≠"没付"） |
| 3 | `tradeClose` | 关单（换渠道/超时/终结） | 已支付不可关（官方返回错误） |
| 4 | `tradeRefund` | 退款 | **同步返回**（`fund_change`），无退款回调 |
| 5 | `verifyNotify` | 异步通知验签 | 一句话，见 §4 |

**为什么隔离**（3 个理由，面试就讲这个）：

1. **换渠道只换实现**：业务只依赖 `PayChannelStrategy`，`AlipayPayStrategy` 是薄适配；接真支付宝 = 换 `AlipayTradeClient` 实现 + 密钥/网关；
2. **状态机只认三个值**：渠道四态在策略层映射为 `1 已付 / 0 未付 / null 不可判定`——**渠道不可达绝不能置失败**；
3. **可测试**：本地模拟服务器用**真实签名/验签**对打——单测测的是契约形态，不是假桩。

```
PaymentService → PayChannelStrategy → AlipayTradeClient → 模拟支付宝（真签名验签）
                                    ↑ 请求用应用私钥签
模拟支付宝 ── HTTP POST form（支付宝私钥签）──▶ /api/payment/notify/alipay（支付宝公钥验）
```

> 两对密钥的方向性（理解即可）：**应用私钥**签请求、**支付宝公钥**验通知。

## 2. 通知处理的三个必答题（核心）

### 2.1 二次校验——验签通过 ≠ 业务可信

验签只证明"消息来自支付宝"，不证明"这条消息是给你的这笔单"。所以处理前**四查**：

1. `trade_status` 可解析（未知/空 → 不可判定，不猜）；
2. `out_trade_no` 能查到支付单；
3. `total_amount` 与本地金额**一致**（不用 `==` 比较金额）；
4. `app_id`/`seller_id` 与配置一致。

任一不过 = 异常通知：**应答 fail + 告警，绝不处理**（不是"跳过继续"）。

### 2.2 明文 ACK 与幂等——重复通知的消化

- **ACK 是明文 `success`（7 字符），不是 JSON**——官方要求应答体精确匹配；
- 应答 `fail`（验签失败/二次校验失败/处理异常）→ **渠道按节奏重试**；`notify_id` 重试时不变；
- 超限放弃 → 记账 undelivered → **查单/对账兜底**（通知会丢，查单不会）；
- **重复通知不靠去重表**：靠状态守卫（`WHERE status=0` 条件 UPDATE）——重复通知影响行数=0，应答 success、不重复处置。

> 一句话：**ACK 是重试开关，幂等是状态守卫**——两者合起来才叫"通知可靠"。

### 2.3 TRADE_CLOSED 双语义——同一状态码，语义取决于本地状态

```
WAIT_BUYER_PAY  等待付款      → 忽略
TRADE_SUCCESS   支付成功      → 成功链路
TRADE_FINISHED  交易结束不可退 → 本地无此概念，按成功映射（注释记录）
TRADE_CLOSED    交易关闭      → 双语义：
    本地待支付       = 未付款超时关闭 → 置失败
    本地已成功/已退款 = 全额退款导致的关闭 → 状态守卫命中（幂等 no-op），绝不能置失败
```

> 面试点：**渠道状态码的语义不是自明的，要按本地状态机当前位置分流。**

## 3. 换渠道：先查后决（衍生，但防的是资损）

官方指引：**已支付的交易不可关闭**。所以换渠道不能直接关旧单：

```
换渠道 = 先 query 前一个交易：
  已支付   → 受理收敛（不新建、不重发——否则双付）
  未支付   → close 旧交易 → 旧单置"已关闭" → 新建新渠道支付单
  不可达   → 不切换（"不知道"≠"没付"，稍后重试）
```

## 4. 签名：一句话（边缘）

**RSA2 验签（支付宝公钥）挡住伪造。** 只记三个边界：
① 验签≠业务可信（所以有 §2.1）；② 必须用**原样参数**验签（解析后重建必错）；③ 方向性：应用私钥签请求、支付宝公钥验通知。
规则细节（剔除 sign/sign_type/空值、字典序、URL 编码）照文档实现，不值得展开。

## 5. 边界：模拟器 ≠ 真渠道（3 行）

- 模拟服务器 = 台账 + 验商户签名 + 签通知并 HTTP 投递（未 ACK 按节奏重试）——**契约形态保真，出金是假的**；
- 接真渠道只改两处：`AlipayTradeClient` 实现换官方 SDK 封装 + 密钥/网关地址；策略、状态机、通知端点零改动；
- 本项目**只有一个渠道支付回调端点**（`/api/payment/notify/alipay`）；`callback/{payType}` 是测试触发口，不是渠道；**退款同步返回、无回调**。

## 6. 值不值得深挖 / 面试口径

- **值得讲透**：二次校验（验签≠业务可信）、ACK/幂等（重复通知的消化）、TRADE_CLOSED 双语义、先查后决；
- **一句话带过**：RSA2 验签（方向性/原样参数/只管来源可信）；
- **一句话**：契约层 = **把渠道的不可信协议挡在状态机之外**——业务永远只看到"1/0/不可判定"。

**简历/面试口径**："渠道契约层：RSA2 验签 + 二次校验 + 明文 ACK/重试 + 状态守卫幂等，换渠道先查后决防双付。"
细节等对方追问再展开。
