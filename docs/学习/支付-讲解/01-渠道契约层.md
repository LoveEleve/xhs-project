# 01 · 渠道契约层（支付宝）

> 本篇解决：**渠道的"不可信协议"怎么挡在状态机外面**。覆盖：契约五件事、两对密钥、RSA2 验签规则、
> 二次校验、trade_status 四态（含双语义）、明文 ACK 与通知重试、先查后决、模拟服务器与接真渠道的边界。
> 前置：`00-应然模型与学习路线.md`。证据：`alipay/` 包、`controller/AlipayNotifyController`、`simulator/`、C-003。

---

## 0. 场景：一笔 199 元的支付，卡在哪

**角色**：用户小王、商户系统（本项目）、支付宝。**单号先记住三个**：

| 单号 | 谁生成 | 作用 |
|---|---|---|
| `out_trade_no`（= paymentNo） | **商户** | 商户侧这笔支付的唯一标识；查单/关单/退款都拿它找渠道 |
| `trade_no` | **支付宝** | 渠道侧这笔交易号；对账/排查用 |
| `notify_id` | **支付宝** | 一条通知的 ID；**重试时不变**（可识别"同一条通知又来了"） |

> 注意：`out_trade_no` 是**支付单号**（paymentNo，PAY 前缀），**不是订单号**（O1001）——
> 一个订单可以有多条支付单（换渠道/超时重建/并发建单复用），渠道侧商户单号必须标识"一次支付尝试"；
> 若用订单号，换渠道时同号不同金额会撞单。payment 模块内部只持有 `orderId`，不持有 orderNo。

**第一幕：正常流程（先建立模型）**

```
① 小王在订单页点"去支付"（订单号 O1001，199.00 元）
② 商户：两件事——
   a) alipay.trade.create（out_trade_no=P2026..., total_amount=199.00）→ 支付宝只返回 trade_no（渠道交易号）
   b) 本地生成 alipay.trade.app.pay orderStr（应用私钥签名，C-016）→ 作为 payParams
   → /pay 响应 PaymentVO{paymentNo, tradeNo, payParams} 给客户端
   → 客户端把 payParams 交给支付宝 SDK 拉起收银台（小王扫码/跳转）
③ 小王付款 199.00 → 支付宝记 TRADE_SUCCESS（并由支付宝发起异步通知）
④ 支付宝 → 商户 POST /api/payment/notify/alipay（form：out_trade_no / trade_no / trade_status / total_amount / sign...）
   商户：验签 → 二次校验 → 本地支付单 status 0→1 → ACK "success"
⑤ 支付结果通知订单（Feign→MQ→补偿→对账，见 02）→ 订单变"已支付"
```

**第二幕：三个"如果"（这就是契约层存在的理由）**

| 如果…… | 后果 | 谁来解决 | 在哪节 |
|---|---|---|---|
| **不验签** | 任何人构造一条 form 就能"伪造支付成功"——钱没到，货发了 | RSA2 验签（支付宝公钥） | §3.5 |
| **不二次校验** | 合法渠道的**错单号/错金额/错商户**通知被当成自己的单 | 四查（存在/金额/商户/状态） | §3.1 |
| **不 ACK / ACK 错** | 渠道一直重试（重复通知）；或一次网络抖动就丢通知 | 明文 `success` + 重试 + 查单兜底 | §3.2 |
| 衍生：**重复通知** | 同一笔成功被处理两次 | 状态守卫（`WHERE status=0`）幂等 | §3.2 |
| 衍生：**乱序/双语义** | 关闭态与成功态互相覆盖 | 四态分流 + 本地状态判语义 | §3.3 |
| 衍生：**双付** | 换渠道时旧单其实已支付，又开了新单 | **先查后决** | §3.4 |

**第三幕：落点**

所以渠道层不是一个"调接口的工具"，而是**一道协议防火墙**：
商户和支付宝之间只有**五件事**（创建/查单/关单/退款/验签）+ **一条应答**（ACK），
渠道的所有"不可信、不完整、会重试、有歧义"都在这一层被收敛成业务能用的**三个值：1 已付 / 0 未付 / 不可判定**。

## 1. 镜头拉近：一条支付宝通知的一生

支付宝服务器给商户 `notify_url` 发 **form 表单**（POST，不是 JSON）：

```
POST /api/payment/notify/alipay        Content-Type: application/x-www-form-urlencoded
notify_id=2026101900001&notify_type=trade_status_sync&notify_time=2026-10-19 10:21:00
&out_trade_no=P2026101910000001     ← 商户订单号（本项目 = paymentNo）
&trade_no=2026101922001100001       ← 支付宝交易号
&trade_status=TRADE_SUCCESS
&total_amount=199.00&app_id=2021000000000001&seller_id=2088000000000001
&sign=<RSA2 Base64>&sign_type=RSA2
```

商户端点 `AlipayNotifyController.doNotify` 做四步（顺序即安全）：

```java
// ① 验签（RSA2 + 支付宝公钥）——验签失败 = 伪造/配置错误 → 应答 fail，不处理
if (!alipayTradeClient.verifyNotify(params)) return ACK_FAIL;

// ② 二次校验：状态可解析 → 支付单存在 → 金额一致 → 商户一致（app_id / seller_id）
AlipayTradeStatus status = notify.status();          // 未知/空 → null（不可判定）
Payment payment = paymentService.findPaymentByNo(notify.getOutTradeNo());
if (!amountMatches(payment, notify.getTotalAmount())) return ACK_FAIL;

// ③ 四态分流
switch (status) {
  case TRADE_SUCCESS, TRADE_FINISHED -> paymentService.handlePayCallback(no, tradeNo, true);
  case TRADE_CLOSED -> paymentService.handlePayCallback(no, tradeNo, false); // 双语义，见 §3.3
  case WAIT_BUYER_PAY -> log.info("等待付款态，忽略");
}
// ④ 明文应答 "success"（7 字符）→ 渠道停止重试；其他 → 渠道按节奏重试
return ACK_SUCCESS;
```

**这一条通知里藏着三个"如果不"**（第二幕的落点）：不验签 → 伪造支付；不二次校验 → 错单；不 ACK → 重复/丢失。

> 术语：**二次校验** = 验签之后、处理之前的本地核对（单号能不能查到、金额对不对、商户对不对、状态能不能解析）——
> 验签只证明"消息来自支付宝"，二次校验才证明"这条消息是给你的这笔单"。

## 2. 为什么需要它：契约层是什么

对一个商户来说，和支付宝的全部交互只有 **五件事**（`AlipayTradeClient`）：

```java
public interface AlipayTradeClient {
    String tradeCreate(Long orderId, BigDecimal amount, String subject, String outTradeNo); // alipay.trade.create
    AlipayTradeQueryResult tradeQuery(String outTradeNo);       // alipay.trade.query（null=渠道不可达）
    boolean tradeClose(String outTradeNo);                      // alipay.trade.close
    RefundTradeResult tradeRefund(String outTradeNo, String outRequestNo,
                                  BigDecimal amount, String reason); // alipay.trade.refund（同步返回）
    boolean verifyNotify(Map<String, String> params);           // 异步通知验签（RSA2）
}
```

**为什么隔离成契约层**（而不是让 `PaymentService` 直接调 SDK）：

| 理由 | 具体表现 |
|---|---|
| 换渠道只换实现 | 业务只依赖 `PayChannelStrategy`（pay/refund/queryPayStatus/close），`AlipayPayStrategy` 是**薄适配**——全部委托 `AlipayTradeClient`；接真实支付宝 = 换这个接口的实现 + 密钥/网关 |
| 状态机只认三值 | 渠道的四态（含不可判定）在策略层映射为 **1 已付 / 0 未付 / null 不可判定**——"不知道 ≠ 没付"（渠道不可达绝不能置失败） |
| 可测试 | 本地 `SimulatedAlipayServer` 用**真实 RSA2 签名/验签**对打——单测测的是"契约形态"，不是假桩 |

**两对密钥**（与真实世界一致，`AlipayMockProperties`）：
- **应用密钥对**：商户用应用私钥签**请求** → 模拟服务器用应用公钥验请求；
- **支付宝密钥对**：模拟服务器用支付宝私钥签**通知** → 商户端点用支付宝公钥验通知。

```
PaymentService → PayChannelStrategy(AlipayPayStrategy) → AlipayTradeClient(Impl) → SimulatedAlipayServer
                                                                       ↑ 请求带应用私钥签名
支付宝服务器（模拟） ── HTTP POST form（支付宝私钥签名）──► /api/payment/notify/alipay（支付宝公钥验签）
```

## 3. 怎么做：核心 2 + 衍生 2 + 边缘 1

> 二次校验与 ACK/幂等是必须讲透的两件；双语义与先查后决是面试加分项；
> 验签是必要实现，但只值"一句话 + 边界含义"。

### 3.1 二次校验——验签通过 ≠ 业务可信（核心 1）

验签只证明"消息来自支付宝"，不证明"这条消息是给你的这笔单"。所以还要四查：
**支付单存在**（out_trade_no 能查到）→ **金额一致**（`total_amount` vs 本地 `amount`）→ **商户一致**（`app_id`/`seller_id`）。
任一不过 = 异常通知：**应答 fail + 告警，绝不处理**（不是"跳过继续"）。


### 3.2 明文 ACK 与幂等——重复通知的消化（核心 2）

- **ACK 是明文 `success`（7 字符），不是 JSON**——官方要求应答体精确匹配；
- 应答 `fail`（验签失败/二次校验失败/处理异常）→ **渠道按节奏重试**；`notify_id` 重试时**不变**；
- 重试节奏（本地模拟简化版）：`5s/15s/60s`，上限 **8 次**；超限放弃 → 记账 `undelivered` → **查单/对账兜底**（通知会丢，查单不会）；
- **幂等不靠"去重表"**：重复通知由 `handlePayCallback` 的 `WHERE status=0` 状态守卫消化——重复通知应答 success、不重复处置。


### 3.3 trade_status 四态——TRADE_CLOSED 是双语义（衍生 1）

```
WAIT_BUYER_PAY  等待付款      → 忽略（只记录）
TRADE_SUCCESS   支付成功      → 成功链路
TRADE_FINISHED  交易结束不可退 → 本地无"不可退款"概念，按成功映射（差异注释记录）
TRADE_CLOSED    交易关闭      → 双语义！
```

`TRADE_CLOSED` 的双语义必须**按本地状态分流**（`AlipayNotifyController` 的注释与实现）：
- 本地**待支付**单收到 = 未付款超时关闭 → 置失败（渠道确认关闭）；
- 本地**已成功/已退款**单收到 = 支付完成后**全额退款**导致的关闭 → 状态守卫命中（CAS no-op）——**幂等收敛，不误置失败**。

> 面试点：这就是"同一个渠道状态码，语义取决于本地状态机当前位置"的典型样本。


### 3.4 先查后决——关单/换渠道前的"契约安全"（衍生 2）

官方指引：**已支付的交易不可关闭**（返回 `ACQ.TRADE_HAS_SUCCESS`）。所以"换渠道"不能直接关旧单：

```
换渠道 = 先 query 前一个交易：
  已支付   → 受理收敛（旧单继续走成功链路，不能重发新单——否则双付）
  未支付   → close 旧交易 → 旧单置"已关闭" → 新建新渠道支付单
  不可达   → 不切换（"不知道"≠"没付"，回头再查）
```

对应代码：`AlipayPayStrategy.close` 在渠道拒绝关闭时**抛异常**，让 `PaymentService` 走"先查后决"分支
（`PaymentService` 的换渠道分支：查 tradeQuery → 已支付=受理收敛 / 未支付=close 后新开 / 不可达=不切换）。


### 3.5 验签（RSA2）——必要，但不是讨论点（边缘）

> 面试一句话：**RSA2 验签（支付宝公钥）挡住伪造**。规则细节（剔除 sign/sign_type 与空值、ASCII 排序、
> URL 编码）属于"照官方文档实现"，不值得展开；真正值得讨论的是它的**边界**——
> ① 验签通过 ≠ 业务可信（所以有 §3.1 二次校验）；② 必须用**原样参数**验签（解析后重建必错）；
> ③ 方向性：商户请求用**应用私钥**签、渠道通知用**支付宝公钥**验。

官方规则：剔除 `sign` 与 `sign_type`、**剔除空值参数**、参数名 **ASCII 字典序**、拼成 `k1=v1&k2=v2`，
再 `SHA256withRSA` → 标准 Base64：

```java
public static String buildSignContent(Map<String, String> params) {
    if (params == null || params.isEmpty()) {
        return "";
    }
    // TreeMap 天然字典序（ASCII 码排序）
    TreeMap<String, String> sorted = new TreeMap<>();
    for (Map.Entry<String, String> entry : params.entrySet()) {
        String key = entry.getKey();
        String value = entry.getValue();
        if (key == null || key.isEmpty()) {
            continue;
        }
        if ("sign".equals(key) || "sign_type".equals(key)) {   // 两者都不参与签名
            continue;
        }
        if (value == null || value.isEmpty()) {                // 空值不参与签名
            continue;
        }
        sorted.put(key, value);
    }
    StringBuilder content = new StringBuilder();
    for (Map.Entry<String, String> entry : sorted.entrySet()) {
        if (content.length() > 0) {
            content.append('&');
        }
        content.append(entry.getKey()).append('=').append(entry.getValue());
    }
    return content.toString();
}
// 之后：Signature.getInstance("SHA256withRSA") → Base64
```

两个容易错的点：
- **必须用原样参数验签**（`AlipayNotifyParams.raw`）——不能"解析成模型后再重建参数"，顺序/空值/编码一变签名就不对；
- 验签的**任何异常都返回 false**（缺 sign / Base64 非法 / 密钥非法）——验签失败就是"不可信"，不抛错到业务层。


## 4. 模拟服务器与"接真渠道要改什么"

`SimulatedAlipayServer` 扮演支付宝侧：
- **台账**（`MockAlipayTradeRepository`）：`alipay.trade.create` 同 `out_trade_no` 幂等返回既有交易；
- **验商户签名**（应用公钥）——请求方向的契约安全；
- **通知生成 + 投递**：`AlipayNotifySender` 以 form POST 真实投递到 `notifyUrl`（连/读超时 2s/5s，透传 X-Trace-Id），
  读到明文 `success` 才算送达；未送达按 `5s/15s/60s` 重试（`notify_id` 不变），上限 8 次；
- **退款幂等**：同一 `out_request_no` 命中幂等返回既有结果——"**同号只退一次**"优先于台账记账（崩溃重试不重复出金）；
- 测试参数已配置化（成功率/延迟/重试节奏都在 `AlipayMockProperties`，不再是硬编码常量）。

**返回给客户端的支付参数（C-016，原来漏了）**：`/api/payment/pay` 的响应（`PaymentVO`）现在带
`tradeNo`（渠道交易号，已落 `t_payment.trade_no`）+ `payParams`——
支付宝 = **`alipay.trade.app.pay` 的 orderStr**（本地应用私钥签名 + URL 编码，客户端直接交给支付宝 SDK 拉起收银台）；
Mock = 等价 JSON 载荷。复用支付单/状态查询时**重建**参数（orderStr 带 timestamp，不能缓存）。
> 教训：渠道交易号只打日志等于"创建了交易却把凭据扔了"——契约对齐不只看入参，也要看**出参**。

**接真实支付宝时只改两处**：`AlipayTradeClient` 的实现换成官方 SDK 封装（trade.create/query/close/refund）、
密钥与网关地址换成真实值。**策略、PaymentService、通知端点、状态机零改动**——这就是契约层的意义。

> **回调端点全景**（别把三类"回调"混了）：
> - **渠道 → 支付域**：`POST /api/payment/notify/alipay`（form，验签即鉴权）——**唯一的渠道支付回调**，内部按 `trade_status` 四态分流；
> - **测试触发口**（不是渠道）：`POST /api/payment/callback/{payType}`（X-Internal-Call）——payType=1 时触发模拟服务器发**真实签名通知**（走上面端点全链路），payType=99 直接走 Mock 同步；
> - **支付域 → 订单域**（商户内部）：Feign `notifyPaySuccess/pay-fail` + MQ `PAY_RESULT_TOPIC`（见 02）。
> - **退款没有异步回调**：C-003 对齐 `alipay.trade.refund` 同步返回（`fund_change`），旧的 `refund-callback` 已删除；
>   接新渠道（如微信）时每个渠道需要自己的 notify 端点。

## 5. 值不值得深挖

**值得讲透**（面试高频、接渠道必踩）：**二次校验**（验签≠业务可信）与 **ACK/幂等**（重复通知的消化）；
**加分项**：TRADE_CLOSED 双语义（状态码语义取决于本地状态）、先查后决（换渠道防双付）。
**一句话带过**：RSA2 验签（方向性/原样参数/只管"来源可信"）。
**一句话**：契约层的价值 = **把渠道的不可信协议挡在状态机之外**——业务永远只看到"1/0/不可判定"三个值。

**追问链**：验签失败怎么处理（fail+告警不处理）→ 重复通知（状态守卫幂等，ACK success）→
通知丢失（查单/对账兜底）→ 异步通知 vs 查单谁为准（查单是事实源，通知是加速）→
渠道不可达（不切换、不置失败，"不知道≠没付"）。

**危险信号**：不验签就进状态机；用 `==` 比较金额；把 `TRADE_CLOSED` 一律当失败；
换渠道直接 close 不看是否已支付；把 `fail` 应答当"处理完成"。
