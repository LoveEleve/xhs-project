# 02 · 支付回调与订单咬合

> **一句话**：支付域只回答"钱到没到"，订单域只回答"订单能不能要这笔钱"；
> 支付成功之后，让订单**一定知道**，并且**只成功一次**。
>
> **本篇带走 4 条**：① 通知进来先过三关（二次校验 / ACK / 四态双语义）
> ② 支付单状态机：成功只有一次，迟到成功要翻转
> ③ 四层通知：Feign 主 → MQ 备 → Job 兜底 → 对账终线
> ④ 三种"不成功"的语义：超时 ≠ 失败、503 ≠ 拒绝、**业务拒绝 ≠ 通知失败**
>
> 前置：`01-渠道契约层.md`（三值/不可判定）。证据：`AlipayNotifyController`、`PaymentService`、
> `PaymentNotifyCompensateJob`、order 侧 `notifyPaySuccess`/`PayResultConsumer`。

---

## 0. 场景：同一个"支付成功"，三种命运

**正常线**：

```
支付宝通知 → 支付单 0→1 → Feign 通知订单 → 订单 0→1（待付款→已支付）→ 发 MQ（备）
```

**但下面三件事在生产里天天发生**：

| 场景 | 现象 | 本篇的答案 | 在哪节 |
|---|---|---|---|
| **Feign 超时** | 订单其实已置成功，支付域却收到超时异常 | 超时=结果未知，不能判死；MQ 备 + Job 兜底（幂等） | §3 |
| **订单已取消，钱到了** | 用户付钱时订单刚好被取消/关单 | 订单返回**业务失败**（非 503）→ 支付域**自动全额退款** | §4 |
| **同一条通知来了三次** | 支付宝没收到 ACK，按节奏重试 | 状态守卫（`WHERE status=0`）影响行数=0 → 应答 success | §1.2 / §2 |

> 记住一句话：**支付成功 ≠ 订单成功**。支付域证明"钱到了"，订单域裁决"这笔钱要不要"。

## 1. 通知进来先过三关

### 1.1 二次校验——验签通过 ≠ 业务可信

验签只证明"来自支付宝"；还要四查：`trade_status` 可解析、`out_trade_no` 能查到支付单、`total_amount` 与本地一致、`app_id`/`seller_id` 与配置一致。任一不过 = **应答 fail + 告警，不处理**。

### 1.2 ACK——渠道重试的开关

- 成功处理：应答**明文 `success`**（7 字符，不是 JSON）；
- 验签失败/校验失败/处理异常：应答 `fail` → 渠道按节奏重试；
- 重复通知：状态守卫命中后**仍然应答 `success`**（已处理 = 成功，不再重试）；
- 渠道最终放弃也没关系：通知会丢，**查单/对账不会**（§3 第四层）。

> ACK 只回答"这条通知我收下了没有"，不回答"业务办成了没有"。

### 1.3 四态与 TRADE_CLOSED 双语义

```
WAIT_BUYER_PAY  → 忽略（用户还没付）
TRADE_SUCCESS   → success=true  → 成功链路
TRADE_FINISHED  → success=true  → 本地无"不可退款"概念，按成功处理（注释记录差异）
TRADE_CLOSED    → success=false → 双语义，交给状态守卫判：
                   本地待支付  = 未付款超时关闭 → 置失败
                   本地已成功/已退款 = 全退后关闭 → 守卫 no-op（绝不能置失败）
```

**双语义不是 if-else 写在控制器里，而是"状态守卫自然消化"**：`handlePayCallback(..., false)` 只在 `status=0` 时置失败；已是 1/3 就幂等返回。这样渠道语义变化时，业务不会被误伤。

### 代码：通知端点（验签 → 四查 → 四态 → ACK）

```java
@PostMapping(value = "/alipay", consumes = MediaType.APPLICATION_FORM_URLENCODED_VALUE)
public String notifyAlipay(@RequestParam Map<String, String> params) {
    try {
        return doNotify(params);
    } catch (Exception e) {
        // 处理异常 → 应答 fail：让渠道重试兜瞬时故障（通知会放弃，查单不会——对账核查分支兜底）
        log.error("[支付宝通知] 处理异常（应答 fail 触发渠道重试）: notifyId={}, outTradeNo={}",
                params.get("notify_id"), params.get("out_trade_no"), e);
        return ACK_FAIL;
    }
}

private String doNotify(Map<String, String> params) {
    AlipayNotifyParams notify = AlipayNotifyParams.fromMap(params);

    // 1. 验签（RSA2 + 支付宝公钥）——验签失败 = 伪造或配置错误，不处理
    if (!alipayTradeClient.verifyNotify(params)) {
        return ACK_FAIL;
    }

    // 2. 二次校验：状态可解析 / 支付单存在 / 金额一致 / 商户一致
    AlipayTradeStatus status = notify.status();
    if (status == null) {
        return ACK_FAIL;
    }
    Payment payment = paymentService.findPaymentByNo(notify.getOutTradeNo());
    if (payment == null) {
        return ACK_FAIL;
    }
    if (!amountMatches(payment, notify.getTotalAmount())) {
        return ACK_FAIL;
    }
    if (!Objects.equals(alipayMockProperties.getAppId(), notify.getAppId())
            || !Objects.equals(alipayMockProperties.getSellerId(), notify.getSellerId())) {
        return ACK_FAIL;
    }

    // 3. 四态分流
    switch (status) {
        case TRADE_SUCCESS, TRADE_FINISHED ->
                paymentService.handlePayCallback(notify.getOutTradeNo(), notify.getTradeNo(), true);
        case TRADE_CLOSED ->
                // 双语义：本地待支付=未付款关闭→置失败；已成功/已退款=全退后关闭→状态守卫幂等
                paymentService.handlePayCallback(notify.getOutTradeNo(), notify.getTradeNo(), false);
        case WAIT_BUYER_PAY ->
                log.info("[支付宝通知] 等待付款态通知，无需处理: outTradeNo={}", notify.getOutTradeNo());
    }
    return ACK_SUCCESS;
}
```

## 2. 支付单状态机：成功只允许发生一次

支付单状态：`0 待支付 / 1 成功 / 2 失败 / 3 已退款 / 4 已关闭`。回调进来只有四种走向：

```
status=0 + success → 条件更新 WHERE status=0 → 成功链路
status=0 + fail    → 置 2（渠道确认未付）
status=2/4 + success（迟到成功）→ 条件翻转 2|4→1 → 成功链路
其他（1/3，或重复通知）→ 幂等返回（应答 success）
```

**两个关键点**：

1. **幂等靠条件更新，不靠去重表**：`UPDATE ... WHERE status=0`，影响行数=0 就是"已被处理"；
2. **迟到成功必须翻转**：支付超时 Job 可能已把单置 2（失败）或换渠道置 4（关闭），此时渠道才成功——
   - 若静默 return：用户已付钱、本地记失败、**没有任何退款通道**（钱货两空）；
   - 正确做法：`WHERE status IN (2,4)` 条件翻转 2|4→1，然后**直接走 `afterPaySuccess`**；
   - 不能复用 `handlePaySuccessInternal`：它带 `WHERE status=0` 守卫，此时必然 0 行、直接 return（通知/退款都不会发生）。

```java
@Transactional(transactionManager = "paymentTransactionManager", rollbackFor = Exception.class)
public void handlePayCallback(String paymentNo, String tradeNo, boolean success) {
    Payment payment = findByPaymentNo(paymentNo);
    if (payment == null) {
        return; // 幂等：不抛异常，静默返回
    }

    // C-016：渠道交易号回填（创建时未落库/落库失败窗口）
    if (tradeNo != null && !tradeNo.isBlank()
            && (payment.getTradeNo() == null || payment.getTradeNo().isBlank())) {
        paymentJdbcTemplate.update(
                "UPDATE t_payment SET trade_no = ? WHERE id = ? AND trade_no IS NULL",
                tradeNo, payment.getId());
        payment.setTradeNo(tradeNo);
    }

    // 幂等：只有"待支付"才能处理；非待支付分三种情况
    if (payment.getStatus() != STATUS_PENDING) {
        // 迟到成功：超时置失败(2) / 换渠道关闭(4) 后渠道才成功
        if (success && (payment.getStatus() == STATUS_FAIL || payment.getStatus() == STATUS_CLOSED)) {
            int previousStatus = payment.getStatus();
            int flipped = paymentJdbcTemplate.update(
                    "UPDATE t_payment SET status = ?, paid_at = ?, updated_at = ? "
                            + "WHERE id = ? AND status = ? AND deleted = 0",
                    STATUS_SUCCESS, LocalDateTime.now(), LocalDateTime.now(), payment.getId(), previousStatus);
            if (flipped > 0) {
                // 状态已是 1，必须直接走 afterPaySuccess（再走 handlePaySuccessInternal 会被 status=0 守卫挡掉）
                afterPaySuccess(payment.getOrderId(), payment.getUserId(), paymentNo, tradeNo);
                return;
            }
        }
        return; // 已成功/已退款/重复通知：幂等
    }

    if (success) {
        handlePaySuccessInternal(payment.getOrderId(), payment.getUserId(), paymentNo, tradeNo);
    } else {
        handlePayFailInternal(payment.getOrderId(), payment.getUserId(), paymentNo);
    }
}

private void handlePaySuccessInternal(Long orderId, Long userId, String paymentNo, String tradeNo) {
    int updated = paymentJdbcTemplate.update(
            "UPDATE t_payment SET status = ?, paid_at = ?, updated_at = ? "
                    + "WHERE order_id = ? AND status = ? AND deleted = 0",
            STATUS_SUCCESS, LocalDateTime.now(), LocalDateTime.now(), orderId, STATUS_PENDING);

    if (updated == 0) {
        log.info("[支付成功] 乐观锁冲突（已处理）: orderId={}, paymentNo={}", orderId, paymentNo);
        return;
    }
    afterPaySuccess(orderId, userId, paymentNo, tradeNo);
}
```

## 3. 四层通知：让订单"一定知道"

| 层 | 触发 | 机制 | 解决什么 | 边界 |
|---|---|---|---|---|
| **1 Feign 主** | 支付单 0→1 后同步调用 | `POST /api/order/pay-success`（内部头） | 低延迟、能拿业务结论 | 超时/503 时结果未知，不能判死 |
| **2 MQ 备** | Feign 未被业务拒绝时发 | `PAY_RESULT_TOPIC:PAY_SUCCESS`，order 消费者，`maxReconsumeTimes=3` | Feign 丢/超时的即时兜底 | 只保证"至少一次"，靠状态守卫幂等 |
| **3 Job 兜底** | 每 2 分钟扫 | `status=1 AND paid_at < now-5min` → 查订单是否仍待支付 → 重发 Feign；计数 10 次告警 | 前两层都失败（进程崩/消息丢） | 窗口内不补（留恢复时间）；不可达继续重试 |
| **4 对账终线** | 日切/定时 | 渠道账单/查单比对；失败单核查（`status=2` 未核实 → 查渠道，已付→收敛成功） | 通知永久丢失、状态漂移 | 天级延迟；见 04 |

**为什么不能只有 Feign**：网络不可靠、进程会崩、订单服务会 503；
**为什么不能只有 MQ**：MQ 也有丢/重/乱序，且延迟不可控；
**为什么还要 Job**：MQ 发送本身可能失败（发送端崩在"状态已更新、消息未发出"之间）；
**为什么还要对账**：前三层都假设"本地状态是对的"——对账是唯一以**渠道**为准的终线。

**先 Feign、后 MQ 的顺序不能反**：必须**先确认订单接不接受**，再发 MQ。
如果业务拒绝（订单已取消）还发了 MQ，退款之后订单消费者又可能把订单置成功——乱序资损。

```java
private void afterPaySuccess(Long orderId, Long userId, String paymentNo, String tradeNo) {
    log.info("[支付成功] orderId={}, paymentNo={}, tradeNo={}", orderId, paymentNo, tradeNo);
    recordPaymentEvent(paymentNo, orderId, userId, "PAY_SUCCESS", null, null);
    businessMetrics.recordPaymentCallback("success");

    // P1-1：若订单明确返回业务失败（已取消/已支付，非瞬态 503）→ 自动退款，避免钱货两空
    // 只有订单接受后才发 MQ，否则退款后消费者可能误处理
    boolean businessRejected = false;
    try {
        R<Void> nr = orderFeignClient.notifyPaySuccess(orderId, tradeNo);
        businessRejected = (nr != null && !nr.isSuccess()
                && nr.getCode() != ResultCode.SERVICE_UNAVAILABLE.getCode());
    } catch (Exception e) {
        // 超时/网络异常 = 结果未知：不判死，交给 MQ 备 + Job 兜底
        log.error("[支付成功] 通知订单服务失败(兜底依赖 paymentNotifyCompensateJob): orderId={}", orderId, e);
    }
    if (!businessRejected) {
        sendPayResultMq(orderId, userId, true, tradeNo);
    }
    if (businessRejected) {
        try {
            Payment p = findByPaymentNo(paymentNo);
            if (p != null && p.getUserId().equals(userId)) {
                RefundRequest rr = new RefundRequest();
                rr.setPaymentId(p.getId());
                rr.setUserId(p.getUserId());
                rr.setRefundAmount(p.getAmount());
                rr.setReason("订单已取消/状态不允许支付，自动退款");
                refund(rr);
            }
        } catch (Exception re) {
            log.error("[支付成功] 自动退款失败(需人工/对账处理): orderId={}", orderId, re);
        }
    }
}
```

订单侧对应的语义（**业务拒绝是终态，不是"通知失败"**）：

```java
@PostMapping("/pay-success")
public R<Void> notifyPaySuccess(@RequestParam("orderId") Long orderId,
                                @RequestParam("tradeNo") String tradeNo,
                                @RequestHeader(value = "X-Internal-Call", required = false) String internalCall) {
    if (!accessTokenGuard.isInternalCall(internalCall)) {
        return R.fail(403, "仅允许内部服务调用");
    }
    boolean success = orderService.onPaymentSuccess(orderId, null);
    if (!success) {
        // P1-1：订单已非待付款（竞态取消/关单/已支付）→ 返回业务失败，供支付侧触发自动退款
        return R.fail(ResultCode.ORDER_STATUS_ERROR, "订单状态不允许支付（已取消/已支付）");
    }
    return R.ok();
}
```

## 4. 三种"不成功"：别把语义揉成一团

| 支付域看到的结果 | 真实语义 | 动作 |
|---|---|---|
| 抛异常 / 读超时 | **结果未知**（订单可能已成功） | 不判死；MQ 备 + Job 兜底（幂等重试） |
| `code=503` | 订单服务**暂时不可用** | 同上（瞬态，继续兜底） |
| `success=false`（业务码） | 订单**明确拒绝**（已取消/已支付） | **不重试、不发 MQ**；自动全额退款 |

**把 503 当业务拒绝** → 订单其实还能收，你却退了款（用户白付）；
**把业务拒绝当 503** → 无限重试 + 已退款订单又可能被置成功（钱货两空 + 乱序）。
这两个方向都是资损，面试就讲这个**语义区分**。

## 5. 坑清单

1. **P1-1 钱货两空**：业务拒绝被当成通知失败 → 重试/不退款。修复 = 区分业务码，拒绝即自动退款。
2. **迟到成功静默 return**：超时 Job 已置 2，回调成功被 `status != 0` 挡掉 → 用户已付却记失败。修复 = 条件翻转 2|4→1。
3. **业务拒绝后仍发 MQ**：退款后消费者又把订单置成功（乱序）。修复 = 拒绝时不发 MQ。
4. **Feign 超时当失败**：订单可能已成功，重复退款/重复通知。修复 = 超时只算"未知"，靠幂等收敛。
5. **补偿无边界**：Job 不能无限重试（窗口 5min / 上限 10 次 / 告警 / 已通知标记）。
6. **只有前两层**：MQ 也会丢（发送端崩在"状态已改、消息未发"之间）——Job 与对账缺一不可。

## 6. 值不值得深挖 / 一句话

- **值得讲透**：四层通知的**分工与边界**、三种失败语义、迟到成功翻转、业务拒绝自动退款；
- **一句话带过**：MQ 消费者重试次数、补偿 Cron、Redis 计数实现（实现细节）；
- **一句话**：**支付域证明"钱到了"，订单域裁决"要不要"；通知可以重复、可以丢，但状态只能成功一次。**
- 横向模式（幂等矩阵/乱序状态机/至少一次/补偿边界）见 **06 分布式专题**。

**面试口径**："支付结果用四层通知（Feign 主/MQ 备/Job 兜底/对账终线）；支付单靠条件更新幂等，迟到成功 2|4→1 翻转；订单业务拒绝（非 503）自动全额退款且不发 MQ，避免钱货两空与乱序。"
