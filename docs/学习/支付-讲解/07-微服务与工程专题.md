# 07 · 微服务与工程专题

> **一句话**：order 拥有订单状态，payment 拥有资金账本——**互不写对方表**，只通过契约咬合；
> 跨域只有三种语义（**成功 / 明确拒绝 / 未知**），没有"回滚"，只有补偿；工程债要诚实分档。
>
> **本篇带走 3 条**：① 域边界（谁拥有什么、怎么咬合）
> ② 三种跨域语义（拒绝 ≠ 503 ≠ 超时）③ 工程债清单（已修 / 已记 / 一句带过）
>
> 前置：02（通知四层）、06（分布式模式）。证据：`OrderFeignClient`/`OrderFeignFallbackFactory`、
> `InternalCallFeignConfig`、`MockPayService`、C-002/003/016。

## 0. 场景：支付成功通知订单超时——谁负责？

支付单已经 0→1，Feign 调订单超时。三个问题：

| 问题 | 谁负责 | 机制 |
|---|---|---|
| 钱记对了吗？ | **payment** | 本地事务 + 状态守卫（0→1 只发生一次） |
| 订单知道了吗？ | **payment 负责"至少一次尝试"** | Feign → MQ → Job → 对账（02 §3） |
| 重复通知会不会重复处理？ | **order** | `onPaymentSuccess` 的 `status=0` 守卫（幂等接收） |

一句话：**谁的数据谁负责；跨域只承诺"至少一次尝试 + 幂等接收"，不承诺"一次成功"。**

## 1. 域边界：两张表、两个库

| 域 | 拥有 | 存储 | 分片 |
|---|---|---|---|
| order | 订单状态、子单、履约 | `my_xhs_order`（`t_order_0..3`/`t_sub_order_0..3`） | 按 `user_id` |
| payment | 资金账本、支付/退款单 | `my_xhs_payment`（`t_payment`/`t_refund`） | 独立库，不分片 |

**为什么必须分开**：

- **分片键不同**：order 按 `user_id` 路由；payment 按 `payment_no`/`order_id` 查，硬塞进分片库会被路由错；
- **故障隔离**：订单库慢不拖垮支付记账；支付库维护不影响下单；
- **审计**：资金账本是独立事实，不能被业务表的结构变更污染。

**跨库的代价**（order 侧 `onPaymentSuccess` 的真实处理）：

```
支付回调只带 orderId（没有 userId）
→ order 无法直接按分片键路由
→ 先查 t_order_no_mapping（不分片公共库）反查 userId
→ 再用 (userId, orderId) 路由到正确分片
```

**互不写对方表**（remote 链路）：

- payment 不写 `t_order`；order 不写 `t_payment`；
- 唯一的例外是 **Mock 模式**：`MockPayService` 用独立数据源直写 `t_payment`（`pay.type=mock` 时的演示捷径）；
  默认 `pay.type=remote`，走真实 payment 服务——**这是已记的工程债，不是主链路**。

**双向契约**：

| 方向 | 接口 | 语义 |
|---|---|---|
| order → payment | `/api/payment/pay`、`/refund`、`/refund-by-order` | 发起支付/退款（内部头鉴权） |
| payment → order | `notifyPaySuccess` / `notifyPayFail` / `notifyRefundSuccess` / `notifyRefundFail` | 结果通知 |
| payment → order | `getOrderPayAmount` / `getOrderStatus` | 支付前回查（P1-1） |

内部调用统一带 `X-Internal-Call`（`InternalCallFeignConfig` 自动注入），防外部伪造回调。

## 2. 三种跨域语义：成功 / 拒绝 / 未知

这是 07 最重要的一张表——**把三种语义揉在一起，两个方向都会资损**：

| order 返回 | 语义 | payment 的动作 | 为什么 |
|---|---|---|---|
| `R.ok()` | 成功 | 继续（发 MQ 备份） | 订单已接受 |
| `R.fail(业务码)` | **明确拒绝**（已取消/已支付） | **不重试、不发 MQ、自动退款** | 钱到了但订单不要 → 钱货两空防护（P1-1） |
| `R.fail(503)` / 超时 / 异常 | **未知**（订单服务不可用） | 不判死；MQ + Job 兜底 | 订单可能已处理成功，退款=资损 |

```java
// 订单侧：业务拒绝是一个"正常返回"，不是异常
boolean success = orderService.onPaymentSuccess(orderId, null);
if (!success) {
    return R.fail(ResultCode.ORDER_STATUS_ERROR, "订单状态不允许支付（已取消/已支付）");
}

// 支付侧：只有"明确失败且不是 503"才算业务拒绝
businessRejected = (nr != null && !nr.isSuccess()
        && nr.getCode() != ResultCode.SERVICE_UNAVAILABLE.getCode());

// 降级：FallbackFactory 一律返回 503（绝不能静默成功）
public R<Void> notifyPaySuccess(Long orderId, String tradeNo) {
    return R.fail(ResultCode.SERVICE_UNAVAILABLE, "订单服务不可用，等待补偿任务重试");
}
```

**为什么降级不能返回成功**：静默成功 = 调用方以为通知到了，补偿不会触发 → 数据永久不一致。

**没有"回滚"**：跨域操作一旦发生（钱扣了、订单取消了），分布式里没有 undo；
只有**新的正向动作**——退款、关单、回补库存。补偿本身也必须幂等、有边界（06 §5）。

## 3. 超时与重试：别在 Feign 层硬扛

| 配置 | 值 | 原因 |
|---|---|---|
| connect timeout | 3s | 快速失败，别拖住支付回调线程 |
| read timeout | 5s | 同上 |
| Feign 自动重试 | **不配** | 非幂等调用（创建支付单）重试会重复；同步重试会放大超时/雪崩 |
| 重试位置 | MQ / Job | 异步层有幂等消费 + 上限 + 告警 |

原则：**同步链路只做一次尝试，重试交给异步层**。
同步重试看起来"更可靠"，实际上是把故障放大到调用方线程池，还绕过了幂等设计。

## 4. 工程债：诚实清单

### 已修（有变更卡/测试）

- 渠道契约对齐（C-003）：HTTP 通知端点 + RSA2 验签 + 同步退款 + 先查后决；
- 预支付响应契约（C-016）：`tradeNo` 落库 + `payParams`（orderStr）；
- 内部调用鉴权（`X-Internal-Call`）、支付前回查订单状态/金额（P1-1）；
- 通知可靠性：Outbox/事务消息、补偿窗口/上限/告警（C-012）；
- 退款：累计可退、部分退续退、出金幂等四道闸（03）。

### 已记（未修/主动取舍）

| 债 | 影响 | 为什么先不修 |
|---|---|---|
| Mock 模式 order 直写 `t_payment` | 破坏"互不写对方表" | 演示捷径；remote 模式不触发 |
| `isMockMode(payType)` 能力泄漏 | 同步/异步差异漏进 PaymentService | 应把 capabilities 放进策略；单渠道下优先级低 |
| `PaymentService` ~1600 行 | 状态机+渠道+补偿+对账混在一起 | 拆分成本高；先保证行为正确 |
| 注释漂移 | Job 说"重发 MQ"实际是 Feign；"预留无消费端"已过时 | 以代码为准；下次触碰时顺手修 |
| 模拟器非真渠道 | 无真实对账文件/证书 | 契约形态保真；接真渠道只换实现 |
| 单渠道（微信已移除） | 无法演示多渠道差异 | 范围取舍 |
| 无运行时验证 | 只有编译 + 单测 | 项目口径如此（AGENTS.md §七） |

### 一句带过（非核心）

参数校验、权限注解、日志格式、配置项命名——工程规范问题，不影响架构判断。

### 面试危险信号（说错就露馅）

- ❌ "我们用 2PC/分布式事务保证支付和订单强一致" → 渠道不参与，实际是最终一致；
- ❌ "Feign 超时就算失败，直接退款" → 超时是未知，退款可能资损；
- ❌ "部分退款也通知订单改状态" → 部分退订单不动（T-077）；
- ❌ "支付回调只靠 MQ 通知订单" → 四层：Feign 主、MQ 备、Job 兜底、对账终线。

## 5. 收口：三句话

1. **边界**：order 拥有订单状态，payment 拥有资金账本；互不写对方表，只通过契约咬合；
2. **语义**：成功 / 明确拒绝 / 未知——拒绝是终态（退款），未知是瞬态（兜底）；
3. **兜底**：至少一次尝试 + 幂等接收 + 有界补偿 + 对账终线；不追求强一致，追求最终收敛。

**面试口径**："payment 和 order 各自拥有自己的状态，通过内部 Feign + MQ 咬合；跨域区分成功/业务拒绝/未知三种语义，拒绝自动退款、未知靠四层兜底；不用分布式事务，走本地事务 + 可靠事件 + 补偿 + 对账。"

## 6. 值不值得深挖 / 一句话

- **值得**：域边界、三种跨域语义、工程债的诚实分档（面试官很吃这套）；
- **一句话带过**：具体 Feign 超时数值、`X-Internal-Call` 实现、Mock 数据源配置；
