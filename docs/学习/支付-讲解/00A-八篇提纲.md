## 01 渠道契约层（支付宝）

- **目标问题**：为什么把渠道做成"契约层"？通知怎么收、怎么回、渠道怎么重试？验签/二次校验防什么？
- **核心结论**：业务只依赖 `PayChannelStrategy` + `AlipayTradeClient`；契约=通知/查单/关单/退款/验签五件事；
  **核心=二次校验（验签≠业务可信）+ ACK/幂等（重复通知的消化）**；衍生=TRADE_CLOSED 双语义 + 先查后决；
  **验签只值一句话**（方向性/原样参数/只管来源可信）。
- **小节**：
  1. 例子：一条支付宝通知的一生（form 参数 → RSA2 验签 → 二次校验（金额/单号/商户）→ trade_status 四态 → ACK）
  2. 契约五件事与策略模式（`PayChannelStrategy.pay/refund` + `AlipayTradeClient` 的 notify/query/close/refund/verify）
  3. 通知重试与 ACK 语义（fail 让渠道重试；重复通知由状态机幂等兜底；-1 未知态绝不当失败）
  4. **先查后决**（换渠道/关单前的契约安全：查前一个交易——已付=受理收敛、未付=close 后新开、不可达=不切换）
  5. 无资质下的保真：`SimulatedAlipayServer`（本地密钥对/台账/通知投递器）与演示口径
  6. 接真渠道要改什么：只换密钥/证书/实现（业务与状态机零改动）
- **证据**：`alipay/AlipaySignatureUtil`、`AlipayNotifyParams`、`AlipayNotifyController`、`simulator/`；`C-003` change + ITER-003。
- **咬合**：gateway（callback 免 JWT/HMAC，验签即鉴权）；order（域间契约不变）。
- **追问链**：验签失败怎么办→重复通知→通知丢失→异步通知 vs 查单谁为准→渠道不可达时的先查后决。

## 02 支付回调与订单咬合

- **目标问题**：钱付了订单怎么知道？通知失败怎么办？回调重复/乱序/撞车怎么处理？
- **核心结论**：结果通知**四层**（Feign 主 → MQ 备 → XXL 补偿 5min 窗口 → 对账终线）；
  回调幂等三层（唯一索引 + `WHERE status=0` 乐观锁 + Redis 键）；**三态解析**（1/0/-1）；
  **迟到成功翻转**（超时置 2 后渠道才成功 → 条件翻转 2→1）；订单**业务拒绝 false = 自动全额退款**（P1-1 钱货两空防护），
  且业务拒绝时**不发 MQ**（防退款后乱序）。
- **小节**：
  1. 例子：支付成功 → 订单变已支付（正常线）/ 订单已取消（自动退款线）
  2. 回调状态机（乐观锁、三态、迟到翻转、重复回调=影响行数 0 即成功）
  3. 四层通知与各自边界（Feign 瞬态 503 不判死；MQ 备；补偿窗口 5min + 上限 + 告警；对账终线）
  4. 撞车：关单 vs 支付（false 语义在两个方向的镜像）
  5. 坑清单：P1-1、T-062（超时误判）、T-077（退款通知对称化）、事务后事件
- **证据**：`PaymentService.handlePayCallback/afterPaySuccess`、`PaymentNotifyCompensateJob`、`PAY_RESULT_TOPIC`；order 侧 `paySuccess`/`terminateOrder`。
- **咬合**：order 状态机（回调接口/业务拒绝语义）；库存（支付成功→confirm）。
- **追问链**：Feign 超时但订单已处理→MQ 重复→补偿上限→对账发现不一致→为什么不用分布式事务。

## 03 退款链路

- **目标问题**：部分退/多次退怎么算？退款幂等？退款结果怎么回传？退款后库存/券怎么回补？
- **核心结论**：可退 = 支付额 − `SUM(成功退款)`；累计校验（渠道 `ACQ.REFUND_AMT_NOT_EQUAL_TOTAL`）；
  全退 → 支付单 `status=3`，**部分退保持 1 可续退**（T-076）；**仅全退才通知订单**（T-077）；
  出金幂等（锁 + refunding 标记 + 状态机；C-002 阶段③）；退款回调模拟器 T-075 修复。
- **小节**：
  1. 例子：199 元分两次退（100 + 99）——每次的可退金额、退款单、支付单状态
  2. 退款状态机与累计校验（SQL 聚合不拉明细；部分/全退分流）
  3. 出金幂等（Redisson 锁 + 标记 + 乐观锁；out 键缺口的兜底与边界）
  4. 退款通知与订单咬合（全退通知/部分退不通知的原因）
  5. 回补链路：退款成功 → 库存 refundRestore（幂等）/ 券退还（RV30 语义）——只讲咬合点
- **证据**：`PaymentService.doRefund/handleRefundSuccessInternal`、`RefundNotifyCompensateJob`；C-002 阶段③；`T-075/076/077`。
- **追问链**：退款中进程崩溃→渠道成功但回调丢→部分退的订单状态→重复退款→退款失败重试。

## 04 对账体系

- **目标问题**：渠道和本地对不上怎么办？以谁为准？差异怎么处理？
- **核心结论**：对账不是"比金额"：`t_channel_flow` 落库 → 日切账单（`uk(日期,渠道)` + `run_no` + `force`）→
  三方对账（**渠道行驱动 + 本地游标**，安全阀）→ **三类差异挂账** → 人工处理不覆盖；
  `statement marker` 防"对账单未到=全量差异"假象；**演练扰动**（MISSING/EXTRA/AMOUNT）验证闭环。
- **小节**：
  1. 例子：某渠道一天 1000 笔，渠道多 1 笔、金额差 0.01——差异如何被发现与挂账
  2. 数据模型（渠道流水/日切账单/差异表）与状态
  3. 账单生成（幂等重跑、金额口径：手续费按收款毛额、`settle=(pay−refund)−fee`）
  4. 三方对账（驱动方式/游标/三类差异/本轮消失的差异收敛/人工已处理不覆盖）
  5. 人工处理与演练（handleDiff 只改状态不补单；voidBill；Perturb）
- **证据**：`SettlementService.generateDailyBill/reconcile/handleDiff/voidBill`、`SettlementRepository`、xxl `settlementBillJob/settlementReconcileJob`。
- **追问链**：对账单没到→重复跑→差异被处理后再次出现→对账与结算的关系→为什么以渠道为准/本地为准。

## 05 结算域（半篇：只讲资金视角/金额口径/重跑作废；对账细节归 04）

- **目标问题**：结算单是什么？和支付/退款/订单什么关系？为什么独立成域？
- **核心结论**：结算=**资金视角**的日切汇总（收款/退款/手续费/应结），与交易视角（订单）解耦；
  幂等重跑 + 作废重开（`run_no`）；手续费按毛额计提（退款不退手续费，与渠道计费一致）。
- **小节**：
  1. 例子：某渠道一天 10 万收款、2 万退款、费率 0.6% → 应结金额
  2. 数据模型与状态（bill/diff 的关系）
  3. 生成/重跑/作废（uk、run_no、force 的语义）
  4. 与 04 的边界：账单既是"应结凭证"也是"对账 statement"——两篇只交叉引用不重复
  5. 域边界：支付流水是事实源，结算是派生账；为什么不让订单算钱
- **证据**：`SettlementService`、`SettlementBill/SettlementDiff`、`SettlementRepository`。
- **追问链**：结算金额公式→退款手续费→重跑重复→结算与订单的差异→分账/对账。

## 06 分布式问题专题（用支付当样本）

- **目标问题**：支付里用到哪些分布式模式？各自解决什么、边界在哪？
- **核心结论**：六件事——**幂等矩阵**（唯一索引/乐观锁/Redis 键/累计校验各管一段）、**乱序状态机**（迟到翻转/重复回调/换渠道）、
  **至少一次通知**（四层 + 上限 + 人工）、**补偿不无限**（窗口/次数/告警/对账终线）、**契约与先查后决**、**对账以谁为准**；
  横向对应 99 §4 的 A（幂等）/B（乱序）/C（对账）/F（消息可靠投递）。
- **小节**：
  1. 支付链路的分布式问题地图（下单→支付→通知→退款→结算）
  2. 幂等矩阵：同一问题在不同层的不同解法与为什么
  3. 乱序与状态机：迟到成功翻转、重复回调、换渠道关闭
  4. 补偿体系：四层、上限、人工、对账——"至少一次+幂等"的统一哲学
  5. 与 99 §4 家族对照：支付贡献了哪些样本（面试横向题）
- **证据**：`PaymentService` 全链路、C-002 review 修复（关闭交易取消回调注册/已关闭迟到成功）。
- **追问链**：为什么不用分布式事务→MQ 事务消息够吗→补偿如何不循环→对账是终线还是兜底。

## 07 微服务与工程问题专题

- **目标问题**：payment↔order 边界怎么划？超时/降级/回滚？工程债有哪些？
- **核心结论**：order 拥有订单状态，payment 拥有资金账本——**互不写对方表**，只通过契约（Feign 通知/查询 + MQ）咬合；
  "业务拒绝 false"是跨域语义（不是报错）；工程债按"已修/已记/一句带过"三档收口。
- **小节**：
  1. 例子：支付成功通知订单超时——谁负责、怎么兜底（Feign 瞬态 vs 业务失败）
  2. 双向 Feign 契约（notify*/getOrderPayAmount/getOrderStatus）+ 超时/降级/重试/回滚语义
  3. 域边界：支付不写订单、订单不写支付表；独立数据源（绕开分片路由）的意义
  4. 工程债清单（C-002/003/016 已修/已记）：占位自消费消费者、注释漂移、Mock 参数硬编码、真渠道验签已补、
     **响应契约缺预支付参数已补（C-016：tradeNo + orderStr）**、**死配置/参数校验/权限一句带过**
  5. 收口：三句话总结 + 面试危险信号
- **证据**：`OrderFeignClient/OrderFeignFallbackFactory`、`PayResultConsumer/RefundResultConsumer`（占位）、C-002/003 change。
- **追问链**：Feign 与 MQ 都失败→订单服务挂了→回滚谁做→为什么支付有独立数据源→如何防止"钱货两空"。
