# 02 · 购物车（my-xhs-cart）· 梳理

> 系列：模块对照 · 阶段一（梳理）。**只记录，不讨论**（问题线索见 §7，待讨论）。
> 口径：标尺 = **真实电商购物车该有的样子（应然）**（见 §2）；代码只是对照项。
> 规模：21 文件 / 2387 行。端口：见 yml（19xxx）。深度档：**中**。
> 建立：2026-10-11。

---

## 1. 定位与职责

用户"**购买意图的暂存区**"：加购/改量/勾选/删除/合并 + 结算前的商品信息展示（有效性与金额）。
架构定位与库存同族：**Redis 为权威（L1）→ MQ 异步落 MySQL（兜底存储）→ 对账收敛**。

被依赖：仅 **home BFF**（`CartFeignClient.getCartList`，购物车页聚合）。无其他 Feign 调用方。

## 2. 应然基准（标尺）与实然对照

> 标尺 = 真实电商购物车：多端一致、营销联动、库存可见、下单联动。

| 应然能力 | 我们 | 差距 |
|---|---|---|
| 多端同步 + 匿名车合并 | ✅ `mergeAnonymousCart`（**匿名车由客户端请求体带入**——服务端不存匿名车） | 变体 |
| 商品有效性联动（下架/删除/失效区展示） | ✅ `valid + invalidReason`（SKU/SPU 双维度）；⚠️ 失效项不自动清理、无"失效区"分区 | 简化 |
| **库存可见**（仅剩 N 件/售罄标记/超卖提醒） | ❌ 列表不返回库存（真实库存校验在下单） | 缺 |
| **价格与优惠预估**（结算前试算/满减提示/凑单） | ⚠️ 仅 `checkedAmount = Σ 单价×数量`，无任何优惠试算 | 简化 |
| 勾选与结算联动 | ✅ checked Set + `checkedAmount/checkedCount`；全选只算有效商品 | — |
| **下单后自动移除已购项** | ❌ **无此机制**（cart 不消费订单事件、order 不调 cart）——需用户手动删/清 | 缺 |
| 限购（活动级/商品级限购 N 件） | ⚠️ 只有平台级上限（50 种 / 单品 99 件） | 简化 |
| 持久化 / 故障恢复 / 对账 | ✅ Redis 权威 + MQ 落库 + 每日对账 + Redis 丢失自动恢复（**超配**） | — |

（边缘：凑单推荐/换购/降价提醒——不展开。）

## 3. 数据模型

| 表 | 关键字段 | 约束 |
|---|---|---|
| `t_cart_item` | id / user_id / sku_id / quantity / checked / created_at / updated_at | **UNIQUE `uk_user_sku(user_id, sku_id)`**（UPSERT 幂等基础） |
| `t_cart_event` | id / user_id / sku_id / action / quantity / checked / event_time / msg_id | **UNIQUE `uk_msg_id`**；append-only，保留 **30 天**（有界清理） |

**Redis 三结构**（`{userId}` hash tag 保 Cluster 同 slot）：
```
myxhs:cart:{userId}:items    Hash  skuId → quantity
myxhs:cart:{userId}:checked  Set   skuId（勾选）
myxhs:cart:{userId}:sort     ZSet  skuId → 加购时间戳（倒序展示）
myxhs:cart:{userId}:cleared  String 清空标记（对账防误删）
```
TTL：**30 天滑动**（每次写操作三键原子 EXPIRE，Lua 内/独立脚本）。

## 4. 核心链路

### A. 写路径：7 个 Lua 脚本全原子化（防并发中间态）

| 脚本 | 语义（原子单元） |
|---|---|
| `cart_add` | HEXISTS →（满 50 种返回 -1）→ HINCRBY → 截断 99 → 新项 SADD + ZADD NX → EXPIRE → **返回 +10000 编码新商品** |
| `cart_update_quantity` | HEXISTS 校验 → HSET（防并发删除后"复活"） |
| `cart_remove` | HDEL + SREM + ZREM 三结构原子删除 |
| `cart_check_item` | HEXISTS → SADD/SREM（防幽灵勾选） |
| `cart_check_all` | HKEYS → DEL → SADD（原子全选；取消=DEL O(1)） |
| `cart_clear` | 三结构删除 + cleared 标记写入（RV30 收敛为单脚本） |
| `cart_merge_item` | 已有项取 max(quantity) / 新项走上限校验 |

- 加购/合并前置 `skuExists`（SKU+SPU 在架校验；**商品服务不可用时降级放行**，可用性优先）。

### B. 同步链路：顺序消息（本模块最讲究处）

- 发 `CART_TOPIC:{action}`，**`asyncSendOrderly` 以 userId 为分区键**（同用户变更固定同队列）；
- 消费端 `ConsumeMode.ORDERLY`——**从源头保证同用户事件顺序**；
- 事件时间戳 = `System.currentTimeMillis() + 单调序列号(nanos)`（防同毫秒误判，C-05）；CLEAR 额外带 `clearBarrierTs`。

### C. 消费侧（两个独立 consumer group，互不影响）

| 消费者 | 组 | 职责 | 幂等 |
|---|---|---|---|
| `CartSyncConsumer` | `cart-sync-consumer-group`（ORDERLY） | 落库 `t_cart_item`：UPSERT（捕获 `DuplicateKeyException` 转 UPDATE）+ **时间戳 CAS**（生产端时钟 eventTime）+ **CLEAR 屏障**（跳过屏障前旧事件） | uk_user_sku + 时间戳 CAS |
| `CartEventSinkConsumer` | `cart-event-sink-group`（ORDERLY） | append-only 落 `t_cart_event`（漏斗分析素材） | msgId 24h + uk_msg_id 兜底 |

- CLEAR 屏障为**进程内 `ConcurrentHashMap`**（有界保护：24h 淘汰 / 5 万条上限则整体清空降级为时间戳 CAS）——依赖"ORDERLY 同用户同队列"假设。

### D. 读路径（getCartList）

```
Pipeline 一次 RTT 取三结构 → 批量 Feign 查 SKU（失效降级标记）→ 组装（valid/invalidReason）
→ 按加购时间倒序 → allChecked 只看有效项
Redis 为空时：cleared 标记 → 直接返回空车；否则从 MySQL 恢复回写 + 重读修正（P2-7/O-P2-7-1）
```

### E. 对账（CartReconcileJob）

- 三场景：Redis 有 MySQL 无 → INSERT；数量/勾选不一致 → UPDATE（以 Redis 为准）；Redis 无 MySQL 有 → DELETE；
- **水位线 300s**（MySQL 近 5 分钟有写入 = 在途，跳过防误判）；
- **防双份全丢**：`itemsKey 不存在且无 cleared 标记` → 跳过删除场景（Redis 故障时不毁 MySQL 兜底）；
- MySQL 枚举源之外，**SCAN 补扫纯 Redis 用户**；
- 事件流水 30 天清理（有界排空 20×5000）。

| 方向 | 内容 |
|---|---|
| 端点（10+2 管理） | add / quantity / remove / check / check-all / list / merge / clear / count；`internal/reconcile`、`internal/reconcile/user`（admin） |

## 6. Jobs 与关键机制

- **XXL-Job**：`cartReconcileJob`（部署 cron `0 0 * * * ?`——**每小时**；代码 javadoc 写"每天凌晨 4 点"→ 注释漂移）；
- 管理端点对账：全量（异步单线程池）/ 单用户（**复用同一把 600s 锁**，token + Lua 比对释放）；
- 线程池：`cart-reconcile`（单线程守护）。

## 7. 现状边界与问题线索（仅记录，待讨论）

1. **下单后不自动清车**：cart 不消费订单事件、order 也不调 cart——已购项留在购物车（真实电商会移除；华仔有清车链路）；
2. **匿名车在客户端**：merge 的 items 由请求体带入，服务端不存匿名车（换设备丢车/可伪造的边界）；
3. **CLEAR 屏障是进程内状态**：依赖 ORDERLY 同队列假设；rebalance/重启后降级为时间戳 CAS（注释自述）；
4. 对账 cron 注释漂移（javadoc 4am vs 部署每小时）——与库存对账"3am vs 每小时"同型；
5. 失效商品**不自动清理**、无"失效区"分区；
6. `checkedAmount` 无优惠试算（结算价在订单侧）；
7. 全量对账锁固定 600s——超时后存在并发窗口（大批量用户时）；
8. `skuExists` 商品服务不可用时**降级放行**——幽灵 SKU 靠列表层 valid 兜底（注释自述）；
9. 恢复链路的"防双份全丢"策略保守——CLEAR 事件丢失时 MySQL 陈旧行会残留（用户不可见，仅占存储）。
