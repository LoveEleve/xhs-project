# 06 · 搜索（my-xhs-search）· 梳理

> 系列：模块对照 · 阶段一（梳理）。**只记录，不讨论**（问题线索见 §7，待讨论）。
> 口径：标尺 = **真实内容/电商搜索域该有的样子**（见 §2）。
> 规模：41 文件 / 6052 行（第二大模块）。端口 19016。深度档：**中**。
> 建立：2026-10-11。

---

## 1. 定位与职责

**检索引擎 + 推荐引擎**，且**没有自己的 MySQL 库**：

1. **搜索**：笔记/商品全文检索（ES + IK 分词 + 高亮 + Search After 深分页）+ 联想（Completion Suggester）+ 搜索历史；
2. **热搜**：分钟桶滑动窗口 + 指数衰减 + 反作弊 + 置顶/屏蔽 + 历史快照；
3. **索引供给**：Canal 双通道（note/product）+ 增量补偿（60s）+ 全量重建（可续/进度）+ 点赞数同步；
4. **推荐**：**5 路召回**（Content/Following/Geo/Hot/ItemCF）并行 + 合并（XXL 三 Job 离线算特征/热门池/相似矩阵）。

数据面：**复用 content 数据源**（`my_xhs_content`，读写 t_note/t_comment/t_item_feature/t_user_behavior/t_hot_search_snapshot + 显式跨库 `my_xhs_product.t_spu`）。

## 2. 应然基准（标尺）与实然对照

| 应然能力 | 我们 | 差距 |
|---|---|---|
| 全文检索（分词/高亮/多字段/多种排序） | ✅ ES + `ik_smart` + multiMatch + highlight + 四型排序（相关/时间/热度/价格/销量） | — |
| 深分页 | ✅ **Search After 游标**（FieldValue double/long 精度区分——防翻页跳记录） | — |
| 索引同步（变更 → 索引） | ✅ **超配**：Canal 双通道 + external version 防乱序 + tombstone 防复活 + 失败 Set 重试 + 增量扫描 + 全量重建 | — |
| 搜索联想 / 历史 | ✅ Completion Suggester + 结果缓存；历史最近 20 条 | — |
| 热搜（实时/衰减/治理） | ✅ 分钟桶 + 指数衰减（λ=0.1）+ **Lua 原子反作弊**（IP/用户/屏蔽词）+ 置顶/屏蔽 + 快照 + 日清 | 超配 |
| 推荐（召回→排序→重排） | ⚠️ **5 路召回完整**（并行 + 2s 超时 + 分数合并）；**无排序层**（粗排/精排/多路权重） | 简化 |
| 搜索接口防护（限流/风控） | ❌ **搜索端点零 @RateLimit**（仅热搜记录有反作弊） | 缺 |
| 索引运维（重建生效方式） | ⚠️ 原地重建（可续/进度可见）；**无别名切换**（重建期间干扰在服；靠 external version 幂等） | 简化（见 §7-1） |

## 3. 数据模型

**无自有 MySQL 库**——数据库连接指向 `my_xhs_content`（master 3306 / slave 3307，复用读写分离底座）：

| 载体 | 对象 | 说明 |
|---|---|---|
| ES | `note_index` / `product_index` / `suggest_index` | `IndexInitializer.createIndexIfNotExists`（IK `ik_smart`；`replicas` 可配默认 0）；ES `192.168.0.142:19200` |
| content 库 | 读 t_note/t_comment；读写 `t_item_feature`（推荐特征）/ `t_user_behavior`（行为）/ `t_hot_search_snapshot`（热搜快照） | **跨域表读写** |
| product 库 | 增量补偿显式 `my_xhs_product.t_spu/t_sku` | P1-5 修复：不加库前缀必失败 |
| Redis | `myxhs:search:hot:realtime(+:tmp RENAME)`、`search:window:{yyyyMMddHHmm}`（分钟桶 2h）、`antispam:user|ip`、`hot:pinned/blocked`、`search:history:`、`suggest:cache:`、`es:sync:failed:note|product`（失败 Set）、`index:rebuild:status`（进度）、各类锁 | |

## 4. 核心链路

### A. 搜索读路径（note / product）

```
Controller（CompletableFuture + recallExecutor 异步化，释放 Tomcat 线程）
→ 副作用：searchHistory.add + hotSearch.record（Lua 反作弊）
→ ES 查询：multiMatch（关键词）+ filter（status / category / 价格区间）+ highlight
→ 排序四型：relevance（_score + noteId 次键）/ 时间 / 热度（likeCount）/ 价格 / 销量
→ Search After：游标序列化/解析（**区分 double/long，防 _score 精度丢失翻页跳记录**）
```

- 笔记：`note_index`（页 20/50）；商品：`product_index`（`status=1` + 分类 + 价格区间）。

### B. 联想与历史

- Suggest：ES Completion Suggester + Redis 缓存（key 哈希；**空结果短 TTL** 防穿透刷缓存）；失败降级空列表；
- 历史：最近 20 条 + 单条删除/清空。

### C. 热搜（`HotSearchService`，523 行）

```
记录（Lua 原子四步）：屏蔽词检查 → IP 限频（10/min）→ 用户同词去重（300s）→ HINCRBY 分钟桶（TTL 2h）
热度计算（@Scheduled 可配，默认 1min；注释"生产建议 5min"）：Pipeline 取最近 60 桶
   → Score = Σ(count × e^(-λΔt))（λ=0.1：1min≈0.9 / 30min≈0.05 / 60min≈0.002）
   → 实时 ZSet 原子切换（写 :tmp → RENAME）
Top50 展示：置顶优先 + 屏蔽剔除 + 标签（determineTag 按分数/排名分级）
快照：定时落 t_hot_search_snapshot（历史按日查询）+ 日清过期快照
```

### D. 索引供给（可靠性最重的部分）

| 通道 | 机制 |
|---|---|
| **Canal 双通道** | `note_instance` → `NOTE_INDEX_TOPIC`；`product_instance` → `PRODUCT_INDEX_TOPIC`；文档**由 Canal 行数据直接构建**（不查库） |
| **防乱序** | ES **external version**：note 侧优先 `es`（Canal 事件序号，严格递增——`ts` 毫秒级同毫秒会重复被拒）降级 `ts`；增量侧用 DB 行 `updated_at`（毫秒，P1-4） |
| **防复活** | **逻辑删除 → 写墓碑**（`status=-1`，**带 version**——防乱序旧消息重新索引）+ 查询侧只搜 `status=2`；⚠️ **Canal DELETE（物理删）走直接物理删除、无墓碑 version**（观察点，见 §7） |
| **失败重试** | 索引失败 SADD 进 `myxhs:es:sync:failed:note|product`，下轮重试 |
| **增量补偿** | `IncrementalIndexSyncJob` @Scheduled(60s)：按失败 Set + 时间窗扫描回补（与全量互补） |
| **全量重建** | `IndexRebuildJob` @Scheduled(`0 0 4 * * ?`) + 手动端点；**原地重建**（id 游标，Redis 进度可续；源表不可用则 skip "data sync not ready"；完成后标 COMPLETED） |

### E. 点赞数同步（T-092 竞态修复值得一读）

`LikeCountSyncConsumer`（`SOCIAL_TOPIC`，`LIKE||UNLIKE`，组 `counter-es-sync-consumer-group`）：
- 仅 `bizType=1`（笔记点赞；评论点赞无关）→ 更新 `note_index.likeCount`；
- **T-092（2026-08-16）**：原读 counter 的计数 key——但 search 与 counter **并行消费同一消息**，counter 写入前 search 读到旧值（实测 likeCount 被更新为 0）；改为读 **analytics 的权威 Set `SCARD(myxhs:like:note:{noteId})`**（点赞接口在 HTTP 响应前同步 SADD，无消费时序竞争）。

### F. 推荐（5 路召回）

```
RecommendService：5 路召回并行（recallExecutor + recallInnerExecutor；每路 100 条、每路超时 2000ms
   超时/异常降级为空）→ 按 noteId 合并去重（分数合并）→ 排序截断
**已看过过滤**：Redis Set myxhs:recommend:seen:{userId}——过滤已曝光后回写（SADD）
策略：Content（用户标签）/ Following（关注最新）/ Geo（地理）/ Hot（全局热门池）/ ItemCF（相似矩阵）
离线（XXL）：recommendFeatureJob / recommendHotPoolJob / recommendItemCFJob
接口：/recommend/feed（推荐流）、/recommend/similar/{noteId}（相似笔记）
预热：SearchCacheWarmer（热搜实时榜 + 推荐热门池）
行为上报：BehaviorReportConsumer（RECOMMEND_BEHAVIOR_TOPIC → INSERT IGNORE t_user_behavior）
```

## 7. 现状边界与问题线索（仅记录，待讨论）

1. **无别名切换（原地重建）**：全量重建直接写线上索引（external version 保证幂等，但重建期间索引数据"半新半旧"）；**与 `docs/interview/xhs/50-Canal深度拷打.md` 中"重建 + 别名切换"的说法不符——该材料需勘误**；
2. **搜索接口零限流**：SearchController 全部端点无 `@RateLimit`（对比其他模块几乎全量加注解）——公开搜索是 DoS/爬虫暴露面（热搜记录里的反作弊只保护计数）；
3. **跨库边界模糊**：search 数据源=content 库、还显式跨库读 product（P1-5 曾因缺前缀"补偿必失败"）；`t_item_feature/t_user_behavior/t_hot_search_snapshot` 物理在 content 库、由 search 读写——"模块↔库"关系非一对一；
4. 推荐只到**召回层**（无排序/权重可配——多路分数直接 sum 合并）——简化点、面试可讲"召回-排序"分层；
5. ES 单节点 + `replicas=0`（默认）——环境事实（无高可用）；
6. 重建的"源表就绪检查"（t_note 不可用 skip）与进度可观测（REBUILD_STATUS_KEY，TTL 1 天）——设计细节可留档；
7. **物理删除路径无 version 墓碑**：逻辑删除走墓碑（带 version，防旧消息复活），但 Canal 物理 DELETE 事件走直接物理删——理论上"物理删后迟到旧 UPDATE"可复活文档（依赖 Canal 顺序保证，观察点）。

### 8.3 核心设计（学习要点）

**A. 失败集收敛（R1/R5）——"什么该重试"是补偿系统第一性问题**：
- version_conflict ≠ 失败（ES 已是更新版本 = 幂等已应用）；确定性失败（数据不完整）重试必然再失败；
- 原实现把两类都回填 → 失败集单调不收敛（每分钟重投 + re-SADD 续期永不过期）；整批异常才保守全量回填（不丢）。

**B. 零中断重建（别名切换）**：写侧只写新实体、读侧只看别名 → 切换瞬间生效、失败不动线上；
窗口重放补偿"构建期间"的增量变更（ExternalGte 幂等）；legacy 回退保证存量可用（部署说明引导迁移）；
中断续传（status 记 targetNoteIndex/targetProductIndex，不重复建实体）。

**C. 墓碑统一（R4）**：物理删与逻辑删都走"版本化墓碑 + deletedAt"——防复活（迟到旧 UPDATE 被 ExternalGte 拒）+ 防泄漏（超龄墓碑 7 天清理）；原物理删直接删文档的代价正是无墓碑可复活。

**D. 同型比对的价值（R2/R3）**：Note 有 remove、Product 没有；rebuild 豁免 conflict、增量没有；structured 已 ts 域、flat 没有——**同族不同实现是最容易漏的一类缺陷**。

### 8.4 记录不做（讲）

推荐权重可配化（演进项）；跨库边界重构（结构事实）；ES 多节点（环境）；suggest 索引别名化（派生小索引，原地重建可接受）。
