## 1. 定位与职责

**交易链路的供给端基础数据**：SPU/SKU/分类的维护（管理端低频写）+ 商品详情读路径（C 端高频）+ 商品浏览埋点。

一句话：**"卖什么、多少钱、在不在架、给谁看"**——只存**静态描述**；库存不在它这里（`t_sku.stock` 是冗余占位，真库存在 inventory）。

被 5 个服务依赖：order / cart / inventory / home / search（见 §4）。

## 3. 数据模型

| 表 | 关键字段 | 说明 |
|---|---|---|
| `t_spu` | id / name / category_id / brand_id / description / images(JSON数组) / status(0下架1上架) / deleted | **无商家字段**；无 creatorUserId |
| `t_sku` | id / spu_id / name / price / original_price / **stock（冗余占位）** / specs(JSON) / status | 图片不在 SKU 上：取所属 SPU 的 images 首图 |
| `t_category` | id / name / parent_id / level(1~3) / sort / icon / status | 三级分类树 |
| `t_product_behavior` | user_id / spu_id / sku_id / behavior_type(1浏览/2收藏/3加购) / event_time | append-only 埋点流水 |

**Redis**：
- `product:spu:{id}` → `RedisCacheData` 包装（**逻辑过期 30min + 物理 TTL 2h**；空值：逻辑 2min + 物理 5min）；
- 分类树 key（2h，Controller 注释口径）+ `myxhs:product:bloom:spu`（Redisson 布隆，100 万容量 / 1% 误判）。

**DB**：`my_xhs_product` **单库不分片**，但启用**读写分离**（master `3306` 写 / slave `3307` 读；RDS 底座见 §4-E）。

## 4. 核心链路

### A. 商品维护（管理端）

```
建 SPU（⚠️ 实码默认直接 ON_SHELF——见 §6-1）
建 SKU：校验 SPU 存在（不要求上架）/ 划线价≥售价 / specs 必须合法 JSON
      → afterCommit：删 SPU 缓存 + Feign 初始化库存（用商品域自带 InitRequest，故障打点、管理端 /api/inventory/init 重试）
上架/下架：上架校验"至少一个上架 SKU"；afterCommit 删缓存
更新 SPU：字段级更新（LambdaUpdateWrapper，防 read-then-write 丢失更新）
        → afterCommit：立即删 + 1s 后二次删（延迟双删，覆盖并发读异步重建窗口）
```

### B. 读路径 `getSpuDetail`（四级防护，本项目最完整的缓存设计之一）

```
① 布隆过滤器（前置拦"一定不存在"；未就绪/异常自动降级放行）
② Redis L2：逻辑过期（30min）未到 → 直接返回
              已过期 + 有值 → 返回旧值 + 异步刷新（分布式锁，只有一人刷）
              已过期 + 空值 → 穿透到 DB 重查
③ MySQL L3（冷 key 并发 miss）：Redisson 锁 + 双重检查 + 3×100ms 有界等待
              拿不到锁→等待重查；仍未命中→降级直查 DB
④ 回填：正常值（30min/2h）或空值缓存（2min/5min）
下架/删除 → 详情不可见（与列表口径一致）
```

- **防穿透双保险**：布隆（省 Redis 查询）+ 空值缓存（防同一误判 ID 反复打 DB）；
- **防击穿**：逻辑过期 + 旧值可用（可用性优先）；
- **防雪崩**：逻辑过期天然分散（无需随机 TTL）。

### C. 缓存一致性（写侧）

- 主策略：**afterCommit 删缓存**（DB 提交后才删，修掉"先删后写"窗口）；
- 删 Redis 失败 → **发 `CACHE_EVICT_TOPIC` 兜底**（消费者重试，删除天然幂等）；
- 延迟双删：只在 `updateSpu`（SKU 变更/上下架仅单删）；
- **商品 binlog 有 Canal 通道——但服务的是"搜索索引"，不是"商品缓存"**：`product_instance`（`t_spu,t_sku`）→ `PRODUCT_INDEX_TOPIC`（search 域消费）；商品自己的 Redis 缓存**没有** Canal 失效通道，外部直改 DB 靠逻辑过期 30min/物理 2h 收敛（与库存缓存用 Canal 直删是不同取舍，见 §7-3）。

### D. 分类树

Redis 缓存（2h）+ **启动预热**（`CacheWarmer` 接口，`myxhs.cache-warmup.targets=product-category-tree`）；构建带**环路检测 + 深度保护**（MAX_DEPTH=10）；空树不缓存。

### E. 读写分离（公共底座 · 全项目 12 模块共用）

- 组件（`my-xhs-common`）：`ReadWriteRoutingDataSource` + `DataSourceContextHolder` + `ReadWriteRoutingInterceptor`（MyBatis Executor 层）+ `ReadWriteRoutingDataSourceConfig`；
- **路由三策略（优先级从高到低）**：① 手动 ThreadLocal 指定（一次性）→ ② `@Transactional(readOnly=true)` → ③ **SQL 分析**（SELECT/SHOW/DESC/EXPLAIN 且非 `FOR UPDATE` → 从库）；
- **事务安全**：活跃写事务中不做 SQL 路由——事务内 SELECT 与写共用主库连接，保证隔离性；
- **从库降级**：从库不可用自动降级主库 + 每 30s 主动探测恢复；从库 Hikari `readOnly=true`、不参与健康检查、启动不阻塞（`initializationFailTimeout=-1`）；
- **Zone 感知（默认关）**：读就近（masterZone / slaveZone）；
- 启用范围：**12 模块全开**（analytics/cart/content/counter/coupon/im/inventory/notification/payment/product/search/user）；**order 例外**（ShardingSphere 自管数据源）；gateway 无 DB；
- 本项目现状：商品模块**无 `@Transactional(readOnly)`**——读路由完全靠拦截器的 SQL 分析兜着。

## 6. Jobs 与关键机制

- **无 XXL-Job**；
- 启动预热：分类树（CacheWarmer）；**布隆异步加载**（分布式锁 + 分批 5000 + 批间 sleep 100ms，不阻塞启动，失败降级）；
- 管理端点：布隆重建（清空/误判率上升时，此前只能重启）；
- 线程池：`spu-async`(2/8/queue100/CallerRuns) 、`spu-delay-evict`(单线程调度)、`spu-view`(1/2/queue500/**DiscardPolicy**)；
- 埋点：浏览事件异步落库（可容忍丢失，绝不影响详情 RT）；
- **读写分离**：`spring.datasource.readwrite.enabled=true`（master 池 20 / slave 池 10 `readOnly`）；`management.health.db.ignore-routing-data-sources=true`（从库不参与健康判定）；SQL 分析路由由 common 拦截器完成；
- 启动自检：admin/internal token 未配置即拒绝启动（fail-closed）。

## 7. 现状边界与问题线索（仅记录，待讨论）

1. ⚠️ **建 SPU 默认直接上架**（`createSpu` 设 ON_SHELF）——与 `createSku` 注释宣称的流程（"建 SPU(下架)→加 SKU→上架"）不一致；"空商品可在架"（listSpu 只筛 ON_SHELF）待验证实际影响；
2. `t_sku.stock` 冗余占位（真库存在 inventory）——下单前置校验走 inventory，字段仅作初始化种子；
3. **缓存一致性无 Canal 失效通道**：商品 binlog 只进 search 索引线（`PRODUCT_INDEX_TOPIC`）；商品**缓存**无 Canal 直删，外部直改 DB 靠逻辑过期 30min/物理 2h 收敛——与库存"Canal 删缓存"是不同取舍；
4. 布隆**只增不减**：下架商品仍"可能存在"，靠空值缓存兜底（注释已记录）；
5. `initInventory` 失败**无自动补偿**（打点 + 管理端手动重试）；
6. 延迟双删只挂 `updateSpu`，不挂 `updateSpuStatus`/`createSku`——是否需要统一，待讨论；
7. 无商品审核流 / 无版本号 / 无操作审计（管理端内部工具定位）；
8. 埋点 `DiscardPolicy` 可丢（设计取舍，已注释）；
9. `t_spu` 无 creatorUserId（越权 TODO，非核心）；
10. **分类只读**：无分类写 API、无缓存失效机制——改 DB 后最长 2h 生效（注释自述）；
11. **AI 线直读商品库**：`ai-tools` 直接 SQL 查 `t_product_behavior`（跨库）——学习范围外，仅记录；
12. **主从延迟**：读写分离带来的天然读延迟（写后立即读可能读到旧值）——系统层默认存在，未见"强制读主"策略（如写后立刻回查场景），待讨论。

> 应然差距（属性体系 / 审核流 / 品牌库 / 多价格 / 定时上下架 / 版本留痕等）集中在 §2 对照表——均为"缺/简化"类，**待讨论**（修/讲/不做）。

### 8.3 缓存一致性（学习要点）

**延迟双删不是生产正解**（猜时间魔数、覆盖不了外部直改）；生产正解 = **binlog 驱动失效**（大厂标配：阿里精卫/美团 Databus；本项目库存同款）。
本项目最终形态（三层）：① afterCommit 立即删（快路径）② 删失败 MQ 兜底（写入侧）③ **Canal（binlog）→ 删缓存（最终保证）**。
终极强一致（版本号 CAS 回写）= 面试深水，记录不做。

### 8.4 记录不做（讲）

审核流/版本留痕（内部工具定位）；布隆只增（取舍）；强制主库（Canal 已收敛）；版本号 CAS；应然大差距（属性体系/多价格/品牌库/定时上下架——大工程）。
