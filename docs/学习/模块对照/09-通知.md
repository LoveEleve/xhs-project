# 09 · 通知（my-xhs-notification）· 梳理

> 系列：模块对照 · 阶段一（梳理）。**只记录，不讨论**（问题线索见 §7，待讨论）。
> 口径：标尺 = **真实社交平台通知管道该有的样子**（见 §2）。
> 规模：19 文件 / 2079 行。端口 19013。XXL executor 9990。深度档：**轻**（SSE 多实例机制密度高）。
> 建立：2026-10-12。

---

## 1. 定位与职责

**通知管道**：MQ 事件入 → 模板渲染 → **自然日聚合** → 未读计数（Redis）→ **SSE 实时推送（多实例定向路由）**；配套列表/已读 API。

**权威口径**（代码自述）："通知的权威来源是列表 API，SSE 只是实时加速"——SSE 即发即忘、失败不重试。

与上游关系：本模块**不生产事件**，消费 analytics（赞/关注）、content（评论）、order（订单状态）发的 `NOTIFICATION_TOPIC`。

## 2. 应然基准（标尺）与实然对照

| 应然能力 | 我们 | 差距 |
|---|---|---|
| 通知全链（事件→存储→实时→未读） | ✅ MQ + 模板渲染 + 聚合 + SSE + 未读计数全链路 | — |
| 幂等 | ✅ 两级：msgId Redis 幂等（24h；**失败删标记让 MQ 重试可重处理**）+ 聚合窗口锁；表**无天然唯一键**（注释自述，靠 Redis） | — |
| 聚合（防轰炸） | ✅ **自然日窗口**（对齐 DB `uk_aggregate`）+ Lua 原子 SETNX（PENDING 占位→真实 ID 替换）+ 聚合标题模板渲染 | — |
| 未读计数一致性 | ✅ 双键 Lua（total + type Hash，**hash tag 同 slot**）+ 防负 + 10 分钟对账（含"Redis 残留清零"兜底与 180 天保留） | — |
| 多实例实时推送 | ✅ 定向 Pub/Sub Channel + Redis 路由键 + 心跳保活——修复了两处"从未生效"级 bug（见 §4B） | — |

## 4. 核心链路

### A. 事件管道（NOTIFICATION_TOPIC → DB → SSE）

```
生产方：analytics（type 1 赞 / type 3 关注）、content（type 2 评论）、order（type 5 订单——新接入，
        同一订单"支付成功→已发货→退款到账"命中同一聚合键，ORDER 特例刷新 content/extra 到最新态）
NotificationEventConsumer（组 notification-event-consumer-group；两级幂等：msgId 24h + 聚合窗口锁；
        自己给自己跳过；失败删幂等标记 → 抛异常触发 MQ 重试）
→ buildNotification（t_push_template 渲染；模板本地缓存 5min TTL【T-130 修复永久缓存】）
→ aggregator.processWithAggregate（@Transactional【T-098：修复读写分离下"UPDATE 后读从库"的聚合计数滞后】）：
     窗口内首条：Lua SETNX 写入 PENDING → INSERT → 回填真实 ID
     后续：incrementAggregateCount + 重建聚合标题（"某某等 N 人…"）；PENDING 自旋重试 3 次
→ 仅"新建"未读 +1（聚合更新不 +1——用户已看过红点）
→ SSE：isOnlineAnywhere（本地 or Redis 路由）→ pushNotification + pushUnreadCount
```

### B. SSE 多实例（两步法鉴权 + 定向路由）

```
鉴权（EventSource 不能带 Header，防 Token 进 URL 日志/代理日志）：
    POST /sse/ticket（X-User-Id）→ 30s 一次性 ticket（getAndDelete 原子消费）
    GET /sse?ticket=xxx → 校验消费 → 建连
连接管理：单实例上限 50000（防打爆）；30min 兜底超时；put 原子替换旧连接；
    remove(key,value) 双参【C7：防旧连接回调误删新连接】；onCompletion/Timeout/Error 清理路由键
路由：myxhs:notification:sse:{userId} → serverId（IP:port#PID——【修复】原 System.getProperty("server.port")
    恒取默认值，同主机多实例 serverId 相同、路由无法区分）
跨实例：定向 Channel myxhs:notification:sse:channel:{serverId}（原为共享 Channel 广播，N-1 次无效投递）；
    JsonNode 保留原始 JSON【2026-09-20 修复：项目 Long→String 序列化下，原 parseLong(toString()) 必失败
    → 所有跨实例消息判"格式异常"→ 跨实例 SSE 从未生效（多实例实测）】
心跳：@Scheduled(10s) Pipeline 批量续期 + 客户端心跳探测；Redis 抖动异常隔离（原实现抛异常跳过死连接清理）
```

### C. 未读计数与对账

```
写：ATOMIC_INCR（INCR total + HINCRBY type + EXPIRE 30d 双键）/ SAFE_DECR_BOTH（防负）/ RESET_BY_TYPE（原子按类归零）
读：脏值安全（非法值按 0 记日志）
对账 unreadReconcileJob（XXL 0 */10 * * * ?，60s 超时）：
   id 游标扫全部未读通知（修复：userId 游标在 LIMIT 边界跳行【坑51】；全局累计修复"跨批覆盖自身制造错值"；
   退出条件按通知条数而非用户数）→ 每用户 Redis vs DB COUNT → 以 DB 为准 forceSetUnread
   → SCAN Redis 残留键（DB 已无未读 → 清零兜底）
   → 日清：180 天保留（SETNX 日切标记 + 40×5000 有界排空）
   限速：每批 50ms、残留扫描每 200 key 50ms
```

## 7. 现状边界与问题线索（仅记录，待讨论）

1. **文档-代码漂移**：`NotificationService.processEvent` javadoc 写"**5 分钟窗口**内合并"，实际是**自然日窗口**（`NotificationAggregator`，对齐 `uk_aggregate`）——注释未随实现更新；
2. **死物**：`t_push_task` 死表（零引用）+ `NotificationMapper.updateAggregateInfo` 死方法（已被 incrementAggregateCount + updateAggregateTitle 取代）；
3. **`forceSetUnread` 不设 TTL**：对账修复后的未读键无过期时间（与"30d 不活跃回收"设计不一致；要等下次 ATOMIC_INCR 才补 TTL）——小；
4. **聚合结构性取舍**（面试素材）：被聚合通知**不写 DB**（"存储层聚合"）——省 N 倍写入，代价是无法回溯每条明细（自述"可接受"）；
5. **表无天然唯一键**（注释自述）：幂等靠 Redis 双层；`uk_aggregate` 的 target_id 为 **NULL 时 MySQL 唯一索引不生效**（type=4 系统通知无 target，当前无生产方——理论缺口）；
6. **对账成本观察点**：`allUserTypeCounts` 全量驻留内存（全站未读按用户聚合）；残留清零对每个残留键做一次 DB COUNT（N+1）；全量扫未读表每 10 分钟一轮；
7. 小项：`resetUnreadByType` 每次 new 脚本对象（未复用 SHA1 缓存，其余脚本均静态）；ORDER 与社交聚合共用管道但走"内容刷新"分型（设计好样本）。

### 8.3 核心设计（学习要点）

- **消息级幂等键保留（F2）**：DLQ 重投由 broker 赋新 msgId → 消息级去重失效；重放时把原 msgId 放自定义属性，消费者幂等键优先取它——"重放已处理消息"被正确去重；
- **post-commit 失败策略（F3）**：抛出=重试重跑聚合（双计）；吞下=未读滞后但 10min 对账以 DB 为准收敛——**能对账收敛的步骤宁可吞，不能收敛的步骤必须抛**；
- **窗口锁自愈（F4）**：删键重选 > 回填（PENDING 场景无法判定"谁的 id 有效"）；自愈后最坏窗口 2 条独立行，不丢事件；
- **通知分级（F6）**：社交通知 best-effort（C-010 口径）/ 终结+状态通知 at-least-once（Outbox）——交易类不适用"可丢"；
- **SSE 定向 Channel 演进**：共享广播（N-1 无效投递）→ 按 serverId 定向发布（与 IM 路由模式一致）。

### 8.4 记录不做（讲）

聚合明细回溯（设计取舍）；SSE 心跳批量优化；uk_aggregate NULL（无生产方）；对账规模上限（内存聚合 + N+1）；推送平台（APNs/FCM 无需求）。
