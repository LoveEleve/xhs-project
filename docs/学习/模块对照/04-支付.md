# 04 · 支付（my-xhs-payment）· 梳理

> 系列：模块对照 · 阶段一（梳理）。**只记录，不讨论**（问题线索见 §7，待讨论）。
> 口径：标尺 = **真实电商支付域该有的样子（应然）**（见 §2）。
> 规模：37 文件 / 4779 行（目前最大）。端口 19012；XXL 执行器 9992。深度档：**深**。
> 建立：2026-10-11。

---

## 1. 定位与职责

**资金域**：支付单生命周期（创建/回调/超时）+ 退款生命周期（含部分退/多次退）+ **对账与结算**（渠道对账文件/日切账单/差异挂账）。

两个身份：

1. **交易链路的资金执行者**：order 发起 `pay` / `refund`；支付结果与退款结果**主动回推 order**（Feign 主 + MQ 备 + XXL 补偿）；
2. **独立资金账本**：`t_payment` / `t_refund` / `t_payment_event` / 结算三表——自己就是一套账。

真渠道以 **Mock 策略**代替（1 支付宝 / 2 微信 均为 Mock 异步实现 + 回调模拟器；99 = 同步 Mock）。

## 2. 应然基准（标尺）与实然对照

| 应然能力 | 我们 | 差距 |
|---|---|---|
| 支付单与状态机（多渠道/多次尝试） | ⚠️ 单渠道、**单次尝试**（paying 键 + status 缓存挡住重试；注释自述"重新支付需重新下单"） | 简化 |
| 渠道对接（签名/验签/证书） | ❌ **无签名验签**（Mock 策略；回调仅 X-Internal-Call，模拟器直调 service） | 环境缺口（真接入必补） |
| 回调处理（幂等/三态/乱序） | ✅ 乐观锁 + **三态解析**（未知→让渠道重试）+ **迟到成功翻转**（2→1） | 超配 |
| 结果通知可靠性（同步+异步+补偿+对账） | ✅ **四层**：Feign 主 → MQ 备 → XXL 补偿（5min 窗口）→ 对账 Job | 超配 |
| 退款（部分/多次退、累计可退、全退通知） | ✅ 累计退款 = `SUM(status=1)`；可退 = 支付额 − 已退；全退置"已退款"、部分退保持可续退（T-076）；全退才通知订单（T-077） | 完备（含 1 处已知缺口） |
| 超时处理（支付/退款） | ✅ 支付 30min 置失败（T-062 修复 DB 扫描）；退款 15 天关闭 | 完备 |
| **对账与结算**（渠道文件/日切账单/差异挂账） | ✅ `t_channel_flow` + `t_settlement_bill` + `t_settlement_diff`：日切账单（幂等重跑/run_no）、三类差异挂账、人工处理不覆盖、**演练扰动**（Perturb） | 超配 |
| 组合支付 / 余额 / 积分抵扣 | ❌ 无（仅支持"全额券=零元单"特殊直记成功路径） | 缺 |

## 3. 数据模型

| 表 | 关键字段 | 约束 |
|---|---|---|
| `t_payment` | order_id / user_id / payment_no / amount / pay_type(1/2/99) / status(0待/1成功/2失败/3已退款) / paid_at | **UNIQUE `uk_payment_no`** |
| `t_refund` | payment_id / order_id / user_id / refund_no / refund_amount / status(0退款中/1成功/2失败/3关闭) / refund_type / refund_channel / success_at | **UNIQUE `uk_refund_no`** |
| `t_payment_event` | payment_no / order_id / event_type(CREATE/PAY_SUCCESS/PAY_FAIL/REFUND/TIMEOUT) / error_code / error_msg / event_time | append-only |
| `t_settlement_bill` | bill_date / channel / run_no / 金额字段 / status | **UNIQUE `uk_bill_date_channel`**（幂等重跑） |
| `t_settlement_diff` | 差异三类（本地有渠道无/渠道有本地无/金额不一致）/ diff_key / 处理状态 | **UNIQUE `uk_diff_key`** |
| `t_channel_flow` | 渠道对账文件落库流水 | **UNIQUE `uk_channel_no`** |

**Redis**：`myxhs:payment:paying:{orderId}`（30min）、`myxhs:payment:refunding:{paymentId}`（7d）、`myxhs:payment:status:{orderId}`（7d）、`myxhs:lock:payment:pay|refund:{id}`（Redisson）、`myxhs:payment:callback:pending:{payType}:{paymentNo}`（24h）、`myxhs:lock:payment:timeout-check|refund-timeout-check|reconcile`、`myxhs:settlement:statement:{…}`。

## 4. 核心链路

### A. 创建支付（`pay`）

```
Redisson 锁(orderId) → 双重检查 status 缓存
→ 【P1-1】回查订单：状态必须=待付款（拿不到状态 → 拒付）
→ 金额比对：请求金额 == 订单实付（/pay-amount）
→ 插支付单(status=0) + Redis paying/status 键
→ 零元单(全额抵扣)：跳过渠道直记成功
→ strategy.pay()（99 同步 Mock；1/2 Mock 异步 → 注册回调模拟器）
失败清理：Redis 键 + DELETE 支付记录（WHERE status=0）
```

### B. 支付回调（`handlePayCallback`）

- **三态解析**：1=成功 / 0=明确失败 / **-1=无法解析或中间态 → 返回 fail 让渠道重试**（防把格式不符的成功回调判成失败）；
- **迟到成功翻转**（精品修复）：支付超时 Job 已置失败(2)，但渠道实际成功 → 条件翻转 2→1 → 直接调 `afterPaySuccess`（绕过 `WHERE status=0` 守卫）→ 订单若已取消 → 业务拒绝 → **自动退款**；
- `afterPaySuccess` 副作用顺序：**先 Feign 通知 order** → 若 `businessRejected`（明确业务失败，非 503）→ **自动全额退款**（P1-1 钱货两空防护）；订单接受或瞬态失败 → 发 `PAY_RESULT_TOPIC`（业务拒绝时不发 MQ，防退款后乱序）。

### C. 回调模拟器（真渠道未接入的替身）

- 支付回调：注册键 TTL **24h**、主循环 `@Scheduled 5s` SCAN + SETNX 锁、随机延迟 1~3s、**90% 成功率**（硬编码常量）；
- 退款回调（T-075 补）：注册键 TTL 5min——修复前"退款永不回调 → 退款单卡退款中"。

### D. 退款（`doRefund` / `handleRefundSuccessInternal`）

```
Redisson 锁 + refunding 标记（7d）→ 归属校验 → 可退金额 = 支付额 − SUM(成功退款)
→ 插退款单(0) → 策略退款（99 同步成功 / 1/2 注册退款回调）
成功后：退款单→1；累计退款==支付额 → 支付单→3（部分退保持 1 可续退，T-076）
→ 删 refunding 标记 → 缓存 status
→ 仅全额退款：sendRefundResultMq + Feign notifyRefundSuccess（T-077 对称化）
```

### E. 超时（两个 Job）

- `checkPaymentTimeout`（T-062 修复）：DB 扫描 `status=0 AND created_at<now-30min` 分批 100 → 乐观锁置 2 + Redis 同步 + TIMEOUT 事件（原实现 SCAN Redis 恒真判定 + 只改 Redis → 修复）；
- `checkRefundTimeout`：退款中 >15 天 → 关闭 + 删标记 + 发退款失败结果。

### F. 补偿与对账（四层通知的最后两层）

| Job | cron | 逻辑 |
|---|---|---|
| `paymentNotifyCompensateJob` | `0 0/2 * * * ?` | 扫支付成功 >5min → 查订单（pay-amount 判态）→ 仍待付款 → 重发 notifyPaySuccess；503/瞬态不清计数**防永久漏补偿** |
| `refundNotifyCompensateJob` | `0 0/3 * * * ?` | 同型（退款通知） |
| `paymentReconcileJob` | `0 0 3 * * ?`（FIRE_ONCE_NOW） | `PaymentService.reconcile()`：扫 status=1 支付单 → 查订单 → 不一致则补偿通知（**原实现无调度入口=死代码**，后补 Job） |

### G. 结算域（`SettlementService`，独立一套）

- **日切账单**：`generateDailyBill`——唯一键 (日期,渠道) 幂等重跑；已对账账单必须 `force=true` 才重算；`run_no` 记重跑次数；金额口径：**手续费按收款毛额计提（退款不退手续费，与渠道计费一致）**，`settle = (pay − refund) − fee`；SQL 聚合不拉明细进 JVM；
- **三方对账**：`t_channel_flow` 落库后逐笔比对（渠道行驱动 → 本地分页扫描，游标 (time,id)，安全阀 1000×500 页）→ 三类差异挂账；**同一商户单号多行报差异**（防覆盖）；**人工已处理不被覆盖**；本轮消失的差异收敛"已忽略"（>500 笔跳过收敛）；**对账单未到则跳过对账**（statement marker，防"全量本地有渠道无"假差异）；账单状态 = **待处理挂账余额**（人工清完自然回到"已对账"）；
- **人工处理**：`handleDiff` 只改状态、**不自动补单**（金额影响次日账单）；`voidBill` 作废后可重开（run_no 继续累计）；
- **演练扰动**：`Perturb` NONE / MISSING（删末行）/ EXTRA（造 100.00 渠道多记行）/ AMOUNT（首行 +0.01）——内置通道验证对账闭环；重跑前清旧演练流水；
- **并发与标记**：生成/对账共用 (日期,渠道) SETNX 锁（5min + token 释放）；**对账单到账标记写入失败则整体回滚**（防"流水已入库但对账永久跳过"）；标记 TTL 30 天。

### H. 事件流水

`t_payment_event` append-only（CREATE/PAY_SUCCESS/PAY_FAIL/REFUND/TIMEOUT/异常原因码）；独立线程池 + DiscardPolicy（**队列满拒绝时打 ERROR 日志**——"可丢但不可静默"）。

## 7. 现状边界与问题线索（仅记录，待讨论）

1. **支付侧自消费消费者是默认关闭的占位**（`@ConditionalOnProperty` + 仅日志）——预留/死代码（`PayResultConsumer`/`RefundResultConsumer`）；
2. **注释漂移**：T-077 注释称"order 无 REFUND_RESULT_TOPIC 消费者 / 当前无消费端"——order 侧后来补了 `RefundResultConsumer`/`PayResultConsumer`（00 报告 P3 同型）；
3. **退款域自身无幂等键**：`refundByOrder` 无 out 键防重（修复在订单侧"重试前查支付事实"；支付域内仍留"部分退款+响应丢失"的理论窗口）——与 `订单-侦察/03-修复记录` 呼应，此处正式挂账；
4. **回调验签缺失**（演示口径：Mock 渠道 + 模拟器直调 service 不经过 HTTP/验签；真实接渠道必须补签名校验）；
5. 模拟器参数硬编码（90% 成功率、1~3s 延迟）——测试参数未配置化；
6. **单次尝试支付模型**：paying 键 + status 缓存挡住"换渠道重试"（注释自述"重新支付需重新下单"）；
7. `checkPaymentTimeout` 的 Redis 锁 TTL 5min（>任务周期 30s）——单实例执行窗口宽松，靠乐观锁防重（同 `refund` 60s 锁）;
8. 结算差异的"自动收敛为已忽略"（本轮消失的差异）——语义待复核（人工处理中差异消失是否误收敛）；
9. **死配置**：yml `pay.timeout.ms: 1800000` 与 `refund.timeout.days: 15` **未接代码**——`PaymentService` 用硬编码常量（`PAY_TIMEOUT_MS`、`minusDays(15)`），改配置不生效（"配置漂移"家族新成员；已正确对接的配置：`myxhs.settlement.channels`、`feeRate`）。
