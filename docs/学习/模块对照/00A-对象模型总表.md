## 附 3 · 盘点观察（自动抽取时发现，待讨论）

1. **coupon 库混入 content 域两表 → 初判 init-all 库段错位**：`t_local_message` / `t_note_event` 在 init-all 的 coupon 段（526/543 行），但 `mysql-content-init.sql` 明确 "放在 my_xhs_content 库"、content 运行时（NoteService）按 content 库写这两表——**按 init-all 引导会造成 content 库缺表**（待 05 内容梳理 / 部署篇定论）；
2. **search 模块无自有 MySQL 库**：索引在 ES；数据源引用 `content.t_user_behavior`；
3. inventory 库含 `t_tcc_fence` / `t_tcc_freeze_detail`（TCC 域已排除，但表在位——仅记录）；
4. **双 SQL 基线命名漂移**：迁移目录与 `mysql-content-init.sql` 里是 `t_hot_search`，`init-all.sql`（docker-compose 挂载的引导脚本）是 `t_hot_search_snapshot`——初始化以 init-all 为准，迁移脚本为旧版（同订单域 V1 与 init-all 的差异同型）；
5. **common `RedisKeyConstants` 半死**：53 个常量中 38 活 / **15 死**（`CART` / `INVENTORY_PRE` / `INVENTORY_STOCK` / `COUPON_STOCK` / `COUPON_USER` / `PRODUCT_SKU` / `NOTE_COUNT` / `SEARCH_SUGGEST` / `COUNTER_BUFFER` 等）——**交易域各模块实际在模块内硬编码键**；只有 user / search / feed / counter / social 域真正在用统一常量。常量治理半途而废的典型（面试可讲"规范 vs 现实"）。
