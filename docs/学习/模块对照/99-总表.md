## 3. 应然-实然一行索引（最强面 / 最大缺口）

| 模块 | 最强面（可讲点） | 最大缺口/观察（阶段二素材） |
|---|---|---|
| 商品 | 缓存三件套：逻辑过期多级 + 布隆防穿透 + 双删&预热 | 建 SPU 默认直接上架（与宣称流程不符，§7-1） |
| 购物车 | 顺序消息 + CLEAR 屏障 + 对账（与库存同族） | **下单后不自动清车**（真实电商会移除） |
| 优惠券 | 双库存模型 + RV30 退券语义（防超发+防绕限领） | 死常量/cron 漂移；T-058 过期券坑 |
| 支付 | 四层通知（Feign 主+MQ 备+XXL 补偿+对账）+ 结算域 | 两个自消费消费者默认关闭（占位/死代码）+ 注释漂移 |
| 内容 | DFA 敏感词全机制 + 本地消息（同事务）+ 双段 Feed 补偿 | **`t_note_event` 建表缺失（事件静默丢失）**；审核半闭环 |
| 搜索 | Canal 双通道 + external version + 5 路召回 | **无别名切换**（面试材料需勘误）；**搜索零限流** |
| 计数 | Buffer-Trigger（满100/5s/双Buffer/回写）+ Lua 去重 + 双对账 | like 集合重建缺失（§7-8 B）；**防清零守卫已修（10-12）** |
| 社交分析 | 双源保护 + MySQL 重建 + 统一消费组（跨组乱序修复） | like/favorite 无重建；**修复颤振**（§7-9）；三代计数 |
| 通知 | SSE 定向路由（两处"从未生效"级修复）+ 自然日聚合 + 未读对账 | 文档漂移（5min vs 自然日）；t_push_task 死表 |
| 私信 | at-least-once（先落离线+ACK）+ 跨实例踢线 + 会话锁 | 一致性哈希 LB **未接线**；unread/seq 无 TTL |
| home BFF | 推拉混合 Feed（断点续推）+ 2 层并行聚合 + 降级分层 | 大V判定双处同构；卡片字段硬编码；**无 @RateLimit** |
| gateway | 8 过滤器 + 16 路由 QPS（注释带实测余量）+ HMAC 完整设计 | 灰度/版本**实例过滤未实现**（半成品）；用户级限流未实现；HMAC 默认关 |
| 订单 | 状态机 + 补偿自循环修复 + P0 注解错位修复 | 退补口径 `max(a,b)` 待设计（遗留） |
| 库存 | prededuct/bucket/版本门/T-066 自愈/热点 resize | TCC 域排除；cron 漂移家族成员 |

## 4. 跨模块机制家族（横向对比 = 学习/面试主线）

| 家族 | 成员（模块：物件） | 一句话 |
|---|---|---|
| **A. 幂等四件套** | msgId Redis 幂等（common/counter/notification）；DB 唯一键（analytics/im/order）；SETNX 窗口锁（notification 聚合）；@Idempotent AOP（analytics/product/coupon）；Lua 原子"去重+业务"（counter） | 面试必答：至少能讲出"为什么单纯 SETNX 不够" |
| **B. 乱序治理/版本门** | 库存（`inventory:event:version:*`/`canal:version`）；analytics 消费端（`analytics:event:version:like/favorite`）；counter（`counter:event:version:like/favorite/comment/follow`） | 四处同构不同实现——"事件版本门"模式复用的最佳样本 |
| **C. 对账/重建** | 24 个 XXL + @Scheduled 群：inventoryReconcile/cartReconcile/couponReconcile/counterReconcile/unreadReconcile/followCounterRepair/paymentReconcile/settlementReconcile/feedCleanup/orderMappingRepair/aftersaleRecovery/orderEventCalibration… | 全系统"以谁为准"的裁决表（Redis 权威/DB 权威/双源保护）——分布式一致性主线 |
| **D. 定向 Pub/Sub** | notification SSE channel（每实例一 Channel）；im route channel（M4：替代 MQ 广播 N-1 浪费） | "广播→定向"演进 + 即发即忘语义的配套（列表 API 才是权威） |
| **E. 缓存治理** | product 逻辑过期+布隆+双删+预热；search suggest 空值短 TTL；inventory 热点 resize；30d TTL 续期治理（like set/counter/未读） | TTL 治理代际差异（部分模块有、部分无——im unread/seq） |
| **F. 消息可靠投递** | order：Outbox（t_local_message）+ 补偿 Job + DLQ 扫描；coupon Outbox 补发；Feign 主+MQ 备+XXL 补偿（payment）；at-least-once（im） | "至少一次 + 消费端幂等"是全系统统一哲学 |
| **G. Lua 原子脚本** | ~30 个：counter(3)+analytics(10)+inventory(6)+notification(4)+im/gateway(2) 等 | 原子边界设计样本（单 Key/双 Key/hash tag 同 slot） |
| **H. 死代码/化石家族** | counter（DECREMENT_SCRIPT 等 5 处）；analytics（2-key Lua/FollowEvent）；notification（t_push_task）；im（一致性哈希 LB 未接线）；gateway（灰度/版本半成品）；common（15 死常量） | "设计超前于接线"的系统性现象——面试可讲"如何识别与治理" |
| **I. cron 漂移家族** | 库存/购物车/优惠券/counter/analytics——**job javadoc 写 X，init-xxljob.sql 注册 Y** | 注释与注册表是两套真相——修复规范观察 |
| **J. 键治理家族** | hash tag（notification/im 双键 Lua 同 slot）；`myxhs:` 前缀统一 vs 硬编码（counter like:set、im channel）；RedisKeyConstants 53 常量 38 活/15 死 | 命名规范与现实的差距标本 |

## 6. 阶段二讨论入口（全模块 §7 汇总的"大项"）

1. **计数/社交域**：like 集合重建（07 §7-8 B）+ 修复颤振（08 §7-9）+ 三代计数治理（08 §7-1）；
2. **内容域**：`t_note_event` 建表修复（部署正确性）；审核队列（应然差距）；
3. **防护面**：搜索/home/counter-batch-get **零限流端点**（网关只兜路由级 QPS——按用户维度仍无）；
4. **网关半成品**：灰度/版本实例过滤（LB 未实现）；用户级限流；
5. **交易域遗留**：退补口径 `max(a,b)`；购物车下单不清车；
6. **一致性质量**：cron 漂移统一（5 模块）；死代码/注释漂移批次治理；
7. **搜索**：无别名切换（+ `50-Canal` 面试材料勘误）；
8. **IM**：unread/seq 无 TTL + 无对账兜底。

## 7. 建议学习顺序（三条主线）

1. **交易主线**（状态/资金/库存最强）：product → cart → coupon → order（家底）→ payment → inventory（家底）——讲"一单的生命周期"；
2. **内容分发主线**（流量最大）：content → home Feed（推拉混合）→ search（索引供给）→ counter（计数）→ analytics/notification（状态与触达）；
3. **横向机制主线**（面试差异化的关键）：§4 的 A-J 家族逐家族跨模块对比——每个家族都能独立成篇（如"全系统幂等的 5 种实现与取舍"）。

> 用法：学每个模块先读其 §2（应然表：真实系统该有什么）+ §7（线索：我们的差距）；阶段二讨论时按 §6 清单逐条翻牌定论。
