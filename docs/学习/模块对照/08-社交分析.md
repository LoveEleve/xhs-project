# 08 · 社交分析（my-xhs-analytics）· 梳理

> 系列：模块对照 · 阶段一（梳理）。**只记录，不讨论**（问题线索见 §7，待讨论）。
> 口径：标尺 = **真实社交平台"互动状态/关系/计数"该有的样子**（见 §2）。
> 规模：28 文件 / 3110 行（FollowService 823 为主）。端口 19003。XXL executor 9999。深度档：**轻**（但三域对账/重建机制密度高）。
> 建立：2026-10-12。
> 深挖轮（10-12）：28 文件全核 + 生产/消费/测试三方对照，§7-9~13 为补录。

## 1. 定位与职责

**社交互动"状态与关系"的权威层**（管状态，不管计数——计数归 counter）：

1. **写**：Redis 权威（Set/ZSet）+ Lua 原子脚本 + 同步发 `SOCIAL_TOPIC` 事件（供 counter/search/通知消费）；
2. **持久**：`t_like`/`t_favorite` 经 **MQ 异步落库**（消费端版本门幂等）；`t_follow` **服务内同步落库**（MQ 消费者存在但**默认禁用**）；
3. **修复**：关注域全套对账/重建（含双源保护）；**点赞/收藏域无任何重建**（不对称，见 §7-2）。

与 counter 分工：analytics = 状态+关系（权威），counter = 计数（消费其事件）。**注意："analytics 权威 Set" 就是本模块的 `myxhs:like:note/:comment:`**（07 §7-8 的 B 方案落点即本域）。

## 2. 应然基准（标尺）与实然对照

| 应然能力 | 我们 | 差距 |
|---|---|---|
| 互动状态权威写入（幂等） | ✅ `SISMEMBER+SADD` / `ZSCORE+ZADD` 原子脚本；DB 唯一索引兜底（`DuplicateKeyException` 幂等忽略） | — |
| 乱序治理 | ✅ **统一消费组**（修复"LIKE/UNLIKE 分属两组 → 跨组乱序"）+ 消费端版本门（`analytics:event:version:like:/favorite:`，actionTime 原子比较 TTL 24h；**业务失败删版本 key 让 MQ 重试可重处理**） | — |
| 关注关系双索引/分页/互关 | ✅ 关注列表+粉丝列表 ZSet（score=时间）；列表分页 clamp（防大V全量）；互关用 Pipeline 批量 ZSCORE；共同关注 intersectAndStore（30s 临时键 + finally 清理） | — |
| 关系对账/重建 | ✅ follow 全套：ZCARD 校准 + **双源保护**（redis < mysql×0.5 → 跳过删除；redis=0 → 按 MySQL 重建 ZSet；>10000 条只告警）+ 绝对值同步 counter | **like/favorite 无重建**（`t_like` 行数据无消费者） |
| 写失败一致性口径 | ⚠️ 模式分裂：正向动作（like/favorite）MQ 失败**不回滚**；逆向动作（unlike/unfavorite）失败**回滚+抛异常**；follow 落库失败仅日志 | 见 §7-3 |

## 3. 数据模型

**自有库 `my_xhs_analytics`**（3306/3307，readwrite=true）：

| 表 | 键 | 说明 |
|---|---|---|
| `t_like` | `uk_user_biz(user_id,biz_type,biz_id)`、`idx_biz(biz_type,biz_id)` | biz_type 1笔记/2评论 |
| `t_favorite` | `uk_user_note(user_id,note_id)`、`idx_note_id` | 收藏 |
| `t_follow` | `uk_user_follow(user_id,follow_user_id)`、`idx_follow_user_id` | 关注（user→follow_user） |

**Redis 键**（8 组）：

| 键 | 用途 |
|---|---|
| `myxhs:like:note:{id}` / `myxhs:like:comment:{id}` | 点赞**正索引**（Set，member=userId；**30d TTL 续期**——2026-09-19 治理） |
| `myxhs:like:user:{uid}:note` | 点赞**反索引**（Set，member=noteId；仅笔记，评论无） |
| `myxhs:favorite:{uid}` | 收藏列表（ZSet，member=noteId，score=时间） |
| `myxhs:follow:list:{uid}` / `myxhs:follow:fans:{uid}` | 关注/粉丝（ZSet，score=时间戳） |
| `myxhs:counter:user_following:{uid}` / `user_follower:{uid}` | **analytics 自有**关注计数（String，Lua 内 INCR/DECR） |
| `myxhs:counter:2:{uid}:7` / `:6` | **counter 模块**的关注/粉丝计数（job 绝对覆盖写，见 §7-1） |
| `analytics:event:version:like:{uid}:{bizType}:{bizId}` / `...:favorite:{uid}:{noteId}` | 消费端版本门（TTL 24h） |
| `myxhs:user:block:{uid}` | 拉黑 Set——**user 域写、analytics 直读**（T-016 跨域键依赖） |

## 4. 核心链路

### A. 点赞（LikeService 480 行）

```
LIKE：validateTarget（content Feign，fail-closed：异常抛 SERVICE_UNAVAILABLE）
  → likeForwardAtomicScript（SISMEMBER→SADD，幂等）
  → 反索引 SADD myxhs:like:user:{uid}:note（仅笔记）
  → renewLikeSetTtl（likeKey+userLikeKey 30d）→ 通知 type=1（自赞跳过，async）
  → sendLikeEventSync（3s；**失败不回滚**，注释理由：防"Broker 已消费但回滚"导致 Redis/DB 不一致）
UNLIKE：反向 Lua（SREM）→ 反索引 SREM → syncSend **失败回滚（SADD 恢复）+ 抛异常**
消费：LikeUnlikeConsumer（组 like-unlike-consumer-group）→ 版本门
  → LIKE：t_like insert（DuplicateKey 幂等）/ UNLIKE：deleteByUserAndBiz
```

### B. 收藏（FavoriteService 237 行）

```
favorite：校验笔记（batch-detail，fail-closed）→ favoriteAtomicScript（ZSCORE+ZADD）→ syncSend（失败不回滚）
unfavorite：先读 originalScore → unfavoriteAtomicScript（ZSCORE+ZREM）
  → syncSend 失败 → 回滚 ZADD（**用原始 score** 防排序跳变）+ 抛异常
列表：ZSet 分页 + ZCARD 计数；消费：FavoriteUnlikeConsumer（同组修复/幂等）
```

### C. 关注（FollowService 823 行）

```
follow：不能自关 → T-013 用户存在校验（Feign fail-closed）→ T-016 拉黑检查（读 Redis，fail-open 放行）
  → self Lua（ZSCORE 防重 → ZADD + INCR 关注数）
  → target Lua（写粉丝侧，失败容忍——"对账修复"）
  → t_follow 同步落库（失败容忍）→ MQ FOLLOW（syncSend 3s）→ 通知 type=3
unfollow 对称（双脚本 + 删 t_follow + MQ UNFOLLOW）
读：列表（ZSet 分页 + 互关 Pipeline）/ 共同关注（intersectAndStore）/ isFollowing（ZSCORE）/ 计数（自有键）
```

### D. 对账与重建（followCounterRepairJob，每 10 分钟）

```
repairUserCounters：ZCARD 校准计数（ZSet=0 但计数>0 → 先按 MySQL 重建；重建>上限 → 标 unknown 跳过）
repairUserRelationships / repairFollowerRelationships：Redis↔MySQL 补插/清孤儿行 + 双源保护
  （redis=0 → MySQL 重建 ZSet；redis<mysql×0.5 → 跳过删除；部分缺失 → 只报告待人工核对）
syncCountersToCounterModule：**绝对覆盖** counter 的 2:{uid}:7|6（单命令 SET+30d TTL；注释自述"绕过 counter 增量/去重语义，已登记待改造"）
```

## 7. 现状边界与问题线索（仅记录，待讨论）

1. **关注的"三代计数"**：① analytics 自有 `myxhs:counter:user_following:`（**主页实际读这个**——home UserProfileAggService → AnalyticsFeignClient）；② counter 模块 `2:{uid}:6/7`（counter 消费 FOLLOW 事件增量写 + 本 job **绝对覆盖**写；**当前服务间未见读取方**）；③ t_follow 行数（重建基准）。job 绝对覆盖绕过 counter 版本门/dedup 语义（自述待改造），且每 10 分钟抹平一次——与 counter 事件并发时存在漂移窗口（观察点）；
2. **like/favorite 无重建**（与 follow 不对称）：t_like/t_favorite 行数据无任何重建/校准 Job——07 §7-8 B 方案（从 t_like 重建 like 集合）落点即本域；favorite 同理（注意：favorite 无 Set 语义、纯 ZSet 用户列表，重建面不同）；
3. **写失败口径分裂**：正向（like/favorite）MQ 失败不回滚（防"Broker 已消费"）；逆向（unlike/unfavorite）失败回滚+抛异常。like 注释称"MQ 真正未送达时用户重试即可"——但重试会命中幂等提前返回（SADD=0 → 直接 return）**不会重发事件**，实际依赖"取消再赞"或数据永缺（观察点；不回滚为有意行为、单测已固化——见 §7-10②）；
4. **Follow 双写者**：同步服务写 + MQ 消费者（默认禁用）；若启用则双写重复（唯一索引兜底，日志噪音）——命中"演化中间态"家族；
5. **M6 注释失真**：Lua 注释写 `social:following:{userId}` + "hash tag 保证同 slot"，实际键 `myxhs:follow:list:{userId}` **无 hash tag**、名称也不符——sentinel 部署无影响，但注释误导（若真上 Cluster 需补 hash tag）；
6. **cron 漂移 +1**：FollowCounterRepairJob javadoc "每小时" vs 注册表 `0 */10 * * * ?`（每 10 分钟，60s 超时/SERIAL）——漂移家族第 4 员；全量扫 t_follow 每个周期跑（用户量大时成本观察点）；
7. **死脚本/死 bean**：`likeAtomicScript`/`unlikeAtomicScript`（2-key 版，`like_atomic.lua`/`unlike_atomic.lua`）零调用——被 forward-only 单键版替代（Cluster 兼容改造弃子）；
8. 小项：拉黑读取 fail-open（读失败放行）/ 用户校验 fail-closed（拒）；通知"用户"类型 targetType 置 null（R5 语义债）；`myxhs:user:block:` 跨域键直读（user 域写）。
9. ★ **修复链路"删除↔插回"颤振（深挖轮主要新发现）**：粉丝侧对账把"MySQL 有、Redis 无"一律当"取关残留"清行（其 javadoc 自述是为修"Step B 失败"）；但同一状态也可由 **follow 的 Step B（粉丝侧 Lua）失败**造成——此时关注侧对账（repairUserRelationships）又把行插回。**两侧修复在同一 Job 周期互相打架：每 10 分钟"删行↔插回"颤振、永不收敛**（触发：Step B 曾失败 + 粉丝列表非空且缺失比例 < 双源阈值 50%——典型"大V 少一个粉丝"；若粉丝列表空/过半缺失会走重建路径反而自愈）。根治方向待讨论（粉丝侧按 t_follow 补员 / 对账引入"另一侧证据"判别）；
10. **LikeService 注释-代码矛盾 ×2**：① 类 javadoc 称反索引 `myxhs:like:user:{uid}:note` "已移除、无写入/读取方"——**代码三处仍在写**（like/unlike/回滚），且全仓确无读取方（write-only 键，白耗 Redis 操作 + 30d TTL 续期）；② `like()` javadoc 称"MQ 发送失败 → 回滚 Redis"，实际**不回滚**（仅日志）——单测两条反向确证不回滚是**有意行为**，是 javadoc 未随行为变更更新；
11. **Lua 注释债**：`favorite_atomic.lua` 注释键名写 `favorite:set:{userId}`（实际 `myxhs:favorite:{userId}`）；`unfavorite_atomic.lua` 注释称"ZSCORE+ZREM+**ZCARD 修正**"（脚本实际无 ZCARD）——与 §7-5（M6 hash tag）同家族；
12. **死 DTO**：`FollowEvent` 零引用（FollowService/FollowConsumer 均用 Map）——死代码家庭 +1（承接 §7-7 死脚本）；
13. **测试覆盖（正向面）**：3 个服务测试共 15 条（like 7 / favorite 4 / follow 4），覆盖"不回滚 vs 回滚"、幂等、MQ 失败分支——机制行为有自动化固化（对比 07 计数的浅测试）；未覆盖：对账/重建/Job/消费者/并发。
