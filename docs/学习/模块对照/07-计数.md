## 1. 定位与职责

**全站互动计数的读写底座**（七类：点赞 1 / 收藏 2 / 评论 3 / 分享 4 / 浏览 5 / 粉丝 6 / 关注 7），纯底座——不生产事件、不依赖任何其他模块：

1. **写路径**：消费 `SOCIAL_TOPIC` 10 个 Tag → Redis 原子去重 + 实时增减 → **CounterBuffer 攒批** → 批量 upsert `t_counter`；
2. **读路径**：Redis → MySQL 两级缓存；单查 + Pipeline 批量（home BFF 四个聚合服务在调）；
3. **一致性**：两级对账——**DB 基准对账**（reconcile）+ **analytics 权威对账**（like 计数读权威 Set SCARD 覆盖）。

数据面：自有库 `my_xhs_counter`（单表）。**双 Set 体系**：analytics 权威 Set（`myxhs:like:note:/comment:`，counter 只读）vs counter 内部优化 Set（`myxhs:like:set:{type}:{id}`，懒迁移桥接）。

## 2. 应然基准（标尺）与实然对照

| 应然能力 | 我们 | 差距 |
|---|---|---|
| 高频计数写（实时可见 + 不压垮 DB） | ✅ Redis 实时 + Buffer-Trigger 攒批（满 100 条 / 5s；合并同 Key；注释例：1 万次点赞 → 合并后一次批量 SQL） | — |
| MQ 幂等 | ✅ **Lua 原子「msgId 去重 + 增减」同执行单元**（消除"去重成功但计数未执行"竞态窗口；dedup TTL 2h）；重复消息静默 ACK 不重试 | — |
| 乱序收敛 | ✅ **Set-based**（点赞 SADD/SREM + SCARD 天然可交换）+ **版本门四家族**（like/favorite/comment/follow，actionTime 原子比较，TTL 24h）——"后到的旧 UNLIKE"实测会把计数改回 0，故 Set 之上还要版本门 | 完善度超一般 |
| 对账修复 | ✅ 双对账：DB 基准（游标 1000/批 + Pipeline multiGet【m20】；不一致以 Redis 为准、Redis=0 以 DB 恢复）+ analytics 权威（SCARD 修正 + **T-113 同步 DB**） | — |
| 计数不丢不超发 | ⚠️ Buffer 失败重试 3 次 → **回写缓冲**（注释：丢了没人补）；归零保护拒负；但**关注双向计数非原子**（手工回滚） | 见 §7-2 |

> 本模块是全项目机制密度最高的单位文件模块：Lua×3、版本门×4、双 Buffer、回写兜底、双对账——轻档模块里的重矿区。

## 3. 数据模型

**自有库 `my_xhs_counter`**（master 3306 / slave 3307，复用读写分离底座）：

| 表 | 列 | 键 | 说明 |
|---|---|---|---|
| `t_counter` | id / target_type / target_id / count_type / count_value / deleted / created_at / updated_at（8 列） | `uk_target_count(target_type,target_id,count_type)` | 唯一索引 = 刷盘 upsert 依据。DDL 注释 target_type 只写"1-笔记 2-用户"（枚举实际 1/2/3/4，小债） |

**枚举**：CountType 1 点赞 / 2 收藏 / 3 评论 / 4 分享 / 5 浏览 / 6 粉丝 / 7 关注；TargetType 1 笔记 / 2 用户 / 3 评论 / 4 商品。

**Redis 键**（两代命名混用——`counter:*` 走统一常量，`like:set:` 硬编码）：

| 键 | 用途 |
|---|---|
| `myxhs:counter:{targetType}:{targetId}:{countType}` | 计数值（每次写续期 30d；读回填单命令 SET+TTL） |
| `myxhs:counter:dedup:{msgId}` | MQ 去重标记（TTL 2h = 覆盖最大重试窗口） |
| `myxhs:like:set:{targetType}:{targetId}` | counter 内部点赞 Set（展示优化缓存；TTL 30d，2026-09-19 review 补） |
| `myxhs:like:note:{id}` / `myxhs:like:comment:{id}` | **analytics 权威 Set**（counter 只读：懒迁移 + 对账数据源） |
| `myxhs:counter:event:version:like:{userId}:{bizType}:{bizId}` | 点赞版本门（TTL 24h） |
| `...:favorite:{userId}:{noteId}` / `...:comment:{commentId}` / `...:follow:{follower}:{followee}` | 收藏 / 评论 / 关注版本门（同族同构） |

## 4. 核心链路

### A. 写链路（SOCIAL_TOPIC → Lua → Buffer → DB）

```
CounterEventConsumer（10 tags 全量订阅——各消费方中最宽；组 counter-consumer-group；maxReconsumeTimes=3）
  事件映射：
    LIKE/UNLIKE     bizType=1→笔记赞(t1/c1)；bizType=2→评论赞(t3/c1)【H4】——走 Set-based 路径
    FAVORITE/UNFAVORITE → 笔记收藏(t1/c2)——delta 路径
    COMMENT/UNCOMMENT   → 笔记评论(t1/c3)【R1】；UNCOMMENT 带 count 级联删除按 N 递减【O-Counter-2】
    SHARE(t1/c4)【R5】、VIEW(t1/c5)【R9】——只增不减
    FOLLOW/UNFOLLOW → 双向：follower 关注数(c7) + followee 粉丝数(c6)（msgId+"_2" 防去重冲突）【R10】
  版本门（先于计数）：like / favorite / comment（按 commentId，级联时跳过）/ follow（按 follower:followee 对）
  → 计数 Lua 二选一：
    delta 路径 INCR_WITH_DEDUP_SCRIPT：EXISTS dedup→{0,0}；SET dedup EX 7200；INCRBY delta（负 Δ 带归零保护 {−1,0}，归零不删 dedup 标记——业务拒绝不重试）；EXPIRE counter 30d（须在 INCRBY 之后——首次创建前 EXPIRE 无效，回归发现）
    like 路径 LIKE_SET_SCRIPT：SET dedup → SADD/SREM（幂等）→ EXPIRE set 30d → SCARD → SET counter → EXPIRE 30d；返回 changed 反映 Set 真实变更量
  → counterBuffer.add(targetType, targetId, countType, delta)

CounterBuffer（Buffer-Trigger）：
  合并：ConcurrentHashMap "t:tid:ct" → AtomicLong delta（+1+1-1 合并为 +1）
  触发：满 100 条 或 @Scheduled(5s)；flush tryLock 非阻塞（不阻塞写入线程）
  双 Buffer 交换 + 跨代写防护（写入后校验 buffer 引用，变了则撤销并入新 buffer）
  刷盘：按 (targetType,targetId,countType) 排序防死锁 → BATCH_SIZE=500 分批 batchUpsert
  失败：重试 3 次（递增退避+抖动）→ 仍失败回写缓冲（注释依据：reconcile 仅以 DB 已有记录为基准，丢失的增量没人补）
  停机：@PreDestroy + GracefulShutdownHook 阻塞式强制 flush
```

### B. 读链路（home BFF 聚合在用）

```
getCount：L1 Redis GET（脏值 NumberFormatException → 降级 DB 不 500）→ L2 MySQL → 回填（单命令 SET 带 TTL，防"set+expire 之间崩溃留永久 key"）
batchGetCounts：Pipeline 批量 GET → 未命中批量查 DB（防 N+1）→ 逐条回填
CounterService 注释专节"为什么不用 Caffeine"：多实例本地缓存失效不可行，Redis <1ms——(面试素材)
```

### C. 对账（reconcile 两段合一，counterReconcileJob 每小时整点）

```
① DB 基准对账：游标分页扫 DB（1000/批）→ Pipeline multiGet：
     Redis 有值且 ≠ DB → 以 Redis 为准（实时权威源）
     Redis=0、DB 有值 → 以 DB 恢复（Redis 可能丢数据）
     自述盲区：DB 无记录但 Redis 有值不处理——等 Buffer 刷盘自然解
② analytics 权威对账 reconcileLikeFromAnalytics（reconcile() 内部调用）：
     SCAN myxhs:counter:{1|3}:*:1 → 对比 myxhs:like:note:/comment: SCARD → 不一致以 analytics 覆盖
     T-113：修正后同步 DB（updateCountValue）——修复前只改 Redis，DB 残留漂移永久不一致
```

> 搜索侧 `LikeCountSyncConsumer` 的 T-092 竞态修复也选了读 analytics 权威 Set（见 `06-搜索.md` §4-E）——**analytics 权威 Set 是全系统的点赞权威快照**。
> 深挖轮补录：DB 扫描经**读写分离路由**（SELECT→从库）；两段联动有边界风险（先"DB 恢复"、后"analytics 覆盖"；**analytics 集合缺失会被当作 SCARD=0**）——详见 §7-8。

## 7. 现状边界与问题线索（仅记录，待讨论）

1. **版本门双实现**：counter（`userId:bizType:bizId`）与 analytics 各自一套"版本比较 Lua"（同构语义）——跨模块重复逻辑（机制复用/冗余观察点）；
2. **关注双向计数非原子**：f1（关注数）/ f2（粉丝数）两次独立 Lua 调用 → f2 失败回滚 f1（msgId+"_rollback"）+ 抛出触发重试；**回滚自身也可能失败**（如归零拒绝），最终靠对账兜底（设计取舍，待讨论）；
3. **reconcile 盲区与 Buffer 回写耦合**：DB 无行 + Redis 有值不覆盖（等刷盘）；"回写缓冲保证增量不丢"是该盲区安全的前提——两个机制互相依赖；
4. **双 Set 职责与治理**：counter Set（展示优化）vs analytics Set（权威）；懒迁移（counter Set 空 + 计数值 >0 → 从权威 Set 拉成员、SCARD 覆盖）是迁移桥；2026-09-19 review 给 Set 补 30d TTL（此前无 TTL，noeviction 下无限增长）；
5. **COMMENT 级联跳过版本门**：级联删除（count>1，父评论+楼中楼）无单一 commentId 锚点 → 放弃版本判断（已知取舍，防误杀）；UNCOMMENT 事件生产方在级联时把 commentId 置 null（CommentService:260）；
6. **小债**：① t_counter DDL 注释 target_type 枚举不全（"1-笔记 2-用户"）；② `myxhs:like:set:` 前缀硬编码在 CounterService（同模块其余键走 `RedisKeyConstants`）；
7. **VIEW 无去重口径**：只增不减 + msgId 去重；同一用户重复浏览是否计数取决于生产方（content），counter 侧无视图去重/防刷——观察点。
8. ★ **深挖轮主要发现：analytics 权威覆盖的两个盲区（like 计数有数据穿越风险）——① 已止血（10-12），② 待讨论**
   - ① **缺集合 ⇒ 清零双写**：`reconcileLikeFromAnalytics` 对 SCAN 到的每个 `myxhs:counter:{1|3}:*:1` 读 `myxhs:like:note|comment:{id}` 的 SCARD——**Key 不存在时 SCARD=0**，代码只判 `analyticsCount != null`（L372）无 EXISTS 守卫 ⇒ `0 ≠ 42` 触发"修正"：Redis 计数清 0 + T-113 把 DB 行也改 0（数据丢失，无 t_like 重建路径可恢复）；
   - 必现组合拳：与 `reconcile()` 第一段联动——老目标（>30 天无互动）两侧 30d TTL 同时过期 → 第一段从 DB"恢复"计数 → 第二段（同一轮）又把刚恢复的值清零（analytics Set 已不在）；**读路径回填（batch-get 未命中）也会单独复活 counter 键**——"counter 活 + analytics 死"的错位窗口来源之一。更广义：**任何原因导致 analytics Set 缺失**（历史/种子数据、Redis 丢失、消息从未写入）都会在第一轮对账被清零；
   - 时间线注记：对账的"以 analytics 为准"语义（T-113 系，8 月）先于权威 Set 的 30d TTL 治理（2026-09-19 review 为防 noeviction 膨胀而加）——**两次独立变更叠加才形成该路径**；
   - ② **只修值不修集合**：修正不重建 counter 内部 `like:set` 成员；而每个 like/unlike 事件都用旧集合 SCARD **无条件覆盖**计数值（LIKE_SET_SCRIPT），两 Set 分叉（如消费重试耗尽进 DLQ）时，修正值会被下一次事件覆盖回去——两套"权威"并存的设计张力；
   - **修复落地（2026-10-12）**：方案 A 保守止血——`reconcileLikeFromAnalytics` 加"防清零守卫"（Set 缺失/为空时跳过修正 + 汇总日志）；单测 +2（缺失跳过不写库 / 存在时正常修正），模块 11 测全过；
   - 遗留待议：B（从 `t_like` 重建集合——属 analytics 域，08 梳理时一并看，对齐 follow 已有重建先例）/ C（对账同时重建 counter 内部 `like:set`）
9. **Job 注释 × 注册表 cron 漂移**：`CounterReconcileJob` javadoc 写"每天凌晨 3 点（`0 0 3 * * ?`）"，`init-xxljob.sql` 实注册 `0 0 * * * ?`（每小时）——库存/购物车/优惠券 cron 漂移家族同款（SERIAL_EXECUTION 提供防重入；以哪个为准待讨论）。
10. **死代码家庭（5 处）**：① `increment()/decrement()+DECREMENT_SCRIPT`（m11 修复物件）生产零调用、仅单测在测——真实写路径全走 dedup 系列；② `incrementWithDedup` 5 参 delta 重载零调用（5 参 decrement 在用）；③ `CounterEvent` DTO 类零引用（生产方各自定义 payload）；④ `COUNTER_BUFFER` 常量死（已补 00A 附 3）；⑤ yml 配 `counter-producer-group` 但模块零生产。
11. **脏值韧性不对称**：`getCount` 对 Redis 脏值降级 DB；`batchGetCounts`（L478）与 `reconcile`（L564）的 `Long.parseLong` 无守卫——单个脏值可使整批请求 500、对账 Job 失败（`reconcileLikeFromAnalytics` 反而有逐 key try/catch）。
12. **公开端点防护不均**：`/get`（50 次/秒）、`/reconcile`（2 次/分 + token）有限流，**`/batch-get` 零限流**——单请求 100 项×7 类型 = 700 键（Pipeline 放大）；与 06-搜索"零限流"同类暴露面。
13. **"单命令回填"修复未全覆盖**：2026-09-21 把 `getCount` 回填改为单命令 SET+TTL（防 set/expire 间崩溃留永久 key），但 `batchGetCounts`（L512-513）、reconcile 恢复（L569-570）、懒迁移（L329-330）仍是 set+expire 两命令；懒迁移还漏给 `like:set` 续 TTL（迁移出的集合在下次事件前无 TTL）。
14. **使用面与测试覆盖**：服务间调用仅 home 4 处 batch-get（`/get` 无服务间调用方）；单测只覆盖非 dedup 老路径 + 读路径——Lua 原子/Set-based/版本门/对账/Buffer 刷盘重试全无自动化覆盖，机制正确性靠注释考古 + 场景推演（面试诚实口径）。

### 8.2 核心设计（学习要点）

**单一收敛语义 = 证据判别 + 完成态幂等 + 可重建**：
- 版本门完成态（只读 stale + 完成后单调推进）——崩溃重投不丢不重；
- like 权威缺失从 t_like 重建（不再"跳过等人工"）；counter 集 SUNIONSTORE 复制收敛；
- 键族补真 hash tag（每脚本单 slot，Cluster 兼容——含对账 SUNIONSTORE 单 slot）。

### 8.3 记录不做（讲）
