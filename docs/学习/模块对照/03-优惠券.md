## 1. 定位与职责

交易链路的**优惠资源域**：券模板管理（管理端）+ 领券中心 + 「我的券」；在交易链路上的三个咬合点：

```
下单试算（getCouponDiscount，只算不核销）→ 下单核销（useCoupon）→ 取消/退款退券（returnCoupon）
```

架构同族：**Redis 库存为同步闸门（防超发）→ MQ 异步落账 MySQL → 对账收敛**。

被依赖：**order**（三件套 Feign）+ **home BFF**（可用券聚合）。

## 4. 核心链路

### A. 领券（防超发主战场）

```
模板缓存读取 → 业务校验（下线/未开始/已结束）
→ claim_coupon.lua 原子：库存检查 → 限领检查 → DECR stock → INCR claimed
    返回：1 成功 / -1 售罄 / -2 超限领 / -3 库存未初始化
→ 同步发 MQ + Outbox：先写 outbox 行 → syncSend → 成功 markSent
    失败 markCancelled（**关键**：作废 outbox 防"调用方已回滚 Redis 但补发仍投递"→ 超发）
→ 发送失败 → 回滚 Redis（return_coupon.lua：INCR stock + DECR claimed）
-3 自愈：initStockFromDb（**读 DB 实时 remain_count**，非缓存旧值）→ 重试一次（按 -1/-2 精确分派）
```

### B. 异步落账（消费端）

`CouponClaimConsumer`（`coupon-claim-consumer-group`，maxReconsume=5）：
- 幂等：msgId 24h + `uk_claim_no` 兜底（兼容 Outbox 重发，claimNo 不变）；
- 事务：插 `t_user_coupon` + **`decrementRemainCount`**（模板 remain−1；affected≠1 → 抛异常整体回滚 → MQ 重试）。

> **双库存语义**：Redis `stock` = 领取闸门（同步、实时）；MySQL `remain_count` = 异步落账。两者以对账收敛（§4-E）。

### C. 下单链路（order 侧视角）

- `getCouponDiscount`（只算）：归属校验 → 责任链 → `calculateDiscount`（满减/折扣/无门槛；**`min(orderAmount)` 防 0 元购**）；
- `useCoupon`（核销）：status=0 校验（精确文案：已用/异常）→ 责任链 → 折扣 → **`markUsed` 乐观锁**（status 0→1 + 写 `used_order_id`）。

### D. 退券（RV30 语义，注释写得很清楚）

- `returnCoupon`：乐观锁（status=1 **AND** `used_order_id=orderId` → 0），幂等（不匹配不报错）；
- **只恢复用户券状态：不回补 stock/remain、不减 claimed**。原因：核销不扣 remain；若回补会形成"remain+已发 > total"的**超发敞口**，且用户可"领→用→退→再领"**绕过 perUserLimit**；
- 旧的"退券 Redis 补偿链"（会 INCR stock/DECR claimed 的旧语义残留）已**整链删除**（2026-09-23，生产者零调用确认）。

### E. 对账（CouponReconcileJob，三件事）

1. **stock 对账**：无 Redis 值 → 从 MySQL 补全；不一致 → **以 Redis 为准**修 `remain_count`；
2. **claimed 计数对账**：SCAN `claimed:*` 键，以 **DB 已发券数**为准修正（语义：claimed 含已用/已过期券）；
3. **卡住 Outbox 告警**：status=0 超 5 分钟 → 打 ERROR + 指标（补发由 Sender Job 负责）。

### F. 过期（CouponExpireJob）

分批标记 status 0→2，批间 sleep 100ms。**T-058 历史坑**：原实现"多表 JOIN UPDATE + LIMIT"是 MySQL 非法语法（Incorrect usage of UPDATE and LIMIT）→ 任务每轮必失败、**过期券永不标记**；现改为派生表子查询（内层 JOIN 选 id 按 LIMIT 分批，外层单表 UPDATE，二次包装规避"UPDATE 子查询引用同表"限制）。

### G. Outbox（CouponOutboxSenderJob）

`@Scheduled(5s)` + Redisson 锁（tryLock 0/4s）：`selectPendingOutbox(cutoff, 200)` → 补发 → 成功 markSent / 失败退避（30→480s 封顶 ±20%）；已发送记录 7 天清理。

### 8.2 核心设计（学习要点）

**领券语义重定义 = Design B：名额锁定即成功 + 券必达·至少一次**：
- 原实现"同步强一致"叙事（发送失败→回滚 Redis + 作废 Outbox）有**两处部分失败→超发洞**：
  ① SEND_OK 后 markSent 失败 → 作废+回滚，**但消息已发出** → 消费者发券 → 超发；
  ② syncSend 超时/非 SEND_OK（消息可能已写入 broker）→ 同样回滚+作废 → 超发；
- 修复：outbox 先落（**同 claimNo 幂等重试一次**——"写入超时≠失败"，DuplicateKey=实际已写按成功）；
  syncSend **任何结果均保留 Outbox**（SEND_OK→markSent 尽力；异常/非 OK→保留交补发）；
  **仅双次写入失败**才回滚+报错（唯一回滚路径：此刻可证"无消息在途"）；闸门放行后恒返回成功；
- 产品语义锚定：**内部故障不进用户视野**（超时≠失败）；重复投递由 uk_claim_no 幂等兜底；漏损为安全方向（对账以 DB 为准收敛）；
- **G35 投递时限领守卫**：消费者 insert 前 `countIssued ≥ perUserLimit → 跳过 + 告警`——防"DLQ 重放 × 对账修正后重领"交叉的超限发放；正常路径永不触发（闸门已保证）；
- **DLQ 重放消费者**（核心线首个自动消费-DLQ 重放）：领券/订单终止两个消费组的 `%DLQ%` 重投源 topic，attempt≤3 超限仅告警；与 AI 线 HITL 工具（dlq.redeliver）互补。
