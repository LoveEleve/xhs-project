# 06 · 规模化：分片、延时与推送

> **口径**：先讲**生产环境/淘宝公开形态**的规模化做法，再对照本项目实现；代码不代表应然标准。
> 所有吞吐/容量数字都是**设计目标或公开产品形态**，不是本项目的压测结论（项目口径：编译+单测，无运行时）。
>
> **一句话**：规模化不是"堆中间件"，而是三件事：**分片（数据怎么切）+ 跨库事务（一致性怎么拆）+
> 延时/推送（时间与流量怎么扛）**。
>
> **本篇带走**：① 32 分片怎么切 ② 分片后跨库事务怎么拆 ③ RocketMQ 24h 窗口怎么绕
> ④ 推送引擎怎么限流 ⑤ 哪些是设计缺口（不吹）。
> 前置：02/05。证据：C-017 全部产出、C-018 规划。

## 0. 例子：从"单库 1000 万"到"32 分片"

假设目标（**设计假设，不是实测**）：

```
1 亿条领券记录；峰值 5 万 QPS（活动开抢）
单表 1 亿 → 索引膨胀、写入热点、DDL/备份都痛
```

分片后的目标形态（生产常见）：

```
user_id 分片：同一用户的券落同一分片（"我的券"单分片查询）
2 库 × 16 表 = 32 分片；模板/Outbox 等小表保持全局
领券：Redis 闸门 + 异步落账；过期：延时消息 + 兜底 Job；推送：分桶 + 批处理 + 限流
```

> 淘宝的具体分片数/中间件不公开；上面是电商优惠券域常见的规模化形态。

## 1. 生产环境怎么做（淘宝/行业常见）

| 维度 | 常见做法 |
|---|---|
| **分片** | 用户券按 `user_id` 分库分表；模板/活动等小表全局或按活动 ID 分片；热点模板单独治理 |
| **热点库存** | Redis 预扣 + 库存分片/本地合并；热点探测与限流 |
| **异步落账** | MQ 削峰；消费端幂等 + 唯一索引；对账收敛 |
| **过期** | 延迟队列/TTL/时间轮/批量任务；按活动或券维度触发 |
| **推送** | 用户分桶、批量消息、线程池+信号量限流、失败重试 |
| **容量** | 压测/容量规划/影子库/在线 DDL；分片预留与扩容方案 |

## 2. 本项目的实现（C-017）

### 2.1 分片：2 库 × 16 表（user_id）

```yaml
rules:
  - !SHARDING
    tables:
      t_user_coupon:
        actualDataNodes: ds_${0..1}.t_user_coupon_${0..15}
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: coupon-db-inline
        tableStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: coupon-table-inline
    shardingAlgorithms:
      coupon-db-inline:
        type: INLINE
        props:
          algorithm-expression: ds_${user_id % 2}
      coupon-table-inline:
        type: INLINE
        props:
          algorithm-expression: t_user_coupon_${(user_id.intdiv(2)) % 16}

  # 全局单表：模板 / Outbox / 推送记录
  - !SINGLE
    tables:
      - t_coupon_template
      - t_coupon_outbox
      - t_coupon_push_record
    defaultDataSource: ds_0
```

- **为什么按 `user_id`**：主查询是"我的券"；同一用户的券落同一分片，避免跨分片；
- **为什么模板/Outbox 不分片**：量小、按 id/列表查；分片会引入广播/映射复杂度；
- **按 id 的读写必须补 `user_id`**：`selectByIdAndUserId`、`markUsed/returnCoupon` 都带 `user_id`，
  否则 ShardingSphere 会广播到 32 张表；
- **SQL**：`sql/mysql-coupon-sharding-init.sql`（32 张表 + 存量迁移）；
- **默认 profile 仍是单库**：`coupon-sharding` 显式启用（`@Profile`），不影响原基线。

### 2.2 跨库事务：不能"一个本地事务"包住

分片后，领券消费端的两步写会落在**不同数据源**：

```
插入 t_user_coupon（ds_0 或 ds_1，按 user_id）
扣减 t_coupon_template.remain_count（ds_0 全局表）
```

ShardingSphere 的本地事务**不保证跨 DS 原子性**。本项目的处理：

- **插券为准**（用户是否拿到券）；
- `remain_count` 是**派生账本**：扣减失败只记 `claim_stock_lag`，不回滚发券；
- `CouponReconcileJob` 以 Redis stock 为准修 `remain_count`；
- 代价：`remain_count` 可能短时间滞后；但"超发"由 Redis 闸门挡，账本滞后是安全方向。

### 2.3 延时过期：RocketMQ 24h 窗口 → 23h 分段

RocketMQ 开源版延时消息窗口默认 **24 小时**，超过会被**立即投递**。
7 天有效期的券不能直接排 7 天，所以：

```java
// CouponExpireDelayProducer
long deliverAt = Math.min(validEndMs, now + MAX_WINDOW_MS); // MAX_WINDOW_MS = 23h
rocketMQTemplate.syncSendDeliverTimeMills(COUPON_EXPIRE_TOPIC, message, deliverAt);

// CouponExpireDelayConsumer：到点还没到期 → 再排一段
if (template.getValidEnd().isAfter(LocalDateTime.now())) {
    expireDelayProducer.schedule(templateId, template.getValidEnd());
    return;
}
// 到期 → 批量 0→2
```

三层保障：

```
预检 Job（建议每日，未来 24h 到期模板补排）
  → 23h 分段延时消息（消费端续排）
  → 兜底 Job（每 5 分钟扫，按模板批量 0→2）
```

> ⚠️ 分片模式：兜底 Job 的 `UPDATE ... WHERE coupon_id=?` **没有分片键**，会广播到 32 张表；
> 量大时应改成"按分片扫描/离线表"（当前可接受，因为是低频批量任务）。

### 2.4 推送引擎：分桶 + 批分割 + 限流

```
XXL-Job（couponExpiryPushJob）
  → 扫"明天到期"的未使用券（id 游标，避免 LIMIT 饥饿）
  → t_coupon_push_record 幂等占位（uk: template_id,user_id,push_date）
  → 分桶：coupon.push.bucket-size=1000/批；UserBucketSplitter 再受 800KB 限制
  → SharedThreadPool（ThreadPoolExecutor + Semaphore 背压）
  → NOTIFICATION_TOPIC → notification 落库 + SSE
```

关键参数/边界：

> ⚠️ 分片模式：`selectUnusedByCoupon(coupon_id, lastId, limit)` 也是**广播查询**；
> id 游标只解决"单库 LIMIT 饥饿"，不能保证 32 张表的全局顺序。生产应改成按分片扫描/离线表。

- `coupon.push.scan-limit`（默认 5000）：单次扫描条数；
- `coupon.push.bucket-size`（默认 1000）：每批/每分桶用户数；
- `Semaphore`：同时在跑的批次数上限，满了**阻塞**而不是堆队列；
- 幂等：已发送跳过、失败重试；推送记录唯一键；
- 画像：最小版按 `user_id` 分桶；**行为标签画像未实现**（06A 设计）。

## 4. 十二个坑

1. **分片键选错**：按 `order_id`/`template_id` 分片会让"我的券"跨分片；本项目按 `user_id`。
2. **按 id 查询不带分片键**：会广播 32 表；所有 id 读写补 `user_id`。
3. **模板/Outbox 乱分片**：小表分片会引入广播/映射；保持 `!SINGLE`。
4. **跨库本地事务**：插券 + 扣模板不能一个本地事务；拆成派生账本 + 对账。
5. **RocketMQ 24h 上限**：直接排 7 天会被立即投递；必须 23h 分段。
6. **推送 LIMIT 饥饿**：无游标时永远只推前 N 条；用 `id > lastId`。
7. **推送不限流**：线程池/信号量不设上限会打爆下游；Semaphore 背压。
8. **推送不幂等**：重跑/重试会重复推；`uk(template_id,user_id,push_date)`。
9. **分片迁移**：存量数据要按同一路由迁移；演示 SQL 是直插，生产要双写/停写。
10. **无运行时验证**：分片路由/延时/推送都只有单测；不要声称压测/生产验证。
11. **按 coupon_id 的批量任务会广播**：过期 Job / 推送扫描没有分片键，32 表都要扫；量大要改分片扫描。
12. **迁移 SQL 是演示级直插**：生产要双写/停写迁移，不能把 32 条 INSERT 当生产方案。

## 5. 值不值得深挖 / 一句话

- **值得**：分片键选择、跨库事务拆分、24h 延时分段、推送限流——规模化面试的核心；
- **一句话带过**：分片算法表达式、Job cron、线程池参数；
- **一句话**：**规模化 = 按 user_id 分片 + 跨库事务拆成派生账本 + 24h 窗口分段延时 + 分桶/批处理/限流推送；数字要压测，不能靠设计声称。**
- 推送设计细节见 **06A**；受控重建/领取意图见 **C-018**。

**面试口径**："用户券按 user_id 做 2 库×16 表共 32 分片，模板/Outbox 单表；按 id 查询补 user_id 避免广播；分片后插券与模板 remain 跨库，拆成'插券为准 + remain 派生 + 对账'；过期用 23h 分段延时绕开 RocketMQ 24h 窗口；推送按 1000/批 + 800KB + Semaphore 限流。"
