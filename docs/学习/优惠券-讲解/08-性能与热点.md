# 08 · 性能与热点

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；所有 QPS/容量数字都是**设计假设**，
> 不是本项目的压测结论（项目口径：编译+单测，无运行时）。
>
> **一句话**：券域性能 = **领券热点在 Redis（Lua 单 slot）+ DB 异步落账 + 查询按 user_id 单分片
> + 推送分桶/批处理/限流**；真正的瓶颈往往不在"扣库存"，而在**同步落库、广播查询、推送下游**。
>
> **本篇带走**：① 领券热点 ② 双库存吞吐取舍 ③ 查询/批量/分页 ④ 推送并发/限流 ⑤ 分片广播与对账成本。
> 前置：02/06。证据：`claim_coupon.lua`、`getTemplateWithCache`、`SharedThreadPool`、`CouponReconcileJob`。

---

## 0. 例子：5 万 QPS 抢 1000 张券（设计假设）

```
活动 10:00 开抢：1000 张券，峰值 5 万 QPS（假设）
  → 绝大多数请求在 Redis Lua 被 -1 挡掉（库存 0）
  → 少量成功请求：Outbox 落库 + syncSend + 消费落券
  → 查询"我的券"按 user_id 单分片
  → 到期提醒：分桶 + 批处理 + 限流推送
```

> 5 万 QPS 是**设计假设**，不是实测；本项目没有压测/运行时验证。

## 1. 生产环境怎么做（淘宝/行业常见）

| 热点 | 常见做法 |
|---|---|
| **领券** | Redis Lua/信号量原子扣减；Cluster 同 slot；热点模板库存分片/本地合并；限流/排队 |
| **模板读** | 本地缓存 + Redis；空值缓存；变更失效 |
| **落账** | MQ 削峰；消费端批量/幂等；DB 只做持久化 |
| **查询** | 按 user_id 分片；游标/分页；避免深分页与跨分片 |
| **推送** | 用户分桶、批量消息、线程池+信号量限流、失败重试 |
| **容量** | 压测/容量规划；热点探测；降级预案 |

## 2. 本项目的实现（代码证据）

### 2.1 领券热点：Lua 一次往返 + 同 slot

```lua
-- KEYS[1] = myxhs:coupon:{templateId}:stock
-- KEYS[2] = myxhs:coupon:{templateId}:claimed:userId
-- 一次 Lua：库存检查 + 限领检查 + DECR + INCR
```

- **一次网络往返**完成"读-判-写"，避免多条命令的竞态与 RTT；
- **`{templateId}` 同 slot**：Cluster 下两个 key 必须同 slot，否则 CROSSSLOT；
- **模板缓存**：`getTemplateWithCache` 先 Redis（30min），未命中查 MySQL；不存在缓存 `NULL` 60s 防穿透；
- **接口限流**：`@RateLimit` 5/60s/用户，挡重复点击。

**天花板**：一个模板一个 stock key，热点集中在单个 Redis slot；超大活动要库存分片/本地合并
（本项目未做，是设计缺口）。

### 2.2 双库存：快慢分离

| 层 | 操作 | 性能特征 |
|---|---|---|
| Redis stock | Lua 同步扣减 | 快（内存 + 单线程原子） |
| MySQL remain_count | 消费端异步扣减 | 慢半拍；失败不阻断，对账修 |
| 领券请求线程 | Outbox 落库 + syncSend | **仍有同步 DB/MQ**，高 QPS 下是瓶颈 |

**别误读**：领券不是"纯 Redis"——`sendClaimEventSync` 仍会在请求线程做 Outbox 插入 + `syncSend`。
生产可进一步异步化/批量/本地消息；本项目优先保证"必达"，接受这部分同步开销。

### 2.3 查询：单分片 + 批量 + 分页

- `selectByIdAndUserId` / `markUsed` / `returnCoupon` 都带 `user_id` → **单分片路由**；
- `getUserCoupons` 有 `LIMIT 200`（防全量）；
- `getAvailableCoupons`：先按 user_id 查未用券，再 **`selectBatchIds` 批量查模板**（C-007 消除 N+1）；
  ⚠️ 但它**没有 LIMIT**——未用券特别多时列表会大，生产应加限制/分页；
- `listClaimableTemplates`：每次查 MySQL（状态/剩余/有效期），**没有缓存**——领券中心高频访问时要加缓存。

### 2.4 推送：分桶 + 批分割 + Semaphore 背压

```java
public SharedThreadPool(@Value("${coupon.push.permits:20}") int permits) {
    int max = Math.max(permits * 2, permits + 1);
    int core = Math.min(max, Math.max(2, Runtime.getRuntime().availableProcessors()));
    this.semaphore = new Semaphore(permits);
    this.executor = new ThreadPoolExecutor(core, max, 60, TimeUnit.SECONDS,
            new SynchronousQueue<>(), new DaemonThreadFactory("coupon-push"));
}

public Future<?> submit(Runnable task) {
    semaphore.acquireUninterruptibly();   // 满了阻塞（背压），不堆无界队列
    return executor.submit(() -> {
        try { task.run(); } finally { semaphore.release(); }
    });
}
```

- 分桶 `coupon.push.bucket-size=1000`；`UserBucketSplitter` 再受 800KB 限制；
- 每批任务里**逐用户 `syncSend`** 到 `NOTIFICATION_TOPIC`——单条同步发送是瓶颈；
  生产可改 `asyncSend`/批量消息/本地队列；
- 幂等：`t_coupon_push_record` 唯一键；失败重试。

### 2.5 分片后的"隐性成本"

| 场景 | 成本 |
|---|---|
| 按 id 查/更新不带 `user_id` | 广播 32 表 |
| 过期 Job `WHERE coupon_id=?` | 广播 32 表（低频批量，可接受） |
| 推送扫描 `coupon_id + id 游标` | 广播；游标不保证 32 表全局顺序 |
| `CouponReconcileJob` 限领对账 | `SCAN claimed:*` + 每个 key 一次 `countIssued` → **N+1 DB 查询** |

这些不是"错"，是规模化后的**运维成本**；量大时要改"按分片扫描/离线表/批量聚合"。

## 3. 对照表：生产 vs 本项目

| 能力 | 生产环境 | 本项目 | 差异 |
|---|---|---|---|
| 领券原子扣减 | Redis Lua/信号量 | ✅ Lua | 对齐 |
| Cluster 同 slot | 必须 | ✅ `{templateId}` | 对齐 |
| 热点库存分片 | 常见 | ❌ 单 key | 缺口 |
| 模板缓存 | 本地+Redis | ✅ Redis（30min/NULL 60s） | 简化（无本地缓存） |
| 领券请求线程 | 异步/批量 | ⚠️ Outbox+syncSend 同步 | 可优化 |
| 查询路由 | user_id 分片 | ✅ 单分片 | 对齐 |
| 查询分页 | 游标/限制 | ⚠️ available 无 LIMIT | 缺口 |
| 推送限流 | 分桶+信号量 | ✅ 1000/批 + Semaphore | 对齐（逐条 sync） |
| 广播/对账成本 | 分片扫描/离线 | ⚠️ 广播 + N+1 | 已知成本 |
| 压测 | 有 | ❌ 无 | 不能声称 QPS |

## 4. 十个坑

1. **Cluster CROSSSLOT**：Lua 多 key 必须同 slot。
2. **单 key 热点**：一个模板一个 stock key；超大活动要库存分片/本地合并。
3. **领券请求线程仍有 DB/MQ**：Outbox 插入 + syncSend；高 QPS 要异步化/批量。
4. **缓存穿透/击穿**：NULL 60s；模板缓存 30min；热点 key 过期要预热/互斥重建。
5. **N+1 查询**：可用券列表已批量查模板；别退回逐个 `selectById`。
6. **`getAvailableCoupons` 无 LIMIT**：未用券多时列表大；生产要分页/限制。
7. **按 id 不带 `user_id`**：广播 32 表；所有 id 读写补分片键。
8. **对账 N+1**：`SCAN claimed:*` + 每 key 一次 DB 查询；量大要批量/离线。
9. **推送逐条 syncSend**：单条同步是瓶颈；可改异步/批量。
10. **没有压测**：所有 QPS/容量都是设计假设，不能当实测结论。

## 5. 值不值得深挖 / 一句话

- **值得**：Lua 同 slot、双库存快慢分离、单分片查询、推送 Semaphore 背压、分片广播成本；
- **一句话带过**：缓存 TTL、线程池参数、限流阈值；
- **一句话**：**券域性能 = Redis 原子闸门（快）+ DB 异步落账（慢半拍）+ user_id 单分片查询 + 推送分桶/批处理/限流；瓶颈常在同步落库、广播查询、逐条推送。**
- 分片/延时见 **06**；规模化缺口见 **06 §3**。

**面试口径**："领券用 Lua 一次往返、两 key 同 slot；Redis 闸门快、MySQL remain 异步落账，对账修；查询按 user_id 单分片、批量查模板；推送 1000/批 + 800KB + Semaphore 背压。瓶颈是请求线程里的 Outbox/MQ、分片广播和对账 N+1；QPS 没有压测，不能声称。"
