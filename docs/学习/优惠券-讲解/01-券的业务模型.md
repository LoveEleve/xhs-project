# 01 · 券的业务模型：淘宝/生产环境怎么定义一张券

> **口径（重要）**：先讲**真实淘宝/生产环境**的券模型，再对照本项目。
> 本项目是**简化实现**，代码只能证明"我们这么做了"，**不能代表应然标准**；
> 涉及淘宝的地方只讲公开产品形态/行业常见做法（具体规则以活动页为准），不冒充内部实现。
>
> **本篇带走 3 条**：① 生产券体系：多券 + 叠加/互斥 + 锁定核销 + 行级分摊
> ② 本项目简化在哪（单券、下单即核销、只有领券中心）③ 哪些差异是取舍、补的话怎么补。

---

## 0. 例子：淘宝下单一笔 300 元（生产视角）

假设活动规则允许叠加（**仅为示例，真实以活动页为准**）：

```
商品金额 300
  → 店铺券「满 200 减 20」           ﹣20
  → 跨店满减「每满 300 减 50」        ﹣50
  → 平台红包 5 元                     ﹣5
  → 实付 225
```

关键不在算术，而在三个动作：

1. **提交订单时"锁定"券**（不是立刻核销）：防止同一张券被两个订单同时用；
2. **支付成功才核销**；取消/超时 → **释放**回"未使用"；
3. 订单里有多个商品时，**整单优惠要分摊到行**：售后按"行金额 − 分摊"退，否则退一件会把整单优惠全退掉。

这三件事，是本项目与生产环境差距最大的地方（下面逐条对照）。

## 1. 生产环境的券体系（淘宝/天猫公开形态）

| 维度 | 生产环境常见做法 |
|---|---|
| **券的归属** | 店铺券、商品券、品类券/行业券、跨店满减、平台红包、会员折扣（如 88VIP） |
| **规则字段** | 类型（满减/折扣/无门槛/立减）、门槛、优惠值、有效期、发放量、每人限领、适用商品/店铺/人群 |
| **叠加/互斥** | 多券按活动规则叠加；有互斥组；结算时算"最优组合"（不是简单全部相加） |
| **发放方式** | 领券中心、活动页、定向发放、兑换码、新人礼包、会员权益 |
| **核销时机** | **下单锁定 → 支付成功核销 → 取消/超时释放**（主流做法；也有下单即核销的变体） |
| **优惠分摊** | 订单级优惠按行金额比例分摊（最大余数法），售后按分摊退 |
| **有效期** | 固定窗口 / 领取后 N 天 / 活动期；过期批量处理 |
| **风控** | 限领、黑名单、防刷、库存与发放节奏控制 |

> 这些是**公开产品形态 + 行业常见做法**；淘宝具体活动的叠加顺序、互斥组、门槛口径由活动规则决定，
> 不能拿"某次活动"当通用标准。

## 2. 本项目怎么实现（代码证据）

### 2.1 券模型：模板 + 用户实例

```java
public class CouponTemplate {
    private Long id;
    private String name;
    /** 类型：1-满减 2-折扣 3-无门槛 */
    private Integer type;
    /** 优惠金额/折扣率（折扣类型时为折扣值，如 8.5 表示 85 折） */
    private BigDecimal discountValue;
    /** 最低消费金额（无门槛券为 0） */
    private BigDecimal minAmount;
    private Integer totalCount;
    private Integer remainCount;
    private Integer perUserLimit;
    private LocalDateTime validStart;
    private LocalDateTime validEnd;
    /** 状态：0-禁用 1-启用 */
    private Integer status;
}

public class UserCoupon {
    private Long id;
    private Long userId;
    private Long couponId;
    private String claimNo;
    /** 状态：0-未使用 1-已使用 2-已过期 */
    private Integer status;
    /** 使用的订单ID（退券时校验"是不是这单用的"） */
    private Long usedOrderId;
    private LocalDateTime receivedAt;
    private LocalDateTime usedAt;
}
```

### 2.2 三种券的计算

```java
private BigDecimal calculateDiscount(CouponTemplate template, BigDecimal orderAmount) {
    BigDecimal discount = switch (template.getType()) {
        case 1 -> template.getDiscountValue();                    // 满减
        case 2 -> orderAmount.subtract(orderAmount.multiply(template.getDiscountValue())
                .divide(new BigDecimal("10"), 2, RoundingMode.HALF_UP)); // 折扣
        case 3 -> template.getDiscountValue();                    // 无门槛
        default -> BigDecimal.ZERO;
    };
    return discount.min(orderAmount); // 不能超过订单金额（防 0 元购/负数）
}
```

示例：满 100 减 20（120→100）；8 折（100→80）；无门槛 5 元（3→0，10→5）。
注意：本项目 `discountValue=8` 表示 **8 折**，不是 0.8——这是**项目约定**，生产系统可能存 0.8/80，别混。

### 2.3 用券校验链（用券时实时执行）

```java
// @Order(1) 门槛：orderAmount < minAmount → 拒绝
// @Order(2) 有效期：now < validStart 或 now > validEnd → 拒绝
// @Order(3) 模板状态：status != 1 → 拒绝（模板下线后，已领取的券也不能用）
for (CouponValidator validator : validators) {
    validator.validate(template, orderAmount);
}
```

### 2.4 核销：**下单即核销**（本项目与生产最大的差异）

订单提交时同步调用 `useCoupon` 核销并绑定 `orderId`；核销失败就取消订单：

```java
// OrderService（下单链路）
if (request.getCouponId() != null) {
    R<BigDecimal> useResp = couponFeignClient.useCoupon(userId, useReq);
    if (useResp == null || !useResp.isSuccess()) {
        terminateOrderQuietly(orderId, userId);   // 核销失败 → 订单取消
        throw new BizException(ResultCode.COUPON_NOT_AVAILABLE, "优惠券核销失败，订单已取消");
    }
}
```

**没有"锁定"态**：`UserCoupon.status` 只有 0/1/2，没有 `LOCKED`；取消/超时靠订单终止事件调用
`returnCoupon` 把 1→0（04 篇）。

### 2.5 优惠分摊：coupon 不做，**order 做**（重要修正）

本项目是**单券/订单级券**（`OrderCreateRequest` 只有一个 `couponId`），但订单在下单时**确实做了行级分摊**：

```java
// OrderTransactionService：订单级优惠 → 行级分摊（最大余数法）
Map<Long, BigDecimal> allocation = DiscountAllocator.allocateByItems(items, discountAmount);
item.setDiscountShare(allocation.getOrDefault(item.getId(), BigDecimal.ZERO));
```

- `t_order_item.discount_share` 落库；行实付 = 行小计 − 分摊；
- 售后按 `discount_share` 计算应退（`AftersaleService`），避免"退一件把整单优惠全退掉"；
- **分摊逻辑属于 order 域，不属于 coupon 域**：coupon 只返回整单折扣，怎么分到行是订单的事。

> 所以准确说法是：**券是单券/订单级；优惠分摊由订单域完成**。之前写"不分摊"是错的，已修正。

## 3. 对照表：生产环境 vs 本项目

| 能力 | 生产环境（淘宝/行业） | 本项目（实然） | 影响 / 补法 |
|---|---|---|---|
| 券体系 | 店铺/商品/品类/跨店满减/红包/会员 | 3 种基础券 | 学习够用；扩展=加类型+计算分支 |
| 叠加/互斥 | 多券叠加、互斥组、最优组合 | **单券**（一单一个 `couponId`） | 补：券规则引擎 + 互斥组 + 组合试算 |
| 发放 | 领券中心/活动/定向/兑换码/新人 | **仅领券中心** | 补：活动/人群包/兑换码 |
| 核销 | **锁定→支付核销→释放** | **下单即核销**（失败回退） | 补：`LOCKED` 态 + 支付成功确认/取消释放 |
| 分摊 | 行级分摊（最大余数） | **order 已做行级分摊**（`discount_share`） | ✅ 这一项本项目是接近生产的 |
| 有效期 | 固定窗口/领取后 N 天 | 固定窗口 | 补：按实例存"领取后 N 天" |
| 过期 | TTL/延迟队列/批量 | Job + 延时消息（23h 分段） | 见 06 |
| 风控 | 限领/黑名单/防刷 | 限领 + 简单限流 | 补：风控规则 |

## 4. 折扣与核销的 7 个坑

1. **折扣值语义**：本项目 `8`=8 折；生产可能存 `0.8`/`80`，跨系统对接必须确认口径。
2. **折扣上限**：`min(orderAmount)` 防负数/0 元购；无门槛券在 3 元订单上只能减 3。
3. **门槛口径**：本项目用订单侧传入的 `orderAmount`；生产叠加多券时要明确"原价/券后/实付"哪个做门槛。
4. **有效期双保险**：实时校验 + 过期 Job；只依赖 `status=2` 会有一段时间窗（Job 延迟）可被用。
5. **模板下线**：`StatusValidator` 让已领取的券也不能用——这是产品决策，要和运营对齐。
6. **券后支付金额一致**：订单实付 = 订单金额 − 折扣；支付域回查订单实付（P1-1），不一致拒付。
7. **分摊在 order**：别在 coupon 里算行级退款；coupon 只返回整单折扣，订单/售后用 `discount_share`。

## 5. 值不值得深挖 / 一句话

- **值得**：生产券体系（多券/叠加/锁定/分摊）与本项目简化点的对照——面试最容易问"你们和淘宝差在哪"；
- **一句话带过**：券名称/管理端字段；
- **一句话**：**生产券 = 多券 + 叠加/互斥 + 锁定核销 + 行级分摊；本项目 = 单券 + 下单即核销 + 订单域分摊——差异是取舍，不是标准。**

**面试口径**："券模型分模板和用户实例；生产环境是多券叠加/互斥、下单锁定、支付核销、行级分摊；我们项目简化为单券、下单即核销，但订单侧用最大余数法做了行级分摊（discount_share），售后按分摊退。"
