# 01 · 券的业务模型：一张券由哪些规则定义

> **一句话**：优惠券 = **规则模板**（`t_coupon_template`）+ **用户实例**（`t_user_coupon`）；
> 规则的最小集是：**类型、门槛、优惠值、有效期、发放量、每人限领**。
>
> **本篇带走 3 条**：① 三种券的计算方式 ② 生命周期五步与规则落点
> ③ 应然 vs 实然：叠加/互斥、发券方式、核销时机这些"缺口"为什么是取舍。
>
> 前置：`00-应然模型与学习路线.md`。证据：`CouponTemplate`/`UserCoupon`、`CouponService.calculateDiscount`、`validator/*`。

---

## 0. 例子：三种券，三笔订单

| 券 | 规则字段 | 订单金额 | 折扣 | 实付 |
|---|---|---|---|---|
| **满 100 减 20** | `type=1, discountValue=20, minAmount=100` | 120 | 20 | 100 |
| 同上 | 同上 | 80 | — | **不可用**（未达门槛） |
| **8 折** | `type=2, discountValue=8, minAmount=0` | 100 | 20 | 80 |
| **无门槛 5 元** | `type=3, discountValue=5, minAmount=0` | 3 | **3**（不能超过订单金额） | 0 |
| 同上 | 同上 | 10 | 5 | 5 |

再加两个通用约束：**有效期 7 天**、**每人限领 1 张**。

> 折扣券的 `discountValue` 是"几折"，不是"折扣率"：`8` = 8 折（付 80%），`8.5` = 85 折。

## 1. 最小规则集：模板与实例

**模板**（`t_coupon_template`）——规则的"定义"：

```java
public class CouponTemplate {
    private Long id;
    private String name;
    /** 类型：1-满减 2-折扣 3-无门槛 */
    private Integer type;
    /** 优惠金额/折扣率（折扣类型时为折扣值，如 8.5 表示 85 折） */
    private BigDecimal discountValue;
    /** 最低消费金额（无门槛券为 0） */
    private BigDecimal minAmount;
    /** 发放总量 */
    private Integer totalCount;
    /** 剩余数量 */
    private Integer remainCount;
    /** 每人限领 */
    private Integer perUserLimit;
    /** 有效期开始 / 结束 */
    private LocalDateTime validStart;
    private LocalDateTime validEnd;
    /** 状态：0-禁用 1-启用 */
    private Integer status;
}
```

**用户券**（`t_user_coupon`）——规则的"实例"：

```java
public class UserCoupon {
    private Long id;
    private Long userId;
    /** 模板ID */
    private Long couponId;
    /** 领券流水号（幂等） */
    private String claimNo;
    /** 状态：0-未使用 1-已使用 2-已过期 */
    private Integer status;
    /** 使用的订单ID（退券时校验"是不是这单用的"） */
    private Long usedOrderId;
    private LocalDateTime receivedAt;
    private LocalDateTime usedAt;
}
```

**三套状态**（后面每篇都会回到这里）：

```
模板：  0 禁用 ↔ 1 启用
用户券：0 未用 ──核销──▶ 1 已用 ──退券──▶ 0
        0 未用 ──过期──▶ 2 过期
库存：  Redis stock（闸门） / MySQL remain_count（落账） / claimed（限领）
```

## 2. 生命周期五步：规则在哪一步生效

| 步骤 | 谁触发 | 生效的规则 | 落在哪 |
|---|---|---|---|
| **建模板** | 管理端 | 类型/优惠值/门槛/有效期/总量/限领 | 创建责任链（09 篇） |
| **领券** | 用户 | 模板启用、未开始/已结束、库存、每人限领 | `claimCoupon` + Lua（02 篇） |
| **用券** | 下单 | 券归属、未使用、门槛、有效期、模板启用 | 校验链 + `markUsed`（03 篇） |
| **退券** | 取消/退款 | 券是"这单用的"、状态=已用 | `returnCoupon`（04 篇） |
| **过期** | 时间到 | `valid_end` | Job + 延时消息（04/06 篇） |

## 3. 折扣计算：三段代码

```java
private BigDecimal calculateDiscount(CouponTemplate template, BigDecimal orderAmount) {
    BigDecimal discount = switch (template.getType()) {
        case 1 -> template.getDiscountValue();                    // 满减
        case 2 -> orderAmount.subtract(orderAmount.multiply(template.getDiscountValue())
                .divide(new BigDecimal("10"), 2, RoundingMode.HALF_UP)); // 折扣
        case 3 -> template.getDiscountValue();                    // 无门槛
        default -> BigDecimal.ZERO;
    };
    // 减免不能超过订单金额（防 0 元购 / 负数）
    return discount.min(orderAmount);
}
```

用券前的校验链（`@Order` 1→2→3）：

```java
// 1) 门槛：订单金额 < minAmount → 拒绝
// 2) 有效期：now < validStart 或 now > validEnd → 拒绝
// 3) 模板状态：status != 1 → 拒绝（管理员下线后，已领的券也不能用）
for (CouponValidator validator : validators) {
    validator.validate(template, orderAmount);
}
```

**为什么有效期要实时校验**：过期 Job 是"批量标记"，有延迟（分钟级）；用券时直接看时间，
不依赖 `status=2`——否则过期后、Job 标记前，券还能被用。

## 4. 应然 vs 实然：本项目简化了什么

| 能力 | 真实系统（应然） | 本项目（实然） | 影响/为什么 |
|---|---|---|---|
| 券类型 | 满减/折扣/无门槛/立减/兑换/运费/品类/店铺 | 3 种（满减/折扣/无门槛） | 学习够用；扩展类型 = 加枚举 + 计算分支 |
| **叠加/互斥** | 平台券 + 店铺券 + 品类券，互斥组、最优组合 | **单券**（订单只有一个 `couponId`） | 避免价格分摊/组合引擎；多券要 item 级分摊 |
| 发券方式 | 领券中心/活动/定向/兑换码/新人券 | **仅领券中心主动领取** | 简化发放；定向券要人群包 |
| **核销时机** | 锁定 → 支付成功核销 → 失败释放 | **下单即核销**（失败回退） | 简单；依赖订单终止事件退券（04） |
| 有效期 | 固定窗口/领取后 N 天/动态 | **固定窗口**（模板 `valid_*`） | 简单；"领取后 N 天"要按实例存过期时间 |
| 过期 | TTL/延迟队列/分片扫描 | Job + 延时消息（23h 分段） | 见 06；RocketMQ 24h 窗口 |
| 优惠分摊 | 券金额分摊到行/子单（部分退可算） | **订单级券**，不分摊 | 部分退只能按支付金额退，不能按商品算 |

> 这些不是"bug"，是**范围取舍**：单券 + 下单即核销让交易链路简单很多；
> 代价是叠加、item 级退款、锁定态这些能力没有。面试可以主动说"知道缺口，以及补的话怎么补"。

## 5. 六个容易踩的坑

1. **折扣值语义**：`8` 是 8 折，不是 0.8；写错会把 80 元订单算出 79.2 的折扣。
2. **折扣上限**：必须 `min(orderAmount)`，否则无门槛券在 3 元订单上会算出负实付。
3. **门槛口径**：本项目的 `orderAmount` 是订单侧传入的金额；如果未来叠加多券，要明确门槛按"原价/券后/实付"哪个算。
4. **有效期双保险**：实时校验 + 过期 Job，不能只依赖 `status=2`。
5. **模板下线**：`StatusValidator` 会让已领取的券也不能用——这是产品决策（下线=停止使用），要跟运营对齐。
6. **用券金额与支付金额一致**：订单实付 = 订单金额 − 折扣；支付域会回查订单实付（P1-1），不一致直接拒付。

## 6. 值不值得深挖 / 一句话

- **值得**：三种券的计算、五步生命周期、应然/实然缺口——这是后面所有篇的"业务字典"；
- **一句话带过**：券名称/描述/管理端字段；
- **一句话**：**券是"规则模板 + 用户实例"；规则最小集 = 类型/门槛/优惠值/有效期/库存/限领；本项目单券、下单即核销，叠加与分摊是应然缺口。**

**面试口径**："券模型分模板和用户实例；三种类型（满减/折扣/无门槛）+ 门槛/有效期/库存/限领四个约束；核销是下单即核销，失败由订单终止退券；单券模型，叠加/互斥和 item 级分摊是设计缺口。"
