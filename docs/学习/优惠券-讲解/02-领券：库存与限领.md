# 02 · 领券：库存与限领

> **口径**：先讲**生产环境/淘宝公开形态**，再对照本项目；代码只证明"我们这么做了"，不代表应然标准。
>
> **一句话**：领券 = 在"名额有限"下做一次 **原子预扣 + 限领 + 异步落账**；
> 难点不是"扣库存"，而是**不超发、不重复、领了必达**。
>
> **本篇带走**：① 生产领券链路 ② 本项目 Lua + 双库存 ③ 差异与 8 个坑。
> 前置：01 业务模型。证据：`CouponService.claimCoupon`、`claim_coupon.lua`、`CouponClaimConsumer`。

---

## 0. 例子：1 万张券、10 万人抢

淘宝/电商活动 10:00 开抢：1 万张券，每人限领 1 张。

```
10:00:00.000  用户 A 点"领取"
              → 校验活动/资格 → 扣库存 → 生成券 → 异步落账 → "领取成功"
10:00:00.100  用户 B 点"领取" → 库存已 0 → "已抢完"
10:00:01.000  用户 A 再点 → "已达限领上限"
```

高并发下要同时保证三件事：

1. **不超发**：1 万张就是 1 万张，不能因为并发扣成负数；
2. **不重复**：同一用户不能领 2 张（限领 1）；
3. **必达**：用户看到"领取成功"，券就必须到账（不能扣了库存却没生成券）。

## 1. 生产环境怎么做（淘宝/行业常见）

| 环节 | 常见做法 |
|---|---|
| **活动/资格校验** | 活动状态、时间窗、用户资格、黑名单/风控 |
| **库存** | Redis 预扣（原子脚本/信号量）+ DB 落账；热门券可能做库存分片/热点探测 |
| **限领** | 用户 × 活动/模板维度计数；风控叠加 |
| **领取** | 预扣 → 生成券 → 异步持久化 → 通知；失败补偿 |
| **幂等** | 请求幂等键（用户+活动）或唯一索引；重复请求返回同一结果 |
| **高并发** | Lua/Cluster 同 slot、限流、本地缓存、热点隔离 |
| **一致性** | Redis 与 DB 对账；以预扣/发放事实为准收敛 |

> 淘宝具体实现不公开；上面是**公开产品形态 + 行业常见做法**。本项目只对齐其中"预扣 + 异步落账 + 对账"这一套。

## 2. 本项目的实现（代码证据）

### 2.1 入口：限流 → 模板校验 → Lua

```java
@PostMapping("/claim")
@RateLimit(prefix = "myxhs:coupon:claim", maxRequests = 5, windowSeconds = 60, perUser = true,
           message = "领券频率过高，请稍后再试")
public R<Void> claimCoupon(@RequestHeader("X-User-Id") Long userId,
                           @Valid @RequestBody ClaimCouponRequest request) {
    couponService.claimCoupon(userId, request);
    return R.ok();
}
```

`claimCoupon` 的顺序：

```
读模板缓存（30min；NULL 60s 防穿透）
→ 模板存在/启用/未开始/已结束
→ Lua 原子领券（库存 + 限领 + DECR + INCR）
→ 结果分派：1 成功 / -1 售罄 / -2 限领 / -3 库存未初始化
```

### 2.2 Lua：一次原子完成"查库存 + 查限领 + 扣减"

```lua
-- KEYS[1] = myxhs:coupon:{templateId}:stock
-- KEYS[2] = myxhs:coupon:{templateId}:claimed:userId
-- ARGV[1] = perUserLimit
-- 返回：1 成功 / -1 售罄 / -2 达限领 / -3 库存未初始化

local stockKey = KEYS[1]
local claimedKey = KEYS[2]
local perUserLimit = tonumber(ARGV[1])

local stock = redis.call('GET', stockKey)
if not stock then
    return -3
end
if tonumber(stock) <= 0 then
    return -1
end

local claimed = tonumber(redis.call('GET', claimedKey) or '0')
if claimed >= perUserLimit then
    return -2
end

redis.call('DECR', stockKey)
redis.call('INCR', claimedKey)
return 1
```

**为什么必须 Lua**：如果拆成 `GET stock → 判断 → DECR` 多条命令，两个并发请求会同时读到 1，
都扣成功 → 超发。Lua 在 Redis 单线程里原子执行，读-判-写一步完成。

**Cluster 关键**：两个 key 都用 `{templateId}` 做 hash tag，保证落在同一个 slot——否则 Lua 直接报
`CROSSSLOT Keys in request don't hash to the same slot`。

### 2.3 `-3`：库存未初始化，不能当"售罄"

Redis 被清空/首次部署时，`stock` 不存在。本项目**从 MySQL 实时读 `remain_count` 补建**，再重试一次：

```java
private void initStockFromDb(Long templateId) {
    CouponTemplate fresh = templateMapper.selectById(templateId);
    if (fresh == null || fresh.getDeleted() != null && fresh.getDeleted() == 1) {
        return;
    }
    stringRedisTemplate.opsForValue().setIfAbsent(
            stockKey(templateId), String.valueOf(fresh.getRemainCount()));
}
```

注意：重试结果要**按 -1/-2 精确分派**（T-121）——不能把"限领"误报成"售罄"。

### 2.4 异步落账：Outbox + MQ（Design B 的入口）

Lua 成功后，`sendClaimEventSync`：

```
① 先写 Outbox（同 claimNo 幂等重试一次；写入超时≠失败）
② syncSend COUPON_CLAIM_TOPIC
   - SEND_OK → markSent（尽力）
   - 超时/非 OK → 保留 Outbox（"发送超时≠失败"，补发必达）
③ 只有 Outbox 双次写入失败才回滚 Redis + 报错（唯一回滚路径）
```

消费端 `CouponClaimConsumer`：

```
完成态幂等（isProcessed/markProcessed）+ uk_claim_no
→ 插入 t_user_coupon
→ decrementRemainCount（派生账本；失败不阻断，对账兜底）
```

> 为什么"发送超时"不回滚？回滚 + 消息补投 = **超发**（05 篇详解）。

### 2.5 双库存：谁管什么

| 口径 | 存储 | 作用 | 失败/延迟 |
|---|---|---|---|
| `stock` | Redis | **同步闸门**（实时扣） | 丢 key → `-3` 自愈 |
| `remain_count` | MySQL 模板 | **落账结果**（异步） | 慢半拍 → 对账修（04） |
| `claimed:{userId}` | Redis | **限领计数** | 对账以 DB 已发券数为准 |

**`claimed` 的语义**：包含已使用/已过期的券；退券**不减** `claimed`（RV30，04 篇）——
否则用户可以"领→用→退→再领"绕过限领。

## 3. 对照表：生产 vs 本项目

| 能力 | 生产环境 | 本项目 | 差异 |
|---|---|---|---|
| 库存预扣 | Redis 原子 + DB 落账 | ✅ Lua + 双库存 | 对齐 |
| 限领 | 用户×活动计数 + 风控 | ✅ `claimed` 计数 | 缺风控/黑名单 |
| 发放方式 | 领券中心/活动/定向/兑换码 | 仅领券中心 | 简化 |
| 幂等 | 请求幂等键 + 唯一索引 | ✅ `claimNo` + `uk_claim_no` + 完成态标记 | 对齐 |
| 热点 | 库存分片/热点探测 | 单 key（`{templateId}` 同 slot） | 超大热点需分片 |
| 失败补偿 | 异步落账 + 对账 | ✅ Outbox + 补发 + 对账 | 对齐 |
| 限流 | 网关/WAF/风控 | `@RateLimit` 5/60s | 简化 |

## 4. 八个坑

1. **Cluster CROSSSLOT**：两个 key 必须同 slot（`{templateId}`），否则 Lua 直接失败。
2. **`-3` 不是售罄**：库存未初始化要自愈重试，别直接返回"抢完了"。
3. **发送超时不要回滚 Redis**：消息可能已落 Broker，回滚 + 补投 = 超发（05）。
4. **`claimed` 退券不减**：否则绕过限领（RV30）。
5. **重复消息**：`uk_claim_no` + 完成态标记；不要只靠 Redis 去重。
6. **缓存穿透**：模板不存在缓存 `NULL` 60s；模板缓存 30min。
7. **热点模板**：单 key 有上限；超大活动要库存分片/本地合并（设计）。
8. **限流/防刷**：接口限流只是第一层，生产还要风控/黑名单。

## 5. 值不值得深挖 / 一句话

- **值得**：Lua 为什么原子、`-3` 自愈、双库存分工、`claimed` 语义——领券是券域最核心的并发点；
- **一句话带过**：模板缓存 TTL、限流阈值；
- **一句话**：**领券 = Redis Lua 原子预扣 + 限领计数 + Outbox 异步落账；不超发靠原子，不重复靠幂等，必达靠补发/对账。**
- 超发洞/Design B 的完整推演见 **05**；过期与对账见 **04**。

**面试口径**："领券用 Redis Lua 一步完成库存+限领+扣减，两个 key 用 templateId 同 slot；MySQL remain 异步落账，双库存对账；发送走 Outbox，超时不一刀切回滚，靠补发+幂等保证必达。"
