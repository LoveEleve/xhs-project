# 04 · 退券、过期与对账

> **口径**：先讲**生产环境/淘宝公开形态**，再对照本项目；代码不代表应然标准。
>
> **一句话**：退券 = 把"已用"恢复为"未用"，但**不回补名额**；过期 = 把未用标过期；
> 对账 = 把 Redis/MySQL/Outbox 拉回一致。
>
> **本篇带走**：① 生产退券规则（取消/超时/全退）② RV30 为什么不能回补 ③ 过期三层 + 三对账。
> 前置：01–03。证据：`returnCoupon`、`OrderTerminationConsumer`、`CouponExpire*`、`CouponReconcileJob`。

---

## 0. 例子：淘宝订单取消/退款，券去哪了

```
下单用券（满 200 减 20）
  ├─ 未支付取消/超时 → 券退回"未使用"，可再用
  ├─ 支付失败        → 券退回"未使用"
  ├─ 部分退款        → 券通常不退（订单仍成立，券已核销）
  └─ 全额退款        → 按活动规则：券可能退回，也可能不退
```

淘宝具体规则以活动页为准；行业常见做法是：**券的名额在"领取"时就被消耗，退券只恢复用户券状态，
不把名额加回去**——否则会超发、也会被"领→用→退→再领"绕过限领。

## 1. 生产环境怎么做（淘宝/行业常见）

| 环节 | 常见做法 |
|---|---|
| **退券触发** | 取消、超时、支付失败、全额退款/售后；部分退款一般不动券 |
| **退券语义** | 恢复用户券状态；**不回补发放名额、不减已领次数** |
| **过期** | 固定窗口/领取后 N 天；延迟队列/TTL/批量任务；用券时实时校验 |
| **对账** | Redis/DB 库存、限领计数、Outbox 卡单；差异告警/修复 |
| **幂等** | 券 ID + 订单 ID 条件更新；重复退券 0 行不报错 |

## 2. 本项目的实现（代码证据）

### 2.1 退券的两个入口

**入口 A：订单终结事件（取消/超时/支付失败/库存失败）**

```
OrderService.terminateOrder → ORDER_TERMINATION_TOPIC
  → coupon.OrderTerminationConsumer
  → couponService.returnCoupon(userId, {userCouponId, orderId})
```

消费者幂等：消息 KEYS（orderNo）24h 去重 + `returnCoupon` 条件更新；
`COUPON_NOT_FOUND`（券不存在/归属不符）视为已收敛，直接 ACK 不重试。

**入口 B：全额退款成功**

```
OrderService.onRefundSuccess（只在全退时调用）
  → returnCouponIfUsed(order)
  → couponFeignClient.returnCoupon(...)
  → 失败发 RETURN_COUPON 补偿消息
```

### 2.2 退券本体：条件更新 + RV30

```java
public void returnCoupon(Long userId, ReturnCouponRequest request) {
    UserCoupon userCoupon = userCouponMapper.selectByIdAndUserId(request.getUserCouponId(), userId);
    if (userCoupon == null || !userCoupon.getUserId().equals(userId)) {
        throw new BizException(ResultCode.COUPON_NOT_FOUND);
    }

    int affected = userCouponMapper.returnCoupon(
            userCoupon.getId(), request.getOrderId(), userId);
    if (affected == 0) {
        // 已退回/状态不匹配：幂等路径，不报错
        return;
    }
    // RV30：只恢复用户券状态；不触碰 stock/remain/claimed
}
```

```sql
UPDATE t_user_coupon
SET status = 0, used_order_id = NULL, used_at = NULL
WHERE id = #{id} AND user_id = #{userId}
  AND status = 1 AND used_order_id = #{orderId}
```

**为什么必须带 `used_order_id`**：券可能被同一用户用在**另一笔订单**；只按 `id + status` 退，
会把别人的订单用过的券退掉。带上 `used_order_id=orderId` 才能保证"退的是这单的券"。

### 2.3 RV30：退券为什么不回补名额

```
券库存（stock/remain）在【领取】时就被扣了；
用券（useCoupon）不扣库存 —— 用户已经持有这张券；
退券如果把 stock +1 / remain +1 / claimed -1：
  → remain + 已发 > total   （超发敞口）
  → 用户可以 领→用→退→再领   （绕过 perUserLimit）
```

所以 RV30 只做一件事：`status 1 → 0`；名额、`remain_count`、`claimed` 都不动。
代价是：用户退券后**不能再领一张**（领取次数已计入），但券本身回到"未使用"，可以继续用。

### 2.4 过期：三层

| 层 | 组件 | 做什么 |
|---|---|---|
| **预检** | `CouponExpirePrecheckJob`（每日） | 扫未来 24h 到期模板，补排/续排延时消息 |
| **延时消费** | `CouponExpireDelayConsumer` | 到点批量 `status 0→2`；未到期则续排下一段 |
| **兜底** | `CouponExpireJob`（每 5 分钟） | 按模板循环 `UPDATE ... WHERE coupon_id=? AND status=0 LIMIT 1000` |

**23h 分段**：RocketMQ 开源版延时窗口默认 **24 小时**，超过会立即投递；
所以 `CouponExpireDelayProducer` 每次最多排 `now+23h`，消费端没到期就再排一段。

**用券时还有实时校验**（`ExpireValidator`）：不能只依赖 `status=2`——Job 有延迟，
过期后、标记前券仍可能被用。

### 2.5 对账：三件事

```java
// ① stock：Redis 为准修 MySQL
if (redisStockStr == null) {
    // 从 MySQL remain_count 补建 Redis（⚠️ 与 -3 同一风险，见下）
    stringRedisTemplate.opsForValue().set(key, String.valueOf(template.getRemainCount()));
} else if (redisStock != mysqlRemain) {
    templateMapper.updateRemainCountOnly(template.getId(), redisStock); // Redis → MySQL
}

// ② claimed：以 DB 已发券数为准
Long dbCount = userCouponMapper.countIssued(userId, templateId);
stringRedisTemplate.opsForValue().set(claimedKey, String.valueOf(dbCount));

// ③ Outbox 卡单：status=0 超 5 分钟 → 告警（补发由 Sender Job 负责）
Long stuck = outboxMapper.countStuck(now.minusMinutes(5));
```

> ⚠️ **对账补 Redis 也有同样的风险**：`redisStockStr == null` 时用 `remain_count` 补建，
> 账本滞后会补高（超发方向）。C-018 规划了"受控重建"（-4 + 排空 + `total−issued`），当前是已知风险。

### 2.6 Outbox 补发（退券/领券共用）

`CouponOutboxSenderJob`：`@Scheduled(5s)` + Redisson 锁 → 扫 `status=0`（200 条）→ `syncSend` →
`markSent`；失败指数退避 30→480s（±20% 抖动），**记录不丢弃**——券事件必须最终送达。

## 3. 对照表：生产 vs 本项目

| 能力 | 生产环境 | 本项目 | 差异 |
|---|---|---|---|
| 退券触发 | 取消/超时/支付失败/全退 | ✅ 终结事件 + 全退 | 部分退不动券，一致 |
| 退券名额 | 通常不回补 | ✅ RV30 | 对齐 |
| 退券幂等 | 条件更新 | ✅ `status=1 AND used_order_id=orderId` | 对齐 |
| 过期 | 延迟队列/TTL/批量 | ✅ 预检 + 23h 分段延时 + Job | 分段是 RocketMQ 限制 |
| 对账 | Redis/DB/卡单 | ✅ stock/claimed/outbox | 对齐 |
| 补 Redis | 受控重建 | ⚠️ 用 remain_count 补建 | 已知风险（C-018） |

## 4. 十个坑

1. **退券不回补名额**：RV30；否则超发 + 绕过限领。
2. **退券必须带 `used_order_id`**：否则可能退掉别的订单用的券。
3. **`affected=0` 是幂等，不是失败**：重复退券/状态不匹配直接返回。
4. **部分退款不退券**：订单仍"已支付"，券保持已用；全退/取消才退。
5. **退券失败要补偿**：终结事件 MQ 重试 + `RETURN_COUPON` 补偿；永久失败会卡"已用"，需告警。
6. **过期不能只看 status**：用券时实时校验有效期。
7. **延时消息 24h 窗口**：必须 23h 分段，不能直接排 7 天。
8. **对账补 Redis 可能补高**：`remain_count` 是异步账本；受控重建是后续加固（C-018）。
9. **claimed 对账含在途**：Outbox 已写、消费未到的领取会让计数偏大；低峰执行。
10. **Outbox 不丢**：失败保留 + 退避补发；卡单 >5min 告警。

## 5. 值不值得深挖 / 一句话

- **值得**：RV30 的两个理由（超发敞口/绕限领）、退券条件里的 `used_order_id`、过期三层、对账三件事；
- **一句话带过**：Job cron、退避参数；
- **一句话**：**退券只恢复用户券状态（不回补名额）；过期靠预检+分段延时+兜底；对账修 stock/claimed/outbox 三件事。**
- 超发洞/Design B 见 **05**；分片/受控重建见 **06/C-018**。

**面试口径**："退券只做 `status 1→0`，不回补库存/限领（RV30，防超发和绕限领）；条件更新带 `used_order_id` 保证幂等且不退错单；过期是预检+23h 分段延时+Job 兜底；对账修 stock、claimed、卡单 Outbox。"
