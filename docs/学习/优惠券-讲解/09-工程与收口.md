## 0. 例子：一次领券失败，怎么被定位/兜底

```
用户点"领取"
  ├─ 售罄        → metric claim_sold_out + 返回"已抢完"
  ├─ 达限领      → metric claim_limit + 返回"已达上限"
  ├─ 库存未初始化 → -3 → 触发重建，返回"稍后"（C-018 规划 -4）
  ├─ 发送超时    → 保留 Outbox → 补发 Job → 消费
  ├─ 消费失败    → MQ 重试 → DLQ → 重放（≤3 次）→ 超限告警
  └─ DLQ 重放×重领 → G35 限领守卫拦截 + 告警
```

每一步都有**指标/日志/兜底**，不是"报个错就完了"。

## 1. 生产环境怎么做（淘宝/行业常见）

| 维度 | 常见做法 |
|---|---|
| 规则组织 | 责任链/规则引擎，按优先级执行；规则可配置/可回放 |
| 测试 | 单测覆盖分支 + 集成测试 + 压测；幂等/并发/故障注入 |
| 可观测 | 指标（成功/失败/延迟/积压）+ 日志 + 链路追踪 + 告警 |
| 兜底 | DLQ + 重放 + 人工工具；对账；runbook |
| 工程债 | 显式登记、分档、定期清理；不把"临时方案"当架构 |

## 2. 本项目的实现（代码证据）

### 2.1 责任链：用券 + 创建

**用券校验链**（`@Order`）：

```java
// 1) AmountValidator：orderAmount < minAmount → 拒绝
// 2) ExpireValidator：now 不在 [validStart, validEnd] → 拒绝
// 3) StatusValidator：模板 status != 1 → 拒绝
for (CouponValidator validator : validators) {
    validator.validate(template, orderAmount);
}
```

**创建校验链**（C-017）：

```java
// 1) TimeWindowCreateValidator：有效期窗口
// 2) DiscountCreateValidator：折扣 0.1~9.9 / 满减、无门槛 > 0
// 3) StockCreateValidator：总量上限、限领 ≤ 总量
// 4) TypeRuleCreateValidator：满减必须有门槛、无门槛门槛为 0
for (TemplateCreateValidator validator : createValidators) {
    validator.validate(request);
}
```

**为什么用责任链**：规则独立、顺序显式、可单测；避免一个 `if-else` 巨块里漏掉某个规则。

### 2.3 可观测：指标 + 日志 + 追踪

**指标族**（`businessMetrics.recordCouponAction`）：

| 前缀 | 例子 | 用途 |
|---|---|---|
| `claim_*` | `claim_ok` / `claim_sold_out` / `claim_limit` / `claim_stock_lag` | 领券漏斗/异常 |
| `use_*` | `use_ok` / `use_fail` | 核销 |
| `return_*` | `return_ok` / `return_skip` | 退券 |
| `push_*` | `push_ok` / `push_fail` / `push_skip` | 推送 |
| `dlq_*` | `dlq_replay_ok` / `dlq_replay_fail` / `dlq_replay_over_limit` | DLQ |
| 其他 | `outbox_stuck` | 卡单告警 |

**日志/追踪**：关键节点带 `userId/templateId/orderId/claimNo`；MQ 消费用 `MqTraceHelper` 恢复 traceId；
领券/退券/推送全链路可追。

### 2.4 DLQ 与 G35：两个兜底

**DLQ 重放**（`CouponDlqReplayConsumer`）：

- 监听 `%DLQ%coupon-claim-consumer-group` 和 `%DLQ%coupon-order-termination-consumer-group`；
- 重投回源 topic，`dlqReplayCount` 属性 +1；
- `MAX_REPLAY=3`：超限只告警 + 指标（防"DLQ→重放→再 DLQ"循环），转人工/对账；
- 重投失败抛异常（让本组重试/进本组 DLQ，不静默丢）。

**G35 投递时限领守卫**（`CouponClaimConsumer`）：

```java
Long issued = userCouponMapper.countIssued(userId, templateId);
if (template != null && template.getPerUserLimit() != null
        && issued >= template.getPerUserLimit()) {
    businessMetrics.recordCouponAction("claim_limit_guard_skip", true);
    idempotentHelper.markProcessed(BIZ_TYPE, msgId, TTL);
    return;   // 跳过 + 告警；stock 漏损是安全方向（少发不超发）
}
```

**为什么需要**：DLQ 重放 × "对账修正 claimed 后重领" 交叉，可能让同一用户超过限领；
守卫在**投递时**以 DB 已发券数为准再拦一次。

### 2.5 工程债：三档，不藏

**已修**：Design B/Outbox、DLQ 重放、G35、完成态幂等、32 分片、23h 分段延时、推送引擎、创建责任链、跨库事务拆分。

**已记（未修/取舍）**：

| 债 | 影响 |
|---|---|
| C-018：`-3` 受控重建 / Lua→Outbox 领取意图 | 两个边缘窗口（少卖/超发方向） |
| 按 `coupon_id` 的批量任务广播 32 表 | 过期/推送扫描成本 |
| `getAvailableCoupons` 无 LIMIT | 未用券多时列表大 |
| `listClaimableTemplates` 无缓存 | 领券中心高频查 DB |
| 推送逐用户 `syncSend` | 单条同步瓶颈 |
| 单券/无叠加/互斥 | 营销能力缺口 |
| `couponId` 命名 = userCouponId | 阅读/对接易错 |
| 无请求级领券幂等键 | 重复点击靠限领/限流 |
| 无"已用券卡住"对账 | 退券永久失败会卡"已用" |

**一句带过**：参数校验、权限注解、日志格式、配置命名——工程规范，不影响架构判断。

### 2.6 面试口径（30 秒 + 追问）

**30 秒**：

> "优惠券域我按三个问题讲：不超发、不重复、必达。领券用 Redis Lua 原子扣名额 + 限领，
> MySQL 异步落账、双库存对账；部分失败用 Design B（名额锁定即成功 + Outbox 至少一次 + `uk_claim_no` 幂等）；
> 核销用乐观锁；退券只恢复用户券状态、不回补名额（RV30）；规模化上做了 32 分片、23h 分段延时和推送引擎。"

**追问准备**：

- "32 分片怎么验证？" → 路由算法单测；无生产流量，运行时未验证（项目口径）。
- "为什么不用分布式事务？" → 跨库拆成"插券为准 + remain 派生 + 对账"；强一致代价高。
- "延时怎么做的？" → RocketMQ 24h 窗口，23h 分段 + 消费续排 + Job 兜底。
- "怎么防超发？" → Lua 原子 + 双库存 + Design B + 对账；残余窗口 C-018。
- "哪些不能吹？" → 5 万 QPS/10 万 msg/s、完整画像、template_id 映射、空分片/影子库、生产验证。

## 3. 值不值得深挖 / 一句话
