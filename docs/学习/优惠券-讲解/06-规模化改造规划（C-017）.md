# 06 · 优惠券规模化改造规划（C-017，可选）

> 定位：**规划稿，不是正文**。目标是把 xhs-project 的优惠券域从"单库 + 定时扫描"补到
> "**32 分片 + 延时消息 + 推送引擎**"，让简历/面试能**诚实**讲这三件事。
> 基线保护：不改订单/支付主链路；默认 profile 不启用新能力；现有 15 模块 726 单测必须保持全绿。

---

## 0. 目标与非目标

**目标**

1. **P1 分片**：`t_user_coupon` 按 `user_id` 分片（2 库 × 16 表 = 32 分片），模板/Outbox 保持全局表；
2. **P2 延时过期**：模板结束时发 RocketMQ 定时消息，消费端批量置过期；XXL-Job 保留兜底；
3. **P3 推送引擎**（可选）：用户分桶 + batch 分割 + `ThreadPoolExecutor + Semaphore` 推送，
   复用 home feed / notification 的推送设施，画像用 `t_user_behavior` + 笔记 tags 做**轻量聚合**。

**非目标**

- 不做真实压测，不声称 5 万 QPS / 10 万 msg/s（无运行时）；
- 不建完整画像服务（只做行为标签的轻量聚合，明确标注"简化"）；
- 不改订单/支付/库存主链路；不复制华仔代码（只参考结构，按本项目规范改写）；
- 不追求"生产验证"——口径仍是编译 + 单测。

## 1. 现状 vs JD 能力

| JD 能力 | 本项目现状 | 差距 |
|---|---|---|
| 32 分片（user_id） | 单库；ShardingSphere 依赖仅预留 | 需配置 + 建表 + 路由适配 |
| Redis Lua 扣库存 | ✅ `claim_coupon.lua`（`{templateId}` 同 slot） | 无 |
| MQ 异步落账 + Outbox | ✅ `COUPON_CLAIM_TOPIC` + Outbox + 消费幂等 | 无 |
| 延时消息过期 | ❌ 只有 XXL-Job 每 5 分钟扫 | 需新增 producer/consumer |
| 推送引擎 | ❌ 无 push 模块；但有 home feed 推拉 + notification | 需新模块/复用 |
| 用户画像 | ⚠️ 有 `t_user_behavior` + 笔记 tags；无画像服务 | 轻量聚合（简化） |
| 双库存/对账/Design B/DLQ/G35 | ✅ 本项目强项 | 无（保持） |

## 3. P1：优惠券 32 分片

### 3.1 分片设计

| 表 | 分片 | 理由 |
|---|---|---|
| `t_user_coupon` | **2 库 × 16 表**，`user_id` 分片 | 查询主路径是"我的券"（user_id）；32 分片对齐 JD/华仔 |
| `t_coupon_template` | **全局表**（ds_0 单表） | 量小；按 id/列表查，分片会引入广播/映射复杂度 |
| `t_coupon_outbox` | **全局表**（ds_0 单表） | 补发 Job 全表扫描；量小、短生命周期 |

> 为什么模板不分片：JD 的"template_id → 分片映射表"是为超大模板量设计的；本项目模板量小，
> 全局表更简单。**面试讲法**："模板是全局表，用户券按 user_id 分片；如果模板量到亿级，
> 再加 template_id 映射做二级路由。"

### 3.2 任务清单

1. 新增 `my-xhs-coupon/src/main/resources/sharding-config.yaml`：
   - `ds_0/ds_1` → `my_xhs_coupon_0/1`；
   - `t_user_coupon` → `ds_${0..1}.t_user_coupon_${0..15}`；
   - 算法：`user_id % 2`（库）、`(user_id / 2) % 16`（表）；INLINE 表达式即可；
   - 模板/Outbox 不配置 → 透传默认 ds_0。
2. 新增 `config/ShardingSphereDataSourceConfig.java`（参考 order 的同名类）：
   - `YamlShardingSphereDataSourceFactory` 手动建数据源；
   - 手动 `MybatisSqlSessionFactoryBean` + `JdbcTemplate`；
   - `@Profile("coupon-sharding")`，默认不加载。
3. SQL：
   - `sql/init-all.sql` 增加 `my_xhs_coupon_0/1` 与 32 张 `t_user_coupon_*`（`uk_claim_no` 每表唯一）；
   - 新增 `sql/migration/coupon/V2__sharding.sql`（存量迁移：按 user_id 路由插入新表）；
   - 同步 `sql/mysql-content-init.sql`（第二份基线）。
4. Mapper 适配（**关键**）：
   - `t_user_coupon` 按 `id` 的 `selectById/update` 目前不带 `user_id` → ShardingSphere 会**广播到 32 表**；
   - 改为 `WHERE id=? AND user_id=?`（请求里已有 userId），保证单分片路由；
   - 列表/统计查询天然带 user_id，无需改。
5. 测试：
   - `CouponShardingRouteTest`：`user_id % 2` / `(user_id/2)%16` 的路由断言（纯算法，不连库）；
   - 现有 24 个 coupon 测试保持通过（默认 profile 单库）；
   - 全仓编译 + 15 模块基线（726）。

### 3.3 验收

- `mvn -o -pl my-xhs-coupon -am test` 绿；
- 默认 profile 下 726 基线不变；
- `coupon-sharding` profile 能编译通过（无运行时启动验证）；
- 路由单测覆盖边界（user_id=0/1/31/32/最大）。

### 3.4 风险

| 风险 | 缓解 |
|---|---|
| MyBatis-Plus + ShardingSphere 配置复杂 | 直接复用 order 的 `ShardingSphereDataSourceConfig` 结构 |
| id 查询广播（性能/一致性） | 所有按 id 的读写补 `user_id` 条件 |
| 测试无 DB | 路由用纯算法单测；Mapper 只做编译/契约测试 |
| 分片后 `uk_claim_no` 只在单表唯一 | 消费幂等仍成立（claimNo 全局唯一由生成端保证）；跨表重复概率可忽略，必要时加全局去重表 |

## 4. P2：延时消息过期

### 4.1 设计

```
模板创建/启用（valid_end 确定）
  → 发 RocketMQ 定时消息（setDeliverTimeMs = valid_end）
  → COUPON_EXPIRE_TOPIC
  → 消费端：分页 UPDATE t_user_coupon SET status=2
            WHERE coupon_id=? AND status=0
  → 幂等：条件更新；valid_end 变更时以最新模板为准
XXL-Job（每 5 分钟）保留兜底（消息丢/延迟偏差）
```

### 4.2 任务

1. `CouponExpireDelayProducer`：`RocketMQTemplate.syncSend` + `setDeliverTimeMs`；
2. `CouponExpireDelayConsumer`（新消费组，maxReconsume=3）：分页 0→2，幂等；
3. `CouponService.createTemplate/updateTemplateStatus` 发送（valid_end 为空/已过期不发）；
4. `CouponExpireJob` 保留；新增指标（delay_sent/consumed/fallback）；
5. 测试：producer payload、consumer 幂等、valid_end 变更、过期边界。

### 4.3 风险

- RocketMQ 5.x 定时消息依赖 Broker 时间轮配置；**无运行时无法验证**，以单测 + 文档标注；
- 同模板重复消息 → 条件更新幂等；
- 时钟偏差 → Job 兜底。

## 5. P3：推送引擎（可选）

### 5.1 用例与设计

**用例**：优惠券到期提醒（发券后第 6 天推送"明天过期"）。

```
XXL-Job（分片广播）
  → 取"明天过期"的用户券（按 user_id 分片）
  → 用户分桶（hash 或 行为标签 top-N）
  → batch 分割（≤800KB/批，对齐 RocketMQ 限制）
  → SharedThreadPool（ThreadPoolExecutor + Semaphore）
  → 推送：复用 notification 站内信（MQ/内部接口）
```

**画像**：用 `t_user_behavior`（点击/点赞/收藏/停留）+ 笔记 tags 聚合"用户 top 兴趣标签"，
用于**分桶/内容匹配**；没有画像服务，面试明确说"轻量聚合，不是完整画像"。

### 5.2 任务（若做最小版）

1. 新模块 `my-xhs-push`（或 notification 内 `push` 包）：pom/app/job/splitter/pool/sender；
2. `UserBucketSplitter`（按 800KB 或 N 条切批）+ `SharedThreadPool`（Semaphore 限流）；
3. 推送通道：notification 内部接口/MQ（若没有，新增 `X-Internal-Call` 端点）；
4. 失败记录表 + 重试 + 指标；
5. 测试：切批边界、信号量限流、幂等、失败重试。

### 5.3 决策点

- **最小实现**（2–3 会话）还是**只写设计文档**（0.5 会话）？
- 推送用例选"到期提醒"（数据现成）还是"活动券推送"（需要运营配置）？

## 7. 验收与口径

**可以诚实讲**：

- "优惠券用户券按 `user_id` 做 2 库 × 16 表共 32 分片，模板/Outbox 为全局表；按 id 的读写带 user_id 避免广播"；
- "模板结束时发 RocketMQ 定时消息（`setDeliverTimeMs`），消费端批量置过期，XXL-Job 兜底"；
- "推送引擎按用户分桶、batch 分割、共享线程池 + Semaphore 限流；画像用行为标签做轻量聚合"。

**不能讲**：

- 5 万 QPS / 10 万 msg/s（未压测）；
- 完整用户画像/推荐系统（只有行为标签聚合）；
- 生产验证（口径仍是编译 + 单测）。
