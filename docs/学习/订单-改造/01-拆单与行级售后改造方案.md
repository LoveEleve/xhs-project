## 一、背景（现状 → 目标）

**现状（xhs）**：单层订单（一个 `status` 字段）+ 订单级售后（售后单挂"订单+SKU"）；无商家维度、无拆单。

**目标**：三层模型——

```
父订单 ×1     （交易/支付维度：一笔钱、一个支付单）
 ├─ 子订单 ×N （商家维度：履约 / 售后入口 / 结算）
 │    └─ 行 ×M（SKU 维度：售后粒度、金额粒度）
 └─ 售后单 ×K（挂在行上：退某件商品 → 挂该行）
```

**运行示例（贯穿全文）**：一笔支付买 2 箱气泡水（200，A 店）+ 短袖（30，B 店）+ 裤子（70，B 店）；平台券满 300-20 + B 店券满 100-10 → 实付 **270**。

## 二、目标模型（设计决策）

### 2.1 三层实体与职责

| 层 | 职责 | 编号的用途 |
|---|---|---|
| 父单 | 交易状态 + 金额 + 支付单绑定 | 支付 / 对账锚点 |
| 子单 | 商家 ID + 履约状态 + 金额（= Σ行） | 履约 / 售后展示锚点 |
| 行 | SKU + 数量 + **分摊后金额** | **售后粒度** |
| 售后单 | 挂行 ID（+ 冗余父单/子单/买家，作路由键） | 售后锚点 |

### 2.2 拆单时点与方式

- **下单即拆**（采用）：结构在支付前就完整；拆单 = 纯本地操作（按商家分组 + 同事务写入子单/行）；
- **不采用异步拆单**：会引入"支付回调先到、结构未建好"的一致性窗口；
- 支付成功只做**状态推进**（幂等），不负责"补建结构"。

### 2.3 展示与存储分离（"支付前是一个整体"从哪来）

- 存储层：**始终三层**（下单即有子单/行）；
- 展示层：未支付时收拢为"一笔待支付订单"入口；支付成功后按子单展开（"待发货"列表按商家分组）；
- **不给子单加"可见/不可见"状态**——可见性是展示逻辑（按支付状态渲染），不是数据模型字段。

### 2.4 状态职责（聚合规则）

- 真正流转的是**子单/行**（发货、收货、退款都发生在这一层）；
- **父单状态 = 子单状态的聚合函数**：子单全完成 → 父单完成；子单全取消 → 父单关闭；"部分"的语义用子单表达，父单保持粗粒度；
- 规则必须**穷尽、单向**（父单不反向控制子单）。

### 2.5 金额守恒（分摊落库）

- 下单时把每个优惠摊到行（存 `discount_share`）；分摊口径 = **按金额比例**（不是按件数平均）；
- 优惠有**适用范围**：平台券摊全部商品；店铺券只摊本店商品；
- 守恒律：**父单实付 = Σ子单 = Σ行**；单行退款 ≤ 行可退；累计退款 ≤ 父单实付；取整误差由"兜底行"吸收；
- 示例计算（上例）：

| 行 | 原价 | 平台券 20（按比例） | B 店券 10（只摊 B 店） | 行实付 |
|---|---|---|---|---|
| 水（×2） | 200 | 13.33 | — | 186.67 |
| 短袖 | 30 | 2.00 | 3.00 | **25.00** |
| 裤子 | 70 | 4.67 | 7.00 | 58.33 |
| 合计 | 300 | 20 | 10 | **270** |

退短袖 → 退 **25.00**（实付口径），不是 30。

### 2.6 分片与查询

- 父单按 `buyer_id` 分片；**子单/行必须同分片**（否则 join 炸）；
- 买家维度查询（"我的订单/售后"）用 `buyer_id`；商家维度（店铺订单/售后）→ **ES / Canal 异构索引**。

## 三、实施路径（四阶段，禁止 big bang）

| 阶段 | 内容 | 独立价值 |
|---|---|---|
| ① **分摊落库** | 下单时把优惠摊到行（`discount_share` 落库） | 行级退款/结算的地基；顺带修复退补口径问题 |
| ② **售后挂行** | 售后单从"订单+SKU"改为挂行 ID（先不拆单） | 粒度先对，独立可上线 |
| ③ **拆单** | 引入子单（商家维度）+ 父单状态聚合 | 换代级 |
| ④ **履约/结算下沉** | 发货/收货/结算按子单 | 收尾 |

## 四、难点清单（按"硬"排序）

1. **金额守恒**：跨店满减 / 平台券 / 店铺券的摊法 + 出资方（平台 vs 商家）+ 取整 + 累计校验——错一分，对账炸；
2. **父单状态聚合**：穷尽所有组合（全完成 / 全取消 / 一半完成一半退款中 / 一半发货一半取消…）+ 单向；
3. **竞态矩阵**：父单/子单/行/售后/退款**五对象交叉**，每一对要定义"谁先赢"：
   - 支付回调 vs 拆单（父单置已付款 + 子单们置已付款，原子性）；
   - 行售后 vs 子单发货（售后中的行是否拦截发货）；
   - 行级退款累计 vs 父单全退（两条路都能"退满"→ 防重复退钱）；
4. **迁移与灰度**：老数据映射（老订单 → 1 父 + 1 子 + N 行）、双跑影子校验（两套模型账目相等）、灰度切流、可回滚可审计；
5. **业务规则重新定位**：关单超时（父单级）、自动确认收货（子单级）、售后时效（行级，从所在子单确认收货起算）、库存占用（行级）、通知/展示（子单·行级）——≈ 半个业务重写。

## 五、验收不变式（执行时的硬指标）

- **金额**：任一时刻 父单实付 = Σ子单 = Σ行；退款累计 ≤ 父单实付；
- **状态**：父单状态 ∈ 聚合函数值域（不存在"聚合不出来的状态"）；
- **竞态**：每个交叉点有明确的"谁先赢"定义 + 测试覆盖；
- **迁移**：影子双跑账目相等；任一步可回滚。
