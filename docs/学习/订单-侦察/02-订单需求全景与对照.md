> 用途：**认知地图 + 面试弹药（不是施工 TODO）**。
> 镜头：真实电商业务与规模 → 需求 → xhs 实现对照 → 缺口三档分级。
> 对象：`my-xhs-order`（细节证据见 `00-侦察报告.md` / `01-华仔订单对比.md`）。
> 建立：2026-10-11。**本文档是模板**——其余核心模块（库存 / 支付 / 购物车 / 优惠券…）按同粒度复制。

---

## 0. 怎么用这份文档

三个用途：

1. **知道边界**：被问"你们订单有对账吗/有大数据出口吗"——能答"没有；因为 X；真实系统这么做 Y"。缺什么不可怕，**不知道缺什么**才可怕；
2. **分级行动**：缺口折成三档（下方），焦虑变计划；
3. **保持聚焦**：项目是简历/学习项目，价值在"讲透已有的 + 讲清缺口的"，不是堆功能。

三档定义：**补**（Tier 1，照抄现有模式即可，低成本高价值）/ **讲**（Tier 2，理解机制 + 面试口径）/ **不做**（Tier 3，明确超出项目定位）。

## 1. 真实业务流（订单域全景）

```
[商详/购物车] ──立即购买 / 勾选结算──▶ [订单确认页]
                                          │ 预下单聚合：商品 + 地址 + 支付方式 + 优惠试算 + 库存展示
                                          ▼
[提交订单] 校验（上架/库存/券/风控）──▶ 预占库存 ──▶ 落单（订单+明细+事件+快照+消息凭据）
                                          │                     ↘ 异步通知下游（券/购物车/数据…）
                                          ▼
[支付] 支付单 ─▶ 收银台 ─▶ 支付回调（会重复/乱序/丢失 → 幂等+兜底）
                                          ▼
[支付成功] 改"已支付" ─▶ 资源核销（库存成交/券核销/积分）─▶ 通知下游（推送/短信/数据）
                                          ▼
[履约] 发货(物流单号) ─▶ 物流轨迹 ─▶ 签收 / 自动确认收货 ─▶ 完成
                                          ▼
[售后窗口] 仅退款 / 退货退款 / 部分退 / 多次退

逆向线：取消（用户/超时/支付失败/库存失败/风控）
数据线：对账（订单↔支付↔库存）、结算、大数据、客服、物流
```

## 2. 需求全景与 xhs 对照（四组）

### A. 交易功能（用户可感知的业务能力）

| 需求 | xhs 现状 | 备注 |
|---|---|---|
| 结算入口：立即购买 / 购物车勾选 | ✅ 购物车模块 + `createOrder`（skuItems 多商品） | |
| 订单确认页 / 预下单聚合 | ⚠️ **部分**——已核实（2026-10-11）：home BFF 聚合了**购物车页**（购物车+可用券+实时库存）及商品详情/笔记/用户主页；但**无结算/确认页聚合**（地址、订单级试算），订单侧亦无预下单接口 | 结算聚合缺口归 Tier 2 |
| 多商家拆单（平台券/店铺券分账） | ❌ 无商家维度（平台单商家模型） | |
| 限购 / 反刷单风控 | ❌ `createOrder` 无风控位 | |
| 金额体系：商品价/运费/多优惠/积分 | ⚠️ 只有"商品价 − 单券"（couponId 单字段）；无运费、无积分、无叠加 | |
| 支付：方式/支付单/金额校验/重复支付防护 | ⚠️ 支付单在 payment 域；金额校验有 `pay-amount` 端点；重复支付=状态闸门 | |
| 履约：发货/物流/自动收货/延长收货 | ⚠️ 有 logisticsCompany+trackingNo 字符串；无轨迹、**无自动确认收货**（status=2 永久停留） | 未找到任何自动收货 Job |
| 售后窗口管理（签收后 N 天可退） | ❌ 无时限窗口（仅要求订单状态 1~3） | |
| 取消（用户/超时/支付失败/库存失败） | ✅ 四来源齐；❌ 风控取消、换货 | |
| 售后：仅退款/退货退款/部分退/多次退 | ✅ 类型 1/2、部分退、恢复任务 | 退补口径缺陷已知（§3 Tier 1-#10） |
| 查询：列表/详情/按单号 | ✅（映射表路由非分片键查询） | |
| 通知：站内/短信/推送 | ⚠️ 站内（type=5）✅；短信/推送 ❌ | |

### B. 一致性与账务（订单 = 交易账本）

| 需求 | xhs 现状 | 备注 |
|---|---|---|
| 库存三态：预占 → 成交 → 退回 | ✅（available/locked 语义 + Lua） | |
| 优惠资源：锁定 → 核销 → 退回 | ⚠️ 券是"下单即核销、取消/退款退回"（**无锁定态**）；红包/积分无 | 与教科书模型差异，可讲 |
| 幂等：重复提交/重复回调/重复消费 | ✅ 四层（bizIdentifier + 状态闸门 + msgId 闸 + 版本门） | |
| 跨服务原子性（下单链路） | ✅ 事务消息 + 本地消息表（双角色）| 缺陷：confirm 无补偿、补偿自循环（Tier 1） |
| 超时与终态收口 | ✅ 关单双通道；❌ 自动收货超时、售后时限 | |
| **对账体系（订单↔支付↔库存）** | ⚠️ 库存 L3 对账 ✅；支付域有补偿/结算对账 Job；**订单↔支付↔库存的三方账务对账无独立体系** | Tier 2 重点 |
| 数据修复（对账/校准/人工） | ✅ 事件校准 Job（干跑）+ 映射修复 Job；盲区已知 | |

### C. 规模与稳定（真实压力量级推导）

| 需求 | xhs 现状 | 备注 |
|---|---|---|
| 大促：限流/降级/熔断/排队削峰 | ⚠️ 网关限流 + Sentinel + @RateLimit ✅；**无排队/削峰**（秒杀级流量会直接打穿） | Tier 2 |
| 存储：分库分表/冷热分离/历史归档 | ⚠️ 4×4 分片 ✅；**无归档**（订单表永久增长） | Tier 1-#8 |
| 缓存：订单详情/商品快照 | ⚠️ 详情缓存键 `myxhs:order:info` **只有删没有写**；下单商品快照 ✅ | Tier 1-#6 |
| 热点 | 库存域 `HotSkuDetector` ✅；账号级热点 ⚠️ | |

| 容灾（DB/MQ 故障降级策略） | ⚠️ fail-closed 有；多机房/强降级 ❌ | |

## 3. 缺口三档分级

### Tier 1 — 补（代码加固；都能"照抄现有模式"）

> **2026-10-11 验证后修订**：经逐条读码验证，真 BUG 共 6 项 → **已修 5**（confirm 补偿 / 补偿自循环 / 竞态 500 / 退款防重 / 回补落标），第 6 项（退补口径）留待设计；原列表中的"归档 / 自动收货"= **功能项**、"缓存坡脚 / TTL / 限流"= 清理与观察项，均已移出"修复"范畴。明细见 `03-修复记录.md`。

| # | 缺口 | 现象（证据） | 参考模式 | 预计 |
|---|---|---|---|---|
| 1 | **confirm 无补偿**（问题 4） | `confirmInventoryDeductSync` 失败仅日志 | 复用 RELEASE 补偿链（补偿消息 + 兜底集合） | 2-3 天 |
| 2 | **补偿自循环无退避**（问题 5） | 失败→吞掉→再发新消息，秒级自旋 | 补偿消息带延时级别 / 重放路径加间隔（`RetryBackoffUtils` 已有） | 1-2 天 |
| 3 | 取消/支付失败竞态未捕获 | `cancelOrder`/`onPaymentFailed` 遇乐观锁冲突抛 500 | 对齐 `onPaymentSuccess` 的 catch + 幂等返回 | 0.5 天 |
| 4 | 退款重试前不查支付域事实 | `retryRefund` 直接重发（可能二次退款） | 对齐 `resolveStuck`：先 `listRefunds` 核对 | 1 天 |
| 5 | `restock_status` 主链路不落标 | 正常完成单靠恢复任务"重放一次"补标 | 在 `executeRefund` 成功分支补 `markRestocked` | 0.5 天 |
| 6 | 订单详情缓存坡脚 | `myxhs:order:info` 9 处 delete、0 处 write | 二选一：补写端 / 移除无写入的删除动作 | 0.5 天 |
| 7 | **自动确认收货 Job** | 无（status=2 永久停留） | 照抄 `OrderCloseJob`（游标扫 + 临界时间） | 1 天 |
| 8 | **历史订单归档 Job** | 无（表永久增长） | 照抄 `ReconcileJob.purgeTablesDaily`（日切标记 + 有界排空） | 1 天 |
| 9 | 兜底集合 TTL 不对称 + `pay/create` 无限流 | OrderService 写入不设 TTL；支付创建无 @RateLimit | 统一 expire / 补注解 | 0.5 天 |
| 10 | 售后退补口径漏补（08 §6.6） | 售后传"本次量"、库存按"累计目标"→ `max(a,b)` 漏补 | **需要跨模块设计决策**（改契约或改语义），成本另算 | 设计+2 天 |

> 执行顺序建议：**1 → 2 → 3/5 → 7/8**（一致性优先，其次功能补齐，最后整洁度）。

### Tier 2 — 讲（不写代码；理解机制 + 面试口径）

| 缺口 | 真实系统怎么做（口径要点） |
|---|---|
| 排队削峰（秒杀） | 网关令牌桶预筛 + Redis 原子预扣 + MQ 异步建单（"下单异步化"）；库存预热；前端答题/预约制 |
| 大数据出口 | Canal 增加 order instance（binlog→MQ→数仓）；或业务事件导出（事件表→同步器）；**不让数仓直连业务库** |
| 三方对账（订单↔支付↔库存） | 日终对账：各方出明细/汇总文件或流水表 → 比对 → 差错池 → 人工/自动调账；xhs 只有库存域内 L3 |
| 多商家拆单 | 父订单+子订单模型：按商家拆、支付合并、履约/退款分拆 |
| 运费/积分/多优惠叠加 | 优惠引擎：规则 + 优先级 + 互斥组 + **行级分摊算法**（部分退款的计算基础） |
| 预下单聚合 | BFF/聚合层或预下单服务：试算 + 防篡改凭证（锁定价格与优惠） |
| 自动收货 / 售后窗口 | 签收/发货后 N 天定时状态推进（与关单 Job 同族） |
| 风控反刷 | 下单前置风控：黑名单/频控/设备指纹 → 拦截或标记人工审 |
| 冷热分离 | 历史订单归档表/冷库，按时间分区；C 端只查热数据 |

### Tier 3 — 不做（明确超出项目定位）

客服系统 / 物流轨迹系统 / 商家体系 / 发票 / 多机房容灾 —— 文档注明即可，面试被问就答"简化掉了 + 真实做法是……（Tier 2 口径）"。

## 4. 面试口径速查（缺口 → 答案）

| 可能被问 | 怎么答 |
|---|---|
| 怎么保证不超卖？ | 预占三态（available/locked）+ Lua 原子 + L3 对账兜底 |
| 订单/支付/库存不一致怎么办？ | 库存有 L3 对账；支付有补偿 Job；**三方账务对账是缺口**——真实系统用日终对账+差错池 |
| 大促怎么扛？ | 限流（网关+注解）+ 分片 + 异步化；**排队削峰是缺口**——真实系统用令牌桶+异步建单 |
| 支付回调重复/丢失？ | 双通道 + 状态闸门 + 支付侧补偿 Job |
| 怎么定位状态错误？ | 事件溯源（不可变事件表）+ 快照 + 校准 Job（重放比对） |
| 售后金额怎么算？ | 优惠分摊到行（`DiscountAllocator`）+ 占用/已退额度校验；**部分退的口径缺陷已知**（Tier 1-#10） |

## 5. 执行建议

1. **Tier 1 先挑 2-3 项**：建议 `confirm 补偿`（一致性核心）+ `归档 Job` + `自动收货 Job`（后两个是照抄模式，最快见效）；
2. **Tier 2 全部转口径**：不写代码，但每个都能讲 2 分钟"真实系统怎么做"；
3. **模板复制**：库存 / 支付 / 购物车 / 优惠券 → 各出一份同结构文档（业务流 → 需求四组 → 对照 → 三档）；
4. 维护方式：本文档与 `00-侦察报告`、`01-华仔对比` 同目录，后续修复/口径更新时同步回写。
