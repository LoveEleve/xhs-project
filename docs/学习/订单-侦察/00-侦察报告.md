## 0. 头号发现（P0 · 已亲验 · 已修复）：`OrderMapper` 注解错位 → 订单模块无法启动

**位置**：`my-xhs-order/src/main/java/com/myxhs/order/mapper/OrderMapper.java:66-80`

```java
66:    @Select("SELECT * FROM t_order WHERE status = 0 AND deleted = 0 " +
67:            "AND created_at < #{deadline} AND id > #{lastId} ORDER BY id ASC LIMIT #{limit}")
68:    /**
69:     * 校准候选：已支付/已发货 + 创建于时间窗内（走 idx_status_created，无分片键广播各分片）
70:     */
71:    @Select("SELECT id, user_id, status FROM t_order WHERE deleted = 0 AND status IN (1, 2) "
72:            + "AND created_at BETWEEN #{start} AND #{end} ORDER BY id ASC LIMIT #{limit}")
73:    List<Order> selectCalibrationCandidates(...);
74:
75:    List<Order> selectTimeoutOrders(...);   // ← 无任何注解
```

- **两个后果**：① `selectCalibrationCandidates` 挂了**两个** `@Select`；② `selectTimeoutOrders` 的注解被"挤走"，**没有语句**。
- **亲验证据**：
  - 字节码（`target/classes`，9-28 编译）：`selectCalibrationCandidates` 的 `RuntimeVisibleAnnotations = Select$List([超时SQL, 校准SQL])`；`selectTimeoutOrders` 无 `RuntimeVisibleAnnotations`；
  - 运行时复现（MyBatis 3.5.16 真实 jar + `target/classes`，`new Configuration().addMapper(OrderMapper.class)`）：
    ```
    addMapper FAILED: org.apache.ibatis.builder.BuilderException
    msg: Detected conflicting annotations '@...Select(...status=0...)' and '@...Select(...status IN (1,2)...)'
         on 'com.myxhs.order.mapper.OrderMapper.selectCalibrationCandidates'
    hasStatement selectTimeoutOrders = false
    hasStatement selectCalibrationCandidates = false
    ```
- **影响**：Spring `@MapperScan` → `MapperFactoryBean` 解析即抛 → **应用上下文启动失败**（订单模块当前不可运行）；即便绕过，`selectTimeoutOrders` 也报 `Invalid bound statement`——**订单超时关单 Job 与补偿兜底重放（`OrderCloseJob`）同时失效**。
- **根因（git 实证）**：本错误由 `ac2538f5`（2026-10-09 收口提交的**工作区快照**）引入——新增"校准候选"方法块时插在了 `selectTimeoutOrders` 的 `@Select` 与方法签名**之间**（diff 可见纯插入）。
- **修复**：把校准方法的 `javadoc + @Select + 签名` 整体移到 `selectTimeoutOrders` 之后，使每个 `@Select` 紧贴自身方法（一行块重排）；建议补一个"Mapper 接口可解析"的冒烟测试防回归。
- **修复记录（2026-10-11 已执行）**：按上述方案重排 `OrderMapper.java`。复验（**编译级，未启动应用**）：`javac` 通过 → MyBatis `addMapper(OrderMapper.class)` 返回 **OK**，`hasStatement(selectTimeoutOrders)=true`、`hasStatement(selectCalibrationCandidates)=true`。修复仅恢复 Mapper 可解析性，不改变任何业务语义。

## 3. 四条主链路

### 3.1 下单链路（`createOrder`，24 步核心）

```
①参数/幂等(24h Redis)/用户级锁(10s) → ②Feign 取真实 SKU(product) → ③SPU 上架校验
→ ④同 SKU 去重 → ⑤前置库存校验(inventory /stock) → ⑥orderNo 生成(Redis 日序列)
→ ⑦定价(真实价) → ⑧券折扣(coupon) → ⑨地址快照(user)
→ ⑩发事务半消息(ORDER_TRANSACTION_TOPIC) → ⑪本地事务[同事务]：插 t_order + 事件 CREATED + t_order_item + **t_local_message**
→ ⑫标记本地消息已投递 → ⑬券核销(失败→取消订单) → ⑭发 30min 延时关单消息
→ ⑮事件双写(幂等 no-op) → ⑯快照 CREATED → ⑰orderNo→userId 映射落公共库(失败靠 RepairJob)
```

要点：**订单号** = `ORD` + `yyyyMMddHHmmssSSS` + `userId%10000` + `seq%10000`（Redis INCR，降级随机）；映射表支撑"非分片键查询"（by-order-no / 回调按 orderId 反查 userId 再路由分片）。

### 3.2 支付链路（双通道 + 竞态）

- **双通道**：payment 侧 Feign `notifyPaySuccess`（主）+ `PAY_RESULT_TOPIC` MQ（常态双发，非"仅失败才发"——注释漂移）；order 侧 `onPaymentSuccess` 以"状态必须=0 + 事件乐观锁"做幂等，竞态时**返回 false 不抛异常**（防 payment 误判无限重试）。
- **成功尾部顺序**：`appendEvent(PAID)` → `setPaidAt` → `confirmInventoryDeduct`(异步 fire-and-forget) → 快照 PAID → 删缓存 → 发通知。
- **confirm 链**：`derivePseudoOrderId(orderNo)`（SHA-256 前 8 字节，与库存侧算法一致）→ `POST /api/inventory/confirm`；**失败仅日志**（问题 4 的 order 侧证据；与 RELEASE 的完整补偿链不对称）。
- **不对称**：同一 `false` 语义——payment Feign 通道收到 businessRejected → **自动退款**；MQ 通道只打日志丢弃。`transient_status_lost`（事件 SQL 失败）返回 false 会被 payment 当业务拒绝触发退款（风险点）。

### 3.3 取消/关单/超时链路（三路径 + 双通道兜底）

- **用户取消**：守卫 status=0 → `EVENT_CANCELLED` → 补 cancelled_at → **并行** release+退券（3s 超时降级）→ 快照/删缓存/通知。竞态未捕获乐观锁异常（会 500，与 onPaymentSuccess 的处理不对称）。
- **超时关单**：延时消息（`ORDER_CLOSE_TOPIC`，delayLevel=16=30min）为主 + `orderCloseJob`（每分钟扫 30min 前待付款）兜底；`closeTimeoutOrder` 幂等（status 守卫），catch 任意异常 → `sendCompensationMessage("CLOSE_ORDER")`。
- **支付失败**：`onPaymentFailed` → `EVENT_CANCELLED`（原因=支付失败）→ release+退券 → **无站内通知**（与 cancelOrder 不一致）。
- **库存失败收口**：`INVENTORY_FAILED_TOPIC` → status=0 直接取消+释放+退券+通知；status=1 仅 ERROR+指标（人工）。

### 3.4 售后/退款链路

```
申请(apply)：权益快照重算(优惠分摊) → 上限校验(单品占用+订单占用) → 唯一键(order,sku,type) 插入/复用
→ 审核(audit,内部)：复核订单状态+额度 → 0→3(REFUNDING) → executeRefund
→ 退款(payment refundByOrder) → 成功: 库存回补 refund-restore → 3→4；失败: 3→6
→ 恢复任务(每10min)：卡死(3>5min)查支付域事实收敛 / 失败(6,≤3次)重试 / 完成未回补(restock_status=0)重补
```

**全额退款旁路**（非售后）：`onRefundSuccess` → 先 `confirmInventoryDeductSync`（清预扣）→ `restoreStockOnRefund`（**整件数量**）→ 退券 → 状态 5。**部分退款不通知订单**（payment 侧仅"累计退款≥支付额"才通知）。

## 4. 可靠性基础设施

### 4.1 本地消息表（一张表，两个角色）

- **角色 A：事务消息回查凭据**（Broker 回查 → 查表 → COMMIT/ROLLBACK）。
- **角色 B：Outbox 补发**（`localMessageRetryJob` 每 30s 扫 `status∈{0,2}` 重投；指数退避 30→480s±20%；5 次失败 → 死信 status=3；`deadLetterScanJob` 每小时重投死信 ≤3 次；7 天清理）。
- COMMIT 后立即 `markSuccessByTransactionId` 抑制重复补发（WHERE `status=0`）。
- **双投窗口**：若 Job 在标记前用新 msgId 重投，靠库存侧 `pseudoOrderId` Lua 幂等（返回 -1 视为成功）吸收——**业务安全依赖下游幂等**。

### 4.2 补偿体系（RELEASE_STOCK / RETURN_COUPON / CLOSE_ORDER）

- 生产：Feign 失败 → `ORDER_COMPENSATION_TOPIC`；**MQ 失败 → 本地兜底集合** `myxhs:order:compensation:pending`（⚠️ OrderService 写入路径不设 TTL）。
- 消费：`OrderCompensationConsumer`（msgId 去重 10min 非原子；`reconsumeTimes>=2` 写兜底集合 24h TTL）。
- 重放：`orderCloseJob.replayCompensationFallback` 每分钟 ≤20 条。
- ⚠️ **自循环（坐实台账问题 5）**：RELEASE 补偿走 `compensateReleaseStock → releaseInventory`，其内部失败**被吞掉**并"再发一条新补偿消息"→ 消费者正常 ACK → 新消息 `reconsumeTimes=0`、无延时 → **秒级自旋、无退避**；`writeCompensationFallback` 永远不触发（条件 `>=2` 在这条路径不成立）。

### 4.3 订单号与映射

见 §3.1；失效时 `orderMappingRepairJob`（每 5min，Redis 游标滚动全分片扫，缺则补录）兜底。

### 4.4 事件溯源

- `t_order_event`（不可变，`uk(order_id,event_seq)`）+ `appendEvent`（快路径幂等 → 白名单校验 → `updateStatusWithLock` 乐观锁 → insertIgnore）。
- 快照 `t_order_snapshot`（CREATED/PAID/CANCELLED/DELIVERED/COMPLETED/REFUNDED）。
- 校准：`orderEventCalibrationJob`（每日 05:00，**trigger_status=0 未启用**）只报告不修复；修复需人工调 `internal/reconcile?repair=true`。

### 9.1 库存 08 篇 §6.6 未决问题——本轮回合成功复核

**结论：口径实锤不一致，存在可复现漏补。**

- 售后侧传 `applyQuantity`（本次量，`AftersaleService.java:494`）；库存侧按 `inventory:refund:{orderId}:{skuId}` 的**累计目标**解析（`REFUND_RESTORE_DELTA_SCRIPT`，只补正增量）。
- 唯一键 `(order_id,sku_id,type)` 限制同 SKU 每类售后单各一张 → 最多两次回补调用（type1 退 a 件、type2 退 b 件）；
- 例：item=3 件，type1 退 1 → 目标 1（补 1）；type2 退 2 → 目标 2（补 1）。**累计补 2 ≠ 退款量 3 → 漏 1 件**（一般结论：累计回补 = `max(a,b)`，不是 `a+b`）。
- **收敛条件**：仅当订单后续走到"全额退款"旁路（传整件=3，补差 1）才补齐；纯部分售后场景**长期漏补**。
- **不可被检测**：库存 L3 对账比对 Redis↔MySQL，两者被同额少加 → "自洽地少"；订单侧也不知道库存欠量 → 无自动检出。
- 佐证链：`AftersaleService.java:485-508 / 551-557 / AftersaleRepository.java:143-149`、`InventoryService.java:76-81`、`OrderService.java:964-986`。

6. **兜底集合 TTL 不对称**（OrderService 写不设 TTL；消费方写设 24h）。
7. **重放"成功"判定失真**（Job 只要不抛异常就移除成员，而失败异常在 releaseInventory 内被吞）。
8. **cancelOrder / onPaymentFailed 未捕获乐观锁竞态**（支付先赢 → 500；onPaymentSuccess 同类竞态则被捕获）。

### P2（工程债/边界）
9. `restock_status` 主链路不落标（正常完成单全靠恢复任务"重放一次 delta=0"补标）。
10. 售后状态 `1=已同意` 是**死状态**（同意直接 0→3；DDL/注释仍写 0→1）。
11. `refund-fail` 回调空实现（仅日志）。
12. 手动/自动退款重试**不先核对支付域事实**（可能二次退款，靠支付域累计上限兜底）。
13. zone-aware 切 slave 会**波及售后写**（t_aftersale 与映射表共用数据源）。
14. 网关未剥离 `X-Internal-Call`/`X-Admin-Call`（纵深防御缺口）。
15. `pay/create` 无任何限流（资金动作防护弱于取消）。
16. 状态机口径三处不一致（事件白名单 / 业务入口 / 对账白名单）。
17. 补偿消费幂等非原子（hasKey + 事后 set，注释写 SETNX）。
18. `t_order_event` ID 职责重叠（实体 AUTO 与 ShardingSphere snowflake 双配置）。

### P3（注释漂移/化石）
19. sharding yaml 头部注释（直接取模）vs 实际 `hashCode` 变形；worker-id 注释 vs 代码（掺 serverPort）。
20. pay.type 注释"默认 mock" vs yaml `remote`（MockPayService/PaymentDataSource 成死配置）。
21. payment 侧多处"MQ 无消费端/仅失败才发"注释与实现相反；`MockPayService` 失败率注释 50% vs 代码 30%。
22. `EVENT_CREATED` 双写（本地事务内一次 + 提交后一次，靠幂等吸收）。
23. `myxhs:order:info` 缓存键**只有 delete 没有写入方**（历史遗留 no-op）。
24. `CompensationMessage` 动作注释缺 CLOSE_ORDER；OrderCloseJob cron 注释写法与 SQL 不同。
25. 两套 SQL 基线并存（init-all 有 t_aftersale；mysql-order-init 没有；V1 不含 t_aftersale 而 V2 直接 ALTER）。
