## 一、修了什么（5 项 · 编译通过）

| # | BUG | 根因 | 修复 | 涉及文件 |
|---|---|---|---|---|
| 1 | **补偿自循环无退避** | `releaseInventory` / `returnCouponIfUsed` / `closeTimeoutOrder` 失败即"再发一条新补偿消息"且无延时 → 消费者 ACK → 秒级自旋；兜底集合（`reconsumeTimes>=2`）永不触发 | 抽出纯执行体 `do*`（返回 boolean、**不发消息**）；补偿方法（`compensateReleaseStock` / `compensateReturnCoupon` / `compensateCloseOrder`）返回真实成败；消费者失败**抛出** → MQ 原生退避重试 + 兜底集合生效；兜底重放（`OrderCloseJob`）按返回值判定，去除"重放成功"失真 | `OrderService`、`OrderCompensationConsumer`、`OrderCloseJob` |
| 2 | **退款重试可二次退款**（资金级） | `refundByOrder` 无幂等键；退款成功即删"退款中标记" → 部分退款 + 响应丢失时重试无法防重 | `retryRefund` 重发前先核对支付域事实（`findUnclaimedSuccessRefund`：`listRefunds` + 认领匹配），已成功则直接收敛为完成、不再重发 | `AftersaleService` |
| 3 | **取消/支付失败竞态落 500** | `appendEvent` 并发流转抛 `IllegalStateException`，`cancelOrder` / `onPaymentFailed` 未捕获 → 全局兜底记 HTTP 500 + "P0 告警"日志 | `cancelOrder` 转 `BizException(ORDER_STATUS_ERROR)`；`onPaymentFailed` 捕获后幂等返回 | `OrderService` |
| 4 | **`restock_status` 主链路不落标** | 仅恢复任务两处标记，正常完成单恒为 0 → 被恢复任务冗余重放 | `restoreStock` 成功即 `markRestocked` | `AftersaleService` |
| 5 | **confirm 无补偿（问题 4）** | `confirmInventoryDeductSync` 失败仅日志，与 RELEASE 补偿链不对称 → 预扣记录残留 → 已付款订单可被超时释放 | 失败发 `CONFIRM_STOCK` 补偿消息；新增 `compensateConfirmStock`；消费者 / 兜底重放支持新 action；`CompensationMessage` 注释同步 | `OrderService`、`OrderCompensationConsumer`、`OrderCloseJob`、`CompensationMessage` |

（另：本批之前已修 `OrderMapper` 注解错位 P0，见 `00-侦察报告.md` §0。）

**验证方式**：`mvn -o -q -pl my-xhs-order -am compile` 通过（`MVN_EXIT=0`，class 产物已刷新）。环境不允许启动，未做运行级验证——**留待有环境时冒烟**。

## 二、为什么没修剩下的（防"顺手改错"）

| 项 | 分类 | 理由 |
|---|---|---|
| 售后退补口径漏补（`max(a,b)`，08 §6.6） | **真 BUG · 留待设计** | 直觉方案"订单侧传累计目标"在**并发售后**（两张单同时退款中）会导致**多补**（超卖方向，比现状"少补"更危险）。需专门设计：候选 a) 订单侧传"已完成+本次"累计 + 库存侧配合；b) 库存侧改增量语义 + 订单侧幂等键；c) restore 加 per-(order,sku) 锁内重算 target。**方案定稿前不动** |
| 归档 Job / 自动确认收货 | 功能缺失（非 BUG） | 属"功能立项"，另立清单（照抄 ReconcileJob / OrderCloseJob 模式） |
| 详情缓存坡脚（9 删 0 写） | 死动作 | 无害；清理项（要么补写端、要么删死动作） |
| 兜底集合 TTL 不对称 | 设计不一致 | consumer 侧 24h TTL 反而有"静默丢失"风险——需统一策略后再改，单独过 |
| `pay/create` 无限流 | 策略加固 | 非缺陷 |

## 三、遗留观察（台账候选）

1. **`onPaymentSuccess` 返回 false 的两种语义**（并发竞态 vs `transient_status_lost`）被 payment 侧统一按 `businessRejected` 处理——存在"补通知重试 → 被判业务拒绝 → 自动退款"的互动疑点（留微服务集成篇分析）；
2. **售后退补并发语义**（见上表第 1 行）——设计题；
3. **补偿链全貌复核**：修 1 后，三张 action（RELEASE/RETURN/CONFIRM）+ CLOSE_ORDER 的失败路径统一为"MQQ 退避重试 → 兜底集合 → Job 每分钟重放"；运行验证时重点观察重试风暴是否消失。
