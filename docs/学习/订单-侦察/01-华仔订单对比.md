# 华仔（ecshop）订单模块对比侦察（01）

> 对象：`/data/workspace/source-code/huazai-ecshop/huazai-order`（分支 `ecshop-chapter-105`，7773 行）；对照：`my-xhs-order`（见 `00-侦察报告.md`，6722 行）。
> 方法：3 路并行深读 + **10 项关键断言亲验**（● = 亲验坐实，○ = 侦察报告结论未逐一亲验）。
> ⚠️ 前提：课程项目按章节演进——**部分缺陷可能是刻意留白/教学素材**，不代表最终形态；本对比只以"当前仓库快照"为准。

## 1. 华仔 order 速览（结构与亮点）

**结构**：controller / service（OrderServiceImpl 1418+、MultiThreadOrderServiceImpl）/ 自研**状态机**（Squirrel 底座 + 封装）/ **校验责任链**（user→skus→stock→coupon）/ MQ（事务消息 + 路由分发器 + 延时关单 + 确认聚合 + ES 同步）/ Feign（inventory/coupon/product/user）/ ShardingSphere（2 库、自定义复合分片算法）/ 快照 / XXL-Job。

**值得借鉴的设计（骨架层面）**：
1. **确认聚合**：下单后由 cart/coupon 各自回发确认消息，`LOCK_COUPON + CART_CLEAR` 双成功才把订单 CREATED→CONFIRM（"最终确认"思路，少见）；
2. **事务消息路由分发器**：按 `businessType` 分发本地事务（order_create / order_cancel），可扩展；
3. **orderId 内嵌路由信息**：`2位业务码+13位序列+4位分表号`，无分片键时可从 orderId 反解分片（与 xhs 的映射表互为两种解法）；
4. **复合分片算法**：`buyer_id` 优先、缺失时从 orderId 末 4 位提取（自定义 `ComplexHashMod`）；
5. **校验责任链**（可插拔节点）与 **状态机图**（13 状态 11 事件，枚举化注册）。

## 3. 与 xhs-order 对比表

| 维度 | 华仔 order | xhs order（我方） | 判定 |
|---|---|---|---|
| 服务拆分 / 网关 | 多服务 + Nacos + 网关（**网关无鉴权过滤器**） | 多服务 + Nacos + 网关（JWT 强制 + 覆盖注入 X-User-Id + 内部/管理 token fail-closed） | **xhs** |
| 数据层 | ShardingSphere 2 库；**16/32/32 三方不一致**；自定义复合分片算法（设计感强） | ShardingSphere 4×4；hash 变形（注释漂移）；映射表兜底非分片键 | 平（双方各有硬伤） |
| 订单号/路由 | 雪花 + 业务码 + **分表号内嵌 orderId**（无映射表） | 时间戳 + 日序列 + **映射表**（RepairJob 兜底） | 平 |
| 事务消息 | 有（路由分发器），但**取消回查恒回滚**、UNKNOWN 当失败抛错 | 事务消息 + **本地消息表双角色**（回查凭据 + Outbox 补发/退避/死信/清理） | **xhs** |
| 幂等 | SETNX 120s（msgId）+ Guava 本地聚合（多实例失效、判断反） | msgId 24h + 版本门（eventTime）+ Lua 业务幂等 + 乐观锁 | **xhs** |
| 状态流转 | Squirrel 状态机（图全，**实际装饰化**） | 事件溯源（不可变事件表 + 乐观锁 + 快照 + 校准 Job） | **xhs**（华仔设计意图好、落地空） |
| 补偿 / 兜底 | 超时 XXL 只关单；回滚被注释；无兜底集合 | RELEASE 完整补偿链 + 本地兜底集合重放（有自循环缺陷，问题 5） | **xhs** |
| 核心业务规则 | **金额不乘件数 / 退券状态错配 / 回补只 1 件 / 延时 3min** | 预扣/确认/释放/回补链路完整、金额/数量口径基本正确（退补口径有漏补缺陷） | **xhs** |
| 工程完成度 | 大量 TODO / 注释掉 / 桩实现 / 死代码 | 链路完整 + 事故修复沉淀（T-xxx、RV31、P1-1）+ 台账/审查文化 | **xhs** |
| 安全 | MCP 免登录越权、回调无签名 | 内部调用 token（fail-closed）+ 管理接口校验 + 限流（pay/create 缺限流） | **xhs** |

## 4. 结论：谁更贴近生产环境

**总体：xhs-order 明显更贴近生产环境**，但两句话都要说全：

1. **xhs 更近的原因**：不是"设计更花哨"，而是 **"接通率 + 正确性闭环 + 安全基线"**——链路是真的接通的（消息有回查凭据、发送有兜底、失败有补偿/对账）、关键账务口径基本正确、网关/内部调用有鉴权、每次事故都有修复沉淀（T-xxx 编号）。这正是"生产系统被事故打磨"的形态。
2. **华仔的价值不在完成度，而在"教学骨架"**：确认聚合（双服务确认后置 CONFIRM）、状态机图枚举化、责任链、orderId 内嵌路由，这些设计值得抄思路；但它的**大量实现停在设计意图**（状态机空转、回滚注释、桩实现），并且有几个**基础业务规则错误**（金额不乘件数、退券状态错配）——如果这些不是课程刻意留白，就是"骨架全、血肉空"的典型。
3. **也要公允**：xhs 自己也有 P0（本次已修的注解错位）和 P1（补偿自循环、confirm 无补偿、退补口径漏补）——两家都达不到"可上线"标准，只是**xhs 离"能跑通且不犯低级账务错"更近**。

**一句话口径**：*华仔是"设计模式教材"，xhs 是"粗糙但真的在运行的系统"。论贴近生产，xhs 赢在完成度和纵深；论可借鉴的架构手法，华仔有几个点值得吸收。*
