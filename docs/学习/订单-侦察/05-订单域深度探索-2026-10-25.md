> **方法**：domain-discovery 9 步（入口 → 执行流 → 侧扫 → 设计决策 → 三信号分类 → 依赖 → 拓扑 → 输出 → 基线校验）。

## 0. 一页结论

1. **三层模型已落地**：`t_order`（父/交易）→ `t_sub_order`（子/商家/履约）→ `t_order_item`（行/SKU/金额），不再是 00/09/12 里写的"单层订单、拆单未做"。
2. **分摊已落库**：`OrderItem.discountShare` 在下单本地事务内用最大余数法写入；`Aftersale` 直接按落库分摊计算应退，不再只是"售后重算、不落库"。
3. **履约/售后已下沉到子单/行**：发货/确认按 `subOrderNo`，售后锚点是 `itemId`，唯一键 `(item_id,type)`；旧 07/08 的"订单级/订单+SKU"口径已过期。
4. **支付已生产化**：当前 `pay.type=remote`，C-002/C-003 做了支付单复用、关单前查渠道、真实通知端点/验签/ACK、同步退款；旧 06 的"mock/模拟器直调/规划"口径已过期。
5. **测试基线已变**：当前 132 个订单测试（旧报告 71），主代码 68 文件/8205 行（旧报告 58/6722）；但仍是 Mockito 单测，没有真实 Redis/MySQL/MQ 集成测试。

## 1. 入口与主链

### 1.1 入口清单

| 入口 | 规模/位置 | 说明 |
|---|---|---|
| HTTP | `OrderController` 18 端点、`AftersaleController` 6、`MappingZoneAdminController` 2（条件装配） | 下单/详情/列表/取消/确认/发货/支付/回调/售后/内部对账 |
| MQ 消费者 | 5 个 | `OrderCloseConsumer` / `PayResultConsumer` / `RefundResultConsumer` / `InventoryFailureConsumer` / `OrderCompensationConsumer` |
| 事务监听器 | 2 个 | `OrderTransactionListener`（下单）、`OrderTerminationListener`（终结） |
| XXL-Job | 6 个 handler | 关单兜底、本地消息补发、死信扫描、映射补录、售后恢复、事件校准 |
| Feign | 5 个客户端 | Product / Inventory / Payment / Coupon / User |
| 数据源 | 6 个逻辑库 | 4 个分片库 + mapping 公共库 + payment 库；zone-aware 可选 |

### 1.2 六条主链（从入口展开）

**A. 下单**（`OrderService.createOrder`）：

```
Controller
→ 幂等键(24h) + 用户锁(10s)
→ Product 批量 SKU（真实价/卖家/图上架校验）
→ 同 SKU 拒绝 + Inventory 前置查库存
→ 金额重算 + Coupon 折扣
→ 事务半消息 ORDER_TRANSACTION_TOPIC
→ OrderTransactionListener → OrderTransactionService 本地事务：
   父单 + 子单(按 seller 拆) + 行(挂子单) + 事件 CREATED + 本地消息
→ 标记本地消息 + 券核销（失败→终结）
→ 30min 延时关单 + 快照 + orderNo→userId 映射
```

**B. 支付收敛**：

```
Payment 通知（Feign/HTTP）或 PAY_RESULT_TOPIC
→ onPaymentSuccess：CAS 0→1 + EVENT_PAID + 全子单 0→1
→ 异步 confirmInventoryDeduct（失败→CONFIRM_STOCK 补偿）
→ 快照 PAID + 缓存失效 + 通知
```

**C. 终结/关单**（五条路径统一入口）：

```
用户取消 / 超时 / 库存失败 / 券失败 / 支付失败
→ terminateOrder
→ 事务半消息 ORDER_TERMINATION_TOPIC
→ OrderTerminationListener → OrderTerminationService 本地事务：
   EVENT_*_CANCELLED(0→4) + 全子单 0→4 + 终结事件本地消息
→ 库存/券/通知/购物车订阅方异步消费
```

**D. 履约**：

```
deliverOrder(subOrderNo)：子单 CAS 1→2（发货）
confirmReceive(subOrderNo)：子单 CAS 2→3（确认）
→ SubOrderService.recomputeParentStatus：父单 = 子单状态聚合（1→2 / 1|2→3）
```

**E. 售后**：

```
apply：行级权益快照（落库分摊）→ 单品/订单双上限 → unique(item_id,type)
→ audit：复核 → 0→3(REFUNDING)
→ executeRefund：payment.refundByOrder（出金幂等键=售后单号）
→ 成功：3→4 + restoreStock(按 applyQuantity，库存累计目标幂等)
→ 失败：3→6 + 10min 恢复任务/最多 3 次
```

**F. 查询/索引**：

```
买家：userId(orderId)→分片路由；orderNo→mapping→userId→分片
商家：sellerId→ES seller_sub_order_index
      （Canal order_instance → SUB_ORDER_INDEX_TOPIC → search 消费者）
```

## 5. 当前代码的风险/观察（探索阶段，不急着改）

| 级别 | 观察 | 证据/影响 |
|---|---|---|
| **P1** | 售后退补 `max(a,b)` 漏补（跨模块旧账） | `AftersaleService.restoreStock` 传本次 `applyQuantity`，库存按累计目标解析；同 SKU 两次售后可能累计少补（`订单-侦察/00 §9.1`） |
| **P2** | `onRefundSuccess` 的 confirm 失败不阻断回补 | `OrderService.onRefundSuccess` 忽略 `confirmInventoryDeductSync` 返回值；极端窗口库存虚增（R-4，对账兜底） |
| **P2** | 自动校准并非纯 dry-run | `OrderCalibrationJob` javadoc 写"只报告不覆盖"，实际先 `recomputeParentStatus` 前向收敛父单；注释/行为漂移 |
| **P2** | 售后行级注释漂移 | `Aftersale` 类注释仍写"同订单同 SKU 同类型"，实际唯一键 `(item_id,type)`；`apply` 仍按 skuId 找行 |
| **P2** | 终结入口注释写"四条路径" | `terminateOrder` javadoc 四条，实际五条（含 `PAY_FAILED`） |
| **P2** | 132 测试全是 Mockito/Standalone MockMvc | 无真实 Redis/MySQL/MQ/支付渠道集成；关键竞态只能靠静态推理 |
| **P3** | `pay.type=remote` 下 `MockPayService` 仍在 | 条件装配的备用路径；读代码容易被"mock 主路径"误导 |
| **P3** | `OrderService` 1799 行 | 下单/支付/终结/查询/补偿集中；工程可维护性一般 |
| **P3** | `t_aftersale` 在公共库不分片 | 售后量级小是当前取舍；规模化后需按 user_id 分片 |
| **P3** | 商家查询跨 order/search | 子单索引经 Canal→MQ→ES；运维/延迟/回填复杂度是 D9 的代价 |
