# 订单模块讲解系列 · 11 · 对账

> **定位**：可靠性体系的最后一环——**补偿修"已知的漏"，对账发现"未知的漏"**。多边账目日终对齐（订单↔支付↔库存↔渠道），差异挂账、人工核销。

## 一、先看"对账"在干什么（例子先行）

场景：用户付了 499，但订单还是"待付款"——支付成功了（钱在平台账上），订单没动（通知丢了：Broker 宕机 / 消费重试耗尽 / 网络分区）。

谁会发现问题？

- 用户不一定注意（他可能以为付款失败）；
- **补偿先兜**：`PaymentNotifyCompensateJob` 每 2 分钟扫一遍"支付成功且超过 5 分钟"的单，发现订单还没动 → 重发通知；重试最多 10 次，超限告警人工——**但补偿有上限、有假设**（补偿任务自己得活着、重试不能耗尽）；
- **对账兜所有剩余**：`PaymentReconcileJob` 每天凌晨全量扫一遍（游标分页），发现不一致 → 补通知——**它不假设前面任何一环成功**（包括补偿本身）。

**一句话**：补偿是"修已知的漏"（针对**已知的失败模式**重做动作——通知会丢，就重发）；**对账是"发现未知的漏"**（不预设失败模式，全量核对最终结果）——它是兜底体系的**最后一道**。

## 二、对什么账（多边）

应然（00 §2.5 的 8 本账）：用户账 / 行级分摊账 / 店铺账 / 平台账 / 支付账 / 库存账 / 结算账 / 物流账。按性质归三类：

| 类型 | 对什么 | 例子 |
|---|---|---|
| **状态账**（信息流） | 同一笔业务在各域的状态一致 | 支付成功 vs 订单已付款；售后完成 vs 退款单成功 |
| **资金账** | 钱的收 / 退 / 结一致 | 支付流水 vs 渠道流水 vs 结算账单 |
| **库存账** | 货的扣 / 回补一致 | Redis 总库存 vs MySQL 可用库存 |

**双边对账**（两方流水逐笔比）是基础；**多边对账**（三方以上：订单↔支付↔库存）靠**共同锚点**（订单号 / 支付单号 / 退款单号）把各域串起来——锚点不统一，账对不上。

## 三、实然：xhs 的对账设施（三个域各有一块）

### 3.1 库存域：L3 对账（L1/L2/L3 分层的最后一层）

- L1：Redis Lua 原子扣减（权威实时源）；L2：MQ 异步落 MySQL；**L3：`InventoryReconcileJob` 每天凌晨 3 点，Redis total vs MySQL available_stock，以 Redis 为准修复 MySQL**；
- 边界自述：若对账时有 L2 消息积压，修复后积压消息再消费可能多扣一次——"概率极低，**下一次对账会再次修复**"（对账是**周期性收敛**，不是一次性动作）。

### 3.2 支付域：两条线

**① "补偿 + 对账"双保险**（机制高度相似：扫 `t_payment` status=1 → `pay-amount` 探针 → 补通知；差异在意图与边界）：

- **准实时补偿**（`PaymentNotifyCompensateJob`，每 2 分钟）：扫"支付成功且超 5 分钟"的单 → 仍待付款 → 重发通知；**重试上限 10 次**（Redis 计数），超限告警人工；成功后置 1 小时防重标记；
- **日终对账**（`PaymentReconcileJob` → `PaymentService.reconcile()`，建议凌晨 3 点）：**全量**游标扫描（批 200 防 OOM）→ 补通知——兜住补偿放弃/漏掉的；Redis SETNX 锁防并发重跑。

**② 结算域**（`SettlementService`，xhs 最完整的一块对账）：

- **日切账单**：每日 02:00 生成 T-1 全渠道账单——收款 − 退款 = 净额，净额 × 费率 = 手续费，应结算；
- **三方对账**：每日 03:00 渠道对账文件 → `t_channel_flow` → 与我方支付/退款流水**逐笔比对** → 三类差异：**本地有渠道无 / 渠道有本地无 / 金额不一致**；
- **差异挂账**：差异单独记台账，**不混入本期应结算金额**——账单金额始终是我方记账口径，差异由人工核销。

### 3.3 订单域：事件流校准（dry-run）

- `OrderCalibrationJob` 每日扫描（窗口 = 创建于 **2~8 天前**，避开在途单）→ 事件流回放 vs 当前状态 → 分叉只告警 + 打指标；
- **修复走人工端点**——"方向保护：**终态差异绝不自动覆盖**"。

### 3.4 缺口（已知，02 文档 Tier 2）

**订单↔支付↔库存的三方独立账务对账体系不存在**——现有的是各域内部对账 + 支付→订单的单向核对。真实系统的形态：日终对账（各方出明细/汇总）→ **差错池** → 人工/自动调账。

## 四、对账的工程要素（从 SettlementService 提炼）

1. **幂等重跑**：账单唯一键 `(bill_date, channel)`；重跑需 `force`；`run_no` 记录次数——对账任务**重跑是常态**；
2. **人工优先**：已人工处理的差异不被自动覆盖；本轮"消失的差异"自动收敛为"已忽略"；
3. **差异分类处置**：三类差异 → 挂账台账（不混入结算）→ 人工核销；
4. **比对口径**：匹配键 = `(业务类型, 商户单号)`——因此要求渠道对账单**回传我们下发的单号**（out_trade_no 语义）；
5. **并发控制**：按 `(日期, 渠道)` Redis SETNX 串行；单渠道失败不影响其他渠道；
6. **扫描工程**：游标分页（防 OOM）、时间窗（避开在途）、分片广播（无分片键时）、XXL-Job 单执行器。

## 五、深水

- **对账逻辑必须有调度入口（死代码教训）**：`reconcile()` 的真实故事——对账逻辑写好了，但**没有任何调度入口**（无 @XxlJob/@Scheduled/调用）→ "每天凌晨对账"的注释从未成立，对账从不执行；后来补上 XXL-Job 入口才真正活过来。**写了不跑 = 没有**；
- **瞬态 ≠ 结论**（扫描型任务的返回分类）："订单不可达/500"是**瞬态**（继续重试）；"订单不存在/已收敛"才是**确定性结论**（清计数收尾）——原实现把瞬态当结论清计数 → 永久漏补偿（已修）。**扫描型任务必须把"查不到"和"查到了没有"分开**；
- **方向性：宁可不修不可错修**——修复要么"以权威源为准"（库存以 Redis），要么"重放收敛"（支付补通知）；**终态差异绝不自动覆盖**（订单校准 dry-run）——错修 = 二次资损；
- **对账的边界**：扫描窗口要避开在途单（2~8 天前）；"对账时点在途的消息"是已知边界（库存 L3 注释自述，靠下一轮收敛）；
- **对账的"对账"**：对账结果本身要可观测（指标 + 告警 + 人工台账）——否则"差异发现了没人看" = 白对；
- **锚点统一**：多边对账的前提是单号体系（订单号 / 支付单号 / 退款单号）全链路贯穿（关联 06/09 的编号设计）。

## 掌握标准 + 背走一句

1. 对账 = 最后一道防线：**补偿修已知的漏，对账发现未知的漏**；
2. 对三类账：状态账（信息流）/ 资金账 / 库存账；多边对账靠**统一锚点**串；
3. xhs 实况：库存 L3（以 Redis 为准）/ 支付对账（补通知）/ 结算域（日切 + 三方对账 + 差异挂账）/ 订单校准（dry-run）——**三方账务体系是缺口**；
4. 工程要素：幂等重跑 / 差异挂账 / 人工优先 / 比对口径（商户单号）/ 扫描窗口；
5. 两条铁律：**对账逻辑必须接调度**（死代码教训）；**宁可不修不可错修**（终态差异绝不自动覆盖）。

> **补偿是"修已知的漏"，对账是"发现未知的漏"——它是所有防线都漏了之后的最后一道；对账的三条铁律：幂等重跑、差异挂账、宁可不修不可错修。**
