# 订单模块讲解系列 · 02 · 价格重算与快照

> **定位**：下单时"钱"从哪来——为什么服务端必须重算、快照固化什么。

## 一、场景一句话

用户在结算页看到"实付 496"——提交时，系统**不会用页面上的 496**，它要自己重新算一遍，并把"下单这一刻的账"**存下来**。

## 二、为什么不让"页面上的金额"说了算

页面上的数字是**展示品**：

- 可能被抓包改掉（496 改成 1）；
- 可能过期（你看页面的这几分钟里，券被别人用掉了 / 商品调价了 / 活动结束了）。

所以下单时，服务端必须**自己重算**：真实价格 × 数量 − 真实券折扣。

## 三、实然：xhs 的做法——最干净的一招：金额根本不让你传

下单接口收的字段（`OrderCreateRequest`）：

```java
List<SkuItem> skuItems;   // 买什么：skuId + 数量
Long couponId;            // 用哪张券（可选）
Long addressId;           // 寄哪里
String bizIdentifier;     // 01 篇讲的防重号
```

**没有金额字段。**客户端只能表达"买什么、几件、用哪张券、寄哪里"——钱，它一个字都插不上嘴。

这比"前端传金额 + 后端校验"高明的地方：**最好的防篡改，是设计上就不给篡改的机会。**

服务端自己算三个数（OrderService.java）：

- `totalAmount`（L1200 `calculateTotalAmount`）：商品价 × 数量；
- `discountAmount`（L1214 `calculateCouponDiscount`）：调券服务**试算**；
- `payAmount`（L199-206）= 两者相减，且不允许为负。

细节先记一句：券在这里只是"试算"，真正的"核销"发生在下单成功后——核销失败就把订单取消（到讲券的时候再抠）。

## 四、算完了，为什么还要"快照"

因为**价格会变，但订单的账不能再变**：今天买是 496，明天商品调价了，这张订单还得是 496；以后退款也要按 496 往回算。

快照 = 把"下单这一刻的价格/商品/地址"整包固化。三拨用户：**订单详情展示、退款算钱、纠纷举证**。

xhs 的实现不是"下单存一次"，而是**每个状态点存一版**（`takeSnapshot` L1144；事件：创建/支付/发货/完成/取消/超时取消/库存失败取消/退款）——任何一个时间点的账都查得到。

## 五、先知道就行的坑

xhs 只算了"整单"的折扣，**没把优惠摊到每个商品行**（满 100 减 20，每个商品各摊几块？没有）。将来退款"按行算钱"就没有地基——留到"退款/售后"篇讲。

## 六、掌握标准 + 背走一句

1. 金额必须服务端算——**最干净的设计是接口根本不收金额**；
2. 算完必须**固化**（快照）——管"以后"的三件事：展示、退款、举证；
3. 记住缺口：**分摊没落库**（xhs 的已知坑）。

> **前端金额只配展示，服务端重算才是账；重算管当下，快照管以后。**
