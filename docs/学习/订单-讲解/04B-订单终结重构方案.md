## 一、现状问题清单（均有代码实证）

| # | 问题 | 说明 |
|---|---|---|
| 1 | **语义错配** | 四种终结原因（用户取消/超时/库存失败/券失败）共用一条 `cancelOrder`；券失败被记为"用户主动取消"（原因硬编码），并向用户发送"订单已取消"的误导通知 |
| 2 | **事前失败走事后补偿** | 券核销失败发生在本单副作用可能尚未发生时，却调用"针对已成立订单"的取消流程（释放/退券多为空操作）——动作顺序颠倒 |
| 3 | **best-effort 吞失败** | 取消流程内释放库存与退券并行执行、总超时 3 秒，失败仅降级日志——副作用完成度不可观测 |
| 4 | **职责过重** | 单个方法承担六个职责（状态迁移/释放/退券/快照/删缓存/通知），多场景复用，演进困难 |
| 5 | **副作用与请求线程耦合** | 补偿动作挂在同步调用链上，与响应时间互相绑架 |
| 6 | **库存乱序占用** | "释放先到、预扣后到"时，释放空操作、迟到预扣生效，热点 SKU 被多锁约 30 分钟 |
| 7 | **演进痕迹** | "取消不发通知"等行为是后补的，路径间语义不一致 |

## 二、重构目标与原则

**原则：**

1. **终结 = 状态迁移（本地事务）+ 终结事件**；副作用（释放库存/退券/通知/指标）由事件消费方统一执行；
2. **一种终结原因 = 一种事件 + 一种通知语义**（不再复用"用户取消"）；
3. **所有副作用幂等、可重试、可观测**；补偿不自循环；
4. **乱序由自愈机制消解**（库存墓碑），不试图控制时序；
5. **可灰度、可回滚**（新旧路径并存过渡）。

**可验收目标：**

- 四种终结原因的事件与通知语义正确；
- 终结接口响应时间不包含任何外部服务调用；
- 乱序场景（释放先到）库存零占用；
- 终结链路全步骤有指标（事件量/原因分布/副作用成功率/补偿延迟/死信量）。

## 三、目标模型

### 3.1 领域模型

- **终结原因枚举**：`USER_CANCELLED` / `TIMEOUT` / `INVENTORY_FAILED` / `COUPON_FAILED`（可扩展）；
- **终结事件**（OrderTerminationEvent）：`orderId / orderNo / userId / reason / occurredAt / traceId`。

### 3.2 统一入口：`terminateOrder(orderId, reason)`（同步部分，仅本地动作）

```
terminateOrder(orderId, reason)
  ① 条件更新状态（CAS：仅非终态可终结；事件白名单校验）
  ② 拍快照（终结时刻）
  ③ 写"终结事件"（Outbox / 事务消息——可靠投递）
  → 返回（终结受理成功）
```

**不变量（二次 Review S2）**：**"状态迁移"与"终结事件写入"必须在同一个本地事务内**（沿用创建侧的"事务消息 + 本地事务回调（context 模式）"，或 Outbox 同事务写）——否则存在"状态已迁移、事件未发出"的缝隙（等价于 03 落库要解决的问题）。

### 3.3 副作用的执行模式：领域事件 + 各域订阅（编舞，非编排）

**Review 修正（R1）**：终结事件发布到 `ORDER_TERMINATION_TOPIC`，由**各领域服务各自订阅、处理本域副作用**（利用 MQ"组间广播"模型），而不是由一个中心消费者逐个调用其他服务（编排）：

```
terminateOrder 发布终结事件（携带 reason）
   ├─ 库存服务订阅：**总是写"已终结"墓碑** + 有预扣记录则释放（原子：检查与墓碑写入一步完成，见 §3.5）
   ├─ 券服务订阅：退还优惠券（幂等：未核销则不动）
   └─ 通知服务订阅：按 reason 选择文案发送（消费端双层去重）
各消费者：失败 → 重试（限次 + 退避）→ 死信 → 重放/人工
```

优点：终结链路无 Feign 调用（各域自洽）；与创建侧对称（创建事件也是各域订阅：库存订阅做预扣）；避免"中心编排消费者"成为新的职责黑洞与单点。

### 3.4 各终结路径接入方式

| 路径 | 触发者 | 调用 |
|---|---|---|
| 用户取消 | 用户 API | `terminateOrder(orderId, USER_CANCELLED)` |
| 超时 | 延时消息 / 兜底扫描 | `terminateOrder(orderId, TIMEOUT)` |
| 库存失败 | 库存失败事件收口 | `terminateOrder(orderId, INVENTORY_FAILED)` |
| 券失败 | 下单流程核销失败 | `terminateOrder(orderId, COUPON_FAILED)` |

### 3.5 库存侧配合：墓碑机制（库存域自洽）

**Review 修正（R2 + 二次 Review S1）**：

- 库存服务订阅终结事件，处理规则为"**总是写墓碑 + 有记录则释放**"：
  - **原子操作**（Lua）：检查预扣记录是否存在 + **无条件写入墓碑**（TTL ≥ 消息可能到达的最晚时间），返回"是否存在记录"；
  - 存在记录 → 继续逐 SKU 释放（释放动作本身幂等）；
  - **为什么必须"总是写"**：① 若只在"无记录"时写，则"释放删除记录之后"，迟到的创建消息重投（超出 msgId 去重窗口，如 DLQ 重放）会**再次预扣**（预扣的幂等依据随记录被删而失效）；② "检查 → 分支写入"之间存在竞态窗口（检查到"无记录"的瞬间预扣刚好落盘 → 墓碑与记录并存 → 无人立即释放，退回 30 分钟占用）——"原子化 + 总是写"同时消除这两个问题；
- 预扣 Lua **原子检查墓碑**：命中 → 跳过（不占库存）；
- 双层防线定位：**墓碑是主要防线**（消除乱序与重投占用）；**预扣超时释放是兜底防线**（覆盖墓碑 TTL 之外的极端迟到）；对账为最终兜底；
- 效果：消除"释放先到、预扣后到"的 30 分钟占用，并封住"终结后重投再预扣"的漏洞。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 过渡期重复副作用 | 所有副作用幂等（释放空操作、退券乐观锁、通知幂等键 orderId+reason） |
| 终结事件积压 | 监控事件堆积量；死信 + 人工处置通道 |
| 状态迁移竞态 | 保留条件更新（CAS）+ 状态机白名单 |
| 迁移期新旧通知重复 | 通知幂等（orderId + reason 去重） |
| 墓碑 TTL 设计错误 | TTL ≥ 消息最大迟到时间（含消费重试窗口）；监控墓碑命中率与库存占用时长 |
| 回滚 | 每阶段独立开关；阶段 2/3 支持"双跑对比"（新事件路径 + 旧逻辑，幂等兜底） |

## 七、验收标准（可度量）

1. 四种终结原因的事件/通知语义正确（抽查事件表 + 通知文案）；
2. 终结接口响应时间不含任何外部调用；
3. 乱序场景（释放先到、预扣后到）：库存零占用（墓碑命中）；
4. 补偿成功率、补偿延迟、死信量可观测且有处置路径；
5. 灰度对比期无重复副作用（幂等校验通过）；
6. **不变量校验**：状态迁移与终结事件写入同事务（故障注入验证无"已迁移未发事件"）；
7. **不变量校验**：终结处理"总是写墓碑"（含"有记录已释放"路径）；终结后重投的创建消息不再产生库存占用；
8. **不变量校验**："检查 + 写墓碑"为原子操作（并发注入下无"记录与墓碑并存且未释放"）。

| # | 发现 | 处置 |
|---|---|---|
| R1 | 副作用执行模式未定义：原为"中心消费者逐个调其他服务"（编排）→ 职责黑洞与单点 | **改为领域事件 + 各域订阅（编舞）**（已并入 §3.3） |

## 十、实现记录（2026-10-14）

### 10.2 关键实现决策（方案细化/偏差）

1. **投递形态 = 事务消息 + 本地消息表兜底**（v1 的 Outbox-only 已在 §十一 C1 修正为与创建侧同构；为什么必须独立模板见 10.1）。
2. **消费者幂等键 = 消息 KEYS（=orderNo）优先、msgId 兜底**。理由：补发/重投会生成新 msgId，仅 msgId 去重对"COMMIT 丢失 / 标记失败 / 补发重投"无效；orderNo 跨重投稳定。各域内在幂等（墓碑 / 退券乐观锁 / 聚合窗口锁）仍为最终防线。
3. **通知文案在通知域按 reason 映射**（§3.3"按 reason 选择文案"）；终结路径不再经 `OrderNotificationPublisher`（取消/库存失败路径的 publishStatusChanged 调用已随路径改写移除；该发布器仍服务于支付/发货/退款等其他状态通知，未动）。
4. **券失败路径用宽容版** `terminateOrderQuietly`：终结异常不改变"下单失败"响应（原实现第一处为硬调用，取消异常会顶替券失败异常返回给用户）；订单保持待付款时由超时关单兜底。
5. **兼容保留**：旧补偿链路（`sendCompensationMessage` + `releaseInventory`/`returnCouponIfUsed` 纯执行体 + 补偿消费者）**未删除**——过渡期 in-flight 补偿消息与兜底重放仍可用；按 §五 阶段 4/5 在双跑观察后移除。
6. **库存失败事件载荷瘦身**：新终结事件不再携带 `skuId/reason` 明细（原 ORDER_INVENTORY_FAILED_CANCELLED 载荷字段）——失败明细已由库存侧日志 + 指标记录，订单侧事件只承担"终结事实 + 归因（reason/source）"。

## 十一、实现深度 Review（2026-10-14，针对 v1 实现）

> 背景：用户 review 质疑 v1 "投递形态复用既有基础设施（Outbox-only）、省掉事务消息机制"是走捷径。逐项审查后确认质疑成立，并连带发现一个严重回查缺陷。以下为完整 findings 与处置（全部已修复并验证）。

| # | 级别 | 问题 | 处置 |
|---|---|---|---|
| C1 | 严重 | **投递形态偏离目标模型**：方案 §四 明确"事务消息 + 本地消息表兜底【R3】"，创建侧已是该形态；v1 为省掉独立事务生产者/模板/监听器/回查机制，只做"本地事务 + 提交后 syncSend + 补发 Job"。后果：① 与创建侧不对称（同系统两套投递机制，理解/运维成本翻倍）；② 恢复路径弱化（创建侧靠 broker 回查分钟级自动收敛；终结侧仅靠补发 Job 扫描周期）；③ 请求线程多一次 3s 同步发送阻塞。 | **已补全**：独立生产者组 + 独立模板 + `OrderTerminationListener`（executeLocalTransaction/checkLocalTransaction）+ 本地消息表兜底，与创建侧完全同构。约束依据：rocketmq-spring 2.3.0 一个模板只能挂一个 `@RocketMQTransactionListener`（重复绑定启动即抛异常，字节码实证）。**连带修正**：事务消息体在半消息发送时定型 → 事件载荷从"事务内生成"前移为"terminateOrder 预读构建"（与本地消息表 payload 同源）。 |
