## 一、总图：一条主链 + 两个终态 + 旁路 + 贯穿机制

```
主链:  0 待付款 ──支付──→ 1 已付款 ──发货──→ 2 已发货 ──确认──→ 3 已完成
终态:  4 已取消（5 条终结路径：用户/超时/库存失败/券失败/支付失败）
       5 已退款（全退收敛：1/3 进；status=2 待收口——08 §5.2）
旁路:  售后（独立聚合，挂"订单+SKU"；全退时与订单咬合）——08
       拆单（未做：父/子/行三层）——09 + 改造方案
       分摊（钱的地基：行级实付 = 明细金额 − 分摊）——10
贯穿:  事件流 · 快照 · 乐观锁/条件更新 · 事务消息/本地消息表 · 补偿 · 对账
```

| 环节 | 机制 | 篇 |

| 支付 | 双通道投递 + CAS 幂等 + **业务拒绝（false）** | 06 / 04A |
| 关单 | 双通道关单 + 条件更新 + 竞态收口 | 04 / 04A |
| 履约 | 状态守卫（人推：发货/确认） | 07 |
| 售后 | 独立聚合 + 三道闸门 + 恢复任务 | 08 |
| 钱 | 分摊（最大余数法）+ 守恒律 | 10 |
| 货 | 预占三态 + Lua 原子 + 累计幂等回补 | 03B / 《库存-讲解》 |
| 兜底 | 补偿（已知漏）+ 对账（未知漏） | 11 |

## 三、可靠性机制对照（应然 vs 实然）

| 机制 | 真实电商怎么做 | xhs 怎么做 | 差距 |
|---|---|---|---|
| 幂等 | 业务幂等号 + 去重表/唯一键 | 幂等号 + 用户锁 + CAS + 消息 KEYS | 同 |
| 状态机 + 锁 | 状态机引擎 + 条件更新 | `appendEvent` 白名单 + 乐观锁 | 同（轻量实现） |
| 事务消息 / 本地消息表 | 同 | 同（下单 + 终结两条链） | 同 |
| 补偿 | 定时扫描 + 重试上限 + 告警 | 通知补偿 / 恢复任务 / 补偿消费 | 同 |
| 对账 | 日终三方对账 + **差错池** + 人工调账 | 库存 L3 / 支付对账 / 结算域三方对账 | 缺"订单↔支付↔库存"三方体系 |
| 限流削峰 | 网关令牌桶 + **排队** + 异步建单 + 库存预热 | 网关限流 + @RateLimit + Sentinel + 异步建单 | 缺排队/削峰 |
| 事件流 / 快照 | 大厂同 | `t_order_event` + 状态快照（每类状态事件一版：主链/退款 5 + 终结 5 = 10 种） | 同（快照触发粒度不同） |

## 四、面试口径总纲（把整个订单系统讲成一个故事）

1. **开场一句话**："订单系统 = 一条状态主链 + 可靠性内核；我把'难而对'的做在可靠性上（幂等/竞态/补偿/对账），把'外围业务对象'（店铺/拆单/运费）做了显式取舍。"
2. **主链讲法**：0→1→2→3 + 两个终态（4/5）+ 五条终结路径 + 售后独立聚合（挂行/挂订单+SKU）。
3. **深水三选一**（看面试官兴趣）：关单竞态（**false 是业务拒绝，不是报错**）/ 退款防重（**超时 ≠ 失败，先查事实**）/ 分摊（最大余数法 + 守恒律）。
4. **缺口要会讲**：拆单 / 分摊落库 / 三方对账 / 自动确认收货——"我知道该怎么做"（指向改造方案）+ 为什么现在不做（定位取舍，不是能力缺失）。
5. **收尾口径**（00 §1.4）："我们'缺'的，都在**外围业务对象**；'难而对'的，都在**可靠性内核**。"
