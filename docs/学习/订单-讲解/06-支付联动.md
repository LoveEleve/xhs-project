## 一、先看"付款"这一跳（订单视角）

例子：小明在订单详情页点"去支付"（订单 status=0 待付款）。整条链有四个域，但**订单只关心四件事**——把支付发出去、把结果收回来、给支付提供回查、把钱到账告诉下游：

```
① 发出：订单域 ──【Feign】──→ 支付域              （发起支付）
② 渠道：支付域 ←── 支付渠道（异步回调）            （订单不参与）
③ 接收：支付域 ──【Feign 主通道 + MQ 兜底】──→ 订单域（收敛订单状态）
④ 联动：订单域 ──【Feign】──→ 库存域              （预扣转正）
```

支付域还会**反向调订单**两个回查契约（订单提供）：`GET /api/order/status`（这单还允许支付吗）和 `GET /api/order/pay-amount`（金额权威 + "订单是否还未收敛"的探针）。

**交互面全景**（本篇主线就是这张表）：

| 方向 | 接口 | 谁调谁 | 订单侧角色 |
|---|---|---|---|
| 出 | `POST /api/payment/pay` | 订单 → 支付 | 发起支付 |
| 入 | `POST /api/order/pay-success` / `pay-fail` | 支付 → 订单 | 收敛状态（主通道） |
| 入 | `PAY_RESULT_TOPIC` | 支付 → MQ → 订单 | 收敛状态（兜底通道） |
| 契约 | `GET /api/order/status`、`pay-amount` | 支付 → 订单 | 提供回查（内部调用） |
| 出 | `POST /api/inventory/confirm` | 订单 → 库存 | 下游联动（第 ④ 跳） |
| 出 | `POST /api/payment/refund-by-order` | 订单 → 支付 | 退款发起（售后链路，见 08） |

（两种支付模式：`pay.type=remote`（生产）走独立支付服务；`pay.type=mock`（本地开发）订单域内 MockPayService 自闭环——同一入口、两种实现。）

## 二、应然：订单侧要解决的三个问题

| # | 问题 | 本质 | 对策 |
|---|---|---|---|
| 1 | 把支付发出去 | 金额可信 + 不重复扣 | 金额以订单为权威；防重复交给支付域（订单不重复造） |
| 2 | 把结果收回来 | **不可靠是常态**：丢失 / 重复 / 迟到 | 双通道投递 + 幂等收敛（CAS） |
| 3 | 把边界说清楚 | 竞态（钱收了单不收）怎么办 | 返回"业务拒绝"（false）→ 支付侧退款；临时故障才是异常 |

## 三、实然：订单侧怎么接（项目落地）

### 3.1 发起支付（出）

- 入口：`OrderController#createPayment`（`/pay/create`）——`remote` 分支取订单实付金额（权威值）→ `paymentFeignClient.pay`；
- 金额权威：支付侧会回查 `pay-amount` 比对，不一致直接拒付；
- 防重复：支付域内部四道防线（Redisson 锁 + 锁后双重检查 + 支付中标记 + 支付单乐观锁）——订单侧不重复造轮子；
- mock 模式：`MockPayService` 本地模拟（payType=2 可模拟失败），失败直接调 `onPaymentFailed`。

### 3.2 接收结果（入）：两条通道，一个收敛函数

| 通道 | 载体 | 何时走 | 订单侧入口 |
|---|---|---|---|
| 主通道 | Feign | 每次支付结果 | `OrderController#notifyPaySuccess` / `notifyPayFail` |
| 兜底通道 | MQ `PAY_RESULT_TOPIC` | 主通道失败/503 时 | `PayResultConsumer` |

两条通道最终都进**同一个收敛函数**（`onPaymentSuccess` / `onPaymentFailed`）。**为什么必须幂等**：双通道 + 渠道重试 → 同一结果可能到达多次；收敛函数用 CAS（`WHERE status=待付款`）保证"只有一个成功"。

### 3.3 收敛函数 `onPaymentSuccess`：四件事

1. **状态迁移（CAS）**：`appendEvent(EVENT_PAID)` → `updateStatusWithLock`（只有待付款才迁得动）；
2. **竞态口径（P0-6）**：关单/取消先赢 → **返回 false，不抛异常**（详见 §4.3）；
3. **联动库存**：`confirmInventoryDeduct`（第 ④ 跳；异步 + 失败补偿，见 §五）；
4. **收尾**：快照（PAID）/ 缓存失效 / 用户通知（type=5）。

### 3.4 `onPaymentFailed`：支付失败 → 订单终结

- 入口：`/pay-fail`（Feign）或 `PAY_RESULT_TOPIC`（success=false）；
- 动作：**统一终结入口** `terminateOrder(PAY_FAILED)`（04B 收尾收敛的第五条路径）→ 状态 0→4 + 终结事件；释放库存/退券/通知由订阅方执行；
- 幂等：已是终态 → 幂等返回；映射缺失 → 跳过（补录任务/30 分钟关单兜底）。

### 3.5 契约：订单给支付提供的两个回查

- `GET /api/order/status`（P1-1）：支付前回查"只有待付款可支付"——把"对已取消/已支付订单收钱"挡在门外；
- `GET /api/order/pay-amount`：金额权威；同时被支付侧补偿 Job 当作"订单是否还未收敛"的探针（**返回非空 = 订单仍待付款 = 没收敛**）；
- 两个都是内部接口（`X-Internal-Call` 校验）。

## 四、深水细节：竞态与幂等

### 4.1 重复到达 → CAS 幂等

双通道 + 渠道重试 → 同一结果多次到 → CAS 第二次拿 0 行 → 幂等返回（不会重复加库存/重复通知）。

### 4.2 支付 vs 关单撞车（04A 的实况对照）

| 谁先赢 | 结果 | 订单侧动作 |
|---|---|---|
| 关单先赢（0→4） | 支付回调到达时状态已 4 | `onPaymentSuccess` 返回 **false** |
| 支付先赢（0→1） | 关单到达时状态已 1 | 关单幂等跳过（无副作用） |

### 4.3 为什么竞态不抛 500（P0-6 教训）

- 抛异常 → 支付侧误判"通知失败" → **无限重试**；
- 正解：**幂等返回 false** —— 这是给支付侧的"业务拒绝"信号 → 支付侧**自动退款**（钱货两空防线）；
- 一句话：**订单侧返回值是有资金后果的**——false ≠ 报错，false = "这单不能收钱，请退款"。

### 4.4 返回值的语义边界：503 与业务拒绝

- **业务拒绝**（返回失败码且非 503）→ 支付侧不发 MQ + 自动退款（终态，不可逆）；
- **503/网络异常**（临时故障）→ 支付侧视为"未收敛"→ 走 MQ + XXL 补偿重试（订单可能只是暂时不可达，退款会错杀）；
- 所以订单侧要分清：**竞态是业务拒绝**（false）；**服务自身不可用才是临时故障**（异常/503）。

## 五、联动下游：确认库存（第 ④ 跳）

- `confirmInventoryDeduct(orderId, orderNo, userId)` → 库存域 `POST /api/inventory/confirm`（伪订单 ID）→ 删除预扣记录（预扣 → 正式扣减）；
- 失败补偿：订单侧发 `CONFIRM_STOCK` 补偿消息重试（防"预扣记录残留 → 被超时任务当弃单释放"）；
- **迟到边界**：支付确认可能早于预扣落（03B §七）——订单侧补偿 + 库存侧"确认标记"改判，双层兜住；
- 库存侧细节（预扣/确认/释放/墓碑）归《库存-讲解》。

## 六、兜底网（订单视角：每层假设上层会漏）

| 环节 | 可能漏什么 | 兜底 |
|---|---|---|
| 发起支付 | 重复支付 | 支付域四道防线；订单侧不重复造 |
| 结果通知 | Feign 失败/丢 | MQ 兜底（PayResultConsumer）+ 支付侧 XXL 补偿 Job |
| 结果重复 | 重复收敛 | CAS 幂等（第二次 0 行） |
| 竞态 | 钱收了单不收 | 返回 false → 支付侧自动退款 |
| 库存联动 | 确认失败/迟到 | `CONFIRM_STOCK` 补偿 + 库存侧确认标记（03B §七） |
| 全链兜底 | 谁都没兜住 | 支付侧对账（支付成功但订单仍待付款 → 补通知） |

## 七、A1 改造规划：支付单复用（记录，2026-10-14）

> 背景：xhs 现状 = "拦新的"（在途 30min 内拒绝重复发起：`statusKey` 存在即拒）。两个问题：① 体验差（放弃/想换渠道后 30 分钟不能再发起）；② 只拦住了"商户侧新建"，真实渠道侧旧交易仍活着（prepay_id 有效期内可付）→ 严格说仍有"双活"窗口。
> 目标形态：**一个订单最多一条"活着的"（status=0）支付单；再次发起 = 复用；换渠道 = 关旧交易 + 新开一单。**

### 7.1 表结构修复（核心不变量）

- 表：`my_xhs_payment.t_payment`（DDL 在 `init-all.sql:613` / `mysql-order-init.sql:24`）；
- 缺口：`uk_payment_no` 只防单号重复、`idx_order_id` 是普通索引——**没有任何约束阻止"同一订单多条 pending"**；
- 修复（MySQL 8.0 函数索引；它是**约束**不是查询索引）：

```sql
ALTER TABLE t_payment
  ADD UNIQUE INDEX uk_order_pending
      ((CASE WHEN status = 0 AND deleted = 0 THEN order_id END));
```

- 存量迁移（先清理后建索引；脚本 `migration/payment/V2__pending_unique.sql`）：同订单多条 pending → 只留最新一条、其余置失败（status=2）。

### 7.2 `pay()` 改造（拦截 → 复用）

```
锁 → P1-1 回查订单 → 金额校验
  → 查 pending（WHERE order_id=? AND status=0 AND deleted=0）：
      ├─ 有 + 同渠道 → 复用：返回同一 paymentNo（真实渠道：同商户单号刷新支付参数；
      │                 渠道按商户单号幂等，不会双交易）；补记 t_payment_event（REUSE）
      ├─ 有 + 换渠道 → close 旧渠道交易（微信 closeorder / 支付宝 trade.close）
      │                 → 旧单置"已关闭"（新增 status=4）→ 新建新渠道单
      └─ 无          → 新建（现有逻辑）
  → 并发兜底：INSERT 撞 uk_order_pending（DuplicateKeyException）→ 重查 pending → 复用
```

要点：
- **支付单是"不可变的渠道凭证"**（一条记录 ↔ 一笔渠道交易，对账/审计的锚点）——换渠道不 UPDATE pay_type，而是"关旧单 + 新开一单"；
- **复用要记事件**：复用方案相对"每次新建"的唯一损失是"尝试历史"——用 `t_payment_event` 补（每次复用记一条）。

### 7.3 旧键处置（阶段 2）

- `myxhs:payment:status:{orderId}`：唯一读点 = 被替换的拦截逻辑 → 写入点清理；
- `myxhs:payment:paying:{orderId}`：只写不读 → 删除。

### 7.4 分阶段

| 阶段 | 内容 | 风险 |
|---|---|---|
| **1** | DDL + 迁移脚本 + `pay()` 复用 + 并发兜底 + 单测 | 低（行为变更：不再"请勿重复支付"，改复用） |
| **2** | 换渠道（close + status=4）+ 死键清理 | 中（动渠道适配层） |
| **3（可选）** | 订单终结时 close pending；mock 模式对齐 | 低 |

### 7.5 行为对比

| 场景 | 现状（拦新的） | 改造后（复用） |
|---|---|---|
| 放弃后再点支付 | 拒绝"请勿重复支付"（30min） | 复用同一支付单，正常唤起 |
| 双击/并发 | 拒绝 | 复用；唯一索引兜底 |
| 换渠道 | 拒绝（30min） | 关旧交易 → 新开一单 |
| 支付单堆积 | 拦失效时可能多条 | 结构上 ≤1 条 pending |
| 失败后重试 | 被"2"挡（订单已终结） | 正常新建 |
| 旧渠道交易泄漏 | 存在（prepay_id 有效期内） | 阶段 2 close 后消除 |

### 7.6 与真实世界做法谱系对照（生产符合性确认）

| 做法 | 说明 | 采用 |
|---|---|---|
| A：复用（一订单一 pending） | 幂等创建；对账"一单对一笔" | **我们的阶段 1** |
| B：每次尝试新单 + 关旧单 | 保留每次尝试记录（风控/审计友好） | **我们的换渠道变体（阶段 2）** |
| C：每次新建、不关旧 | 靠"多笔成功→退款去重"兜底 | 不采用（风险自担） |
| D：前端缓存参数复用 | 客户端层复用（同一渠道交易） | 后端无感，兼容 |

结论：**A 与 B 都是主流生产做法**；我们的方案 = A（同渠道复用）+ B（换渠道关旧 + 新开），符合"支付单 = 渠道凭证、一订单最多一活单"的常识。

## 八、与生产标准的差距（记录，2026-10-14）

> 结论：**支付超时处置这段不是生产标准实现**。生产标准 = "关单/置失败前先查渠道，按渠道真相处置"；xhs = "到点直接置失败"（mock 环境可接受，接真渠道必补）。

生产标准三步 vs xhs 实况：

| | 生产标准 | xhs 实况 |
|---|---|---|
| ① 扫候选 | DB 扫"超窗未决" | ✅ 同（`checkPaymentTimeout` DB 扫描） |
| ② 关单前查渠道 | 调渠道查单（微信 orderquery / 支付宝 trade.query），按**渠道真相**分支 | ❌ **缺失**：直接按本地时钟置失败 |
| ③ 查不到怎么办 | **不处置、留到下一轮**（"不知道"≠"没付"） | —（无此分支） |

四条差距（现象 / 后果 / 修复方向）：

- **GAP-1：关单前不查渠道**——29 分付款（回调在路上）会被误标失败。修复：超时处置前先查渠道；查不到（渠道也超时）→ 不处置留下一轮。
- **GAP-2：置失败无"已核实"证据**——后续无法区分"真失败"和"误标"。修复：置失败时记录核实方式（渠道已确认无支付 / 超时未核实）。
- **GAP-3：渠道侧交易没被关闭**——本地"失败"了，渠道 prepay_id 有效期内仍可付；用户付了 → 撞车退款链（能兜，但多一次退款 + 体验差）。修复：超时处置时调渠道关闭接口（closeorder / trade.close）再标本地失败。
- **GAP-4：误标失败 + 回调永久丢失 = 永久错位**——`paymentNotifyCompensateJob` 只扫 status=1，未收敛成功单没人看；订单侧已关单。只能靠 T+1 结算对账人工发现。修复：GAP-1 修掉后（关单前已查渠道），此类永久错位基本消失；另给 reconcile 加"已失败但渠道可能已付"的核查分支。

为什么 xhs 这样也能跑：全链路渠道都是模拟的——回调 1~3 秒必到，"回调永久丢失"几乎不发生；且有"迟到成功翻转"补救误标。**mock 环境 OK，接真渠道必补（至少 GAP-1 + GAP-3）。**

## 掌握标准 + 背走一句

1. 订单的支付交互面 = 发起 / 接收（Feign+MQ 双通道）/ 提供回查（status、pay-amount）/ 联动下游（库存确认、退款发起）；
2. 接收必须幂等：双通道 + 重试 → CAS 收口（第二次 0 行）；
3. **返回 false ≠ 报错**：竞态返回 false 是"业务拒绝"信号 → 支付侧自动退款（P0-6：绝不抛 500 触发无限重试）；
4. 金额以订单为权威（支付侧回查比对）；
5. 下游联动靠补偿（CONFIRM_STOCK）+ 库存侧确认标记双层兜底（03B §七）。

> **订单与支付的联动就三件事：把支付发出去（金额权威在订单）、把结果收回来（双通道幂等收敛）、把拒绝说清楚（返回 false 让支付侧退款，而不是抛异常让支付侧重试）。**
