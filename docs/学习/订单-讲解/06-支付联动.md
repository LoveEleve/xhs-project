## 一、先看"付款"这一跳（订单视角）

小明在订单详情页点"去支付"（订单 `status=0`）。整条链涉及支付域/渠道/订单/库存，但**订单只关心四件事**：

```
① 发出：订单 ──Feign──→ 支付域             （发起支付）
② 渠道：支付域 ←──HTTP 通知── 支付宝        （订单不参与）
③ 接收：支付域 ──Feign 主通道 + MQ 兜底──→ 订单（收敛状态）
④ 联动：订单 ──Feign──→ 库存域              （预扣转正）
```

**交互面**：

| 方向 | 接口 | 谁调谁 | 订单角色 |
|---|---|---|---|
| 出 | `POST /api/payment/pay` | 订单 → 支付 | 发起/复用支付 |
| 入 | `POST /api/order/pay-success` / `pay-fail` | 支付 → 订单 | 收敛（主通道） |
| 入 | `PAY_RESULT_TOPIC` | 支付 → MQ → 订单 | 收敛（兜底） |
| 契约 | `GET /api/order/status`、`pay-amount` | 支付 → 订单 | 回查（内部） |
| 出 | `POST /api/inventory/confirm` | 订单 → 库存 | 支付成功后确认扣减 |
| 出 | `POST /api/payment/refund-by-order` | 订单 → 支付 | 售后退款 |
| 入 | `POST /api/order/refund-success` | 支付 → 订单 | 全额退款收敛 |

> 当前 `pay.type=remote`；`MockPayService` 仅在 `pay.type=mock` 时装配，是本地开发备用路径，不是主链。

## 二、订单侧要解决的三个问题

| # | 问题 | 本质 | 对策 |
|---|---|---|---|
| 1 | 把支付发出去 | 金额可信 + 不重复扣 | 金额以订单为权威；支付域做幂等/复用 |
| 2 | 把结果收回来 | 丢失/重复/迟到是常态 | 双通道 + CAS 幂等 |
| 3 | 把边界说清楚 | 钱收了单不收 | 竞态返回 false（业务拒绝）→ 支付侧退款 |

## 三、支付域生产化：订单必须知道的契约

### 3.1 一订单最多一条"活着的"支付单（C-002）

- 唯一约束 `uk_order_pending`（函数索引）保证同一订单最多一条 `status=0` 支付单；
- 再次发起：
  - 同渠道 → **复用同一 paymentNo**（渠道按商户单号幂等，不会双交易）；
  - 换渠道 → **先查渠道**：已付=受理收敛；未付=close 旧交易 → 新开一单；不可达=不切换（"不知道"≠"没付"）；
- 订单终结 → 支付域订阅 `ORDER_TERMINATION_TOPIC`，关闭 pending（订单侧零改动）；
- 支付单是"渠道凭证"：换渠道不 UPDATE，而是关旧 + 新开。

### 3.2 超时处置：先查渠道，再决定（C-002）

```
DB 扫超窗 pending
→ 查渠道
   ├─ 已支付 → 受理成功（迟到成功）
   ├─ 明确未支付 → close 渠道 + 本地 status=2（失败）+ verify_method=1（已核实）
   └─ 查不到/不可达 → 不处置，留到下一轮（"不知道"≠"没付"）
```

- 置失败必须记录 `verify_method`（1=渠道已确认，2=超时未核实）；
- 已关闭(4)的支付单收到迟到 `TRADE_SUCCESS` → 受理（C-002 行为）；
- 对账分支：status=2 且 verify_method=2 → 重查渠道，已付则收敛。

### 3.3 支付宝通知契约（C-003）

```
支付宝 → POST /api/payment/notify/alipay（form）
→ RSA2 验签
→ 二次校验：out_trade_no 存在 / total_amount 一致 / app_id+seller_id 一致
→ 四态：
   TRADE_SUCCESS / TRADE_FINISHED → 支付成功
   TRADE_CLOSED → 双语义（本地待支付=未付关闭；已成功/已退款=全退后关闭，幂等）
   WAIT_BUYER_PAY → 忽略
→ 应答明文 "success"（不重试）或 "fail"（渠道按节奏重试）
```

- 通知重试按 `notify_id` 不变；业务幂等靠支付单状态 CAS；
- 验签失败/二次校验失败 → `fail` + 告警，不误处理；
- 通知重试耗尽 → 查单兜底（对账核查分支）。

### 3.4 退款：同步 + 出金幂等（C-003）

- 退款按支付宝真实契约**同步返回**，不再走退款回调链；
- 出金幂等键 `out_refund_no`（售后单号）：同键重复请求返回既有退款单；
- 全额退款成功后支付域通知订单（`refund-success` / MQ）；**部分退款不通知订单**；
- 退款异常（结果未知）→ 售后单停留退款中，恢复任务用同一 out 键重试。

## 四、订单侧实现

### 4.1 发起支付

```java
// pay.type=remote
OrderVO order = orderService.getOrderDetail(userId, orderId);
payRequest.setAmount(order.getPayAmount());  // 订单金额权威
return paymentFeignClient.pay(payRequest, userId);
```

- 订单只提供 `orderId/userId/amount/payType`；复用/换渠道/防重由支付域处理；
- 支付域会回查 `pay-amount` 做金额校验；
- `pay/create` 当前**没有限流**（资金动作防护弱于取消/下单，已知边界）。

### 4.2 成功收敛 `onPaymentSuccess`

四件事：

1. **CAS 0→1**：`appendEvent(EVENT_PAID)` + 乐观锁；
2. **竞态**：已支付/已取消/已关闭 → 返回 false，不抛 500；
3. **子单推进**：全部子单 0→1（幂等；重复通知可机会式自愈）；
4. **联动/收尾**：异步 `confirmInventoryDeduct`（失败→CONFIRM_STOCK 补偿）+ 快照 PAID + 缓存失效 + 通知。

> ⚠️ 重复成功（订单已是 1）当前也返回 false。正常支付重复通知会在支付单状态守卫处被吸收，不会走到这里；但人工/新调用方若重放，支付侧可能把它当业务拒绝（潜在自动退款）。理想口径是"已支付返回 success 幂等"（P2）。

### 4.3 失败收敛 `onPaymentFailed`

- 统一走 `terminateOrder(PAY_FAILED)`（第五条终结路径）；
- 父单 0→4 + 全子单 0→4 同事务；库存/券/通知由 `ORDER_TERMINATION_TOPIC` 订阅方执行；
- 已是终态 → 幂等；映射缺失 → 跳过，30min 关单兜底。

### 4.4 退款收敛

- `onRefundSuccess(orderId)`：只处理**全额退款**，父单 1/2/3→5 + 全子单 1/2/3→5；
- 顺序：`confirmInventoryDeductSync` → `restoreStockOnRefund` → 退券 → 快照/通知；
- 部分退款不通知订单：订单主状态保持 1/2/3，退款事实由售后单/支付域表达；
- `refund-fail` 回调当前是**空实现（仅日志）**——退款失败不改订单状态，靠售后单/支付域重试，属已知债。

### 4.5 内部契约

- `GET /api/order/status`：只有 0 待付款可支付；
- `GET /api/order/pay-amount`：金额权威 + "订单是否仍未收敛"探针；
- 两者都要求 `X-Internal-Call`。

## 五、深水：竞态与返回值语义

### 5.1 双通道 + 渠道重试 → CAS 幂等

同一结果可能从 Feign/MQ/渠道重试到达多次；`onPaymentSuccess` 第二次 CAS 0 行 → 返回 false/已支付，不重复加库存、不重复通知。

### 5.2 支付 vs 关单

| 谁先赢 | 结果 | 订单动作 |
|---|---|---|
| 关单先赢（0→4） | 支付回调到达时已 4 | 返回 false → 支付侧按业务拒绝退款 |
| 支付先赢（0→1） | 关单到达时已 1 | 终结返回 INVALID_STATUS/幂等跳过 |

### 5.3 false ≠ 报错

- 抛异常 → 支付侧误判"通知失败" → 无限重试；
- 返回 false → 支付侧视为**业务拒绝** → 自动退款；
- 一句话：**订单侧返回值有资金后果**。

### 5.4 503 与业务拒绝

- 业务拒绝（非 503）→ 支付侧不重试 + 自动退款（终态）；
- 503/网络异常 → 支付侧视为"未收敛"→ MQ/XXL 补偿重试；
- 订单侧要分清：竞态=false；自身不可用=异常/503。

### 5.5 迟到成功与已关闭

- 支付单已本地关闭(4)，渠道迟到 `TRADE_SUCCESS` → 支付域受理（C-002）；
- 订单侧可能已 4（取消）→ `onPaymentSuccess` 返回 false → 支付侧退款；
- 这是"钱已收、单已关"的最终防线，不能只靠本地状态。

### 5.6 部分退款

- 支付域只对**全额退款**通知订单；部分退款订单主状态不变；
- 若误把部分退款当全退，会把父/子置 5，后续履约/售后全乱；
- 全额/部分由支付域按累计退款额判断，订单侧不做金额推断。

## 六、兜底网

| 环节 | 可能漏什么 | 兜底 |
|---|---|---|
| 发起支付 | 重复 pending | `uk_order_pending` + 复用/换渠道 |
| 支付通知 | Feign 失败/丢 | MQ 兜底 + 支付侧 XXL 补偿 Job（2min） |
| 结果重复 | 重复收敛 | CAS 幂等 |
| 竞态 | 钱收单不收 | false → 支付侧自动退款 |
| 超时误判 | 29 分付款 | 先查渠道 + verify_method + 迟到成功受理 |
| 渠道通知 | 验签/金额/商户异常 | 二次校验 + fail 重试 + 查单兜底 |
| 退款 | 重复出金 | `out_refund_no` 唯一 + 同键返回既有退款单 |
| 库存联动 | 确认失败/迟到 | CONFIRM_STOCK 补偿 + 库存确认标记 |

## 八、十二个坑

1. **同一订单多条 pending**：必须唯一约束 + 复用；否则双活支付。
2. **换渠道直接新建**：旧渠道仍可付；先查/close 再新建。
3. **订单终结不关 pending**：用户取消后还能付；支付域订阅终结事件关闭。
4. **超时直接置失败**：29 分付款被误杀；先查渠道，"不知道"不处置。
5. **置失败不记 verify_method**：无法区分"真失败/未核实"；对账无从下手。
6. **关闭渠道失败不复查**：用户恰在 close 前付款；close 失败再查，已付受理。
7. **已关闭收到迟到成功不接受**：钱收了单不收；受理并走退款/收敛。
8. **通知应答 JSON**：支付宝只认明文 `success`；格式错会无限重试。
9. **只验签不二次校验**：金额/商户/单号不符仍处理；必须二次校验。
10. **TRADE_CLOSED 一律置失败**：全退后的关闭会误伤已退款单；按本地状态双语义。
11. **退款不用 out 键**：重试/补偿重复出金；`out_refund_no` 唯一。
12. **把 false 抛成 500**：支付侧无限重试；false=业务拒绝，异常=临时故障。

## 九、值不值得深挖 / 一句话

- **值得**：支付单复用、超时先查渠道、通知验签/二次校验/ACK、false 语义、退款 out 键——支付联动的生产级内核；
- **一句话带过**：支付域内部渠道实现、XXL 补偿细节；
- **一句话**：**订单负责金额权威/状态收敛/竞态语义，支付域负责一单一条活支付、先查后决、验签 ACK、同步退款；false 是业务拒绝，不是报错。**
- 售后见 **08**；对账见 **11**；收口见 **12**。

**面试口径**："订单发起支付只给 orderId/userId/金额；支付域保证一订单最多一条 pending，同渠道复用、换渠道先查后 close、订单终结关 pending；超时先查渠道，未知不处置，置失败记 verify_method。渠道通知走支付宝契约：form+RSA2+二次校验+四态+明文 ACK；退款同步、out 键幂等。订单侧成功 CAS 0→1、失败统一终结、竞态返回 false 让支付侧退款，绝不把业务拒绝抛成 500。"
