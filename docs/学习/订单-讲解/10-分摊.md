# 10 · 分摊：订单级优惠 → 行级金额（已落库）

> **定位**：钱的地基——把"订单级优惠"翻译成"行级实付金额"；退款、结算、展示三本账都以它为准。分摊算错，后面全错。
> **修订（2026-10-25）**：分摊已落库（ITER-001）；本篇从"纯函数重算"改为"下单落库 + 重算兜底"。
> **素材**：`DiscountAllocator`、`OrderTransactionService`、`AftersaleService`、`OrderVO`、`t_order_item.discount_share`。
> **系列导航**：`00` → `01` → `02` → `03` → `03A` → `03B` → `04` → `04A` → `04B` → 05-库存预占（跳过） → `06-支付联动` → `07-履约线` → `08-售后线` → `09-拆单` → **10-分摊** → `11-对账` → `12-收口`。

---

## 一、先看"分摊"在干什么（例子先行）

小明买 2 箱气泡水（200）+ 短袖（30）+ 裤子（70），标价合计 300；用一张订单券减 30，实付 **270**。

问题：**退短袖，退多少钱？**

- 按标价退 30？——**多退**（优惠份额没扣回来）→ 资损；
- 按"优惠平均到件数"退 22.5？——**算法错**（水 200 和短袖 30 不可能减同样多）；
- 正确：**优惠按金额比例摊到每一行**——

| 行 | 原价 | 券 30（按金额摊） | 行实付 |
|---|---|---|---|
| 水×2 | 200 | 20.00 | 180.00 |
| 短袖 | 30 | 3.00 | **27.00** |
| 裤子 | 70 | 7.00 | 63.00 |
| 合计 | 300 | 30.00 | **270.00** |

短袖实付 = **27 元**，退款也只能退 27；按 30 退就多退 3。

> 当前 xhs 只有**订单级单券**（没有平台券/店铺券/红包的归属与出资方）。上面的"按金额摊"是通用骨架；如果将来加店铺券，还要加"摊分基数 = 本店商品"的约束（见 §5）。

---

## 二、为什么必须分摊（三本账）

| 账 | 不分摊会怎样 |
|---|---|
| **退款账** | 退一件按标价退 → 多退（资损）；按平均摊 → 算错（不公平） |
| **结算账** | 商家应收 = 商品金额 − 分摊优惠 − 佣金；没有行级金额，分账无从谈起 |
| **展示账** | 用户要知道"每件实际花了多少"；`OrderVO` 已返回行级 `discountShare/payAmount` |

还有两个隐藏维度——**每笔优惠都有两个属性**：

- **归属**（哪些商品能用）：平台券摊全部；店铺券只摊本店；单品券只摊单品；
- **出资**（谁掏钱）：平台券平台出、店铺券商家出——影响结算/分账。

**分摊/结算的全部复杂度，都从这两个属性长出来。** 当前 xhs 只有订单级单券，所以这两个维度还没真正用上；算法是通用骨架。

---

## 三、怎么摊：算法原则

1. **按金额比例**（不是按件数平均）：行 i 的份额 ∝ 行金额；
2. **适用范围约束**：店铺券的摊分基数 = 本店商品金额（当前未实现）；
3. **取整策略**：以"分"为单位整数运算；逐项取下整 → 差额按余数补齐（**最大余数法**）；
4. **确定性**：同一订单任何时刻重算结果一致（平局按明细 ID 定序）；
5. **守恒不变量**：Σ分摊 == min(优惠, 商品总额)；单项分摊 ≤ 该项金额。

## 四、当前实现：下单落库 + 重算兜底

### 4.1 下单：分摊进本地事务

`OrderTransactionService.executeLocalTransaction` 在**父/子/行同一本地事务**内：

```java
// 行：预分配 ID + 金额
item.setId(IdWorker.getId());
item.setTotalAmount(price.multiply(qty));

// 分摊：最大余数法
Map<Long, BigDecimal> allocation =
        DiscountAllocator.allocateByItems(items, discountAmount);
item.setDiscountShare(allocation.getOrDefault(item.getId(), BigDecimal.ZERO));

// 子单：Σ行小计 / Σ行分摊 / Σ行实付
sub.setTotalAmount(subTotal);
sub.setDiscountAmount(subDiscount);
sub.setPayAmount(subTotal.subtract(subDiscount));
```

- 落库字段：`t_order_item.discount_share`（行分摊）；
- 守恒：`父单实付 = Σ子单 = Σ行(total - share)`；
- 行 ID 预分配，是为了"分摊以行 ID 为键"且平局可定序。

### 4.2 售后：以落库份额为准

`AftersaleService.entitlement`：

```java
BigDecimal share = item.getDiscountShare();
if (share == null) {
    // 仅存量数据（无落库值）回退重算
    share = DiscountAllocator.allocateByItems(items, order.getDiscountAmount())
            .getOrDefault(item.getId(), BigDecimal.ZERO);
}
BigDecimal refundableTotal =
        DiscountAllocator.refundableAmount(item, share, item.getQuantity());
```

- **主口径 = 落库 `discount_share`**；重算只对存量 null 数据兜底；
- 售后单自身落 `discount_share/refund_amount`，但它是**本次申请对应份额**，不是整行份额（部分数量时两者不同）；
- 部分数量：`refundableAmount` 按比例向下取整；退满时 `resolveRefundable` 用"整件可退 − 已占用"补差，保证累计不超退、不少拿几分。

### 4.3 展示

- `OrderVO.OrderItemVO` 返回 `discountShare` + `payAmount = totalAmount - discountShare`；
- 子单/父单金额在创建时已算好，不依赖前端重算；
- 当前没有独立"结算页"聚合；展示层直接用行级字段即可。

> ⚠️ 代码注释漂移：`DiscountAllocator` 类注释仍写"分摊结果无需落库"，与当前 `discount_share` 落库不一致；以代码/DDL 为准。

## 五、为什么必须落库（而不是每次重算）

| | 只重算（旧） | 落库（当前） |
|---|---|---|
| 时点 | 售后时按订单快照重算 | 下单时摊到行，随订单事务落库 |
| 共享 | 退款/结算/展示各自重算，口径易漂 | 一份行级金额，所有下游共用 |
| 一致性 | 依赖"当时的算法"；算法演进会改变历史订单 | 行级金额被**冻结**为账务事实 |
| 完整性 | 未退过的行没有行级凭证 | 每一行都有 `discount_share` |
| 性能 | 每次售后都要重算 | 直接读；重算只作存量兜底 |

三个理由：

1. **跨系统共享**：结算/对账/展示不该各自重算；
2. **口径冻结**：账务数据一旦产生，不应被算法演进改变；
3. **完整性**：对账要拿"所有行的实付"对平支付金额。

> 旧 10 写的"改造①分摊落库"已经完成；现在的改造重点不是"落不落"，而是"多优惠归属/出资"和"售后数量口径"。

## 六、深水

### 6.1 取整与确定性

- N 行最多 N-1 分误差，最大余数法兜底；
- 平局按明细 ID 定序，保证同一订单重算结果一致——这是"可重算"的前提，也是"落库校验"的前提；
- 以"分"为单位，避免浮点误差。

### 6.2 部分退款与退满补差

- 未退满：`refundableTotal × applyQuantity / quantity`，向下取整（永不超退）；
- 最后一次退满：`refundableTotal - occupied`，补齐之前向下取整的几分钱；
- 两个规则配合，累计退款严格等于整件可退。

### 6.3 数量口径的旧账：`max(a,b)`

- 金额按"比例"摊；数量回补按"本次量 vs 库存累计目标"——跨模块口径不对齐，出现同 SKU 两次售后累计少补（`08 §5.1`）；
- 分摊落库解决了"金额锚点"，但没有解决"数量锚点"；这是独立旧账。

### 6.4 多优惠叠加（当前未实现）

- 平台券、店铺券、红包的摊分基数/顺序/出资方不同；
- 加店铺券时，摊分基数必须限定本店商品；跨店满减还要"多店合计达标、优惠摊回各店各件"；
- 当前只有单券，算法骨架可复用，但归属/出资维度没有落地。

### 6.5 结算分账（仍未做）

- 行级 `discount_share` 已具备"按行算商家应收"的基础；
- 但当前没有商家分账/结算单，支付域结算表也不按 seller 分账；
- 这是 11-对账/结算域的缺口，不是分摊算法本身。

## 八、十二个坑

1. **按件数平均摊**：水 200 和短袖 30 减同样多，算错；按金额比例。
2. **店铺券摊全部商品**：摊分基数必须是本店金额（当前未实现，扩展时别忘）。
3. **用浮点算钱**：分单位整数 + 最大余数法。
4. **只取下整不补余**：Σ分摊 ≠ 优惠，账对不上。
5. **平局不定序**：同一订单重算结果漂移；按明细 ID 定序。
6. **单项分摊超过行金额**：负实付；`min(share, amount)`。
7. **只重算不落库**：算法演进改变历史口径、未退行没有凭证（当前已修）。
8. **把售后单的 `discount_share` 当整行份额**：它是"本次申请份额"；部分数量时不同。
9. **部分退款比例上取整**：累计超退；向下取整。
10. **最后一次不补差**：用户少拿几分；退满补差。
11. **`max(a,b)` 数量旧账**：金额对了，数量回补仍可能少补；跨模块单独修。
12. **多优惠顺序不定**：先摊平台券还是店铺券会改变行分摊；规则要定死（当前单券暂无）。

## 九、值不值得深挖 / 一句话

- **值得**：最大余数法、确定性、部分退/退满补差、落库 vs 重算——订单金额账的地基；
- **一句话带过**：代码细节、DDL 字段；
- **一句话**：**分摊 = 把整单优惠按金额比例摊到行；xhs 用最大余数法在下单事务内落库，售后按落库份额退；部分退向下取整、退满补差。**
- 拆单见 **09**；售后见 **08**；对账见 **11**。

**面试口径**："订单优惠按行金额比例用最大余数法摊到行，分摊结果在下单本地事务里落 `discount_share`；行实付 = 行金额 − 分摊，父单/子单/行三层守恒。售后以落库份额为准，部分数量按比例向下取整，最后一次退满补差；旧数据无落库值时回退确定性重算。多优惠的归属/出资和 `max(a,b)` 数量口径仍是缺口。"
