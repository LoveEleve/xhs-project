## 一、先看"分摊"在干什么（例子先行）

小明买 2 箱气泡水（200）+ 短袖（30）+ 裤子（70），标价合计 300；平台券满 300-20、B 店券满 100-10（短袖+裤子恰好 100）→ 实付 **270**。

问题：**退短袖，退多少钱？**

- 按标价退 30？——**多退**（两笔优惠的份额没扣回来）→ 资损；
- 按"优惠平均到件数"退 22.5？——**算法错**（优惠不是平均分的，水 200 和短袖 30 不可能减同样多）；
- 正确：**优惠按金额比例摊到每一行**——

| 行 | 原价 | 平台券 20（摊全部） | B 店券 10（只摊本店） | 行实付 |
|---|---|---|---|---|
| 水×2 | 200 | 13.33 | — | 186.67 |
| 短袖 | 30 | 2.00 | 3.00 | **25.00** |
| 裤子 | 70 | 4.67 | 7.00 | 58.33 |
| 合计 | 300 | 20 | 10 | **270** |

短袖实付 = **25 元**，退款也只能退 25。

> 分摊就是把"整单减 30"翻译成"每件商品各自减多少"。注：店铺券是应然形态；xhs 只有订单级单券（无归属方维度），但算法逻辑一致（见 §四）。

## 二、为什么必须分摊（三本账）

| 账 | 不分摊会怎样 |
|---|---|
| **退款账** | 退一件按标价退 → 多退（资损）；按平均摊 → 算错（不公平） |
| **结算账** | 商家应收 = 商品金额 − 分摊优惠 − 佣金——没有行级金额，分账无从谈起（→ 11-对账） |
| **展示账** | 用户要知道"每件实际花了多少"（App 显示优惠后价格）——xhs 当前没做 |

还有两个隐藏维度——**每笔优惠都有两个属性**：

- **归属**（哪些商品能用）：平台券摊全部商品；店铺券只摊本店商品；单品券只摊单品；
- **出资**（谁掏钱）：平台券平台出、店铺券商家出——影响结算/分账。

**分摊/结算的全部复杂度，都从这两个属性长出来。**

## 三、怎么摊：算法原则

1. **按金额比例**（不是按件数平均）：行 i 的份额 ∝ 行金额；
2. **适用范围约束**：店铺券的摊分基数 = 本店商品金额（不是整单）；
3. **取整策略**：以"分"为单位整数运算；逐项取下整 → 差额按余数补齐（**最大余数法**）；
4. **确定性**：同一订单任何时刻重算结果一致（平局按明细 ID 定序）；
5. **守恒不变量**：Σ分摊 == min(优惠, 商品总额)；单项分摊 ≤ 该项金额。

## 四、实然：xhs 的 DiscountAllocator（纯函数重算）

`DiscountAllocator.allocateByItems(items, totalDiscount)` —— 最大余数法（Largest Remainder）：

```java
// 1) 逐项取下整：base_i = floor(优惠分 × 金额分_i / 总额分)
long base = Math.min(exact / 1_000_000L, amounts[i]);   // 单项分摊不超过该项金额
// 2) 取整差额（最多 N-1 分）按余数从大到小逐项 +1 分补齐
// 3) 平局按明细 ID 升序（保证同一订单任何时候重算结果一致）
```

- 全程"分"为单位的整数运算（放大 1e6 只用于余数比较）——**无浮点误差**；
- **不变量（自校验）**：Σ分摊 == min(优惠, 商品总额)，且每项分摊 ≤ 该项金额 → "退款 = 明细金额 − 分摊"天然不会超退；
- 使用点：售后重算 `allocateByItems(items, order.getDiscountAmount())` → 行分摊 → 行可退；
- 部分数量：`refundableAmount` 按比例**向下取整**（永不超退）；**退满时补齐差额**（`resolveRefundable`：整件可退 − 已占用）——多次部分退的累计严格等于整件可退，不因取整让用户少拿几分；
- 设计立场（代码注释）："分摊结果**无需落库**，售后时按订单快照重算即可"——指**订单侧**无需落库（本次申请的结果仍随售后单落库：`t_aftersale.discount_share/refund_amount`，见 §五）；依据 = 纯函数 + 确定性 + 不变量自校验。

## 五、应然 vs 实然：为什么"不落库"最终还是要改

| | 淘宝（应然） | xhs（实然） |
|---|---|---|
| 时点 | 下单时摊到行，**落库** | 售后时**重算**——订单侧不落库；只有"本次申请"的结果随售后单落库 |
| 共享 | 退款 / 结算 / 发票共用同一套行级金额 | 订单侧无行级金额来源；展示、结算要用时得各自重算 |
| 一致性 | 行级金额 = 下单时**冻结**的账务事实 | 重算依赖"订单快照 + 当时的算法"——算法演进会改变历史订单的重算口径 |

"确定性重算"不等于"可以依赖重算"，三个理由：

1. **跨系统共享**：结算/对账/展示不该各自重算（口径会漂）——需要一份统一的行级金额来源；
2. **口径冻结**：账务数据一旦产生，不应被"算法演进"改变——落库 = 冻结，重算 = 每次都依赖当时的代码；
3. **完整性**：对账要拿"所有行的实付"对平支付金额——xhs 只有被退过的行在售后单里留下结果，未退的行没有任何行级凭证。

→ 所以改造四阶段的**第①步 = 分摊落库**（`discount_share` 落库，见《订单-改造/01》§三）。

## 六、深水

- **取整误差**：N 行最多 N-1 分误差，最大余数法兜底；"平局按 ID 定序"是为了**确定性**（重算一致，不是随便定）；
- **退满补齐**：未退满按比例向下取整、退满补差额——两个规则配合才能保证"累计退 = 整件可退"；
- **数量口径的教训（`max(a,b)`）**：金额按"比例"摊、数量按"本次量 vs 累计目标"——跨模块口径不对齐就是 08 §5.1 的旧账；分摊落库也是给"金额与数量口径对齐"立锚；
- **多优惠叠加顺序**：平台券、店铺券、红包的摊分基数是否相同？先摊哪个会影响各行分摊结果——规则要**定死**（应然：定义摊分顺序与基数）；
- **跨店满减**（最难的一类）：多店合计达标、优惠摊回各店各件——归属跨店、出资在平台。

## 掌握标准 + 背走一句

1. 分摊 = 把订单级优惠**按金额比例**翻译成行级金额（不是按件数平均）；
2. 每笔优惠有**归属**（适用范围）+ **出资**（谁掏钱）两个属性——结算复杂度的源头；
3. 算法 = **最大余数法**（分单位整数运算 + 余数补齐 + 平局定序 → 确定性 + 守恒不变量）；
4. xhs = 纯函数重算（确定性自证）；应然 = 下单落库（跨系统共享 / 口径冻结 / 完整性三个理由）；改造① = 分摊落库；
5. 退款口径 = 行实付（明细金额 − 分摊）；部分退向下取整、退满补齐。

> **分摊就是"把整单优惠按金额比例翻译成每件商品各自减多少钱"——退款、结算、展示三本账都靠它；xhs 用确定性重算顶住了当下，账务化（落库）是改造的地基。**
