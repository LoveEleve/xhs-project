# 00 · 订单域：三层账本、状态机与学习路线

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
> **修订（2026-10-25）**：以当前代码为准。拆单、分摊落库、行级售后、支付生产化、商家维度查询均已落地；旧 00–12 中相关段落正在逐篇修订，冲突处以本篇和《订单-侦察/05-订单域深度探索-2026-10-25.md》为准。
> **一句话**：订单 = **父单（交易/支付）→ 子单（商家/履约）→ 行（SKU/金额）** 的三层交易账本；核心不是 CRUD，而是**状态机 + 幂等 + 事务消息/Outbox + 拆单聚合 + 分摊/退款 + 对账**。
> **系列**：00 总纲 → 01 防重 → 02 价格/快照 → 03/03A/03B 事务消息 → 04/04A/04B 关单/终结 → 06 支付 → 07 履约 → 08 售后 → 09 拆单 → 10 分摊 → 11 对账 → 12 收口；13 查询/索引、14 工程/测试为待补篇。

### 2.1 三层状态机（当前）

```
父单 t_order：0 待付款 → 1 已付款 → 2 已发货 → 3 已完成
                 ↘ 4 已取消（五条终结路径）
                 ↘ 5 已退款（全退收敛）

子单 t_sub_order：0 待付款 → 1 待发货 → 2 已发货 → 3 已完成
                     ↘ 4 已取消（父单未支付终结时全子单同事务）
                     ↘ 5 已退款（全退收敛）

行 t_order_item：不单独流转；履约/售后/金额锚点
```

父单状态 = 子单状态聚合（`SubOrderService.computeParentStatus`）：

```
全取消 → 4；全退款 → 5；全终态（混合：部分取消/退款 + 部分完成）→ 3；
存在活跃子单：活跃全待付款 → 0；活跃全 ≥已发货 → 2；其余 → 1。
```

> 聚合是**纯函数**；`recomputeParentStatus` 只把 2/3/5 走聚合事件，0/1/4 由支付/终结专属流程推进（避免重复状态写）；CAS 冲突重试，日终校准兜底。

## 三、一笔订单的全景（当前例子）

两个卖家、3 行、优惠券 35：

```
行1：卖家 A，100×1
行2：卖家 B，100×2
行3：卖家 B，50×1
商品合计 = 350；券减 35；父单实付 = 315

下单（同一本地事务）：
  父单 1 条（315）
  子单 A：行1，100 - 10 = 90
  子单 B：行2+行3，250 - 25 = 225
  行分摊：10 / 20 / 5（最大余数法，Σ=35）
  子单号：orderNo-1 / orderNo-2

支付成功：
  父单 0→1；两个子单 0→1（批量）

履约：
  A 发货 → 父单仍 1（B 未发）
  B 发货 → 两个子单都 ≥2 → 父单聚合 1→2
  A、B 都确认 → 父单聚合 2→3

未支付取消：
  父单 0→4 + 全部子单 0→4（同一事务）

全额退款：
  父单 1/2/3→5 + 全部子单 1/2/3→5

部分售后：
  只退行2的 1 件 → 行级售后单；整行分摊 20（单件 10），应退 = 200/2 - 10 = 90
```

这就是"三层账本"的实际含义：**交易看父单，履约看子单，金额/售后看行**。

## 四、三条主取舍（定位决定简化）

1. **平台自营 + 轻量卖家**：不建店铺第一等公民；SKU/行/子单带 `sellerId`，按卖家拆单、按卖家查询；不做店铺券/分账/多包裹。
2. **单券 + 分摊落库**：只支持单张优惠券；下单时把整单优惠按行金额比例分摊并落库；不做平台券/店铺券/跨店满减/红包。
3. **单支付通道 + 生产化**：不做组合支付/预售定金；当前接独立 payment 域（remote），order 侧只负责状态收敛、幂等、退款与补偿。

> 拆单、分摊、行级售后、支付生产化、商家维度查询**都已落地**，不再是"讲而不做"。

## 八、仍缺什么（诚实清单）

1. **完整店铺维度**：只有 `sellerId`，没有店铺主体、店铺券、分账、多包裹；要做得换代。
2. **物流对象化 / 自动确认收货**：当前只有两个字符串，确认靠用户手动。
3. **订单↔支付↔库存三方对账**：有局部校准，没有统一差错池/人工调账。
4. **优惠生态**：无平台券/店铺券/跨店满减/红包；单券 + 单分摊。
5. **售后边界**：无换货；退货退款的回补时点在退款受理后（简化）；`max(a,b)` 漏补是已知跨模块旧账。
6. **工程**：无真实 Redis/MySQL/MQ 集成测试；无压测/故障注入；`OrderService` 1799 行偏大。

## 十、面试口径（30 秒）

> "订单是父/子/行三层账本：父单管交易和支付，子单按卖家拆、管履约，行管 SKU 和金额。下单用幂等键+用户锁+事务消息，本地事务里落父单、子单、行、事件和本地消息；支付成功回调的重复/竞态不抛 500（基础设施失败按可重试语义）；未支付终结统一走五条路径（用户/超时/库存/券/支付失败），父单和全子单同事务取消；拆单后父单状态由子单聚合，发货/确认按子单；优惠按最大余数法摊到行并落库，售后退款按行分摊算；商家查询走 Canal→ES 异构索引。缺口是自动确认收货、三方对账、完整店铺/优惠生态和集成测试。"

**追问应对**：

- **"拆单怎么做的？"** → 下单本地事务按 seller 分组；父单/子单/行三层；父单状态纯函数聚合；履约下沉子单。
- **"分摊为什么落库？"** → 退款/售后/结算都需要行级金额；下单时最大余数法落 `discountShare`，重算只作存量兜底。
- **"售后为什么行级？"** → 同一订单不同行可能部分退；`itemId` 锚点 + `(item_id,type)` 唯一，金额按行分摊。
- **"支付怎么防重？"** → 支付域 out 键幂等；order 侧状态 CAS + 重复通知返回 false（业务拒绝，不抛 500）。
- **"最大风险？"** → 售后退补 `max(a,b)` 漏补、无三方对账、无集成测试。
