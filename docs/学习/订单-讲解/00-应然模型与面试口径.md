## 一、对象模型：应然 vs 实然（第 0 讲 B · 已核实）

| 对象 | 应然（淘宝） | 实然（我们） | 差距 |
|---|---|---|---|
| 用户 / 收货地址 | ✓ | ✓ user 模块 + `addressSnapshot` | — |
| 商品 SPU / SKU | ✓ | ✓ `t_spu`/`t_sku`（无商家字段） | — |
| 购物车 | ✓ | ✓ cart | — |
| 订单 / 明细 / 事件 / 快照 | ✓ | ✓ `t_order/item/event/snapshot` | — |
| 库存三态（预占/成交/退回） | ✓ | ✓ | — |
| 优惠券 | 平台券 + 店铺券 + 活动 | ✓ 单券（无归属方维度） | 简化 |
| 红包 | ✓ | ✗ | 缺 |
| 运费 / 运费险 | ✓ | ✗ | 缺 |
| **店铺 / 商家** | ✓ 核心 | ✗（平台自营模型） | 缺 |
| **拆单（父单/子单）** | ✓ 核心 | ✗（单层订单） | 缺 |
| 物流对象 / 多包裹 | ✓ | ✗（只有两个字符串） | 缺 |
| 支付单 / 退款单 | ✓ | ✓ 支付域 | — |
| 组合支付 | ✓ | ✗ | 缺 |
| 售后单（仅退/退货/换货） | ✓ | ✓（仅退/退货退款；无换货） | 部分 |
| 结算单（多商家分账） | ✓ | ⚠️ 支付域有结算表，无分账 | 简化 |
| 发票 / 评价 / 客服 | ✓ | ✗ | 缺 |

（证据：`订单-侦察/02-订单需求全景与对照.md` §2 + 2026-10-11 核查）

### 1.1 三条主取舍（定位决定简化——"缺"了不算错）

1. **平台自营 vs 多商家集市**：砍掉"店铺"第一等公民 → 拆单/店铺券/分账/多包裹全都不用做；代价 = 无法表达"多商家混合下单、部分发货"（要它 = 父/子单**换代级**改造）。
2. **单券 vs 优惠生态**：无平台券/店铺券/活动/跨店满减/红包；代价 = 无"跨店累计"心智；红利 = 分摊复杂度大降（但**分摊本身仍需要**，见 1.2-②）。
3. **单通道支付 vs 组合支付/预售**：无定金尾款、无余额+卡组合；mock 定位下可接受。

### 1.2 三个"同名不同义"的对照细活

① **快照**：淘宝 = 下单节点固化（价格/优惠/地址"当时版"）；我们 = 按**状态事件**存（10 种：CREATED/PAID/DELIVERED/COMPLETED/REFUNDED + 5 类终结 CANCELLED/TIMEOUT_CANCELLED/INVENTORY_FAILED_CANCELLED/COUPON_FAILED_CANCELLED/PAY_FAILED_CANCELLED，各一版）——同为"点时刻固化"，触发粒度不同；
② **分摊**：淘宝在**下单时**把优惠摊到行（退款/结算/发票共用同一套行级金额）；我们 `DiscountAllocator` 只在**售后重算、不落库**——退补口径问题的来源之一（见 `订单-侦察/03-修复记录.md`）；
③ **售后**：淘宝三类（仅退/退货退款/换货）；我们两类（无换货），且按"订单+SKU"而非子单。
④ **聚合层**：淘宝 = 结算页服务端试算 + 价格防篡改凭证；我们 = **home BFF** 聚合了购物车页（含可用券 + 实时库存）与商品详情/笔记/用户主页，但**无结算确认页聚合**、无试算凭证——价格在 `createOrder` 提交时服务端重算兜底（已核实 2026-10-11）。

### 1.3 缺口处置（对齐 §7 与 02 三档）

- **可补小件**：运费 / 分摊落库 / 物流对象化（3-5 天，高学习价值）
- **讲而不做**：店铺维度 / 优惠生态 / 拆单（换代级）
- **不做**：组合支付 / 预售 / 发票 / 客服

### 1.4 一句结论（面试口径）

> "我们'缺'的，都在**外围业务对象**（店铺/运费/物流/活动）；'难而对'的，都在**可靠性内核**（快照/事件/幂等/对账/补偿）——外围是业务定位问题，内核才是工程能力问题。"

## 二、一笔淘宝订单的全景（第 0 讲 A · 应然世界）

### 2.1 场景

双 11 晚，用户**阿真**抢了**三款商品、共 4 件**（两家店）：汉服「春山」299×1（A 店）、古风发簪 59×2（B 店）、马面裙 199×1（B 店）。

### 2.2 金额明细（下单第一步：616 → 496）

| 项 | 金额 | 说明 |
|---|---|---|
| 商品合计 | 616 | **跨店满减按商品金额计算（不含运费）** |
| 运费 | +8 | B 店首重 8 元；A 店包邮 |
| **订单总额** | **624** | |
| 跨店满减「每满 300 减 50」 | −100 | 616 满 600 → 2 档 ×50；平台活动、**跨店累计** |
| A 店铺券（满 200 减 20） | −20 | **只能用于 A 店商品** |
| 红包 | −8 | 用户持有，**有出资方** |
| **实付** | **496** | 624 − 128 |

⚠️ 三笔优惠各有**两个隐藏属性**：**归属**（哪些商品能用）+ **出资**（谁掏钱：平台还是商家）——"分摊/结算"两讲的全部复杂度从这里长出来。

### 2.3 时间线

| 时间 | 事件 | 系统动作 |
|---|---|---|
| 20:02:05 | 点"提交"，卡顿，**再点一次** | —— |
| 20:02:06 | 抢购高峰（汉服剩 3 件 / 500 人抢） | 锁库存、占券、生成 **1 个父单 + 2 个子单**；**关单线 = 20:17:05（15 分钟）** |
| 20:16:58 | 支付成功 **496**（**距关单线 7 秒**） | 支付单落账、回调订单 |
| 20:17:00 | app 卡顿，**回调再发一次** | —— |
| 次日 | A 店发货；B 店**拆 2 个包裹**（发簪/马面裙不同仓） | 3 个包裹 = 1 次交易 |
| 收货后 | 马面裙尺码不对 → **退货退款**；一支发簪瑕疵 → **仅退款** | 两张售后单，退款都按**分摊**从 496 往回算 |

### 2.4 本单出场的对象（应然世界全景）

| 对象 | 在本单里是什么 |
|---|---|
| 店铺 | A 店、B 店（交易的第一等公民） |
| **父订单** | 1 个：交易/支付维度（496 对应它） |
| **子订单** | 2 个：A 店、B 店——履约/售后/结算维度 |
| 明细行 | 4 行（含各行**分摊后的实际成交价**） |
| 订单快照 | 价格/地址/优惠的"下单当时版" |
| 支付单 | 1 个（496） |
| 优惠对象族 | 跨店满减、A 店铺券、红包——各有归属与出资方 |
| 运费 | B 店 8 元 |
| 物流单 / 包裹 | 3 个包裹（A 店 1 + B 店 2） |
| 售后单 | 2 张（退货退款 / 仅退款） |
| 结算单 | A、B 两家各一份（货款 − 佣金 − 退款扣回） |
| 发票 / 评价 / 通知 | 边缘但真实存在 |

### 2.5 多本账：496 要同时对上 8 本账

1. **用户账**：付了 496；该退多少（按分摊）
2. **行级分摊账**：马面裙 199 里，满减/红包各摊几块——退款与结算的地基
3. **店铺账**：A、B 各应收多少
4. **平台账**：满减 100、红包 8 谁出资（平台 vs 商家）
5. **支付账**：496 一笔进账 vs 退款分笔出账
6. **库存账**：4 件（3 个 SKU）预占→成交；马面裙退货回补、发簪仅退款不回补（货没回来）
7. **结算账**：平台↔商家对账（含退款扣回、佣金）
8. **物流账**：1 次交易 / 2 子单 / 3 包裹

### 2.6 四个结构性复杂度（后续讲次骨架）

1. **拆单**：一次支付 = 多份履约 → 父/子单双层模型（§3）
2. **分摊**：所有优惠摊到行——否则退款算不出、结算对不平（§4）
3. **双层状态机**：父单状态 = 子单状态的聚合（子单全完成→父单完成；部分子单退款→部分退）
4. **多边对账**：8 本账日终对齐——财务/大数据入口（§5）

### 2.7 八个雷（后续讲次索引）

双击提交 / 库存竞争 / 双回调 / 关单竞态（距线 7 秒）/ **拆单** / **分摊** / 多类型售后 / 双 11 峰值
