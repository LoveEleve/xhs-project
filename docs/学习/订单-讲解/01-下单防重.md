## 〇、先对齐名词：下单 ≠ 支付

**用户操作与系统动作是两回事**：

1. 选商品 → 结算页（确认订单）；
2. 点「**提交订单**」= **下单** → 系统创建订单（状态=待付款）+ 锁定库存 + 占用券 + 设置关单线（超时未付款自动关闭）；
3. 跳收银台 → 点「**支付**」= **付款** → 对**已存在的订单**发起支付（支付单必须挂在 orderId 上）；
4. 渠道回调 → 支付成功 → 订单状态推进（待付款 → 已付款）。

**关键**：支付永远发生在下单之后——没有订单，支付没有对象可挂。很多 App 把两步包装成一次点击（点「去支付」，后台先 createOrder 再跳收银台），但后端永远是两个动作、两个接口。

**防重对照**：

| 用户动作 | 系统接口 | 防重要防什么 | 在哪讲 |
|---|---|---|---|
| 双击「提交订单」 | `createOrder` | 不产生两个订单 | 本篇（下单防重） |
| 双击「支付」/ 渠道重复回调 | 发起支付 / 回调处理 | 不重复扣款、状态不乱 | 八个雷之③「双回调」（支付篇） |

**术语**：标准说法是"接口幂等 / 防重复提交"，落在下单接口上，效果是"订单唯一"。"订单防重"不是标准词。

## 一、场景：双击的代价

**场景**：结算页点"提交订单"，页面卡了一下，用户又点一次——两个创建订单请求几乎同时到达（间隔 300ms）。

不做防护的后果：

| 后果 | 说明 |
|---|---|
| 两笔订单 | 两个订单号；用户看到两个待付款单 |
| 双占库存 | 库存被预占两遍（都成功就可能超卖） |
| 双扣券 | 优惠券用两次 → **真金白银的资损** |
| 客服介入 | "为什么有两个订单" |

创建订单是所有接口里**最贵**的一次操作（占库存/占券/生成单据/触发事件）——所以它链路上的第一道关卡必须是防重。

## 二、为什么需要防重（应然）

- 天然易重：用户双击、客户端/网关超时重试、恶意重放；
- **不能靠前端**：按钮置灰只是体验优化，服务端必须自己防（"客户端保证"等于没有保证）；
- 应然做法：**幂等 token**——结算页时服务端下发一次性 token（绑定用户 + 本次结算内容），提交时校验并**一次性消费**，同一 token 再来直接拒。
- 本质：把"这次结算意图"唯一化，而不是"查库里有没有一样的订单"。

## 三、实然：xhs 的实现（两层防重 + 释放策略）

**第一层：bizIdentifier + SET NX（防"同一次提交的重放"——网络重试等）**

```java
// L142-148
// 幂等键带 userId：原实现不带 → 不同用户提交相同 bizIdentifier 会互相拒绝，且可被恶意抢占
String idempotentKey = IDEMPOTENT_KEY_PREFIX + userId + ":" + request.getBizIdentifier();
Boolean setResult = stringRedisTemplate.opsForValue()
        .setIfAbsent(idempotentKey, "1", 24, TimeUnit.HOURS);
if (Boolean.FALSE.equals(setResult)) {
    throw new BizException(ResultCode.IDEMPOTENT_REJECT, "请勿重复下单");
}
```

三个设计点：

1. **SET NX 原子占位**：谁先占到谁执行——一次 Redis 原子操作就是全部成本（对比"查库判重"：又慢又有并发漏洞）；
2. **键作用域 = userId + bizIdentifier**：`userId` 是后补的（原实现不带 → 跨用户互拒 + 可被恶意抢占）；
3. **24h TTL**：幂等 ≠ 永久，只需覆盖重复窗口；窗口外"再下一单"是正常业务。

**第二层：用户级创建锁（防"短时间多次提交"——双击且每次带不同 bizIdentifier 的场景）**

```java
// L150-158
String lockKey = CREATE_LOCK_PREFIX + userId;          // myxhs:order:create:lock:{userId}
String lockValue = UUID.randomUUID().toString();
Boolean lockResult = stringRedisTemplate.opsForValue()
        .setIfAbsent(lockKey, lockValue, 10, TimeUnit.SECONDS);
if (Boolean.FALSE.equals(lockResult)) {
    stringRedisTemplate.delete(idempotentKey);          // 关键：顺手释放刚占的幂等键
    throw new BizException(ResultCode.LOCK_ACQUIRE_FAIL, "操作过于频繁，请稍后重试");
}
```

两层分工：**幂等键防"同一次提交的重放"；用户锁防"短时间多次提交"**。

**精华：幂等键释放策略 = 与"真实后果"对齐**

```java
// javadoc L132-134 原文：
// - 本地事务提交前失败 → 释放幂等键（允许重试）
// - 本地事务提交后     → 不释放幂等键（订单已创建，后续步骤失败不影响）
```

半消息发送异常时的判例（L263-274）：

```java
if (sendResult.getSendStatus() != SendStatus.SEND_OK) {
    // 已提交 → 保留幂等键按成功返回（否则"订单已创建但接口报失败 → 用户重试生成重复订单"）
    if (context.getOrderId() == null) {
        stringRedisTemplate.delete(idempotentKey);      // 未提交 → 真失败，释放
        throw new BizException(ResultCode.INTERNAL_ERROR, "下单失败: 消息发送异常");
    }
    // orderId 非空 → 按成功处理
}
```

一句话：**"报错"≠"没下单"——幂等的边界要与"真实后果"对齐，而不是与"代码执行到哪"对齐。**（"半消息"是什么，到 03-落库 篇展开。）

## 四、坑清单

1. 幂等键作用域缺 userId（跨用户互拒 + 可被抢占）——已修复的教训；
2. 锁抢失败必须**顺手删掉刚占的幂等键**，否则用户"稍后重试"被自己 24h 自锁（已修复）；
3. "失败"必须分"有没有产生后果"，不能一律删/一律留；
4. 两个不同 bizIdentifier 的重复，幂等键挡不住——靠锁/业务规则；
5. 幂等键只是缓存层；最终兜底靠 DB 唯一约束/对账（留到"可靠性"篇展开）。

## 五、背走一句

> **幂等 = 唯一标识 + 一次性的原子占位 + 与"真实后果"对齐的释放策略。**
