## 一、场景一句话

用户点了"提交订单"——系统**不只写一张订单表**：它还要让库存预占、让券核销、让后续服务知道"这单来了"。要保证两件事：

1. **自己的几张表**：要么都成、要么都不成（订单 + 明细 + …）；
2. **通知下游**：要么一定送到、要么绝不"假装送到"。

## 二、把问题摆清楚：两类事故

落库到底包含几件事：

- **写自己的库**：订单主表 1 行 + 明细 N 行（+ xhs 还有一条"待发送消息"记录）——**同一个本地事务**能管住；
- **通知别人**：库存要预扣、券要核销、后续还有通知/索引……——**跨服务**，本地事务管不了。

两类事故（后续讨论的靶子）：

| 事故 | 现场 | 后果 |
|---|---|---|
| **A 类：建了没人知道** | 订单建好了，下游没收到通知 | 订单"悬空"：没人扣库存、没人核销券 |
| **B 类：知道了没建** | 下游做了（货扣了/券没了），订单没建出来 | 用户手上没有订单，账却动了 |

## 三、笨办法为什么不行

- **建单后同步依次调**（调库存 → 调券 → 调通知）：中间任何一步失败 → A 类事故；下游一慢，用户就干等；无脑重试还可能重复扣（B 类反过来）。
- **先调下游、后建单**：中途失败 → B 类事故。
- 根本矛盾一句话：**这两件事分属两个系统，没有"共同的本地事务"。**

## 四、解法 A：本地消息表（Outbox）

思路：**把"跨系统的事"折叠成"本地的事"**。

1. 在"写订单"的**同一个本地事务**里，顺手写一行"待发送：ORDER_CREATED"到**本地消息表**；
2. 另有一个后台程序（补发 Job）不停地把"未发送"的记录发给 MQ，发成功标记"已发送"。

效果："订单"和"消息"**同生共死**（同一个事务），剩下的只是"把消息送出去"这个纯工程问题（重试、补发）。

## 五、解法 B：事务消息（半消息 + 回查）——顺便揭晓 01 篇的谜底

流程（说人话版）：

1. 消息先发给 MQ，但**"藏着"**（半消息，消费者看不见）；
2. 执行本地事务（建订单）；
3. 成功 → 让 MQ"放行"（commit，消费者这才可见）；失败 → "扔掉"（rollback）；
4. 如果生产者挂了、MQ **收不到第 3 步的答复** → MQ **回查**：主动问生产者"那笔到底成没成？"，生产者查自己的库（有没有这单）再回答。

**这就是 `01-下单防重` 里那个"半消息发送异常"的谜底**：那段代码处理的正是边角——"发送结果异常"≠"本地事务成没成"，必须查本地事实（orderId）才能定论。

## 六、xhs 的选择：主 + 备

- **事务消息为主**（回查方法在：`OrderTransactionListener.checkLocalTransaction`）；
- **本地消息表兜底**：投递失败有补发 Job（30s 周期）；事务消息 COMMIT 后立即打标（`markSuccessByTransactionId`），补发 Job 只补未打标的，避免"**双投**"；
- **下游怎么被通知**：库存服务消费订单事务消息 → 做预扣（幂等 + 重试 5 次 + 死信队列）——预扣细节留到《库存-讲解》；
- 顺带一个不对称（值得记）：xhs 的**券核销是同步** Feign（因为核销失败要立刻取消订单），**库存预扣是异步**消息（失败可重试/补偿）——为什么这么分，见《库存-讲解》/06 篇。

一句话总结 xhs 的分层哲学：**每一层都假设上一层会漏**（事务消息怕漏 → 本地消息表兜；消息可能重 → 消费端幂等兜）。

## 七、引申讨论（面试深水）

1. **为什么不用分布式事务（Seata/2PC）？** 重、慢、锁太久；"订单 + 通知下游"这类场景，"可靠消息 + 消费端幂等"是主流答案（最终一致）。
2. **全系统统一哲学**："至少一次投递 + 消费端幂等"——消息允许重复，消费方必须能认出来（01 篇学的防重，在这里成了消费端标配）。
3. **这套机制的边界**：它保证"消息一定送出去"，**不保证"下游一定处理成功"**（比如库存真不够）——下游自己的失败靠自己的机制（失败补偿/反向消息/状态机），这就是《库存-讲解》的内容。
4. **顺带回答"下单为什么要快"**：建单 + 消息写本地事务（快），库存预扣等交给消息（异步）——**用户侧快 与 系统侧可靠，由这套机制同时拿到**。

## 八、掌握标准 + 背走一句

1. 落库的本地部分 = **一个本地事务**写"订单 + 明细 + 待发消息"；
2. 跨服务通知 = 可靠消息（本地消息表 / 事务消息半消息+回查），**不在"建单"和"通知"之间留缝隙**；
3. 两组词：**至少一次投递 + 消费端幂等**；xhs = **事务消息为主、本地消息表兜底**。

> **订单落库不怕慢、不怕重，就怕"建了没人知道"和"知道了没建"——把"建单"和"要发的消息"塞进同一个本地事务，再让 MQ 可靠地送出去。**
