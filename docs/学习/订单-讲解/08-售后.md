# 08 · 售后线（行级）

> **定位**：订单履约之后的**逆向流程**——售后申请、商家审核、退款执行、库存回补。售后是**独立聚合**：订单状态机装不下的"部分退款/多次退款/多类型退款"都落在它身上。
> **修订（2026-10-25）**：售后已从"订单+SKU"下沉到**行级 `itemId`**；支付退款已改为同步 + `out_refund_no` 幂等；status=2 全额退款已收口。
> **素材**：`AftersaleService`、`Aftersale`、`AftersaleRepository`、`AftersaleRecoveryJob`、`OrderService.onRefundSuccess`；C-003。
> **系列导航**：`00` → `01` → `02` → `03` → `03A` → `03B` → `04` → `04A` → `04B` → 05-库存预占（跳过） → `06-支付联动` → `07-履约线` → **08-售后线** → `09-拆单` → `10-分摊` → `11-对账` → `12-收口`。

---

## 一、先看"售后"在干什么（例子先行）

小明买 3 行、共 4 件（实付 496，含优惠分摊）：马面裙（199×1）尺码不对 → **退货退款**；一支发簪（59×2 中的 1 支）瑕疵 → **仅退款**。

两张售后单，锚点都是**订单行 `itemId`**，退款都按**行分摊后的实付**算——不是按标价退。

**题眼**：正向订单是一条线（0→1→2→3），逆向售后是**可多次、可部分、可不同类型**的：

- 一单多行 → 每行可各自发起售后（粒度 = **行 `itemId`**）；
- 每张售后单有自己的状态机；
- **部分退款不能动订单主状态**（订单还在履约/已完成，只退了一行的钱）。

订单只有一个 `status`，装不下 N 张并行售后单——所以售后必须**独立聚合 + 独立状态机**。

## 二、当前模型

### 2.1 售后单

| 字段 | 说明 |
|---|---|
| `itemId` | **行级锚点**（`t_order_item.id`） |
| `skuId` | 冗余，便于按 SKU 汇总/回补 |
| `type` | 1=仅退款，2=退货退款（无换货） |
| `status` | 0 待审核 / 1 已同意（历史死状态）/ 2 已拒绝 / 3 退款中 / 4 已完成 / 5 已取消 / 6 退款失败 |
| `applyQuantity` | 本次申请数量 |
| `itemAmount` | 本次申请对应的商品金额（未扣优惠） |
| `discountShare` | **本次申请**对应的分摊优惠 |
| `refundAmount` | 本次应退 = itemAmount − discountShare |
| `restockStatus` | 0 待回补 / 1 已回补 |
| `refundNo` | 支付域退款单号（归属锚点） |
| `returnWaybill` | 退货物流单号（预留；当前流程未使用） |

- 唯一键：**`(item_id, type)`**——同一行同类型只允许一张活动单；
- 售后表在公共库（`my_xhs_order`），不走分片；量级小是当前取舍；
- `Aftersale` 类注释仍写"同订单同 SKU 同类型"，与 `(item_id,type)` 不一致（注释漂移）。

### 2.2 状态机（实际生效）

```
0 待审核 ──同意──→ 3 退款中 ──成功──→ 4 已完成
   │                └──失败──→ 6 退款失败 ──重试──→ 3
   ├─驳回──────→ 2 已拒绝（可重新申请）
   └─用户撤销──→ 5 已取消（可重新申请）
```

- `STATUS_APPROVED=1` 是历史死状态：审核通过直接 0→3，不经过 1；
- `AftersaleService` 类注释仍写"0→1/2→3"，与代码不一致（注释漂移）。

## 三、申请：行级资格 + 三道金额闸门

### 3.1 资格守卫

```java
if (order.getStatus() < 1 || order.getStatus() > 3) reject;   // 只有已付款/已发货/已完成可售后
if (type == RETURN_REFUND && order.getStatus() == 1) reject;  // 未发货只能仅退款
```

- 状态 1（已付款未发货）：只能"仅退款"；
- 状态 2/3：仅退款/退货退款都可；
- 申请入参仍是 `skuId`，服务端在订单行中按 SKU 定位 `itemId`（下单已禁止同 SKU 多行，所以唯一）。

### 3.2 行级权益

```java
// 分摊以落库 discount_share 为准；存量 null 才回退重算
BigDecimal share = item.getDiscountShare();
BigDecimal refundableTotal = refundableAmount(item, share, item.getQuantity());
```

- 行整件可退 = 行金额 − 行分摊；
- 部分数量：按比例向下取整；最后一次退满补差；
- 售后单落的是**本次申请对应份额**，不是整行份额。

### 3.3 三道金额闸门

```java
// ① 本次可退 > 0
if (refundable.signum() <= 0) reject;

// ② 同 SKU 跨类型累计 ≤ 整件可退（退款中/已完成占用）
if (occupiedAmount + refundable > refundableTotal) reject;

// ③ 订单累计退款 ≤ 订单实付
if (sumRefundedAmount(orderId) + refundable > payAmount) reject;
```

- ② 防"仅退款退一部分 + 退货退款再退整件"的超退；
- ③ 防"每行都按整单金额退"式的超退；
- 审核时再复核一次（订单状态/额度可能已被并发单改变）。

### 3.4 申请幂等

- 唯一键 `(item_id, type)`；
- 已拒绝/已取消/退款失败 → 可重新申请（复用原单，字段覆盖，状态回 0）；
- 已完成 → 同类型不再受理（同 SKU 同类型一次结清）。

## 四、审核与退款执行

### 4.1 审核

```java
if (!approve) { 0→2; return; }
// 批准前复核订单状态 1/2/3、SKU/订单额度
if (order 不合法 || 额度不足) { 自动驳回 0→2; return; }
0→3 (REFUNDING); executeRefund();
```

- 审批与发起退款合并成一步（0→3）；
- 状态 1（已同意）不参与流转。

### 4.2 退款：同步 + 出金幂等

```java
R<String> resp = paymentFeignClient.refundByOrder(
    new RefundByOrderRequest(orderId, refundAmount, reason, type,
                             aftersaleNo),  // outRefundNo = 售后单号
    userId);
```

- C-003 后支付域退款**同步返回**，不再走退款回调链；
- `out_refund_no = aftersaleNo`：重试/补偿同键，支付域返回既有退款单，防重复出金；
- 成功 → `restoreStock` → 3→4（记录 refundNo）；
- 失败 → 3→6（退款失败），由恢复任务/人工重试；
- `refund-fail` 回调当前仍是**空实现（仅日志）**；退款失败状态由售后单/支付域表达，不改订单主状态。

### 4.3 库存回补

```java
inventoryFeignClient.refundRestore(orderId, userId, skuId, applyQuantity);
```

- 库存域按 `(orderId, skuId)` 累计目标幂等，只补正增量；
- 成功后 `restockStatus=1`；失败保持 0，由恢复任务重试；
- 退货退款（type=2）当前在**退款受理成功后**回补，而不是"退货入库质检后"——简化口径，代码注释已说明；
- 全额退款链路另有 `restoreStockOnRefund`，与售后回补靠库存累计幂等吸收重复。

### 4.4 恢复任务

`AftersaleRecoveryJob`（每 10 分钟）兜三类异常：

| 异常 | 处置 |
|---|---|
| 退款中卡死（>5min） | 先核对支付域退款单事实：已成功→补回补+置完成；仍有处理中→等待；无记录→转失败 |
| 退款失败 | 退避 10min、最多 3 次；重试前先核对支付域，防二次退款 |
| 已完成未回补 | 重试回补并标记 |

- 所有流转仍是条件更新；与人工审核/重试并发只有一个赢家。

## 五、与订单状态机的咬合

| 场景 | 支付侧 | 订单主状态 | 说明 |
|---|---|---|---|
| **部分退款** | 不通知订单 | 不动（1/2/3） | 只退一行，履约/完成态不变 |
| **全额退款（1/2/3）** | Feign `refund-success` + MQ 兜底 | **1/2/3→5** | 确认预扣 + 回补 + 退券 + 快照 + 通知 |
| 售后单完成 | 不改订单 | 保持 | 由售后单表达 |

- **status=2 的全额退款已收口**：`onRefundSuccess` 现在允许 1/2/3（旧 08 的"status=2 被拒"已修）；
- 部分退款不触发父/子 5；全退才父+全子 5；
- 全额退款与售后单可能叠加：支付域只在"累计退款=支付额"时通知订单，订单侧不做金额推断。

## 六、旧账与边界

### 6.1 售后退补 `max(a,b)`（仍未修）

- 售后侧传"本次数量"；库存侧按"累计目标"解析；
- 同 SKU 两次售后：type1 退 1、type2 退 2 → 累计目标 max(1,2)=2，而实际应退 3 → 漏 1；
- 修复方向（不直接改）：
  - 订单侧传"已完成 + 本次"累计；
  - 库存侧改增量语义 + 订单侧幂等键；
  - restore 加 per-(order,sku) 锁内重算 target。
- 直接改"传累计目标"会在并发售后时多补（超卖方向更危险），方案定稿前不动。

### 6.2 退货流程简化

- 无退货物流/验货/质检/入库环节；`returnWaybill` 字段预留未用；
- type=2 在退款受理后回补，不是"货退回后"；
- 无换货类型。

### 6.3 时效缺失

- 无售后入口时限、审核时限、寄回时限；
- 无自动审核/自动关闭；
- 依赖用户/商家主动操作 + 恢复任务。

### 6.4 其他

- 售后表公共库不分片：量级小可接受，规模化需按 `user_id` 分片；
- 申请 API 仍以 `skuId` 定位行（未直接传 `itemId`）：当前下单禁止同 SKU 多行；历史/迁移数据若有重复 SKU，行级定位会取第一行，存在歧义。
- `AftersaleService`/`Aftersale` 类注释与行级/状态机实现有漂移；
- 无商家 sellerId 归属校验（与履约同边界）。

## 八、十二个坑

1. **售后挂订单+SKU**：拆单后必须挂 `itemId`；否则多行同 SKU/部分退算不清。
2. **唯一键用 (order_id,sku_id,type)**：当前是 `(item_id,type)`；旧注释/旧文档会误导。
3. **部分退款改订单 5**：只有全退才 5；部分退不改主状态。
4. **按标价退**：必须按行金额 − 行分摊；否则多退。
5. **部分数量向上取整**：累计超退；向下取整，退满补差。
6. **只做 SKU 上限**：还要订单累计 ≤ 实付；否则多行叠加超退。
7. **审核不复核**：申请后订单可能已取消/全退；批准前再查状态/额度。
8. **退款不用 out 键**：重试重复出金；`out_refund_no=aftersaleNo`。
9. **退款失败盲目重试**：先查支付域事实，防二次退款。
10. **退货退款立即回补**：真实应在退货入库后；当前简化，需明确口径。
11. **`max(a,b)` 当已修**：金额对了，数量回补仍可能少补。
12. **`refund-fail` 当已处理**：当前空实现；退款失败靠售后/支付域。

## 九、值不值得深挖 / 一句话

- **值得**：行级售后、三道金额闸门、同步退款 + out 键、恢复任务先查事实、`max(a,b)` 并发风险——售后是订单域最复杂的逆向流程；
- **一句话带过**：状态常量、字段；
- **一句话**：**售后 = 行级独立聚合；申请三道闸门、审核复核、退款同步 + out 键、库存累计回补；部分退不动主状态，全退才父+全子 5。**
- 分摊见 **10**；退款/支付见 **06**；收口见 **12**。

**面试口径**："售后挂订单行 itemId，唯一键 (item_id,type)；申请看订单 1/2/3、按落库分摊算应退，过三道闸门（本次>0、同 SKU 累计、订单累计≤实付）；审核再复核；退款调支付域 refund-by-order，out_refund_no=售后单号，同步返回；成功后回补库存并置完成，失败 3→6 由恢复任务先查支付事实再重试。部分退款不动订单主状态，全退才 1/2/3→5；status=2 已收口。剩余旧账是 max(a,b) 数量漏补和退货流程简化。"
