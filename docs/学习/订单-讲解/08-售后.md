# 订单模块讲解系列 · 08 · 售后线

> **定位**：订单履约之后的**逆向流程**——售后申请、商家审核、退款执行、库存回补。售后是**独立聚合**：订单状态机装不下的"部分退款 / 多次退款 / 多类型退款"，全部落在它身上。
> **素材**：xhs-project 实况（`AftersaleService` + 支付域退款契约 + 库存回补语义）+ 应然对照（淘宝三类售后）。
> **系列导航**：`00` → `01` → `02` → `03` → `03A` → `03B` → `04` → `04A` → `04B` → 05-库存预占（跳过：见《库存-讲解》） → `06-支付联动` → `07-履约线` → **08-售后线** → **09-拆单** → **10-分摊** → **11-对账** → **12-收口**（完）
> 建立：2026-10-16。
> 关联：07 §2.3（status=2 悬挂边界在此收口）；06 §一（退款发起契约 `refund-by-order`）；00 §1.2-③（售后：两类 vs 淘宝三类）；《库存-讲解》07/10（回补语义）。

## 一、先看"售后"在干什么（例子先行）

小明买 3 款商品、共 4 件（实付 496，含优惠分摊）。收货后：马面裙（199）尺码不对 → **退货退款**；一支发簪（59×2 里的 1 支）瑕疵 → **仅退款**。两张售后单，退款都按**分摊后的实付**往回算——不是按标价退。

**题眼**：正向订单是"一次性"的（0→1→2→3 一条线走完），逆向售后是**可多次、可部分、可不同类型**的：

- 一单多品 → 每件商品各自发起售后（粒度 = **订单+SKU**）；
- 每张售后单有自己的生命周期（待审核 → … → 完成/拒绝/取消）；
- 部分退款**不能**动订单状态（订单还在履约/已完成，只是退了一件的钱）。

订单只有一个 `status` 字段，装不下"N 张并行售后单各自走到哪了"——所以售后必须**独立聚合 + 独立状态机**（07 §一那个"两套状态机"的由来）。

## 二、应然 vs 实然

| 维度 | 淘宝（应然） | xhs（实然） |
|---|---|---|
| 类型 | 三类：仅退款 / 退货退款 / 换货 | 两类：仅退款(1) / 退货退款(2)，**无换货** |
| 粒度 | 子订单维度 | 订单+SKU（无拆单，见 09） |
| 时效 | 入口窗口 / 审核时限 / 寄回时限（都从确认收货起算） | **全缺**：入口无时效、审核无超时自动判（连锁 07 的时钟缺口） |
| 退货环节 | 退货物流 → 验货 → 质检 → 入库 → 退款 | **简化**：审核通过即退款+回补，无退货物流环节 |
| 状态展示 | 售后状态叠加在订单上 | 两套状态机独立（前端未合成展示——无售后角标，缺口） |

`returnWaybill`（退货物流单号）字段在实体里**预留未用**——真实退货流程被简化后留下的占位。

## 三、实然：售后单状态机与三个动作

### 3.1 状态机（实际生效的流转）

```
0 待审核 ──同意──→ 3 退款中 ──成功──→ 4 已完成
   │                └──失败──→ 6 退款失败 ──重试──→ 3
   ├─驳回──────→ 2 已拒绝（可重新申请）
   └─用户撤销──→ 5 已取消（可重新申请）
```

- 注：实体里 `STATUS_APPROVED=1`（"已同意"）**是预留常量，全仓无流转到它**——审核通过直接 APPLIED→REFUNDING（审批与发起退款合并成一步）；
- 状态常量：`Aftersale.java:22-35`；类型：`TYPE_REFUND_ONLY=1` / `TYPE_RETURN_REFUND=2`。

### 3.2 申请（用户侧）：订单状态守卫 + 三道金额闸门

```java
// AftersaleService.apply —— 资格守卫
if (order.getStatus() == null || order.getStatus() < 1 || order.getStatus() > 3) {
    throw new BizException(ResultCode.ORDER_STATUS_ERROR, "当前订单状态不支持申请售后");
}
if (type == Aftersale.TYPE_RETURN_REFUND && order.getStatus() == 1) {
    throw new BizException(ResultCode.ORDER_STATUS_ERROR, "未发货订单请选择仅退款");
}
```

只有 1/2/3 可申请；状态 1（未发货）只能"仅退款"——退货退款的前提是"货在买家手里"。

**三道金额闸门（防超退）**：

```java
// 闸门一：可退金额必须为正（单品可退 = 明细金额 − 分摊优惠，按订单快照重算；为 0 则拒）
SkuEntitlement entitlement = entitlement(order, items, target);
BigDecimal refundable = resolveRefundable(entitlement, quantity);
if (refundable.signum() <= 0) {
    throw new BizException(ResultCode.PARAM_INVALID, "该商品可退金额为 0（可能已退完）");
}
// 闸门二：同 SKU 跨类型累计 ≤ 整件可退（occupied = 退款中/已完成占用）
if (entitlement.occupiedAmount().add(refundable).compareTo(entitlement.refundableTotal()) > 0) {
    throw new BizException(ResultCode.PARAM_INVALID, "该商品累计退款金额超过可退上限");
}
// 闸门三：订单累计 ≤ 实付（防"每件都按整单金额退"式的超退）
BigDecimal occupied = aftersaleRepository.sumRefundedAmount(order.getId());
if (occupied.add(refundable).compareTo(payAmount) > 0) {
    throw new BizException(ResultCode.PARAM_INVALID, "累计退款金额将超过订单实付金额");
}
```

金额口径的细节（`resolveRefundable`）：未退满 → 按数量比例**向下取整**（永不超退）；本次退满 → 用"整件可退 − 已退金额"**补齐差额**（多次部分退款累计严格等于整件可退，不因取整让用户少拿几分）。

**申请幂等**：唯一键 `(order_id, sku_id, type)`——同订单+SKU+同类型只允许一张活动单；`已拒绝/已取消/退款失败`三种状态可**重新申请**（复用原单，业务字段整体覆盖，状态回到待审核）；`已完成`后同类型**不再受理**（同 SKU 同类型一次结清——想再退只能换类型，或首次申请足量）。

### 3.3 审核（商家动作）：批准前复核

```java
// AftersaleService.audit —— 批准前复核订单状态
if (order == null || order.getStatus() == null || order.getStatus() < 1 || order.getStatus() > 3) {
    // 订单已被取消/已全额退款 → 售后自动驳回（避免在"钱已退过"的单上重复动作）
    aftersaleRepository.updateOnAudit(aftersale.getId(), APPLIED, REJECTED, "自动驳回: " + reason);
    return aftersaleRepository.findByNo(aftersaleNo);
}
// 额度复核：并发下同一 SKU 可能同时存在"仅退款/退货退款"两张待审单，
// 申请时都通过了校验；审核时以最新占用为准再判一次，超限自动驳回
```

两级门的差异：**申请守卫管"能不能申请"；审核守卫管"批准时事实是否还成立"**（订单状态可能已变、额度可能被并发单占用）。这和履约的"发货=商家动作"同一性质——**关键业务动作前，把事实再核对一遍**。

### 3.4 退款执行：钱与货两条链

```
audit 同意 → executeRefund
   ├─ ① 钱：支付域 refundByOrder(orderId, 金额, 原因, 类型)
   │        └─ 返回 refundNo（未回传则回查"认领"，防同额误认）
   │        └─ 全额退款时：支付域反向通知订单（Feign + MQ 兜底，见 §四）
   ├─ ② 货：库存域 refundRestore(orderId, skuId, 本次数量)
   └─ ③ 售后单 → 4 已完成（记录 refundNo）
   失败 → 6 退款失败
```

- **支付域契约**（`PaymentService.refundByOrder`，06 §一交互面）：上游只给 orderId；支付域内部做分布式锁 + 归属校验 + 可退金额上限（累计退款 ≤ 支付金额）；mock 模式**同步**完成退款，真渠道异步回调；
- **库存回补**（`InventoryService.refundRestore`）是"**累计正增量**"语义——幂等键记"已受理的应回补目标"，只补正增量：

```java
String idemKey = "inventory:refund:" + orderId + ":" + skuId;  // 记"已受理的应回补目标"
delta = lua(idemKey, quantity);   // delta = 本次请求量 − 已记目标（并更新目标）
if (delta <= 0) return;           // 重复调用 → 幂等跳过
restore(delta);                   // 只回补正增量
```

- **两条回补路径叠加**：全额退款时，订单侧 `restoreStockOnRefund`（按整件数量）与售后侧 `restoreStock`（按本次数量）都会调 refundRestore——靠上述累计幂等兜住重复（"与全额退款链路重复调用安全"）。

**恢复任务**（`recoverStuckAndRetry`，XXL-Job）兜三类异常单：

| 异常 | 处置 |
|---|---|
| 退款中卡死（>5min） | **先核对支付域事实**（退款单列表，金额/类型/时间窗匹配）——已成功→补回补+置完成；仍有处理中→保持等待；都没有→转退款失败。**不盲目重试**（覆盖"Feign 超时但支付域已成功"的未知结果） |
| 退款失败 | 退避 10 分钟、最多自动重试 3 次；重试前同样先核对支付域（防二次退款），支付域可退金额上限是最终防线 |
| 已完成未回补 | 重试回补并标记（覆盖"跨服务调用失败、库存域补偿表无记录"的盲区） |

## 四、与订单状态机的咬合（关键边界）

| 场景 | 支付侧行为 | 订单状态 | 说明 |
|---|---|---|---|
| **部分退款** | **不通知订单**（"部分退款，不通知订单状态变更"） | 不动（保持 2/3） | 订单还在履约/已完成，只退了一件的钱 |
| **全额退款**（订单在 1/3） | Feign `notifyRefundSuccess` + MQ 兜底 | 1/3 → **5 已退款** | 收敛动作：确认预扣 + 回补库存 + 退券 + 快照 + 通知 |
| **全额退款**（订单在 **2**） | 同上 | **被拒绝**（`return false`，停在 2） | 07 §2.3 留的缺口，见 §5.2 |

```java
// OrderService.onRefundSuccess —— 全额退款收敛的收口守卫
if (order.getStatus() != 1 && order.getStatus() != 3) {
    // 5 幂等返回 true；0(待付款)/2(已发货)/4(已取消) 拒绝
    return order.getStatus() == 5;
}
```

**边界语义**：部分退款归售后状态机管（订单不动）；**只有"累计退款 = 实付"的全额退款才触发订单收敛**——这就是"两个状态机各管各的、在'全退'这一点咬合"的设计。

## 五、旧账：两个待设计的问题

### 5.1 售后退补 `max(a,b)` 漏补（跨模块缺陷，方案定稿前不动）

- **机制**：库存侧按"**累计目标**"语义（幂等键记应回补目标，只补正增量），但售后侧传的是"**本次量**"；
- **例子**：SKU 共 3 件——先仅退 1 件（目标 1，补 1），再退货退 2 件（目标 2，补 1）→ **累计回补 2 ≠ 退款 3，漏 1 件**；
- **一般结论**：累计回补 = `max(各次请求量)`，而不是 sum；
- **为什么不能直觉修**：订单侧改传"累计目标"后，**并发售后**（两张单同时在退）会各算各的目标 → **多补**（超卖方向，比"少补"更危险）。候选方案（03-修复记录 §二）：a) 订单侧传"已完成+本次"累计 + 库存侧配合；b) 库存侧改增量语义 + 订单侧幂等键；c) restore 加 per-(order,sku) 锁内重算 target。

### 5.2 status=2（已发货）的全额退款不收敛

- **场景**：已发货订单（2）走售后全额退款 → 支付侧退钱成功 → 通知订单 → `onRefundSuccess` 只收 1/3 → **钱退了，订单停在 2**；
- **收口方向（待定）**：放宽守卫到 2（承认"已发货全退"是合法收敛）；或由售后完成来驱动订单收敛（售后侧调订单收敛接口）。——两条路各有语义代价，08 讨论后定。

## 掌握标准 + 背走一句

1. 售后是**独立聚合**（独立状态机 + 类型 + 订单+SKU 粒度）——因为订单状态机装不下"可多次、可部分、可多类型"的逆向流程；
2. **三道金额闸门**（可退>0 / SKU 累计 / 订单累计 ≤ 实付）+ **两级门**（申请守卫、审核复核）；
3. 执行链 = **钱**（支付域退款，全退时反向通知订单）+ **货**（库存累计幂等回补）+ 恢复任务（核对事实，不盲目重试）；
4. 咬合边界：**部分退款不动订单；全额退款才收敛到 5**；status=2 的全退目前不收敛（旧账）；
5. 旧账：售后退补 `max(a,b)` 漏补——修复有并发"多补"风险，方案定稿前不动。

> **正向订单一条线（0→1→2→3），逆向售后一张网（可多次、可部分、可多类型）；两个状态机 + 钱按分摊、货按回补两本账对齐，才是售后真正的难点。**
