## 一、"下单成功"的语义：受理 ≠ 就绪

| 设计 | "下单成功"的承诺 |
|---|---|
| 同步 | **强承诺**：库存已扣、券已核销、订单已落库——一切就绪，只等支付 |
| 异步 | **弱承诺**：订单已落库 + 资源占用**已可靠发起**——要么占用成功，要么订单被取消；**不允许"订单有效但资源没占"的终态** |

异步设计要保证的不是"支付那一刻库存已扣好"，而是"**最终不会出现『能支付但库存没占住』的坏终态**"。这个保证不来自状态机本身，来自三件套（§四）。

## 二、支付前如何感知异步结果：**订单状态 = 聚合视图**

时间线例子（预扣失败场景）：

```
12:00:00.000  用户下单 → 订单落库成功 → 返回"下单成功"（status=0）
12:00:00.050  库存消费者预扣失败 → 发 INVENTORY_FAILED_TOPIC（库存服务不改订单！）
12:00:00.060  订单域收口：handleInventoryFailure → terminateOrder → status 0→4 + 通知用户
12:00:05      用户点"去支付" → 支付前回查 getOrderStatus → status=4 → 拒绝：
              "订单当前状态不允许支付"（钱根本不会扣）
```

所以**用户不需要查询"库存预扣成功了吗"——订单状态就是那个答案**。支付前回查只校验订单状态（+金额），足以 gate 掉"资源没占住"的订单（前提：收口机制保证"预扣失败 ⇒ 订单必被终结"）。

**但聚合视图有盲区**："预扣**进行中**"不体现在订单状态里（仍是 0、支付入口开放）——见 §七。

## 三、谁扭转订单状态：**单一写入者原则**

- **库存服务**：只改自己的库存数据 + **失败时上报事件**（成功不上报——fail-only，避免事件风暴）；
- **券服务**：同理；
- **订单域是订单状态的唯一写入者**：订阅失败事件 → 收口（terminateOrder）→ 改自己的状态。

xhs 实况链路：

```java
// ① 库存侧：预扣失败（重试耗尽）→ 发 INVENTORY_FAILED_TOPIC（不改订单）
// ② 订单侧消费者：
orderService.handleInventoryFailure(orderId, mapping.getUserId(), reason, skuId);
//    → status==0 → terminateOrder(orderId, userId, TerminationReason.INVENTORY_FAILED, "SYSTEM")
//    → 订单域自己完成 0→4 + 写终结事件（ORDER_TERMINATION_TOPIC）
// ③ 终结事件被库存/券/通知订阅 → 各自善后：
//    库存：释放已占用的其他 SKU + 写终结墓碑；券：退券；通知：告知用户
```

为什么必须这样：如果允许库存服务**直接改订单状态**（分布式写），订单状态机会被多方写入——竞态无法用 CAS 收口、无法审计、职责混乱。**各域上报结果，订单域裁决，裁决后再通知各域善后**。

## 四、状态机为什么不够：**三件套**

1. **可靠上报**：失败必须变成事件（MQ 重试 + 死信 + 本地消息表兜底）；
2. **收口动作**：订单域对每种失败有**确定的**终结动作（04B 的 `terminateOrder`：五条路径收敛到唯一入口）；
3. **兜底**：事件彻底丢了也有保障——**超时关单**（30min 无差别终结未付款订单）+ **对账**。

三件套齐了，"异步"才成立；缺任何一件都有洞。

## 五、资源的"查"与"扣"：为什么必须两段

**"查"是快照，"扣"是裁决；快照会过期，裁决才作数。**

- 同步段（下单步骤 3.5）：`queryStock` → `getStock` ——**纯只读**（`GET inventory:{skuId}:total`），不占用任何库存；
- 异步段（事务消息 → 库存消费者）：`preDeduct` → Lua ——**原子扣减**（`DECRBY total/bucket` + 写预扣记录）。

例子（库存剩 1 件，A/B 同时下单）：**查**——两人都读到 `available=1`，都通过前置校验；**扣**——Lua 原子执行，只有一个 `DECRBY` 成功，另一个返回库存不足。

| 方案 | 结果 |
|---|---|
| 只查不扣 | **超卖**（快照人人可见，无人裁决） |
| 只扣不查 | 库存不足的用户也经历"下单成功→立刻被取消"（垃圾单 + 体验差） |
| **查 + 扣**（现状） | 查：多数库存不足在**下单入口**拒绝；扣：**权威占用**（竞态由失败收口兜底） |

**为什么"扣"不放同步流程**（放同步也能做，但有代价）：① 下单请求强依赖库存服务（可用性耦合）；② 下单 RT +1 次跨服务写；③ 本地事务 + 远程写不能同事务，跨系统一致性问题照旧要处理。本项目的选择：**同步查（快速失败）+ 异步扣（事务消息保证"创建成功 ⇒ 预扣发生，否则收口"）**。

## 六、同步 vs 异步：心智模型 + 按失败语义逐资源选择

| 维度 | 同步 | 异步（事务消息/Outbox + 收口） |
|---|---|---|
| 下单成功含义 | 资源已就绪 | 资源占用已受理（成功或被收口） |
| 失败的表达方式 | 下单接口**当场报错** | **订单被取消**（状态 + 通知） |
| 用户支付前感知 | 无需感知 | 通过**订单状态**感知（终结 → 支付入口失效） |
| 可用性 | 绑定所有依赖 | 只绑定订单本地事务 |
| 一致性 | 请求内闭环（跨系统问题仍在） | 最终一致（可靠投递 + 收口 + 兜底） |
| 复杂度 | 低 | 高（幂等/事件/收口/兜底都要有） |

**xhs 的真实形态是混合的**（不是全局一刀切）：

- **券 → 同步**：失败晚暴露兜不住（同一张券可重复用 = 资损），必须请求内闭环 → 下单成功 = 券已核销（强承诺）；
- **库存 → 同步查 + 异步扣**：失败晚暴露兜得住（订单取消即可，钱货无损）→ 下单成功 = 占用已受理（弱承诺 + 收口保障）。

判据：对每个依赖问一句——"**它的失败晚暴露，代价是什么？**"代价兜得住 → 异步换可用性；兜不住 → 同步保正确性。

## 七、已知盲区：聚合视图漏了"进行中"（2026-10-14）

"预扣进行中"不在订单状态的聚合范围内（仍是 0、支付入口开放）→ 用户可以在"预扣还没落"时完成支付。两条分支：

1. **预扣迟到失败** → INVENTORY_FAILED → 收口时 status=1 → 人工/对账分支（有处置，敞口已知）；
2. **预扣迟到成功** → confirm（支付成功时）已因"记录不存在"静默 no-op → **孤儿预扣记录** → 30 分钟后 `PreDeductTimeoutJob` 到期释放 → **已支付订单的库存被放回可售池（超卖方向）**——现有机制兜不住（confirm no-op 被当成功 → 补偿不触发；超时 Job 不查订单状态；库存对账 Redis↔MySQL 自洽看不到订单；终结墓碑不适用）。

该边界与《库存-讲解》07 §3.5②、10 §7.3 问题 4 的"疑似边界"对应（本轮补全了"no-op 假成功"这个更隐蔽的变体）。

**已修复（2026-10-14）——确认标记方案**（与"终结墓碑"对称）：

- `InventoryService.confirmDeduct` 找不到预扣记录时写 `inventory:confirmed:{orderId}`（TTL 24h，配置 `inventory.confirmed.marker-ttl-seconds`）；
- `PreDeductTimeoutJob` 释放前检查该标记：命中 → 改判"**补确认**"（删记录、库存保持扣减、发 CONFIRM 落账事件），不再释放——已付款订单的迟到记录不再被放回货架；
- 效果：孤儿记录仍会迟到落盘，但 30 分钟后的"误释放"被改判为"补确认"，终态正确（库存扣减保留）；
- 验证：新增 3 用例（确认标记写入 + 超时任务"改判/释放"两分支），四模块 195 单测全绿。

## 掌握标准 + 背走一句

1. "下单成功"在异步设计里 = **受理**（要么就绪、要么取消）；
2. 支付前感知靠**订单状态**（异步结果的聚合视图）——注意"进行中"是盲区；
3. 状态扭转遵循**单一写入者**：各域上报、订单域裁决、裁决后通知善后；
4. 异步成立需要**三件套**：可靠上报 + 收口动作 + 兜底；
5. **"查"是快照，"扣"是裁决**——两段式：同步查快速失败，异步扣权威占用。

> **异步下单：下单成功是"受理"，订单状态是"聚合视图"，收口是"兑现机制"，超时/对账是"安全网"；同步还是异步，按每个依赖的"失败晚暴露代价"逐项选择；查是快照、扣是裁决，两者缺一不可。**
