## 一、先看"拆单"在干什么（例子先行）

小明一笔支付买 2 箱气泡水（A 店，200）+ 短袖（B 店，30）+ 裤子（B 店，70），用券后实付 **270**。

支付成功后打开"待发货"：显示 **2 个分组**（A 店、B 店），B 店下面 2 个条目（短袖、裤子）——**不会因为"2 箱水"拆成 2 个条目**（件数是行内字段）。他单独退了裤子——水、短袖的进度完全不受影响。

这笔交易在系统里其实是三层：

```
父订单 ×1     （交易/支付维度：一笔钱、一个支付单）    270
 ├─ 子订单 ×2 （商家维度：履约 / 售后入口 / 结算）     A店 200 / B店 100
 │    ├─ 行 ×1（SKU 维度：售后粒度、金额粒度）         水 200（数量 2）
 │    └─ 行 ×2                                       短袖 30 / 裤子 70
 └─ 售后单 ×N（挂在行上：退裤子 → 挂"裤子行"）
```

**为什么要拆？三个"粒度对不上"：**

1. **钱的粒度**：一笔支付 ≠ 一份履约——不同商家、不同仓库、不同物流，钱是一笔、货是多份；
2. **状态的粒度**：一个 `status` 装不下多份并行进度（08 已讲）——每份履约（子单）要有自己的状态；
3. **售后的粒度**：退货是"退某一件"——必须有一个"件"级的锚点（行）。

## 二、应然 vs 实然

| 维度 | 淘宝（应然） | xhs（实然） |
|---|---|---|
| 结构 | 父单 / 子单 / 行 三层 | 单层订单 + 明细行 |
| 商家维度 | 子单（一个商家一份） | 无（平台自营模型） |
| 售后粒度 | 挂行 / 子单 | 订单+SKU（**行的弱化近似**） |
| 履约 | 按子单 / 包裹 | 整单一次发货 |
| 结算 | 按子单分账 | 无分账（11-对账展开） |

一句话：xhs 的"订单+SKU"已经是一个**弱化的行**——缺的是"商家子单"这一层，以及它带来的一切（分组展示 / 独立履约 / 分账）。

## 三、关键设计点（讨论提炼）

### 3.1 拆单时点：下单即拆（推荐）

- 结构在支付前就建好：拆单 = **纯本地操作**（按商家分组 + 同事务写入子单/行记录）；支付成功只做**状态推进**（幂等）；
- 不采用异步拆单（线程池/MQ）：会引入"支付回调先到、子单还没拆好"的一致性窗口。

### 3.2 展示与存储分离（"支付前是一个整体"从哪来）

- 存储层：**始终三层**（下单即有子单/行）；
- 展示层：未支付时收拢为"一笔待支付订单"入口；支付成功后按子单展开（"待发货"列表按商家分组）；
- 常见错误：给子单加"可见/不可见"状态——**可见性是展示逻辑**（按支付状态渲染），不是数据模型字段。

### 3.3 双层状态机：父单状态 = 子单状态的聚合函数

- 真正在流转的是**子单/行**（发货、收货、退款都发生在这一层）；
- 父单不自己流转，它是**算出来的**：子单全完成 → 父单完成；子单全取消 → 父单关闭；"部分"的语义用子单表达，父单保持粗粒度；
- 规则必须**穷尽、单向**（父单不反向控制子单）。

### 3.4 行级金额：分摊必须落库（→ 10-分摊）

- 行必须携带"**分摊后的实付金额**"——否则"退一件退多少钱"算不出来（08 §3.2 的三道闸门全部以它为基础）；
- 守恒律：**父单实付 = Σ子单 = Σ行**；分摊口径 = 按金额比例（不是按件数平均），且店铺券只摊本店商品。

### 3.5 分片与查询

- 同聚合同分片：父单按 `buyer_id` 分片 → 子单/行**必须跟随**（否则 join 炸）；
- 买家维度查询用 `buyer_id`；商家维度（店铺订单/售后）→ **ES / Canal 异构索引**（华仔那套的通用解法）。

## 四、深水：拆单带来的新问题（难点，详见改造方案 §四）

- **竞态矩阵**：单层只有"订单 vs 售后"一对；三层后是父单/子单/行/售后/退款**五对象交叉**，每一对都要定义"谁先赢"（支付回调 vs 拆单、行售后 vs 子单发货、行级退款累计 vs 父单全退）；
- **聚合规则穷尽**：一半完成一半退款中 → 父单是什么？每个组合都要有明确答案；
- **迁移灰度**：订单是账务数据——老数据映射、双跑影子校验、灰度切流、可回滚可审计；
- **业务规则重新定位**：关单（父单级）/ 自动确认收货（子单级）/ 售后时效（行级）/ 库存占用（行级）——每条规则都要回答"挂哪层"。

## 五、xhs 的改造路径（讲而不做 → 已规划）

四阶段（每步独立有价值，禁止 big bang）：

| 阶段 | 内容 |
|---|---|
| ① 分摊落库 | 下单时把优惠摊到行（`discount_share` 落库） |
| ② 售后挂行 | 售后单从"订单+SKU"改为挂行 ID（先不拆单） |
| ③ 拆单 | 引入子单（商家维度）+ 父单状态聚合 |
| ④ 履约/结算下沉 | 发货/收货/结算按子单 |

详细方案（PRD 级）：`docs/学习/订单-改造/01-拆单与行级售后改造方案.md`。

## 掌握标准 + 背走一句

1. 拆单的本质：**一次支付 = 多份履约** → 父单（钱）/ 子单（商家）/ 行（SKU）三层；
2. **下单即拆**（同步、同事务）；**展示与存储分离**（别给子单加"可见性"状态）；
3. **父单状态 = 子单状态的聚合**（穷尽、单向）；
4. 行级金额靠**分摊落库**（10 的地基）；同聚合同分片、商家维度走异构索引；
5. xhs 现状 = 单层 + "订单+SKU"弱化行；改造四阶段：分摊落库 → 售后挂行 → 拆单 → 履约下沉。

> **拆单就是"把一笔钱摊给多份履约"：钱留在父单、货分到子单、售后挂到行；父单状态是算出来的，行级金额是摊出来的。**
