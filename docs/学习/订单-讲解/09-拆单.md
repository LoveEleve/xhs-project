# 09 · 拆单：父/子/行三层（已实现）

> **定位**：一次支付 = 多份履约。父单/子单/行三层模型——为什么拆、怎么拆、拆完状态怎么管；也是行级售后、履约下沉、商家维度查询的地基。
> **修订（2026-10-25）**：拆单已落地（ITER-001），不再是"讲而不做"；本篇按当前代码重写。
> **素材**：`SubOrder`/`SubOrderService`/`OrderTransactionService`/`OrderService`；`订单-改造/01` 与 `ITER-001` 产物。
> **系列导航**：`00` → `01` → `02` → `03` → `03A` → `03B` → `04` → `04A` → `04B` → 05-库存预占（跳过） → `06-支付联动` → `07-履约线` → `08-售后线` → **09-拆单** → **10-分摊** → `11-对账` → `12-收口`。

---

## 一、先看"拆单"在干什么（例子先行）

小明一笔支付买 2 箱气泡水（A 店，200）+ 短袖（B 店，30）+ 裤子（B 店，70），用券 30，实付 270。

支付成功后打开"待发货"：显示 **2 个分组**（A 店、B 店），B 店下面 2 个条目（短袖、裤子）——**不会因为"2 箱水"拆成 2 个条目**（件数是行内字段）。他单独退了裤子——水、短袖的进度完全不受影响。

系统里是三层：

```
父订单 ×1     （交易/支付：一笔钱、一个支付单）        270
 ├─ 子订单 ×2 （商家/履约/售后入口）                  A 总200/实付180；B 总100/实付90
 │    ├─ 行 ×1（SKU/金额/售后粒度）                   水 200（数量 2，分摊20）
 │    └─ 行 ×2                                       短袖 30（分摊3）/ 裤子 70（分摊7）
 └─ 售后单 ×N（挂行：退裤子 → itemId=裤子行）
```

**为什么拆？三个"粒度对不上"：**

1. **钱的粒度**：一笔支付 ≠ 一份履约——不同商家、不同仓库、不同物流；
2. **状态的粒度**：一个 `status` 装不下多份并行进度；
3. **售后的粒度**：退货是"退某一件"——必须有行级锚点。

## 二、当前实现：父/子/行

### 2.1 三层对象

| 层 | 表/实体 | 关键字段 | 职责 |
|---|---|---|---|
| 父单 | `t_order` / `Order` | 状态 0–5、三金额、地址快照、券 | 交易/支付/用户视角 |
| 子单 | `t_sub_order` / `SubOrder` | `subOrderNo`、`sellerId`、状态 0–5、子单金额、履约时间 | 商家/履约/父单聚合 |
| 行 | `t_order_item` / `OrderItem` | `subOrderId`、`sellerId`、价格/数量/总额、`discountShare` | SKU/金额/售后粒度 |
| 售后 | `t_aftersale` / `Aftersale` | `itemId`、`(item_id,type)` 唯一、`applyQuantity`、`restockStatus` | 行级售后 |

- 子单号：`subOrderNo = orderNo + "-" + 序号`；
- 子单与父单**同分片键 `user_id`**，`bindingTables` 绑定，避免跨分片 join；
- `sellerId` 来自 SKU（缺失兜底 0=平台自营）；**没有 `t_shop`**，商家只是轻量维度。

### 2.2 状态机

```
父单：0 待付款 → 1 已付款 → 2 已发货 → 3 已完成
        ↘ 4 已取消（五条终结路径）
        ↘ 5 已退款（全退收敛）

子单：0 待付款 → 1 待发货 → 2 已发货 → 3 已完成
        ↘ 4 已取消（未支付终结，父+子同事务）
        ↘ 5 已退款（全退收敛）
```

**父单状态 = 子单聚合**（`SubOrderService.computeParentStatus`）：

```
全取消 → 4
全退款 → 5
全终态（混合：部分取消/退款 + 部分完成）→ 3
存在活跃子单：
  活跃全待付款 → 0
  活跃全 ≥已发货 → 2
  其余 → 1
```

> 聚合是纯函数；`recomputeParentStatus` **只把 2/3/5 走聚合事件**，0/1/4 由支付/终结专属流程推进。

### 2.3 下单即拆：同一本地事务

`OrderTransactionService.executeLocalTransaction` 在同一个 DB 事务内完成：

```java
// 1) 行：预分配行 ID + 行金额 + 分摊
item.setId(IdWorker.getId());
item.setSellerId(sku.getSellerId() != null ? sku.getSellerId() : 0L);
item.setTotalAmount(price.multiply(qty));

Map<Long, BigDecimal> allocation =
        DiscountAllocator.allocateByItems(items, discountAmount);
item.setDiscountShare(allocation.getOrDefault(item.getId(), BigDecimal.ZERO));

// 2) 按 seller 分组生成子单
for (entry : bySeller) {
    SubOrder sub = new SubOrder();
    sub.setOrderId(order.getId());
    sub.setSubOrderNo(orderNo + "-" + subIndex++);
    sub.setSellerId(entry.getKey());
    sub.setStatus(SubOrder.STATUS_PENDING_PAYMENT);
    sub.setTotalAmount(subTotal);
    sub.setDiscountAmount(subDiscount);
    sub.setPayAmount(subTotal.subtract(subDiscount));
    subOrderMapper.insert(sub);
    for (OrderItem item : sellerItems) item.setSubOrderId(sub.getId());
}

// 3) 父单/子单/行/事件/本地消息同一事务
```

**为什么下单即拆，而不是支付后异步拆？**

- 拆单是纯本地操作（按 seller 分组），不需要外部服务；
- 放在创建本地事务内，父/子/行天然一致；
- 支付回调只做状态推进（父+子 0→1），不会出现"支付已成功、子单还没拆好"的窗口。

### 2.4 金额三层守恒

```
父单实付 = Σ子单实付 = Σ行(总额 - 分摊)
```

- 行：`totalAmount - discountShare`；
- 子单：`Σ行总额 - Σ行分摊`；
- 父单：`Σ子单`；
- 分摊用最大余数法（行级落库，见 10）。

## 三、履约/售后下沉

### 3.1 履约按子单

```java
// 发货：子单 CAS 1→2
SubOrder sub = subOrderMapper.selectBySubOrderNo(subOrderNo, userId);
subOrderMapper.markDelivered(sub.getId(), userId);

// 父单聚合：全部子单发货 → 父单 1→2
subOrderService.recomputeParentStatus(userId, sub.getOrderId());
```

- 发货/确认入参是 `subOrderNo`，不是父单 ID；
- 子单 CAS 失败（状态已变）→ 业务异常；
- 父单只在聚合流转时更新 `deliveredAt`/`completedAt` 并写快照；
- 发货前拦截"进行中的仅退款售后"（防钱货两空）。

### 3.2 售后挂行

- `Aftersale.itemId` 是行级锚点；唯一键 `(item_id,type)`；
- 申请时按 `skuId` 找到行（下单已禁止同 SKU 多行），落 `itemId`；
- 应退 = 行金额 − 行分摊（支持部分数量，向下取整，最后一次退满补差）；
- 部分售后**不改变**子单/父单主状态；全额退款回调才把父+全子收敛到 5。

### 3.3 取消/全退

- 未支付终结：父单 0→4 + **全部子单 0→4**（`OrderTerminationService` 同一本地事务）；
- 全额退款：父单 1/2/3→5 + **全部子单 1/2/3→5**（`onRefundSuccess` + `refundAll`）。

## 四、查询：买家分片 + 商家异构索引

| 维度 | 路径 |
|---|---|
| 买家详情/列表 | `userId + orderId` 路由分片；`orderNo → mapping → userId` 再路由 |
| 商家列表 | `sellerId → ES seller_sub_order_index`（Canal `order_instance` → `SUB_ORDER_INDEX_TOPIC` → search 消费者） |
| 商家详情 | `subOrderNo → orderNo（去 "-N"）→ mapping → userId → 分片读` |

- 订单接口返回三层：父单 + `subOrders`（含各自 `items`），同时保留平铺 `items` 兼容旧调用；
- **是否在未支付时收拢展示**是展示层逻辑，模型不加"可见性"字段；
- 商家 ES 是**异构索引**，不是订单账本的事实源；丢失/延迟靠回填/重放。

## 五、深水：拆单后的新问题

### 5.1 聚合规则的"混合终态"

- 一半完成、一半退款/取消 → 父单是 3（混合终态），不是 5；
- 只有全部子单退款才是 5；只有全部取消才是 4；
- 规则必须穷尽、单向；父单不反向控制子单。

### 5.2 支付/终结/履约的写入者

- 父单 0→1：支付回调专用；
- 父单 0→4：终结专用（父+全子同事务）；
- 父单 1/2/3→5：全退专用；
- 父单 2/3：子单聚合（发货/确认）；
- 不要让多个入口各自 `UPDATE t_order.status`。

### 5.3 竞态矩阵（当前）

| 竞态 | 谁先赢 | 当前处理 |
|---|---|---|
| 支付成功 vs 取消/关单 | 父单 CAS | 支付先赢 → 终结返回 INVALID_STATUS；取消先赢 → 支付回调返回 false（支付侧按业务拒绝退款） |
| 子单发货 vs 仅退款售后 | 商家审核/子单 CAS | 发货前查进行中的仅退款；检查与 CAS 非同一事务，窗口存在，靠商家审核/售后状态处理，非强一致 |
| 全额退款 vs 售后审核 | 父单状态 | 审核复核订单状态，父单已 5 → 自动驳回；避免钱退两次 |
| 父单聚合 vs 并发子单流转 | 事件 CAS | `recomputeParentStatus` 重试 3 次；仍冲突由日终校准兜底 |
| 重复支付回调 | 父单 CAS | 已支付/已终结返回 false，不抛 500；子单推进幂等 |
| 取消 vs 子单聚合 | 终结本地事务 | 父单 0→4 + 全子单 0→4 同事务；聚合不再参与 |

### 5.4 部分退款 vs 全额退款

- 部分售后：只动售后单/行金额，**不动**子单/父单主状态；
- 全额退款：支付域通知 → 父单 5 + 全子单 5；
- 两者不要混：不能用"有售后单"推断父单已退款。

### 5.5 存量迁移

- 本项目**无生产存量数据**，ITER-001 直接演进 DDL，没有写"老订单 → 1 父 + 1 子 + N 行"的回填脚本；
- 生产化时必须补：老订单子单回填、`subOrderNo` 生成、行 `subOrderId` 回填、影子双跑账目校验；
- 老订单没有子单：`getOrderDetail` 返回空 `subOrders`；`recomputeParentStatus` 会先判空并返回 false（不抛），只有纯函数 `computeParentStatus` 才会抛"子单列表为空"；履约按 `subOrderNo` 直接找不到。

### 5.6 商家维度

- 当前只有 `sellerId`，没有店铺主体/店铺券/分账/多包裹；
- 拆单只解决"按卖家分组履约/查询"，不解决"平台↔商家结算"；
- 商家列表走 ES 是读写分离的异构索引，不是分片键改成 sellerId。

## 七、十二个坑

1. **支付后异步拆单**：支付回调可能先到，子单还没建 → 一致性窗口；拆单必须在下单本地事务。
2. **拆单不在同一事务**：父单成功、子单失败 → 三层账对不上；父/子/行/本地消息同事务。
3. **父单状态被履约代码直接写**：绕过聚合 → 与子单分叉；统一走 `recomputeParentStatus`。
4. **聚合规则拍脑袋**：混合终态（部分完成+部分退款）不是 5；按穷尽规则算。
5. **把"有售后"当"父单已退款"**：部分售后不改主状态；只有全退才 5。
6. **0/1/4 也走聚合事件**：支付/终结有专属流程，聚合只处理 2/3/5。
7. **子单另起分片键**：父子跨分片 join；子单/行必须同 `user_id` + binding。
8. **sellerId 为空不兜底**：分组丢失/空指针；缺失按 0=平台自营。
9. **subOrderNo 用随机/重复**：履约/售后找不到；`orderNo-N` + 唯一键兜底。
10. **给子单加"可见性"字段**：未支付收拢是展示逻辑，不是数据模型。
11. **老订单无子单**：`recomputeParentStatus` 返回 false、履约按 `subOrderNo` 找不到（纯函数才抛"子单列表为空"）；生产化必须回填。
12. **把商家 ES 当事实源**：ES 只是检索，详情/扣减仍回订单分片。

## 八、值不值得深挖 / 一句话

- **值得**：下单即拆、父单聚合、混合终态、行级售后、同分片/异构索引——订单域最结构性的设计；
- **一句话带过**：子单号格式、VO 字段；
- **一句话**：**拆单 = 下单同事务按卖家拆父/子/行；履约下沉子单，父单状态由子单聚合（2/3/5），金额按行分摊；买家分片、卖家走 ES。**
- 金额见 **10**；售后见 **08**；收口见 **12**。

**面试口径**："下单本地事务里按 seller 拆父/子/行，子单号 orderNo-N；父单状态是子单聚合纯函数——全取消 4、全退款 5、混合终态 3，0/1/4 由支付/终结专属流程；发货/确认按 subOrderNo CAS，父单聚合后写快照；售后挂 itemId，部分退款不动主状态，全退才父+全子 5；子单与父单同 user_id 分片，商家维度走 Canal→ES，ES 不是事实源。"
