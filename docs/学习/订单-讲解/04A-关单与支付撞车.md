## 一、场景

订单 X 处于"待付款"，关单线为 T。两个动作可能在 T 前后并发到达：

- **支付回调**（渠道通知"支付成功"）→ 期望迁移：待付款 → 已付款；
- **关单触发**（延时消息 / 兜底扫描）→ 期望迁移：待付款 → 已关闭。

支付回调的到达时刻不可控（渠道延迟、重试），关单触发时刻亦不可控——**并发是常态**。设计目标：无论到达顺序如何，最终"钱货两清、状态一致"。

## 二、后果矩阵

| 到达顺序 | 结果 | 善后 |
|---|---|---|
| 支付先成功，关单后到 | 订单 = 已付款 | 关单校验状态后**幂等跳过**（无副作用） |
| 关单先成功，支付后到 | 订单 = 已关闭，**但渠道已扣款** | **必须退款**（或按业务重开）——否则资损 |
| 同时到达 | 条件更新保证仅一个成功 | 同上二选一 |

## 三、技术机制：状态迁移以条件更新（CAS）收口

状态迁移必须实现为**带条件的原子更新**：

```
UPDATE orders SET status = :target WHERE id = :id AND status = :expected
```

- 受影响行数 = 1 → 迁移成功；
- 受影响行数 = 0 → 状态已被并发修改 → 读取最新状态后按业务规则决策。

要点：**并发控制只收口在"状态迁移"这一个点上**。支付回调存在多条到达路径（主通知、补偿查询、重复通知），关单也存在多条路径（延时消息、兜底扫描）——若在每个入口各自处理并发，逻辑会发散；统一收口到状态迁移点，各入口只负责调用迁移。

## 四、失败方的善后（业务决策优先于技术）

- **关单失败**（支付先赢）：跳过。关单逻辑幂等，不产生副作用。
- **支付失败**（关单先赢）：最危险场景。原则：
  1. **终态不可逆**：已关闭订单不得直接改回"已付款"（关单副作用——库存释放、退券、通知——已发生且可能不可逆）；
  2. **钱的优先级高于单**：渠道已扣款 → 必须发起退款（自动退款 + 通知用户）；
  3. 备选方案"重开订单"仅在关单副作用可完整撤销时可行（库存可能已被他人购买，实际不可靠）→ 主流选择退款。

## 五、迟到成功（late success）

- 用户在关单线前完成支付，但渠道回调延迟到关单执行之后才到达；
- 判定依据：**渠道时间戳**（支付发生在关单线之前还是之后）；
- 处理策略：
  - 缓冲设计：关单时间 = 截止时间 + 缓冲量（吸收短延迟）——降低概率，不能消除；
  - 最终处理：一律走"退款"（或按业务规则重开）——不因"本应成功"而突破终态不可逆原则。

## 六、三层防线

| 防线 | 机制 | 覆盖 |
|---|---|---|
| 第一层 | 条件更新（CAS） | 并发互斥：同一迁移仅一个成功 |
| 第二层 | 失败方善后（退款） | 业务兜底：钱货两清 |
| 第三层 | 对账任务（支付单 ↔ 订单状态） | 漏网兜底：回调丢失、退款失败、极端时序 |

## 七、通用化

该模式适用于所有"同一实体的并发状态迁移"：取消 vs 支付、发货 vs 退款、退款 vs 收货等。统一模式：

1. 迁移 = 条件更新（CAS）；
2. 失败方按业务规则善后（跳过 / 退款 / 补偿）；
3. 终态不可逆；
4. 对账兜底。

## 掌握标准 + 背走一句

1. 并发是常态：状态迁移必须以**条件更新（CAS）**收口，且**只在"状态迁移点"收口一次**（多入口共用）；
2. 迁移失败方按业务善后：关单输 → 跳过；**支付输 → 退款**（钱优先于单）；
3. **终态不可逆**：已关闭不得直接改回已付款；"迟到成功"按渠道时间戳判定，最终仍走退款/重开；
4. 三层防线：CAS（并发互斥）→ 善后（钱货两清）→ 对账（漏网兜底）。

> **并发状态迁移的统一模式：条件更新收口、失败方善后、终态不可逆、对账兜底——"钱优先于单。"**
