## 引子（先看问题）

阿真下单成功，系统要干两件事：**① 订单库加一张订单；② 库存库扣一件货。** 两个数据在两个不同的库（甚至两个服务）里。

问题：怎么保证"两件事都成、或者都不成"？
只成一半就出事——订单在、库存没扣 → 超卖；库存扣了、订单没了 → 用户没单货没了。

这就是"**跨服务数据一致性**"问题。下面这条链，讲的就是人类对这问题的三代解法。

## 第一站：本地事务——"一个库内"的原子性

**先看它是什么**：你在同一个数据库里做"扣 A 100、加 B 100"（转账），数据库自己保证**要么都成、要么都不成**——这就是本地事务。

**它凭什么做到**（背不出没关系，知道有这些零件）：

- **A 原子性**：一组操作不可分割（主角就是它）；
- **C 一致性**：事务前后业务约束不被破坏；
- **I 隔离性**：并发事务之间互不干扰（靠锁/MVCC）；
- **D 持久性**：提交后就丢了算它输（靠日志）。

**它的边界**：只有"**同一份数据库**"才受它管。一跨库、一跨服务，这套保证就没了。

## 第二站：跨服务之后，原子性没了

订单库的事务提交了，库存库根本不知道——它有它自己的事务，两者之间**没有一根"事务指挥棒"**。

你可以在代码里手动补：订单成功后调库存；库存失败就把订单删了。但这就回到 03 篇的"缝隙"问题——**删订单这个"补偿动作"本身也可能失败**，然后越补越乱。

## 第三站：2PC（两阶段提交）——"强行找一个指挥棒"

**它想干什么**：让多个库/服务表现得像"一个库"：要么全提交、要么全回滚。**这是"强一致"的解法**。

**流程**（还是阿真下单，订单库 + 库存库两个参与者）：

```
协调者（Coordinator —— 事务的"总指挥"）
  │
  ├─ 阶段①【准备/投票 prepare】：问两边"把活干好但不提交，行不行？"
  │    订单库：写好订单（未提交、锁住）→ 回"行"
  │    库存库：扣好库存（未提交、锁住）→ 回"行"
  │
  └─ 阶段②【提交/回滚 commit/abort】：
       两票都"行" → 通知两边"提交！"（真正落库、放锁）
       只要一票"不行" → 通知两边"回滚！"
```

**它为什么被嫌弃**（四个硬伤）：

1. **慢**：两轮网络往返 × 所有参与者，还得等最慢的；
2. **锁太久**：从"准备"到"提交"之间，数据一直锁着（库存那行就被锁住）——高并发下是灾难；
3. **协调者单点**：总指挥一挂，参与者**举着锁干等**，不知道该提交还是回滚（叫 **in-doubt 悬挂事务**）——这叫"阻塞协议"，等它回来才解套；
4. **脆**：任何一个参与者挂掉，整个事务卡住。

所以 2PC 的定位：**"用性能和可用性，换强一致"**。它真实用在哪儿：强一致刚需、并发不高的场景；数据库层的 **XA 协议**就是 2PC 的工业标准。

（顺带：你项目的库存域里其实躺着一套 **TCC** 的实现——当时我们扫库时登记过表 `t_tcc_fence` 等，但没细讲。等你学完这节，回头看它就有坐标了。）

## 第四站：换思路——最终一致

**核心转折**：既然"同时都对"这么贵——那**不追求"同时对"，追求"最后都对"**。

例子还是阿真下单（就是 03 篇的机制，现在你能看懂它为什么长这样了）：

1. 先把"订单"和"一条待发送的'去扣库存'通知"**在同一个本地事务里**写进订单库（Outbox）；
2. 然后这条通知慢慢送——失败了**重试**、重复了**幂等**挡掉、万一漏了还有**对账**兜底；
3. 过了很短一个窗口（毫秒~秒级），订单库和库存库就一致了。

**强一致 vs 最终一致，一句话对比**：

| | 保证 | 代价 |
|---|---|---|
| 强一致（2PC） | **任何时刻**大家看到的都一样 | 慢、锁、怕挂 |
| 最终一致 | **过一小段时间**后大家一样 | 换来：快、扛并发、能容错 |

（术语对仗记一下就行：ACID ↔ **BASE**——Basically Available 基本可用、Soft state 软状态、Eventually consistent 最终一致。）

**注意**：最终一致 ≠ "允许乱"——它要求**最后一定收敛**。收敛不能靠许愿，靠下面的四件套。

## 第五站：最终一致的"四件套"（映射回 03）

| 件套 | 解决什么 | 03 / xhs 里的对应 |
|---|---|---|
| **可靠投递** | 消息不能丢 | 本地消息表（Outbox）/ 事务消息半消息+回查 |
| **重试** | 失败一次就再来 | 消费端重试（最多 N 次）、补发 Job（30s） |
| **幂等** | 重复投递不重复生效 | msgId 幂等、库存预扣的 pseudoOrderId 幂等 |
| **对账** | 上面全漏了，事后抓出来修 | 定时对账 Job（订单↔库存↔支付） |

**四件套缺一个，"最终一致"就变成"永远不一致"。**

## 附：分布式事务"家族图"（知道位置就行）

| 方案 | 一句话 | 位置 |
|---|---|---|
| 2PC / XA | 强行两阶段，强一致，重 | 刚需低频场景 |
| TCC | 业务层自己实现"两阶段"（每步配补偿） | 资金类精细场景（你项目库存域有影子） |
| Saga | 一串本地事务，每步配一个补偿动作 | 长流程（订单→支付→发货→……） |
| **本地消息表 / 事务消息** | 把"通知"做成可靠事件 | **互联网最常用（03 篇主角）** |

选择口诀：**能不让它"跨"就别跨（同库/合并服务）；非要跨，先问业务"能不能接受最终一致"——能就用消息；不能才考虑 TCC/Saga/2PC。**

## 掌握标准 + 背走一句

1. 本地事务只在"一个库"内有效；**跨服务 = 没有共同事务**；
2. 2PC = 两阶段（准备/提交）+ 协调者：换强一致，代价是**慢、锁、单点**；
3. 互联网主流 = 最终一致：**可靠投递 + 重试 + 幂等 + 对账**，过一个小窗口后一致。

> **"同时都对"太贵，"最后都对"够用——四件套撑起最终一致。**
