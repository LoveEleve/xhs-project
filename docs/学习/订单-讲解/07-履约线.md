# 07 · 履约线（子单维度）

> **定位**：订单从"已付款"到"已完成"这一段——发货、确认收货（以及仍缺失的自动确认）。拆单后履约**下沉到子单**，父单状态由子单聚合。
> **修订（2026-10-25）**：拆单已落地；履约从"订单级"改为"子单级"；旧 07 的"整单一次发货/status=2 退款被拒"已过期。
> **素材**：`OrderService.deliverOrder/confirmReceive`、`SubOrderService.recomputeParentStatus`、`SubOrderMapper`、`OrderController`。
> **系列导航**：`00` → `01` → `02` → `03` → `03A` → `03B` → `04` → `04A` → `04B` → 05-库存预占（跳过） → `06-支付联动` → **07-履约线** → `08-售后线` → `09-拆单` → `10-分摊` → `11-对账` → `12-收口`。

---

## 一、先看"履约"在干什么（例子先行）

小明一笔支付买了 A 店 2 箱水 + B 店短袖、裤子。拆单后：

```
父单（已付款 1）
 ├─ 子单 A（待发货 1）
 └─ 子单 B（待发货 1）
```

- A 店先发货 → 子单 A `1→2`；父单**仍是 1**（B 未发）；
- B 店发货 → 子单 B `1→2`；两个子单都 ≥2 → 父单聚合 `1→2`；
- 小明先确认 A → 子单 A `2→3`；父单仍是 2（B 未确认）；
- 再确认 B → 两个子单都终态 → 父单聚合 `2→3`（交易闭环）。

**履约三要素**：谁发货（商家/运营，不是买家）、货到哪了（物流信息）、什么时候算完成（买家确认或系统自动确认）。

## 二、当前实现：按子单履约

### 2.1 发货（子单 1→2）

入口：`POST /api/order/deliver`，入参 `subOrderNo + logisticsCompany + trackingNo`，要求 `X-Admin-Call`。

```java
SubOrder sub = subOrderMapper.selectBySubOrderNo(subOrderNo, userId);
if (sub.getStatus() != SubOrder.STATUS_TO_SHIP) throw ...; // 只能发待发货
if (hasActiveRefundOnlyAftersale(userId, sub)) throw ...;  // 进行中的仅退款 → 拒绝
int affected = subOrderMapper.markDelivered(sub.getId(), userId); // CAS 1→2
boolean parentMoved = subOrderService.recomputeParentStatus(userId, sub.getOrderId());
if (parentMoved) { setDeliveredAt; snapshot(DELIVERED); }
notify(userId, orderNo, "子订单已发货", shipInfo); // 通知按子单
```

要点：

- **作用对象是子单**，不是父单；
- 子单 CAS `1→2`，失败说明状态已变；
- 父单只在**全部子单都 ≥已发货**时聚合 `1→2`；
- 父单快照只在聚合流转时写；通知按子单触发（文本/物流），但 payload 仍用父单 orderId，未带 subOrderNo（多包裹时无法区分）；
- **不校验库存**：库存在支付确认/预扣阶段处理，发货是人工动作；
- **发货拦截**：子单下存在进行中的"仅退款"售后（待审核/已同意/退款中）→ 拒绝发货，防钱货两空。

### 2.2 确认收货（子单 2→3）

入口：`POST /api/order/confirm`，入参 `subOrderNo`，买家 `X-User-Id` 归属校验。

```java
SubOrder sub = subOrderMapper.selectBySubOrderNo(subOrderNo, userId);
if (sub.getStatus() != SubOrder.STATUS_SHIPPED) throw ...; // 只能确认已发货
int affected = subOrderMapper.markCompleted(sub.getId(), userId); // CAS 2→3
boolean parentMoved = subOrderService.recomputeParentStatus(userId, sub.getOrderId());
if (parentMoved) { setCompletedAt; snapshot(COMPLETED); }
```

- 父单只在**全部子单终态**时聚合 `2→3`；
- 混合终态（部分完成 + 部分退款/取消）也聚合为 3（"部分"语义由子单表达）；
- **不发通知**：动作发起人就是用户自己（与支付成功通知"对方"不同）。

### 2.3 父单聚合：只处理 2/3/5

```
全取消→4；全退款→5；全终态混合→3；
活跃全待付款→0；活跃全≥已发货→2；其余→1
```

- `recomputeParentStatus` 只把 **2/3/5** 走聚合事件；
- 0/1/4 由支付/终结专属流程推进；
- 子单 CAS 成功后再聚合；CAS 冲突重试 3 次，日终校准兜底。

### 2.4 查询与商家维度

- 订单详情 `OrderVO` 返回父单 + `subOrders`（每个子单含 `items`）；
- 买家列表按 `userId` 分片；
- 商家列表 `sellerId → ES`（Canal `order_instance` → `SUB_ORDER_INDEX_TOPIC`）；
- 商家详情 `subOrderNo → orderNo → mapping → userId → 分片读`；
- ES 是异构索引，不是履约事实源。

## 三、深水：子单履约带来的边界

### 3.1 状态机位置

```
父单：0→1→2→3；4/5 终态
子单：0→1→2→3；4/5 终态
```

- 履约只推进子单 1→2→3；父单 2/3 是聚合结果；
- 终结/全退是另一条线：父+全子同事务 4，或全退 5；
- 父单 4/5 与子单 4/5 必须同向，不能只改一层。

### 3.2 部分履约

- 部分子单发货：父单保持 1，直到所有活跃子单 ≥2；
- 部分子单确认：父单保持 2，直到所有子单终态；
- 混合终态（部分完成 + 部分退款/取消）：父单 3；
- 不要用"任一子单完成"或"任一子单退款"推断父单状态。

### 3.3 履约与售后/退款

- 发货前拦截进行中的**仅退款**（type=1）；退货退款（type=2）在未发货时不可申请；
- 检查与 CAS 非同一事务：存在"检查后、发货前售后创建"的窗口，靠商家审核/售后状态处理，非强一致；
- **全额退款现在允许 status 2**（旧 07 的"status=2 被拒"已修）：父单 1/2/3→5 + 全子单 1/2/3→5；
- 部分售后不改子单/父单主状态：售后单表达退款，主链保持履约进度。

### 3.4 自动确认收货仍缺失

- 无延时消息、无 Job、无配置；
- 用户不点确认 → 子单永久停在 2（已发货）；
- 影响：父单在途、统计/结算/售后时钟没有"自动完成"起点；
- 补法：延时消息/定时扫描 + 子单 CAS 2→3 + 父单聚合（与关单同构）。

### 3.5 物流只是字符串

- `t_sub_order` 只有 `delivered_at`；物流公司/单号在通知/请求里，不是独立物流对象；
- 无多包裹、无物流轨迹、无签收状态；
- 真实电商需要物流对象/包裹/轨迹，当前是简化。

### 3.6 商家权限边界

- 发货入口只校验 `X-Admin-Call`，`deliverOrder` 按 `subOrderNo + userId` 查子单，**没有校验 `sellerId` 归属**；
- 当前"商家"是轻量 `sellerId`，没有商家账号体系；生产化需要"子单 sellerId == 当前商家"的校验；
- 商家列表/详情同样依赖管理端/internal 头，不是完整商家鉴权。

## 四、对照表：应然 vs 当前

| 维度 | 淘宝（应然） | xhs（当前） | 差距 |
|---|---|---|---|
| 履约粒度 | 子单/包裹 | ✅ 子单 | 无包裹对象 |
| 发货 | 商家按子单/包裹 | ✅ 子单 CAS 1→2 | 无 seller 归属校验 |
| 确认 | 买家/自动 | ✅ 买家按子单 | ❌ 无自动确认 |
| 父单状态 | 子单聚合 | ✅ 2/3/5 聚合 | 对齐 |
| 物流 | 对象/轨迹/多包裹 | 两个字符串 | 缺口 |
| 通知粒度 | 子单/包裹级 | 按子单触发，但 payload 仍父单 orderId | 无 subOrderNo |
| 售后拦截 | 发货前检查 | ✅ 仅退款拦截 | 非强一致 |
| 退款边界 | 已发货可退 | ✅ 1/2/3→5 | 对齐 |
| 商家维度 | 店铺/子单 | sellerId + ES | 无店铺/鉴权 |

## 五、十二个坑

1. **按父单发货**：拆单后必须按 `subOrderNo`；父单没有发货动作。
2. **不做子单 CAS**：并发重复发货；`markDelivered` 条件更新 1→2。
3. **父单状态手写**：绕过聚合 → 与子单分叉；统一 `recomputeParentStatus`。
4. **任一子单发货就父单 2**：必须全部活跃子单 ≥2。
5. **任一子单完成就父单 3**：必须全部子单终态；混合终态才 3。
6. **发货不拦仅退款**：钱货两空；检查进行中的 type=1 售后。
7. **拦截当强一致**：检查与 CAS 非同一事务；窗口靠商家审核/售后状态。
8. **以为 status=2 不能全退**：旧文档过期；当前 1/2/3 都可全退。
9. **部分售后改父单 5**：部分退不改主状态；全退才 5。
10. **确认收货发通知**：动作发起人就是用户；当前不发。
11. **自动确认缺失当"已完成"**：2 会永久悬挂；需要 Job/延时补齐。
12. **物流字符串当物流对象**：无轨迹/多包裹/签收；生产化要对象化。
13. **不校验 sellerId**：管理端可发任意子单；生产化要商家归属校验。

## 六、值不值得深挖 / 一句话

- **值得**：子单履约、父单聚合、部分履约、发货拦截、status=2 全退——拆单后履约的核心；
- **一句话带过**：物流字段、通知文案；
- **一句话**：**履约 = 按子单发货/确认（CAS），父单由子单聚合 2/3；部分履约不提前推进父单；自动确认和物流对象仍是缺口。**
- 拆单见 **09**；售后见 **08**；收口见 **12**。

**面试口径**："拆单后履约下沉子单：发货按 subOrderNo CAS 1→2，拦截进行中的仅退款；确认按 subOrderNo CAS 2→3；父单只在全部子单发货/终态时聚合为 2/3，混合终态为 3。全退现在允许 1/2/3→5，部分售后不改主状态。自动确认收货、物流对象化、商家 sellerId 归属校验仍是缺口。"
