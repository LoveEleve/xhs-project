# 订单模块讲解系列 · 07 · 履约线

> **定位**：订单从"已付款"到"已完成"这一段——发货、物流、确认收货（以及缺失的自动确认）。履约是"钱货两清"里"货"的那一半。
> **系列导航**：`00` → `01` → `02` → `03` → `03A` → `03B` → `04` → `04A` → `04B` → 05-库存预占（跳过：见《库存-讲解》） → `06-支付联动` → **07-履约线** → **08-售后线** → **09-拆单** → **10-分摊** → **11-对账** → **12-收口**（完）
> 建立：2026-10-14。
> 关联：04A（撞车）；03B §七（确认边界）；08（售后/退款与已发货的关系）。

## 一、先看"履约"在干什么（例子先行）

小明付完款（订单 = 已付款）。接下来（应然）：

1. 商家看到待发货订单 → 打包 → 填快递单号 → 点"发货" → 订单 = 已发货，小明收到"已发货，请注意查收"（附物流信息）；
2. 快递送到，小明签收/点"确认收货" → 订单 = 已完成（**交易闭环**）；
3. 如果小明一直不点 → N 天后系统**自动确认收货**（防"永远待收货"）。

**履约三要素**：谁发货（商家动作，非买家）/ 货到哪了（物流信息）/ 什么时候算"完成"（买家确认 or 系统自动确认）。

## 二、实然：xhs 怎么做

### 2.1 发货（1→2）：商家动作 + 状态守卫

- 入口：`POST /api/order/deliver`（商家/运营调用）；
- 校验：订单存在 + **status==1**（只能对已付款发货）；不校验库存；
- 动作：`appendEvent(EVENT_DELIVERED, deliveredTime + 物流公司/单号)` → `setDeliveredAt` → 快照（DELIVERED）→ 删缓存 → 用户通知（"已发货，请注意查收" + 物流信息）；

### 2.2 确认收货（2→3）：买家动作

- 入口：`POST /api/order/confirm`（买家自己，`X-User-Id` 归属校验）；
- 校验：**status==2**（只能确认已发货的订单）；
- 动作：`appendEvent(EVENT_COMPLETED)` → `setCompletedAt` → 快照（COMPLETED）→ 删缓存；
- 注：确认收货**不发通知**——动作发起人就是用户自己（和"支付成功发通知"对称：通知是给"没发起动作的那方"看的）。

### 2.3 缺失：自动确认收货

- **全仓无实现**（无延时消息、无 Job、无配置）——03-修复记录已记为"功能缺失"；
- 后果：用户不点 → 订单**永远停在 2**（已发货）；
- 连锁（08-售后展开）：`onRefundSuccess` 只接受 status 1/3 → **已发货未确认的订单，全额退款回调会被拒绝**（`return false`）——售后线要处理这条边界。

## 三、深水细节

### 3.1 状态机位置

- 履约占了 6 状态里的 **1→2→3**（主链路后半段）；
- 终结线（4/5）与履约线在 1、2、3 处**各有一个出口**：取消（`EVENT_CANCELLED` 白名单 {0,1,2}）、退款（`EVENT_REFUNDED` 白名单 {1,2,3,4}）——04B 白名单里那两个集合，就是这两个出口的显式化；
- 售后/退款与履约状态的耦合（部分退款、已发货退款）——08 展开。

### 3.2 缺失的自动确认意味着什么

- 正常系统：7~15 天自动确认（买家不操作也闭环）→ 资金结算/售后时钟都以它为起点；
- xhs 缺失 → 2 状态可永久悬挂 → 影响：统计（在途订单）、售后（已发货单的退款口径）、对账（未完成单）；
- 补法（记录，不实施）：延时消息/定时扫描 + 条件更新 2→3（与 04 关单同构）。

## 掌握标准 + 背走一句

1. 履约 = **发货**（商家，1→2）+ **确认收货**（买家，2→3）；终结线在 1、2、3 各有一个出口（取消/退款白名单）；
2. 发货只校验状态不校验库存——"发货守卫"指人工动作本身；
3. **自动确认收货缺失**：2 可永久悬挂 → 全额退款回调拒收 status=2（08 处理）。

> **履约就是"钱货两清"的"货"那一半：发货（商家把货交出去）→ 确认收货（买家说收到了）→ 交易闭环；中间缺的自动确认，是 xhs 留下的一个功能缺口。**
