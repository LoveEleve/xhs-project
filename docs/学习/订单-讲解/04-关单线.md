## 一、为什么要有"关单"

场景：阿真 20:02 下单成功——订单"待付款"、库存被占住、券被占住。然后她放下手机去刷视频了。

**如果永不关单**（不付款的单一直挂着）：

| 后果 | 说明 |
|---|---|
| 货被锁死 | 紧缺货被"幽灵订单"占着，想买的人买不到、平台也卖不出 |
| 券被锁死 | 券绑在死单上，用户不能在别的单用 |
| 数据垃圾 | 海量"待付款"污染统计/对账 |
| 体验混乱 | 用户回头看到一堆待付款单，不知道哪些还能付 |

规则：待付款订单有一个**付款窗口**（一般 15~30 分钟），窗口内不付 → **系统自动关单** = 取消 + 释放库存 + 退回券。用户也可主动取消。关了没损失——想买重新下一单即可（所以"关"不是损失，"占着资源"才是）。

## 二、怎么让系统"30 分钟后想起这件事"——两条主流路

| | ① 定时扫描 | ② 延时消息 |
|---|---|---|
| 怎么"想起来" | 大闹钟翻名册：扫"待付款且已超时"的订单 | 每单自带小闹钟：发一条"30 分钟后见"的消息 |
| 精度 | 差（± 一个扫描周期，分钟级） | 准（到点即触发） |
| 压力形态 | 集中在扫描那一刻 | 分散（各单彼此独立） |
| 怕什么 | 名册变大、多实例重复扫 | **消息丢了这个单可能永远不关** |
| 依赖 | 无（只靠自己的库） | 依赖 MQ |

## 三、实然：xhs 怎么做关单（项目落地）

一句话：**延时消息为主 + 定时扫描兜底 + 乐观锁抢状态 + 释放/退券复用"取消"逻辑**。

**① 下单时：埋一条延时消息**
- 发到 `ORDER_CLOSE_TOPIC`，**延时档位默认 16 = 30 分钟**（测试配 5 = 1 分钟）；
- payload 就一个 orderId；消息头带 orderNo / userId（**分库分表路由要用**）；
- 发送失败只记日志——因为下面还有兜底。

**② 到点：消费者执行关单**
- `OrderCloseConsumer`（独立消费组）收到消息 → 解析 orderId + userId（**userId 取不到就查"订单号映射表"兜底**，保证能路由到正确的分片）→ 调 `closeTimeoutOrder`。

**③ 关单执行体（幂等）`doCloseTimeoutOrder`：**

1. 查单：不存在 / 已不是"待付款" → **直接跳过（幂等）**；
2. 追加"超时取消"事件 → 状态迁移走**乐观锁**（`updateStatusWithLock`：只有"当前状态 = 待付款"才更新得动）← **这就是和支付抢状态的机制**；
3. 释放库存（`releaseInventory`，用**伪订单号**——与用户主动取消复用同一段逻辑）；
4. 退还优惠券（`returnCouponIfUsed`，同样复用）；
5. 拍快照（TIMEOUT_CANCELLED）+ 删订单详情缓存；
6. 执行失败 → 外层发**补偿消息**（CLOSE_ORDER）进补偿重试（执行体本身不发消息、防自循环——2026-10-11 的修复）。

**④ 兜底扫描：`orderCloseJob`（XXL，每分钟）**
- 扫"**30 分钟前创建且仍待付款**"的订单（游标分页，每批 100）→ 逐单走同一个关单执行体；
- 注释原话：兜底延时消息丢失（Broker 宕机、磁盘故障等极端情况）。

**⑤ 竞态兜底**：乐观锁抢输的一方会收到"订单状态已变化"——支付侧对"关单先赢"有专门处理（钱已扣但单被关 → 走退款/补偿），这是下半场正题。

**⑥ 一个变体**：库存预扣失败时（`INVENTORY_FAILED_TOPIC` 收口），待付款订单**不等 30 分钟**——直接按"库存预扣失败"取消（释放其他 SKU + 退券 + 通知）。

## 四、深水细节（REVIEW 补）

### 4.1 定时扫描的坑

- **SQL 与索引**：条件是 `status=待付款 AND expire_at <= now`，要专门的联合索引；必须**分批**（LIMIT + 游标），避免"一次关几万单"的大事务；
- **多实例**：部署 4 个实例不能 4 个一起扫（重复关单、互相抢）→ **分布式锁**（只让一个扫）或**分片**（每个实例扫一段，如按 userId 取模）；xhs 订单分了 4 片，扫描要按分片维度组织；
- **频率 vs 精度**：1 分钟跑一次 = 最坏晚关 1 分钟；想更准就扫更勤，成本线性涨；
- 它有一个天然优点：**不怕消息丢**——订单还在库里，这一轮漏了下一轮还会看到。

### 4.2 延时消息的坑

- **机制一句话**：消息先存到 broker 的"定时区"（定时轮），**到点了才被投到真正的队列**；
- **档位制**（老版本）：只能选固定档位（1s/5s/10s/30s/1m/…/20m/30m/1h/2h，共 18 档）——"30 分钟"能选，"90 分钟"做不到（只能 1h 或 2h）；新版本（5.x）支持任意时刻；
- **上限 2 小时**：更长的延时（如"7 天自动确认收货"）不能用它，得换方案；
- **堆积**：大促上亿订单 = 上亿条延时消息在 broker 里趴 30 分钟——容量要评估；
- **可靠性**：消息存在 broker 磁盘上，`03-落库` 说的"会漏"场景同样适用 → 必须兜底；
- **重复**：至少一次投递 → 关单动作必须幂等；
- xhs 实况：延时消息为主（档位 16 = 30 分钟，测试环境配 1 分钟）+ 定时扫描兜底。

### 4.3 隐藏的选型维度："关单线"是会被改的业务参数

- 付款窗口各平台/品类不同（15 分钟 ~ 24 小时）；**大促期间"延长付款时间"是常规操作**；
- **延时消息**：消息已经发出去了（带着档位），**改不了**——想延期只能"撤回+重发"，难看；
- **定时扫描**：每轮读**最新规则 / 每单的 expire_at**，灵活得多；
- 所以对"参数灵活"要求高的场景，扫描反而更优。xhs 把关单线固定为配置项（不动态变），所以"延时为主"没问题。

## 五、第三条路：懒判定（Lazy）——只能当兜底防线

不主动关，只在"用到"时判超时：来付款 → 判"早超时了 → 拒绝"；有人想买被锁的货 → 判"锁过期没 → 过期就抢走"。

- 优点：**零定时机制、零扫描成本**；
- 缺点：**资源不及时释放**（低流量品类可能挂几天直到"恰好有人来"）、状态被动（订单显示待付款但其实已死）、超时判断散落到每个读取方（付款、查单、抢库存……都要写，容易漏）；
- 结论：单独用不行；但**一定要有**——作为最后一道防线（付款接口自己校验超时：就算关单机制全挂了，也不会出现"超时还能付款"）。又是"每层假设上层会漏"。

## 六、关单不是一个动作，是一次"mini 反向流程"（REVIEW 补）

关单要做：**状态迁移 + 释放库存 + 退回券 + 通知用户**——和下单一样是跨服务串，`03` 学的一切原样再来一遍：

- 订单侧：本地事务（状态迁移）+ 可靠通知（释放库存/退券）→ 失败重试 / 对账兜底；
- **库存侧还有一层自己的"预占超时释放"**（第二层保险——否则关单消息丢了，货就永久锁死）；
- 两层超时时间要**配合设计**：订单关单线 vs 库存预占 TTL（谁先谁后？涉及"以谁为准"）——留到 05-库存预占细讲；
- 失败兜底：订单关了但库存没释放 → 对账发现 → 补释放。

## 七、通往下半场的底座：条件更新（CAS）

关单落地 = 一条**带条件的更新**："只有当前还在待付款，才关得动"（`UPDATE ... WHERE status = 待付款`）。
下半场"关单和支付撞车"讲的就是：**关单和支付都在对同一个状态做"带条件的迁移"，谁的条件先成立，谁赢**。

## 掌握标准 + 背走一句

1. 两条主流（定时扫描 / 延时消息）+ 一条懒判定（**只能当兜底防线**）；
2. 深水差异：延时消息看"**档位 / 上限 / 堆积 / 可靠性**"；扫描看"**索引 / 分批 / 多实例 / 参数灵活**"；
3. 关单 = **mini 反向流程**：同样要可靠通知 + 对账；库存侧还有一层自己的超时保险；
4. 技术底座 = 条件更新（CAS）→ 并发撞车的完整讨论见 `04A-关单与支付撞车.md`。

> **关单是一次反向的最小交易：状态条件更新 + 释放资源 + 可靠通知；选"闹钟"要看清两点——能不能改期（参数会变）、丢了怎么办（兜底在哪）。**
