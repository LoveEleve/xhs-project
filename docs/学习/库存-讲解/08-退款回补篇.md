# 08 · 退款回补篇：REFUND_RESTORE 全解（累计正增量）

> 系列位置：07 讲完 CONFIRM/RELEASE。本篇讲**第四个也是最后一个动作**——退款后的库存回补（REFUND_RESTORE），核心是"**累计正增量**"幂等模型。
> 核心源码：`InventoryService.refundRestore` / `REFUND_RESTORE_DELTA_SCRIPT` / `OrderService.restoreStockOnRefund` / `AftersaleService.restoreStock` / `InventoryDeductConsumer.handleRefundRestore` / 补偿表 type=2。
> 建立：2026-10-10（对话精讲 + 源码核对后落笔）。

---

## 1. 业务/例子

### 1.1 语义：第四种动作，独立成一套

四个动作的账目全家福：

| 动作 | Redis | MySQL | 语义 |
|---|---|---|---|
| PRE_DEDUCT | `total -= 2` | `available -= 2, locked += 2` | 占住 |
| CONFIRM | 不动 | `locked -= 2` | 成交 |
| RELEASE | `total += 2` | `locked -= 2, available += 2` | 没成交 → 退回 |
| **REFUND_RESTORE** | **`total += 2`** | **`available += 2`** | **成交后退货 → 回补** |

**RELEASE 与 REFUND_RESTORE 的区别**（都有 `available +=`，另一半不同）：

```
RELEASE：处理"还在 locked 里"的量 → locked → available（转移）
REFUND ：处理"locked 早已清零"的量 → 直接 available +=（回补）
```

原因：退货发生在**成交之后**——locked 被 confirm 清掉了，货不在"锁定"池里，只能直接加回可售。

### 1.2 数据快照：回补发生的那一刻

延续例子（订单伪 ID `5080522866062586953`、SKU1001 ×2，已支付并成交）：

```
Redis：
  inventory:{1001}:total                  = "98"     ← 2 件卖出去了
  inventory:prededuct:5080522866062586953 = 不存在   ← confirm 已删
  inventory:prededuct:index               = 无该 member

MySQL：
  t_inventory(1001):  available = 98, locked = 0
  订单: status = 1（已付款）→ 进入退款流程
```

**回补完成后**：

| 存储 | 回补前 | 回补后 |
|---|---|---|
| Redis `total` | "98" | **"100"**（INCRBY +2） |
| MySQL | available=98, locked=0 | **available=100, locked=0** |
| 累计键 `inventory:refund:{orderId}:{skuId}` | 无 | `"2"`（TTL 30 天） |
| 预扣记录/索引 | 无 | 无（与本次回补无关） |

### 1.3 触发方（两个入口）

| 触发 | 代码 | 传的 quantity | 时机 |
|---|---|---|---|
| **全额退款** | `OrderService.restoreStockOnRefund`（:962） | 遍历 `t_order_item`，逐 SKU 传**整件数量** | 退款成功后 |
| **售后** | `AftersaleService.restoreStock`（:485） | `aftersale.getApplyQuantity()`（**本次申请量**） | 退款受理成功后（简化口径，注释注明） |

两个易混点：

1. **传的是真实 `orderId`（DB 主键），不是伪订单号**！退款链路与预扣链路用的是**两个 ID 空间**：预扣用 `derivePseudoOrderId(orderNo)` 派生；退款用 DB 主键（`aftersale.getOrderId()` / `OrderItem.getOrderId()`）。两者各自自洽、不通兑。
2. **退款前 confirm 先行**（07 已讲）：退款流程 = `confirmInventoryDeductSync`（清预扣记录，通常 no-op）→ `restoreStockOnRefund`。目的：避免"release 回补 + refundRestore 回补"双通道叠加造成库存虚增。

售后路径失败时的兜底（注释原文）："跨服务失败（库存域整体不可用等）：库存域内部补偿表不会留下记录，由售后单的 `restock_status=0` + 恢复任务兜底重试（库存域按 orderId+skuId 累计幂等）"。

## 2. 问题：退款回补要解决什么

退款可以发生在各种时序里（Feign 重试、售后重复受理、部分退多次退、与全额退款路径叠加），所以这次回补要解决：

| # | 难题 | 期望 |
|---|---|---|
| 1 | **重复调用**（Feign 超时重试、售后恢复任务重试） | 不重复补 |
| 2 | **分次退货**（先退 1 件、后补剩余） | 不漏补 |
| 3 | **双通道叠加**（售后路径 × 全额退款路径都来调） | 总量正确，不虚增 |

解法：**"累计正增量"模型**——键里记"已受理的应回补目标"，每次只补 `目标 − 已受理` 的正增量。

## 3. 库存侧核心：`refundRestore`（全文 + 逐段）

### 3.1 全文（原文）

```java
/**
 * 退款回补库存（T-071，2026-08-14）
 * <p>
 * 全额退款后调用：confirm 已清预扣记录 → release 无记录可退（G5 实证退款不退库存）。
 * 独立语义：Redis total/路由桶 +qty + MQ REFUND_RESTORE（L2 同步 MySQL available_stock）。
 * 幂等（累计语义，2026-09-21）：key inventory:refund:{orderId}:{skuId} 记录"已受理的应回补数量"，
 * 只回补正增量——重复调用/重试 delta=0 跳过；分次退货（先 1 件后 2 件）不会漏补；
 * 与全额退款路径叠加时后到者 delta=0，不会重复回补。失败时回滚累计值允许重试。
 * </p>
 */
public void refundRestore(com.myxhs.inventory.dto.request.RefundRestoreRequest request) {
    Long orderId = request.getOrderId();
    Long skuId = request.getSkuId();
    int quantity = request.getQuantity();

    // 幂等（累计语义）：key 记录"该订单该 SKU 已受理的应回补数量"，只回补正增量——
    // - 重复调用 / Feign 重试：target 不变 → delta=0 → 跳过（幂等）
    // - 分次售后：先退 1 件补 1，再退剩余 2 件补 2（不漏补）
    // - 售后与全额退款路径叠加：任一先到，后到者 delta=0（不重复补）
    // 扩容暂停窗口（preDeduct/release/confirm 都检查）：窗口内回补可能落旧桶被重分配覆盖，
    // 且必须在推进累计键之前判断——否则重试时 delta=0 会静默跳过（漏补）
    if (Boolean.TRUE.equals(stringRedisTemplate.hasKey("inventory:paused:" + skuId))) {
        log.warn("[库存退款回补] SKU扩容暂停窗口内, 落补偿表稍后重试: orderId={}, skuId={}", orderId, skuId);
        recordRefundRestoreCompensation(orderId, skuId, quantity, request.getUserId(), "resize-paused");
        return;
    }

    String idemKey = "inventory:refund:" + orderId + ":" + skuId;
    Long delta;
    try {
        delta = stringRedisTemplate.execute(new DefaultRedisScript<>(REFUND_RESTORE_DELTA_SCRIPT, Long.class),
                java.util.List.of(idemKey), String.valueOf(quantity),
                String.valueOf(java.time.Duration.ofDays(30).getSeconds()));
    } catch (Exception e) {
        // Redis 不可用：不能直接返回（调用方会当作回补成功而不再重试）——落补偿表由 Job 重试
        log.error("[库存退款回补] 累计幂等键读取失败, 落补偿表待重试: orderId={}, skuId={}", orderId, skuId, e);
        recordRefundRestoreCompensation(orderId, skuId, quantity, request.getUserId(), e.getMessage());
        return;
    }
    if (delta == null || delta <= 0) {
        log.info("[库存退款回补] 幂等跳过（本次请求 {} 件, 累计已受理）: orderId={}, skuId={}",
                quantity, orderId, skuId);
        return;
    }
    int restoreQty = delta.intValue();
    try {
        // 防御（T-078）：Redis total 缺失时先自愈重建（canal 延迟删除/Redis 故障场景），
        // 否则 INCR 空 key 从 0 开始 → 错误回补
        if (!Boolean.TRUE.equals(stringRedisTemplate.hasKey(totalKey(skuId)))) {
            if (!rebuildStockFromDb(skuId)) {
                log.error("[库存退款回补] Redis缺失且MySQL无记录, 放弃回补: orderId={}, skuId={}", orderId, skuId);
                return;
            }
        }
        // 路由桶（userId 可空，缺省桶 0）
        String bucketCountStr = stringRedisTemplate.opsForValue().get(bucketCountKey(skuId));
        int bucketCount = bucketCountStr != null ? Integer.parseInt(bucketCountStr) : defaultBucketCount;
        Long userId = request.getUserId();
        int bucketNo = (userId != null && bucketCount > 0)
                ? (int) Math.floorMod(userId, (long) bucketCount) : 0;
        String totalKeyStr = totalKey(skuId);
        String bucketKeyStr = bucketKey(skuId, bucketNo);

        // Redis 原子回补（total + 桶），数量取正增量
        String script = "return redis.call('INCRBY', KEYS[1], ARGV[1]) + redis.call('INCRBY', KEYS[2], ARGV[1])";
        stringRedisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
                java.util.List.of(totalKeyStr, bucketKeyStr), String.valueOf(restoreQty));
        log.info("[库存退款回补] Redis回补: orderId={}, skuId={}, delta={}, bucket={}",
                orderId, skuId, restoreQty, bucketNo);

        // MQ 同步 MySQL（available_stock +delta）
        if (!sendInventoryEvent(orderId, skuId, restoreQty, "REFUND_RESTORE")) {
            log.error("[库存退款回补] MQ发送失败(依赖Outbox/对账兜底): orderId={}, skuId={}", orderId, skuId);
        }
    } catch (Exception e) {
        // 回滚累计值到本次之前（best-effort），允许重试，避免"没回补却记成已受理"
        try {
            stringRedisTemplate.opsForValue().set(idemKey, String.valueOf(quantity - restoreQty),
                    30, java.util.concurrent.TimeUnit.DAYS);
        } catch (Exception rollbackEx) {
            log.error("[库存退款回补] 累计值回滚失败(可能漏补, 需人工核对): orderId={}, skuId={}",
                    orderId, skuId, rollbackEx);
        }
        // 落补偿表由 InventoryCompensationJob 自动重试（type=2 退款回补）；已有待处理记录则不重复堆积
        // 注意：补偿行存"累计目标"（quantity），不是本次增量 delta——
        // 重试接口按累计目标判定，存 delta 会被当成目标导致重试无效（静默少补）
        recordRefundRestoreCompensation(orderId, skuId, quantity, request.getUserId(), String.valueOf(e.getMessage()));
        throw e;
    }
}
```

### 3.2 逐段讲解

**① 扩容暂停检查（放置位置有讲究）**

```java
if (Boolean.TRUE.equals(stringRedisTemplate.hasKey("inventory:paused:" + skuId))) {
    recordRefundRestoreCompensation(...);
    return;
}
```

- resize 窗口内回补可能落旧桶被重分配覆盖 → 不硬做，落补偿表让 Job 稍后重试；
- **必须在"推进累计键之前"判断**（注释原文）："否则重试时 delta=0 会静默跳过（漏补）"——先占坑再暂停，重试会被自己的坑挡住。

**② 累计幂等键 + delta 脚本**

```java
String idemKey = "inventory:refund:" + orderId + ":" + skuId;
delta = execute(REFUND_RESTORE_DELTA_SCRIPT, [idemKey], quantity, 30天);
```

脚本全文（内联常量）：

```lua
local cur = tonumber(redis.call('GET', KEYS[1]) or '0')
local target = tonumber(ARGV[1])
if target <= cur then return 0 end
redis.call('SET', KEYS[1], tostring(target), 'EX', tonumber(ARGV[2]))
return target - cur
```

语义（本方法的名字就来自它）：**键存"已受理的应回补目标"；本次只补 `目标 − 已受理` 的正增量**。

- Redis 不可用：**不能静默 return**（调用方会当回补成功而不再重试）→ 落补偿表；
- `delta <= 0` → 幂等跳过（重复调用/更小目标）。

**③ T-078 自愈防御**

```java
if (!hasKey(totalKey(skuId))) {
    if (!rebuildStockFromDb(skuId)) { 放弃回补; return; }
}
```

Redis total 缺失时（canal 延迟删除/Redis 故障），先重建再加——否则 `INCRBY` 空 key 从 0 开始，回补出一个荒谬的值。

**④ 原子回补（Redis 层唯一一次加库存）**

```java
String script = "return redis.call('INCRBY', KEYS[1], ARGV[1]) + redis.call('INCRBY', KEYS[2], ARGV[1])";
execute(script, [totalKey, bucketKey], restoreQty);
```

- 一次脚本同时加总库存和桶（原子）；
- 桶由 `userId % bucketCount` 路由（缺省桶 0）——分桶细节按惯例不展开。

**⑤ 落 REFUND_RESTORE 事件**

```java
if (!sendInventoryEvent(orderId, skuId, restoreQty, "REFUND_RESTORE")) {
    log.error("[库存退款回补] MQ发送失败(依赖Outbox/对账兜底): ...");
}
```

发的是**增量 delta**（不是 target）——L2 只加本次该加的量；失败留表补发（不可回滚动作的规则）。

**⑥ 异常处理：回滚累计值 + 补偿表（type=2）**

```java
// 回滚累计值到本次之前（best-effort）
stringRedisTemplate.opsForValue().set(idemKey, String.valueOf(quantity - restoreQty), 30, DAYS);
// 落补偿表（注意：存"累计目标" quantity，不是 delta）
recordRefundRestoreCompensation(orderId, skuId, quantity, request.getUserId(), reason);
throw e;
```

两个"讲究"：

1. **回滚累计值**："避免'没回补却记成已受理'"——回补失败时把键退回去，允许重试重算 delta；
2. **补偿行存"累计目标"（quantity），不是 delta**（注释原文）："重试接口按累计目标判定，存 delta 会被当成目标导致重试无效（静默少补）"——Job 重试时调用的还是同一个 `refundRestore`，传参口径必须与首次一致。

### 3.3 数据推演（四种场景，订单×SKU 条目数量 2 为例）

| 场景 | 键 cur（受理前） | target（本次） | delta | Redis total | 结论 |
|---|---|---|---|---|---|
| 首次全额退款（传 2） | 0 | 2 | **2** | 98 → 100 | 回补 2 ✅ |
| 重复调用（同传 2） | 2 | 2 | **0** | 不变 | 幂等跳过（记日志） ✅ |
| 分次退货（先传 1，后传 2※） | 0 → 1 | 1 → 2 | **1 → 1** | 99 → 100 | 累计补 2（※见 §6 观察点） |
| 双通道叠加（售后 1 先到，全额 2 后到） | 0 → 1 | 1 → 2 | **1 → 1** | +2，总量 = max(1,2) | 不重复、不漏 ✅ |

> **不变式（背）**：无论调用顺序与次数，**累计回补量 = 所有请求 target 的最大值**。
> "防重复"来自 `target <= cur → 0`；"可追加"来自 `target > cur → 补差`。

## 4. L2 落账端（消费 REFUND_RESTORE 事件）

`InventoryDeductConsumer.handleRefundRestore`（与 06 的四路分流同构）：

```java
private void handleRefundRestore(InventoryDeductEvent event) {
    withEventVersion(event, () -> {
        int affected = inventoryMapper.refundRestoreStock(event.getSkuId(), event.getQuantity());
        if (affected > 0) { log.info("[库存L2] 退款回补MySQL成功: ..."); }
        else { log.warn("[库存L2] 退款回补MySQL失败: ...（等待L3对账修复）"); }
    });
}
```

SQL（`InventoryMapper`）：

```sql
UPDATE t_inventory SET available_stock = available_stock + #{quantity},
       updated_at = NOW()
WHERE sku_id = #{skuId} AND deleted = 0
```

注意：**没有 locked 条件**（区别于 RELEASE 的 `WHERE locked >= qty`）——因为它就是"凭空加回可售"，没有前置条件可校验；失败（影响 0 行）只可能是 SKU 行不存在 → 记日志，等 L3。

## 5. 补偿体系：type=2（退款回补）

- 库存侧补偿表 `t_inventory_compensation` 的 `type`：**1=预扣回滚、2=退款回补**（V2 迁移定义）；
- `recordRefundRestoreCompensation`：写 type=2 行（**先查 `countPendingCompensation` 防重复堆积**）；
- `InventoryCompensationJob`（30s 一轮）的 type=2 分支：**重新调用 `inventoryService.refundRestore(req)`**——"累计正增量幂等，重复重试安全"，Success → markResolved；
- 覆盖的失败面：resize 暂停、Redis 不可用、回补中途异常（落表后 throw 给 Feign 调用方）；
- 还有一层是**售后侧自己的恢复任务**（`restock_status=0`）——"库存域整体不可用"时，库存内部补偿表可能都没写成，由售后侧重试（注释原文）。

## 6. 边界与口径（背）

1. **回补时点是简化口径**（`AftersaleService` 注释原文）："当前在'退款受理成功'后回补库存，对 type=1（未发货/协商退款）语义正确；对 type=2（退货退款）**真实系统应在'退货入库质检通过'后回补**，本实现按简化口径在退款受理时回补"——如需严格时点，按 type 分流 + 新增入库确认步骤。
2. **ID 空间**：退款链路用**真实 orderId**（两调用方一致）；预扣生命周期用伪订单号——两套 ID 不可混。
3. **"后到者 delta=0"的完整口径**：注释原文如此，但更普适的不变式是"**累计回补量 = max(target)**"——后到者的 target 若更大，是"补差"（正确），不是重复。
4. **resize 暂停检查必须在推进累计键之前**：否则重试 delta=0 静默跳过 → 漏补（注释原文）。
5. **T-078**：total 缺失先重建再回补，防"INCRBY 空 key 从 0 开始"的错误回补。
6. **观察点（待复核，未臆断）**：售后路径传 `applyQuantity`（**本次申请量**，实体/校验代码已核对）；而 delta 脚本按"累计目标"判定。多次部分售后时，"分次不漏补"是否严格成立，取决于后续申请传参是否为累计值——售后模块未读完（受 `(order_id, sku_id, type)` 唯一键约束，可能不构成问题）。标记为待核对项。
7. 引用编号核对：`T-071`（退款回补语义）、`T-078`（total 缺失自愈）、V2 迁移（补偿 type）均按源码注释原文。

## 7. 检查题（2 道）

1. 用"不变式"回答：同一订单×SKU 依次发起 target=1、target=2、target=1 三次回补调用——每次 delta 分别是多少？最终 Redis total 加了几件？如果顺序换成 2、1、1 呢？
2. 回补失败落补偿表时，行里为什么存"累计目标（quantity）"而不是"本次增量（delta）"？存错了会发生什么（用 Job 重试的调用口径推演）？
