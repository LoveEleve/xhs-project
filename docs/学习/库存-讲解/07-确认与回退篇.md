# 07 · 确认与回退篇：CONFIRM + RELEASE 全解

> 系列位置：06 讲了"事件如何可靠落到 MySQL"（Outbox + 版本门 + 落账消费者）。本篇讲**两个下游动作的完整链路**：
> **CONFIRM**（支付成功 → 成交）与 **RELEASE**（取消/超时/失败收口 → 退回），覆盖"外部契约 → Lua → Java → 落账 → 失败面"。
> 核心源码：`OrderService.onPaymentSuccess / confirmInventoryDeduct(Sync) / releaseInventory / sendCompensationMessage`、`confirm.lua`、`release.lua`、`InventoryService.confirmDeduct / releaseStock`、`PreDeductTimeoutJob`。
> 建立：2026-10-10（对话精讲 + 代码核对后落笔）。

## 1. 业务/例子

### 1.1 两个动作的语义（各一条 SQL，与 06 衔接）

| 事件 | 核心 SQL | 语义 |
|---|---|---|
| CONFIRM | `locked_stock -= 2` | 成交（锁定清零，总量下降 = 真正卖出） |
| RELEASE | `locked_stock -= 2, available_stock += 2` | 退回（锁定 → 可售，总量不变） |

关键差异先记住：

```
CONFIRM：Redis 侧【不动库存】（预扣时已扣）——只删预扣记录 + 清超时索引
RELEASE：Redis 侧【动库存】——把数量加回来源桶 + 总库存，再删记录 + 清索引
```

### 1.2 数据快照：支付成功那一刻（CONFIRM 执行前）

延续例子（订单伪 ID `5080522866062586953`、SKU1001 × 2、14:30 下单、14:35 支付成功）：

**Redis（L1 真相）**：

```
inventory:{1001}:total                     = "98"
inventory:prededuct:5080522866062586953    = { "1001": "2", "1001:bucket": "3" }   （TTL 剩 ~2100s）
inventory:prededuct:index                  = { member 5080... → score = 15:00:00 }
inventory:event:version:5080...:1001       = "T1"（14:30 预扣事件的 eventTime，24h）
```

**MySQL（L2 镜像）**：

```
t_inventory (sku=1001):  available_stock = 98, locked_stock = 2
t_inventory_prededuct_idem:  (5080..., 1001) 占位行在
t_inventory_outbox:          PRE_DEDUCT 行 status=1
t_order:                      status 即将 0(待付款) → 1(已付款)
```

**CONFIRM 执行后的目标状态**：

| 存储 | 变化 |
|---|---|
| Redis | total 不动；`HDEL 1001 / 1001:bucket` → Hash 空 → `DEL + ZREM`（超时索引移除） |
| MySQL | `locked 2 → 0`；available 不动 |
| 净效果 | Redis 98 ↔ MySQL 98/0 继续镜像；该订单不会再被超时释放 |

### 1.3 触发总览

| 动作 | 触发方 | 方式 |
|---|---|---|
| CONFIRM | 支付成功（`PayResultConsumer` → `onPaymentSuccess`）；退款前二次确认 | 异步 Feign / 同步 Feign |
| RELEASE | 用户取消、超时关单（`closeTimeoutOrder`）、库存失败收口（`handleInventoryFailure`）、支付失败取消、补偿重试端点（`compensateReleaseStock`） | 异步/同步 Feign |
| RELEASE（兜底） | `PreDeductTimeoutJob`（定时扫描过期预扣） | 内部直接调 release.lua |

## 2. 问题：两个动作各自要解决什么

| 动作 | 核心问题 | 解法 |
|---|---|---|
| CONFIRM | ① 清理预扣占用（Redis 记录 + 超时索引 + MySQL locked）<br>② 防止"release 回补 + refundRestore 回补"双通道叠加 | ① confirm.lua 原子删记录<br>② 退款前先同步 confirm |
| RELEASE | ① 把库存退回**来源桶**（不是随便一个桶）<br>② 与并发释放（用户取消 × 超时 Job × 补偿重试）互斥 | ① 从记录读 `{skuId}:bucket`<br>② release.lua 的 `HGET + HDEL` 原子——只有一方能成功回退 |
| 共同 | 记录不存在怎么办？扩容窗口内怎么办？ | 静默 no-op（幂等）；`inventory:paused:{skuId}` 时抛错等重试（N10） |

## 3. CONFIRM 全链路

### 3.1 外部契约：谁在什么时机调 CONFIRM

```
支付服务（钱收到，支付单已落定）
```

> **双通道与自动退款**（支付侧决策，PaymentService 原文）：先同步 Feign 拿订单业务答复——订单**明确业务拒绝**（已取消/已支付且非 503）→ **不发 MQ + 自动退款**（"避免钱货两空"）；订单接受或 Feign **503 临时故障** → 发 MQ 兜底。通道③ 为注释提到的终极补偿 Job。

```java
// OrderService.java:753 —— 支付成功主链路（原文）
public boolean onPaymentSuccess(Long orderId, Long userId) {
    // 分库分表后状态更新需要 userId 作为分片键路由
    if (userId == null) {
        OrderNoMapping mapping = orderNoMappingRepository.selectByOrderId(orderId);
        if (mapping == null) {
            log.error("[订单] 支付回调但映射表中找不到orderId: orderId={}", orderId);
            return false;
        }
        userId = mapping.getUserId();
    }

    // 查询订单（需要 userId + orderId 联合查询）
    Order order = orderMapper.selectOne(
            new LambdaQueryWrapper<Order>()
                    .eq(Order::getUserId, userId)
                    .eq(Order::getId, orderId));
    if (order == null) {
        log.warn("[订单] 支付回调但订单不存在: orderId={}", orderId);
        businessMetrics.recordOrderPayResult("not_found");
        return false;
    }
    if (order.getStatus() != 0) {
        log.warn("[订单] 支付回调但订单状态不是待付款: orderId={}", orderId);
        businessMetrics.recordOrderPayResult("race"); // 已支付/已取消/已关闭：正常竞态终态
        return false;
    }

    // Event Sourcing: 追加支付事件并更新状态
    boolean statusUpdated = false;
    try {
        orderEventService.appendEvent(order, OrderEventService.EVENT_PAID,
                Map.of("paidTime", LocalDateTime.now().toString()));
        statusUpdated = true;
        orderMapper.setPaidAt(orderId, userId);
    } catch (IllegalStateException | IllegalArgumentException e) {
        // 并发: 关单/取消先赢→支付已成功(钱已扣)但订单状态已变
        // 不抛异常: 抛异常→payment侧误判通知失败→P0-6无限重试
        log.error("[订单] 支付回调竞态(订单状态已变): orderId={}, status={}", orderId, order.getStatus(), e);
        businessMetrics.recordOrderPayResult("race");
        return false;
    } catch (org.springframework.dao.DataAccessException e) {
        // SQL 异常：可能 setPaidAt/事件落库瞬时失败，但状态可能已改为已支付。
        // 不向上抛 500（否则 payment 侧误判失败并自动退款已支付订单）。
        // 若状态已更新则返回 true 并记录，paid_at/事件由对账兜底；若状态未更新则返回 false。
        if (statusUpdated) {
            log.error("[订单] 支付已成功但 paid_at/事件 SQL 失败(对账兜底): orderId={}", orderId, e);
            businessMetrics.recordOrderPayResult("transient_event_failed");
            confirmInventoryDeduct(orderId, order.getOrderNo(), userId);
            takeSnapshot(orderId, userId, "PAID");
            stringRedisTemplate.delete("myxhs:order:info:" + orderId);
            orderNotificationPublisher.publishStatusChanged(userId, orderId, order.getOrderNo(),
                    "支付成功，我们将尽快为你发货", null);
            return true;
        }
        log.error("[订单] 支付事件 SQL 失败且状态未更新: orderId={}", orderId, e);
        businessMetrics.recordOrderPayResult("transient_status_lost");
        return false;
    }

    // 确认库存扣减（预扣 → 正式扣减，异步不阻塞主链路，失败由补偿+对账兜底）
    confirmInventoryDeduct(orderId, order.getOrderNo(), userId);

    takeSnapshot(orderId, userId, "PAID");
    stringRedisTemplate.delete("myxhs:order:info:" + orderId);
    // 订单通知（type=5）：支付成功
    orderNotificationPublisher.publishStatusChanged(userId, orderId, order.getOrderNo(),
            "支付成功，我们将尽快为你发货", null);
    log.info("[订单] 支付成功: orderId={}", orderId);
    return true;
}
```

```java
private void confirmInventoryDeduct(Long orderId, String orderNo, Long userId) {
    java.util.concurrent.CompletableFuture.runAsync(() -> {
        confirmInventoryDeductSync(orderId, orderNo, userId);
    }, ORDER_ASYNC_EXECUTOR);
}

private void confirmInventoryDeductSync(Long orderId, String orderNo, Long userId) {
    try {
        long pseudoOrderId = derivePseudoOrderId(orderNo);
        Map<String, Object> request = Map.of("orderId", pseudoOrderId);
        R<Void> result = inventoryFeignClient.confirmDeduct(request);
        if (result == null || !result.isSuccess()) {
            log.error("[订单] 退款前确认库存扣减失败，依赖对账兜底: orderId={}, result={}", orderId, result);
        } else {
            log.info("[订单] 退款前确认库存扣减成功: orderId={}", orderId);
        }
    } catch (Exception e) {
        log.error("[订单] 退款前确认库存扣减异常，依赖对账兜底: orderId={}", orderId, e);
    }
}
```

**三个设计点**：

1. **异步**：支付回调要求快速处理；库存确认失败不能反馈给支付链路——代价与兜底见 3.5。
2. **只传一个 `pseudoOrderId`**：库存端靠它定位整个订单的预扣 Hash，**Hash 里有全部 SKU 字段，服务端自行遍历**——多 SKU 订单无需传列表。
3. **两层幂等**：订单侧 `status==0` 乐观锁（重复支付回调不重复处理）；库存侧"记录不存在 → 静默 no-op"（3.3）。

**第二个触发点（退款路径，:1304）**：全额退款流程**同步**再调一次 confirm，注释原文："确保预扣记录被清理，避免「releaseInventory 回补 + refundRestore 回补」双通道叠加造成库存虚增，也避免预扣记录残留被 PreDeductTimeoutJob/对账二次回补。"

### 3.2 `confirm.lua` 全文 + 逐行

```lua
-- 确认扣减 Lua 脚本（原子操作）
--
-- 支付成功后，删除预扣记录（库存已经在预扣时扣减了，确认只需删除预扣记录）。
-- Redis 层面的库存不需要再变动，因为预扣时已经 DECRBY 了。
-- MySQL 层面的 locked_stock → 0 由 MQ Consumer 处理。
--
-- KEYS[1] = inventory:prededuct:{orderId}    (Hash: 预扣记录)
-- KEYS[2] = inventory:prededuct:index      (ZSet: 预扣索引, 记录全删时 ZREM orderId)
--
-- ARGV[1] = skuId
-- ARGV[2] = orderId
--
-- 返回值：
--   > 0 : 确认成功，返回确认的数量
--   0   : 预扣记录不存在
--

local predeductKey = KEYS[1]
local indexKey = KEYS[2]
local skuId = ARGV[1]
local orderId = ARGV[2]

-- 1. 获取预扣数量
local quantity = redis.call('HGET', predeductKey, skuId)
if not quantity then
    return 0  -- 预扣记录不存在
end

local qty = tonumber(quantity)

-- 2. 删除预扣记录（确认扣减 = 预扣变为正式扣减）
redis.call('HDEL', predeductKey, skuId)
redis.call('HDEL', predeductKey, skuId .. ':bucket')

-- 3. 如果预扣记录 Hash 为空，删除整个 Key 并从索引 ZSet 移除
local remaining = redis.call('HLEN', predeductKey)
if remaining == 0 then
    redis.call('DEL', predeductKey)
    redis.call('ZREM', indexKey, orderId)
end

return qty
```

逐行要点：

| 行 | 做什么 | 为什么 |
|---|---|---|
| `HGET ... skuId` | 读预扣数量 | 存在才处理；**不存在返回 0**（幂等：已确认/已过期/从未预扣都走这里） |
| `HDEL skuId` / `HDEL skuId:bucket` | 删除该 SKU 的两个 field | 只删字段不删整个 Hash——**多 SKU 订单还有其他 field** |
| `HLEN == 0 → DEL + ZREM` | 最后一个 field 删掉后清 key + 清索引 | 索引清掉的直接效果：该订单**不会再被超时释放** |
| 返回值 | `>0` 数量 / `0` 不存在 | `0` 在 Java 侧只打日志（见 3.3） |

**注意：全程没有 `INCRBY`/`DECRBY`**——这就是"confirm 不动库存"的代码证据。

### 3.3 `confirmDeduct` Java 侧（全文 + 逐段）

```java
// InventoryService.java:394-448（原文）
public void confirmDeduct(ConfirmDeductRequest request) {
    Long orderId = request.getOrderId();
    String predeductKey = predeductKey(orderId);

    // 获取预扣记录中的所有 SKU
    var entries = stringRedisTemplate.opsForHash().entries(predeductKey);
    if (entries.isEmpty()) {
        log.warn("[库存] 确认扣减-预扣记录不存在(可能已确认或已过期): orderId={}", orderId);
        return; // 幂等：已确认或已过期，不报错
    }

    // 逐个 SKU 确认
    for (var entry : entries.entrySet()) {
        String fieldName = entry.getKey().toString();
        // 过滤 :bucket 辅助字段（同 releaseStock 逻辑）
        if (fieldName.contains(":bucket")) {
            continue;
        }

        Long skuId;
        int quantity;
        try {
            skuId = Long.parseLong(fieldName);
            quantity = Integer.parseInt(entry.getValue().toString());
        } catch (NumberFormatException e) {
            log.warn("[库存] 确认扣减跳过脏数据(skuId/数量非数字): orderId={}, field={}, value={}",
                    orderId, fieldName, entry.getValue());
            continue;
        }

        // 【N10】扩容窗口保护：SKU 正在 resize 时延迟处理（confirm 只删预扣记录不动库存，
        // 但预扣记录里的桶号可能已过期，需等待 resize 完成）
        String pauseKey = "inventory:paused:" + skuId;
        if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(pauseKey))) {
            log.info("[库存] SKU正在扩容中，延迟确认: orderId={}, skuId={}", orderId, skuId);
            throw new ResizeInProgressException("SKU扩容中，稍后重试: skuId=" + skuId);
        }

        // Lua 原子删除预扣记录（传入 predeductKey + indexKey）
        Long result = stringRedisTemplate.execute(
                confirmScript,
                List.of(predeductKey, PREDEDUCT_INDEX_KEY),
                fieldName, String.valueOf(orderId)
        );

        log.info("[库存] 确认扣减: orderId={}, skuId={}, qty={}, result={}",
                orderId, skuId, quantity, result);

        // L2: MQ 异步更新 MySQL（同步发送，失败记录日志，等 L3 对账修复）
        if (!sendInventoryEvent(orderId, skuId, quantity, "CONFIRM")) {
            log.error("[库存] 确认扣减MQ发送失败(等待L3对账修复): orderId={}, skuId={}, qty={}",
                    orderId, skuId, quantity);
        }
    }
}
```

逐段：

1. **`entries.isEmpty() → return`**：整个订单没有记录 → 静默幂等返回。**这条路径不区分"已确认"和"从未预扣"**——边界见 3.5。
2. **遍历过滤 `:bucket` field**：只处理 SKU 字段（数量），跳过辅助字段。
3. **N10 扩容暂停**：`inventory:paused:{skuId}` 存在 → 抛 `ResizeInProgressException`——**半途抛异常会让前面已确认的 SKU 保持已确认、后面的重试**（异常 → 消费者重投 → 整单重放，已删的 field 自然跳过）。
4. **Lua 执行**：per-SKU 原子删记录。
5. **落 CONFIRM 事件**：L2 落账（消费者 `handleConfirm` → `locked -= qty`）——细节在 06。

### 3.4 落账端与失败收口（指向 06）

`CONFIRM` 事件由 `InventoryDeductConsumer.handleConfirm` 处理：`confirmDeduct` SQL 影响 0 行 → `CONFIRM_FAILED` → `INVENTORY_FAILED_TOPIC` → 订单侧收口（未支付自动关单 / 已支付人工）。细节见 06 §5。

### 3.5 边界（两条，第二条是疑似问题）

**① 静默 no-op 的双义性**（口径已修正过，见《工程问题台账》问题 3 相关）：

```
记录不存在 → 静默返回的三种可能：
  a. 已确认（正常重放）        → 正确
  b. 已过期被超时释放          → 特殊场景（迟到支付）
  c. 从未预扣过（残留窗口）    → 应该告警却没告警
confirm 不报错、不区分——这是设计选择（幂等优先），但掩盖了 c 类异常
```

**② 疑似边界（待评估/待记录）：confirm 失败无重试，与超时释放的交互**

```
代码事实：
  1. confirmInventoryDeductSync 对一切异常 catch + 日志，无重试、无补偿记录
  2. PreDeductTimeoutJob 到期扫描不检查订单支付状态（也无从知晓）
推演：
  14:35 支付成功（订单已置已付款）→ confirm Feign 调用失败（库存服务瞬时不可用）
  → 预扣记录不会被删
  → 15:00 超时 Job 扫描到期索引 → release.lua 把库存加回（+2）+ 发 RELEASE 事件
  → "已支付订单的货被放回货架" → 超卖风险；对账只能让 MySQL 跟随 Redis，阻止不了释放
对照：RELEASE 失败有订单侧补偿（ORDER_COMPENSATION_TOPIC + 本地兜底集合，见 4.1）——
      CONFIRM 失败没有对等机制，这处不对称值得记录与评估修复方向
```

```java
// OrderService.java:562-582 —— 释放调用 + 失败补偿（原文）
private void releaseInventory(Long orderId, String orderNo, Long userId) {
    try {
        // 库存预扣记录以 fold-hash(orderNo) 派生的 pseudoOrderId 为幂等键
        // （OrderTransactionConsumer 在半消息阶段只有 orderNo，订单未入库无法获得真实 orderId），

            log.info("[订单] 释放库存成功: orderId={}", orderId);
        }
    } catch (Exception e) {
        log.error("[订单] 释放库存异常，需补偿: orderId={}", orderId, e);
        sendCompensationMessage("RELEASE_STOCK", orderId, userId, e.getMessage());
    }

            stringRedisTemplate.opsForSet().add(ORDER_COMPENSATION_FALLBACK_KEY, member);
```

### 4.2 `release.lua` 全文 + 逐行

```lua
-- 释放库存 Lua 脚本（原子操作）
--
-- 取消订单或预扣超时时，将预扣的库存回退到来源桶。
--
-- 【修复M14】桶 Key 由调用方传入 KEYS[3]，不再在脚本内动态拼接（Cluster 兼容）。
-- 调用方需要先 HGET predeductKey {skuId}:bucket 获取桶号，再构建桶 Key 传入。
--
-- KEYS[1] = inventory:{skuId}:total               (String: 总可用库存)
-- KEYS[2] = inventory:prededuct:{orderId} (Hash: 预扣记录)
-- KEYS[3] = inventory:{skuId}:bucket:{bucketNo}   (String: 来源桶库存)
-- KEYS[4] = inventory:prededuct:index             (ZSet: 预扣索引, 记录全删时 ZREM orderId)
--
-- ARGV[1] = skuId
-- ARGV[2] = orderId
--
-- 返回值：
--   > 0 : 释放成功，返回释放的数量
--   0   : 预扣记录不存在（已释放或已确认）

local totalKey = KEYS[1]
local predeductKey = KEYS[2]
local bucketKey = KEYS[3]
local indexKey = KEYS[4]

local skuId = ARGV[1]
local orderId = ARGV[2]

-- 1. 获取预扣数量
local quantity = redis.call('HGET', predeductKey, skuId)
if not quantity then
    return 0  -- 预扣记录不存在
end

local qty = tonumber(quantity)

-- 2. 回退库存到来源桶
redis.call('INCRBY', bucketKey, qty)

-- 3. 回退总库存
redis.call('INCRBY', totalKey, qty)

-- 4. 删除预扣记录
redis.call('HDEL', predeductKey, skuId)
redis.call('HDEL', predeductKey, skuId .. ':bucket')

-- 5. 如果预扣记录 Hash 为空，删除整个 Key 并从索引 ZSet 移除
local remaining = redis.call('HLEN', predeductKey)
if remaining == 0 then
    redis.call('DEL', predeductKey)
    redis.call('ZREM', indexKey, orderId)
end

return qty
```

**confirm vs release 对照（背）**：

| 步骤 | confirm.lua | release.lua |
|---|---|---|
| 取数量 | `HGET`（无 → 返回 **0**） | `HGET`（无 → 返回 **0**） |
| 动库存 | **不动**（已扣过） | `INCRBY 桶` + `INCRBY total` |
| 删记录 | `HDEL` 两个 field | 同左 |
| 收尾 | 空则 `DEL + ZREM` | 同左 |

**"谁先谁生效"的互斥性**（Job 注释原文）：`HGET + HDEL` 在同一个 Lua 里原子执行——并发释放时只有一方能成功回退，另一方读到空（返回 0），**不会双重回退**。

### 4.3 `releaseStock` Java 侧（全文 + 逐段）

```java
// InventoryService.java:459-535（原文）
public void releaseStock(ReleaseStockRequest request) {
    Long orderId = request.getOrderId();
    String predeductKey = predeductKey(orderId);
    // 获取预扣记录中的所有 SKU
    var entries = stringRedisTemplate.opsForHash().entries(predeductKey);
    if (entries.isEmpty()) {
        log.warn("[库存] 释放库存-预扣记录不存在(可能已释放或已确认): orderId={}", orderId);
        return; // 幂等：已释放或已确认，不报错
    }

    // 逐个 SKU 释放
    for (var entry : entries.entrySet()) {
        String fieldName = entry.getKey().toString();
        // 【修复M12】过滤 :bucket 辅助字段，只处理 skuId 字段
        if (fieldName.contains(":bucket")) {
            continue;
        }

        Long skuId;
        int quantity;
        try {
            skuId = Long.parseLong(fieldName);
            quantity = Integer.parseInt(entry.getValue().toString());
        } catch (NumberFormatException e) {
            log.warn("[库存] 释放库存跳过脏数据(skuId/数量非数字): orderId={}, field={}, value={}",
                    orderId, fieldName, entry.getValue());
            continue;
        }

        // 【N10】扩容窗口保护：SKU 正在 resize 时延迟释放
        // （释放写旧桶号后 resize 用收集值覆盖 → 释放的库存丢失）
        String pauseKey = "inventory:paused:" + skuId;
        if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(pauseKey))) {
            log.info("[库存] SKU正在扩容中，延迟释放: orderId={}, skuId={}", orderId, skuId);
            throw new ResizeInProgressException("SKU扩容中，稍后重试: skuId=" + skuId);
        }

        // 获取来源桶号（release.lua 需要桶 Key 作为 KEYS[3]）
        Object bucketNoObj = stringRedisTemplate.opsForHash().get(predeductKey, fieldName + ":bucket");
        int bucketNo = 0;
        if (bucketNoObj != null) {
            try {
                bucketNo = Integer.parseInt(bucketNoObj.toString());
            } catch (NumberFormatException e) {
                // 脏桶号按桶 0 处理并告警（原实现直接 500；其它路径均容错）
                log.warn("[库存] 预扣记录桶号非法, 按桶0处理: orderId={}, skuId={}, raw={}",
                        orderId, skuId, bucketNoObj);
            }
        }

        String totalKeyStr = totalKey(skuId);
        String bucketKeyStr = bucketKey(skuId, bucketNo);

        // Lua 原子释放（传入 totalKey + predeductKey + bucketKey + indexKey）
        Long result = stringRedisTemplate.execute(
                releaseScript,
                List.of(totalKeyStr, predeductKey, bucketKeyStr, PREDEDUCT_INDEX_KEY),
                fieldName, String.valueOf(orderId)
        );

        log.info("[库存] 释放库存: orderId={}, skuId={}, qty={}, bucket={}, result={}",
                orderId, skuId, quantity, bucketNo, result);

        // L2: MQ 异步更新 MySQL（同步发送，失败记录日志，等 L3 对账修复）
        if (!sendInventoryEvent(orderId, skuId, quantity, "RELEASE")) {
            log.error("[库存] 释放库存MQ发送失败(等待L3对账修复): orderId={}, skuId={}, qty={}",
                    orderId, skuId, quantity);
        }
    }
}
```

逐段与 confirm 的差异：**多了一步"读来源桶号"**（`{skuId}:bucket`，缺省/脏数据按桶 0 + 告警）——因为库存要加回**当时扣的那个桶**。

### 4.4 超时兜底释放：`PreDeductTimeoutJob`

**为什么需要**：Redis Key 过期是"惰性删除 + 定期删除"（Job 注释原文），不保证精确过期；如果没人主动处理，过期预扣会变"幽灵锁定"（Redis 里记录到期了、库存却没还）。

```java

    long cutoffMs = System.currentTimeMillis();
    java.util.Set<String> expiringOrderIds = stringRedisTemplate.opsForZSet()
            .rangeByScore(PREDEDUCT_INDEX_KEY, 0, cutoffMs);
    ...

        String key = PREDEDUCT_KEY_PREFIX + orderIdStr;
        int released = releasePreDeduct(key);

            stringRedisTemplate.opsForZSet().remove(PREDEDUCT_INDEX_KEY, orderIdStr);
        }
        releaseCount += released;
    }

}
```

`releasePreDeduct` 内部：按 SKU 逐条调 **release.lua**（与 4.3 相同的脚本）+ 发 `RELEASE` 事件（Job 注释："Redis 回退成功后，RELEASE 事件同步发 MQ 并保留 Outbox，避免 MySQL locked_stock 永久掉队"）。

**三个释放者（用户取消 / 超时关单 × 超时 Job / 补偿重试）互不打架**，靠的就是 4.2 的原子性 + `result == 0` 的幂等语义。

**注意**（与 3.5② 呼应）：该 Job **只看到期时间，不检查订单支付状态**——confirm 失败的已支付订单，记录到期后会被它释放。

### 4.5 落账端

`RELEASE` 事件 → `InventoryDeductConsumer.handleRelease`（06 §5）：`releaseStock` SQL 影响 0 行 → **只记日志**（"等待 L3 对账修复"）——RELEASE 失败不影响资金链路，不打扰订单侧。

## 5. 边界与口径（背）

1. **CONFIRM 不动库存**（预扣时已扣，只删记录+清索引）；**RELEASE 动库存**（加回来源桶 + 总库存）。两条语义别混。
2. **记录不存在均为静默 no-op**，但含义不同：confirm 是"已确认/已过期"；release 是"已释放/已确认"。共同作用：让重放安全。
3. **互斥靠 Lua 原子**：`HGET + HDEL` 同脚本——并发释放/确认只有一个生效，不存在双重回退。
4. **失败面不对等**：RELEASE 失败有订单侧补偿链（ORDER_COMPENSATION_TOPIC + 本地兜底集合 + 消费重试 + DLQ）；CONFIRM 失败**仅日志**——疑似边界（3.5②），待评估修复方向（如：confirm 失败落补偿表重试 / 超时 Job 释放前查询订单状态 / 支付侧对确认结果做回查）。
5. **退款前 confirm 先行**（:1304）：防"release 回补 + refundRestore 回补"双通道叠加造成库存虚增。
6. **N10 扩容窗口**：confirm/release 都要等 `inventory:paused:{skuId}` 消失再执行（抛异常重试）。
7. 引用编号核对：`M12`（过滤 :bucket）、`N10`（扩容保护）、`T-070`（支付失败补 cancelled_at）、`P0-6`（支付回调竞态不抛 500）均来自源码注释原文。
