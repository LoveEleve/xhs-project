# 01 · 业务篇：库存的业务、调用方与四条链路

> 读完本篇能回答：库存服务在平台上扮演什么角色、谁在用它、货是怎么流动的、为什么预扣走 MQ 而确认走 Feign。

---

## 1. 例子先行：一件商品的库存一世

| 时刻 | 事件 | Redis（主账） | MySQL（备份账） | 代码入口 |
|---|---|---|---|---|
| T0 | 商品上架，初始化 100 件 | total=100、桶 50+50 | available=100 | `initStock`（商品建 SKU 后自动 / 管理端） |
| T1 | 用户下单（订单 888，买 1 件） | total=99 + 写欠条 | available 还是 100（等落账） | 订单事务消息 → `OrderTransactionConsumer` → `preDeduct` |
| T2 | 落账消息被消费 | — | available=99、locked=1 | `InventoryDeductConsumer`（PRE_DEDUCT） |
| T3a | 支付成功 | **撕欠条（数字不动）** | 该单 locked 减 1（本例回 0） | Feign `/confirm` → `confirmDeduct` |
| T3b | 取消订单（T3a 之前） | total 回 100，撕欠条 | 该单 locked 减 1、available 回 100 | Feign `/release` → `releaseStock` |
| T3c | 一直不付钱 | 订单侧 30min 延时关单 + 库存侧兜底 Job 自动回退 | 同 T3b | `orderClose` → release；兜底 `PreDeductTimeoutJob`（60s） |
| T4 | 退款 | total/桶 +1 | available +1 | Feign `/refund-restore` → `refundRestore` |

> 一句话：**下单"占"、支付"成"、取消"还"、退款"补"**；Redis 实时主账，MySQL 慢半拍备份账。

## 2. 对外能力（4 写 + 1 查）

| 操作 | 触发方 | 方式 | 幂等手段 | 失败兜底 |
|---|---|---|---|---|
| 预扣 `preDeduct` | 订单服务（下单） | **MQ 事务消息** | msgId + Lua HGET + MySQL 幂等占位 | 崩溃→Outbox 补发；发送失败→作废+回滚（回滚失败落补偿）；L2 失败→收口 |
| 确认 `confirm` | 订单服务（支付成功） | Feign | 欠条不存在 → 直接跳过 | 事件失败 → L3 对账 |
| 回退 `release` | 订单服务（取消）/ 库存超时 Job | Feign / 内部 | 同上 + Lua 原子 | 调用方重试 / 下次扫描重试 / 对账 |
| 回补 `refundRestore` | 订单 / 售后（退款） | Feign | **累计正增量** | 补偿表（type=2） |
| 查询 `getStock` | 商品服务（详情/列表展示） | Feign | — | 读 MySQL 兜底（不回填） |

接口细节见《掌握地图》8.2；鉴权：管理端 `X-Admin-Call` / 内部服务 `X-Internal-Call`（`AccessTokenGuard`，启动时强制校验已配置）。

## 3. 调用方全景

```
[下单]     订单服务 ──MQ 事务消息(ORDER_TRANSACTION_TOPIC)──▶ 预扣
[支付成功] 订单服务 ──Feign /confirm─────────▶ 确认
[取消]     订单服务 ──Feign /release─────────▶ 回退
[退款]     订单/售后 ──Feign /refund-restore──▶ 回补
[看库存]   商品服务 ──Feign /stock/{skuId}───▶ 查询
[建账]     商品(建 SKU 后自动, X-Internal-Call) / 管理端(X-Admin-Call) ──▶ /init /reinit
[反向]     库存 ──MQ(INVENTORY_FAILED_TOPIC)──▶ 订单侧收口（待付款自动取消 / 已付款人工）
[自转]     库存内部：4 个 Job + 3 个消费者
```

## 4. 四条链路时序

### 4.1 下单链路（本篇最重要的"为什么"）
- 订单服务：先发**半消息**（对消费者不可见）→ 执行**本地事务**（写订单 + 事件 + 本地消息表，同一个 DB 事务）→ 提交事务消息 → 消息才对消费者可见
- 库存消费者收到消息 → 对订单里**每个 SKU** 调一次预扣
- **为什么走 MQ 而不是 Feign**：预扣必须和"订单创建"处于**同一个一致性边界**——本地事务提交后消息才对消费者可见；若 Producer 中途崩溃，Broker 会**回查本地事务状态**来决定消息投递；库存服务哪怕当时挂了，消息重投也能把库存补上。普通 Feign 是一次性 RPC，失败就断在那，订单与库存"同生共死"无从保证。
- 失败路径（两条要分开）：
  - **入口预扣失败**（如库存不足）→ 抛异常触发 MQ 重试（最多 5 次）→ 超限进 DLQ
  - **L2 落账最终失败** → 发 `INVENTORY_FAILED_TOPIC` → 订单侧收口

### 4.2 支付链路
order 支付成功 → Feign `confirm`（同步）→ **撕欠条** + 发 CONFIRM 事件 → MySQL `locked` 清零。
- 幂等：欠条不存在直接返回；重复回调无害
- 事件发送失败：只记日志，等 L3 对账

### 4.3 取消 / 超时链路
- 主动取消：order → Feign `release`（回原桶）
- 超时未支付（订单侧）：RocketMQ 延时消息（**30 分钟**）+ `orderCloseJob` 每分钟兜底扫描 → 关单 → Feign `release`
- 超时兜底（库存侧）：`PreDeductTimeoutJob` 扫"闹钟"（ZSet 索引）→ `release` + RELEASE 事件（防订单侧漏关）
- 所有路径都走 `release.lua` 原子操作（HGET+HDEL 原子）→ **不会双重回退**

### 4.4 退款链路
- 售后退款成功 → order/售后 → Feign `refundRestore`
- **语义独立（T-071）**：confirm 之后欠条已撕，退款不能走 release；所以有独立的"回补"
- 幂等靠 `inventory:refund:{orderId}:{skuId}` 的**累计正增量**（第 7 篇详解）

## 5. 一致性边界（把"为什么"讲成人话）

| 动作 | 走什么 | 边界 | 为什么 |
|---|---|---|---|
| 预扣 | MQ 事务消息 | 与订单创建同一事务边界 | 订单在，库存必扣；失败了能重投/回查 |
| confirm / release / 退款 | Feign 同步 | 订单已提交后的后续动作 | 失败可重试 + 对账兜底，不需要进订单事务 |
| 失败收口 | 反向 MQ | 库存 → 订单 | 已提交订单发现库存失败：待付款自动取消、已付款人工 |

## 6. 业务规则与取舍

- **允许少卖，绝不允许超卖**（分桶/借桶都不能破这条）
- 预扣有效期 30 分钟（物理记录再加 600s 缓冲）
- 扩容窗口内：预扣/确认/回退/回补四条链路全部延迟重试（N10）
- Redis 是实时主账；MySQL 允许慢半拍；对账以 Redis 为准
