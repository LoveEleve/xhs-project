## 1. 它是什么（一次调用干一笔"订单×SKU"的预扣）

- 调用方：`InventoryService.doPreDeduct`（04 篇）——把 KEYS/ARGV 组装好传进来；
- 一次 Lua 调用只处理**一个订单的一个 SKU**（多 SKU 订单 = Java 循环多次调用，幂等粒度 `(orderId, skuId)`）；
- 脚本要么全做（幂等检查 → 库存检查 → 扣减 → 写记录 → 写索引），要么不做（提前 return 返回码）——**中间没有并发插入的机会**（Redis 单线程执行脚本）。

真实数据贯穿（示例）：

```
订单伪ID = 5080522866062586953   SKU = 1001   数量 = 2
expireSeconds = 1800（30 分钟）  recordTtl = 2400（40 分钟 = 1800 + 600 缓冲）
```

执行前状态：

```
inventory:{1001}:total                  = "100"
inventory:prededuct:5080522866062586953 = 不存在
inventory:prededuct:index               = 空 ZSet
```

执行后（成功）：

```
inventory:{1001}:total                  = "98"
inventory:prededuct:5080522866062586953 = { "1001": "2" }        (TTL 2400s)
inventory:prededuct:index               = { member=5080…, score=15:00:00 的毫秒戳 }
```

## 2. 头注释 = 跨语言契约

脚本头部的 KEYS/ARGV/返回码声明，**就是 Java `execute(script, keys, args...)` 的对齐依据**（04 讲过对齐原则）：

```
KEYS[1] = inventory:{skuId}:total         (String: 总可用库存)
KEYS[2] = inventory:prededuct:{orderId}   (Hash: 预扣记录)
KEYS[3] = inventory:prededuct:index       (ZSet: member=orderId, score=到期时间戳ms)

ARGV[1] = skuId
ARGV[2] = orderId
ARGV[3] = quantity
ARGV[4] = expireSeconds      (业务到期时间，秒)
ARGV[5] = recordTtlSeconds   (记录物理 TTL，秒 = 到期 + 缓冲)

返回： 1=成功  0=库存不足  -1=重复预扣  -2=未初始化
```

> KEYS 的**顺序**和 ARGV 的**顺序**必须与 Java 实参严格一一对应——错位轻则行为错、重则脚本崩溃。

## 3. 去桶版全文（主教材）

```lua
-- ============================================================
-- 去桶版 preDeduct（预扣减）
-- KEYS[1] = inventory:{skuId}:total         (String: 总可用库存)
-- KEYS[2] = inventory:prededuct:{orderId}   (Hash: field=skuId → quantity)
-- KEYS[3] = inventory:prededuct:index       (ZSet: member=orderId, score=到期时间戳ms)
--
-- ARGV[1] = skuId
-- ARGV[2] = orderId
-- ARGV[3] = quantity
-- ARGV[4] = expireSeconds      (业务到期时间，秒)
-- ARGV[5] = recordTtlSeconds   (记录物理 TTL，秒 = 到期 + 缓冲)
--
-- 返回： 1=成功  0=库存不足  -1=重复预扣  -2=未初始化
-- ============================================================

local totalKey     = KEYS[1]
local predeductKey = KEYS[2]
local indexKey     = KEYS[3]

local skuId  = ARGV[1]
local orderId = ARGV[2]
local quantity = tonumber(ARGV[3])
local expireSeconds = tonumber(ARGV[4])
local recordTtlSeconds = tonumber(ARGV[5])

-- 0. 幂等检查：同一订单同一 SKU 不能重复预扣
local existingQty = redis.call('HGET', predeductKey, skuId)
if existingQty then
    return -1
end

-- 1. 库存未初始化检查
local totalStock = redis.call('GET', totalKey)
if not totalStock then
    return -2
end

-- 2. 库存充足检查
if tonumber(totalStock) < quantity then
    return 0
end

-- 3. 到期时间戳（毫秒），用于超时索引 score
local time = redis.call('TIME')
local expireAtMs = time[1] * 1000 + expireSeconds * 1000

-- 4. 扣减 + 写预扣记录 + 写超时索引
redis.call('DECRBY', totalKey, quantity)
redis.call('HSET', predeductKey, skuId, quantity)
redis.call('EXPIRE', predeductKey, recordTtlSeconds)
redis.call('ZADD', indexKey, expireAtMs, orderId)

return 1
```

## 4. 逐段讲解（真实数据）

### 第 0 段：幂等检查

```lua
local existingQty = redis.call('HGET', predeductKey, skuId)
if existingQty then
    return -1
end
```

| 执行 | 返回 | 含义 |
|---|---|---|
| `HGET inventory:prededuct:5080… 1001` → `(nil)` | 继续 | 这个 (订单, SKU) 没扣过 |
| `HGET … 1001` → `"2"` | **-1** | 该 (订单, SKU) 已扣过 → 重复预扣，拒绝 |

- 这就是"**幂等粒度 = (orderId, skuId)**"的物理形态：一个订单一个 Hash，一个 SKU 一个 field；
- 值本身（"2"）在这个分支只用于**判断存在性**；它的真实含义（上次扣的数量）供 confirm/release 使用；
- 命中返回 `-1` 是**正常返回码**（不是报错）——Java 侧把它当"已办成功"处理（04 的 switch）。

### 第 1 段：未初始化检查

```lua
local totalStock = redis.call('GET', totalKey)
if not totalStock then
    return -2
end
```

- `GET` 为 `nil`（key 不存在，如被 canal 删除）→ `-2`。**fail-closed**：不知道库存就不动手；
- 与 Java 前置检查（含 `rebuildStockFromDb` 自愈）形成纵深——Java 挡大部分，这里是竞态兜底。

### 第 2 段：库存充足检查（防超卖核心）

```lua
if tonumber(totalStock) < quantity then
    return 0
end
```

- `"100"` ≥ `2` → 继续；若 `"1"` < `2` → `0`；
- **与随后的 `DECRBY` 在同一个脚本里**——Redis 单线程执行期间没有命令能插队，从设计上消灭 check-then-act 竞态（所以不需要锁）。

### 第 3 段：到期时间戳

```lua
local time = redis.call('TIME')
local expireAtMs = time[1] * 1000 + expireSeconds * 1000
```

- 用 **Redis 服务器时间**（非客户端时间）：避免多客户端时钟漂移；
- 真实数据：`TIME → ["1791527400", "500000"]`（= 14:30:00）→ `expireAtMs = 1791529200000`（= 15:00:00）；
- 为什么换算成**绝对时间戳**：它要当 ZSet 的 score，超时 Job 用 `ZRANGEBYSCORE index -inf now` 扫"已到期"的订单——相对值没法做范围查询。

### 第 4 段：四连写（核心）

```lua
redis.call('DECRBY', totalKey, quantity)          -- ① 扣总库存
redis.call('HSET', predeductKey, skuId, quantity) -- ② 写预扣记录（field=skuId → 数量）
redis.call('EXPIRE', predeductKey, recordTtlSeconds) -- ③ 记录物理 TTL
redis.call('ZADD', indexKey, expireAtMs, orderId) -- ④ 写超时索引（score=到期时刻）
```

| 命令（真实参数） | 效果 |
|---|---|
| `DECRBY inventory:{1001}:total 2` | `"100"` → **`"98"`** |
| `HSET inventory:prededuct:5080… 1001 2` | Hash 从无到有：**`{ "1001": "2" }`** |
| `EXPIRE inventory:prededuct:5080… 2400` | 该 Hash 的 TTL = 2400 秒（15:10 物理消失） |
| `ZADD inventory:prededuct:index 1791529200000 5080…` | 索引新增 member，score=15:00:00 |

两个易错点：

1. **ZADD 参数顺序是 `score → member`**（先分值后成员）。写反了两者都是数字、不报错，但语义全坏：超时 Job 用 `ZRANGEBYSCORE` 查"已到期"会永远扫不到。
2. **`EXPIRE` 用的是 `recordTtlSeconds`（不是 `expireSeconds`）**——两个时间的差别见 §6。

### 收尾：`return 1`

告诉 Java 侧"扣减成功"——04 的 switch 里 `case 1` 会打点 + 落 L2 事件（Outbox）。

## 5. 两个必须理解的性质

1. **原子执行**：整段脚本在 Redis 中不可分割——"查幂等 → 查库存 → 扣减 → 写记录 → 写索引"五步没有并发窗口。这是"无锁防超卖 + 无锁防重复扣"的来源。
2. **原子 ≠ 事务回滚**：脚本中途若某条命令报错，**之前的写入不会撤销**。所以脚本遵循"**fail-before-write**"——所有可能提前返回的判断（幂等、未初始化、库存不足）全部放在写入段之前；写入段只保留不会失败的基础命令。

---

## 6. 两个时间参数 + 索引 ZSet 的用途

| 参数 | 值（例子） | 写在哪 | 被谁消费 | 含义 |
|---|---|---|---|---|
| `expireSeconds` | 1800s（30min） | 算出 `expireAtMs` → ZADD score | 超时 Job | **业务到期**：30 分钟没支付就该释放 |
| `recordTtlSeconds` | 2400s（40min = 1800+600） | `EXPIRE` | Redis 自身 | **记录物理寿命**：保证超时 Job 到期后来释放时，**记录还在** |

- 时间线：14:30 写入（TTL 到 15:10）→ 15:00 到期，超时 Job 扫到 → 读记录（还活着）→ 回退；
- 历史修复（脚本注释原文）："原先 TTL==score，任务只能提前 60s 释放，窗口内支付确认会找不到记录"——加 600s 缓冲后两个问题都消失；
- 索引 ZSet（`inventory:prededuct:index`）：给超时 Job 做 O(logN+M) 的范围扫描，替代全库 SCAN；订单 confirm/release 完成时会把 member 移除（首选），Job 发现记录不存在时也会清理陈旧 member（兜底）。

## 7. 返回码 → Java 侧对照（回顾 04）

| Lua 返回 | 含义 | Java 侧动作（`doPreDeduct` switch） |
|---|---|---|
| `1` | 成功 | 打点 → 落 L2 事件（失败则回滚 Redis + 抛错） |
| `0` | 库存不足 | 打点 insufficient → 抛 `STOCK_NOT_ENOUGH` |
| `-1` | 重复预扣 | 记日志 → **按成功处理**（幂等） |
| `-2` | 未初始化 | 抛 `SKU_STOCK_NOT_INITIALIZED`（重试时触发重建） |
| 其它 | 未知 | 抛错（协议漂移必须暴露） |

## 8. 真实版差异对照（桶相关——非教学重点，读代码时对照用）

真实版 = 去桶版 + 一组桶机制。差异逐项：

| 维度 | 去桶版 | 真实版（仓库 prededuct.lua） |
|---|---|---|
| KEYS | `[total, prededuct, index]` | `[total, prededuct, bucket:0..N-1, index]`（M14：全部经 KEYS 传参，Cluster 兼容规范） |
| ARGV | 5 个 | 8 个（+bucketCount、+userId[备用]、+routeBucket） |
| 路由 | 无（直接扣 total） | `routeBucket` 由 **Java 侧**精确取模传入（T-073：Lua 双精度对 >2^53 雪花 ID 取模失真恒偏） |
| 扣减段 | 一段四连写 | 两段：先试路由桶；不足则**遍历其他桶**（桶间均衡） |
| 记录 | `HSET skuId=quantity` | 多记一个 `HSET skuId:bucket=sourceBucket`（供 release 回退到原桶） |
| 超时索引 | ZADD（相同） | ZADD（相同，score/member 顺序同样易错） |

> 教学时按去桶版理解语义（幂等/检查/扣减/记录/索引五件事不变）；真实版多出来的只是"从哪个桶扣"的分支。
> 分桶收益口径（已结论化）：单实例/同 slot 下无吞吐收益，不写简历，面试可讲边界——《工程问题台账》问题 1 + `01-库存.md` 补充章。

## 9. 边界与口径（背）

1. **返回码区分严格**：`-1`（该订单×SKU 已扣过）与 `0`（库存不足）语义完全不同；`-2` 与 `0` 也不同——Java 侧对它们的处理各不相同。
2. **幂等是双层**：本脚本的 `HGET` 是第二层；第一层是 Java 侧更早的 **MySQL 幂等占位**（T-079，insert 探测）——两层的目的、触发条件不同（04/06 都讲过）。
3. **fail-before-write 的保证边界**：判断都前置 + 写入段不会失败 + 脚本原子——三者合起来才等值于"要么全做、要么不做"。Redis 不提供脚本回滚。
4. **时钟口径**：到期时间以 **Redis 服务器时间**为准（`TIME`），不是应用节点时间。
5. 记录物理 TTL = 业务到期 + 600s 缓冲（历史 T-段修复）：这是"超时任务到期后仍可读记录"的关键。
