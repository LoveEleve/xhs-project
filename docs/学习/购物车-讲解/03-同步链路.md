# 03 · 同步链路：顺序消息 + 时间戳 CAS + CLEAR 屏障

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：Redis 写完 → **顺序消息（userId 分区）** → 消费端 **UPSERT + 时间戳 CAS + CLEAR 屏障** → MySQL 兜底；
> 顺序是主防线，CAS/屏障是乱序兜底。
>
> **本篇带走**：① 顺序消息 ② 时间戳 CAS ③ CLEAR 屏障 ④ 事件流水 ⑤ 边界与债。
> 前置：02。证据：`CartService.sendCartSyncEvent`、`CartSyncConsumer`、`CartEventSinkConsumer`、C-006。

---

## 0. 例子：同用户加购 → 删除 → 加购

```
① 加购 1001（qty 1） → CART_TOPIC:ADD    → UPSERT
② 删除 1001          → CART_TOPIC:DELETE → timestamp CAS 后删
③ 再加购 1001（qty 2）→ CART_TOPIC:ADD    → UPSERT（createdAt/updatedAt=eventTime）

如果③的旧消息先到、②后到：
  时间戳 CAS 会跳过旧事件；CLEAR 屏障还会挡住清空前的旧写。
```

## 1. 生产环境怎么做（淘宝/行业常见）

| 问题 | 常见做法 |
|---|---|
| 顺序 | 同一聚合根（userId）固定分区；消费端顺序消费 |
| 乱序兜底 | 版本号/时间戳 CAS；最后写入优先 |
| 删除/清空 | 屏障/墓碑，挡住屏障前的旧事件 |
| 幂等 | 唯一键 UPSERT / 事件 ID |
| 失败 | MQ 重试 + 对账；Redis 权威，落库可滞后 |

## 2. 本项目的实现（代码证据）

### 2.1 发送：`CART_TOPIC:{action}` + userId 分区

```java
// 事件时间：毫秒 + 单调序列号（防同毫秒误判）
Instant eventTs = Instant.ofEpochMilli(System.currentTimeMillis())
        .plusNanos(EVENT_SEQ.incrementAndGet());
event.setTimestamp(eventTs);
if ("CLEAR".equals(action)) event.setClearBarrierTs(eventTs.toEpochMilli());
// clearBarrierTs 仅随事件携带/日志；消费端屏障值取 eventTime

rocketMQTemplate.asyncSendOrderly(
        CART_TOPIC + ":" + action,       // topic:tag（ADD/UPDATE/DELETE/...）
        message,
        String.valueOf(userId),          // 分区键：同一用户固定同一队列
        callback);
```

- **同一 userId 固定同一 MessageQueue** → 消费端 `ConsumeMode.ORDERLY` → 从源头保证同用户事件顺序；
- **单调序列号**：`System.currentTimeMillis()` 同毫秒时用 nanos 区分（C-05）；
- **MQ 失败不影响购物车**：Redis 已是权威，失败只记日志（对账兜底，05）。

### 2.2 消费：UPSERT + 时间戳 CAS

`CartSyncConsumer`（`CART_TOPIC`，`ORDERLY`，`maxReconsumeTimes=3`）：

```java
switch (action) {
    case "ADD", "UPDATE" -> upsertCartItem(event);
    case "DELETE"        -> deleteCartItem(event);
    case "CHECK"         -> updateCheckedStatus(event);
    case "CHECK_ALL"     -> checkAllItems(event);
    case "CLEAR"         -> clearCartItems(event);
}
```

**UPSERT**：先 `INSERT`，`DuplicateKeyException` 转 `UPDATE`（`uk_user_sku` 兜底并发）。

**时间戳 CAS**（所有写路径）：

```java
LocalDateTime eventTime = LocalDateTime.ofInstant(event.getTimestamp(), ZoneId.systemDefault());
if (existing.getUpdatedAt() != null && !existing.getUpdatedAt().isBefore(eventTime)) {
    return;   // DB 时间 >= 事件时间 → 旧事件，跳过
}
```

- 用**生产者时钟**（eventTime）而非消费者 `now()`，统一时钟域；
- `DELETE`/`CHECK`/`CHECK_ALL` 都做同样的 CAS；
- `CHECK` 对应条目不存在 → 跳过（不凭空创建幽灵项）；
- `upsert` 时 `createdAt`/`updatedAt` 都设为 `eventTime`；**CLEAR 实际按 `updatedAt` 过滤**（代码注释仍写 `createdAt`，属注释漂移）。
  副作用：MySQL 的 `createdAt` 变成最后写入时间，Redis 丢失后恢复排序用它（见 04）。

### 2.3 CLEAR 屏障：进程内、有界、ORDERLY 假设

```java
private static final ConcurrentHashMap<Long, LocalDateTime> CLEAR_BARRIERS = new ConcurrentHashMap<>();

private void putClearBarrier(Long userId, LocalDateTime clearTime) {
    CLEAR_BARRIERS.put(userId, clearTime);
    // 超 5 万条才清理：先淘汰 24h 前；仍超则整体清空（退化为时间戳 CAS）
}
```

- `CLEAR` 先写屏障，再删 `updatedAt < eventTime` 的行；
- 后续 `ADD/UPDATE/DELETE/CHECK/CHECK_ALL` 若 `eventTime < barrier` → 跳过；
- **进程内、多实例不共享**：依赖"ORDERLY 同用户同队列"；重启/rebalance 后屏障丢失，退化为时间戳 CAS；
- **有界**：条目数超过 5 万时，先淘汰 24h 前条目；仍超则整体清空（**不是定时淘汰**，平时旧条目会留着）。

### 2.4 事件流水：独立消费组、append-only

`CartEventSinkConsumer`（`cart-event-sink-group`，ORDERLY）：

```java
INSERT INTO t_cart_event (id, user_id, sku_id, action, quantity, checked, event_time, msg_id)
```

- **幂等**：`MessageIdempotentHelper`（msgId 24h）+ `uk_msg_id`；
- **购物车级动作**（CLEAR/CHECK_ALL）无具体 SKU → `sku_id=0` 哨兵；
- 与 `cart-sync-consumer-group` 互不影响（一个失败不拖另一个）；
- 保留 30 天，供漏斗/分析。

> ⚠️ 事件流水消费者用 `isFirstProcess` **前置标记**：标记后、insert 前崩溃 → 重投被跳过（只影响分析流水，不影响主链路）；属于已知债。

### 2.5 边界与已知债

| 点 | 现状 |
|---|---|
| 时钟 | 生产者时钟 + 同毫秒序列号；多实例时钟倾斜仍可能乱序（CAS 兜底） |
| DB 精度 | `init-all` 是 `DATETIME(3)`；`migration/content/V1` 仍是 `DATETIME`（漂移）；eventTime 带 nanos，比较在 Java 层，落库截断 |
| 屏障 | 进程内；重启/rebalance 退化时间戳 CAS |
| MQ 失败 | 不影响购物车；对账修复 |
| 事件流水 | 前置标记崩溃窗口（分析数据） |

## 3. 对照表：生产 vs 本项目

| 能力 | 生产环境 | 本项目 | 差异 |
|---|---|---|---|
| 顺序消息 | 聚合根分区 | ✅ userId 分区 + ORDERLY | 对齐 |
| 乱序兜底 | 版本/时间戳 CAS | ✅ eventTime CAS | 对齐 |
| 清空屏障 | 屏障/墓碑 | ⚠️ 进程内 + 有界 | 简化 |
| 幂等 | 唯一键 | ✅ uk_user_sku/uk_msg_id | 对齐 |
| 落库失败 | 重试+对账 | ✅ 重试 + 对账 | 对齐 |
| 事件流水 | append-only | ✅ 30 天 | 对齐 |

## 4. 十二个坑

1. **不按 userId 分区**：同用户消息乱序；CAS 只能兜底，不能保证语义顺序。
2. **消费端不是 ORDERLY**：分区有序也白费；必须 `ConsumeMode.ORDERLY`。
3. **没有时间戳 CAS**：旧 ADD/DELETE 覆盖新状态。
4. **同毫秒不区分**：`currentTimeMillis` 相同被 `!isBefore` 跳过；用 nanos 序列号。
5. **用消费者 now()**：时钟域不一致；用生产者 eventTime。
6. **CLEAR 用 createdAt 删**：会误删清空后重新加购的行；用 `updatedAt < eventTime`。
7. **屏障清理时机**：不是定时淘汰；只有超 5 万条才清 24h 前/整体清空，平时旧条目会留着。
8. **屏障重启/重平衡丢失**：进程内、多实例不共享；依赖 ORDERLY，退化 CAS，别假设永久有效。
9. **CHECK 先到**：条目不存在不能凭空创建；跳过等主事件/对账。
10. **UPSERT 不捕获 DuplicateKey**：并发消费 insert 冲突；捕获转 update。
11. **MQ 失败当写失败**：Redis 权威；失败只影响落库，对账兜底。
12. **事件流水前置标记**：崩溃窗口丢分析事件；主链路不受影响（已知债）。

## 5. 值不值得深挖 / 一句话

- **值得**：顺序消息 + 时间戳 CAS + CLEAR 屏障——"Redis 权威、MySQL 兜底"的核心；
- **一句话带过**：序列号实现、屏障上限；
- **一句话**：**顺序是主防线（userId 分区 + ORDERLY），CAS 是乱序兜底，CLEAR 屏障挡清空前旧事件；MySQL 只是兜底。**
- 对账/恢复见 **05**；清车/回补见 **06**。

**面试口径**："购物车写 Redis 后发 `CART_TOPIC:{action}`，以 userId 为分区键 `asyncSendOrderly`，消费端 ORDERLY；落库用 uk_user_sku UPSERT + 生产者 eventTime 时间戳 CAS；CLEAR 用进程内屏障挡清空前旧事件（有界，重启退化 CAS）；事件流水独立消费组 append-only。"
