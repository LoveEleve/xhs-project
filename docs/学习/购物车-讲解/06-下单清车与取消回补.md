# 06 · 下单清车与取消回补

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：下单清车/取消回补 = **跨两个订单事件的分布式联动**；用**三标记 + 定序握手**
> 解决"孤儿窗口"和"重复投递抬数量"。
>
> **本篇带走**：① 事件与载荷 ② 清车 ③ 回补 ④ 三标记定序握手 ⑤ 边界/残余。
> 前置：02/03。证据：`CartOrderLinkageService`、`OrderCreatedCartConsumer`、`OrderTerminationCartConsumer`、C-006。

---

## 0. 例子：四种时序

```
① 正常：下单(source=CART) → 清车；支付成功 → 不回补
② 取消：下单 → 清车；取消/超时/支付失败 → 回补（merge max）
③ 秒取消竞态：回补先到、清车后到 → 定序握手，恰好一方 merge
④ 直接购买(source=DIRECT) → 从不清车；终结置 pending 后自然过期（零副作用）
```

## 1. 生产环境怎么做（淘宝/行业常见）

| 问题 | 常见做法 |
|---|---|
| 下单清车 | 订单创建事件 → 仅购物车来源清车；直接购买不碰 |
| 取消回补 | 订单终结事件 → 回补已购项（保留购买意图） |
| 乱序 | 事件带来源/明细；标记位/状态机定序 |
| 重复 | 去重标记（已清/已补）+ 幂等 merge |
| 兜底 | Outbox/DLQ；对账（演进） |

## 2. 本项目的实现（C-006）

### 2.1 事件与载荷

**创建事件**（`ORDER_TRANSACTION_TOPIC`）：

```json
{"orderNo":"...","userId":...,"skuItems":[{"skuId":...,"quantity":...}],"source":"CART|DIRECT"}
```

- `source` 由前端下单透传（`OrderCreatePage` 的 `state.source==='cart' ? 'CART' : 'DIRECT'`）；
- 消费组 `cart-order-created-group`；**仅 `source=CART` 清车**。

**终结事件**（`ORDER_TERMINATION_TOPIC`）：

```json
{"orderId":...,"orderNo":"...","userId":...,"reason":"...","items":[{"skuId":...,"quantity":...}],"eventVersion":2}
```

- 五类终结（用户取消/超时/库存失败/券失败/支付失败）都触发回补；
- 旧版事件（`eventVersion=1`，无 items）→ 安全跳过；
- 消费组 `cart-order-termination-group`。

### 2.2 清车：source=CART + cleared 去重

```java
public void handleOrderCreated(String orderNo, Long userId, String source, List<LinkageItem> items) {
    if (!"CART".equalsIgnoreCase(source)) return;          // 直接购买不碰
    String clearedKey = markerKey("cleared", orderNo);
    if (hasKey(clearedKey)) {                              // 重复投递：已清过
        // F1 深审查：若 pending 存在且未 restored，说明握手回补未完成 → 补做
        if (hasKey(pendingKey) && !hasKey(restoredKey)) restoreItems(...);
        return;
    }
    cartService.removeBySkus(userId, skuIds);              // cart_remove_batch.lua
    set(clearedKey, "1", 7d);
    if (hasKey(pendingKey)) restoreItems(...);             // 竞态：回补先到
}
```

- **cleared 去重**：防重复投递把用户清车后**新加购**的商品删掉；
- **F1 部分失败重入**：cleared 已存在但握手回补未完成 → 补做，避免"商品被清后永不回补"。

### 2.3 回补：pending 先置 + cleared 再查

```java
public void handleOrderTerminated(String orderNo, Long userId, List<LinkageItem> items) {
    if (hasKey(restoredKey)) return;                       // 重复：已回补，防抬回数量
    setIfAbsent(pendingKey, "1", 1h);                      // ① 先置 pending
    if (hasKey(clearedKey)) {                              // ② 再查 cleared
        restoreItems(orderNo, userId, items, pendingKey);
    } else {
        // 清车未到/直接购买：pending 挂起，等清车侧消费或 1h 过期
    }
}
```

`restoreItems`：

```java
for (item : items) {
    cartService.mergeItem(userId, skuId, quantity);       // merge=max，失败抛出重试
}
setIfAbsent(restoredKey, "1", 7d);                        // 整批成功后置
delete(pendingKey);
```

- **merge=max**：用户调小后重复投递不会抬回；
- **新项默认勾选**；**已有项保留用户勾选**（`cart_merge_item` 不触碰 checked）——
  PRD 写的是"checked=true"，代码对已有项**没有强制**（已知偏差）；
- 失败抛出 → MQ 重试；restored 未置位，merge 幂等收敛。

### 2.4 三标记 + 定序握手

| 标记 | TTL | 含义 |
|---|---|---|
| `cleared:{orderNo}` | 7 天 | 清车已执行 |
| `restore-pending:{orderNo}` | 1 小时 | 回补已到达、等清车 |
| `restored:{orderNo}` | 7 天 | 回补已完成 |

**操作序（关键）**：

```
restore：① SETNX pending → ② 查 cleared（有 → merge + SETNX restored + 删 pending）
clear：  ① 批量移除 → ② SET cleared → ③ 查 pending（有 → merge + SETNX restored + 删 pending）
```

- **回补先到**：pending 已置；clear 完成后查 pending → merge；
- **清车先到**：cleared 已置；restore 查 cleared → merge；
- **任意到达序恰好一方 merge**；重复投递由 restored/cleared 去重；
- **clear 永久失败**：商品从未被清，restore 看到无 cleared → 挂起，自愈；
- **直接购买**：source≠CART，pending 自然过期，零副作用。

### 2.5 测试与指标

- `CartOrderLinkageServiceTest` 11 例：正常清车/回补、重复投递、竞态两到达序、部分失败重入、直接购买；
- `OrderCreatedCartConsumerTest` 2、`OrderTerminationCartConsumerTest` 2；
- 指标：`myxhs_cart_order_linkage_total{op,result}`、`myxhs_cart_linkage_handshake_total{path=restore-arrived-first}`。

### 2.6 边界与残余

| 点 | 现状 |
|---|---|
| 清车失败 | 商品未清 → 自愈；restore 挂起/过期 |
| 回补失败 | MQ 重试；merge 幂等；restored 未置位 |
| clear 成功 + restore 永久丢失 | 靠 order Outbox + DLQ 扫描（小时级）兜底；**无 cart 侧联动对账 Job**（演进） |
| 秒取消竞态 | 定序握手；最坏双方 merge（微秒级、max 幂等） |
| 已有项 checked | 保留用户勾选（PRD checked=true 未强制，已知偏差） |
| 批量 merge | 逐项 merge；无批量 Lua（取舍） |

## 4. 十二个坑

1. **所有订单都清车**：直接购买也会被清；必须 `source=CART`。
2. **cleared 去重缺失**：重复投递删掉用户清车后新加购的商品。
3. **restored 去重缺失**：重复回补把用户调小的数量抬回。
4. **先查 cleared 再置 pending**：孤儿窗口（restore 先到、clear 后到）→ 商品永不回补。
5. **先查 pending 再置 cleared**：同样漏掉竞态；操作序必须反过来。
6. **直接购买不置 pending**：其实置了也会 1h 过期；但别去碰购物车。
7. **clear 失败当成功**：商品未清；握手让 restore 挂起，自愈。
8. **merge 覆盖而非 max**：重复投递抬数量；用 max。
9. **已有项强制 checked=true**：会覆盖用户勾选；当前代码保留（PRD 与代码有偏差）。
10. **部分失败不重入**：cleared 已存在但回补未完成 → 永远不会补；F1 已修。
11. **marker TTL 太短**：覆盖不了 Outbox 重投窗口；7d/1h。
12. **没有联动对账**：restore 永久丢失只能靠 order Outbox/DLQ；演进项。

## 5. 值不值得深挖 / 一句话

- **值得**：跨 topic 定序握手、三标记、孤儿窗口/重复抬数量——分布式联动面试的高含金量题；
- **一句话带过**：marker TTL、指标名；
- **一句话**：**下单清车/取消回补 = 两个订单事件 + 三标记定序握手；任意到达序恰好一方 merge，重复靠 marker 去重。**
- 对账见 **05**；工程收口见 **07**。

**面试口径**："下单创建事件仅 source=CART 清车（批量原子删 + cleared 去重）；终结事件按 items 回补（merge max + restored 去重）；跨 topic 用三标记定序握手——restore 先置 pending 再查 cleared，clear 先置 cleared 再查 pending，任意到达序恰好一方 merge；直接购买零副作用，clear 失败自愈。"
