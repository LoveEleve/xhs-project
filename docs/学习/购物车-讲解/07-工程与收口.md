# 07 · 工程与收口

> **口径**：先讲**生产环境/行业常见做法**，再对照本项目；代码不代表应然标准。
>
> **一句话**：工程收口不是"功能都写完了"，而是三件事：**结构能分工、行为能证明、债能说清**。
>
> **本篇带走**：① 代码结构 ② 33 测试的覆盖/盲区 ③ 指标与观测 ④ 工程债账本与面试口径。
> 前置：01–06。证据：`my-xhs-cart` 源码、测试、`02-购物车.md` §7/§8。

---

## 0. 例子：一次加购的"工程面"

```
POST /cart/add
  → CartController
  → CartService.addItem（校验/上限）
  → cart_add.lua（Redis 三结构原子）
  → 发 CART_TOPIC:ADD（userId 分区、顺序）
  → CartSyncConsumer（UPSERT + CAS）
  → MySQL t_cart_item
  → CartReconcileJob（每小时兜底）
```

功能跑通只是起点。工程上要回答：

1. **谁负责哪一层**？改一个上限/脚本，会不会牵动 800 行大服务？
2. **怎么证明行为对**？33 个测试覆盖到哪，哪些只是 Mock？
3. **线上怎么知道坏了**？指标/日志/告警够不够？
4. **哪些是取舍、哪些是债**？债有没有 owner/到期日？

## 1. 生产环境怎么做（行业常见）

| 工程面 | 常见做法 |
|---|---|
| 测试 | 单元 + 契约 + 集成（Redis/MySQL/MQ）+ 少量 E2E；关键链路有并发/故障注入 |
| 观测 | 黄金四指标（延迟/流量/错误/饱和度）+ 业务指标（同步延迟、对账修复数、握手次数、DLQ） |
| 告警 | 指标阈值 + 日志关键字 + 值班 runbook |
| 债管理 | 每笔债有级别/owner/到期日；P1 进迭代，P3 明确"接受" |
| 代码结构 | 按变更原因拆（读/写/同步/联动/对账），避免上帝服务 |

## 2. 本项目的实现（代码证据）

### 2.1 代码结构：24 个 Java + 8 个 Lua

```
controller/CartController              HTTP 入口
service/CartService (847 行)           加购/改量/删除/清空/列表/匿名合并/发事件
service/CartOrderLinkageService (181)  下单清车/取消回补/三标记握手
lua/*.lua (8)                          add/update/remove/remove_batch/check/check_all/clear/merge
consumer/CartSyncConsumer (298)        Redis→MySQL：UPSERT/CAS/CLEAR屏障
consumer/CartEventSinkConsumer (121)   事件流水 append-only
consumer/OrderCreatedCartConsumer      订单创建事件解析（source=CART）
consumer/OrderTerminationCartConsumer  订单终结事件解析（items/eventVersion）
job/CartReconcileJob (333)             每小时对账 + 事件清理
feign/ProductFeignClient/Fallback      SKU 详情/存在性（降级放行）
mapper/entity/dto/config               持久化/模型/脚本 Bean
```

规模：Java 主代码约 **2814 行**、测试约 **918 行**；`CartService` 单类 847 行。

**观察**：

- Lua 把"三结构原子"隔离在脚本层，是最清晰的一条边界；
- 同步/流水/联动/对账各自独立 consumer/job，故障隔离好；
- `CartService` 仍偏"上帝服务"：读写、Feign、事件、匿名合并都在一个类，改一处要跑全量 16 个测试——可维护性的一般水平，不是灾难。

### 2.2 测试：33 个用例，覆盖"行为规格"，不覆盖"基础设施"

| 测试类 | 数量 | 覆盖 | 盲区 |
|---|---:|---|---|
| `CartServiceTest` | 16 | 加购/列表/改量/删除/清空/数量/合并 | Mockito 模拟 Redis，未跑真 Lua |
| `CartOrderLinkageServiceTest` | 11 | 清车/回补/重复/两种竞态/部分失败/直接购买/旧事件 | 未跑真 Redis marker |
| `CartSyncConsumerTest` | 2 | CLEAR 屏障旧写拦截/新写放行 | UPSERT/CAS/DELETE/CLEAR/CHECK 未测 |
| `OrderCreatedCartConsumerTest` | 2 | 解析 + 缺字段重试 | 未做契约测试 |
| `OrderTerminationCartConsumerTest` | 2 | 解析 + 旧事件无 items | 未做契约测试 |
| **合计** | **33** | | |

**这 33 个测试的价值**：联动 11 个是"行为规格"——把"两种到达序恰好一方 merge、重复不抬数量、部分失败可重入、直接购买零副作用"钉死，比源码注释更可信。

**没覆盖的**：

- `CartReconcileJob`（对账 Job）**0 测试**；
- `CartEventSinkConsumer` **0 测试**；
- `CartController` 无 MockMvc；
- `CartSyncConsumer` 的 UPSERT/CAS/CLEAR/DELETE 主逻辑只有 2 个屏障用例；
- 没有 `@SpringBootTest`/Testcontainers/真实 Redis/MySQL/MQ 集成测试；
- 没有并发压测/故障注入/E2E。

运行：`mvn -pl my-xhs-cart -am test`（当前 33 个用例）。

### 2.3 指标与观测：只有联动两个 Counter

```java
Counter.builder("myxhs_cart_order_linkage_total")
        .tag("op", op).tag("result", result)     // clear/restore × ok/skip
        .register(meterRegistry).increment();

Counter.builder("myxhs_cart_linkage_handshake_total")
        .tag("path", "restore-arrived-first")
        .register(meterRegistry).increment();
```

能回答：

- 清车/回补成功/跳过各多少；
- 竞态握手（回补先到）发生多少次。

**不能回答**（观测缺口）：

- 加购/列表 P99 延迟、Redis 错误率、MQ 堆积/消费延迟；
- 对账修复数、水位线跳过数、SCAN 补扫数；
- 联动 `pending` 挂了多久、DLQ 多少；
- 通用 dashboard（JVM/Tomcat/API/业务）与告警规则已有，但**没有购物车专属面板/告警**（`alert_rules` 无 cart 规则）。

日志侧有 `MqTraceHelper` 恢复 traceId，链路可追；但**指标覆盖不足**，线上主要靠日志排查。

### 2.4 工程债账本

> 级别：P1 影响正确性/可恢复性；P2 影响可运维性/一致性边界；P3 业务取舍。

| 级别 | 债 | 影响 | 建议 |
|---|---|---|---|
| P1 | 联动**无对账 Job** | restore 永久丢失只能靠 order Outbox+DLQ（小时级） | 增加 linkage 扫描/补偿 |
| P1 | `CartReconcileJob` **无单测** | 对账改动回归风险高 | 补三场景/水位线/防双丢测试 |
| P2 | CLEAR 屏障**进程内** | 重启/rebalance 后退化为时间戳 CAS | 屏障外置（Redis/DB）或明确接受 |
| P2 | 对账锁固定 **600s** | 大批量用户超时后并发窗口 | 续租/分批/监控 |
| P2 | 回补已有项**不强制 checked=true** | PRD 写 checked=true，代码保留用户勾选（文档漂移） | 统一语义或改文档 |
| P2 | 事件流水 `isFirstProcess` 前置标记 | 标记后 insert 前崩溃 → 重投被跳过（只影响分析） | 后置标记/幂等插入 |
| P2 | `skuExists` 商品服务不可用**降级放行** | 幽灵 SKU 靠列表 valid 兜底 | 熔断/异步校验 |
| P2 | 无集成/契约测试 | 订单载荷/字段变更可能到线上才发现 | Testcontainers + 契约测试 |
| P3 | 匿名车在**客户端** | 换设备丢车/可伪造 | 服务端匿名车（若产品需要） |
| P3 | 失效商品**不自动清理** | 只标 `valid/invalidReason`，占存储 | 定时清理/失效区 |
| P3 | 库存/优惠**不在车** | 列表不返库存、无优惠试算 | 结算侧试算（当前边界） |
| P3 | 退款**不回补** | 非标准购物车行为 | 明确产品语义 |
| P3 | 无批量 merge Lua | 逐项 merge，回补大单多 RTT | 批量脚本（当前够用） |

> 债账本的关键不是"列出来"，而是**级别 + 影响 + 建议**；P1 要进迭代，P3 要写"接受"。

### 2.5 面试怎么讲（30 秒版）

> "购物车以 Redis 为实时权威：8 个 Lua 保证三结构原子；写后发 userId 分区的顺序消息，消费端 UPSERT+时间戳 CAS，CLEAR 屏障挡旧写；MySQL 兜底，每小时对账三场景修复、水位线避在途、`items` 不存在且无 cleared 时跳过删除防双份全丢；下单清车/取消回补用三标记定序握手，任意到达序恰好一方 merge。工程上用 33 个单测钉行为，指标覆盖联动清车/回补/握手，但还没有集成测试和对账单测，这是已知债。"

**追问应对**：

- **"怎么证明握手？"** → 联动 11 测：两种到达序、重复、部分失败重入、直接购买、旧事件；
- **"哪些没做？"** → 债账本 P1/P2/P3，明确"取舍 vs 债"；
- **"上生产先补什么？"** → 集成测试（真 Redis/MQ）、对账 Job 单测、同步延迟/对账修复指标、联动补偿扫描。

## 3. 对照表：生产 vs 本项目

| 维度 | 生产环境 | 本项目 | 差距 |
|---|---|---|---|

| 单元测试 | 关键链路覆盖 | ✅ 33 个，行为规格清晰 | 对齐 |
| 集成/契约 | 常见 | ❌ 全 Mock | 缺口 |

| 告警/runbook | 有 | ⚠️ 通用告警有，无购物车专属告警/runbook | 一般 |
| 债管理 | owner/到期日 | ⚠️ 有清单，无 owner | 一般 |

## 4. 十二个坑

1. **测试数量当质量**：33 个全是 Mock 单测，不能证明 Lua/Redis/MQ 真语义。
2. **只测 happy path**：同步主逻辑（UPSERT/CAS/CLEAR）只有 2 个屏障用例。
3. **对账 Job 无测试**：三场景/水位线/防双丢最容易改错。
4. **指标只有计数**：没有延迟/错误率/饱和度，线上排障靠日志。
5. **没有同步延迟指标**：Redis 写成功、MySQL 落后多少不知道。
6. **没有对账修复指标**：修了多少、跳过多少、SCAN 补了多少不可见。
7. **上帝服务**：`CartService` 847 行，读写/Feign/事件/合并耦合。
8. **债无 owner/到期日**：清单会变成"永远待办"。
9. **文档与代码漂移**：回补 checked 语义 PRD 与实现不一致。
10. **进程内屏障**：重启/rebalance 后语义降级，不能当永久保证。
11. **固定锁 TTL**：600s 超时后并发，没续租。
12. **无契约测试**：order 侧 `source/items/eventVersion` 字段变更，cart 侧只能线上发现。

## 5. 值不值得深挖 / 一句话

- **值得**：33 测试怎么钉行为、两个指标能回答什么、债账本怎么写——面试"你做的项目怎么保证质量"的抓手；
- **一句话带过**：代码行数、测试类名；
- **一句话**：**工程收口 = 结构能分工 + 行为能证明 + 债能说清；本项目行为和边界讲得清，集成测试/观测/补偿是主要缺口。**
- 全系列回到 **00** 看学习路线；单篇细节看 01–06。

**面试口径**："购物车 24 个 Java + 8 个 Lua；33 个单测钉住读写/联动行为，联动 11 个覆盖两种到达序和部分失败；指标只有清车/回补/握手两个 Counter，缺集成测试、对账单测和同步延迟指标；债按 P1/P2/P3 分级，P1 是联动无对账和对账无测试。"
