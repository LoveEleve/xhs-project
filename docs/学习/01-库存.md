## 第 1 步 · 业务链路（只先看这一节）

**一句话业务**：下单先在 Redis **预占**库存，支付成功后落成 DB 库存（条件更新），取消/超时自动回退，退款按累计正增量回补。**允许少卖，绝不允许超卖。**

```
1. 下单 → order 发事务消息 → InventoryService.preDeduct
   ① DB 幂等占位：t_inventory_prededuct_idem INSERT IGNORE（走主库）
   ② 单 Lua 脚本 prededuct.lua：HGET 幂等 → 选桶 → 桶间遍历
      → DECRBY 总库存 → HSET inventory:prededuct:{orderId} 记真实 bucket
      → ZADD 过期索引（score=到期时间）
2. 支付成功 → confirmDeduct：Lua 转已扣 + DB 条件更新
   （WHERE available_stock >= qty，影响 0 行即失败）
3. 取消/超时 → releaseStock：Lua 回加桶 + 总库存
4. DB 落账 ← InventoryDeductConsumer（available/locked 两侧都带条件）
5. 超时兜底 ← PreDeductTimeoutJob（60s 一轮）：ZRANGEBYSCORE 只取真正到期
   （物理 TTL = 逻辑过期 + 600s 缓冲，防窗口内支付找不到预扣）
6. 对账/重建 ← InventoryReconcileJob：两侧比对修差异；
   重建走 total = available + locked + SETNX（N7 修复，防虚库存）
```

**本步过关标准**：合上文件，能用 5 句话讲出"从下单到支付成功，库存走了哪几步"。

## 第 2 步 · 表结构（六表 + Redis 三结构）

学表结构只问三个问题：**① 它在链路哪一步？② 唯一键/索引在防什么？③ 谁读写它？**

| 表 | 链路里的位置 | 关键设计 | 能问出的面试题 |
|---|---|---|---|
| `t_inventory` | 主表：三态库存 | `available/locked/freezing` + `uk_sku_id` | 为什么三态？`WHERE available>=qty` 怎么防超卖？ |
| `t_inventory_prededuct_idem` | 预扣幂等兜底 | **PK (order_id, sku_id)** | 为什么主键就是幂等键？为什么走主库？7 天清理窗口安全吗？ |
| `t_inventory_outbox` | 本地消息表 | **uk (order_id, sku_id, action)** + `retry/next_retry` | action 为什么进唯一键？指数退避怎么设计？ |
| `t_inventory_compensation` | 回滚失败补偿 | `status(0待/1成/2转人工)` + `idx(status,retry,created)` | 谁写入？超限转人工怎么判定？ |
| `t_tcc_fence` | fence 判定层 | **PK (xid, branch_id)** + `status 1/2/3` | 空回滚/悬挂/幂等分别靠哪列判定？ |

Redis 的"三张隐形表"（同样三问）：
- 桶：`inventory:{skuId}:bucket:{i}`（2→8；⚠️ 分桶的收益边界见文末补充章节）
- 预扣记录：`inventory:prededuct:{orderId}` hash（字段 `skuId:bucket`——F-037 靠它）
- 过期索引：`inventory:prededuct:index` ZSet（score=到期时间）

## 第 3 步 · 机制与 bug 故事

### 3.1 解决方案（难点 → 方案 → why）

| # | 难点 | 方案 | why |
|---|---|---|---|
| 1 | 防超卖 | Lua 内"校验+扣减"原子 + DB `WHERE available>=qty` | Redis 扛并发，DB 做最终防线，双保险 |
| 2 | 热点 SKU | 分桶 + HotSkuDetector 滑动窗口（10s/100 次）自动扩 2→8 桶 | ⚠️ 修正：单实例下分桶**无并发收益**（命令单线程）；收益需"分片 + 桶粒度 tag"，详见文末《分桶的完整认知》 |
| 3 | 超时回收慢 | ZSet 过期索引替代全库 SCAN | O(N)→O(logN)，只差一次范围查询 |
| 4 | 重复消息重扣 | 预扣幂等表 INSERT IGNORE + Lua HGET 幂等 | 消费重试/回查双投都不怕 |
| 5 | 补偿释放扣错桶 | 按预扣时的真实 bucket 释放（F-037） | 早期按 bucket 0 兜底会把别的桶扣错 |
| 6 | TCC 三异常 | fence 状态机 1/2/3 + 乐观锁 | 空回滚：Cancel 无记录插 3；悬挂：Try 遇 3 拒绝；幂等：`WHERE status=1` |
| 7 | 超时误回退 | 新 TccTimeoutJob 按 xid 逐条，先 cancelFence(1→3) 再解冻 | 旧实现按 SKU 聚合有三个致命缺陷 |
| 8 | Redis 故障 | fail-closed：预扣不可用即拒绝下单 | 降级 DB 硬扣会把 DB 打穿 |

## 补充 · 分桶 / 分片 的完整认知（2026-10-04，拉取课程源码对比后修正）

> 背景：查了原版课程 `huazai-ecshop` 的库存实现（持久化克隆：`/data/workspace/source-code/huazai-ecshop`，branch: ecshop-chapter-105），做了三方对比。
> 结论：**分桶是一道"部署形态题"**——收益只在「分片部署 + 桶粒度 tag + 放弃跨 key 原子（对账兜底）」三者同时成立时出现；当前项目三个都不满足，**分桶不写进简历**。

### 1. 分片是什么
- 单台 Redis 两个天花板：单线程（命令排一条队）+ 单机内存天花板 → 解法：多台各存一部分（分片 sharding）
- Redis Cluster = 官方分片（16384 slot）；hash tag `{xxx}` 控制"哪些 key 必须在一个节点"
- **单实例**：1 个桶和 8 个桶都是"一条队伍" → 分桶无并发收益
- **分片后**：桶分散到不同节点 → 多条队伍并行 → 分桶才有收益（= "把单 key 热点拆到多个节点"）

### 2. 三方对比（关键）
| 维度 | 课程原版 huazai-ecshop | 我们 xhs 项目 | 正确形态（分片场景） |
|---|---|---|---|
| 桶数 | = Redis 节点数（单机=1） | 固定 2→8 | = 分片数 |
| 全局 total | 无（查询时 pipeline 各桶求和） | **每笔预扣都 DECRBY total** | 无 / 异步聚合 + 对账 |
| key 设计 | 无 hash tag → 桶可散落不同节点 | `{skuId}` tag → 永远同节点 | 桶粒度 tag：{sku:b0} 一对 key 同 slot；桶间可跨节点 |
| 路由 | 每请求 DECR 计数器取模（轮转） | 按 userId 固定路由 | 均可 |
| 实际收益 | 单机=1 桶（机制没启用）；集群双 key 同脚本 → CROSSSLOT 跑不了 | 单机 0、集群也 0 | 跨节点并行 ✓ |
| 其他瑕疵 | 流水 hash 无 TTL（大 key）；每请求打全局计数 key；合并扣减调用只传 1 个参数（脚本要 2 个）；合并后无条件抛异常 | total 是每笔必碰的热 key | — |

### 3. 正确形态长什么样
```
{sku1001:b0}:stock  + {sku1001:b0}:stream   → 同 tag → 同节点（桶内 Lua 原子）
{sku1001:b1}:stock  + {sku1001:b1}:stream   → 另一 tag → 可落到另一个节点（并行）
每笔请求：选桶 → 只碰该桶的 key（单节点原子）
总库存：查询时求和 / 异步聚合 + 对账（不每笔更新）
```

### 4. 面试话术（分桶追问专用）
> "分桶本质是分片题：桶要能跨节点才有收益。我们参考的分段库存（含课程原版）桶数跟节点数走、意图是对的，但单机退化成 1 桶、集群下双 key 无 hash tag 会 CROSSSLOT；我们自己的版本固定 2→8 + 同 slot，收益也有限。真要做，得每桶同 slot 成对、桶间跨节点、放弃跨 key 原子用对账兜底——这是明确的演进判断。"

### 5. 简历口径（2026-10-04 已执行）
- ❌ 不写"分桶 / 扩容 2→8"来支撑任何 QPS 或"分散热点"——技术讲不通 + 无运行证据
- ✅ QPS 数字只归因真因素（类加载锁修复 / ES 调优 / 无本地缓存口径）
- ✅ 知识留作面试弹药（"我复盘过这个设计的边界"是加分项）

### 6. 补充发现：我们的脚本也不是真 Cluster-ready（2026-10-04 实测拼接）
- `total` / `bucket` 用 tag `{skuId}`；但预扣记录实际是 `inventory:prededuct:888`（**无花括号**，Lua 注释里的 `{orderId}` 与真实代码不符）；`index` 也无 tag
- → `prededuct.lua` 同时碰 **3 个不同的 slot**，真上 Redis Cluster 会 CROSSSLOT；只是 Sentinel 单实例（无 slot 概念）能跑
- 面试口径："我们跑 Sentinel 单主；这个 Lua 严格说跨 slot，不是真 Cluster-ready，上集群要重构 key 设计（同 tag 或拆脚本）"
