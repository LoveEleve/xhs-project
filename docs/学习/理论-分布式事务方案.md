# 理论补课 · 分布式事务方案（跨模块通用）

> 用途：库存 / 订单 / 支付都会引用。先懂"有哪些方案、什么时候用"，再看各模块的具体实现。
> 建立：2026-10-04。

## 1. 为什么需要分布式事务

单机 ACID（事务）跨不了服务、跨不了库。业务上"下单成功的同时库存必须扣掉"这种**跨服务、跨库的"要么全做、要么一致"**需求，就叫分布式事务问题。

## 2. 五种主流方案（一句话 + 什么时候用）

| 方案 | 一句话 | 代价/特点 | 我们的项目对应 |
|---|---|---|---|
| XA / 2PC（强一致） | 两阶段提交：准备+提交，全锁住一起交 | 强一致但**慢、锁资源**，不适合高并发热点 | 没用 |
| TCC | Try 预留 / Confirm 确认 / Cancel 取消，业务自己实现三段 | 侵入大（三接口 + 空回滚/悬挂/幂等三异常），**适合资金冻结类语义** | 库存 TCC 接口（未接线） |
| 本地消息表 / Outbox | 消息先落**本地表**再发 + 消费者幂等 | **最终一致**；生产者保"不丢"，消费者保"不重" | 订单本地消息表、库存 Outbox |
| 事务消息（RocketMQ） | 半消息 + 本地事务 + Broker 回查 | Outbox 的升级版：Broker 帮你确认"本地事务到底提交没" | 订单下单（ORDER_TRANSACTION_TOPIC） |
| SAGA | 长事务拆成多步，每步配一个**补偿动作**（失败了反向执行） | 适合长流程；补偿设计复杂 | 没用（用事务消息 + 对账代替） |
| 最大努力通知 | 尽力发 + 重试，失败人工介入 | 最弱；必须配对账 | 支付通知类场景 |

## 3. 选型原则（生产共识）

1. **高并发热点** → 消息最终一致（别让分布式锁/事务卡请求）
2. **资金强一致语义** → TCC / XA（代价是侵入和复杂度）
3. **长流程** → SAGA
4. **永远配对账**：无论哪种方案，最后都有一层"兜底账"——这是生产实践的共同哲学（BASE：基本可用 + 柔性状态 + 最终一致）

## 4. 关键术语（一次记牢）

| 术语 | 人话 |
|---|---|
| 最终一致 | 现在可以不一样，但**最终**会一样（中间允许短暂不一致） |
| at-least-once | 消息**至少送达一次**（可能重复，Outbox 保证的就是这个） |
| 幂等 | 重复执行效果和一次一样（版本门/条件更新/状态机都是干这个的） |
| 补偿 | 做反了就"反向执行"回来（如退款、回退、取消） |
| 对账 | 定期拿两边的数据比对，差多少补多少（最终兜底） |
| 本地消息表 | Outbox 的别名：消息先落本地 DB 表再发 |

## 5. 我们项目的"组合拳"（对照）

```
订单下单：事务消息（半消息+本地事务+Broker回查）+ 本地消息表
库存预扣：Redis 预占 + Outbox(不丢) + 消费者幂等(不重) + 版本门
支付回调：状态机（重复回调不改状态）
全平台：对账任务（最终兜底）+ 失败收口
```
