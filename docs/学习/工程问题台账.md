## 问题 1：库存键设计的集群兼容问题（分桶"名不副实"）

**现象**
1. `prededuct.lua` 一次操作跨 **3 个 slot**：
   - `inventory:{skuId}:total` / `inventory:{skuId}:bucket:N`（tag = skuId，同一 slot）
   - `inventory:prededuct:888`（**无花括号**，Lua 注释里的 `{orderId}` 与实现不符）
   - `inventory:prededuct:index`（无 tag）
   → 在 Redis Cluster 下直接 **CROSSSLOT 报错**
2. "分桶"在单实例下**无并发收益**：`total` 每笔预扣必碰 + 命令单线程执行；且 `{skuId}` tag 让同 SKU 的所有 key 永远同节点 → 桶不可能跨节点分散
3. 项目文档宣称"即使单机也按 Cluster-ready 规范写"，**与实现不符**；对照课程原版 huazai-ecshop：同样跑不了集群（双 key 无 tag → CROSSSLOT；单机模式 `getActiveNodeCount()` 返回 1 → 分桶退化为单桶）

**根因**
"跨 key 原子"与"分片分散"存在结构性冲突：要原子 → 同 slot；要分散 → 跨 slot。键模型"一单一记录"（按 orderId 聚合）天然无法与按 SKU 的桶共享同一 slot。

**现状缓解**
部署为 Sentinel 主从（无 slot 概念）→ 当前**无实际影响**，属"潜在约束"而非运行 bug。

**根治方向（三选一/组合）**
1. 桶粒度 hash tag：记录与索引都按 SKU 重键 → `inventory:{skuId}:prededuct:{orderId}`、`inventory:{skuId}:prededuct:index`
   （代价：一单一记录 → 一单一 SKU 一记录；跨 SKU 操作复杂化；全局"扫到期"变难）
2. 拆脚本：脚本只碰 total+bucket（同 slot），记录/索引由 Java 侧写 + 对账兜底
3. 维持单机设计，明确不上集群（规模驱动）

**简历包装评估**
- ❌ 现在**不能**写"分桶支撑 QPS / 分散热点"（无收益、无落地）
- ⚠️ 若未来完成改造 1/2 并实测：可写"库存键模型集群兼容改造：桶粒度 slot + 记录/索引重键 + 跨桶对账兜底，消除 CROSSSLOT、支持分片扩展"
- ✅ 现阶段定位：**面试深水区素材**（体现"做过且能复盘边界"）

**面试话术**
> "分桶本质是分片题——桶要能跨节点才有收益。我们做了分桶形态（含热点检测扩容），但复盘明确了边界：单实例/同 slot 下不提升单 SKU 并行度；真分散需要分片 + 桶粒度 tag + 放弃跨 key 原子用对账兜底。这是明确的演进判断。"

## 问题 2：对账任务与在线写"无屏障"（快照式对账的经典问题）

**现象**
`InventoryReconcileJob` 的做法是：读 MySQL 快照 → 逐 SKU 读 Redis → 不一致就 `updateAvailableStockOnly` **无条件覆盖写**。与 MQ 消费者（在线写）并发时存在两个经典问题：
1. **丢更新**：读快照到写库之间的窗口里，在线写（延迟落账/释放）会覆盖新变化
   - 例：对账读得 Redis=98 → 期间取消订单把两边改成 99 → 对账按旧快照写 98，把对的改错
2. **假差异**：两个系统无法同一瞬间读取 → "不一致"可能是消息滞后的时间差，不是真差异

**代码证据**
- `InventoryReconcileJob.java`：Redisson 锁仅防"对账 × 对账"重叠（注释：原实现无锁会互相覆盖）；注释明确避免全字段盲写以防"幻影锁复活"→ 只更新 available 单列，但**该列覆盖无 CAS**
- `InventoryMapper.updateAvailableStockOnly`：裸 `SET available_stock = ?`，无条件、无版本号

**现状缓解**
① Redisson 锁防任务自身重叠；② 只更新单列（不碰 locked）；③ 以 Redis 为准 + 下一轮对账收敛；④ 每小时整点执行（单轮成本有界：在途预扣 key 数 ≈ 在途订单数）
→ 影响被压小（读/卖主链路走 Redis，不读 MySQL），但**到下一轮前 MySQL 账面失真**，属"有缓解、无根治"

**根治方向**
- CAS 条件更新：`UPDATE ... SET available=? WHERE sku_id=? AND available_stock=?`（快照值）
- 行版本号 / 乐观锁
- 水位线：跳过"有在途消息"的 SKU（等消息追平再对）
- 静默窗口：低峰停写再对
- 进阶：**CDC 增量对账**——两条变更流（Redis 事件流 + MySQL binlog）按 skuId 按序号逐笔核对；工业组合 = 全量基线 + 增量持续 + 全量巡检兜底

**简历包装评估**
- ⚠️ 若实现 CAS/水位线并验证：可写"对账从快照覆盖改为条件收敛（CAS + 水位线），消除与在线消息写的丢更新窗口"——属于一致性治理的亮点故事（类似 F-037 的"发现-修复"叙事）
- ✅ 现阶段：面试素材（"无严格屏障，缓解是 X，根治是 Y"），**不写进简历**

**面试话术**
> "对账和在线写确实无严格屏障，这是快照式对账的经典问题（丢更新 + 假差异）。目前控制手段：单列更新防止幻影锁复活、Redisson 锁防任务重叠、以 Redis 为准下轮收敛。要根治需要 CAS 条件更新或水位线，再进一步是 CDC 增量对账。"

## 问题 3：幂等闸门的"残留窗口"（前置标记语义缺陷，L1/L2 两处同构）

**现象**
多 SKU 订单消费过程中进程崩溃后，重投消息被自己的幂等标记拦死，未处理的 SKU 永久不被预扣：

```
t1  isFirstProcess(msgId) SETNX 成功 → 标记置位（TTL 24h）
t2  循环扣 SKU1001 成功
t3  处理 SKU1002 前进程崩溃（kill -9 / OOM）→ catch 未执行 → removeMark 未执行
    → 标记残留；onMessage 未正常返回 → 消费位点未提交 → 消息必然重投
t4  新实例收到重投 → isFirstProcess(msgId)=false → return（跳过整条消息）
    → SKU1002 不被预扣
```

同型代码存在于两个消费者：`OrderTransactionConsumer:88`、`InventoryDeductConsumer:94`。

**同构窗口 B（L2/MySQL 层）：幂等占位残留（T-079）**

"执行前置位"这一形态在 L2 也有一处——MySQL 幂等占位同样是"开始前写入、无法区分是否完成"：

```
t1  insertPredeductIdem 成功（占位行 order_id=pseudoOrderId, sku_id 写入 MySQL）
t2  doPreDeduct 执行前/中进程崩溃（kill -9 → finally 的 deletePredeductIdem 不执行）
    → 占位残留；且 Redis 扣减尚未完成 → 消息重投
t3  新实例收到重投 → insertPredeductIdem 返回 0（主键冲突被 IGNORE）→ return（跳过）
    → 该 SKU 永久不被预扣（若崩溃发生在 Redis 扣减完成之后，跳过则恰好正确）
```

- 代码位置：`InventoryService.java:254-258`（探测 + 0 即返回）、`:266`（finally 失败删占位，崩溃时不执行）、`InventoryMapper.java:59-61`（INSERT IGNORE）、`:65`（DELETE）
- 与窗口 A 完全同构（"执行前标记"被当作"已完成"）；修复须与 A 同批处理，只修 L1 会留下 L2 同病

**根因**
标记语义是"**已开始处理**"（执行前置位），却被当作"**已处理完成**"用于跳过重投。崩溃时"标记已置位、业务未完成"的组合没有被任何规则识别。消费位点由框架按 `onMessage` 返回值提交（正常返回 = CONSUME_SUCCESS），崩溃路径"位点未提交 + 标记残留"叠加即形成窗口。

**现状缓解（2026-10-09 修正：无自动检出通道）**
① 概率极低：窗口 = `[标记置位, 处理完成)` 毫秒级区间，且崩溃后消息须被重投；
② **对账检不出**：现有对账比对的是 Redis ↔ MySQL 两边一致性（available 覆盖写、locked 重算、分桶求和），窗口造成"两边一致地少一笔扣减"→ 无差异可修；
③ **confirm 不是检出点**：对"预扣记录不存在"为静默幂等返回（`InventoryService.java:399-403`；release 同理 `:466-469`）；`INVENTORY_FAILED_TOPIC` 由 L2 落账重试耗尽触发（`InventoryDeductConsumer:287-297`），窗口里 event 从未产生、不适用；
④ 后果放大器：退款回补 `refundRestore`（累计正增量）不校验预扣记录 → 缺失扣减的订单若退款，会给未扣的 SKU 回补 → available 虚增；
⑤ 复查文档已确认并定性"低概率但安全敏感"（`docs/test-2/_archive/task2-era/DIRECT-REVIEW.md:53`）。
→ 结论：**目前无自动检出通道**（仅人工 / 未来业务对账），修复标记语义的优先级高于此前评估。

**根治方向（完成标记语义）**
1. 跳过规则反转：**仅当标记 = done 才跳过；缺失 / processing 一律重放**（重放安全由 L2 保证）；
2. 循环完成后写 `done`（TTL 24h）；失败路径不写 done；
3. 可选优化：`processing` + 租约——重投时租约未过期 → `RECONSUME_LATER` 延迟处理以减少并发重放；**禁止"processing → 跳过"**（B 跳过后 A 崩溃 = 窗口重开）；
4. 最简正确形态 = 单 `done` 标记（processing 非必需，仅为减少重复执行）；
5. 组件共用：`MessageIdempotentHelper` 的两个使用方需同步改造 + 单测；
6. **同构窗口 B 同批修复**：MySQL 占位改完成态语义（成功后才写占位；或"0 行"时不直接跳过、先核对 Redis/落账端扣减是否真正完成再决定重放）——与 L1 一并通过故障注入验证；
7. **（检出通道，可选）业务对账**：以订单为真值核对（有效/已支付订单 → 各 SKU 是否留有扣减痕迹），缺失即告警/补偿——不做标记语义修复时，这是唯一的自动检出手段。

**重放安全前提（已验证）**
- Lua 重复返回 `-1` → Java 视为成功（`InventoryService.java:375-379`）
- MySQL 幂等占位：`insertPredeductIdem` 重复 insert 返回 0 → 直接幂等返回（`InventoryService.java:254-258`，T-079）
→ 重放最坏是多一轮空转，不会重复扣减。

**验证方法（落地前必做）**
故障注入：多 SKU 处理中途 `kill -9` → 触发重投 → 断言：缺失 SKU 被补扣、已完成 SKU 无重复扣减、MySQL 幂等表与对账数据一致。

**简历包装评估**
- ⚠️ 落地并完成故障注入验证后，可写："修复消费幂等残留窗口：前置去重标记改为完成态标记（done-only skip + 未完成重放），崩溃重投自愈，L2 幂等保障重放安全"
- ✅ 现阶段：面试素材（缺陷机理 + 修复方案 + 验证方法可完整讲清）

**面试话术**
> "消费幂等 L1 用执行前 SETNX 标记，复查发现一个残留窗口：崩溃在'标记已置位、循环未完成'之间时，重投会被自己的标记拦死、未处理的 SKU 不补。修复方向是把标记语义反转成完成态——只认 done 跳过、未完成一律重放；重放安全由 L2 的 Lua 幂等与 MySQL 幂等表保证。代价是极端场景多一轮空转，但窗口被彻底关闭。"
