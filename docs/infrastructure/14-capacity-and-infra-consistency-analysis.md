# my-xhs 量级目标与基础设施自洽性分析

> 100万DAU配单节点ES、Redis Sentinel单主——量级目标和基础设施规模必须自洽。
> 否则面试官一追问就暴露出"数字是编的"。

---

## 一、问题定义

### 1.1 当前量级目标

| 指标 | 目标值 |
|------|--------|
| DAU | 100万 |
| 笔记发布量 | 10万/天 |
| 商品SKU | 100万 |
| 日订单量 | 5万 |
| QPS峰值 | 1万 |
| 可用性 | 99.95% |

### 1.2 当前基础设施规模

| 组件 | 配置 | 问题 |
|------|------|------|
| MySQL | 1主1从 | ⚠️ 主库单点写入瓶颈 |
| Redis | Sentinel 1主2从3哨兵 | ⚠️ 单主写入瓶颈 |
| Elasticsearch | 单节点 | 🔴 不满足100万DAU搜索需求 |
| RocketMQ | 1主 | ⚠️ 单点故障风险 |

### 1.3 自洽性校验方法

```
自洽性公式：
  峰值QPS = DAU × 日均操作次数 × 峰值系数 / 86400

峰值系数：
  - 一般业务：3倍（早晚高峰）
  - 秒杀场景：10倍
  - 热点事件：20倍
```

## 二、逐组件自洽性校验

### 2.1 Redis 自洽性校验

```
计算模型：
  DAU 100万 → 同时在线用户 = 100万 × 20% = 20万
  每用户每秒操作 = 2次（浏览+点赞/评论）
  峰值QPS = 20万 × 2 × 3（峰值系数）= 120万 → 实际到Redis的QPS

  但大部分请求被本地缓存（Caffeine）拦截
  实际到达Redis的QPS = 120万 × 20% = 24万

单主Redis性能：
  - SET/GET: 10万QPS（单线程瓶颈）
  - Pipeline批量: 50万QPS
  - Lua脚本: 8万QPS

结论：单主Redis 24万QPS扛不住！
```

**修正方案**：

| 方案 | 配置 | 能力 | 选择 |
|------|------|------|------|
| Redis Sentinel | 1主2从 | 10万QPS写入 | ❌ 不够 |
| Redis Sentinel 3分片 | 3主6从 | 30万QPS写入 | ✅ 够用 |
| Redis Sentinel 6分片 | 6主12从 | 60万QPS写入 | ✅ 冗余 |

**建议**：将 Redis Sentinel 修改为 **Redis Sentinel 3分片**（3主6从）

```
修正后的设计：
  Redis Sentinel: 3主6从
  - 每个主节点承载1/3的写入
  - 总写入QPS: 30万
  - 总读取QPS: 60万（从节点分担读）
  - 内存: 每主节点5GB，总15GB
  - 满足100万DAU需求
```

### 2.2 Elasticsearch 自洽性校验

```
计算模型：
  索引文档数：
  - 商品: 100万
  - 笔记: 5000万（1年积累）
  - 订单: 1.5亿（3年积累）
  - 搜索建议: 100万

  搜索QPS：
  - 100万DAU × 5次搜索/天 × 峰值3 / 86400 = 1736 QPS
  - 加上搜索建议(每次输入触发): 5000 QPS

单节点ES性能：
  - 搜索QPS: 1000-2000（取决于索引大小和查询复杂度）
  - 写入QPS: 5000（Bulk批量写入）
  - 内存: 建议32GB（JVM堆16GB + 系统缓存16GB）

结论：单节点ES勉强扛搜索QPS，但不满足可用性要求（单节点无副本）
```

**修正方案**：

| 方案 | 配置 | 搜索QPS | 可用性 | 选择 |
|------|------|---------|--------|------|
| 单节点 | 1节点 | 1500 | 无保障 | ❌ |
| 2节点(1主1副本) | 2节点 | 3000 | 高可用 | ✅ |
| 3节点集群 | 3节点 | 5000+ | 高可用+扩容 | ✅ 推荐 |

**建议**：ES 改为 **3节点集群**（1主2副本，或3主0副本+分片）

```
修正后的设计：
  Elasticsearch 3节点集群
  - 每节点: 8C16G + 500GB SSD
  - 索引分片: 3主分片 + 1副本
  - 搜索QPS: 5000+
  - 写入QPS: 15000（Bulk）
  - 满足100万DAU需求 + 高可用
```

### 2.3 MySQL 自洽性校验

```
计算模型：
  写入QPS：
  - 订单: 5万/天 → 峰值 5万×3/86400 = 1.7 QPS
  - 笔记: 10万/天 → 峰值 3.5 QPS
  - 社交互动: 100万/天 → 峰值 35 QPS
  - 总写入QPS: ~100（含所有业务）

  读取QPS：
  - 写读比约1:10 → 读取QPS ~1000
  - 大部分读走Redis缓存 → 实际到MySQL的读QPS ~200

单主MySQL性能：
  - 写入QPS: 3000-5000（SSD，简单写入）
  - 读取QPS: 10000+（从库）
  - 连接数: 5000

结论：1主1从的MySQL完全够用！
```

**MySQL不需要调整**，1主1从足够支撑100万DAU。

### 2.4 RocketMQ 自洽性校验

```
计算模型：
  消息量估算：
  - 下单事务消息: 5万/天
  - 社交互动通知: 100万/天
  - Canal数据同步: 50万/天
  - 缓存失效: 20万/天
  - 总量: ~200万/天 → 峰值QPS: 70

单Broker性能：
  - 写入QPS: 5万+
  - 消费QPS: 10万+

结论：1主Broker够用，但不满足高可用（单点故障）
```

**修正方案**：

| 方案 | 配置 | 可用性 | 选择 |
|------|------|--------|------|
| 单主 | 1Broker | 单点故障 | ❌ 不满足99.95% |
| 主从 | 1主1从 | 主从切换 | ✅ 够用 |
| Dledger集群 | 3节点 | Raft协议选主 | ✅ 推荐 |

**建议**：RocketMQ 改为 **1主1从**（同步双写）或 **Dledger 3节点集群**

## 四点五、流量漏斗模型推算（QPS 科学推算链路）

> 参考华仔第98篇：流量漏斗模型。以下推算链路让 QPS 数字"有据可查"，面试时不会被追问露馅。

### 推算公式

```
某接口峰值QPS = DAU × 日均访问次数 × 漏斗转化率 × 峰值系数 / 86400
```

### my-xhs 流量漏斗

```
100万 DAU（日活用户）
  │
  ├─ 80% 打开首页 → 80万用户 × 5次/天 = 400万次 → 峰值QPS 139
  │    ├─ 60% 点击笔记 → 48万用户 × 8次/天 = 384万次 → 峰值QPS 133
  │    │    ├─ 20% 点赞 → 9.6万用户 × 3次/天 = 28.8万次 → 峰值QPS 10
  │    │    ├─ 10% 评论 → 4.8万用户 × 0.5次/天 = 2.4万次 → 峰值QPS 0.8
  │    │    └─ 15% 收藏 → 7.2万用户 × 2次/天 = 14.4万次 → 峰值QPS 5
  │    └─ 30% 搜索 → 24万用户 × 2次/天 = 48万次 → 峰值QPS 17
  │
  ├─ 30% 浏览商品 → 30万用户 × 3次/天 = 90万次 → 峰值QPS 31
  │    ├─ 10% 加购 → 3万用户 × 0.5次/天 = 1.5万次 → 峰值QPS 0.5
  │    └─ 5% 下单 → 1.5万用户 × 0.2次/天 = 3000次 → 峰值QPS 0.3
  │         └─ 80% 支付 → 1.2万用户 × 0.2次/天 = 2400次 → 峰值QPS 0.3
  │
  └─ 5% 发布笔记 → 5万用户 × 1次/天 = 5万次 → 峰值QPS 1.7
```

> **关键结论**：100万DAU的外部请求峰值QPS约430，加上服务间调用放大（约3倍），到各中间件的总QPS约1300。
> 这与下方"五、峰值QPS推算表"的数据一致，形成了完整的推算闭环。

## 六、生产决策与表达

### Q: 你的系统真的能扛100万DAU吗？

> "我做过容量推算。100万DAU的峰值QPS约1000，主要在首页Feed和笔记详情。Redis Sentinel 3分片能扛30万QPS，ES 3节点集群能扛5000搜索QPS，MySQL 1主1从的写入QPS 3000+完全够用。日常20个服务实例，预留了50%冗余。如果实际流量超过预期，K8s HPA自动扩容，30秒内新增实例。"

### Q: 为什么不用单节点Redis/ES？

> "单节点Redis单线程写入上限10万QPS，100万DAU峰值到Redis的QPS约24万——单主扛不住。而且单节点没有高可用，挂了缓存全丢。ES单节点同理，搜索QPS 1500但100万DAU需要5000+，而且单节点没有副本，磁盘故障数据全丢。生产环境必须集群。"

### Q: 扩容时怎么保证平滑？

> "Redis Sentinel在线添加分片，槽位自动迁移；ES增加节点后调整分片副本数；K8s HPA根据CPU利用率自动扩缩容。扩容期间服务不中断。"
