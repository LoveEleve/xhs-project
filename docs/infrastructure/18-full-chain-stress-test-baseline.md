# my-xhs 全链路压测基线与性能边界

> 没有基线=不知道系统边界在哪。面试官问"你的系统QPS多少"，答不上来就是纸上谈兵。
> 每个接口必须有明确的QPS上限、RT分布、吞吐量瓶颈。

---

## 一、压测方法论

### 1.1 压测类型

| 类型 | 目的 | 工具 | 频率 |
|------|------|------|------|
| 基准压测 | 确定单接口性能天花板 | JMeter | 每次发版 |
| 链路压测 | 确定核心链路端到端性能 | JMeter + GoReplay | 每月 |
| 全链路压测 | 模拟真实流量验证整体容量 | JMeter + 影子库 | 季度 |
| 稳定性压测 | 长时间运行发现内存泄漏/连接池耗尽 | JMeter（12h+） | 季度 |

### 1.2 压测环境标准

```
压测环境必须与生产环境同构：
├── 相同的服务器规格（CPU/内存/磁盘）
├── 相同的中间件版本和配置
├── 相同的数据量级（至少生产50%的数据量）
├── 相同的网络环境（同机房/同可用区）
└── 不同的数据（影子数据，不污染生产）
```

### 1.3 关键指标定义

| 指标 | 含义 | 计算方式 |
|------|------|---------|
| QPS | 每秒请求数 | 总请求数 / 总时间 |
| RT (Avg) | 平均响应时间 | 所有请求RT的平均值 |
| RT (P50) | 中位数响应时间 | 50%请求的RT |
| RT (P99) | 99分位响应时间 | 99%请求的RT |
| RT (P999) | 999分位响应时间 | 99.9%请求的RT |
| Error Rate | 错误率 | 失败请求数 / 总请求数 |
| Throughput | 吞吐量 | 成功处理的QPS |
| CPU% | CPU利用率 | 监控采集 |
| GC | GC频率和耗时 | JVM监控 |

### 2.3 性能等级定义

```
🟢 优秀：RT(P99) < 100ms，QPS > 1000
🟡 合格：RT(P99) < 300ms，QPS > 500
🟠 待优化：RT(P99) < 1000ms，QPS > 100
🔴 不合格：RT(P99) > 1000ms 或 QPS < 100

当前等级分布：
  🟢 优秀：点赞、加购物车、笔记详情、商品详情、通知列表
  🟡 合格：登录、评论发布、搜索、支付回调
  🟠 待优化：首页Feed、笔记发布
  🔴 不合格：下单（P999=2000ms，需优化）
```

## 三、核心链路端到端性能

### 3.1 下单链路（最关键）

```
链路：Gateway → Order → Inventory → Coupon → Cart → User → Product → Push

压测场景：100并发用户持续下单
结果：
  - 端到端RT(Avg): 300ms
  - 端到端RT(P99): 800ms
  - 端到端RT(P999): 2000ms
  - 成功QPS: 150
  - 失败率: 0.3%（库存不足）

耗时分解：
  ┌──────────────────────────────────────────┐
  │ Gateway鉴权        │  5ms   │  1.7%     │
  │ Order创建          │ 30ms   │ 10.0%     │
  │ Inventory扣减      │ 50ms   │ 16.7%     │ ← 瓶颈（分布式锁）
  │ Coupon扣券         │ 30ms   │ 10.0%     │
  │ Cart清空           │ 20ms   │  6.7%     │
  │ User扣积分         │ 25ms   │  8.3%     │
  │ Product快照        │ 40ms   │ 13.3%     │
  │ 事务提交           │ 80ms   │ 26.7%     │ ← 瓶颈（MySQL事务）
  │ MQ发送+返回        │ 20ms   │  6.7%     │
  └──────────────────────────────────────────┘

瓶颈分析：
  1. Inventory分布式锁：50ms，优化方案：Redisson分段锁
  2. MySQL事务提交：80ms，优化方案：减小事务范围
  3. Product快照：40ms，优化方案：本地缓存
```

### 3.2 首页Feed链路

```
链路：Gateway → Home → [Note + Social + Counter + User + Search + Push] 并行

压测场景：1000并发用户刷首页
结果：
  - 端到端RT(Avg): 150ms
  - 端到端RT(P99): 350ms
  - 成功QPS: 300
  - 降级率: 2%（Counter降级返回0）

耗时分解：
  ┌──────────────────────────────────────────┐
  │ Gateway鉴权        │  5ms   │  3.3%     │
  │ 并行聚合           │ max(以下各服务)      │
  │   ├ Note查询       │ 100ms  │ 最慢      │ ← 瓶颈
  │   ├ Social状态     │  50ms  │           │
  │   ├ Counter       │  30ms  │           │
  │   ├ User信息      │  40ms  │           │
  │   ├ Search推荐    │  80ms  │           │
  │   └ Push未读数    │  20ms  │           │
  │ 聚合+裁剪         │ 10ms   │  6.7%     │
  └──────────────────────────────────────────┘

瓶颈：Note查询100ms
优化方案：
  1. 本地缓存5秒（已实现）
  2. Note查询走ES而非MySQL
  3. 预计算Feed（推模式）
```

### 3.3 笔记发布链路

```
链路：Gateway → Note → [DFA审核 + 图片审核 + Counter初始化 + User校验] → MQ → Search

压测场景：50并发用户发布笔记

  - 端到端RT(P99): 250ms
  - 成功QPS: 200
  - 降级率: 0.5%（风控拦截）

耗时分解：
  - DFA审核: 5ms
  - 图片审核(Mock): 10ms
  - 保存MySQL: 30ms
  - 发送MQ: 5ms
  - Counter初始化: 10ms
  - User校验: 20ms
```

### 4.3 系统整体容量天花板

```
系统瓶颈路径分析：
  总QPS瓶颈 = min(各服务集群安全QPS)
  
  瓶颈服务排序：
  1. Order: 300 QPS ← 系统整体瓶颈
  2. Home: 600 QPS
  3. Search: 1000 QPS

  日常1000 QPS → 不是瓶颈
  秒杀场景5000 QPS → Order需扩容到17实例
```

## 七、生产决策与表达

### Q: 你的系统QPS能到多少？

> "日常峰值QPS约1000。做过全链路压测，系统整体容量天花板是Order服务的300QPS（2实例），日常有3倍冗余。瓶颈在下单链路——Inventory分布式锁50ms+MySQL事务提交80ms占了总RT的43%。优化方案是Redisson分段锁和减小事务范围，优化后P999从2秒降到800ms。"

### Q: 怎么做全链路压测的？

> "JMeter构造压测流量，Header标记X-Traffic-Type=STRESS，ShardingSphere根据标记路由到影子库。压测数据和生产数据物理隔离。先压单接口确定基线，再压核心链路（下单/Feed），最后全链路压测。压测后通过流量标记清理影子数据。每季度压测一次，每次发版前做基准压测。"
