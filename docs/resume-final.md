# 项目经历

## 小红书电商平台（【时间，如 2025.03–2025.12】 | 核心开发）
该项目是一个内容和交易都做的社交电商平台，后端 15 个 Spring Cloud 微服务。交易侧有商品、购物车、库存、优惠券、订单，内容侧有用户、笔记、Feed、搜索、推荐；中间件用 RocketMQ、Redis Sentinel、Elasticsearch、ShardingSphere、Canal、XXL-Job，监控是 ELK、Prometheus/Grafana、SkyWalking，Docker 部署。我负责交易和内容核心模块的开发，后期主要做稳定性和容量优化。

主要工作：
- 库存：Redis 分桶 + Lua 原子预扣，DB 做账本，跨服务冻结用 TCC。热点 SKU 自动扩分桶，超时预扣用 ZSet 过期索引回收；幂等靠预扣表和 Outbox 唯一键兜底。
- 订单：ShardingSphere 4 库 4 表，非分片键查询走订单号映射表，雪花 workerId 按实例动态计算。下单和扣库存用事务消息 + 本地消息表，靠 Broker 回查保证最终一致；超时关单用延迟消息加状态机。
- 购物车与优惠券：领券在一个 Lua 里做完库存校验、限领和扣减，msgId 加唯一键两层防重。购物车以 Redis 为准，多 key 操作收进 Lua，清空加屏障标记，事件带序号防乱序。
- 内容与 Feed：笔记发布用本地消息表保证内容和消息在同一个事务。Feed 推拉结合，普通作者推收件箱、大 V 走拉模式，批量用 Pipeline 写，支持断点续推。
- 搜索与推荐：Canal 把 MySQL 变更同步到 ES，用版本号拒掉旧消息、删除标记防止已删笔记被写回来；推荐侧做了行为上报到特征、热池、ItemCF 的链路。
- 长连接：WebSocket 用一致性哈希固定实例，跨实例消息走 Redis pub/sub，没送到就转离线、上线补发；通知按自然日聚合，SSE 支持跨实例；鉴权用一次性 ticket，不把 token 放 URL 里。
- 稳定性：搭 L1~L4 测试矩阵，做故障注入和压测；网关限流按实测容量重新校准；traceId 打通服务、MQ 和长连接；修复死信积压监控恒为 0 的问题。

项目成果：
- 20 并发扣库存不超卖；TCC 的幂等、空回滚、悬挂等 11 个场景全过；事务回查注入 75 秒延迟后库存只扣一次。
- 消息重放不重复计数、不重复发券；10 并发领券严格限 2 张；购物车并发加购和清空都不串数据。
- 上线前联调发现两个高风险问题：退款补偿把部分退款当全额、会多释放库存；事务拦截器失效、几个服务的 @Transactional 实际没生效。补齐调度任务和缺失的 topic 后，兜底链路才真正跑通。
- 压测基线：商品 1020、笔记 1096、首页 764、推荐 761、搜索 683 RPS。ES 从 0.5 核扩到 2 核后，搜索从 175 涨到 683 RPS，P50 从 115ms 降到 29ms。
- 限流按容量调到商品/内容 500、首页/推荐 300；下游注入 6 秒延迟时，首页约 2 秒降级返回。Redis 切主实测 2.3 秒，会话没乱。

## 小红书 AI 运维诊断 Agent（【时间】 | 独立开发）
这是给上面那套系统做的运维诊断 Agent，从零开始做。用户用自然语言提问，Agent 自己去查 DLQ、日志、指标、知识库和代码并给出结论；涉及重投死信这类变更操作，会先挂起等人工审批再执行。技术栈是 AgentScope 2.0（Java）、Spring Boot 3.2.5，接 RocketMQ Admin、ES、Prometheus、MySQL、Redis，单机 systemd 部署。

主要工作：
- 工具层：写了 16 个工具。ES 查询和 PromQL 都在服务端拼装，模型只填业务参数（服务名、时间窗等），解决模型自己写 DSL 反复报错的问题。
- 审批闭环：诊断→提案→审批→执行→核验→审计。重投后按消息所在队列的消费位点确认是否真被消费，不是发出去就算成功；审批超时作废，崩溃补执行，卡在"执行中"的会被回收成失败。
- 评测：分三层——检索命中率、答案（关键词 + 引用校验）、Agent 行为（工具选择、调用路径、重复运行稳定性），和单测一起进提交前门禁。
- 成本：模型网关带重试、熔断、降级；按用户做 token 预算，用到 80% 切轻量模型，超限直接 429。
- 稳定性与安全：状态在 Redis，进程重启能接着聊，状态丢了从消息表和会话摘要恢复；请求幂等防重复提交；审计日志加哈希链、改一条能查出来；管理接口收 ADMIN 角色。

项目成果：
- 10 个真实故障案例全部给出完整证据，平均 1.63 分钟；人工保守估算 20.6 分钟，降幅约 92%。
- 知识库检索 30 条全中；答案评测 50 条全过、引用能对回原文（首轮 47 条，修复后复测全过）。
- 工具调用 12 道题全对；同批题重复跑的稳定性得分 0.917。
- 原先让模型自己拼 ES DSL，P95 排查题 98 秒还答偏；改成服务端拼装后 50 秒答对。
- 重投演练中，毒丸消息再次进死信被正确判为 reentered_dlq，没有误报成功。
- 预算三段实测正常（软限切模型、硬限 429、单次问答计量 5577 token）。
- 去掉 MCP 依赖、工具全部自研后，杀掉两个 MCP 进程，ES 和 PromQL 的问题仍能正常回答（19 秒、39 秒）。
