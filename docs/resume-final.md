# 项目一 · 小红书电商平台

xhs 是一个内容和交易都做的社交电商平台，15 个 Spring Cloud 微服务。交易侧有商品、购物车、库存、优惠券、订单，内容侧有用户、笔记、Feed、搜索、推荐。中间件用的 RocketMQ、Redis Sentinel、Elasticsearch、ShardingSphere（订单 4 库 4 表）、Canal、XXL-Job，监控是 ELK、Prometheus/Grafana 加 SkyWalking，整体 Docker 部署。我在项目里负责交易和内容核心模块的设计开发，后期主要精力放在稳定性和容量优化上。

## 职责描述
- 库存：Redis 分桶加 Lua 原子预扣，DB 做账本，跨服务冻结用 TCC；热点 SKU 会自动扩分桶，超时的预扣用 ZSet 过期索引回收，不扫全库；幂等有预扣表和 Outbox 唯一键兜底。
- 订单：ShardingSphere 4 库 4 表，非分片键查询走订单号映射表，雪花 workerId 按实例动态计算。下单和库存预扣用事务消息加本地消息表，靠 Broker 回查保证最终一致；超时关单用延迟消息加状态机。
- 优惠券与购物车：领券是一个 Lua 脚本里做完库存校验、限领和扣减，msgId 加唯一键两层防重。购物车以 Redis 为准，多 key 操作都收进 Lua，清空加了屏障标记，事件带序号防乱序，异步落库。
- 内容与 Feed：笔记发布用本地消息表保证内容和消息在同一个事务。Feed 推拉结合，普通作者推收件箱，大 V 走拉模式，批量用 Pipeline 写，支持断点续推。
- 搜索与推荐：Canal 把 MySQL 变更同步到 ES，用版本号拒绝旧消息、删除标记防止已删笔记被重新写回来。推荐做了行为上报到特征、热池、ItemCF 的离线链路。
- 长连接：WebSocket 用一致性哈希把会话固定到实例，跨实例消息走 Redis pub/sub，没送到就转离线消息、上线补发。通知按自然日聚合，SSE 同样支持跨实例。长连接鉴权用一次性 ticket，避免 token 放在 URL 里。
- 稳定性：搭了 L1 到 L4 的测试矩阵，做了故障注入和压测。网关限流是压测之后按实际容量重新调的。traceId 打通了服务、MQ 和长连接，另外修了死信积压监控一直是 0 的问题。

## 关键结果
- 20 个并发扣库存没有超卖；TCC 的幂等、空回滚、悬挂等 11 个场景全部通过；给事务回查注入 75 秒延迟，库存也只扣了一次。
- 同一条消息重放，计数和优惠券都不会重复；10 个并发领券严格限制在 2 张；购物车并发加购、清空都不会串数据。
- 上线前联调时查出一批问题，比较严重的有两个：退款补偿把部分退款当成全额，会多释放库存；事务拦截器没生效，几个服务的 @Transactional 其实没起作用。补上调度任务和缺失的 topic 之后，兜底链路才真正跑起来。
- 压测基线：商品 1020、笔记 1096、首页 764、推荐 761、搜索 683 RPS。ES 之前只分了 0.5 核，搜索 P50 有 115ms，扩到 2 核后涨到 683 RPS，P50 降到 29ms。
- 限流按压测结果调到商品和内容 500、首页和推荐 300；给下游注入 6 秒延迟，首页还能在 2 秒左右降级返回。
- 死信积压监控现在覆盖 26 个消费组，之前漏了 8 个；Redis 主从切换实测 2.3 秒，会话没乱。

# 项目二 · 小红书 AI 运维诊断 Agent

xhs-ai 是给上面这套系统做的运维诊断 Agent，从零开始做的。用户直接用自然语言提问，Agent 自己去查 DLQ、日志、指标、知识库和代码，整理出结论；碰到重投死信这类有风险的操作，会先挂起来等人工审批，审批完才执行。框架用的 AgentScope 2.0（Java），Spring Boot 3.2.5，接了 RocketMQ Admin、ES、Prometheus、MySQL 和 Redis，部署在单台机器上用 systemd 托管。

## 职责描述
- 工具：一共写了 16 个。ES 查询、PromQL 这些都放在服务端拼好，模型只填业务参数，比如查哪个服务、什么时间段，这样它不会因为不会写 DSL 反复报错。
- 审批：做了从诊断、提案、审批、执行、核验到审计的完整流程，审批超时会自动作废。重投发出去之后不是看到发送成功就算了，会按消息所在队列的消费位点确认它真的被消费了。
- 评测：分三层，检索看命中率，答案看关键词和引用，Agent 看工具选得对不对、调用路径合不合理、重复跑稳不稳定。评测和单测一起放进门禁脚本，提交前跑一遍。
- 成本：模型网关带重试、熔断和降级。按用户做了 token 预算，用到 80% 自动切便宜模型，再超就直接返回 429。单次诊断大概 1.8 万输入、1400 输出 token。
- 可靠性：状态存在 Redis，进程重启能接着聊；Redis 状态丢了也能从消息表和会话摘要恢复。审批卡在"执行中"会被定时任务回收成失败，交给人工重试，不会自动重放。重复提交用 X-Request-Id 挡住。
- 安全：管理接口收敛到 ADMIN 角色；审计日志加了哈希链，改过一条能查出来；上线前做了 8 项攻击测试。

## 关键结果
- 10 个真实故障案例都给出了完整证据，平均 1.63 分钟；人工保守估算 20.6 分钟，降了大概 92%。
- 知识库检索 30 条全中；答案评测 50 条全过、引用能对上原文（第一轮 47 条，修完问题复测全过）。
- 工具调用 12 道题全对；同一批题重复跑，稳定性得分 0.917。
- 一开始让模型自己拼 ES 的 DSL，经常缺参数。改成服务端拼之后，同一道 P95 排查题从 98 秒还答偏，变成 50 秒答对。
- 做过一次重投演练：毒丸消息重投后又进了死信，系统判成了 reentered_dlq，没有误报成功。
- 预算实测：软限切模型正常，硬限返回 429，单次问答计量 5577 token。
- 后来把 MCP 依赖去掉了，工具全部自己实现。杀掉两个 MCP 进程，ES 和 PromQL 的问题照样能回答（19 秒、39 秒）。
