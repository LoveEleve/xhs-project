## A. 一致性陷阱（他把你说过的话拼起来打你）⚠️ 最危险

> 这类题没有准备过必卡壳。答法统一：**先承认两个说法都说过 → 指出各自的适用边界**。

| # | 陷阱 | 一句话拆解 |
|---|---|---|
| A1 | "你说库存对账'以 Redis 为准'，又说 DB 是账本——到底谁是权威？" | "**分字段**：available 走 Redis 权威（实时扣减发生在那）；locked 走**在途预扣记录**权威（Redis 记录为准，MySQL 只是落账）；两者对账方向相反是因为实时发生地不同。" |
| A2 | "你说消费 at-least-once + msgId 去重——客户端重启后去重集合没了怎么办？" | "去重集合是**去重优化**不是正确性保证：重启后重复消息最多重复展示一次提醒，按时间戳/内容幂等展示无副作用；真正要防重复的是资金（DB 唯一键）。" |
| A3 | "你说分布式锁只做效率——那抢锁失败直接拒绝，用户重试不就绕过了？" | "绕过抢锁的重复请求最终撞**唯一键/条件 UPDATE**：第一个成功、第二个被拦。锁只是省掉无谓的 DB 开销，不是防重本身。" |
| A4 | "你说幂等切面 Redis 故障 fail-open——那它还有什么用？" | "它挡住的是**高频重复提交**（99% 场景）；fail-open 只是 Redis 故障时的可用性降级，且**打点可观测**（`myxhs_common_fail_open_total`）。正确性从不依赖它。" |
| A5 | "你说缓存可以丢，但库存对账又以 Redis 为准——缓存丢了库存不就错了吗？" | "两个'Redis'要分清：**缓存**（allkeys-lru，可丢）和**业务账本 Redis**（noeviction + AOF + 对账）是两个实例；可丢的是缓存，账本丢了从 MySQL 重建（对账反向重建）。" |
| A6 | "分片键 user_id，客服按订单号查——跨 16 片全扫？" | "不扫：order_no → mapping 表 → user_id → 路由单片。mapping 表独立数据源不经 ShardingSphere，写失败有 5 分钟补录兜底。" |
| A7 | "你说状态机'条件 UPDATE 单一赢家'——那赢家写事件失败了呢？" | "事件与状态在**同一事务**：状态更新失败则事件回滚、事件写失败则状态回滚，不存在'状态进了事件没进'的窗口。" |
| A8 | "你两个票据 TTL 不一样（IM 5 分钟 / SSE 30 秒），安全口径怎么定的？" | "实现不同导致：IM 票据是 JWT（签发开销大、握手链路长）；SSE 是不透明随机串（现生成现用）。安全上 30 秒更优，**统一是改进项**——不能编一个'故意设计'。" |
| A9 | "你说重试次数按重要性定，可消费者有 3 次也有 5 次——标准在哪？" | "资金/库存类 5 次（重放幂等、不能丢），事件/通知类 3 次（丢了有对账）；分类不彻底是事实，统一成配置项是改进方向。" |
| A10 | "你说首页聚合单路失败不 500，但购物车又硬失败——降级标准是什么？" | "按**页面语义**：首页少卡片可接受；购物车页没有购物车=页面无意义。降级方向是产品语义决定的，不是技术开关。" |
| A11 | "你说订单号是唯一键兜底——那唯一键撞了订单创建不就失败了？" | "撞了=极小概率（同毫秒+同用户尾号+同序列余数），失败是**明确报错可重试**；比'静默重复单'安全得多。我们做过冲突概率测算。（见 V′）" |
| A12 | "你说 40 条告警治理过，日报还拆出 633 条失败——是不是告警冗余？" | "633 是**调度日报**的原始条目（含 625 条误报/未上报），不是 40 条运维告警；拆解本身就是为了消掉假告警，现在规则只留真实失败扇出。" |

## B. 第四层追问（对已准备答案再钻一层）

### 库存
| # | 第四层问题 | 关键洞察 |
|---|---|---|
| B1 | 桶不足时"扫其它桶"——扫多少？桶多呢？ | 从路由桶起**环形最多扫一圈**；桶数量级是 2~8，单次预扣最坏 8 次 GET，可接受；不开到百桶是刻意控制 |
| B2 | 扩容 2→8 桶时正在扣减？ | 扩容走"暂停标记 + 延迟消费"：消费端见 `inventory:paused:{sku}` 抛异常重投；期间不落新预扣 |
| B3 | 预扣 TTL 加了 10 分钟缓冲——那这 10 分钟里支付算"超时"吗？ | 订单侧 30 分钟是权威超时（支付发起会被拒）；库存侧的缓冲只影响"何时能安全回收记录"，不对用户可见 |
| B4 | 预扣幂等占位为什么"成功也保留 7 天"？ | 占位的职责是"Redis 记录丢了也不同订单重复扣"；重投窗口（MQ 重试+人工补）最长按天算，7 天是安全边界 |
| B5 | 对账发现 Redis 少扣了——补扣还是回滚订单？ | 只修账的差异（保守方向），**不反向动订单**；资金/订单语义由各自域负责，对账只做"账实相符" |

### 订单
| # | 第四层问题 | 关键洞察 |
|---|---|---|
| B6 | 事件冲突"回滚让调用方重试"——谁重试？会风暴吗？ | 重试来自 MQ 消费（3 次）或用户请求（手动）；冲突前提是"并发流转",重试时状态已是目标值→幂等跳过；不会放大 |
| B7 | 回查返回 UNKNOWN 后 Broker 多久再查？ | RocketMQ 默认最多回查 15 次、间隔递增（首查约 60s）；期间订单可能已超时关单——回查只决定"消息投不投"，关单是另一条路 |
| B8 | 状态校准多久跑一次？全量扫会不会太重？ | 每日一次、走 (status, created_at) 索引 + 时间窗（创建 2~8 天）+ 每分片 LIMIT，只做 dry-run 报告 |
| B9 | 订单分片扩容怎么不停机？ | 双写期→按新规则回填→路由切换→校验对比；历史用映射表兜非分片键查询（预案，未真实扩过容——承认） |

### 支付
| # | 第四层问题 | 关键洞察 |
|---|---|---|
| B10 | 迟到成功翻转 2→1，如果同时来了两条成功回调？ | 翻转是条件 UPDATE（WHERE status=2），单一赢家；赢家执行 afterPaySuccess，输家 0 行直接返回 |
| B11 | 延迟成功后自动退款也失败了呢？ | 只记 ERROR 日志——**这是已知缺口**（已登记）：应补"待退款"补偿任务/告警 |
| B12 | 对账差异人工标记已处理，下次对账又出现？ | 规则是"重现自动复位"（回到待处理）——防的是"假处理"；真已修复的差异不会重现 |
| B13 | 支付 30 分钟超时和预扣 30 分钟是同一个时钟吗？ | 都基于应用时间（同机同区）；跨时区/节点时钟漂移是理论风险，靠 NTP；更严可改用 DB 时间 |

### 券 / 购物车
| # | 第四层问题 | 关键洞察 |
|---|---|---|
| B14 | "回滚 Redis + 作废 Outbox"两步之间崩了？ | 顺序是**先作废后回滚**（作废成功才回滚）：崩溃在中间=Outbox 作废但 Redis 未回滚→计数偏紧（少发），对账按已发券修正回来（安全方向） |
| B15 | claimed 对账的"在途 ±1"窗口，恶意用户能否利用？ | 窗口是"已扣未发"的瞬态（秒级），对账日切执行；且限领多 1 次不产生资损（券库存仍原子扣） |
| B16 | 购物车合并取 max——用户想"以匿名车为准"呢？ | 语义选择：登录车是"主车"，max 防丢；要覆盖应给用户显式操作，而不是猜 |
| B17 | CLEAR 屏障 50k 满了被整体清空——此时乱序事件？ | 屏障只是第三层兜底；主保证是"按 userId 分区 ORDERLY"，清空屏障不会让主链路乱序 |

### 搜索 / IM / 通知 / 网关
| # | 第四层问题 | 关键洞察 |
|---|---|---|
| B18 | tombstone 7 天后，一个更早的 update 消息到了？ | 7 天>MQ 最大重试窗口（含 DLQ 人工重投时限），超过 7 天到达的消息按流程不会再投；这是"窗口设计"不是无懈可击 |
| B19 | 全量重建进行中，用户搜到死文档吗？ | 会（死文档清理在重建尾部）——但搜索的是**近似**：死文档可见窗口 ≤ 一次重建周期，且真实删除已由 tombstone 在增量链处理 |
| B20 | IM 客户端 ACK 丢了呢？ | 副本不删→重连补发→客户端按 msgId 去重；ACK 是"优化删除"不是"确认语义"（at-least-once 的代价） |
| B21 | 离线消息 1000 条截断——被裁掉的消息用户永远看不到？ | 裁掉的是**最老**的（ZREMRANGEBYRANK 0..n），新消息优先；老消息用户要回溯应走历史接口（从 DB 读） |
| B22 | 网关 503 时全站认证不可用，这不比 401 更糟？ | 语义不同：401 会让客户端**清 token 强制登出**（误伤）；503 可重试不登出。两害相权，选 503；根治是黑名单本地缓存+广播 |
| B23 | HMAC 默认关闭——那这条链有什么意义？ | 可选增强：高敏接口按需开；默认关的理由是客户端全量改造（签名+nonce 管理）成本高，收益（防篡改）在 HTTPS 下有限 |

## C. 白板设计题（用你们组件当积木，他会让你"现场设计"）

**C1. 给你一个 1 万 QPS 的秒杀，用你们现有组件怎么设计？**
骨架答法：① 资格前置——网关路由级限流 + 用户维度 @RateLimit（只放 N 倍库存的请求进来）② 库存分桶 + Lua 原子预扣（热点 SKU 自动扩桶）③ **异步下单**——预扣成功进 MQ，订单异步落库，前端轮询/推送结果 ④ 幂等——用户+商品维度唯一键 ⑤ 对账——库存/订单双向对账兜最终一致。关键取舍：同步转异步、拒绝率做在前端体验里（排队页），不硬扛 DB。

**C2. 设计一个对账系统，怎么保证不重不漏？**
骨架答法：① 定**权威源**（这里=渠道账单）② 幂等：`(账单日,渠道)` 唯一键 + 条件更新，重跑覆盖不产生重复 ③ 差异分类挂账（三类）+ 三态（待处理/已处理/已忽略）+ 收敛规则（消失/重现）④ 内存有界（游标分页 + 安全阀）⑤ 锁串行（按 (日期,渠道)）⑥ 未到账跳过（防假差异）。

**C3. 订单表要涨到 100 亿行，你的方案？**
骨架答法：① 先看查询模型（用户维度为主）② 水平扩容：4 库→N 库（一致性哈希/预分片位扩展），双写迁移+校验 ③ 时间维度归档：冷单进历史库，热窗口留 6~12 个月 ④ 非分片键查询继续走映射表 ⑤ 承认：扩片是大工程，预案比嘴上方案重要。

**C4. 怎么设计一个灰度发布系统？**
骨架答法：① 实例打标（Nacos 元数据 gray-tag）② 入口按用户哈希/白名单决定灰度标记（网关染色）③ 负载均衡按标记过滤实例（我们的 Zone LB 同构）④ 观测对比：灰度/稳定两组核心指标对比 + 自动回滚阈值 ⑤ 回滚：切回标记 + 版本回退（我们有版本化发布+自动回滚）。

**C5. 如果让你从零重做这个项目，哪里会改？**
骨架答法（诚实+判断）：① 事件表从第一天就带归档策略（现在补）② 票据/重试次数这类口径做成统一配置而不是散在各服务 ③ 幂等/限流的降级指标第一天就接告警（现在补）④ 少一个"计划外"的公共组件（如多版本 API），把复杂度花在交易链路。

## D. 反事实题（考判断力，别硬答"都行"）

| # | 问题 | 答法要点 |
|---|---|---|
| D1 | 分片键换 order_id 会怎样？ | 用户维度"我的订单列表"变跨片查询（最常用查询变最贵）；换来的是按单号点查更好——**查询模型决定分片键**，不值得 |
| D2 | 不用 Redis，库存怎么做？ | 纯 DB 行锁（`UPDATE ... WHERE available>=n`）能正确但 QPS 掉一个量级；折中是 DB 号段预分配+本地缓存（复杂度爆炸）。Redis 是这个问题的正确工具 |
| D3 | MQ 换 Kafka？ | 事务消息/延迟消息是我们的核心依赖——Kafka 无原生事务消息（有 EOS 但不是一回事）、延迟消息要自己搭；RocketMQ 功能匹配度更高 |
| D4 | 去掉 ES，搜索怎么做？ | MySQL LIKE 只能演示；真正替代是 PG 全文/Doris 等；ES 的代价是同步一致性，收益是分词/相关性/聚合——搜索域没有便宜的替代 |
| D5 | 团队 3 个人，15 个服务砍到几个？ | 砍到 5~6 个（用户+内容+交易+支付+网关+一个聚合），核心链路不能省（资金/库存必须独立隔离）；服务数应该跟**团队与故障域**走，不是跟域模型走 |

## E. 行为深挖（对 90 秒故事再钻）

| # | 追问 | 答法要点 |
|---|---|---|
| E1 | "682 行迁移期间服务在跑吗？数据一致性怎么保证？" | 迁移是**按 id 游标分批**、每条迁移后核对新旧路由；迁移期间双读校验（旧路由查不到就查新）——真实演练里服务未停 |
| E2 | "类加载锁为什么之前没人发现？" | 压测前 QPS 低，锁竞争没显现；**是压测把它逼出来的**——所以容量测试的价值不是达标数字，是暴露隐藏锁 |
| E3 | "三次技术分歧，有没有你错的时候？" | 有：我最初坚持"锁内重算 seq"，被 review 指出反向锁序死锁风险后改成"回滚重试"——**评审能改变我的结论，这比自己永远对更重要** |
| E4 | "你犯的错造成后果了吗？" | workerId 重号在演练环境被台账系统标出（353 vs 454 异常对比），**未流入生产**；保留清理吞吐不足是我自己 review 轮抓的——两个都是"机制抓到"不是"运气好" |
| E5 | "怎么证明你修好了？" | 每个修复都留了验证物：单测（59 个订单用例）、演练脚本输出（JSON 证据）、对账差异归零报表；不是"我觉得好了" |
| E6 | "如果给你更大的团队，你怎么带？" | 按域拆 owner + 接口契约先冻结 + 变更影响面广播 + 复盘沉淀到事实表；我自己就是这么被组织的，知道哪一步最容易被跳过 |
