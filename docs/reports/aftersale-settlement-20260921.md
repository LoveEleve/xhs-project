# 售后域 + 结算域：设计决策与分布式处理（2026-09-21）

> 范围：本次新增的两个业务域（售后/退款分摊、结算/三方对账）及配套的库存回补累计语义、恢复任务、业务指标。
> 用途：面试讲解底稿 + 后续维护的事实依据。所有金额口径与不变量都可从代码/表结构复核。

## 1. 售后域（order 域，t_aftersale）

### 1.1 状态机（全部条件更新 `WHERE status=期望值`）
```
待审核(0) ──同意──> 退款中(3) ──支付域受理成功──> 已完成(4)
   │                    │
   │                    └─失败/未知结果──> 退款失败(6) ──退避重试(≤3)──> 退款中(3)
   ├──驳回──> 已拒绝(2) ──可重新申请（重置同一行）
   └──撤销──> 已取消(5) ──可重新申请
```
- 唯一键 `(order_id, sku_id, type)`：同商品同类型只允许一张单；重新申请复用原行（`reapply` 带期望状态）。
- 并发审核/撤销/重试只有一个赢家（条件更新返回 0 即拒绝）。

### 1.2 金额口径 = 订单优惠分摊（`DiscountAllocator`，纯函数）
- 优惠按明细金额比例分摊（**分**为单位整数运算 + 最大余数法；平局按明细 ID → 同一订单重算结果恒定）。
- 不变量：`Σ分摊 == 优惠额`、`单项分摊 ≤ 单项金额`；`应退 = 明细金额 − 分摊优惠`。
- 部分数量按比例**向下取整**；**本次退满**时用"整件可退 − 已退金额"补齐差额 → 多次部分退款累计严格等于整件可退金额。
- 分摊结果不落库（按订单快照确定性重算）；若将来调整算法需加版本号。

### 1.3 三层金额护栏（防止超退）
| 层 | 校验 | 位置 |
|---|---|---|
| SKU 维度 | 同一 SKU 跨售后类型累计应退 ≤ 整件可退金额（申请时 + 审核时各判一次） | `AftersaleService.apply/audit` |
| 订单维度 | 已占用（退款中/已完成）+ 本次 ≤ 订单实付 | 同上 |
| 支付域 | `可退 = 支付金额 − Σ成功退款`（最后防线，任何上游绕过都被拦） | `PaymentService.doRefund` |

### 1.4 库存回补（inventory 域，按 SKU 累计正增量）
- 幂等键 `inventory:refund:{orderId}:{skuId}` 记录"已受理的应回补数量"，只回补**正增量**：
  重复/重试 `delta=0` 跳过；分次退货（先 1 件后 2 件）不漏补；与全额退款链路叠加不重复补。
- 失败时回滚累计值 + 写 `t_inventory_compensation(type=2)`，由 `InventoryCompensationJob` 自动重试（≤3 次）。

### 1.5 恢复任务（`AftersaleRecoveryJob`，10 分钟）
- 退款中卡死（>5 分钟）：**先查支付域退款单事实**（金额 + 类型 + 时间窗 + 退款单号归属）→
  已成功则补库存并置完成、仍有进行中则等待、无记录才转失败。解决"Feign 超时但支付已受理"的未知结果。
- 退款失败：退避 10 分钟自动重试，上限 3 次。
- 退款单号归属：支付域 `refund-by-order` 直接回传 `refundNo`，订单域按 `refund_no` 认领（一个成功退款只归属一张售后单）。

## 2. 结算域（payment 域，t_settlement_bill / t_settlement_diff / t_channel_flow）

### 2.1 日切口径（T-1 自然日，容器 TZ=Asia/Shanghai）
- 收款 = 当日 `paid_at` 的成功支付（含之后被退款的单，退款在退款侧统计）；退款 = 当日 `success_at` 的成功退款。
- 净额 = 收款 − 退款（可为负）；**手续费按收款毛额计提**（退款不退手续费）；应结算 = 净额 − 手续费。

### 2.2 幂等重跑
- 唯一键 `(bill_date, channel)`；重跑走条件更新（`status` 必须仍是读取时的值），`run_no` 累计重跑次数。
- 已对账账单需 `force=true`：**先重算成功、再清差异**（顺序不能反，避免条件更新失败时破坏差异记录）。
- 作废（VOID）后可重新生成即"重开"；对账遇到 VOID 账单会跳过（不复活）。

### 2.3 三方对账
- 匹配键 = (业务类型, 渠道回传的商户单号)：支付对 `payment_no`、退款对 `refund_no`（真实渠道的 `out_trade_no`/`out_refund_no` 语义）。
- 差异三类：本地有渠道无（短款）/ 渠道有本地无（长款，含未回传商户单号的行与重复行）/ 金额不一致。
- 挂账三态：待处理(0)/已处理(1)/已忽略(2)。重复对账幂等：人工已处理不被覆盖；**已忽略的差异重现时自动复位为待处理**（防漏报）。
- 自动收敛：本轮已无差异的待处理挂账置为"已忽略"（>500 笔时跳过，避免超长 SQL）。
- 账单差异口径 = **待处理挂账余额**（人工核销完自动回到"已对账"）；差异**不混入本期应结算金额**。
- 对账单未到（渠道延迟）→ 按到账标记跳过对账，避免"全量本地有渠道无"的假差异；空对账单也能打标。

### 2.4 渠道文件
- 导入幂等（唯一键 `(channel, channel_no)`）+ **整批事务**（解析中途失败不留半份对账单）。
- 演练入口 `simulate`（NONE/MISSING/EXTRA/AMOUNT）用于验证"对账 → 差异 → 挂账"闭环。

## 3. 分布式问题清单（本次处理）

| 问题 | 处理 | 兜底 |
|---|---|---|
| 售后审核并发（双类型同 SKU） | 申请 + 审核两次额度校验；超限自动驳回 | 支付域可退上限 |
| 跨库（公共库售后表 vs 分片库订单表） | 不做分布式事务：唯一键 + 条件更新 + 额度护栏 | 支付域上限 + 恢复任务 |
| 退款未知结果（超时/崩溃） | 恢复任务先查支付域事实再决策 | 退款单号唯一归属 |
| 库存回补分次/叠加 | 累计正增量语义 | 补偿表 + Job 重试 |
| 生成/对账并发 | `(日期,渠道)` SETNX 锁（生成与对账共用） | 条件更新 + 返回 0 告警 |
| 对账重复执行 | 差异 upsert 幂等 + 收敛/复位规则 | 唯一键 |
| 对账单延迟 | 到账标记，未到不对账 | 账单保持"已生成" |

`aftersale.apply.total{result}`、`aftersale.refund.total{result}`、`settlement.diff.total{channel,diffType}`、`settlement.reconcile.total{result}`（启动预注册空标签，避免系列被吞）。

## 5. 遗留（明确不做 / 待排期）
1. 退货退款(type=2) 的库存回补时点简化为"退款受理时"（真实应在入库质检后）；
2. 卡在"退款中"且支付域查询失败的售后单无自动回收上限（持续重试，需人工兜底）；
3. 渠道文件真实解析（CSV/SFTP）与"文件批次 + 校验和"未做（当前 import 接口 + 演练生成）；
4. 差异不自动补单（人工挂账处理，避免动钱）；出款/银行回单环节未做；
5. 分摊算法未加版本号（改算法会影响历史订单退款金额）；
6. 结算费率单一（未做按渠道/产品分档）。
