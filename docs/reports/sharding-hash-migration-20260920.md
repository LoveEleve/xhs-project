# 分片倾斜修复：取模 → 哈希取模 + 存量迁移（2026-09-20）

> 触发：跨片正确性 review 发现 order 分片严重倾斜（131 单全部落在 2/16 片，最大占比 75%）。

## 一、发现与根因（真问题）

| 证据 | 结果 |
|---|---|
| 16 分片分布（修复前） | ds1.t0=99、ds2.t0=32，其余 **14 片=0**（最大占比 75%） |
| 下单用户 `user_id mod 16` | 仅出现 **{1, 2}** |
| ID 增量 | 相邻用户 ID 增量 ~10^11-10^14，且常为 16 的整数倍 |
| 映射表一致性 | 131 = 131 ✓（非一致性问题） |

**根因**：Snowflake 增量 = `Δms << 22 + Δseq`；`Δms << 22` **恒被 16 整除**，低流量下 `Δseq` 多为 0 → 相邻用户 `user_id mod 16` 恒定。因此"**直接取模分片 + 时间型 ID**"在低流量/批量注册/导入场景**必然倾斜**（生产同样成立，不只是测试数据问题）。

## 二、修复：哈希取模 + 存量迁移

1. **算法**（`sharding-config.yaml` 6 条表达式）：
   `h = (user_id.hashCode() & 0x7fffffff)`；库 `ds = h % 4`；表 `t_xxx = (h / 4) % 4`（Groovy INLINE，ShardingSphere 5.5.1）。
2. **迁移**（`scripts/migrate-sharding-hash.py`，支持 `--dry-run`）：5 张分片表 × 16 片，按新算法逐行 `INSERT...SELECT + DELETE`。
   - DRY-RUN 预检：**682 行**需迁移；停 order 服务（~2 分钟窗口）后执行，共迁移 682 行。
   - 说明：算法切换是**破坏性变更**——不迁移存量则旧数据在新算法下不可见。
3. **审计工具**（`scripts/sharding-distribution-check.sh`）：分布倾斜（阈值可传，默认 50%）+ 映射一致性 + 路由抽查（按新算法复算期望分片），exit code 可用于告警/巡检。

## 五、边界与口径（面试可讲）
1. **取模 vs 哈希**：取模在"键低位均匀"时最简单；但时间型 ID（Snowflake）低位不平坦 → 哈希取模更稳；代价是**扩容/换算法都要数据迁移**（本项目无 rehash 方案）。
2. **同用户同片**是分片设计红线：热点用户会集中单片（10001 即例），可评估"热点用户二次拆分"或读写分离缓解。
3. **worker-id**：env `WORKER_ID` 优先、IP 兜底；**同机多实例会取同值**（本环境曾出现多实例）→ 容器部署必须注入唯一 WORKER_ID，否则 Snowflake 可能发重号。
4. **fold-hash（库存伪 orderId）**：SHA-256 取前 8 字节（64bit），碰撞概率 ~2^-32，可忽略（P2-12 已修）。
