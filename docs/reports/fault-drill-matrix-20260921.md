# 故障注入静态推演矩阵（2026-09-21）：故障 × 链路 → 用户可见行为 / 兜底 / 恢复上界

> 口径：单机仿真环境（故障用 pause / stop / iptables / kill 注入）。表内"恢复上界"= 依赖恢复后系统自动回到一致的**最坏时间**，不含人工介入。
> 用途：面试"故障题"答案库 + 兜底能力自检。每条都可回代码复核。

## 0. 恢复机制时间常数（先记住这些，推演全靠它）
| 机制 | 周期 | 说明 |
|---|---|---|
| 库存补偿 Job | 30s（`@Scheduled`，不经 XXL） | 预扣回滚 / 退款回补重试，最多 3 次 |
| 售后恢复 Job | 10 分钟（XXL） | 退款中卡死回收 + 退款失败重试 + 未回补重试 |
| 订单本地消息补发 | 30/60/120/240/480s 指数退避 + 死信小时级重投 | 事务消息兜底 |
| 购物车/关注对账 | 每日 4:00 / 每 10 分钟 | Redis↔MySQL 收敛 |
| 结算账单/对账 | 每日 02:00 / 03:00（misfire=FIRE_ONCE_NOW 会补跑） | 日切 |
| MySQL 主从切换 | 实测 RTO≈32s | 已演练 |
| Redis Sentinel 切主 | 实测 2.3s | 已演练 |
| MQ 消费重试 | RocketMQ 默认退避，`maxReconsumeTimes=3` 后进 DLQ | DLQ 有治理与清账 |

## 1. Redis 不可用（pause/不可达；含 Cluster 分片不可用）
| 链路 | 用户可见行为 | 兜底路径 | 恢复上界 |
|---|---|---|---|
| 售后申请/审核 | 申请：正常（售后不依赖 Redis）；审核：退款受理失败 → 售后单显示"退款失败" | 恢复任务退避重试（≤3 次自动，之后人工/重试端点） | ≤10 分钟/轮 |
| 结算生成/对账 | 内部可见：任务失败（抢锁/到账标记不可用），**不产生错误账单** | 下轮任务重试（每日任务 FIRE_ONCE_NOW 补跑） | 次轮（≤24h） |
| 库存回补 | 售后照常完成，库存稍后补齐 | ① 累计键读取失败 → **落补偿表**（本轮修，此前会静默放弃）；② 订单侧 `restock_status=0` → 恢复任务重试 | ≤30s（补偿 Job）/≤10 分钟（恢复 Job） |
| 购物车顺序消费 | 加购/改量直接失败（Redis 为权威，fail-fast，不是静默） | 无消息产生，无需兜底 | Redis 恢复即恢复 |

## 2. MySQL 主库不可用（切换窗口 ≈32s）
| 链路 | 用户可见行为 | 兜底路径 | 恢复上界 |
|---|---|---|---|
| 售后 | 申请/审核报错（写失败）→ 用户重试 | 唯一键 + 条件更新保证重试幂等 | 切换 32s + 用户重试 |
| 结算 | 任务失败日志 | 下轮重试 | 次轮 |
| 库存回补 | Redis 已加、MySQL 未加（不一致） | Outbox 事件表 + `InventoryOutboxSenderJob` 重发；对账以 Redis 为准修 DB | ≤ Outbox Job 周期 |
| 顺序消费 | 落库失败 → 消费重试 | `maxReconsumeTimes=3` → DLQ → DLQ 治理/对账 | 重试退避 + DLQ 处置 |

## 3. MySQL 从库不可用
| 链路 | 行为 | 兜底 |
|---|---|---|
| 全部新链路 | **无影响**：售后/结算读写的都是主库（order 走 ShardingSphere 主库、payment 单数据源；未开读写分离） | 库存服务若启用读写分离，从库故障自动降主 + 30s 探测恢复（既有实现） |

## 4. RocketMQ 不可用（Broker pause）
| 链路 | 用户可见行为 | 兜底路径 | 恢复上界 |
|---|---|---|---|
| 售后 | **无影响**（同步 Feign 退款，不经 MQ） | — | — |
| 结算 | **无影响**（读同库表） | — | — |
| 库存回补 | 库存 Redis 已加、MySQL 未加 | Outbox 表 + OutboxSenderJob 重发（消费者幂等） | Outbox Job 周期 |
| 购物车顺序消费 | 购物车操作仍成功（Redis 权威），落库事件丢失 | 每日 4:00 对账补录 MySQL | ≤24h |
| 订单/支付 MQ | 下单事务消息发送失败 → 业务失败无半成品（已实测） | 本地消息表补发 | 指数退避 |

## 5. 支付域整体不可用
| 链路 | 用户可见行为 | 兜底路径 | 恢复上界 |
|---|---|---|---|
| 售后审核 | 售后单"退款失败"（明确可见，不是假成功） | 恢复任务：查支付域事实→仍不可达则保持等待；可达后重试退款 | ≤10 分钟/轮 |
| 恢复任务 | 查询失败 → **保持"退款中"不误判**（避免把"查不到"当成"没退过"） | 下轮再查 | ≤10 分钟 |
| 结算 | 随支付域一起不可用（同服务）→ 账单延迟 | FIRE_ONCE_NOW 补跑 + 幂等重跑 | 次轮 |
| 库存回补 | 无影响 | — | — |

## 6. 库存域整体不可用（请求未到达）
| 链路 | 用户可见行为 | 兜底路径 | 恢复上界 |
|---|---|---|---|
| 售后 | 退款照常完成（支付域独立），库存稍后补齐 | ① 订单侧 `restock_status=0` → 恢复任务重试（本轮修，覆盖"请求未到达、库存域内部无记录"盲区）；② 重试幂等（累计正增量） | ≤10 分钟/轮 |
| 结算 | 无影响 | — | — |

## 7. XXL-Job 停摆（调度器/执行器挂）
| 链路 | 用户可见行为 | 兜底路径 | 恢复上界 |
|---|---|---|---|
| 在线交易链路 | **无影响**（申请/审核/退款都是同步执行，不等 Job） | — | — |
| 售后异常单 | 卡死单不回收、退款失败不重试、未回补不重试（延迟，无数据错误） | Job 恢复后按 id 扫描一次性追平 | Job 恢复即追平 |
| 结算 | 账单缺失/不对账 | 每日任务 FIRE_ONCE_NOW 补跑 + 幂等重跑 | 恢复后当日补跑 |
| 库存补偿 | **不受影响**（`@Scheduled` 自带调度） | — | — |
| 顺序消费 | **不受影响**（RocketMQ 推送驱动） | — | — |

## 8. 面试速答（每条一句话）
1. **Redis 挂**：售后照常（不依赖 Redis），结算是"干净失败"（不产错账），库存回补走补偿表/restock_status，购物车 fail-fast。
2. **MySQL 主挂**：切换 32s 内写失败即报错，重试幂等；库存侧靠 Outbox + 对账收敛。
3. **MySQL 从挂**：新链路读全走主库 → 无影响（这也是"金额校验必须主库读"的原因）。
4. **MQ 挂**：售后与结算完全不受影响（同步链路）；库存靠 Outbox，购物车靠每日对账。
5. **支付域挂**：售后单明确置"退款失败"而不是假成功，恢复任务先查事实再决策（查不到就等待，不误判）。
6. **库存域挂**：跨服务盲区由售后单 `restock_status` 兜底（请求未到达也能补）。
7. **XXL 停摆**：只影响"兜底型任务"（延迟不丢数据），在线链路同步执行不受影响；库存补偿自带 `@Scheduled` 不受影响。
