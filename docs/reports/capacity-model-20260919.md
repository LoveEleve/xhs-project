# 容量模型演算（基于实测基线的 10× 扩容推演）2026-09-19

> 目的：把"实测 RPS"升级成"可回答白板题的容量模型"：公式 → 底数 → 10× 演算 → 瓶颈排序。
> 数据来源：`batch-release-baseline-20260917.md`（权威）、`comment-sql-tuning-20260917.md`、`skywalking-overhead-20260918.md`；所有假设显式标注。

## 一、实测基线（单实例，16C/62G 单机，与 14 个服务/中间件共享）

| 接口 | 实测 RPS | P99 | 口径 |
|---|---:|---:|---|
| product 详情 | **4,871** | 50ms | 类加载锁修复后；**无本地缓存**（L1 已按决策移除） |
| comment 列表 | **4,418** | 70ms | 清僵尸连接后（ab n=20000 c=64，0 失败） |
| home 聚合 | **1,861** | 49.6ms | c=64（c=128 时 1,794 / P99 89.7ms） |
| search | **1,448** | 61ms | ES 容器 CPU 2→6 核、客户端 IO 线程 16、recall 池 32/64 |

## 三、五条容量公式（白板用）

1. **在途并发（Little's Law）**：`在途 = RPS × P99(s)`
   - product：4,871 × 0.050 ≈ **244**；comment：4,418 × 0.070 ≈ **309**；home：1,861 × 0.0496 ≈ **92**
   - 推论：Tomcat 默认 200 线程时，comment 这类 309 在途的链路必须靠"线程数 ≥ 在途 + 队列"或异步化，否则排队先于 CPU 饱和。
2. **实例数**：`N = 目标RPS / 单机RPS × 安全系数(1.5)`
3. **分片数**：`分片 ≥ 写目标 / 单库写能力`（order 已 4×4；读扩展用从库/分片，不靠加线程）
4. **连接池**：`池 ≥ RPS × 单请求持有时长`（每秒并发查询数 ≈ RPS × 每请求 SQL 数；别把 500 个 MySQL 连接当作可无限切）
5. **缓存杠杆**：命中率每降 10%，回源 QPS 增约 `RPS × 10% × 每请求回源次数`——本项目读路径无 L1，Redis/索引即杠杆。

## 四、10× 演算（目标：读 5 万级、写千级）

假设：目标 = 当前实测 ×10；安全系数 1.5；单服务先水平扩应用，再动中间件。

| 对象 | 10× 目标 | 演算 | 结论 |
|---|---:|---|---|
| product | 48,710 RPS | 48,710/4,871×1.5 ≈ **15 实例** | 应用 CPU 先扩；DB 基本不参与（缓存+索引） |
| comment | 44,180 RPS | ≈ **14 实例**；DB 连接 106×10=**1,060 > 500** | **必须先分片/读副本**（按 note_id 8 片），否则连接数是硬墙 |
| home | 18,610 RPS | ≈ **15 实例**（聚合层，P99 需 <100ms） | 聚合层降级策略要同步扩 |
| search | 14,480 RPS | 应用 ≈15 实例；ES 1,448/节点 → **≥10 节点** | 索引分片×副本重规划（当前单节点=单点故障） |
| 网关 | 50,000 RPS | 单实例未单测，按 5k-10k/实例估 → **5-10 实例 + LB** | Sentinel 限流从"单点挡洪"变"集群协同"，规则仍走 Nacos |
| 写链路（order） | 假设峰值 500 TPS | 当前 1 实例承载 4 逻辑库；单库写能力按 1-2k TPS 估 | **第一步：4 个逻辑库拆到 4 个物理实例**；再按 user_id 扩 4→8 库 |
| Redis | 读 ops ≈ 50k×2 + 库存 Lua/计数 | 单主理论上限 ~10 万 ops/s，**10× 已接近** | Redis Cluster/多主（已有双主 LWW 经验）+ 库存分桶（bucketCount 已 2，可调） |
| MySQL（整体） | 连接/CPU/buffer pool | buffer_pool 仅 1GB | 扩容同时提 buffer pool 到内存 50%+，否则索引命中先崩 |
| MQ | 订单/事件 10× | 单 broker 顺序写余量充足 | 先不动，观察发送 RT 与堆积即可 |

## 五、瓶颈排序（先修谁）

1. **MySQL 单实例**：连接数上限 500 + buffer pool 1GB + 僵尸连接教训（曾打到 459/500）→ 扩容量第一步。
2. **ES 单节点**：search 既是功能依赖又是单点故障。
3. **Redis 单主**：接近单主 ops 上限且 noeviction，扩容要动数据面。
4. **应用侧**：水平扩实例 + 先把线程/池按 Little's Law 调准（否则扩了实例仍排队）。
5. **MQ/网关**：余量大，主要是集群化配置与规则协同。

## 六、验证计划（下一步该压什么）
- 单库写能力实测（order create TPS 拐点）→ 校准分片数；
- 网关单实例吞吐（开/关 Sentinel）→ 校准网关实例数；
- Redis ops 上限实测（Lua 库存脚本）→ 校准 Cluster 阈值。

## 七、与架构专题的关系
`docs/interview/专题-架构专题.md` 的"扩容 10 倍"话术升级为：**先用 Little's Law 算在途、用实例数公式扩应用、用连接数/ops 上限定位数据面瓶颈、写链路先拆物理库**——数字与公式全部来自本文。
