# Review 第六轮（2026-09-19）：限流规则 vs 真实流量匹配度

> 换面：把"限流生效"升级为"限流配置是否匹配业务"——覆盖对照、阈值 vs 容量/峰值、误伤检查、风险清单。

## 一、覆盖对照

| 项 | 结果 |
|---|---|
| 网关路由 vs Sentinel gw-flow 规则 | **16 : 16，双向无缺口** ✓ |
| `@RateLimit` 注解 | 40 处（读 30-120/min、写 2-20/min、管理类 2-5/min 全局） |
| 双层职责 | 网关=路由级 QPS（防入口洪峰）；注解=用户级/接口级（防单用户高频） |

## 二、阈值 vs 容量 vs 观测

| 对象 | 规则阈值 | 实测容量（无本地缓存口径） | 24h 观测峰值 |
|---|---:|---:|---:|
| product 路由 | 500 QPS | 4,871 RPS | <1 RPS |
| content 路由 | 500 QPS | 4,418 RPS | <1 RPS |
| search 路由 | 300 QPS | 1,448 RPS | <1 RPS |
| home 路由 | 300 QPS | 1,861 RPS | <1 RPS |
| payment 路由 | **5 QPS** | 未单测 | <1 RPS |
| order 路由 | **10 QPS** | 未单测 | <1 RPS |

- 读路由规则 ≈ 容量的 1/3 ~ 1/10 → 作为"入口保护"合理（留出业务增长与突发余量）。
- 当前系统空闲（峰值 <1.3 RPS），全部规则余量 ≥4×，无正常流量误伤。

## 四、风险清单（发现，待决策）

1. **payment 路由 5 QPS 覆盖渠道回调**（`Path=/api/payment/**` 含 `/api/payment/callback/**`）：
   生产大促时渠道回调可能突发 >5/s，被网关限流将导致订单状态收敛延迟（依赖对账/补偿兜底）。
   建议：为回调单独路由（如 `/api/payment/callback/**`）并放宽/豁免，或提高 payment 路由配额；需产品/风控决策，**本轮未改**。
2. **`counter:get` 全局 50 QPS（无 perUser）**：若被直连高频调用会全局误伤；
   澄清：home 聚合走 `/api/counter/batch-get`（未限流）不受影响，属潜在而非现存问题。建议提高配额或改 perUser。
3. **双层叠加口径**：写操作同时受"路由 QPS + 用户级注解"限制（如 order create 5/min/user + 路由 10 QPS），属有意防刷；面试需能解释两层互补而非冲突。

## 五、结论
- 规则-路由零缺口、正常流量零误伤；阈值与容量呈合理保护比。
- 两项风险（payment 回调、counter 全局桶）登记待决策，改动会影响线上行为，本轮只报告不改配置。
