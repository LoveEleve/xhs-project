## 二、网关与限流（重要修正）

**现象**：网关 wrk 出现 8k~16k RPS，一度疑似"缓存"。经对账：
- 网关 6s 服务 83,551 请求（13.9k RPS），但**后端仅收到 300**（= user 路由 50 QPS × 6s）；
- 突发 200 连发：**50×200 + 150×429** —— 全部是 **Sentinel 限流（50 QPS）** 的快速 429 路径，不是缓存、不是真实容量。

**动态放行后（Nacos 改 100000 QPS，无需重启）**：
| 指标 | 直连 | 经网关 |
|---|---:|---:|
| RPS | 958~981 | **962.6** |
| P50 | ~33ms | **32.8ms** |
| P99 | 68ms | **66.6ms** |
| 后端收单 | 全量 | delta=14,481 ≈ 962×15 ✅ 全量转发 |

结论：**网关代理开销 ≈ 0**（吞吐持平、延迟持平）；网关侧快速 429 通道吞吐 ~14k RPS（限流削峰能力）。
规则已恢复 50 QPS（复测 50/150 ✅）。

## 五、深核修正（2026-09-17 晚，重要）
1. **search "0.2% 失败" 系误判**：ab 报 `Length: 1`（响应体可变导致的长度不匹配），`Non-2xx=0`；应表述为"长度不匹配，非 HTTP 失败"。
2. **cart "2940/3000 失败" 系业务限流**：`@RateLimit 60/min/user` 超限后返回 **HTTP 200 + code 40202**（body 长度不同 → ab 记为 Length 失败）。实测：配额内顺序 70 发全 200；超配额并发 100 全 `40202` —— 限流器工作正常，但**限流返回 HTTP 200** 是 API 语义问题（客户端/SLO 监控会当成功）。
3. **Metaspace 99% 撤销**：运行实参仅 `-Xmx512m`（**未设 MaxMetaspaceSize**），M%≈used/committed 属正常水位；此前"风险项"结论撤回（若未来设 256m 上限再评估）。
4. **网关高吞吐 ≠ 缓存**：是 Sentinel 50 QPS 放行 + 快速 429 通道（突发 50×200+150×429；后端 delta=50×6s=300 对账吻合）。

**方法论教训（写进 SOP）**
1. ab 对 chunked+keep-alive（网关/home）不兼容 → 统一用 wrk；
2. 业务错误可能返回 HTTP 200 → 必须校验 body `code`；
3. 压测前先单发校验（注意业务码），避免打"错误路径"得出假容量（note/1 案例）；
4. 网关基准必须先看限流配额，或用 Nacos 动态放行。
