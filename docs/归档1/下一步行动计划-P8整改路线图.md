| # | 任务 | 工时 | 说明 |

- 购物车 Key `myxhs:cart:*`、社交 Key `myxhs:follow:*` `myxhs:like:*` `myxhs:favorite:*`、优惠券 Key `coupon:template:*:stock`、ID Key `id:sequence:*` 全部存储在 noeviction 实例中
- 缓存 Key `cache:*` 存储在 allkeys-lru 实例中
- 验证脚本确认无 Key 错误分布

## 十、风险提示

| 风险 | 影响 | 缓解措施 |
|:---|:---|:---|
| Redis 拆分涉及代码改动量大（8 类数据 × 多模块） | 可能引入新 Bug，购物车/社交功能异常 | 先在 dev 分支验证，每步有回滚方案，按模块逐一切换而非批量 |
| ES single-node→3节点迁移 | 数据重建耗时（snapshot/restore 可能数小时） | 先在测试环境演练，记录迁移耗时，预留充足的维护窗口 |
| Sentinel 全覆盖可能触发意外限流 | 影响可用性，正常流量被拒 | 初期阈值设为极高值（仅观测不拦截），逐步收紧；每步有 Grafana 面板监控 |
| 测试补充需要理解业务逻辑 | 工时可能超预估（33 个用例涉及事务消息/Lua/Mock） | 优先覆盖核心路径（下单/支付/库存），边际用例后续补充 |
| Jenkins/K8s 部署依赖运维资源 | 可能延期 | 如 K8s 不可用，先用 Docker Compose + 脚本实现滚动更新 |
| **ShardingSphere MOD→一致性 Hash 切换** | 数据迁移错误导致订单路由混乱 | 严格按 任务 37 的迁移方案执行，先在测试环境全量验证，迁移时双写过渡 |
| **推荐引擎真实化（精排/Geo/特征）质量** | 如果补全实现粗糙，推荐效果可能不如简单的热门兜底 | 精排先做加权规则（非 ML），Geo 先用 ES geo_distance 验证召回率，AB 对比后再上线 |
| **第 5~6 周工时密度最高（原始 94h/2周，1 人绝对无法完成）** | 限流四层+推荐引擎+ShardingSphere 切换三条线并行 | **强制 2 人并行**：1 人限流体系（任务 47-60），另 1 人推荐引擎+ShardingSphere（任务 70-73）。或延后 L4 非核心限流（任务 57-60）到第 7 周 |
| **第 7~8 周工时同样超单人上限（原始 91h/2周）** | CI/CD+测试+压测+中间件HA+P1收尾五线并行 | 中间件 HA（任务 90-93，19h）标注"资源允许时"，可延后到第 9~10 周独立阶段 |
| **Refresh Token Rotation 安全测试复杂度** | 旧 token 失效逻辑可能误杀正常用户 | 先在测试环境模拟 token 盗用场景，灰度发布时分批验证 |
