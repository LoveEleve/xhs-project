# 消息可靠性全链路

> 所属维度：分布式方案 | 开发阶段：Phase-6 | 核心组件：RocketMQ + 本地消息表

---

## 🎯 一、消息可靠性的本质

> 📖 **知识来源**：《深入理解分布式事务》第7章 — 消息可靠性保证
> - "消息可靠性 = 生产端不丢 + 消费端不丢 + 不重复消费。三者缺一不可"
> - "生产端：事务消息保证'本地事务成功则消息一定发出'，回查机制兜底"
> - "消费端：幂等消费(业务唯一键去重) + 死信队列(消费失败进DLQ) + 人工兜底"

---

## 📋 二、六大环节

| # | 环节 | 问题 | 解决方案 | my-xhs落地 |
|---|------|------|----------|-------------|
| 1 | **生产端发送** | 发到MQ失败 | 本地消息表 + 定时重发 | ✅ |
| 2 | **MQ存储** | MQ宕机丢消息 | 同步刷盘 + 主从复制 | ✅ RocketMQ配置 |
| 3 | **MQ投递** | 网络问题未投递 | 消费者确认机制 | ✅ |
| 4 | **消费端处理** | 业务处理失败 | 重试(16次阶梯间隔) + 死信队列 | ✅ 封装在common |
| 5 | **消费端幂等** | 重复消费 | @Idempotent + Redis去重 | ✅ |
| 6 | **消息顺序** | 同一业务消息乱序 | HashQueue(同一key走同一queue) | ✅ 评论场景 |

## 🏗️ 三、死信队列处理流程

```
消费者失败 → 重试1次(10s) → 重试2次(30s) → ... → 重试16次(2h)
                                                            ↓
                                                      进入死信队列
                                                            ↓
                                                    DeadLetterHandler
                                                            ↓
                                              ┌────────────┼────────────┐
                                              ↓            ↓            ↓
                                          记录日志     告警通知    XXL-Job定时
                                          (ES/DB)     (钉钉/企微)   人工处理
```

## 💻 四、核心实现

### 4.1 本地消息表

```
为什么需要本地消息表？
- RocketMQ可能丢消息(磁盘故障/网络分区)
- 半消息可能超时未提交

实现：
1. 下单时同时写入order表和local_message表(同一事务)
2. 发送MQ消息
3. XXL-Job每分钟扫描local_message表(status=未发送/超时)
4. 重新发送消息
5. 消费成功后更新local_message.status=已发送
```

### 4.2 幂等消费

```java
@RocketMQMessageListener(topic = "order_create")
public class OrderCreateConsumer implements RocketMQListener<MessageExt> {
    @Override
    public void onMessage(MessageExt msg) {
        String bizId = msg.getKeys();  // orderId作为幂等Key
        // Redis SET NX判断是否已处理
        if (!redis.setnx("idempotent:" + bizId, "1", 86400)) {
            log.info("重复消息，跳过: {}", bizId);
            return;
        }
        // 业务处理...
    }
}
```

### 4.3 顺序消费

```java
// 评论场景：同一笔记的评论必须有序
// 发送时：用noteId作为hashKey，保证同一笔记的消息进同一个queue
rocketMQTemplate.sendOneWay("comment_topic", 
    MessageBuilder.withPayload(comment)
        .setHeader(RocketMQHeaders.KEYS, comment.getNoteId().toString())
        .build(),
    comment.getNoteId().toString());  // hashKey = noteId
```

## ⚖️ 五、方案对比

### 5.1 消息可靠性方案对比

| 维度 | 事务消息 | 本地消息表 | 事务消息+本地消息表 |
|------|---------|-----------|------------------|
| 实时性 | 高(Broker实时投递) | 低(定时扫描) | 高(正常走事务消息) |
| 可靠性 | 依赖Broker | 不依赖Broker | 最高(互补) |
| 复杂度 | 中 | 中 | 高 |

**最终选择**：事务消息(主) + 本地消息表(兜底) — 正常走事务消息保实时性，Broker故障时本地消息表补偿。

## 🐛 六、踩坑记录（已知坑）

### 6.1 MQ消息重复消费导致重复扣库存

- **现象**：库存扣了2次，实际只有1个订单
- **原因**：MQ至少投递1次(at-least-once)，网络抖动导致ACK丢失，MQ重投
- **解决**：@Idempotent注解 + Redis SETNX(bizId, "1", 24h)
- **教训**：**所有消费者都必须做幂等**，没有例外

### 6.2 事务消息回查频率过高

- **现象**：Broker频繁回查本地事务状态，日志刷屏
- **原因**：本地事务执行太慢(>60秒)
- **解决**：本地事务只做快操作(写order表+写local_message表)，慢操作交给消费端
- **教训**：事务消息的本地事务要尽量快

### 6.3 消费堆积

- **现象**：消息堆积数万条
- **原因**：消费端有慢查询/突发流量
- **解决**：临时增加消费者实例 + 消费端优化(批量消费)
- **教训**：监控消费堆积数 > 5000 → 告警

## 🎤 七、面试考察点

### Q1: 消息可靠性怎么保证的？

**推荐回答思路**：

> 1. "分6个环节保证：发送端本地消息表、MQ同步刷盘+主从、消费端重试+死信、幂等消费、顺序消费"
> 2. "重点说事务消息+本地消息表双保险：正常走事务消息，MQ挂了本地消息表定时补偿"
> 3. "消费端@Idempotent保证重复消费不出错"

### Q2: 消息丢了怎么办？

**推荐回答思路**：

> 1. "生产端丢：本地消息表 + XXL-Job每分钟扫描补发"
> 2. "Broker丢：同步刷盘+主从复制，极端情况本地消息表兜底"
> 3. "消费端丢：重试16次+死信队列+告警+人工处理"
