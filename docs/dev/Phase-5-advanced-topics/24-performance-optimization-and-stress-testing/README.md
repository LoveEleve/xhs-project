## 🎯 一、压测方法论

### 1.1 压测目标

| 维度 | 目标 | 说明 |
|------|------|------|
| 性能基线 | 各核心接口 QPS/RT/P99 | 知道系统能扛多少 |
| 瓶颈定位 | 找到最先扛不住的环节 | CPU/内存/IO/网络/DB/Redis |
| 容量规划 | 需要多少机器扛住目标流量 | 大促扩容依据 |
| 优化验证 | 优化前后数据对比 | 证明优化有效 |

### 1.2 压测场景设计

| 场景 | 接口 | 目标 QPS | 说明 |
|------|------|---------|------|
| 首页 Feed | GET /api/home/feed | 20000 | 最高频页面 |
| 笔记详情 | GET /api/home/note/{id} | 10000 | 详情页 |
| 搜索 | GET /api/search/note | 8000 | 搜索 |
| 下单 | POST /api/order/create | 2000 | 核心交易 |
| 支付 | POST /api/pay/create | 1000 | 核心交易 |
| 领券 | POST /api/coupon/claim | 5000 | 大促抢券 |
| 混合场景 | 以上按比例混合 | 50000 | 模拟真实流量 |

### 1.3 压测工具

| 工具 | 用途 | 说明 |
|------|------|------|
| JMeter | HTTP 接口压测 | 支持分布式压测、参数化、断言 |
| wrk | 轻量级压测 | 单机高并发，适合单接口基线 |
| GoReplay | 流量录制回放 | 录制生产流量 → 回放到压测环境 |
| Arthas | 在线诊断 | 方法级耗时分析、火焰图 |
| SkyWalking | 链路追踪 | 慢链路定位 |

## 🏗️ 二、瓶颈定位方法论

### 2.1 四步定位法

```
Step 1: 压测 → 观察 QPS/RT/错误率
Step 2: 监控 → Grafana 看 CPU/内存/IO/网络
Step 3: 链路 → SkyWalking 找慢 Span
Step 4: 方法 → Arthas trace/watch 定位到具体代码行
```

### 2.2 常见瓶颈与优化

| 瓶颈 | 现象 | 定位方式 | 优化手段 |
|------|------|---------|---------|
| DB 慢查询 | RT 高，CPU 低 | SkyWalking SQL 耗时 | 加索引/优化 SQL/读写分离 |
| Redis 热 Key | RT 抖动 | Redis MONITOR | 本地缓存/分桶 |
| 连接池耗尽 | 错误率飙升 | Druid 监控 | 调大连接池/优化慢查询 |
| GC 停顿 | RT 毛刺 | GC 日志 | 调整堆大小/G1 参数 |
| 线程池满 | 请求排队 | Tomcat 线程监控 | 调大线程池/异步化 |
| 网络带宽 | QPS 上不去 | 网卡监控 | 压缩响应/减少数据量 |

## 💻 三、优化案例

### 3.1 案例：下单接口从 600ms 优化到 150ms

```
优化前：串行调用 4 个服务
  查地址(50ms) → 查SKU(80ms) → 查库存(60ms) → 查优惠券(40ms) = 230ms
  + 写DB(100ms) + 发MQ(50ms) = 380ms
  总计 ≈ 600ms

优化后：CompletableFuture 并行查询
  并行查(地址+SKU+库存+优惠券) = max(80ms) = 80ms
  + 写DB(100ms) + 发MQ(50ms) = 230ms
  总计 ≈ 150ms（提升 75%）
```

### 3.2 案例：Feed 流从 500ms 优化到 80ms

```
优化前：串行聚合 6 个服务
优化后：CompletableFuture 2层并行 + Caffeine 5秒缓存
  第1层并行(笔记+社交+通知) = 50ms
  第2层并行(用户+计数) = 30ms
  总计 = 80ms
  缓存命中时 = 0ms
```

## 🐛 五、踩坑记录

### 5.1 JMeter 压测端成为瓶颈

- **现象**：QPS 上不去，但服务端 CPU 很低
- **原因**：JMeter 单机线程数过多，JMeter 自身成为瓶颈
- **解决**：JMeter 分布式压测（多台压测机）

### 5.2 压测数据污染生产

- **现象**：压测后生产数据库多了大量测试订单
- **解决**：全链路流量染色 + 影子表（参考 23-全链路流量染色）

## 🌊 七、流量漏斗模型（科学推算各接口 QPS）

> 参考华仔第98篇：流量漏斗模型。my-xhs 之前的 QPS 预估是拍脑袋的，缺少从"100万DAU→各接口QPS"的科学推算链路。

### 7.1 什么是流量漏斗模型

互联网产品本身就是一个虚拟的漏斗，用户的行为路径逐层递减：

```
100万 DAU
  │
  ├── 80% 浏览首页 Feed → 80万次/天 → 峰值 QPS = 80万×3/86400 ≈ 28
  │     │
  │     ├── 60% 点击笔记详情 → 48万次/天 → 峰值 QPS ≈ 17
  │     │     │
  │     │     ├── 10% 点赞 → 4.8万次/天 → 峰值 QPS ≈ 1.7
  │     │     ├── 5% 评论 → 2.4万次/天 → 峰值 QPS ≈ 0.8
  │     │     └── 3% 收藏 → 1.4万次/天 → 峰值 QPS ≈ 0.5
  │     │
  │     └── 20% 搜索 → 16万次/天 → 峰值 QPS ≈ 5.6
  │
  ├── 30% 浏览商品 → 30万次/天 → 峰值 QPS ≈ 10
  │     │
  │     ├── 15% 加购物车 → 4.5万次/天 → 峰值 QPS ≈ 1.6
  │     │
  │     └── 5% 下单 → 1.5万次/天 → 峰值 QPS ≈ 0.5
  │           │
  │           └── 80% 支付 → 1.2万次/天 → 峰值 QPS ≈ 0.4
  │
  └── 5% 发布笔记 → 5万次/天 → 峰值 QPS ≈ 1.7
```

> **注意**：以上是单次访问的漏斗。实际用户一天会多次访问，所以日调用量 = DAU × 日均访问次数 × 漏斗转化率。

### 7.2 my-xhs 流量漏斗推算

| 行为 | 日均次数/用户 | DAU转化率 | 日调用量 | 峰值系数 | 峰值QPS |
|------|-------------|----------|---------|---------|---------|
| 首页Feed | 5次 | 80% | 400万 | 3 | 139 |
| 笔记详情 | 8次 | 60% | 480万 | 3 | 167 |
| 搜索 | 2次 | 30% | 60万 | 5 | 35 |
| 点赞 | 3次 | 20% | 60万 | 3 | 21 |
| 评论 | 0.5次 | 10% | 5万 | 3 | 1.7 |
| 商品详情 | 3次 | 30% | 90万 | 3 | 31 |
| 加购 | 0.5次 | 10% | 5万 | 5 | 2.9 |
| 下单 | 0.2次 | 5% | 1万 | 10 | 1.2 |
| 领券 | 0.1次 | 5% | 5000 | 20 | 1.2 |
| 登录 | 1次 | 50% | 50万 | 5 | 29 |
| **合计** | — | — | — | — | **≈430** |

> **结论**：100万DAU的峰值总QPS约430，加上内部服务间调用放大（约3倍），到各中间件的QPS约1300。这与 `14-capacity-and-infra-consistency-analysis.md` 中的推算一致。

### 7.3 为什么需要流量漏斗（vs 拍脑袋）

| 维度 | 拍脑袋 | 流量漏斗 |
|------|--------|---------|
| 可信度 | 面试官一追问就露馅 | 有推算过程，可自圆其说 |
| 精确度 | 各接口QPS比例不合理 | 符合真实用户行为分布 |
| 扩展性 | DAU变了全部重算 | 只需调整DAU，漏斗比例不变 |
| 面试价值 | "我估计QPS是1万" | "我按流量漏斗推算，100万DAU峰值QPS约430" |

## 🔄 八、GoReplay 全链路压测实战

> 参考华仔第98/100篇：GoReplay 流量录制/重放技术深度实战。
> 单接口 JMeter 压测有盲区——某些低QPS接口可能是系统瓶颈，全链路压测才能发现。

### 8.1 为什么需要全链路压测（vs 单接口压测）

| 维度 | 单接口压测（JMeter） | 全链路压测（GoReplay） |
|------|-------------------|---------------------|
| 覆盖范围 | 单个接口 | 所有接口按真实比例混合 |
| 流量模型 | 人工构造 | 录制线上真实流量 |
| 发现问题 | 单接口瓶颈 | 接口间连锁反应、资源竞争 |
| 典型盲区 | ❌ 低QPS接口拖垮全局 | ✅ 能发现 |
| 数据真实性 | 参数化数据 | 真实用户请求参数 |

### 8.2 GoReplay 工作原理

```
生产环境                          测试环境
┌──────────┐                    ┌──────────┐
│  Nginx   │                    │  Nginx   │
│  :8080   │                    │  :8080   │
└────┬─────┘                    └────▲─────┘
     │                               │
┌────▼─────┐    录制/回放        ┌────┴─────┐
│ GoReplay │ ──────────────────▶│ GoReplay │
│ (监听网卡)│    .gor文件         │ (回放)    │
└──────────┘                    └──────────┘
```

**GoReplay 不是代理**，而是在后台监听网卡流量，对生产环境零侵入。

### 8.3 GoReplay 实战命令

```bash
# ① 录制：捕获生产环境 8080 端口的 HTTP 流量，保存到文件
sudo gor --input-raw :8080 \
  --output-file /tmp/gor/traffic-%Y%m%d.gor

# ② 回放：将录制的流量回放到测试环境
sudo gor --input-file /tmp/gor/traffic-*.gor \
  --output-http http://test-env:8080

# ③ 流量放大（2倍速回放，模拟流量突增）
sudo gor --input-file /tmp/gor/traffic-*.gor \
  --output-http http://test-env:8080 \
  --output-http-track-response \
  --output-http-workers 16 \
  --output-http-timeout 10s \
  "|200%"

# ④ 实时镜像（生产流量实时复制到测试环境）
sudo gor --input-raw :8080 \
  --output-http http://test-env:8080

# ⑤ 过滤指定路径（只录制 /api/ 开头的请求）
sudo gor --input-raw :8080 \
  --http-allow-url "/api/" \
  --output-file /tmp/gor/api-traffic.gor

# ⑥ 排除健康检查等无关请求
sudo gor --input-raw :8080 \
  --http-disallow-url "/actuator/" \
  --http-disallow-url "/health" \
  --output-file /tmp/gor/traffic.gor
```

### 8.4 GoReplay vs 其他流量重放方案

> 参考华仔第98篇方案对比，以下是 my-xhs 的选型结论：

| 方案 | 层级 | 优点 | 缺点 | my-xhs 采纳？ |
|------|------|------|------|-------------|
| **GoReplay** | 网络层 | 轻量零侵入、支持HTTP、流量放大、过滤 | 仅支持HTTP | ✅ **采纳** |
| Nginx mirror | Web服务器层 | 原生支持 | reload影响线上、mirror子请求阻塞nginx | ❌ 不采纳 |
| JVM-Sandbox-Repeater | 应用层 | 支持Java方法级录制 | 挂载瞬间占资源、功能不完善需二次开发 | ❌ 不采纳 |
| TcpCopy | 网络层 | 支持TCP全协议、放大20倍 | 需部署intercept辅助服务器、不支持应用层解析 | ❌ 不采纳 |

**选型理由**：my-xhs 是 HTTP 微服务架构，GoReplay 完全满足需求，且零侵入、部署简单、大厂（腾讯/京东/阿里）广泛使用。

### 8.5 全链路压测实施步骤

```
Step 1: 部署 GoReplay 到生产环境（与服务同机器）
Step 2: 录制 1 小时高峰期流量（保存 .gor 文件）
Step 3: 在测试环境部署影子库/影子表（数据隔离）
Step 4: 1倍速回放 → 观察各服务 QPS/RT/错误率
Step 5: 2倍速回放 → 找到系统容量上限
Step 6: 定位瓶颈 → SkyWalking 链路分析 → Arthas 方法级分析
Step 7: 优化 → 重新压测 → 对比基线
Step 8: 输出压测报告
```
