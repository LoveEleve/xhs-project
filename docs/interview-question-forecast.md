## B. 交易链路（简历最重的部分，他会钻最深）

### B1 库存（H-C/D）

| # | 预测问题 | 难度 | 一句话答案 | 陷阱 |
|---|---|---|---|---|
| B1.1 | 分桶预扣怎么保证不超卖？ | 🟢 | 单 Lua 原子：查总量→路由桶扣减→不足扫其它桶；MySQL 只做账本+对账 | 他会追"桶之间并发呢"——每桶独立 DECR，total 同脚本扣 |
| B1.2 | 为什么要分桶？桶数怎么定？热点 SKU 呢？ | 🟡 | 单 key 是热点→拆分桶；默认 N 桶（可配）；滑动窗口 10s/100 次触发热点→2→8 桶自动扩容 | 他会问"扩容时正在扣减怎么办"——reinit 锁+暂停标记+延迟消费 |
| B1.3 | 预扣超时怎么回收？支付卡在超时边缘呢？ | 🔴 | ZSet 过期索引 O(logN)+**只回退真正到期**（记录物理 TTL 加 10 分钟缓冲，杜绝窗口内支付找不到预扣） | 这是他最可能钻的：原实现提前 60s 释放→支付确认找不到记录。答"我们踩过并修了" |
| B1.4 | TCC 接进订单链路了吗？ | 🔴 | **没有**：接口+11 场景验证完成，订单链路走事务消息预扣；若接入需定义 Confirm/Cancel 的幂等与空回滚 | ❌ 别含糊说"用了 TCC"；主动交代边界+接入前提 |
| B1.5 | 库存对账以谁为准？ | 🟡 | available 以 Redis 分桶为准；locked 以在途预扣记录为准（幽灵锁修复）；MySQL 是账本 | 他会问"Redis 丢了怎么办"→从 MySQL 重建+对账收敛 |
| B1.6 | 预扣幂等怎么做的？ | 🟡 | MySQL INSERT IGNORE 占位（走主库）+ 成功后保留占位 7 天清理；Redis 记录丢失时防重复扣 | 追"占位表会涨吗"→7 天保留+日切排空（刚修） |

### B2 订单与事务消息（H-E/X/V）

| # | 预测问题 | 难度 | 一句话答案 | 陷阱 |
|---|---|---|---|---|
| B2.1 | 下单一致性怎么保证？ | 🟢 | RocketMQ 事务消息+本地消息表+Broker 回查；半消息→本地事务（订单+明细+本地消息同事务）→COMMIT | 他会问"回查查什么"→查本地消息表（与订单同事务，状态必然一致） |
| B2.2 | 为什么不用 Seata / 不用 TCC？ | 🟡 | 事务消息解决"本地事务+消息投递"原子性（下单只需这一层）；Seata AT 需代理数据源、与分片叠加复杂；跨服务补偿已用对账兜 | 别否定 Seata；讲"这个问题恰好是事务消息的标准解" |
| B2.3 | 订单状态怎么防并发（取消 vs 支付）？ | 🟡 | 所有流转条件 UPDATE（WHERE status=前值）单一赢家；事件流先写（序号唯一键）再更新状态 | 追"两个请求同时改状态+写事件"→见 B2.4 |
| B2.4 | 事件序号冲突怎么办？ | 🔴 | INSERT IGNORE 返回 0 ⇒ 对方也在追加 ⇒ 本事务状态更新必失败 ⇒ **整体回滚让调用方重试**（重试幂等跳过） | ❌ 别说"加锁重算 seq"——那会有"事件锁↔订单锁"反向锁序死锁（我们排除过） |
| B2.5 | 订单号怎么生成？ | 🔴 | 两个号：对外 orderNo（ORD+时间戳+用户尾号+Redis 日序列，唯一键兜底）+ 对内 Snowflake 主键 | 他会举反例（时钟回拨/降级随机/枚举）——见 H-V 全表 |
| B2.6 | 分片键为什么 user_id？按订单号查呢？ | 🟡 | 查询模型以用户维度为主；非分片键走映射表（order_no→user_id）定位分片，写失败由 5 分钟补录兜 | 追"映射表也是单点吗"→独立数据源+唯一键+补录幂等 |
| B2.7 | 分片倾斜遇到吗？怎么发现？ | 🔴 | 遇到过：Snowflake 低位恒定→131 单 75% 落 2/16 片；改哈希取模+迁 682 行→16/16 | 这是"把发号器特性联系到存储层"的 P7-P8 鉴别题 |

| F2 | "渠道都是 Mock，这套支付逻辑有意义吗？" | 状态机/幂等/迟到处理/对账全部是真实设计；Mock 只替换渠道适配层；接入清单三条已明确（验签 SPI/前置查询/公网配套） |
| F3 | "ES 单节点还敢叫搜索架构？" | 承认单节点（replicas=0）；双通道+版本号+tombstone+重建对账与节点数无关；扩副本/调 refresh 是部署动作 |
| F4 | "suggest/GEO 这些是不是没做完？" | suggest 只随全量重建刷新（无增量）；GEO 无数据源策略恒空——**在文档里都标了设计项**，不是假装有 |
| F5 | "事件表只增不删，跑三年怎么办？" | 归档（冷表+路由）在接入清单；本地消息/购物车流水/行为表已做保留（7/30/90 天）；订单事件是真相源不删只归档 |
| F6 | "1000 条上限的统计，超过就错了？" | 上限保护+说明口径；正确做法是按用户维度聚合计数（有 counter 域），当时按笔记逐条拉是简化 |
| F7 | "手续费单档，多费率怎么办？" | 费率表（渠道×品类+生效时间版本）是接入项；现在单档是为了把对账差异逻辑先跑通 |
| F8 | "订单号能猜，安全吗？" | 单号不是凭证：按单号查询强制 userId 归属校验（非本人 403）+下单限流；seq%10000 回绕有唯一键兜底 |
| F9 | "限流是单机的，集群下不就超了？" | 承认单机+余量 40%；集群精确限流要 Token Server，评估规模不值得——这是**容量决策**不是遗漏 |
| F10 | "服务直接信 X-User-Id，内网被入侵呢？" | 信任边界：只信网关注入（set 覆盖伪造头）+内部调用令牌；直连服务不在公网暴露；更进一步是 mTLS/服务网格 |
