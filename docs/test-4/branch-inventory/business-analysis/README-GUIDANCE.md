# business-analysis 指导文档

> 来源：基于 `docs/test-2/` 与 `docs/test-3/` 的现有方向、方法论与踩坑记录整理。
> 原则：**只做提炼，不覆盖旧文档，不改写旧结论。**

## 1. 本目录接下来要做什么

`business-analysis/` 只负责当前分支下各微服务的业务梳理，不直接承担部署盘点、运行记录或旧测试归档。

特别说明：
- `my-xhs-gateway` 虽然不是典型业务模块，但它是外部入口、鉴权入口、路由入口，必须作为“入口/边界模块”单独分析
- 除 `gateway` 外，其余目录按业务微服务模块展开

当前目录的目标是：
- 按微服务模块梳理业务职责
- 梳理业务链路、上下游依赖、状态流转
- 记录跨模块交互（Feign / MQ / Redis / ES / 定时任务）
- 为后续重测提供业务上下文

## 3. 事实优先级与分析顺序

### 3.1 事实优先级
后续写分析时，事实来源优先级固定为：
1. 当前代码与当前工作区实际内容
2. 当前运行结果（服务启动状态、接口行为、日志、数据）
3. `docs/test-3/` 中的方法论、cases、pitfalls
4. `docs/test-2/` 中的业务理解与历史分析

规则：
- `test-2` / `test-3` 只能辅助理解，不能覆盖当前代码事实
- 旧文档与当前代码冲突时，以当前代码和当前运行结果为准
- 当前分支中的工作区改动必须单独标出，不能混成“历史既有设计”

### 3.2 分析顺序
先按业务正确性，再逐层展开，不能反过来。

### 3.3 分析过程中允许优化代码
分析不是只做静态记录。

规则：
- 如果在分析过程中确认当前代码存在明显问题，可以提出并修复
- 不要默认“现有代码就是对的”
- 但修复前要先把问题、影响范围、修复理由记录清楚
- 业务分析文档要区分“当前事实”“发现的问题”“已修复的问题”

### Layer 1：业务逻辑正确性
每个模块先回答：
- 这个模块是做什么的
- 它暴露哪些核心业务能力
- 它的主要业务链路是什么
- 它依赖哪些上游/下游服务
- 它有哪些关键状态流转与边界场景

### Layer 2：数据正确性
再看：
- Redis 用了哪些 key
- MySQL 落哪些表
- MQ 发哪些 topic / 消费哪些消息
- ES 是否参与索引同步

### Layer 3：生产级问题
再补：
- 微服务调用问题（Feign / 熔断 / 降级 / 超时）
- 分布式问题（幂等 / TCC / 本地消息表 / 分片 / 一致性）
- 性能问题（缓存 / 限流 / RT / 线程池）
- 安全问题（JWT / X-Admin-Call / X-Internal-Call）

### Layer 4：可观测性
最后才补：
- Trace
- Metrics
- Log
- 调度任务与补偿链路

## 4. 当前业务分组建议（沿用 test-3）

后续分析建议先按业务组，再落回单服务：

- G1：认证 / 用户
- G2：内容 / 社交
- G3：商品 / 购物车
- G4：优惠券
- G5：订单 / 支付 / 库存
- G6：搜索 / 首页 / 推荐
- G7：通知 / IM / 计数

对应到当前目录下的服务时，不要只写“单服务孤立分析”，要写清楚它在业务组中的位置。

## 5. 写业务分析时必须包含的内容

每个微服务后续文档至少应包含：
- 模块职责
- 核心接口/能力
- 核心业务链路
- 上下游依赖
- 状态机/关键对象
- 缓存/数据库/MQ/ES 参与点
- 定时任务/补偿任务
- 当前分支下的关键改动点
- 后续测试重点

建议统一结构：
1. 当前模块定位
2. 当前代码事实
3. 历史参考与差异点
4. 当前分支改动点
5. 业务链路与上下游
6. 数据与中间件参与点
7. 风险点/待确认点
8. 后续测试重点

建议统一文件命名：
- `01-module-overview.md`
- `02-business-flow.md`
- `03-data-and-middleware.md`
- `04-branch-changes.md`
- `05-test-focus.md`

`gateway` 例外说明：
- `gateway` 不应机械套用普通业务服务模板
- `gateway` 更适合优先写：入口定位、鉴权链路、路由分发、下游边界、限流与安全边界
- 如果从 `gateway` 开始，可以先写一篇入口边界样板，再决定是否拆成 5 个文件

如果某个模块暂时不需要拆成 5 个文件，也至少要在首篇文档里按以上 8 个章节顺序写，避免后续失控。

## 5.1 每轮分析后的覆盖对账

每个模块分析完成后，必须做一次“文件覆盖对账”：
- 用 `project-directories/` 中该模块的目录盘点作为基准
- 列出本轮实际阅读/引用过的文件清单
- 对比哪些文件已覆盖、哪些未覆盖、哪些明确暂不分析
- 如果有未覆盖文件，必须说明原因，不能默认忽略

目标：
- 避免凭印象分析
- 避免遗漏关键配置、文档、脚本或资源文件
- 保证后续回看时能证明“本轮分析覆盖到了哪些文件”
