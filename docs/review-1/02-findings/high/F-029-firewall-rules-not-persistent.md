# F-029 防火墙脚本规则默认不持久化，重启后中间件保护可能消失

## 严重度

High

## 涉及文件

- `setup-firewall.sh:21-40`
- `config/deploy-cloud/DEPLOY-README.md:77-84`

## 现象

`setup-firewall.sh` 直接写入 iptables，但脚本不会持久化规则。它在结尾仅打印提示，让运维人员自行安装持久化工具。

同时部署文档把 iptables 标记为“可选纵深”，而云主机公网暴露面被明确描述为更大。

## 证据

1. 脚本逐端口写 INPUT ACCEPT/DROP：`setup-firewall.sh:21-33`。
2. 脚本明确提示“规则仅本次生效（重启丢失）”：`setup-firewall.sh:38-40`。
3. 部署文档称安全组和 iptables 是两层防护，但 iptables 被标为可选：`DEPLOY-README.md:77-84`。
4. 同一文档同时要求 Nacos/Redis/MySQL 不允许公网直连，说明这些 DROP 规则属于安全底线而非可选功能。

## 触发条件

1. 主机重启、iptables 服务重载或容器/宿主机网络变更。
2. 运维人员未执行持久化命令，或只执行了应用部署而遗漏防火墙步骤。
3. 云安全组未同步配置或配置被修改。

## 影响

1. Nacos、Redis、MySQL、ES、RocketMQ 等端口可能在重启后重新暴露。
2. F-001/F-002/F-017/F-018/F-026 的实际攻击面会扩大。
3. 应用看起来正常运行，但安全边界已经与部署前不同，属于典型配置漂移。

## 修复建议

1. 将安全组/防火墙规则纳入部署自动化和启动前置检查，不能依赖人工提示。
2. 脚本执行后自动验证规则持久化状态，并在启动时检查关键端口来源限制。
3. 把“中间件端口仅允许指定来源”设为部署阻断条件，而不是可选项。
4. 通过 IaC 固化安全组和 iptables/nftables，避免手工配置漂移。

## 是否需要补充验证

需要在重启后检查 `iptables-save` 与实际监听端口，并从非允许来源验证 Nacos/Redis/MySQL/ES 是否不可达。
