# 非安全 / 非运维问题最终分层（深度复核版）

> 目标：从 F-001 ~ F-043 中，只保留真正属于业务逻辑 / 工程 / 分布式 / 微服务主线的问题。
> 本文不讨论凭据、TLS、host network、Nacos 鉴权、脚本泄漏等安全/运维项。

## 一、应保留为“真 bug”的主线问题

### P0 级：确定性会造成资损 / 状态不收敛

#### 1. F-007 多 SKU 退款只回补一个 SKU
- 结论：**确定是真 bug**
- 原因：订单侧按 SKU 循环调用 `refundRestore()`，库存侧却用 `inventory:refund:{orderId}` 做幂等键，第二个 SKU 起直接被跳过。
- 特征：代码级必现，不依赖概率，不依赖外部故障。
- 为什么之前没测出：退款用例大概率只覆盖了单 SKU 订单。

#### 2. F-010 退款成功回调无条件返回 ok
- 结论：**确定是真 bug**
- 原因：`notifyRefundSuccess()` 无论 `onRefundSuccess()` 是否真正完成都 `R.ok()`；补偿任务会误判为已成功通知。
- 特征：不是单纯降级，而是把失败包装成成功。
- 为什么之前没测出：需要构造 refund 回调到达时订单侧异常/映射缺失/状态不符的场景，普通 happy-path 回归不会触发。

#### 3. F-006 补偿消息在路由缺失时被正常 ACK
- 结论：**确定是真 bug**
- 原因：`OrderCompensationConsumer` 查不到 mapping 时直接 `return`，RocketMQ 不会重试。
- 特征：这是补偿链断点，不是设计取舍。
- 为什么之前没测出：要构造 mapping 缺失或延迟写入的异常路径，常规回归不打这类故障注入。

#### 4. F-016 领券消费者不检查库存扣减结果
- 结论：**确定是真 bug**
- 原因：先插 `t_user_coupon`，再 `decrementRemainCount()`，但忽略影响行数；库存条件不满足时用户券也会提交。
- 特征：业务语义破坏，DB 会出现“有券但库存未扣”。
- 为什么之前没测出：需要人为制造 Redis/MySQL 库存漂移或重放消息，不是正常领券场景。

#### 5. F-036 订单映射补录窗口只有 1 小时
- 结论：**确定是真 bug**
- 原因：mapping 写入失败只记日志，补录任务只看最近 1 小时，持续故障后老订单永久遗漏。
- 特征：分库分表下的补偿窗口设计错误。
- 为什么之前没测出：需要 mapping 存储层故障持续超过 1 小时，普通测试窗口太短。

## 二、应保留为“高价值主线问题”的项

### A. 微服务边界 / 语义错误

#### 6. F-013 AI 会话归属与取消权限缺失
- 结论：**确定是真 bug**
- 原因：会话列表/详情与 run cancel 缺少归属/角色校验。
- 说明：虽然由 AI 团队负责代码，但问题本身是真实的业务边界错误。
- 为什么之前没测出：之前测试范围不包含 `/ai-api/**` 生产路径和多角色语义。

#### 7. F-043 like/favorite 在目标校验异常时放行
- 结论：**确定是真 bug**
- 原因：content 校验异常时 `return true`，会对不存在/不可见内容继续写 Redis/MQ。
- 特征：不是可用性降级，而是把依赖失败包装成业务成功。
- 为什么之前没测出：需要在 content 不可用或超时时发起互动请求，普通接口回归不做依赖熔断测试。

#### 8. F-039 Home BFF 把下游失败伪装成业务空/不存在
- 结论：**确定是真 bug**
- 原因：BFF 将 user/product/cart 下游失败折叠成 404 或空购物车，而不是明确降级状态。
- 特征：200/404 语义错误，会误导前端和监控。
- 为什么之前没测出：回归更多测“结构正确、响应码合理”，没测“依赖失败时错误语义”。

### B. 搜索 / 推荐产物错误

#### 9. F-023 商品索引增量补偿会重建不完整文档
- 结论：**确定是真 bug**
- 原因：补偿分支只查 `t_spu`，把价格/品牌/分类名写成占位值。
- 为什么之前没测出：需要先让商品索引同步失败，再跑增量补偿，普通搜索回归走不到。

#### 10. F-042 商品索引消费者在 Feign 失败时仍写入不完整文档
- 结论：**确定是真 bug**
- 原因：product Feign 补全字段失败时不重试，直接把半成品写入 ES。
- 为什么之前没测出：需要在 product 服务不可用时触发 Canal 商品增量消息。

#### 11. F-024 全量笔记索引重建会把计数清零
- 结论：**确定是真 bug**
- 原因：`buildNoteDocument()` 直接把 like/collect/comment 写 0。
- 为什么之前没测出：回归通常不主动触发全量重建，也不在重建后校验 ES 计数字段。

#### 12. F-021 推荐行为消费者吞掉写库异常
- 结论：**偏真 bug，保留**
- 原因：行为写失败直接吞掉，推荐样本静默丢失。
- 说明：这是推荐质量问题，不是资损，但会长期污染离线结果。
- 为什么之前没测出：要模拟 t_user_behavior 写入失败。

#### 13. F-041 推荐任务内部失败仍向 XXL-Job 报成功
- 结论：**偏真 bug，保留**
- 原因：离线任务内层 catch 吃掉异常，外层仍 `handleSuccess()`。
- 说明：这是“平台假成功”，会让推荐结果长期停留旧版本。
- 为什么之前没测出：回归没看 XXL-Job 执行结果与产物是否一致。

### C. 分布式补偿粒度问题

#### 14. F-008 退券 afterCommit Redis 失败无补偿
- 结论：**偏真 bug，保留**
- 原因：MySQL 成功后 Redis 失败无 durable retry。
- 说明：这是典型“主流程成功、侧写失败、无补偿”的分布式问题。
- 为什么之前没测出：需要在事务提交后刻意打 Redis 故障。

#### 15. F-037 库存补偿固定回 bucket0
- 结论：**偏真 bug，保留**
- 原因：补偿不恢复原 bucket，分桶语义错误。
- 说明：不一定立刻表现为超卖，但会积累分桶失真。
- 为什么之前没测出：需要让预扣落到非 0 bucket，再制造释放失败走补偿。

#### 16. F-038 优惠券对账只看启用且未过期模板
- 结论：**偏真 bug，保留**
- 原因：历史模板漂移不会被修复，重上线后带病恢复。
- 为什么之前没测出：测试通常只盯活跃模板。

## 三、建议降级成“二线问题/实现缺陷”的项

#### 17. F-004 库存确认失败后 locked_stock 虚高残留
- 结论：**降级保留**
- 原因：对账会修 `available_stock`，不会修 `locked_stock`，影响从“资损”降为“统计/管理不准确”。
- 仍保留原因：这是补偿模型不完整的信号。

#### 18. F-005 库存 Outbox 唯一键不含 action
- 结论：**降级保留**
- 原因：happy path 顺序执行基本可工作，但异常时序下 action 语义不清。
- 仍保留原因：是库存补偿/Outbox 粒度问题的根因之一。

#### 19. F-012 NoteIndexSyncConsumer 读 counter 滞后源
- 结论：**降级保留**
- 原因：counter 有对账收敛，影响是短暂计数回退，不是永久错误。

#### 20. F-025 RecommendComputeJob 读 t_counter 做质量分
- 结论：**降级保留**
- 原因：本质与 F-012 同类，是“滞后衍生源进入离线产物”。

#### 21. F-015 坏事务消息被正常确认
- 结论：**降级保留**
- 原因：需要 malformed message 才触发，正常生产链路不常见。

#### 22. F-040 FeedCleanup 节流计数器重置
- 结论：**降级保留**
- 原因：是真缺陷，但影响偏性能/运维噪声，不是主业务错误。

## 五、为什么这么多轮回归没测出来

### 1. 回归模型偏 happy-path，同步接口导向
- 测的是“接口能不能通、状态码对不对、主字段对不对”
- 没测：下游超时、MQ 异常、mapping 缺失、Redis 故障、补偿窗口过期、定时任务运行后的产物

### 2. curl 脚本入口不真实
- 直连 `19001~19016` 业务端口
- 手工带 `X-User-Id`
- 绕过 gateway 的真实身份/限流/HMAC/路由语义
- 这会掩盖一类微服务边界问题，也测不到真实生产流量模型

### 3. 缺少“副作用断言”
- 很多问题不是接口返回错，而是：
  - Redis 写了但 DB 没写
  - DB 写了但 MQ 没补
  - ES 写了但字段是错的
  - 任务显示成功但产物没更新
- 之前的回归断言大多没覆盖这些副作用面

### 4. 用例覆盖单实体，没覆盖多实体/多步骤
- F-007：要测多 SKU 退款
- F-037：要测非 0 bucket 补偿
- F-036：要测长时间 mapping 故障
- F-023/F-042：要先造 consumer failure 再跑补偿/增量

### 5. 没有把调度任务当成主功能面来测
- `IndexRebuildJob`
- `RecommendComputeJob`
- `OrderMappingRepairJob`
- `CouponReconcileJob`
- `UnreadReconcileJob`
这些都不是“辅助脚本”，而是业务一致性链路的一部分。
