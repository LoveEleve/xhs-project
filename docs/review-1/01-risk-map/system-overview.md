# system-overview

## 1. 系统轮廓

`my-xhs` 是一个把社交内容、交易履约、搜索推荐、消息通知、AI 诊断台拼在一起的多模块微服务系统。

从顶层 `pom.xml` 看，核心模块可分成六个簇：

1. **入口与身份簇**：`my-xhs-gateway`、`my-xhs-user`、`my-xhs-common`
2. **内容与互动簇**：`my-xhs-content`、`my-xhs-counter`、`my-xhs-analytics`
3. **商品与交易簇**：`my-xhs-product`、`my-xhs-cart`、`my-xhs-order`、`my-xhs-payment`、`my-xhs-inventory`、`my-xhs-coupon`
4. **分发与触达簇**：`my-xhs-home`、`my-xhs-search`、`my-xhs-notification`、`my-xhs-im`
5. **AI 簇**：`my-xhs-ai-app`、`my-xhs-ai-tools`、`my-xhs-ai-mcp`、`my-xhs-ai`
6. **测试与运维簇**：`my-xhs-test`、`my-xhs-benchmark`、`config`、`scripts`、`sql`、`deploy`、`k8s`

这不是“很多独立服务”，而是**多个共享状态来源、共享中间件、共享身份模型的耦合系统**。

## 2. 高层调用视角

### 2.1 入口链

典型外部流量先经过 `my-xhs-gateway`，再进入用户、内容、交易、AI 等服务。

这里最关键的不是路由本身，而是网关同时承担：

1. JWT 鉴权
2. HMAC 校验/白名单
3. 用户身份 header 注入
4. 限流
5. 某些内部调用的信任边界建立

这意味着 **gateway 不是纯转发器，而是整个系统的身份根节点**。

### 2.2 内容链

内容发布/删除/互动通常不是同步闭环，而是：

1. content 写主数据
2. counter / analytics 维护统计
3. search 同步索引
4. home 构建 feed
5. notification / im 触发触达

这是一个天然存在异步传播、重复消费、晚到消息和权威源漂移风险的链路。

### 2.3 交易链

交易链路至少包含：

1. 商品与 SKU 读取
2. 购物车约束
3. 库存预扣/释放/确认
4. 订单状态推进
5. 支付回调/退款回调
6. 优惠券占用/核销

这里最危险的是 **状态机 + 幂等 + 补偿** 三者是否真的闭环。

### 2.4 AI 链

AI 诊断台并不是独立系统，它依赖主系统提供：

1. gateway 身份与限流
2. 订单、内容、事件、统计数据
3. 会话归属与角色边界
4. MCP 工具调用能力

因此 AI 风险并不只在 AI 模块本身，而在**AI 如何跨越主系统边界读取和操作数据**。

## 3. 共享基础设施

从仓库结构和既有运行态可见，系统强依赖：

1. MySQL（含分库分表）
2. Redis
3. RocketMQ
4. Elasticsearch
5. Nacos / Sentinel
6. SkyWalking / 日志 / 指标

这意味着很多错误不会表现为“单服务 bug”，而是表现为：

- 某个服务看起来成功，但下游未收敛
- 数据库、缓存、ES 三者相互打架
- 重试成功掩盖了原始状态机漏洞
- 脚本把端口拉起了，但功能路径仍然失败

## 4. 权威状态的初步判断

首版 review 先假设以下状态归属，后续逐项验证：

1. **身份**：`user + gateway + common` 共同定义，真正外部信任入口在 gateway
2. **订单/支付/库存**：各自主库是权威源，但状态推进依赖消息与回调
3. **内容主数据**：content 为主
4. **统计/聚合**：counter 与 analytics 可能分工不一致，需重点审查
5. **搜索结果**：ES 不是权威，只是投影
6. **AI 诊断结果**：本质是多服务数据的二次解释，不是基础业务权威源

## 5. 首版系统结论

第一轮 review 不应该平均用力，而应优先盯以下四个系统面：

1. **身份边界是否完整**：因为它影响所有服务
2. **交易状态是否收敛**：因为它直接对应资金与库存风险
3. **异步传播是否可靠**：因为内容、搜索、通知、统计都依赖它
4. **运维脚本是否可信**：因为当前系统明显依赖脚本和运行态约定
