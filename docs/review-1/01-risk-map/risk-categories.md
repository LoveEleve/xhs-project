# risk-categories

## 1. 风险分类总表

| 类别 | 优先级 | 涉及服务 | 主要风险 | 最坏影响 |
|---|---|---|---|---|
| 身份与权限边界 | P0 | gateway、user、common、ai-app、各 internal/admin 入口 | header 伪造、权限绕过、token 撤销不完全、角色校验只做半截 | 越权访问、敏感操作被匿名或低权限触发 |
| 交易一致性 | P0 | order、payment、inventory、cart、coupon、product | 状态机跳变、回调重放、库存悬挂、幂等缺失、分片错路由 | 资金错误、超卖、订单状态错误、无法对账 |
| 异步消息与收敛 | P0 | order、content、search、home、notification、analytics、counter | outbox 不闭环、重复消费、顺序假设错误、补偿不可靠 | 状态长期不一致、消息丢失或重复副作用 |
| 内容传播与搜索投影 | P1 | content、home、search、counter、analytics | 删除回写、索引晚到、聚合读错源、分页/推荐错乱 | 用户看到脏数据、排序错误、统计失真 |
| AI 接入边界 | P1 | ai-app、ai-tools、ai-mcp、gateway、frontend | 身份透传不完整、SSE/限流不闭环、MCP 暴露过宽、工具高成本调用 | 会话串号、越权诊断、资源滥用、外部依赖拖垮入口 |
| 运维与配置漂移 | P1 | scripts、config、sql、deploy、k8s、全部服务 | 启停误判、端口假阳性、环境变量漂移、schema 偏差、密钥散落 | 线上状态与仓库认知不一致、错误修复路径 |
| 可观测性缺口 | P2 | 全部服务 | 成功/失败信号不可靠、关键链路无审计、补偿无指标 | 问题长期隐蔽、误判系统健康 |
| 结构复杂度与维护性 | P3 | 全仓 | 职责交叉、约定分散、重复实现、边界模糊 | 修改成本高、易引入回归 |

## 2. 重点解释

### 2.1 为什么“身份与权限边界”排第一

这个系统把大量安全语义放在 gateway：JWT、HMAC、header 注入、白名单、限流都在这里。

只要这里有一个 trust boundary 漏洞，后面所有服务都可能带着“伪造但看似可信”的 header 继续执行。

### 2.2 为什么“异步消息与收敛”是 P0

内容分发、订单补偿、索引同步、通知触达，都依赖异步链路。

单个 consumer 看起来没问题，不代表整体状态会收敛。真正的 P0 风险来自：

1. 业务提交了但消息没出
2. 消息到了但状态没收敛
3. 重试成功掩盖了中间状态漏洞
4. 顺序消费假设在多个主题/多个 group 上失效

### 2.3 为什么“AI 接入边界”不是独立风险岛

AI 模块本身可能代码不大，但它跨读订单、内容、统计、会话等多个域。

所以 AI 风险实质是：

- 它是不是站在正确的身份上下文里
- 它是不是能看到不该看的数据
- 它是不是把贵的、慢的、不稳定的调用挂在了公网入口后面

### 2.4 为什么“运维与配置漂移”放到 P1

这个仓库对脚本与运行态依赖很强。只看代码会高估系统可靠性。

首轮 review 已经可以预期要验证：

1. 重启脚本是否真的只拉起了目标服务
2. 健康检查是不是只看端口，不看功能
3. 本地配置、Nacos、环境变量是否互相打架
4. 仓库里的 SQL/DDL 与实际库结构是否漂移

## 3. 风险传播关系

### 身份问题会传播到

- AI 角色越权
- internal/admin 接口绕过
- 删除/封禁后旧 token 继续可用
- 跨服务 header 信任错误

### 交易问题会传播到

- 对账失败
- 搜索/首页看到过期交易状态
- 优惠券与库存状态不同步
- 补偿任务不断修但永远修不平

### 异步问题会传播到

- ES 索引脏数据
- 首页 feed 回写脏内容
- 通知重复或漏发
- 统计结果读旧值

## 4. 本轮建议的审查顺序

1. 身份与权限边界
2. 交易一致性
3. 异步消息与收敛
4. 内容传播与搜索投影
5. AI 接入边界
6. 运维与配置漂移
7. 可观测性缺口
8. 结构复杂度与维护性
