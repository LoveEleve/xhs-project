# review-1 总体规划

## 1. 目标

本轮 review 不是做代码导览，也不是做零散找茬，而是围绕 `my-xhs` 的高风险链路做一轮系统级深度审查。

目标只有三个：

1. 找出会导致错误结果、越权、资金/库存异常、消息错乱、数据长期不一致的问题。
2. 识别系统级设计弱点，而不只盯单个函数实现。
3. 形成可持续复用的 review 工作台，让后续轮次可以直接沿用。

## 2. 范围

本轮覆盖以下九个工作区：

1. `01-risk-map`：全局风险地图
2. `02-findings`：审查结论与问题清单
3. `03-open-questions`：待确认问题
4. `04-auth-and-identity`：鉴权与身份链路
5. `05-transaction-consistency`：交易一致性链路
6. `06-content-and-distribution`：内容分发与检索链路
7. `07-async-and-mq`：异步消息与收敛机制
8. `08-ai-integration`：AI 接入与边界
9. `09-infra-and-ops`：配置、脚本、部署与运行态

## 3. 不做什么

本轮不做以下事情：

1. 不做逐文件平铺式浏览。
2. 不以代码风格、命名喜好、注释多少作为主结论。
3. 不先跑大规模测试再找问题，先从架构与关键链路切入。
4. 不把无法证实的怀疑直接写进 findings。
5. 不在 review 文档里混入修复实现细节，修复另开记录。

## 4. 审查分层

采用三层审查法：

### L0：系统层

看服务边界、调用路径、共享约束、状态来源、最终一致性策略。

产出：`01-risk-map`

### L1：专题层

围绕高风险专题审查一组相关服务，而不是单个模块。

产出：`04` 到 `09`

### L2：证据层

对可疑点下钻到代码、配置、脚本、SQL、消息消费者、定时任务、运行时行为。

产出：确认后的问题进入 `02-findings`；无法闭环的问题进入 `03-open-questions`。

## 5. 优先级模型

本轮 review 以风险而不是代码量排序。

### P0

会造成越权、资金损失、库存错误、订单状态错误、消息丢失、不可恢复数据损坏的问题。

### P1

会造成长时间数据不一致、ES/缓存明显脏读、重要审计链缺失、AI 网关身份链错误的问题。

### P2

会造成局部错误、回退困难、可观测性缺口、脚本运维风险的问题。

### P3

可读性、结构味道、轻微重复、潜在但未证实问题。

## 6. 目录职责

### `01-risk-map`

只记录系统级风险图谱：风险类别、涉及服务、关键入口、状态归属、最坏影响。

### `02-findings`

只记录已经确认的问题。这里的内容默认面向最终输出。

建议按严重度拆分子文件或按编号沉淀。

### `03-open-questions`

记录无法仅靠代码确定的问题，如业务预期、补偿语义、边界责任归属、第三方依赖假设。

### `04-auth-and-identity`

聚焦 `gateway/user/common` 以及所有内部调用里的身份透传。

### `05-transaction-consistency`

聚焦 `order/payment/inventory/cart/coupon` 的状态收敛与幂等。

### `06-content-and-distribution`

聚焦 `content/home/search/counter/analytics` 的传播与读写一致性。

### `07-async-and-mq`

横向检查 MQ、outbox、消费者、重试、顺序性、补偿与死信。

### `08-ai-integration`

聚焦 `ai-app/ai-tools/ai-mcp/frontend/gateway` 的接入边界。

### `09-infra-and-ops`

聚焦脚本、部署、配置、环境变量、初始化 SQL、运行态偏差。

## 7. 执行顺序

推荐固定顺序：

1. `01-risk-map`
2. `04-auth-and-identity`
3. `05-transaction-consistency`
4. `07-async-and-mq`
5. `06-content-and-distribution`
6. `08-ai-integration`
7. `09-infra-and-ops`
8. `02-findings`
9. `03-open-questions`

说明：

- `02-findings` 不是最后才写，而是确认后随时沉淀。
- `03-open-questions` 用来承接所有无法立刻定性的点。
- `01-risk-map` 需要先做，否则后续容易陷入局部细节。

## 8. Findings 模板

每条 findings 固定包含：

1. 标题
2. 严重度
3. 涉及服务/文件
4. 现象
5. 触发条件
6. 证据
7. 实际影响
8. 修复建议
9. 残余风险
10. 是否需要补充验证

## 9. Open Questions 模板

每条 open question 固定包含：

1. 问题描述
2. 为什么现有代码无法定论
3. 需要谁确认
4. 若确认 A 的影响
5. 若确认 B 的影响

## 10. 本轮重点检查清单

### 鉴权与身份

- JWT 与 HMAC 的职责边界是否清晰
- `X-User-*` 头是否可伪造
- 内部接口是否存在绕过主鉴权链的入口
- token 撤销是否真正传导到所有关键入口
- 角色与权限是否只在网关校验、还是服务内也兜底

### 交易一致性

- 订单、支付、库存状态机是否存在跳变或不收敛
- 幂等 key 是否覆盖重试、回调重放、消息重复
- 分库分表下是否存在路由错位或跨库读写隐患
- 补偿与回滚是否有双写/漏写窗口

### 内容分发

- 内容删除、点赞、关注、推荐是否存在异步传播脏读
- ES、Redis、数据库三者谁是权威源是否明确
- 聚合统计是否读了异步中的非权威状态

### 异步消息

- outbox 与本地事务是否真正绑定
- 消费失败、重试、顺序消费是否会导致状态倒退
- 是否存在“消息成功但状态未收敛”或相反情况

### AI 接入

- AI 请求身份是否从网关可信注入
- SSE、限流、超时、角色校验是否闭环
- MCP 与工具权限是否最小化
- prompt/tool 调用是否存在越权或高成本路径

### 运维与脚本

- 重启脚本是否会误判成功
- 是否存在僵尸进程、端口占用误判、健康检查假阳性
- 环境变量/SQL/配置文件与运行态是否偏离
- 密钥、只读账号、初始化脚本是否有漂移

## 11. 输出纪律

1. 结论优先，描述次之。
2. 所有结论必须能落到代码、配置、日志、脚本或数据库证据。
3. 不能证实的内容不写成问题。
4. 发现问题后先记录风险，不急着给修复实现。
5. 目录内文档尽量短而硬，避免写成长篇散文。

## 12. 第一阶段里程碑

第一阶段不是出最终结论，而是完成三件事：

1. 建好 `01-risk-map` 的初版风险图。
2. 为 `04` 到 `09` 各自列出检查面和预期证据。
3. 建立 `02-findings` 与 `03-open-questions` 的统一模板。

完成这三件事后，再进入正式深审。
