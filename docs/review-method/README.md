# my-xhs 复审方法论

> 版本：2026-08-06 | 目的：防止任何 AI/人工审查时遗漏系统性问题
> 使用方法：复审任何模块前，先读本文件确定该模块需要查哪些维度，然后按维度文档逐项执行
> 编写状态：全 25 篇已全部完成（2026-08-06）

---

## 一、为什么需要这套方法论

2026-08-05~06 的 02-07 六模块两轮 fresh-eyes 复审证明：**没有强制 SOP 的审查必然遗漏**。

| 轮次 | 声称结论 | 实际问题 |
|------|---------|---------|
| 02-04 人工审查 | "FINAL/生产级" | 后续 Agent 全量扫描新发现 11🔴+30🟡（跨模块 key 不一致/丢失更新/级联缺失/测试不可编译等） |
| 02-04 Agent 修复后 | "49/49 全部修复" | 3 假修复（FavoriteServiceTest 编译失败/ZINTER 仅改注释/版本检查 TOCTOU）+ 1 额外测试编译失败（NoteServiceTest） |
| 05-07 之前审查 | "生产级就绪" | 07-inventory 实测缺 2 张表/confirm 零调用方/Canal 回声自残/TCC fence 装饰性 |

**遗漏的根因不是能力问题，是流程问题**：没有清单 → 凭记忆和经验审查 → 系统性盲区。

**何时使用本方法论**：
- 新模块开发完成、上线前的全量复审
- 任何"修复完成"声明后的回归验证（防假修复）
- 遗留系统接手时的摸底审查
- 重大架构变更（如 Sentinel→Cluster 迁移）前的现状评估

## 二、三层审查体系

### 第一层：通用维度（01-13）——每个模块必查

不区分模块类型，所有模块都必须过一遍：

| # | 维度 | 查什么 | 典型遗漏案例 |
|:--:|------|------|------|
| 01 | 输入校验 | DTO 完整性/边界值/IDOR/状态机 | replyToId 无 @Min(0)、pageNum 负数 500 |
| 02 | 并发与原子性 | TOCTOU/Lua/锁/MyBatis-Plus 陷阱 | update(null,wrapper) 不触发 auto-fill |
| 03 | 数据一致性 | 双写/乱序/对账/回填 | 回填用滞后 MySQL 快照 → 超卖 |
| 04 | MQ 可靠性 | 幂等/格式/顺序/死信/事务 | Consumer 失败不 removeMark → 吞消息 |
| 05 | 缓存架构 | 权威方向/降级链/Canal/穿透击穿 | L2 回声删 L1 权威数据 |
| 06 | 分布式事务 | TCC fence/Outbox/SAGA 补偿 | fence 结果不门禁业务 → 双冻结 |
| 07 | 安全与鉴权 | 凭据/内部认证/回调验签/限流 | 空 token `"".equals("")` 绕过 |
| 08 | 跨模块契约 | key 格式/事件 schema/ID 派生/级联传播 | pseudoOrderId ≠ order 侧真实 orderId |
| 09 | 测试质量 | 编译/运行/假测试/表结构实测 | "修复完成"但 mvn test 直接失败 |
| 10 | 运维就绪 | 优雅关闭/资源/Job/监控 | GracefulShutdownListener 未注册 @Component |
| 11 | 注册中心 | Nacos 健康检查/元数据/传播延迟 | （待 08-15 复审补充案例） |
| 12 | 微服务治理 | 服务边界/依赖图/循环依赖 | （待 08-15 复审补充案例） |
| 13 | 可扩展性 | 厂商锁定/抽象层/迁移成本 | **记录不强制修**（如 Feign→Dubbo 切换成本） |

### 第二层：领域维度（14-22）——按模块类型查

每个模块有自己领域特有的问题域，通用维度覆盖不到：

| # | 领域 | 覆盖模块 | 领域特有问题示例 |
|:--:|------|---------|------|
| 14 | 用户与认证 | 01-user | JWT 吊销/HMAC/禁用用户 Session 拦截 |
| 15 | 内容与 Feed | 02-content, 12-home | DFA 敏感词/Feed 推拉/断点续推/级联删除 |
| 16 | 社交与计数 | 03-analytics, 04-counter | 关注图一致性/双计数体系/Buffer 攒批/Set 幂等 |
| 17 | 商品与目录 | 05-product, 11-search | 布隆过滤器/分类树/ES 索引一致性 |
| 18 | 购物车与库存 | 06-cart, 07-inventory | 三结构合并/分桶/TCC/超卖防护 |
| 19 | 优惠券与营销 | 08-coupon | 防刷/双花/并发抢券/过期边界 |
| 20 | 订单与支付 | 09-payment, 10-order | 回调验签/分库分表/状态机/对账 |
| 21 | 通知与 IM | 13-notification, 14-im | SSE 连接/WebSocket 会话/消息送达 |
| 22 | 网关路由 | gateway | 路由断言/过滤器链顺序/HMAC 验签/请求转发完整性 |

### 第三层：元层级（23-25）——防自欺欺人

| # | 维度 | 查什么 |
|:--:|------|------|
| 23 | 假修复识别 | 注释冒充修复/非原子声称原子/同级字段缺项/合并只修一个实体/测试假 mock/缺表实测 |
| 24 | 验证协议 | 可执行的 mvn/grep/mysql 命令清单，不是抽象口号 |
| 25 | 已知陷阱库 | @RequiredArgsConstructor+final 陷阱/update(null,wrapper)/空 token 绕过 等 |

### 第四层：真实验证（26）——防假测试

| # | 维度 | 查什么 |
|:--:|------|------|
| 26 | 全链路真实验证 | 逐端点五层验证（HTTP/MySQL/Redis/MQ/Trace）——不只看 200 |

## 三、审查流程

```
0. 【必须】自证已读——审查开始前，输出"已读维度清单"表：
   列出该模块需要的**每一个维度独立行**（01/02/.../13/领域/23/24/25 逐行列出），
   每行标注 ✅。**禁止**合并写"01-13 通用维度 | ✅"——合并=未执行=审查无效。
   需输出 17~20 行（通用 13 + 领域 1+ + 元 3），每行一个维度编号+名称。
1. 确定模块 → 查本文件的模块→维度映射表
2. 人工逐文件审查：通用维度 01-13 + 该模块领域维度。
   【必须】发现按维度分组输出，每条标注来源维度编号（如 [04] / [06.1]）。
   【必须】每个已使用的维度在报告中以 `[XX] 维度名审查：发现 N 项` 为标题输出。
   缺失某维度的输出标题 = 该维度未被执行 = 审查无效。
3. 【必须】Agent 全量扫描——人工审查仅覆盖 25-50% 问题（02-07 两轮实测），
   必须派 Explore Agent 做系统化审计（DTO/SQL/Redis key/Consumer/Entity 全模式扫描）
4. 第三层：23 假修复识别（对之前声称已修复的项逐项独立验证）
5. 发现分级：🔴 数据丢失/安全/链路断裂 | 🟡 功能缺陷/性能/一致性风险 | 🟢 代码质量/注释/死代码
6. 【必须】修复方案先记录到文档并 REVIEW——方案分两类：
   "需调整"（技术方案有误，直接改）和"需决策"（涉及业务/架构取舍，用户拍板），
   决策全部明确后才动手
7. 修复：全部修复（无"已记录"终态），一次一个文件，每模块修完立即编译
8. 【必须】修复语义自查（两级验证）：(1)正确性——方案是否根治因而非症状、
   每个参数的语义在每个数据结构中是否正确（同名不同义是高频陷阱，如 member 在正向索引=userId、
   反向索引=bizId）；(2)生产级——边界/失败模式/规模是否覆盖
9. 验证：按 24 验证协议执行（mvn compile + test-compile + test + 实测）
10. 新发现的问题模式追加到 25 已知陷阱库
11. 【必须】审查结束后自审
12. 全链路真实验证——按 26 维度逐端点五层验证
    （HTTP/MySQL/Redis/MQ/Trace），不只看 200
```——以下三项任一为"否"→审查无效，返回重做：
    (a) 是否执行了步骤 3（Agent 全量扫描）？人工审查仅覆盖 25-50%——无 Agent=必有遗漏
    (b) 发现是否按维度编号分组输出？无编号=未按方法论执行
    (c) 是否真的读了维度文档（而非凭经验）？自证方法：第一条发现标注了来源维度编号
```
> 首轮审查 08-coupon 跳过步骤 3→仅发现 3 项→第二轮 Agent 全量扫描新发现 14 项——证明步骤 3 绝非可选。

## 五、使用原则

1. **不信任任何"已完成"声明**——所有声称已修复的项必须独立验证（编译+运行+实测）
2. **清单驱动**——按维度逐项过，不凭记忆和经验
3. **可执行命令**——每个检查项附 grep/mvn/mysql 命令，不是"注意 XX"这种抽象话
4. **案例驱动**——每条规则附实测案例，案例必须带**文件:行号锚点**（可 grep 验证），格式：现象/根因/修复/位置
5. **单一权威**——每条规则只在一个维度文档中完整定义，其他维度引用而非重复（如 MQ 乱序在 04 定义，03 引用），防止两处描述漂移
6. **持续追加**——每次复审发现新模式时，立即追加到对应维度和 25-known-traps
7. **可扩展性记录**——13 维度发现的问题记录即可，不强制立即修改（如 Feign→Dubbo 切换成本评估）
