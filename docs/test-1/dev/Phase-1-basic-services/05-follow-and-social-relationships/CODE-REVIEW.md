## 二、架构设计亮点

### 2.1 数据分层策略

```
┌─────────────────────────────────────────────────────────────┐
│                    数据分层架构                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Redis ZSet（权威数据源）                                    │
│  ├── social:following:{userId}  → 关注列表                  │
│  ├── social:follower:{userId}   → 粉丝列表                  │
│  └── counter:user_xxx:{userId}  → 计数（衍生数据）           │
│                                                             │
│  MySQL t_follow（持久化兜底）                                │
│  └── 同步落库，Redis 不可用时可从 MySQL 恢复                 │
│                                                             │
│  设计原则：                                                  │
│  ├── Redis 为权威数据源（高频读写，毫秒级响应）              │
│  ├── MySQL 为持久化兜底（Redis 宕机后可恢复）                │
│  └── 计数为衍生数据（可通过 ZCARD 对账修复）                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 为什么选 Redis ZSet 而不是 MySQL？

| 维度 | Redis ZSet（✅ 选定） | MySQL |
|------|---------------------|-------|
| 查询性能 | O(logN) 分页，毫秒级 | 需要 ORDER BY + LIMIT |
| 共同关注 | 内存交集，毫秒级 | 需要子查询或 JOIN |
| 关注判断 | ZSCORE O(1) | 需要 SELECT COUNT |
| 去重 | ZSet 天然去重 | 需要唯一索引 |
| 排序 | score=时间戳，天然排序 | 需要 ORDER BY |

## 三、🔥 深度技术分析：Lua 脚本的"原子性"边界

### 3.1 三层辨析

| 层次 | 是否保证 | 说明 |
|------|:--------:|------|
| **执行隔离性**（不被其他命令打断） | ✅ | Redis 单线程，Lua 执行期间不会穿插其他命令 |
| **失败回滚**（部分执行后回滚） | ❌ | 如果第 N 步失败，前 N-1 步不会回滚 |
| **持久化原子性**（写入 AOF/RDB） | ⚠️ | `appendfsync everysec` 下最多丢失 1 秒数据 |

### 3.2 与 MySQL 事务的本质区别

```
MySQL 事务：
  BEGIN → INSERT A → INSERT B → COMMIT
  如果 INSERT B 失败 → ROLLBACK → A 也撤销 ✅

Redis Lua 脚本：
  ZADD A → ZADD B → INCR C → INCR D
  如果 INCR D 失败（OOM）→ A/B/C 已执行，不会回滚 ❌
```

### 3.3 我们的防御策略

```lua
-- follow_and_count.lua 中的命令顺序是精心设计的：

-- 第 1 步：写入关注关系（核心数据，优先保证）
redis.call('ZADD', KEYS[1], ARGV[3], ARGV[1])  -- 关注列表
-- 第 2 步：写入粉丝关系（核心数据）
redis.call('ZADD', KEYS[2], ARGV[3], ARGV[2])  -- 粉丝列表
-- 第 3 步：更新关注数（衍生数据，可对账修复）
redis.call('INCR', KEYS[3])
-- 第 4 步：更新粉丝数（衍生数据，可对账修复）
redis.call('INCR', KEYS[4])
```

**设计原则**：
1. **核心数据优先**：关注关系（ZSet）是核心数据，优先写入
2. **衍生数据后置**：计数（INCR）是衍生数据，即使丢失也可修复
3. **对账修复兜底**：`repairUserCounters()` 以 ZCARD 为准覆盖 counter

### 3.4 风险场景分析

| 场景 | 概率 | 后果 | 防御 |
|------|:----:|------|------|
| Lua 执行到第 3 步时 Redis OOM | 极低 | 关注关系正确，计数少 1 | 对账修复 |
| Redis 宕机（AOF 丢失 1 秒） | 低 | 最近 1 秒的关注操作丢失 | MySQL 兜底 + 对账 |
| Redis 和 MySQL 不一致 | 中 | MySQL 落库失败 | Redis 为准，后续对账 |
| 并发关注同一用户 | 中 | ZSet 天然去重，不会重复 | Lua 脚本内 ZSCORE 检查 |

### 3.5 对账修复机制

```java
/**
 * 修复策略：以 ZSet 的 ZCARD 为准覆盖 counter 值
 * 触发时机：定时任务（每小时）/ 管理后台手动触发
 */
public String repairUserCounters(Long userId) {
    Long actualFollowing = stringRedisTemplate.opsForZSet().zCard(followingKey);
    Long actualFollower = stringRedisTemplate.opsForZSet().zCard(followerKey);
    
    // 如果 counter 与 ZCARD 不一致，以 ZCARD 为准覆盖
    if (!String.valueOf(actualFollowing).equals(oldFollowing)) {
        stringRedisTemplate.opsForValue().set(followingCountKey, String.valueOf(actualFollowing));
    }
}
```

### 3.6 面试标准回答

> **Q: Lua 脚本真的能保证原子性吗？**
>
> A: 要分两个层面看：
>
> 1. **执行隔离性**：能保证。Redis 单线程模型下，Lua 脚本执行期间不会被其他命令打断，这是我们用 Lua 的核心原因——4 个命令不会被穿插。
>
> 2. **事务回滚**：不能保证。如果脚本执行到一半 Redis OOM 或被 kill，已执行的命令不会回滚。这和 MySQL 事务有本质区别。
>
> 3. **我们的防御**：
>    - 数据分层：关注关系（ZSet）是核心数据优先写入，计数（INCR）是衍生数据
>    - 对账修复：定时任务用 `ZCARD` 校准 counter 值
>    - 最终一致：即使计数短暂不一致，也不影响核心功能（关注关系本身是正确的）
>
> 4. **为什么不用分布式事务？** 因为关注操作是高频场景（QPS 1000+），分布式事务的性能开销不可接受。用"最终一致性 + 对账修复"是更合理的工程权衡。

## 六、面试话术

### Q1: 关注系统怎么设计的？

> 1. **存储选型**：关注关系存在 Redis ZSet 中（score=关注时间戳），天然支持排序+分页+去重+O(1)判断。MySQL 作为异步落库的持久化兜底。
>
> 2. **原子操作**：关注/取关涉及 4 个 Redis 命令（2×ZADD + 2×INCR），用 Lua 脚本保证执行隔离性，不会被其他命令穿插。
>
> 3. **数据分层**：关注关系（ZSet）是核心数据，计数（counter）是衍生数据。即使计数不一致，也可通过 ZCARD 对账修复。
>
> 4. **共同关注**：分别 ZRANGE 取出两个用户的关注列表，在内存中求交集。限制最多取 5000 个防止 OOM。

### Q2: 为什么用 Lua 脚本而不是分布式锁？

> | 维度 | Lua 脚本（✅） | 分布式锁 | Pipeline |
> |------|---------------|---------|----------|
> | 原子性 | ✅ 单线程保证 | ✅ 锁保证 | ❌ 非原子 |
> | 性能 | 高（1 次网络往返） | 低（加锁+释放锁） | 高（批量发送） |
> | 复杂度 | 中（需写 Lua） | 中（锁管理） | 低 |
>
> 选择 Lua 的原因：关注操作是高频场景（QPS 1000+），分布式锁的加锁/释放锁开销不可接受。Lua 脚本在 Redis 单线程中执行，天然原子，且只需 1 次网络往返。

### Q3: Lua 脚本能保证原子性吗？有什么限制？

> （见上方第三节"深度技术分析"的完整回答）

### Q4: 共同关注怎么实现？为什么不用 SINTER？

> 1. 关注列表用 ZSet 存储（需要按时间排序），SINTER 只支持 Set
> 2. 所以先 ZRANGE 取出两个列表，再在内存中 `retainAll()` 求交集
> 3. 限制最多取前 5000 个，防止大 V 关注列表过大导致 OOM
> 4. 优化方向：如果关注列表很大，可以异步预计算共同关注并缓存

### Q5: Redis 和 MySQL 数据不一致怎么办？

> 1. **设计原则**：Redis 为权威数据源，MySQL 为持久化兜底
> 2. **写入策略**：Redis 成功即返回用户成功，MySQL 落库失败不影响用户体验
> 3. **修复机制**：
>    - 定时对账任务：扫描 Redis ZSet 与 MySQL t_follow 的差异
>    - 计数修复：ZCARD 为准覆盖 counter 值
>    - 全量修复：极端情况下从 MySQL 重建 Redis 数据
