# 分布式ID方案

> 所属维度：分布式方案 | 开发阶段：Phase-6 | 核心实现：雪花ID + 号段模式

---

## 🎯 一、为什么需要分布式ID

```
问题：分库分表后，各库自增ID独立
  库1: 1,2,3,4,5...
  库2: 1,2,3,4,5...  ← ID冲突！

需求：全局唯一 + 趋势递增(B+树友好) + 高性能
```

---

## ⚖️ 二、五方案对比

| 方案 | 趋势递增 | 性能 | 依赖 | 缺点 | my-xhs采用 |
|------|----------|------|------|------|-------------|
| UUID | ❌ | 高 | 无 | 无序，B+树性能差 | ❌ |
| DB自增 | ✅ | 低 | MySQL | 分库分表后冲突 | ❌ |
| DB号段模式 | ✅ | 高 | MySQL | 号段用完需要取新段 | ✅ 用户ID |
| 雪花ID | ✅ | 高 | 时钟 | 时钟回拨问题 | ✅ 订单ID |
| Redis自增 | ✅ | 高 | Redis | Redis不可用则不可用 | ✅ 流水号 |

## 🏗️ 三、雪花ID方案

### 3.1 结构

```
雪花ID结构(64bit)：
0 | 00000000000000000000000000000000000000000 | 00000 | 00000 | 000000000000
符号 | 41bit时间戳(可用69年)                  | 5bit数据中心 | 5bit机器ID | 12bit序列号
```

### 3.2 WorkerId 分配（Redis方案）

```
问题：多实例部署，WorkerId不能重复
解决：Redis INCR 分配WorkerId(0-31)，实例启动时申请，关闭时释放

流程：
1. 服务启动 → Redis INCR "snowflake:worker:counter" → 得到WorkerId
2. 服务运行中 → 使用该WorkerId生成雪花ID
3. 服务关闭 → 释放WorkerId(可选)
```

### 3.3 时钟回拨检测

```
检测逻辑：
- 当前时间 < 上次生成ID的时间 → 发生时钟回拨！

处理策略：
- 回拨 < 5ms → 等待回拨时间后继续
- 回拨 ≥ 5ms → 拒绝生成ID → 报错 + 告警
- 运维介入检查NTP配置

故障兜底：
- Redis不可用 → 使用本地缓存的WorkerId(启动时已分配)
- 时钟回拨告警 → 运维介入检查NTP配置
```

## 💻 四、号段模式方案（用户ID）

```
原理：
1. MySQL维护一张号段表：当前最大值 + 步长
2. 服务启动时一次取1000个ID的段(如 1001-2000)
3. 内存中分配，用完再取新段
4. 减少DB交互(1000次ID生成只需1次DB查询)

优势：
- ID较短(8-10位) vs 雪花ID(18位)
- 适合对外暴露的URL(用户主页链接)
```

## 📋 五、my-xhs ID策略汇总

| 业务 | ID方案 | 理由 |
|------|--------|------|
| 用户ID | 号段模式 | 短ID，适合URL展示 |
| 订单ID | 雪花ID | 趋势递增，适合B+树分库分表 |
| 流水号 | Redis自增 | 简单，适合日志流水 |
| 笔记ID | 雪花ID | 趋势递增 |
| 评论ID | 雪花ID | 趋势递增 |

## 🐛 六、踩坑记录（已知坑）

### 6.1 ShardingSphere分库后自增ID冲突

- **现象**：不同库生成了相同的自增ID
- **原因**：分库后各库独立自增
- **解决**：全部改用雪花ID
- **教训**：分库分表项目禁止使用数据库自增ID

### 6.2 雪花ID时钟回拨

- **现象**：服务报错"Clock moved backwards"
- **原因**：NTP时间同步导致时钟回拨
- **解决**：小回拨等待(sleep)，大回拨告警+人工介入
- **教训**：K8s Pod的NTP配置要确认

## 🎤 七、面试考察点

### Q1: 分布式ID用什么方案？

**推荐回答思路**：

> 1. "订单ID用雪花ID——趋势递增适合B+树索引，64bit不浪费空间"
> 2. "用户ID用号段模式——一次取1000个ID，减少DB交互，ID较短适合URL"
> 3. "WorkerId通过Redis INCR分配，保证多实例不冲突"

### Q2: 雪花ID有什么问题？怎么解决？

**推荐回答思路**：

> 1. "核心问题：时钟回拨——NTP同步可能导致时间倒退"
> 2. "解决：小回拨(<5ms)等待，大回拨(≥5ms)拒绝+告警"
> 3. "WorkerId分配：Redis INCR自动分配，启动时申请，避免手动配置出错"
