> 所属维度：性能工程 | 开发阶段：Phase-5 | 状态：⏳ 待开发
>
> **核心观点**：没有数据，一切压测/分库分表验证都是纸上谈兵。
> 本文档参考华仔电商实战项目第41/46/98篇，结合 my-xhs 实际业务设计。

## 🎯 一、为什么需要造数据

### 1.1 问题

| 场景 | 没有数据的后果 |
|------|--------------|
| 分库分表验证 | 无法验证分片路由是否均匀、跨库查询是否正确 |
| 压测 | 空库压测 QPS 虚高，无法暴露真实瓶颈（索引失效、慢查询、GC） |
| ES 搜索 | 空索引搜索无意义，无法验证分词效果、相关性排序 |
| 缓存策略 | 无法验证缓存命中率、热点 Key 分布 |
| 监控告警 | 无法触发水位告警，无法验证告警规则 |

### 1.2 数据量目标

| 服务 | 表 | 目标数据量 | 说明 |
|------|-----|----------|------|
| User | t_user | **1000万** | 模拟100万DAU的用户基数 |

| Note | t_note | **5000万** | 1年积累量 |

## 🏗️ 二、数据生成策略

### 2.1 数据生成原则

1. **数据分布要真实**：不能全是均匀分布，要有热点（20%用户产生80%内容）
2. **关联关系要正确**：订单引用的用户/商品/地址必须真实存在
3. **时间分布要合理**：不能全是同一天的数据，要分散在1年内
4. **ID 生成要符合分片规则**：分库分表的数据 ID 要能正确路由

### 2.2 数据生成顺序（有依赖关系）

```
Step 1: 基础数据（无依赖）
  ├── t_user（1000万）
  ├── t_spu + t_sku（100万 + 1000万）
  └── t_coupon_template（1万）

Step 2: 关联数据（依赖 Step 1）
  ├── t_user_address（依赖 user_id）
  ├── t_follow（依赖 user_id）
  ├── t_note（依赖 user_id）
  ├── t_inventory（依赖 sku_id）
  └── t_user_coupon（依赖 user_id + template_id）

Step 3: 二级关联数据（依赖 Step 2）
  ├── t_comment（依赖 note_id + user_id）
  ├── t_like（依赖 note_id + user_id）
  ├── t_counter（依赖 note_id / user_id）
  ├── t_cart_item（依赖 user_id + sku_id）
  └── t_order + t_order_item（依赖 user_id + sku_id + address_id）
```

### 2.3 数据分布模型

```
用户活跃度分布（帕累托分布）：
  - 头部用户（1%）：每人发布 100+ 笔记，10万+ 粉丝
  - 活跃用户（19%）：每人发布 10-50 笔记，1000-1万粉丝
  - 普通用户（80%）：每人发布 0-5 笔记，0-100 粉丝

商品热度分布：
  - 爆款商品（1%）：日销 1000+，库存频繁扣减
  - 热门商品（9%）：日销 100-1000
  - 长尾商品（90%）：日销 0-10

时间分布：
  - 按天分散在最近365天
  - 工作日 vs 周末比例 5:2
  - 每天内按小时分布（高峰 10-12, 19-22）
```

## 💻 三、批量写入方案

### 3.1 方案对比

| 方案 | 写入速度 | 适用场景 | 缺点 |
|------|---------|---------|------|
| 单条 INSERT | 100条/秒 | 调试 | 太慢，1000万需28小时 |
| JDBC Batch | 5万条/秒 | 中等数据量 | 需要编码 |
| MyBatis-Plus saveBatch | 3万条/秒 | 中等数据量 | ORM 开销 |
| LOAD DATA INFILE | 50万条/秒 | 大数据量 | 需要生成 CSV |
| **多线程 + JDBC Batch** | **20万条/秒** | **亿级数据** | **推荐方案** |

### 3.2 推荐方案：多线程 + JDBC Batch + 分片写入

```
架构设计：
  ┌─────────────────────────────────────┐
  │          DataGenerator              │
  │  ┌─────────┐  ┌─────────┐          │
  │  │ Thread-1 │  │ Thread-2 │  ...×N  │
  │  │ ID: 1~1M │  │ ID: 1M~2M│         │
  │  └────┬─────┘  └────┬─────┘         │
  │       │              │               │
  │  ┌────▼─────┐  ┌────▼─────┐         │
  │  │ Batch    │  │ Batch    │         │
  │  │ 5000条/批 │  │ 5000条/批 │         │
  │  └────┬─────┘  └────┬─────┘         │
  └───────┼──────────────┼───────────────┘
          │              │
     ┌────▼────┐    ┌────▼────┐
     │ MySQL-0 │    │ MySQL-1 │  (分库分表场景)
     └─────────┘    └─────────┘
```

**关键参数**：

| 参数 | 值 | 说明 |
|------|-----|------|
| 线程数 | CPU核数 × 2 | 4核机器用8线程 |
| 批次大小 | 5000条/批 | 太大会导致事务超时 |
| 连接池大小 | 线程数 + 2 | 每线程一个连接 |
| rewriteBatchedStatements | true | MySQL JDBC 批量优化必开 |
| 提交策略 | 每批提交一次 | 不要整个线程一个事务 |

### 3.3 各表预估写入时间

| 表 | 数据量 | 预估速度 | 预估时间 |
|-----|--------|---------|---------|
| t_user | 1000万 | 20万/秒 | 50秒 |
| t_note | 5000万 | 15万/秒 | 5.5分钟 |
| t_comment | 1亿 | 15万/秒 | 11分钟 |
| t_follow | 10亿 | 10万/秒 | 2.8小时 |
| t_order（分库分表） | 1亿 | 8万/秒 | 21分钟 |
| **总计** | **~25亿** | — | **约4小时** |

## 🔍 四、全量同步 ES 性能优化

> 参考华仔第46篇：千万级商品数据全量同步 ES 性能优化

### 4.1 问题

Canal 增量同步适合日常变更，但初始化时需要全量同步千万级数据到 ES。

### 4.2 全量同步方案

```
架构：
  MySQL → 分页查询 → 多线程 → ES Bulk API → ES集群

优化要点：
  1. 分页查询：基于ID范围分页（WHERE id > lastId LIMIT 5000），避免 OFFSET 深分页
  2. 多线程并行：8线程并行写入 ES
  3. ES Bulk API：每批 5000 条，bulk 写入
  4. 关闭副本：同步期间 number_of_replicas=0，同步完恢复
  5. 调大刷新间隔：refresh_interval=30s（默认1s），同步完恢复
  6. 断点续传：记录最后同步的 ID，中断后可继续
```

### 4.3 全量同步性能预估

| 索引 | 文档数 | 优化前 | 优化后 | 提升 |
|------|--------|--------|--------|------|
| product_index | 100万 | 30分钟 | 3分钟 | 10倍 |
| note_index | 5000万 | 25小时 | 2.5小时 | 10倍 |
| order_index | 1亿 | 50小时 | 5小时 | 10倍 |

### 4.4 ES 全量同步优化参数

```json
// 同步前：关闭副本 + 调大刷新间隔
PUT /product_index/_settings
{
  "number_of_replicas": 0,
  "refresh_interval": "30s"
}

// 同步完成后：恢复
PUT /product_index/_settings
{
  "number_of_replicas": 1,
  "refresh_interval": "1s"
}
```

## 🛡️ 五、数据隔离与安全

### 5.1 压测数据隔离

> 参考华仔第98篇：压测脏数据隔离

| 隔离维度 | 方案 | 说明 |
|---------|------|------|
| 数据库 | 影子表（`_shadow` 后缀） | 压测数据写入影子表，不污染正式数据 |
| Redis | Key 前缀（`shadow:` 前缀） | 压测缓存与正式缓存隔离 |
| MQ | Topic 后缀（`_SHADOW`） | 压测消息与正式消息隔离 |
| ES | 索引后缀（`_shadow`） | 压测索引与正式索引隔离 |
| 日志 | 标记（`traceId` 含 `shadow`） | 压测日志可过滤 |

### 5.2 敏感数据脱敏

| 字段 | 脱敏规则 | 示例 |
|------|---------|------|
| 手机号 | 随机生成 138xxxx 格式 | 13800001234 |
| 邮箱 | user{id}@test.com | user1000@test.com |
| 姓名 | 随机中文名生成器 | 张三、李四 |
| 地址 | 随机省市区 + 门牌号 | 北京市朝阳区xx路xx号 |
| Token | 不生成 | — |

## 🎤 七、面试考察点

### Q1: 你的项目数据量是多少？怎么造的数据？

> 1. "用户1000万、笔记5000万、关注关系10亿、订单1亿——这是按100万DAU运营1年推算的"
> 2. "自研了多线程批量写入工具，8线程+JDBC Batch 5000条/批+rewriteBatchedStatements，写入速度20万条/秒"
> 3. "数据分布模拟真实场景：帕累托分布（1%头部用户产生20%内容），时间分散在365天"

### Q2: 千万级数据全量同步 ES 怎么优化的？

> 1. "基于ID范围分页（避免OFFSET深分页）+ 8线程并行 + ES Bulk API 5000条/批"
> 2. "同步期间关闭副本（replicas=0）+ 调大刷新间隔（refresh_interval=30s），同步完恢复"
> 3. "支持断点续传，记录最后同步的ID，中断后可继续"
> 4. "100万商品3分钟同步完成，比优化前提升10倍"

### Q3: 压测数据怎么隔离的？

> 1. "全链路流量染色：请求Header带 X-Traffic-Tag=shadow"
> 2. "数据库影子表、Redis shadow前缀、MQ shadow Topic、ES shadow索引——四层隔离"
> 3. "压测结束后一键清理影子数据"
