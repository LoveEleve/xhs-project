# my-xhs 服务降级预案手册

> 每个服务都有明确的降级方案，不是"挂了就挂了"。
> 降级不是失败，是系统在极端情况下保护核心链路的主动策略。

---

## 一、降级原则

```
原则1：核心链路不降级，非核心链路可降级
原则2：降级是主动策略，不是被动失败
原则3：降级有明确的触发条件和恢复条件
原则4：降级操作必须可观测（告警+日志+指标）
原则5：降级方案必须经过演练（混沌工程验证）
```

### 1.1 业务分级

| 级别 | 业务 | 不可降级 | 说明 |
|------|------|---------|------|
| **P0** | 用户登录/注册 | ✅ | 没有用户什么也做不了 |
| **P0** | 笔记发布/浏览 | ✅ | 核心内容形态 |
| **P0** | 下单/支付 | ✅ | 核心交易链路 |
| **P1** | 点赞/收藏/评论 | ❌ 可降级 | 社交互动，非交易核心 |
| **P1** | 搜索 | ❌ 可降级 | 可用推荐替代 |
| **P1** | Feed流 | ❌ 可降级 | 可降级为热门推荐 |
| **P2** | 通知推送 | ❌ 可降级 | 延迟通知可接受 |
| **P2** | 计数展示 | ❌ 可降级 | 显示0可接受 |
| **P2** | IM私信 | ❌ 可降级 | 非核心功能 |
| **P3** | 热搜榜 | ❌ 可降级 | 运营功能 |
| **P3** | 后台管理 | ❌ 可降级 | 内部工具 |

## 二、逐服务降级方案

### 2.1 搜索服务降级

```
触发条件：
  - ES集群健康状态=RED
  - 搜索接口P99 RT > 3秒
  - 搜索接口错误率 > 5%

降级策略：
┌─────────────────────────────────────────────────┐
│ L1: 降级为缓存结果                               │
│   - 返回最近一次成功的搜索结果（Redis缓存5分钟）   │
│   - 适合：热门搜索词（覆盖60%搜索量）              │
├─────────────────────────────────────────────────┤
│ L2: 降级为热门推荐                               │
│   - 返回全站热门笔记/商品（Redis ZSet预计算）      │
│   - 前端文案变为"为你推荐"（替代"搜索结果"）       │
│   - 适合：非热门搜索词                            │
├─────────────────────────────────────────────────┤
│ L3: 降级为纯分类浏览                             │
│   - 返回分类列表（Redis缓存），用户按分类浏览      │
│   - 适合：ES完全不可用                           │
└─────────────────────────────────────────────────┘

恢复条件：
  - ES集群健康状态=GREEN 且 RT < 500ms 持续5分钟
  - 逐步恢复：先10%流量走ES → 50% → 100%
```

### 2.2 计数服务降级

```
触发条件：
  - Counter服务实例全部不可用
  - Redis Sentinel主从切换中

降级策略：
┌─────────────────────────────────────────────────┐
│ L1: 返回缓存计数                                 │
│   - 返回Redis中的计数（可能延迟1-2分钟）           │
│   - Buffer-Trigger数据在内存中，切换期间可能丢失    │
├─────────────────────────────────────────────────┤
│ L2: 返回0计数                                    │
│   - 所有计数显示为0                               │
│   - 点赞/收藏按钮仍可点击（操作写入Redis）          │
│   - 前端文案："点赞功能暂时无法显示数量"            │
├─────────────────────────────────────────────────┤
│ L3: 隐藏计数区域                                 │
│   - 前端隐藏点赞/收藏/评论数区域                   │
│   - 保留交互按钮                                  │
└─────────────────────────────────────────────────┘

恢复条件：
  - Counter服务健康且RT < 100ms
  - 自动恢复，无需人工干预
```

### 2.3 通知服务降级

```
触发条件：
  - Push服务不可用
  - MQ消费堆积 > 50000

降级策略：
┌─────────────────────────────────────────────────┐
│ L1: 通知延迟                                     │
│   - MQ消息不消费，堆积在Broker                    │
│   - Push恢复后批量消费，通知延迟送达               │
├─────────────────────────────────────────────────┤
│ L2: 关闭实时推送                                 │
│   - SSE连接断开，不尝试重连                        │
│   - 用户手动刷新时才拉取通知                       │
├─────────────────────────────────────────────────┤
│ L3: 通知功能下线                                 │
│   - 前端隐藏通知入口                              │
│   - 不影响核心浏览/下单流程                       │
└─────────────────────────────────────────────────┘

恢复条件：
  - Push服务健康且MQ堆积 < 1000
  - 先恢复MQ消费 → 再恢复SSE推送
```

### 2.4 推荐系统降级

```
触发条件：
  - 推荐服务RT > 2秒
  - 推荐接口错误率 > 10%

降级策略：
┌─────────────────────────────────────────────────┐
│ L1: 简化推荐路数                                 │
│   - 关闭协同过滤和内容召回（计算密集）             │
│   - 只保留热门召回 + 关注召回（轻量）              │
├─────────────────────────────────────────────────┤
│ L2: 纯热门推荐                                   │
│   - 返回全站热门笔记（Redis ZSet）                │
│   - 前端文案："热门推荐"                          │
├─────────────────────────────────────────────────┤
│ L3: 按时间倒序                                   │
│   - 返回最新发布的笔记（DB查询，走索引）           │
│   - 无个性化，但保证有内容                        │
└─────────────────────────────────────────────────┘

恢复条件：
  - 推荐服务RT < 500ms 且错误率 < 1% 持续5分钟
```

### 2.5 Feed流降级

```
触发条件：
  - Social服务不可用（关注数据无法获取）
  - Feed聚合RT > 2秒

降级策略：
┌─────────────────────────────────────────────────┐
│ L1: 关注流降级为发现流                            │
│   - 关注Tab内容用推荐填充                          │
│   - 前端提示"关注动态加载中，先看看推荐"            │
├─────────────────────────────────────────────────┤
│ L2: 降级为纯热门                                 │
│   - 关注Tab和发现Tab都显示热门内容                │
│   - 无个性化Feed                                  │
├─────────────────────────────────────────────────┤
│ L3: 降级为分类浏览                               │
│   - 按分类展示笔记                               │
│   - 最基础的内容消费方式                          │
└─────────────────────────────────────────────────┘
```

### 2.6 商品/库存服务降级

```
触发条件：
  - Product服务不可用
  - Inventory服务不可用

降级策略：
  - Product不可用：商品详情页返回缓存数据（Caffeine+Redis），可能延迟
  - Inventory不可用：显示"库存查询中"按钮，用户点击时重试
  - 商品搜索：降级为ES缓存结果
  - 价格展示：使用缓存价格 + "以实际下单价格为准"提示
```

### 2.7 订单服务降级

```
触发条件：
  - Order服务RT > 1秒
  - Order服务错误率 > 3%

降级策略：
  - ❌ 订单服务不可降级（核心交易链路）
  - 但可以做以下保护：
    1. 下单接口限流（降级为排队模式："前方拥挤，请稍后重试"）
    2. 订单查询走ES缓存（延迟1分钟，可接受）
    3. 取消订单限频（1分钟1次，防恶意取消）
    4. 库存扣减失败 → 友好提示"手慢了，商品已售罄"
```

## 三、中间件降级方案

### 3.1 Redis 降级

```
触发条件：
  - Redis Sentinel主从切换中（30秒不可用）
  - Redis内存不足触发淘汰

降级策略：
┌──────────────┬──────────────────────────────────────┐
│ 功能         │ 降级方案                              │
├──────────────┼──────────────────────────────────────┤
│ 缓存读取     │ 直接查DB（DB连接池加大临时）           │
│ 购物车       │ 降级为DB查询（异步落DB的兜底数据）     │
│ 分布式锁     │ 降级为本地锁（单实例有效）             │
│ 限流计数     │ 降级为本地令牌桶（不精确但可用）       │
│ 计数服务     │ 返回0/隐藏计数                        │
│ Session      │ 本地Session（单实例有效）              │
└──────────────┴──────────────────────────────────────┘

恢复条件：Sentinel切换完成 + 主节点可读写
```

### 3.2 MySQL 降级

```
触发条件：
  - MySQL主库不可用
  - 主从延迟 > 5秒

降级策略：
┌──────────────┬──────────────────────────────────────┐
│ 场景         │ 降级方案                              │
├──────────────┼──────────────────────────────────────┤
│ 主库不可用   │ ShardingSphere自动切从库（30秒内）     │
│              │ 期间写入请求返回"系统维护中"           │
│ 主从延迟     │ 写后5秒内的读走主库（HintManager）     │
│ 慢查询      │ 慢SQL自动熔断（Sentinel热点参数）      │
│ 连接池耗尽   │ 非核心查询降级，保核心写入             │
└──────────────┴──────────────────────────────────────┘
```

### 3.3 RocketMQ 降级

```
触发条件：
  - Broker不可用
  - 消费堆积 > 100000

降级策略：
┌──────────────┬──────────────────────────────────────┐
│ 场景         │ 降级方案                              │
├──────────────┼──────────────────────────────────────┤
│ Broker不可用 │ 事务消息降级为本地消息表               │
│              │ 非核心消息直接丢弃（记录日志）         │
│ 消费堆积     │ 非核心消费者暂停消费                  │
│              │ 核心消费者增加实例/批量消费            │
│ 顺序消息异常 │ 降级为普通消息（顺序不保证但不丢）     │
└──────────────┴──────────────────────────────────────┘
```

### 3.4 Elasticsearch 降级

```
触发条件：
  - ES集群状态=RED
  - 搜索RT > 3秒

降级策略：见2.1搜索服务降级
```

## 四、降级开关管理

### 4.1 降级开关配置

```yaml
# Nacos配置中心 — 降级开关统一管理
# DataId: degradation-switches.yml
# Group: COMMON_GROUP

degradation:
  search:
    enabled: false          # 搜索降级总开关
    level: 0                # 0=正常 1=缓存 2=热门 3=分类
  counter:
    enabled: false
    level: 0                # 0=正常 1=缓存计数 2=返回0 3=隐藏
  push:
    enabled: false
    level: 0                # 0=正常 1=延迟 2=关闭SSE 3=下线
  feed:
    enabled: false
    level: 0                # 0=正常 1=推荐填充 2=纯热门 3=分类
  recommend:
    enabled: false
    level: 0                # 0=正常 1=简化路数 2=纯热门 3=时间倒序
```

### 4.2 降级开关操作规范

```
操作流程：
1. 发现问题 → 确认降级触发条件已满足
2. 修改Nacos配置 → @RefreshScope热更新
3. 验证降级效果 → 监控面板确认
4. 记录降级操作 → 运维日志
5. 恢复时逐级提升 → 0% → 10% → 50% → 100%

禁止事项：
❌ 不允许直接kill服务实例（应该先从Nacos注销）
❌ 不允许跳级降级（必须逐级）
❌ 不允许无监控降级（必须有告警配合）
```

## 六、生产决策与表达

### Q: 系统挂了怎么办？

> "我们有完整的降级预案。核心链路（登录/浏览/下单）不降级，非核心链路按级别降级。比如搜索挂了降级为热门推荐，计数挂了显示0，通知挂了延迟推送。每个服务有3级降级策略，通过Nacos配置中心热更新切换。降级方案每季度用ChaosBlade演练一次，确保方案可用。"

### Q: 降级和熔断有什么区别？

> "熔断是自动的、微观的——某个接口错误率超过阈值，Sentinel自动熔断，直接返回降级响应。降级是手动的、宏观的——某个服务整体不可用，运维通过配置中心手动开启降级开关，整个服务走降级逻辑。熔断是代码级的保护，降级是架构级的策略，两者配合使用。"
