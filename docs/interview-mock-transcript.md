# 第一轮 · 技术面（约 60 分钟）

## 开场（3 分钟）

**面试官**：先花两分钟介绍一下你自己和这个项目，重点说**你负责什么**。

**候选人**（90 秒逐字稿）：
我是后端开发，主要方向是交易链路和稳定性。这个项目是一个内容+交易一体的电商平台，15 个 Spring Cloud 微服务、27 个容器，基础设施是 MySQL 分库分表 + Redis Sentinel + RocketMQ + ES + Canal + XXL-Job。
我负责两块：**交易与内容核心链路的设计开发**——库存、订单、支付、售后、结算、搜索、IM、网关这些链路的主体是我落的；以及**稳定性建设**——SLO 与告警、混沌演练、容量校准、多活容灾这些专项我主导。团队是分域协作，公共组件和基础设施是共享维护的。

`【旁注】`"主体是我落的"+"分域协作"两句话：既体现 ownership，又留了"不是全是我写的"的余量——P7 面试官最反感两件事：说不清边界、和夸大。**别说**"全是我一个人做的"。

**面试官**：系统什么量级？压测过吗？

**候选人**（60 秒）：
15 微服务 27 容器；压测是**单机同城双活仿真口径**：网关放行后约 4,640 RPS、商品详情 4,871 RPS（P99 50ms）、用户信息 5,846、首页聚合 1,861（P99 49.6ms）、搜索 1,448（P99 61ms）。容量是按限流余量 40% 校准的，不是拍脑袋填 QPS。

`【旁注】`"仿真口径"四个字是护身符——上千万级的话术一被问"生产集群多大"就穿帮；主动交代口径反而是资深信号。数字要背到"能立刻报出 + 知道冷热"（P99 熟记）。

## 深挖一：库存（12 分钟）

**面试官**：挑一个你觉得最能体现深度的链路讲。

**候选人**（2 分钟逐字稿）：
我讲库存。它解决的问题是"高并发下单不能超卖，同时不能因为库存服务拖垮下单"。
方案是**三级扣减**：Redis 分桶 + Lua 原子预扣 → MySQL 只做账本 → 对账收敛差异。预扣时单 Lua 完成"查总库存 → 按路由桶扣减 → 桶不足扫其它桶"，避免热点 key；热点 SKU 由滑动窗口（10s/100 次访问）自动触发扩容，默认 2 桶扩到 8 桶。
预扣记录用 ZSet 索引做超时回收，是 O(logN) 而不是全库 SCAN；幂等用 MySQL `INSERT IGNORE` 占位做兜底（Redis 记录丢失时防重复扣）。
验证数据：20 并发预扣不超卖（可用数 149→129）、超量请求整单拒绝；注入 75 秒事务回查延迟后库存仍然只扣一次。

**面试官（追问 1）**：超时回收和"支付成功确认"撞在一起怎么办？——比如预扣马上要过期，用户刚好付款成功。

**候选人**（90 秒逐字稿）：
这个我们**踩过并修了**。原实现是"提前 60 秒释放"：扫"60 秒内即将过期"的记录直接回退——本意是抢在 Redis TTL 到期前把记录读到，但代价是**支付如果在最后 60 秒完成，确认时找不到预扣记录**，那笔库存已经被还回池子了。
修复是两条：一是给预扣记录的**物理 TTL 加 10 分钟缓冲**（到期时刻不变，记录多活 10 分钟），二是回收任务改成**只回退真正到期的记录**。这样"支付在窗口内到达"一定能找到记录，"窗口外"才释放。另外预扣时长（30 分钟）和订单超时（30 分钟）是对齐的，支付侧过了 30 分钟会拒绝发起，所以边界上不会出现"订单还能付但库存已释放"。

`【旁注】`这题是**鉴别题**：能说出"原实现为什么提前释放（TTL 与索引 score 同域）"+"改了什么"+"窗口怎么闭合"，说明你真在做这套系统。**别说**"我们没问题"——面试官最想听的就是"踩过什么坑、怎么修的"。

**面试官（追问 2）**：TCC 呢？你简历里写了 TCC fence。

**候选人**（60 秒逐字稿）：
TCC 我**没有接进订单主链路**，这点先说清楚。我做的是：为库存提供 Try/Confirm/Cancel 冻结接口 + fence 状态机，覆盖了 11 个场景验证——幂等、空回滚、悬挂、超量拒绝、fence 状态流转。
订单链路最终走的是"事务消息 + 预扣"这套，因为下单只需要"本地事务与消息投递的原子性"，事务消息正好是这个问题的标准解；接 TCC 需要先把 Confirm/Cancel 的幂等语义和编排入口定义清楚，属于排期问题。

`【旁注】`主动交代边界 + 给出"接入前提"，比含糊说"用了 TCC"安全十倍。这是 P7-P8 最看重的"知道自己系统的真实状态"。

## 深挖二：订单与分布式事务（12 分钟）

**面试官**：下单是怎么做的？

**候选人**（90 秒逐字稿）：
下单用 **RocketMQ 事务消息 + 本地消息表**。流程是：先发半消息 → Broker 回调执行本地事务（订单 + 明细 + 本地消息表在同一个 DB 事务里）→ 成功 COMMIT、失败 ROLLBACK。Broker 长时间没收到结果会**回查**，回查查的就是本地消息表——因为本地消息和订单同事务写入，状态天然一致。
订单表是 ShardingSphere 4 库 × 4 表，分片键 user_id；按订单号查走映射表定位分片，映射写失败有个 5 分钟补录兜底。

**面试官（追问）**：订单状态的并发怎么处理？比如取消和支付同时发生。

**候选人**（2 分钟逐字稿）：
所有状态流转都是**条件 UPDATE**：`WHERE status = 期望前置值`，并发只有一个赢家，输家拿 0 行受影响走各自补退。关单和支付成功都要求 `status=0`，所以"取消 vs 支付"最多一个成功；如果支付赢、取消输，就是正常支付；如果取消赢、支付迟到了，走"支付成功但订单已取消 → 自动退款"闭环。
状态变更还会**先追加事件再更新状态**：事件表 `(order_id, event_seq)` 唯一键。这里有个考点：并发时两个事务同时为同一订单追加事件，序号会撞唯一键——我们的做法是 `INSERT IGNORE` 返回 0 就**整体回滚让调用方重试**，而不是在原地加锁重算序号。理由是：冲突说明对方也在追加，那两边的状态乐观锁也必然只有一个赢家，本事务本来就该失败；如果在冲突处抢锁，会形成"事件锁 → 订单锁"和调用方"订单锁 → 事件锁"的**反向锁序**，直接制造死锁面。重试时幂等检查看到状态已是目标值，会直接跳过，不会无限失败。

`【旁注】`这段是全场**最高分的回答**之一：把"为什么不在冲突处加锁"讲成锁序分析，是 P8 味。**别说**"加锁重算就行"。

**面试官（追问）**：那如果事件写进去了但人工改库把状态改回去了呢？

**候选人**（60 秒）：
会出现"事件在、状态退"的永久不一致——我们真实遇到过。修复是不重复插事件，但用**乐观锁把状态收敛回事件的目标值**。
另外为了能发现这类分叉，做了**回放校准**：按事件流重放订单状态，和当前状态比对，dry-run 默认只报告；要修复必须显式传 repair，而且**终态差异只报告不自动覆盖**（方向保护）。这套已经自动化成每日干跑任务，差异走告警。

## 深挖三：支付（10 分钟）

**面试官**：支付回调怎么保证不重复不丢？

**候选人**（90 秒）：
支付单是状态机：0 待支付 → 1 成功 / 2 失败 / 3 已退款，所有流转条件 UPDATE，所以**重复回调天然幂等**——status 不是 0 就直接返回。
回调结果做**三态判定**：成功 / 明确失败 / 无法判定。解析不出来（格式不符）必须回 "fail" 让渠道重试、**不改状态**——我们修过这个坑：原实现把解析失败当失败处理，结果一个格式不符的成功回调会被标记支付失败并触发订单取消。
超时方面：30 分钟未支付置失败；如果之后渠道终态成功才到，条件翻转 2→1 并重新执行全部成功副作用（通知订单、MQ、自动退款判断）。

**面试官（追问）**：用户超时被置失败、订单取消了，然后渠道说付款成功了——钱怎么办？

**候选人**（60 秒）：
迟到成功会先把支付单翻回成功，再看订单状态：订单如果还是待付款→正常走支付成功；订单已被取消→走"业务拒绝自动退款"，钱原路退回，订单保持取消，用户无感知损失。这个闭环的意义是：**钱和状态必须有一个权威顺序**，我们的原则是"钱不能悬空"。

**面试官（追问）**：渠道是 Mock 的，这套设计怎么证明能接真实渠道？

**候选人**（60 秒逐字稿）：
状态机、幂等、三态解析、迟到处理、对账这些**和渠道无关**的部分都是真实实现，Mock 只替换了渠道适配层。接入真实渠道我列了三个前置条件：一是**验签 SPI**（支付宝 RSA2 / 微信 V3，校验失败不改任何状态并告警）；二是**超时前置查询 + 关单**——置失败前先查渠道，防止"本地失败渠道已收钱"，关单防止"已关单却被付款成功"；三是回调端点公网化配套：IP 白名单、独立限流、原始报文留存（对账举证）。这三条都是接入前置，不是优化。

`【旁注】`这题**必须主动交代"Mock 是适配层、设计是真的"**，然后给接入清单。装成生产渠道=当场穿帮；这样答=把危机变成展示"边界感"的机会。

## 深挖四：售后分摊 + 结算（8 分钟）

**面试官**：退款金额怎么算？举个例子。

**候选人**（90 秒）：
订单级优惠要按明细分摊，否则"整单减 50"退一件就无从下手。算法是**最大余数法，分为单位整数运算**：比如 300 元订单用 50 元券，三件 100/120/80，退 120 那件——分摊 = 50×120/300 = 20 元，应退 100 元。
取整规则：逐项下整（floor），差额按小数余数从大到小补分，平局按明细 ID 升序——保证**同一订单任何时候重算逐分一致**。两个硬不变量：**Σ 分摊 == min(优惠, 商品总额)**、**每项分摊 ≤ 该项金额**，所以"退款=明细金额−分摊"天然不超退。

**面试官（追问）**：部分数量退款呢？10 分钱的东西退 1/3 怎么算？

**候选人**（60 秒）：
按比例**向下取整**——宁可少退不多退。但纯下整多次退会累计少拿几分：三次各退 1/3 累计 9 分，一次退满 3/3 是 10 分。所以加了一条："**本次退满**（已退数量+本次 ≥ 购买数量）时用'整件可退 − 已占用'**补齐差额**"，多次退款累计严格等于整件可退。另外"已占用"包含**退款中**的单子，防止"仅退款+退货退款"两种类型并发双退。

**面试官（追问）**：结算对账呢？

**候选人**（60 秒）：
按 T-1 生成渠道账单（收款/退款/净额/手续费），三方对账出三类差异：本地有渠道无、渠道有本地无、金额不一致，全部挂账。规则是：重复对账幂等、**人工已处理的差异不被覆盖**（尊重人工结论）、差异消失自动收敛、重现自动复位。对账文件没到就按标记跳过这一渠道——先有"到账"事实再做对账，避免产出假差异。

## 深挖五：搜索与长连接（8 分钟）

**面试官**：ES 和 MySQL 怎么保持一致？

**候选人**（90 秒）：
把同步当"持续对账"做：**双通道**——Canal 解析 binlog 实时同步（毫秒级）+ MQ 补偿通道补漏；**外部版本号**（毫秒时间戳）拒绝陈旧写——乱序或重投都不会让旧文档覆盖新文档；删除写 **tombstone** 再删文档，防止"更早的 update 消息晚到把已删数据复活"。
每日还有**全量重建**兜底：id 游标断点续传、完成后清零断点（否则次日"全量"退化成增量）、尾部清理源表已删的死文档。重建的写入也带外部版本，和增量竞争时"版本新的赢"；版本冲突当成"已最新"跳过而不是批次失败。

**面试官（追问）**：那你怎么知道 ES 和 MySQL 真的是一致的？

**候选人**（30 秒）：
全量重建本身就是一致性校验——它扫 MySQL 全量 upsert 到 ES 并清死文档；平时靠版本号保证写入序。诚实的部分：没有做双向逐文档 diff 的巡检。

**面试官**：IM 跨实例，消息会丢吗？

**候选人**（60 秒）：
**不丢，但是 at-least-once**——会重复，客户端按 msgId 去重。设计是：消息先落离线持久副本（Redis ZSet，1000 条/7 天）→ 再尝试在线推送 → 客户端 ACK 后才删副本。跨实例走 Redis Pub/Sub 定向投递（每实例一个 channel），目标实例挂掉时消息还在副本里，重连补发。校验真值：单实例挂掉后消息在重连时补发，协议层把"必须 ACK、必须去重"写进客户端契约。

## 深挖六：稳定性（8 分钟）

**面试官**：你说主导稳定性，具体做了什么？

**候选人**（90 秒）：
三层：**可观测**——40 条分级告警（severity + Runbook）、SLO 错误预算（30 天 43 分 12 秒）、Watchdog 心跳、告警端到端演练；**可恢复**——混沌演练 7 个场景（Redis/MQ 暂停、CPU 满载、磁盘写满、MySQL 暂停、优雅停机），每个场景明确"链路行为"（比如 Redis 挂：网关黑名单 fail-closed 503、缓存路径回退 DB、计数走缓冲/对账）；**可定位**——traceId 跨 HTTP/MQ/线程池/长连接全链路。
数字：MySQL 故障转移演练 RTO ≈32s（停主 10.2s / 提升 0.087s / 应用切换 22s）；Redis 切主 2.3s 业务无错乱；同 zone 优先在跨区延迟注入下吞吐 +34%、P99 降 33~47%。

**面试官（追问）**：Redis 挂了系统是什么行为？你想过吗？

**候选人**（60 秒）：
按路径分类设计过：**认证链路**（网关 Token 黑名单）→ fail-closed 返回 503 但要和"真吊销的 401"区分，客户端可重试；**缓存路径**→ 回退查 DB（CacheHelper 捕获 RedisUnavailable 降级），但读路径要有超时上限（客户端 commandTimeout 1s，不然回退永远等不到）；**计数/幂等这类写路径**→ fail-closed 或打点后降级，靠对账收敛。原则是：**缓存可以丢，认证和资金不能含糊**。

# 第三轮 · 行为面（约 15 分钟，7 个 90 秒故事逐字稿）

**1）最有成就感的事？**
商品详情的性能治理。压测发现 QPS 上不去，火焰图定位到**类加载锁**：每个请求都在做 `Class.forName`，92/99 个 Tomcat 线程 BLOCKED 在同一把锁上。改成静态桥接后，商品模块从 1,074 涨到 4,871 RPS（4.5 倍），P99 50ms 且没有加本地缓存。成就感来自"根因是 JVM 层、修复是一行桥接"的反差。
`【卡点】`1,074→4,871、4.5x、92/99 BLOCKED、P99 50ms。

**2）最难排查的 bug？**
有个 bug 排查了两轮：同机多实例的 Snowflake **worker-id 重号**——只按 IP 派生时两个实例都算出 257，同毫秒同序列会生成相同的订单 ID。修复是加入端口维度，实测变成 354 和 454。更值钱的是它的延伸：我们发现 Snowflake 在低流量下低位增量恒定，导致按 `id mod 16` 预分片时 131 单 75% 落在 2/16 片——**发号器的特性漏进了存储层**，最后改成按 user_id 哈希取模并迁移了 682 行。
`【卡点】`257/257 → 354 vs 454；75% → 2/16 片；迁移 682 行 → 16/16。

**3）一次故障演练的复盘？**
MySQL 故障转移演练：停主库 10.2 秒、选主 0.087 秒、应用侧连接池切换 22 秒，RTO 约 32 秒。复盘沉淀了 5 项短板，最关键的是应用切换占了 2/3 的时间——来自连接池探测粒度，整改方向是缩短探测间隔+预热连接。演练的价值不是数字好看，是**知道数字背后是谁慢**。

**4）和别人有技术分歧？**
有三个我记得的：一是订单事件序号冲突——对方主张"加锁重算 seq"，我坚持"整体回滚让调用方重试"，理由是在冲突处抢锁会制造反向锁序死锁；二是券的发送失败处理——我坚持"回滚 Redis 必须和**作废 Outbox** 成对"，只回滚会被补发任务超发；三是敏感词热更新——我坚持 copy-on-write 重建 trie，不能原地改。三次都是我最终说服了团队，靠的是给出**反例**（死锁/超发/撕裂读），不是"我觉得"。

**5）你怎么保证代码质量？**
四个抓手：CI 门禁（编译+单测+规范扫描，实测拦截违规提交）；117 项测试矩阵覆盖关键链路；文件级覆盖审计（购物车 34 文件、内容 38/38、网关 11 个核心类）；以及**多轮 review 制度**——每个模块修完必须再过一轮 review，两轮之间至少抓到 5-10 个问题（包括我自己改出来的，比如除零、括号结构、CROSSSLOT）。

**6）你犯过的错？**
两个：一是 worker-id 只按 IP 派生导致同机多实例重号——教训是"派生规则必须包含实例唯一维度"，后来所有 ID/路由派生都先问"同机多实例会不会撞"；二是做保留策略时第一版按天单批清理，没算日增量，追不上增长——教训是**清理必须核算"日增量 vs 单次吞吐"**。

**7）你怎么和他人协作？**
接口契约先行：跨服务调用先把请求/响应/错误码定下来再并行开发；沉淀可复用资产：把排查过程写成事实表和手册（团队新人照着能跑通全链路）；边界清晰：我主导的模块我负责到底，共享组件改动先在群里同步影响面。

# 第四轮 · 收尾（5 分钟）

**面试官**：如果让你继续改进这套系统，你第一步做什么？

**候选人**（60 秒）：
如果**接真实渠道**，第一步是验签 SPI——这是资金安全的前置；如果是**日常演进**，第一步是把三个"隐式"变"显式"：订单状态机的转移表（已做）、事件流的归档策略、以及幂等/限流的 fail-open 指标（已做）。我的习惯是：改进项必须有**触发条件**，不然就是技术债换技术债。

**面试官**：你有什么想问我的？

**候选人**：
三个：① 团队现在交易/基础架构的分工和我的角色预期？② 稳定性目前最大的痛点是什么——是故障响应还是容量规划？③ 如果我加入，前三个月最希望我解决什么问题？

`【旁注】`三个问题分别指向**角色、痛点、预期**——都是"我准备干活"的视角，比问福利/加班加分得多。
