# 问题排查方法论与场景清单（xhs 项目）

> 目标：把"问题排查"从"背命令"变成**可复用的决策树 + 真实演练资产**。
> 工具家底：arthas（/opt/arthas/arthas-boot.jar）、stress-ng、jstack/jmap/jstat/jcmd/jinfo、tc netem、wrk、chaosblade(OS级)、docker exec。

## 一、核心心法（排查不是背命令，是决策树）

```
【第0步 · 看监控/可观测（入口，先于任何命令）】
  告警触发了什么？哪个节点/服务/时间？
  Grafana/Prometheus：RED（QPS/错误率/延迟）+ USE（CPU/内存/磁盘/网络/饱和度）
  趋势：突变 vs 渐变，同比环比，是否已自愈

【第1步 · 缩小范围】
  trace（SkyWalking 慢链路/慢 span）+ 日志（ELK 关键时间点）
  → 定位到具体服务/接口/实例

【第2步 · 假设 + 命令验证（监控指向哪层，才上哪层命令）】
  假设 → 最小代价命令证伪 → 证据（数字/栈/火焰图）

【第3步 · 根因 + 修复 + 复盘】
  根因能解释所有现象 → 修复（先止血后根治）→ 复测 + 可复现回归
```

> **核心心法（修正版）：命令是验证手段，监控才是入口。** 一上来就 `top`/`jstack` 是"盲查"——正确的排查一定从监控大盘/告警出发（先知道是哪个节点、哪个服务、哪个指标、什么趋势），再用 trace/log 缩到具体请求，最后才用命令去验证监控指向的那个假设。

**三条铁律**：
1. **先分段再深挖**：接口慢不要一上来就 jstack——先用 traceId/耗时把"网关→服务→DB→下游"分段，锁定段再深挖；
2. **先看资源再看代码**：CPU/内存/IO/网络四象限先排除系统层，再看 JVM，最后看代码；
3. **用数据证伪**：每个假设必须有"验证命令 + 判据"，例如"如果是我怀疑的线程，top -H 的 tid 转 16 进制应在 jstack 里出现"。

## 二、分层排查体系（8 层，L0 可观测层是入口）

| 层 | 关注 | 核心工具/命令 | 典型症状 |
|---|---|---|---|
| **L0 可观测（入口）** | 大盘/告警/RED/USE | Grafana、Prometheus(`node_*`/`jvm_*`/`hikaricp_*`/`tomcat_threads_*`)、告警规则、SkyWalking trace、ELK | 哪个节点/服务/指标异常、趋势突变 |
|---|---|---|---|
| **L1 OS/容器** | CPU/内存/IO/磁盘/网络 | `top -H`、`free -m`、`df -h`、`iostat -x 1`、`ss -s`、`/proc/<pid>/*` | 负载高、磁盘满、端口耗尽 |
| **L2 JVM** | GC/线程/堆/锁 | `jstat -gcutil <pid> 1000`、`jstack <pid>`、`jmap -histo:live`、`jcmd GC.heap_info`、arthas `dashboard/thread/profiler` | GC 频繁/停顿长、BLOCKED、死锁、OOM |
| **L3 应用** | 接口分段/池/降级 | traceId 链路、HikariCP 指标、线程池指标、arthas `trace/watch/tt` | 接口慢、连接池满、线程池拒绝 |
| **L4 MySQL** | 慢SQL/锁/连接 | `SHOW PROCESSLIST`、慢查询日志、`EXPLAIN`、`information_schema.innodb_trx/locks`、`SHOW ENGINE INNODB STATUS` | 慢查询、锁等待、死锁 |
| **L5 Redis** | 慢命令/大key/热key/内存 | `SLOWLOG GET`、`--bigkeys`、`--hotkeys`、`INFO memory`、`MEMORY USAGE` | 响应慢、内存满、热key |
| **L6 MQ** | 积压/消费慢/重试 | `consumerProgress`、消费组 LAG、DLQ 数、`messageTrack` | 积压、重复消费、死信 |
| **L7 网络/网关** | 延迟/丢包/状态码 | `tc qdisc`、`ping/mtr`、`ss -s`、网关 access log、`curl -w` 分段 | 502/503/504、超时、抖动 |

## 三、症状 → 层 快速索引（面试最常问）

| 症状 | 第一跳 | 第二跳 | 第三跳 |
|---|---|---|---|
| **接口慢** | 分段耗时（网关/服务/DB/下游） | 哪段慢 → 该层工具 | 慢SQL / 下游超时 / GC 停顿 / 连接池等 |
| **CPU 飙高** | `top -H` 看是哪个线程 | 业务线程 → jstack/arthas profiler；GC 线程 → jstat | 热点方法 / 频繁 GC / 自旋 |
| **内存高/OOM** | `jmap -histo:live` 看对象 | 堆内 vs 堆外（NMT） | 泄漏对象 / 大对象 / 缓存无上限 |
| **GC 频繁** | `jstat -gcutil` 看 YGC/FGC 与耗时 | 堆大小/晋升速率 | 新生代太小 / 内存泄漏 / 大对象 |
| **502/503/504** | 502=网关到服务不通；503=服务不可用/限流；504=后端超时 | 对应层（进程/线程池/下游） | 进程挂 / 池满 / 下游慢 |
| **连接超时** | 网络（tc/ping） | DB 连接池 / Redis 连接 | 丢包 / 池耗尽 / 慢命令 |
| **MQ 积压** | consumer lag | 消费速率 vs 生产速率 | 消费者宕机 / 消费逻辑慢 / 毒丸 |
| **线程 BLOCKED** | `jstack` 找阻塞点 | 锁竞争（类加载锁/同步块） | 热点锁 / 类加载 / 连接池 |
| **磁盘满** | `df -h` + `du` 定位目录 | 日志/临时文件/数据文件 | 日志未轮转 / 大文件未清 |
| **TIME_WAIT 多** | `ss -s` | 短连接/未复用 | 连接池缺失 / keep-alive 配置 |

## 五、落地路线
1. **工具**：arthas ✅ / stress-ng ✅ / JDK 五件套 ✅ / tc ✅；
2. **逐场景演练**（P0 优先）：构造 → 注入 → 排查（记录命令与输出）→ 定位根因 → 修复 → 回归 → 报告；
3. **沉淀**：`scripts/troubleshoot-*.sh`（分层一键采集）、`docs/reports/troubleshoot-*.md`（每场景一份）；
4. **接入 AI Agent**：把排查路径做成诊断工具/知识卡（xhs-ai 已有 metric/log/lag 工具，可扩 GC/线程/慢SQL 工具）；
5. **面试素材**：本文件 + 各场景报告 → 题库"问题排查"专题 + 追问。

## 六、命令速查（节选，按层；L0 监控优先）
```bash
# L0 监控/可观测（先做这个）
curl -s 'http://127.0.0.1:19090/api/v1/query?query=node_load1'   # 节点负载
curl -s 'http://127.0.0.1:19090/api/v1/query?query=node_cpu_seconds_total'
curl -s 'http://127.0.0.1:19090/api/v1/query?query=jvm_gc_pause_seconds_sum'
curl -s 'http://127.0.0.1:19090/api/v1/query?query=hikaricp_connections_active'
curl -s 'http://127.0.0.1:19090/api/v1/query?query=tomcat_threads_busy_threads'
# 告警规则: config/prometheus/alert_rules/myxhs_rules.yml（HighGcPause/HighHikariPoolUsage/HighErrorRate/HighResponseTime/...）
# trace: SkyWalking；日志: ELK(kibana)

# L1
top -H -p <pid>            # 线程级 CPU；tid 转 16 进制去 jstack 找
free -m; df -h; du -sh /path/* | sort -h | tail
iostat -x 1 3; ss -s; ss -ltnp | grep <port>
cat /proc/<pid>/status | grep -E "Threads|VmRSS"
# L2
jstat -gcutil <pid> 1000 10
jstack <pid> > /tmp/stack.txt; grep -A20 "BLOCKED" /tmp/stack.txt
jmap -histo:live <pid> | head -20; jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>
jcmd <pid> GC.heap_info; jcmd <pid> Thread.print
java -jar /opt/arthas/arthas-boot.jar <pid>   # dashboard/thread -b/profiler start/trace/watch/tt/ognl
# L3
curl -w "dns:%{time_namelookup} conn:%{time_connect} ttfb:%{time_starttransfer} total:%{time_total}\n" -o /dev/null -s <url>
# L4
SHOW PROCESSLIST; SHOW ENGINE INNODB STATUS\G
SELECT * FROM information_schema.innodb_trx\G
EXPLAIN ANALYZE <sql>;
# L5
redis-cli -p 6379 --bigkeys; redis-cli SLOWLOG GET 10; redis-cli INFO memory
# L6
mqadmin consumerProgress -n <ns> -g <group> | awk 'NR>1{s+=$6}END{print s}'
# L7
tc qdisc show; tc qdisc add dev eth0 root netem delay 100ms loss 5%
```
