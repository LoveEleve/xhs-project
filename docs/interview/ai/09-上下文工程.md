# 第09题 | 上下文工程：摘要、重建、截断

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：会话摘要、阈值触发、批量摘要、上下文重建、截断策略、Token 预算平衡

## 问题
长会话上下文怎么管？历史消息多了怎么办？会话摘要怎么做的？

## 面试可讲版（五段式）

**① 业界背景**
上下文窗口是稀缺资源：全量塞历史会烧钱 + 超窗 + 注意力稀释。主流策略：**滑动窗口**（丢最老的）→ **摘要压缩**（老历史压成摘要）→ **检索增强**（按相关性取历史片段）。工程上摘要要解决：何时触发（阈值）、怎么压缩（LLM 摘要）、怎么恢复（摘要+近窗口重建）、失败怎么办（重建兜底）。

**② 项目选择**
xhs-ai 上下文工程：
- **异步摘要**：`SessionSummaryJob` 调度（**600s 间隔**，初始延迟 120s），条件：会话消息 **≥50 条**、**批处理 5 个会话**/轮 → `SessionSummaryService` 调模型生成摘要；
- **摘要选择**：`SummarySelector` 决定注入哪个摘要（最近摘要优先）；
- **上下文重建**：F7 方案——用"摘要 + 最近 N 条消息"重建上下文；消息表可恢复（崩溃/重启后能重建会话）；
- **截断**：超出窗口按策略截断（保留 system + 摘要 + 近消息），与 Token 预算联动。

**③ 坑**
- **同步摘要会阻塞对话**：摘要是慢操作（LLM 调用），必须异步（定时任务），不能塞在请求链路；
- **摘要质量**：模型摘要可能丢关键信息（订单号/金额）——关键实体要么结构化存储，要么摘要 Prompt 强制保留；
- **阈值设计**：50 条触发太早浪费（短会话也被摘要），太晚超窗；按"消息数 + Token 数"双阈值更稳；
- **崩溃恢复**：只在内存里维护上下文，重启就全丢——必须有消息表 + 重建逻辑（F7 的核心价值）。

**④ 兜底**
- 消息落库（可重建）；摘要任务失败重试 + 幂等（同一会话不重复摘要）；
- 重建失败退化到"仅近窗口"（最差也能继续对话）；
- 批量摘要限速（5 会话/轮）防集中调用打爆预算；
- 观测：摘要任务执行日志 + 会话上下文长度指标。

**⑤ 话术**
> "上下文我们分三层：消息全量落库可重建，异步摘要任务每 10 分钟扫一次、会话满 50 条就压摘要、每轮最多处理 5 个；重现时用'摘要 + 最近消息'重建。摘要是异步的，绝不放对话链路里；崩溃恢复靠消息表 + F7 重建逻辑。摘要 Prompt 会强制保留关键实体，防止订单号金额被压掉。"

## 追问与参考回答
**追问1：为什么是 50 条不是 Token 数？** 消息条数简单稳定；更严谨是"条数 + Token 双阈值"，本项目主用条数、Token 由预算体系兜底。
**追问2：摘要用哪个模型？** 摘要质量要求高、量不大，可用主力模型；也可便宜模型+人工抽检（按评测）。
**追问3：多个摘要怎么选？** 最近摘要优先；`SummarySelector` 可按时间/相关性选，未来可接 RAG 式检索。
**追问4：摘要丢了关键信息怎么办？** Prompt 强制保留结构化字段（订单号/金额/ID）+ 原始消息永远在库里，需要时回查。
**追问5：上下文和 RAG 什么关系？** 摘要压缩会话内历史，RAG 检索会话外知识；两者都是"选择性注入"，可以叠加。

## 发散追问地图（横向）
- 上下文策略：滑动窗口、摘要、分层记忆（短期/长期）、MemGPT 思路。
- 记忆：向量记忆、实体记忆、画像。
- 成本：摘要摊薄 vs 全量重放；缓存命中。
- 恢复：消息表、checkpoint、F7 重建。
- 评测：摘要质量（关键实体保留率）、重建成功率。

## 面试官评分点
**高级开发级**：能讲摘要/截断/重建三件套；知道摘要是异步的。
**架构师加分**：双阈值设计；关键实体保留；崩溃重建（F7）；批量限速防预算集中消耗。
**危险信号**：同步摘要；无落库只靠内存；摘要不保留关键实体。
