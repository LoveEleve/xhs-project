# 第19题 | 需求工程与架构决策：34 场景 / REQ→AC→TC / 23 条 ADR

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：场景库、REQ→AC→TC 追溯、量化 NFR/SLO、STRIDE、ADR、框架边界

## 问题
AI 项目的需求怎么定的？怎么保证需求都被实现和测试？架构决策怎么做的？

## 面试可讲版（五段式）

**① 业界背景**
AI 应用项目的需求天然发散（"诊断助手"一句话可以无限展开），业界两种失败模式：**没有需求锚点**（做着做着变成万能聊天）与**没有决策记录**（几个月后没人记得为什么选它）。工程化解法是把需求工程当一等公民：场景库（用例即契约）、量化 NFR/SLO（可测量的非功能）、STRIDE 威胁模型（安全需求显式化）、ADR（决策+理由+备选+止损）。

**② 项目选择（四件套）**
- **场景库（34 个）**：`REQ-DIAG`（15 个诊断：下单失败/支付未收敛/DLQ 积压/traceId 定位…）、`REQ-KB`（知识问答）、`REQ-OPS`（动作+审批）、`REQ-PLAT`（平台）——每个场景写明**输入、期望证据形态、数据源、优先级 P0/P1**；场景锚定 xhs 真实链路/表/中间件/历史案例（不是拍脑袋的 demo 用例）；
- **量化 NFR/SLO**：流式首字 P95 ≤2s、端到端 P95 ≤15s（无审批）、只读工具 P95 ≤3s、变更工具 P95 ≤10s、服务可用性 ≥99.5%（v1 单机）；同时出 **STRIDE 威胁模型**（每条威胁有缓解）；
- **REQ→AC→TC 追溯矩阵**：每条 REQ 至少 1 个自动化 TC；**P0 场景 E2E + EVAL 双覆盖；红队为发布门槛**；TC 编号 `TC-<层>-<域><序号>`（UT/CT/IT/E2E/EVAL/RED/PERF）——需求不是写完就完，落到门禁里；
- **23 条 ADR**（决策+理由+备选，部分带止损条件）：
  - 框架：AgentScope 2.0 Java（内置 Harness/HITL/状态）vs Spring AI/LangChain4j；
  - 状态：Redis(Sentinel) CAS，RPO≤1s/RTO≤30s，写失败 fail-closed（拒绝状态分叉）；
  - 检索：**BM25 先行 + 评测触发向量**（止损：无 ≥5% 提升即删除向量路径）；
  - 模型网关自研薄层（预算/审计/缓存/降级深度耦合，上游 OpenAI 兼容可替换）；
  - 工具契约：never-throw + timeout 声明 + intent/effect/settlement；策略引擎 last-match-wins + 默认 ask；
  - 分阶段策略：代码导航（JGit→jdtls v1.1 触发）、扩展框架两代（Java SPI → Sidecar，禁止 in-process full-trust）；
  - v1.5 需求演进：MCP 提升一等公民 + SQL 从"禁止"改为**受控只读查询**（AST 校验+READ ONLY 事务+只读账号+行数/超时+脱敏+审计）。
- **框架边界（很能打的细节）**：Flyway **只管 `ai_*` 表，不碰 `agentscope_*`**（框架自管 schema）——自定义与框架的迁移责任切干净，升级框架不炸业务表。

**③ 坑（主动承认）**
- **需求会演进**：开发中发现 MCP 生态成熟度超预期（D09 对标），把"MCP 桥接"升为"一等公民"、SQL 从"一刀切禁止"改为"受控只读"——ADR 记录变更理由，避免"文档是三个月前的"；
- **过度设计风险**：向量检索、沙箱、jdtls、Sidecar 都是"设计存在、v1 不启用"，靠**触发条件+止损规则**约束，而不是"简历需要所以上"（RV09）；
- **场景覆盖率靠门禁不靠自觉**：P0 场景双覆盖是门禁脚本卡出来的，人工维护的追溯矩阵一定会腐化；
- **缺口公开**：14 项生产化缺口（OTel/Langfuse 0 命中、DLP 仅密钥、Prompt 版本化缺失等）写进文档而不是藏起来。

**④ 兜底**
- 需求变更走 ADR（新增/修订+理由），场景库与 TC 同步更新（同一 PR 内）；
- 门禁（单测+审计一致性+哈希链+评测）作为最终仲裁；
- 框架边界用 Flyway 脚本目录硬隔离（`ai_*` vs `agentscope_*`）。

**⑤ 话术**
> "AI 项目最怕需求发散和决策失忆，所以我们先建场景库：34 个场景全部锚定 xhs 的真实链路——下单失败、支付未收敛、DLQ 积压这类，每个都写清输入、期望证据、数据源和优先级；非功能量化到 SLO：首字 P95 两秒、只读工具三秒；安全有 STRIDE 威胁模型。所有这些落到 REQ→AC→TC 追溯矩阵，P0 场景必须 E2E+评测双覆盖、红队卡发布。架构决策记了 23 条 ADR，包括 BM25 先行的止损规则和框架边界——Flyway 只管 ai_* 表，不碰 agentscope_*。需求演进也有记录，比如 MCP 从桥接升成一等公民。"

## 发散追问地图（横向）
- 需求工程：用户故事/用例、可测试性、需求优先级（P0/P1）、变更控制。
- 非功能：SLO/错误预算、容量估算、时延预算分解。
- 安全：STRIDE/OWASP LLM Top10、威胁建模与缓解对应。
- 决策实践：ADR 模板、止损规则、技术债登记。
- 交付：追溯矩阵、门禁、发布门槛（红队/评测）。

## 面试官评分点
**高级开发级**：能讲场景库/追溯矩阵/ADR 的基本做法。
**架构师加分**：REQ→AC→TC 落门禁的闭环；量化 NFR 与止损规则（BM25 vs 向量）的商业理性；框架边界（Flyway 隔离）的长期价值；需求演进（MCP 一等公民）的记录方式。
**危险信号**：需求全靠拍脑袋；SLO 无量化；没有决策记录；框架表和业务表混管。
