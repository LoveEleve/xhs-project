# 第21题 | 部署与运维：systemd / 日志 / 指标回环 / 脚本化运营

> 难度：★★★☆☆｜频率：★★★★☆｜区分度：中
> 关键词：systemd 托管、readiness/liveness、JSON 日志滚动、指标回环、10 个运维脚本

## 问题
你这个 Agent 怎么部署的？升级怎么做？日志和指标怎么采集？依赖挂了会怎样？

## 面试可讲版（五段式）

**① 业界背景**
AI 应用服务有个尴尬的现实：**状态在框架/Redis、依赖跨系统（LLM+中间件）、单实例验证**。容器化（K8s）是终态方向，但在"平台已有 systemd + 单机中间件"的约束下，最务实的做法是 systemd 托管 + 脚本化运营：把可靠性（自启/自愈）、可观测（日志/指标/审计）、运营（成本/评测/演练）全部沉淀成可执行资产，而不是靠手工操作。

**② 项目选择（实配）**
- **托管**：`xhs-ai.service`（systemd）——`Restart=always` + `RestartSec=10` + `TimeoutStopSec=45`（优雅停机窗口），两个 EnvironmentFile（`tokens.env` 令牌 + `.env.local` 环境差异），`-Xmx1g`，端口 19020；
- **健康语义**：liveness=进程存活；**readiness=MySQL/Redis 可达**（本地关键依赖）——AI 的可用性前提是"能读状态、能读数据"；
- **日志**：Logback JSON（Logstash encoder）→ **100MB/文件、保留 7 天、总量 2GB 上限**；traceId 贯穿 HTTP/工具/审计；
- **指标**：Micrometer → Prometheus；抓取走 **127.0.0.1:19020 回环**（prometheus.yml 显式 loopback）——指标不经过公网，减少暴露面；
- **依赖面**（与 xhs 平台共用）：MySQL（审计/业务表）、Redis（状态/预算/审批）、ES（日志检索/知识 BM25）、RocketMQ Admin（DLQ 诊断）、Prometheus（指标查询）、LLM API（出网收敛）；
- **脚本化运营（10 个）**：`gate.sh`（一键门禁：单测+审计一致性+哈希链）、`audit-gate.sh`/`audit-verify.sh`/`audit-check.sql`（审计链）、`cost-week.sh`（周成本）、`load-test.sh`（会话压测）、`red-team.sh`（8 项红队）、`tool-eval.sh`（工具评测）、`order-flow.sh`（全链路下单演练）、`traffic-gen.sh`（造流量）——运维动作全部可执行、可复现。

**③ 坑（主动承认）**
- **MCP 子进程管理**曾是运维痛点：框架只规定"怎么连"不规定"进程崩了怎么办"→ 做进程自愈（探测+三连击+限流+systemd 拉起）后，最终选择**去 MCP 化**（工具全自研，MCP 只留运维直连）；
- **资源约束是硬边界**：AI 组件新增 4-6GB 磁盘依赖扩容；jdtls（1.2-1.5GB）在磁盘/内存紧张时可降级——容量规划写进 ADR-20；
- **单机单实例**：可用性目标 99.5%（v1），无多副本编排；Bulkhead 隔离、只读降级模式是设计项未落地；
- **补数/评测的运行态偶发**：预算额度、评测隔离用户这些"非功能问题"会以"评测失败"的面目出现——运维知识要写进脚本注释而不是人脑。

**④ 兜底**
- `Restart=always` + readiness 探针 + 优雅停机（45s，等在途请求与状态落盘）；
- 状态存 Redis（可恢复/可重建）；审计与成本有独立脚本对账；
- 所有运维动作脚本化 + 文档化（10 个脚本即 runbook）。

**⑤ 话术**
> "部署很务实：systemd 托管，Restart=always、45 秒优雅停机、两个环境文件区分令牌和配置；健康检查区分 liveness 和 readiness——readiness 要 MySQL 和 Redis 都能连，因为 AI 的状态和依赖都在那边。日志是 JSON 100MB 滚动 7 天，指标让 Prometheus 从回环地址抓，不走公网。运维全部脚本化：门禁、审计校验、成本周报、压测、红队、工具评测、全链路演练一共 10 个脚本，相当于把 runbook 变成了可执行代码。边界也清楚：单机单实例、99.5% 可用性目标，K8s 和多副本是下一步。"

## 发散追问地图（横向）
- 部署：systemd vs 容器 vs K8s、蓝绿/滚动、优雅停机。
- 可观测：JSON 日志规范、指标回环 vs 全量、trace 采样。
- 运维：runbook 脚本化、变更窗口、容量规划。
- 依赖治理：中间件共用、出网白名单、令牌管理（EnvironmentFile）。

## 面试官评分点
**高级开发级**：能讲 systemd 托管、健康检查语义、日志指标采集。
**架构师加分**：readiness 与状态依赖的绑定逻辑；指标回环的安全考量；runbook 脚本化；资源约束写进 ADR。
**危险信号**：部署靠手工、日志无上限、指标裸奔公网、没有优雅停机。

## 本轮补充（2026-09-20 演练注入教训）
- **systemd 环境注入坑**：drop-in 的 `Environment=` 会被 `EnvironmentFile=`（tokens.env/.env.local）覆盖——演练/临时改参必须改 EnvironmentFile 并重启；`systemctl show` 显示的值未必是进程实际值（以 /proc/<pid>/environ 为准）。
- 演练后恢复流程：还原 .env.local → 重启 → 校验进程环境 + 业务回归（chat 200/E2E 10/10）；评测报告 JSON 归档进仓库。
