# 第04题 | 变更闭环：intent→effect→settlement 与核验

> 难度：★★★★★｜频率：★★★★☆｜区分度：高
> 关键词：变更三板斧、提案-批准-执行-核验、可证伪断言、位点核验、幂等、审计追溯

## 问题
问题：Agent 执行了重投，你怎么知道"真的生效了"而不是接口返回 200 就完事？

## 面试可讲版（五段式）

**① 业界背景**
SRE 的变更管理强调"可灰度、可监控、可回滚"，并且有一个朴素共识：**ack ≠ 生效**。对 Agent 执行生产变更更苛刻：要能回答三个问题——谁批准的（intent）、到底做了什么（effect）、结果是否真的达成（settlement）。业界的验证范式是**可证伪断言**：不是"调用成功"，而是"断言某个可观测状态成立"，否则不许标成功。

**② 项目选择**
把变更建模为闭环：**intent**（审批记录：工具、参数、`raw_input_hash` 指纹）→ **effect**（执行器 CAS 后重投，写 settlement=待核验）→ **settlement**（`RedeliverVerifier` 在 10 分钟窗口后**两级判定**：① 双 ID 再入检测——消息又回 DLQ 就是 `reentered_dlq`（**失败裁决**：重投无效，需排查消费者）；② 未再入则做队列级位点核验——`consumerOffset > queueOffset` 判 `verified_consumed`（成功），否则 `verified_no_reentry`（交人工复核））→ **审计**（哈希链留痕）。三段任一段失败：标失败 + 人工介入，绝不静默。

**③ 坑（都是实测踩出来的）**
- 只看 MQ API 返回成功不够：**"发送成功 ≠ 生效"**——核验器要等到窗口后看队列位点；
- 双 ID 兼容是踩出来的：不同 RocketMQ 回退链路写的是 `uniqId` 或物理 `offsetMsgId`，核验器两者都查（`findByOriginMsgId(group, offsetMsgId) || (group, newMsgId)`）；
- "又回 DLQ"和"已被消费"是两种终局：`reentered_dlq` 说明重投没解决问题（毒丸消息就是这样），必须人工排查而不是重投到成功；
- 执行器崩溃留下 executing 孤儿 → 回收 Job 标 failed（>600s，不自动重放副作用）；
- 核验本身可能误判（窗口内消费慢）→ 位点未越过时不标成功，标 `verified_no_reentry` 交人工复核。

**④ 兜底**
- 核验失败不抛弃数据：置 FAILED 并保留现场（审计链可回放）；
- 状态机 + 事件总线（ApprovalEventBus）让 UI/指标实时可见；
- 审批指纹绑定参数，核验绑定真实队列状态，两端都可复算；
- 每日对账兜底：审批/执行/核验三表可交叉核验。

**⑤ 话术**
> "变更闭环的终点不是接口 200，而是可证伪的断言：要么队列位点越过消息位点（已消费），要么它又回到了 DLQ（重投无效，换方案）。核验不过就是失败，fail-closed、人工接手——生产变更不许'大概好了'。"

## 追问与参考回答
**追问1：什么叫可证伪断言？** 能明确为真/假且不依赖操作者自述的观测：消息是否再次进入 DLQ（查得到/查不到）、队列消费位点是否越过消息位点（数值比较）；"接口返回 success"不算。
**追问2：位点核验核什么？** 先记下发时消息落在哪条队列的哪个 `queueOffset`，窗口后读该队列 `consumerOffset`：越过即被消费（verified_consumed）；没越过且没再入 DLQ 则人工复核（verified_no_reentry）。
**追问3：核验失败但实际成功了怎么办？** 按失败处理（宁可人工复核），核验器设计时用"不在原队列"这类强断言降低误判；不确定就标 UNKNOWN 不标成功。
**追问4：为什么审批和核验要分开？** 批准是意图，核验是事实；同一个组件同时做"决策"和"验收"会失去独立性。
**追问5：可回滚吗？** DLQ 重投本身是"加消息"，补偿方式是再次消费/丢弃；闭环记录让回滚可审计（谁批、执行了几次、核验结论）。

## 面试官评分点
**高级开发级**：能说清 intent/effect/settlement 三段；知道 ack≠生效；能给出可证伪断言示例。
**架构师加分**：位点核验与假生效的拆穿、孤儿执行回收、审计链闭合、失败语义（FAILED vs UNKNOWN）与人工介入路径。
**危险信号**：以 API 200 作为成功标准；核验用"自己说成功"；失败后静默重试无记录。

## 本项目真实证据
- `approval/RedeliverVerifier`：`@Scheduled`(首延迟 60s/间隔 30s) 扫 `status='approved' AND result LIKE '%pending_verification%'`；`reentered` 判定 = `findByOriginMsgId(group, offsetMsgId) || (group, newMsgId)`；位点判定 = `queueProgress(group, originTopic, brokerName, queueId)` 的 `consumerOffset > queueOffset`；三裁决 `reentered_dlq` / `verified_consumed` / `verified_no_reentry` 写回 result + 审计。
- `ApprovalExecutor`：白名单仅 `dlq.redeliver`；settlement 记录 backlogBefore/newMsgId/offsetMsgId/brokerName/queueId/queueOffset/sentAt（10 分钟核验窗口）。
- 实测：live-drill 中毒丸消息重投→`reentered_dlq`（核验器识破"重投无效"）；production-gaps 报告闭环记录。

## 发散追问地图（横向）
- 变更管理：SRE 三板斧（可灰度/可监控/可回滚）；变更窗口与告警抑制。
- 核验设计：可证伪断言、位点核验、双 ID、窗口与重试。
- 副作用事务性：幂等、补偿、人工兜底；"不自动重放"的取舍。
- 回滚策略：什么条件自动回滚、回滚本身的风险与审计。
- 审计链：哈希链、不可抵赖、取证与合规。
- 演练体系：混沌注入、毒丸消息、故障注入剧本。
- 指标体系：变更成功率、核验失败率、人工介入率、MTTR。
