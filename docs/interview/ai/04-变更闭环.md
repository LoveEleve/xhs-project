# 第04题 | 变更闭环：intent→effect→settlement 与核验

> 难度：★★★★★｜频率：★★★★☆｜区分度：高
> 关键词：变更三板斧、提案-批准-执行-核验、可证伪断言、位点核验、幂等、审计追溯

## 问题
问题：Agent 执行了重投，你怎么知道"真的生效了"而不是接口返回 200 就完事？

## 面试可讲版（五段式）

**① 业界背景**
SRE 的变更管理强调"可灰度、可监控、可回滚"，并且有一个朴素共识：**ack ≠ 生效**。对 Agent 执行生产变更更苛刻：要能回答三个问题——谁批准的（intent）、到底做了什么（effect）、结果是否真的达成（settlement）。业界的验证范式是**可证伪断言**：不是"调用成功"，而是"断言某个可观测状态成立"，否则不许标成功。

**② 项目选择**
把变更建模为闭环：**intent**（审批记录：工具、参数、指纹）→ **effect**（执行器 CAS 抢占后执行，队列级位点核验防"重投但消息没走"）→ **settlement**（`RedeliverVerifier` 断言消息已离开 DLQ/落回目标，`reentered_dlq` 为核验证据）→ **审计**（哈希链留痕）。三段任一段失败：FAILED + 人工介入，绝不静默。

**③ 坑（都是实测踩出来的）**
- 只看 MQ API 返回成功不够：重投接口成功但消息仍占用 DLQ（位点未推进）→ 修复为队列级 `queueOffset` 核验 + 双 ID 匹配（offsetMsgId + uniqId），把"假生效"拆穿；
- 执行器崩溃留下 EXECUTING 孤儿 → 回收 Job 释放重试；
- 重复批准/重复执行 → CAS + 幂等键；
- 核验本身可能误判（消息刚被别的消费组带走）→ 断言用队列级事实而不是单一视图。

**④ 兜底**
- 核验失败不抛弃数据：置 FAILED 并保留现场（审计链可回放）；
- 状态机 + 事件总线（ApprovalEventBus）让 UI/指标实时可见；
- 审批指纹绑定参数，核验绑定真实队列状态，两端都可复算；
- 每日对账兜底：审批/执行/核验三表可交叉核验。

**⑤ 话术**
> "变更闭环的终点不是接口 200，而是可证伪的断言：消息不在原 DLQ、且位点真的推进了。核验不过就是失败，fail-closed、人工接手——生产变更不许'大概好了'。"

## 追问与参考回答
**追问1：什么叫可证伪断言？** 能明确为真/假且不依赖操作者自述的观测：队列里消息不存在、位点推进到某值、DLQ 计数下降；"接口返回 success"不算。
**追问2：位点核验核什么？** 重投后消息在源队列的位移/移出事实；RV18 修复了双 ID 匹配（offsetMsgId+uniqId）与队列级 queueOffset 校验，解决"看起来重投了实际还占着"。
**追问3：核验失败但实际成功了怎么办？** 按失败处理（宁可人工复核），核验器设计时用"不在原队列"这类强断言降低误判；不确定就标 UNKNOWN 不标成功。
**追问4：为什么审批和核验要分开？** 批准是意图，核验是事实；同一个组件同时做"决策"和"验收"会失去独立性。
**追问5：可回滚吗？** DLQ 重投本身是"加消息"，补偿方式是再次消费/丢弃；闭环记录让回滚可审计（谁批、执行了几次、核验结论）。

## 面试官评分点
**高级开发级**：能说清 intent/effect/settlement 三段；知道 ack≠生效；能给出可证伪断言示例。
**架构师加分**：位点核验与假生效的拆穿、孤儿执行回收、审计链闭合、失败语义（FAILED vs UNKNOWN）与人工介入路径。
**危险信号**：以 API 200 作为成功标准；核验用"自己说成功"；失败后静默重试无记录。

## 本项目真实证据
- `approval/RedeliverVerifier`（核验器，reentered_dlq 断言）；`ApprovalExecutor`（CAS 执行）；`ApprovalExecutionRecoveryJob`/`ApprovalExpiryJob`（补执行/回收/超时）。
- RV18 修复：双 ID 匹配（offsetMsgId+uniqId）、队列级 queueOffset 位点核验、执行 CAS、诊断鉴权、EventBus 指标；`docs/reports/` 中 production-gaps 与 live-drill 报告（实测重投→核验闭环）。

## 版本与来源
SRE 变更管理公开实践；Google SRE 变更三板斧；本项目 RV18 报告与 approval 模块代码。

三段闭环、核验器、孤儿回收、位点核验均为代码与报告事实；核验断言细节以 `RedeliverVerifier` 实现为准。
