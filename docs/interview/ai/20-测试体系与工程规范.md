# 第20题 | 测试体系与工程规范：六层矩阵 / E1-E7 / 依赖治理

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：六层测试、契约 fixture、DLQ 门禁、Enforcer、CVE 扫描、断言打副作用

## 问题
AI 项目的测试怎么做？LLM 不确定怎么测？依赖冲突怎么治理？CI 门禁卡什么？

## 面试可讲版（五段式）

**① 业界背景**
AI 应用的测试比传统后端多两层难题：**外部依赖不可控**（LLM 输出不确定、ES/Prom 数据在变）与**质量定义模糊**（"答得好"没有断言）。工程解法：LLM 桩 + fixture 录放（契约层）、评测集版本化（质量层）、红队当发布门槛（安全层）；同时工程规范（依赖/出网/权限/审计）必须可执行——写成文档不执行等于没有。

**② 项目选择（六层矩阵 + E1-E7）**
- **六层测试矩阵**（层级/触发/阈值）：
  | 层 | 内容 | 触发 | 阈值 |
  |---|---|---|---|
  | UT | 策略/状态机/脱敏/检索/评测器/Guard/成本 | 每提交 | 0 失败（实测 **61 个单测**/20 类） |
  | CT | 外部系统契约（LLM 桩 + fixture 录制回放） | 每提交 | schema 变更必须更新 fixture |
  | IT | MySQL/Redis/ES 真实集成 | PR | 0 失败 |
  | E2E | 对话/SSE/审批/权限/负向 | nightly + 发布前 | 0 失败（<20min） |
  | EVAL | 知识问答 + 诊断质量（**50 条答案 + 14 条轨迹**，知识 30/诊断 15/安全 5） | PR 子集 / nightly 全量 | 通过率 ≥90%、回退 ≥2% 阻断、引用必须有效 |
  | RED | 注入/越权/危险指令（**8 项**红队脚本） | 发布前 | 全部拦截 |
  | PERF | **4 个场景**：50 并发 SSE / 10 并发诊断 / 工具 QPS / 审批高峰 | 发布前 | 满足 D07 SLO |
- **断言打副作用（RV11 原则）**：不只打主流程返回值——三条独立完整性门禁：`TC-EVAL-OPS-01` DLQ 全量零积压（每轮回归后 `%DLQ%*` backlog=0）、`TC-CT-EVENT-01` 消费者动作词汇表契约（逐动作"发布数=落库数"，无 SKU 动作走 0 哨兵）、`TC-CT-SCHEMA-01` schema 契约（代码声明与 DDL 机械比对，uk 类漂移零容忍）；
- **E1-E7 工程规范**（可执行版）：E1 构建与依赖（精确版本禁 LATEST、Enforcer 三规则、OWASP dependency-check 高危阻断）、E2 运行时与并发（SSE 桥接/线程池隔离/多副本会话一致性/背压/优雅停机）、E3-E7 权限/审计/灰度回滚等；**出网收敛到两个域名**、受控只读 SQL 三层（AST+READ ONLY+只读账号）；
- **CI 三段门禁（设计）**：PR = UT+CT+IT+EVAL 子集+依赖扫描；nightly = E2E 全量+EVAL 全量+引用有效性全扫；release = RED+PERF+E2E 全量+手工验收清单；
- **落地差（主动披露）**：六层矩阵是**设计 + 分阶段落地**——当前仓库实际资产：UT **61**、**CT 已落地（ModelContractTest：fixture 回放 200/429/500/连接中断重试 4 用例，全量 65/65 绿）**、EVAL（kb 30 + tool 14 + answer 50）、RED（8 项脚本）、PERF（4 场景脚本）；**IT/E2E 目前是 TC 清单**（已定义编号与断言），本地门禁实跑"单测（含契约）+审计一致性+哈希链（可选 LLM 评测）"，CI 仅跑单测（默认不出网）。

**③ 坑（主动承认）**
1. **依赖冲突 4 项**（全部实测处置）：okhttp 版本降级（对齐 AgentScope BOM）、jedis 漂移、org.json 重复类、MCP 的 json 包冲突——MCP 包做了**豁免并附退出条件**（临时豁免必须写"何时撤销"，否则永久腐化）；另排除 AgentScope 中运行无关的重依赖（kubernetes-client/aliyun-sdk-oss 等）；
2. **LLM 测试的诱惑**：想"每次都真调模型"→ CI 默认不出网，只有 `-Peval-live` 才访问 LLM/Ark；契约层用桩 + fixture，评测层用版本化数据集；
3. **测试环境依赖真实中间件**：本地方案是复用已运行中间件（不追 Testcontainers），代价是"测试与环境耦合"，隔离靠每用例独立 `(userId,sessionId)` + 清理钩子；
4. **评测门禁的教训**：预算硬限曾拦截评测请求（默认 20 万→50 万），评测隔离必须用专用用户 + 运行前清零额度。

**④ 兜底**
- fixture 回放让外部系统漂移可复现；评测集 git 版本化让质量可对比；
- CVE 扫描 + 精确版本 + 依赖收敛防供应链风险；
- 红队脚本化（8 项）作为发布前最后一道卡口。

**⑤ 话术**
> "AI 项目测试我按六层设计：实际落地的是 61 个单测、94 条评测用例（知识 30/工具 14/答案 50）、红队 8 项、性能 4 个场景；契约、集成、E2E 是已定义的 TC 清单、按环境逐步落地，CI 目前只跑单测——设计矩阵和落地进度我会分开讲。最关键的差异是断言打在副作用上：每轮回归后 DLQ 必须零积压、消费者逐动作发布数等于落库数、schema 声明和 DDL 机械比对。工程规范写成 E1-E7 可执行版，依赖精确版本加 Enforcer 加 CVE 扫描；CI 三段门禁 PR/nightly/release 各卡各的。LLM 不确定性用桩和版本化评测集隔离，CI 默认不出网。"

## 发散追问地图（横向）
- 测试分层：测试金字塔、契约测试、属性测试、变异测试。
- LLM 测试：桩/录放、非确定性断言、评测集设计、评审员偏差。
- 供应链：Enforcer、CVE 扫描、SBOM、许可证。
- CI/CD：门禁设计、nightly/release 分层、回滚流程。
- 工程规范：出网白名单、只读 SQL 三层、审计只追加。

## 面试官评分点
**高级开发级**：能讲六层矩阵、LLM 桩与 fixture、CI 门禁。
**架构师加分**：断言打副作用的门禁设计（DLQ/schema/事件词汇表）；依赖豁免的退出条件；评测与预算隔离的实操教训；文档规范"可执行化"。
**危险信号**：LLM 输出当确定性断言；CI 真调大模型；依赖冲突靠删代码绕过；豁免无退出条件。
