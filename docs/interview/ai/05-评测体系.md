# 第05题 | 评测体系：三层 + 轨迹部分分

> 难度：★★★★★｜频率：★★★★★｜区分度：高
> 关键词：工具选择评测、答案级评测、轨迹评测、部分给分、稳定性重复、评测隔离、门禁

## 问题
问题：Agent 质量怎么量化？改了 Prompt/工具怎么知道变好还是变坏？

## 面试可讲版（五段式）

**① 业界背景**
Agent 评测比模型评测难：输出是"过程+结果"（工具调用轨迹 + 最终答案），且非确定性。业界实践分三层：**组件级**（工具选择/检索命中）、**结果级**（答案正确性，LLM-judge 或关键词/引用断言）、**轨迹级**（步骤序列是否正确、冗余多少）。共识：不要只测最终答案——过程错了答案可能是蒙对的；也不要用单次运行下结论——要重复测稳定性。

**② 项目选择**
三层评测体系：
- **工具选择**：12 例（该用哪个工具），**12/12**；
- **答案级**：50 条用例（KB30 知识 + DIAG15 诊断 + SEC5 拒答安全），通过判定=关键词命中**或**引用卡片/代码位置；安全用例要求明确拒绝且无泄漏（`sk-/ark-/glsa_/系统提示`）；**引用有效性 100%**；
- **轨迹级**：14 例覆盖 7 类能力，`expected` 集合匹配（命中比例给分）、`sequence` **有序子序列**（允许中间探索，但关键步骤顺序必须对）；稳定性 = 代表 4 例 × 3 次，**均值 0.917**（11/12 满分，1 次是客户端 240s 超时的基础设施抖动）。
另有知识卡评测（55 卡）作为 KB 语料质量门。

**③ 坑（都是实测踩的）**
- **预算拦截污染评测**：首轮全量 14 例被当日 50 万硬限拦截（TS-12/13/14 毫秒级 429），一度误判为"轨迹失败"→ 改为 `EVAL_UID=1001` 评测专用用户 + 运行前清零额度，评测与真实用户预算隔离；
- **超时抖动要单独归因**：稳定性 12 次里 1 次失败是客户端 240s 超时（基础设施），不能算模型能力——报告里单独标注、不混入均值；
- **集合匹配比例给分**：多工具任务命中部分也给分，否则"对了一半"和"全错"同分，看不出改进；
- 评测集别写太死：固定工具名会随工具重构失效（去 MCP 化后要同步更新 expected）。

**④ 兜底**
- 门禁脚本（`gate.sh`/`audit-gate.sh`/`audit-verify.sh`）+ 单测 61 项：改动后先跑单测与门禁再看评测；
- 评测报告落盘（answer-eval/tool-selection-eval/trajectory-eval + nightly-100 历史样本）；
- 新用例先跑单条复测（支持 type/limit/ids 定向），再跑全量；
- 失败用例归因分类：模型能力 / 工具设计 / 基础设施 / 评测集缺陷。

**⑤ 话术**
> "Agent 评测要测三层：工具选对没、答案对不对、轨迹像不像；过程允许探索，但关键步骤顺序用有序子序列卡。评测本身也要防污染——我们被预算硬限坑过一次，后来用专用评测用户+清零额度隔离，所有失败都要归因到'模型/工具/基础设施/评测集'四类之一。"

## 追问与参考回答
**追问1：为什么用有序子序列而不是完全一致？** Agent 路径天然有探索空间，完全一致会把合理探索判错；有序子序列保证关键步骤顺序与关键工具覆盖。**追问2：LLM-judge 用吗？** 当前答案级以确定性断言（关键词/引用）为主，LLM-judge 有偏差（偏好长答案/自我风格），若引入要做校准与双盲；稳定性报告里的评分是确定性部分分，不依赖 judge。**追问3：12/12、0.917 是小样本吗？** 是，样本量有限是事实；所以用"重复运行+部分分+归因"提高信息量，而不是宣称统计显著。**追问4：评测集怎么维护？** 用例随能力域扩充（KB/DIAG/SEC/轨迹），expected 与工具/知识卡版本同步；门禁保留历史报告可回归。**追问5：在线指标呢？** 靠 17 项可观测指标（工具耗时/错误率、P95、预算消耗）做线上兜底，离线评测管质量。

## 发散追问地图（横向）
- 评测方法论：rubric 评分、pairwise 对比、LLM-as-judge 偏差（位置/长度/自我偏好）与校准。
- 统计：重复次数与置信区间、pass@k vs pass^k（稳定性）、方差随温度变化。
- 评测集工程：覆盖度矩阵、难例挖掘、污染与泄漏（训练数据 vs 评测题）、版本化与冻结。
- 在线评测：影子流量、A/B、canary、用户反馈闭环（点赞/修正回灌）。
- 成本与评测：评测也要花 token（我们用专用额度），预算与样本量权衡。

## 面试官评分点
**高级开发级**：能说清三层与部分给分；知道稳定性要重复跑；能解释评测隔离。
**架构师加分**：失败归因体系、评测集维护与版本化、judge 偏差意识、门禁与回归流程、离线/在线指标体系。
**危险信号**：只测最终答案；单次运行下结论；评测消耗真实用户预算；把基础设施抖动算作模型失败。
