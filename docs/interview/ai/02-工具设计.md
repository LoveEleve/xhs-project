# 第02题 | 工具设计：16 个自研工具与选择准确率

> 难度：★★★★☆｜频率：★★★★★｜区分度：高
> 关键词：function calling、工具选择、服务端封装 DSL/PromQL、never-throw、schema 预算、tool_search

## 问题
问题：Agent 的工具怎么设计的？为什么不让模型直接写 ES DSL/PromQL？工具多了模型选错怎么办？

## 面试可讲版（五段式）

**① 业界背景**
Function calling 普及后有两条经验之争：① **工具数量**——业界观察"注册工具越多，模型选择准确率越低"，Anthropic 建议像设计 API 一样设计工具（描述即 prompt、参数正交、返回结构化）；② **谁能写查询**——让模型直接产 ES DSL/PromQL 灵活但极易幻觉（字段名/语法/聚合写错），封装成语义工具稳但覆盖面受限。加上 MCP 标准化带来的黑盒/权限/热替换问题，工具层的工程化成了 Agent 落地的分水岭。

**② 项目选择**
20 个工具全自研（运维 16 + 业务 4）、按域分类：DLQ（dlq_list/detail/redeliver）、日志（log_search/log_top_services）、指标（metric_top/trend/labels）、ES（es_search/es_index_list）、知识（knowledge_search/catalog + code_locate/card_read），另有 consumer_lag_top；业务类：order_trace/order_stats/inventory_query/coupon_query（业务库只读 SELECT）。**模型只传语义参数**（服务名、时间窗、关键词、topN），ES DSL/PromQL 由服务端构造（`LogQueryBuilder`/`MetricQueryBuilder`）；工具描述写明"何时用、参数示例、返回结构"；所有工具 never-throw，错误以结构化结果回给模型自纠。

**③ 坑**
- 早期暴露 raw DSL 查询工具，模型频繁写错字段/语法，重试成本高 → RV21 简化为 log_search/log_top_services（**P95 最慢接口题 98s 答偏 → 50s 答对**；ERROR Top 服务题 98s+ → 12.8~43.5s）；RV22 同类改造 metric_top/metric_trend；
- 工具描述含糊会让模型"用错域"（用日志工具查指标）→ 描述里加适用/不适用场景，选择评测才到 12/12；
- 工具 schema 也要 token：历史实测 3428 tokens（当时 32 工具含 MCP 口径），软限 12k——工具数再翻倍就会顶到；
- 权限默认 ASK 让无只读注解的工具永久挂起（空答复 503）——工具"注册成功≠可调用"。

**④ 兜底**
- 工具预算双护栏：数量软 36/硬 40（超硬拒绝启动）+ schema token 软 12k；
- 参数校验失败返回纠错提示（禁止同结构重调）；结果截断 + 分页；
- traceId 逐工具透传，工具级指标（耗时/错误率/调用次数 17 项指标之一）；
- 评测兜底：工具选择 12/12、轨迹评测 0.917，回归时能发现"该用没用/用错工具"。

**⑤ 话术**
> "工具设计是 Agent 的接口设计：模型只做语义决策，查询构造留在服务端；工具数量不是越多越好，我们给数量和 schema token 都设了预算，超了就上渐进式 tool_search。"

## 追问与参考回答
**追问1：多少工具算多？** 没有绝对值，看选择准确率与 schema 预算。我们实测 16 个 12/12，所以把硬限放 40；再涨用 tool_search 两段式加载。
**追问2：为什么不让模型写 DSL？** 幻觉不可控、安全不可控（可能扫全索引/大范围聚合）；语义参数 + 服务端构造还能做白名单与限流。
**追问3：工具返回多大？** 截断 + 摘要（如日志只回 top 行 + 计数），超限提示模型收窄条件；避免大结果把上下文吃掉。
**追问4：怎么防"工具该用没用"？** 提示词硬约束（系统本体问题必须走知识检索）+ 评测用例回归 + 轨迹评分。
**追问5：MCP 工具和自研工具怎么选？** 核心链路自研（可控、可测、可热修）；MCP 只用于运维直连与外部能力接入（双白名单、未知工具快速失败）。

## 面试官评分点
**高级开发级**：能讲清语义工具 vs raw query 的取舍；能解释工具描述与选择准确率的关系；知道 never-throw 与自纠。
**架构师加分**：工具预算（数量/schema token）、渐进式加载、权限与安全边界、工具级可观测、评测驱动迭代。
**危险信号**：工具无预算无白名单；让模型直接拼查询；工具异常直接把堆栈抛给模型。

## 本项目真实证据
- `agent/tools/` 20 个工具类（16 运维 + 4 业务）+ `LogQueryBuilder`/`MetricQueryBuilder`（服务端构造）+ `business/BusinessQueryService`；去 MCP 化后 MCP 已旁路（旧 19s/39s 口径作废，2026-09-20 复核为 15.1s 快速失败 + 1.2s 重建）。
- `ToolBudget`：软 36/硬 40；schema 历史实测 3428 tokens（32 工具口径）；工具选择评测 12/12；轨迹稳定性 0.917。
- 权限 ASK 挂起 P0 修复（`tools_enabled`/只读注解/BYPASS 取舍）见 RV18。

## 发散追问地图（横向）
- 粒度设计：粗粒度业务工具 vs 细粒度 API 暴露；谁写查询（模型 vs 服务端）。
- 描述工程：描述即 prompt、参数示例、错误信息可自纠、命名一致性。
- Schema 设计：参数正交、枚举收敛、默认值、必填最小化；token 成本。
- 渐进加载：tool_search、工具分组、按场景暴露；白名单与版本。
- MCP 对比：协议收益与黑盒/权限/热替换问题；进程隔离与自愈。
- 工具安全：风险分级、审计、幂等、幂等与审批的接入点。
- 评测：选择准确率、参数正确率、错误恢复率；用评测驱动工具迭代。
