# 第14题 | 可靠性：自愈、崩溃恢复、幂等、并发

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：审批执行崩溃恢复、幂等、并发闸门、McpHealthMonitor、X-Request-Id、F7 重建

## 问题
Agent 服务的可靠性怎么保证？崩溃了怎么办？并发怎么控制？

## 面试可讲版（五段式）

**① 业界背景**
Agent 比普通服务多三类故障：**长链路中途崩溃**（LLM+工具多轮，执行到一半挂了）、**外部进程依赖**（MCP/工具子进程）、**并发放大**（一个用户开多会话烧资源）。可靠性设计=幂等 + 恢复 + 限流 + 自愈，核心是**先落库再执行**（有据可查、可恢复）。

**② 项目选择**
xhs-ai 四道防线：
- **审批执行崩溃恢复**：`ApprovalExecutionRecoveryJob`（延迟 120s、批量 20）扫描 `status='approved'` 但无结果的审批单——**重新执行**（`ai_approval_recovered_total`）或**回收待人工**（`ai_approval_reclaimed_total`）；"执行中断未落结果"的明确状态，不静默丢失；
- **幂等**：审批单/执行结果落库（`raw_input_hash` 去重）；重复执行有状态判定；
- **并发闸门**：`AgentConcurrencyGuard`——**单用户最大 2 个在途**、**全局最大 8 个在途**（超限排队/拒绝），防单用户烧资源 + 全局过载；
- **进程自愈**：`McpHealthMonitor` 存活监控 + 重启（默认仅告警，第 13 题风暴复盘）；
- **会话可重建**：F7 上下文重建（消息表为准，第 9 题）。

**③ 坑**
- **"执行了但没落结果"是最大盲区**：崩溃点恰在"改完数据、没写结果"之间——恢复任务必须能识别这种中间态（`approved` 无 result）；
- **恢复的幂等**：重试执行可能重复变更——执行动作本身要幂等（如 DLQ 重投按消息 id 幂等）；
- **并发闸门放哪**：放业务代码会漏；放在 Agent 入口层统一收口；
- **恢复任务自己挂**：恢复是"兜底的兜底"，要有指标 + 告警（`ai_approval_reclaimed_total` 飙升说明系统在异常）。

**④ 兜底**
- 崩溃恢复：重启后恢复任务自动扫描未完成单；无法恢复的回收为"待人工"（不假装成功）；
- 幂等：hash 去重 + 状态机流转；
- 限流：用户级 + 全局级双层；
- 观测：`ai_agent_runs_total`/`ai_tool_errors_total`/审批恢复指标 + 告警规则。

**⑤ 话术**
> "可靠性我按四层做：审批执行先落库、崩溃后有恢复任务扫'approved 没结果'的单，能重跑就重跑、不能就回收给人工，绝不假装成功；执行动作本身幂等（hash 去重）；并发有双层闸门——单用户 2 个、全局 8 个在途；MCP 进程有健康监控和自愈但默认只告警。会话本身的消息落库，崩溃后能重建上下文。"

## 追问与参考回答
**追问1：恢复任务怎么判断该重跑还是回收？** 看执行动作是否幂等 + 是否有部分成功标记；不确定就回收人工（安全侧）。
**追问2：为什么恢复延迟 120s？** 给正常执行留足时间（LLM+人工介入慢），避免把"还在跑"的当"挂了"重跑。
**追问3：并发闸门超限怎么办？** 排队/快速拒绝（明确提示），而不是无界等待。
**追问4：和传统服务可靠性的差异？** 多轮长链路 + 外部模型/工具 + 非确定性输出，所以更要"落库+幂等+恢复"，不能靠"调用成功=完成"。
**追问5：怎么验证恢复逻辑？** 故障注入：执行中 kill 进程，重启后观察恢复/回收计数与审批单状态。

## 发散追问地图（横向）
- 工作流可靠性：Temporal/Cadence、Saga、补偿事务。
- 幂等：幂等键、去重表、状态机。
- 限流：信号量/漏桶/并发闸门、舱壁隔离。
- 崩溃恢复：checkpoint、WAL、任务状态机。
- 观测：恢复/回收指标、告警、演练。

## 面试官评分点
**高级开发级**：能讲幂等+恢复+限流三件套；知道"执行与落库间隙"的坑。
**架构师加分**：先落库再执行；中间态识别（approved 无 result）；恢复的幂等；双层并发闸门；自愈保守策略。
**危险信号**：只靠重试；无幂等；把"没报错"当"成功"；恢复逻辑无指标。
