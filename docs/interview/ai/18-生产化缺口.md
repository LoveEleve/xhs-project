## 面试可讲版（五段式）

**① 业界背景**
"能跑 Demo"和"生产可用"之间有一张很长的清单：可观测（分布式追踪/LLM 观测）、安全合规（DLP/多租户）、工程化（Prompt 版本、契约测试、灰度）、SLO（首字延迟/成功率）。面试里最能拉开差距的不是"我全做了"，而是**能系统性列出缺口 + 说清优先级与补法**——这叫工程成熟度。

**② 项目选择（主动披露清单）**
xhs-ai 的生产化缺口（对照 `observability-truth-and-gaps` 报告，14 项）：
1. **分布式追踪**：零命中 OTel → **已接入**（OTel Agent → OAP OTLP → `sw_zipkin_span`，52 条 span 实测；Langfuse 语料级仍未部署）；
2. **首字延迟（TTFT）未采数**——流式体验最关键指标目前没指标化；
3. **DLP 只覆盖密钥形态**（sk-/ark-/glsa_），PII/商业数据未覆盖；
4. **多租户未做**（当前按用户，无 tenant 维度隔离/配额）；
5. **Prompt 无版本化**（改 Prompt 无版本/灰度/回滚机制）；
6. **契约测试缺失**（模型/工具接口变化靠人工回归）；
7. **只读模式（ADR-23）设计未接线**（第 17 题）；
8. **成本无实时指标**（有周报但无在线成本面板/告警）；
（其余：评测样本量、模型供应商单点、无 A/B 等，见报告 14 项）

**③ 坑（为什么没做/怎么补）**
- **优先级判断**：先在"能证明价值"的地方做深（评测/审计/幂等/自愈），OTel 这类"基础设施型"后置——但**面试要能讲清后置是选择不是遗漏**；
- **Langfuse 0 命中**：调研后评估"收益/成本不匹配"（自建 traceId+审计已够用），这类"试过决定不做"也是加分（同 RAG 题的止损思路）；
- **DLP 只做密钥**是风险最大的缺口（合规红线），补法：PII 识别（正则+模型）+ 输出侧拦截；
- **多租户**是架构级改造（隔离模型/配额/权限），补法：tenant 维度贯穿（库表/缓存键/指标标签）。

**④ 兜底**
- 缺口清单入库并定期复核（不是嘴上承认）；
- 每个缺口给出**补法与优先级**（合规类 > 体验类 > 工程类）；
- 现有兜底：审计/幂等/审批/限流已覆盖主要风险面；
- 面试策略：主动披露 + 排序 + 补法三段，避免被追问时被动。

**⑤ 话术**
> "离生产还有一张清单，我按优先级说：最急是 DLP 只覆盖密钥、PII 没做，这是合规红线；其次是首字延迟没采数、多租户没做、Prompt 没版本化、OTel 没接——OTel 和 Langfuse 我们调研过，评估收益成本不匹配暂时没上，这是选择不是遗漏；只读模式是设计完成、脚本在库、没接线的状态。补的优先级是合规>体验>工程。"

## 追问与参考回答
**追问1：为什么先做审计/幂等而不是 OTel？** 风险优先：审计/幂等防的是"数据/合规事故"，OTel 是排障效率；且 traceId+审计已覆盖主要排障需求。
**追问2：多租户怎么补？** tenant 维度贯穿：身份→权限→数据隔离（表/行）→配额（Token/并发）→指标标签；改造量在数据层。
**追问3：Prompt 版本化怎么做？** Prompt 模板入库+版本号+灰度+回滚；评测按版本跑回归；当前是代码内模板（缺口）。
**追问4：契约测试是什么？** 对模型/工具接口的 schema/行为做自动化契约校验（消费方驱动）；防供应商或工具变更导致静默破坏。
**追问5：怎么证明缺口清单不是"自黑"？** 每条有状态（未做/设计中/已调研不做）+ 补法 + 优先级；定期复核；"试过决定不做"同样有记录。
