# 第13题 | MCP 协议、白名单与去 MCP 化

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：MCP、进程隔离、工具收敛、去依赖决策、自愈监控、误报风暴

## 问题
MCP 是什么？你们怎么用 MCP？为什么后来"去 MCP 化"？

## 面试可讲版（五段式）

**① 业界背景**
MCP（Model Context Protocol）是"模型-工具"的标准协议：把外部能力（文件/命令/API）以标准 server 暴露给模型客户端。优势是生态与即插即用；代价是**进程依赖**（server 挂/慢/泄漏直接拖累 Agent）、**能力过宽**（进程/文件级权限）、**可观测性差**（黑盒）。工程决策：MCP 适合"运维直连/探索"，生产 Agent 更适合**自研受控工具**。

**② 项目选择**
xhs-ai 的演进：
- **MCP 阶段**：接入 20 个 MCP 工具，做运维直连；
- **去 MCP 化（RV27）**：Agent 运行时只用**16 个自研工具**（log_*/metric_*/es_search/知识/代码域），**MCP 子进程不参与 Agent 运行**——消除进程依赖与能力过宽风险；
- **自愈监控保留**：`McpHealthMonitor` 监控 MCP 进程（存活/重启），但**默认仅告警不重启**（`self-restart-enabled=false`）；
- **实测**：kill MCP 进程后 Agent 主链路不受影响（19s/39s 观测口径）；工具选择评测 12/12。

**③ 坑**
- **进程链误判引发重启风暴（RV19 复盘）**：MCP 经 `npm exec` 包装，进程链多级，命令行探测抖动 → 误判死亡 → 自动重启 → **NRestarts=24** 的风暴。教训：自愈默认保守（只告警），确认真死再重启 + 频率上限（max-per-hour=3）；
- **能力过宽**：MCP 文件/命令工具直接暴露给模型 = 把宿主机交给 LLM——生产必须收窄；
- **协议不是目标**：上 MCP 是为了能力，不是为协议而协议；能力可自研且更贴合业务时，去依赖是正确选择；
- **监控的生命周期**：MCP 进程由谁拉起/回收/防重复——进程管理本身就是复杂度。

**④ 兜底**
- 主链路零 MCP 依赖：MCP 全挂 Agent 仍可用（自研工具）；
- 自愈保守策略：仅告警（默认）+ 重启开关 + 每小时上限 + 确认真死；
- 工具收敛：白名单注册，能力最小化；
- 观测：MCP 存活指标 + 重启计数 + 工具调用指标。

**⑤ 话术**
> "MCP 我们用来做运维直连，但 Agent 运行时 16 个工具全是自研的——MCP 子进程不参与，这样进程依赖和能力过宽风险都消掉了，实测 kill 掉 MCP 主链路也不受影响。自愈这块踩过坑：进程链是多级包装，探测抖动导致误判重启，一小时内重启了 24 次，后来改成默认只告警、确认真死才重启、还有每小时上限。"

## 追问与参考回答
**追问1：MCP 和 Function Calling 区别？** Function Calling 是模型厂商的调用格式；MCP 是跨厂商的工具服务协议（更侧重工具侧的标准化与复用）。
**追问2：去掉 MCP 后能力怎么补？** 把运维常用能力写成自研工具（对数/指标/ES/知识/代码），更贴合业务且可控；MCP 保留给人工运维直连。
**追问3：怎么判断一个外部依赖该不该去？** 看：主链路是否依赖、故障半径、能力是否可替代、维护成本；MCP 是"可替代+风险高"的典型。
**追问4：自愈怎么避免重启风暴？** 确认死亡（多次探测+进程实际状态）再重启；频率上限；默认关闭自动重启只告警。
**追问5：进程监控怎么做？** 存活探测（pid/端口/健康）+ 指标 + 告警；重启动作要幂等（防重复拉起）。

## 发散追问地图（横向）
- 协议：MCP/Function Calling/OpenAPI、A2A、工具 schema 设计。
- 进程管理：supervisor/systemd、进程链、僵尸进程、端口冲突。
- 自愈：健康检查、重启退避、熔断、频率限制。
- 工具治理：白名单、版本、权限、审计。
- 架构：Agent 与工具解耦、Sidecar、沙箱。

## 面试官评分点
**高级开发级**：能讲 MCP 定位与代价；知道去依赖的动机。
**架构师加分**：进程链误判风暴的复盘（数值 NRestarts=24）；自愈保守策略（告警优先/上限/确认真死）；"能力 vs 协议"的务实取舍。
**危险信号**：为协议而协议；无脑自愈重启；能力过宽暴露给模型。
