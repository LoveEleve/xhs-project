# 专题：决策台账（架构 / 选型 / 方案设计 / 权衡 —— 逐项可追问）

> 用法：面试官问"为什么这么设计"时，按行回答五要素：**备选 → 选择 → 关键理由 → 代价/放弃 → 证据**；再准备"追问变体"（§五）。
> 所有数字均有报告/代码锚点（§七），不背没有出处的结论。

## 二、中间件与组件选型

| B5 | 数据同步 | 双写 / Canal / MQ 事件 | **Canal**：binlog 解耦，天然带 ts 做 **external version + tombstone**（让 ES 拒旧写）；双写一致性差 | 组件运维成本；延迟窗口 | 题库 50-Canal；缓存一致性报告 |

## 三、方案设计决策（一致性 / 消息 / 限流 / 缓存 / 长连接）

| # | 决策点 | 备选 | 选择与关键理由 | 代价/放弃 | 证据锚点 |
|---|---|---|---|---|---|
| C1 | 库存扣减 | DB 行锁 / 纯 Redis / 分桶+Lua+DB | **三级**：Redis 分桶 + Lua 原子预扣（先扣 Redis）→ DB `WHERE available>=qty` 最终防线；**最终防线必须在 DB**（Redis 全挂也不超卖） | 两本账需对账 | 手册 §C；20 并发不超卖；Redis 阻断实测 |
| C2 | 分布式事务 | Seata AT/TCC / 事务消息 / 自研 TCC | 主链走**事务消息+本地消息表**；库存专项走**自研 TCC+fence**：不引 Seata——只有一个专项链路用 TCC，TC 集群成本不划算；**fence 独立表**（Cancel 可能先于 Try，"业务行不存在"状态业务表表达不了） | 两套机制并存（明确"TCC 与分桶两本账"风险，靠对账隔离） | 手册 §D/§E；TCC 11 场景 |
| C3 | 消息可靠性 | 只用事务消息 / 只用本地消息表 / 两者 | **两者都要**：事务消息=回查锚点；本地消息表=Broker 全挂兜底 + 补发（`markSuccessByTransactionId` 消重） | 存储与代码冗余 | 手册 §E；75s 回查只扣一次 |
| C4 | 幂等 | 单层唯一键 / 多层 | **四层**：唯一索引 → 状态机条件 UPDATE → 幂等表/Token → 消费端消重；不同链路取不同层 | 各层维护成本 | 手册 §F；重复请求 0s 回放、并发 200/409 |
| C5 | 乱序治理 | 全局顺序消费 / 版本号 / 混合 | **按链路混用**（先消灭乱序源，再谈版本）：库存 eventTime(Lua 内比较) / 点赞 actionTime 版本+24h 窗口 / 购物车 CLEAR 屏障+DB 时间戳 / ES external version / Feed 已删标记 5min；**不全局顺序消费**——写扩散与计数是吞吐敏感链路 | 每链路一套语义，心智负担 | 手册 §G；乱序注入被拒实测 |
| C6 | 对账权威源 | 统一以 DB / 统一以 Redis | **按账本选**：库存/券/购物车/关注=Redis 权威（用户操作直写 Redis）；未读=DB 权威；8 个 Job 分频（未读 5min → 映射补录 5min → 本地消息 30s → 超时关单 1min → 关注 1h → 券 2 点 → 库存 3 点 → 购物车 4 点） | 口径不统一，需文档化 | 手册 §R；对账覆盖矩阵报告 |
| C7 | DLQ 治理 | 自动无限重投 / 只告警 / 三级 | **三级**：有限重试(maxReconsumeTimes=3) → DLQ → 人工审批重投（HITL）/补偿通道；毒丸识别（reentered_dlq） | 需人工介入 | 手册 §O；毒丸演练全链 |
| C8 | 限流 | 只网关 / 只服务 / 双通道 | **双通道**：网关 16 路由规则（粗粒度，扛入口）+ 服务侧 @RateLimit 40 处（细粒度）；算法 Sentinel 流控 vs Lua 滑动窗口按场景 | 两处配置需对齐（已做匹配度审计：16:16 全覆盖） | 限流审计报告；两风险登记（支付回调 5QPS / counter:get 50） |
| C9 | 缓存一致性 | 先删后写 / 延迟双删 / Canal | **延迟双删 500ms + 删缓存重试 3 次 + MQ 广播失效 + 对账兜底**；承认 **Canal 方案更优**，列为下一步 | 窗口期内可能脏读 | 手册 §B；更新→读 24ms 一致实测 |
| C10 | 计数实现 | DB 行锁 / Caffeine 本地 / Redis Set+双缓冲 | **不用 Caffeine**（多实例下各节点看到不同值，换不来分布式不一致）；点赞收藏用 **Set**（SCARD 天然幂等）+ actionTime 版本门；`CounterBuffer` 5s/500 条批量落库 | 内存占用；版本门需生产端时间戳 | 手册 §K；乱序注入被拒 |
| C11 | IM/SSE 跨实例 | MQ 广播 / Redis 订阅 / 路由表+点对点 | **一致性哈希(150 vnodes) + Redis 路由表 + 每实例专属 channel 点对点**；替代 MQ 广播（延迟+无效投递不可接受）；SSE ticket 一次性两步鉴权 | 路由表维护（心跳续期） | 手册 §I/§J；跨实例推送实测 |
| C12 | 未读数 | Redis 权威 / DB 权威 | **DB 权威**（与计数相反）：未读是"每人每会话"高基数小值，DB 更稳；Redis 只做加速 | 与计数口径不一致，需文档化 | 对账矩阵；未读 Job 5min |
| C13 | 灰度与多版本 | 不做 / 网关属性注入 | 网关灰度(+3000)/版本(+3100) 过滤器做属性注入，业务无感 | 过滤器链变长 | 手册 §Q |
| C14 | TIME_WAIT/端口耗尽 | 调内核参数 / 连接池 | 连接池化（HC5）+ 同 zone 优先 + 优雅停机（摘注册+传播等待）；内核参数为辅 | 需压测验证 | 题库 19；优雅停机实测 |
| C15 | JVM 类加载锁 | 加大线程 / 修锁竞争 | 定位类加载锁竞争（92/99 线程 BLOCKED）→ 修复后 product 1,074→4,871 RPS（4.5x）；线程池隔离防饥饿 + MDC 跨池保留 | — | JVM 报告；手册 §? |

## 六、决策原则（"你是怎么拍板的"）

1. **实测校准**：所有关键决策有数字（容量/故障/演练），不靠直觉；数字全部有报告锚点。
2. **代价显式**：每个选择写明放弃了什么（写进本台账"代价"列）——比"我们选了 X 因为 X 好"高一个层次。
3. **缺口披露**：已知缺口主动列（§四 D6/D7/D9），不藏；面试官追问到边界时直接给。
4. **先消灭乱序源，再谈版本**（C5）；**权威源按账本选，不统一**（C6）；**最终防线在 DB**（C1）——这三条是贯穿性决策哲学。
5. **不为性能盲区引入长期成本**（D3 Dubbo）：试点→数据→决策→留档，可回滚。
