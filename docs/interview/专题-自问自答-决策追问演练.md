# 专题：自问自答 · 决策追问演练（面试官视角 × 决策台账逐条拷打）

> 规则：每条四段——**【追问】**（面试官第一层）→ **【应答】**（30 秒版，带数字）→ **【杀招】**（第二层追问）→ **【兜底】**（继续追问的答法/边界/roadmap）。
> 标注：✅=有实测可扛 / ⚠️=需话术兜 / ❌=弱项（诚实认 + roadmap，别硬撑）。
> 配套：《专题-决策台账》《专题-架构专题》《答辩手册》A~S。

## 一、架构类

### Q1 服务拆分 ✅
- 【追问】15 个服务，边界怎么划的？为什么不是 8 个或 30 个？
- 【应答】三条标准：数据所有权（谁写谁负责）、独立扩容需求（如 counter 写放大独立扩）、故障隔离（交易主链与支撑域分离）。反例说明：content/comment 理论上可合并，但合并只省一次调用，换来域边界模糊，不划算。
- 【杀招】过拆了怎么收场？改一个需求要动 5 个服务怎么办？
- 【兜底】认边界成本：跨域需求用"契约优先"（接口冻结+契约测试）；团队×10 时按域分组，边界已对齐组织；真要合并，网关路由层可先做聚合 BFF 过渡。

### Q2 网关过滤器顺序 ✅
- 【追问】为什么鉴权必须在限流之前？反了会怎样？
- 【应答】顺序=安全模型：BodyCache(0) 最先（HMAC 要 bodyHash 验签）→ 鉴权(+1000) → 染色(+1200) → HMAC(+1500) → 限流(+2500) → 灰度(+3000) → 版本(+3100)。鉴权先于限流：未认证流量不占业务限流预算，否则攻击流量能把正常用户限掉。
- 【杀招】fail-open / fail-closed 怎么定的？
- 【兜底】按风险定：nonce 缓存挂了宁可放行（防误伤正常请求）；签名密钥读不到宁可拒绝（防绕过）；鉴权服务不可用 fail-closed（503 可重试，不是 401 误登出——这是 Redis 故障演练修出来的语义）。

### Q3 Dubbo 不引入 ✅
- 【追问】Dubbo A/B 只 +4.9%，这个测试可信吗？会不会测法有问题？
- 【应答】同脚本、同数据量、同实例规格，只替换调用层；结论 +4.9% 低于我们的引入阈值（20%+ 才值得加一套 RPC 治理面）。测试局限：单机仿真、没有长连接/多语言场景。
- 【杀招】流量涨 10 倍呢？会不会打脸？
- 【兜底】重评条件写死：长连接诉求 / 多语言 / 服务数>50 / 调用链 P99 被网络层主导——任一触发才重评；决策数据留档、可回滚，不是拍脑袋。

### Q4 分片键与映射表 ✅
- 【追问】为什么用 user_id 不用 order_no 做分片键？客服按订单号查怎么办？
- 【应答】用户维度是主查询路径（我的订单）；客服/风控按订单号走 `t_order_no_mapping` 映射表拿 user_id 再路由；`MappingRepairJob` 5 分钟补录，消除"写映射失败"窗口。不用基因法：订单号承担对账/回调的外部语义，改结构风险大。
- 【杀招】映射表本身不一致/丢了怎么办？
- 【兜底】映射表是广播表（每库可查）+ 对账补录；最坏情况按订单号 16 片全扫（分片数少，可接受）。分片键真要换：已有一次哈希迁移经验（682 行、双写+校验+停服 2 分钟），脚本可复用。

### Q5 Zone 多活 ⚠️
- 【追问】数据面单主，这也叫多活？
- 【应答】准确说是"接入层+应用层多活，数据面单主"：zone 级故障时接入与应用不中断、容量可叠加；数据面自动切主（RTO≈32s、本次 RPO=0）。
- 【杀招】那和主备有什么区别？
- 【兜底】区别在应用层故障域与容量（主备是 1:1 冷备，我们是 N:N 活活）；数据面多主/分片多活明确列为下一步，不吹成"异地多活"。

## 二、选型类

### Q6 RocketMQ vs Kafka ✅
- 【追问】Kafka 吞吐更高，为什么不用？
- 【应答】交易域要的是**事务消息/延迟消息/重试队列/DLQ 开箱即用**；Kafka 的"事务"是流处理事务（读-处理-写），不是"本地事务+跨系统消息"的语义，延迟消息要自研；吞吐也不是瓶颈（单库写 5,485 TPS 才是先爆点）。
- 【杀招】那 Kafka 的生态优势呢？
- 【兜底】认生态差距（Connect/Streams 我们不用）；选型按"语义匹配 + 运维成本"，不是按吞吐排行榜。

### Q7 Redis Sentinel 非 Cluster ⚠️
- 【追问】单主 ~3 万 ops，流量涨了怎么办？
- 【应答】扩容白板有演算：10× 目标 → 单主不够 → 上 Cluster（跨槽限制提前评估）；当前 Cluster 的运维与约束成本不划算，先用 Sentinel + 多 zone 数据源。
- 【杀招】Sentinel 切主会丢锁，你说业务兜底——具体兜哪个？
- 【兜底】券领取/库存类锁丢了，最终防线是 DB 唯一索引 + 条件更新（`WHERE available>=qty`）——锁只是第一道防线；"最终防线在 DB"是贯穿原则（见台账 §六）。

### Q8 ES 双用途 ⚠️
- 【追问】搜索和日志混一套 ES，不怕互相影响？
- 【应答】实测过：容器 CPU 2→6 核 + 客户端 IO 线程 4→16 后搜索 508→1,448 RPS（P99 191→61ms）；索引前缀白名单做权限隔离；日志 ILM 30 天控膨胀。
- 【杀招】资源竞争到峰值呢？
- 【兜底】认：单机仿真是折中；生产建议日志 ES 与搜索 ES 物理分离（成本换稳定），已写进缺口与 roadmap。

## 三、方案类

### Q9 库存三级扣减 ✅
- 【追问】最终防线在 DB，那 Redis 分桶的意义是什么？
- 【应答】扛并发：Redis 分桶 + Lua 原子预扣把绝大多数无效请求挡在 DB 之前；DB 条件更新是正确性底线。没有分桶，秒杀场景 DB 行锁直接成热点。
- 【杀招】Redis 和 DB 不一致怎么办？
- 【兜底】对账 Job（凌晨 3 点）以 Redis 修 DB；超时取消按 xid 冻结明细回退；Redis 阻断演练下无幽灵数据（鉴权 fail-closed + DB 条件更新兜底）。

### Q10 TCC 两本账 ✅（主动披露型）
- 【追问】TCC 和分桶两本账，出过事故吗？
- 【应答】没有出过资金/库存事故，但这是**明确登记的风险**：混用有覆盖风险，靠对账隔离。fence 独立表解决三宗罪：一刀切回退该 SKU 全部冻结 / 热 SKU 超时永远不可达 / 回退后迟到 Confirm 导致超卖。
- 【杀招】为什么不用 Seata 省掉这些坑？
- 【兜底】只有一个专项链路用 TCC，TC 集群（部署+存储+高可用）成本不划算；自研 fence 逻辑可控（约百行）+ 11 场景测试。团队大了/链路多了会重新评估。

### Q11 消息双保险 ✅
- 【追问】事务消息+本地消息表，会不会双投？
- 【应答】会——这是 at-least-once 的代价，消费端必须幂等；`markSuccessByTransactionId` 消重；换来 Broker 全挂时仍能补发。
- 【杀招】既然消费端幂等，为什么不用一个就够？
- 【兜底】两者职责不同：事务消息的回查是"本地事务↔消息投递"的原子锚点；本地消息表是"Broker 不可用"的兜底与补发源。只留本地消息表=回查语义自建；只留事务消息=Broker 挂就丢。

### Q12 缓存一致性 ⚠️
- 【追问】延迟双删 500ms 凭什么够？
- 【应答】不够（诚实），所以配了：删缓存重试 3 次 + MQ 广播失效 + 对账兜底；24ms 是"更新→读"实测，不是并发极值。**Canal 方案更优，是明确下一步。**
- 【杀招】用户看到旧数据怎么解释？
- 【兜底】读多写少场景接受秒级窗口；强一致诉求走主库读；写后立即读由 MQ 失效 + 重试压缩窗口。口径不掩饰。

### Q13 限流双通道 ⚠️
- 【追问】16 路由全覆盖，那新增路由没配规则怎么办？
- 【应答】审计结论：现有 16:16 覆盖、零误伤；但**新增路由必须同步配规则**（列入变更流程）。两个已登记风险：支付回调路径 5 QPS 可能误伤重试、`counter:get` 全局 50 可能不够。
- 【杀招】支付回调真被限了怎么办？
- 【兜底】回调路由应单独放行或提阈值（风险已登记待调）；另外限流 fail-open 策略保证缓存类组件故障不误伤。

### Q14 DLQ 人工审批 ✅
- 【追问】半夜死信没人批怎么办？
- 【应答】重投必须审批（危险变更），但告警会发（P1）；非紧急可等，毒丸本来就不该自动重投；自动补偿通道与人工重投分开。
- 【杀招】那"积压 8 小时 P1 空转"那次怎么发生的？
- 【兜底】事故复盘：09-17"清理"只归档未删 + 指标恒 0（无 0 基线，`increase()` 算不出）→ 修复：动态发现消费组（消除 15× 告警重复）、0 基线预注册、规则改 `increase([10m])`；教训"归档≠删除"。

### Q15 对账权威源 ✅
- 【追问】为什么库存以 Redis 为准而不是 DB？这不是反直觉吗？
- 【应答】按账本选，不统一：库存/券/购物车/关注——用户操作直写 Redis，MySQL 只是异步落盘副本，Redis 是实时真相 → 以 Redis 修 DB；未读相反（每人每会话高基数小值）→ DB 权威。8 个 Job 分频调度（未读 5min → 本地消息 30s → 关单 1min → … → 库存 3 点）。
- 【杀招】Redis 数据真丢了怎么办？
- 【兜底】Redis 持久化（AOF/RDB）+ 对账修复 + 极端情况 DB 快照重建；这是登记过的边界（未做 Redis 备份审计）。

## 四、权衡类

### Q16 服务侧熔断未配 ⚠️
- 【追问】你讲高可用，但服务侧没有熔断规则？
- 【应答】认：目前只有网关 gw-flow 规则；服务侧靠 Feign 分级超时 + 52 处降级点 + 线程池隔离（聚合链路在 4s 慢下游下 3.0s 准时降级）。
- 【杀招】某服务慢调用会不会拖垮上游？
- 【兜底】超时是底线、熔断是优化：慢调用被超时+隔离挡在局部；熔断规则补齐已列 roadmap（热点服务优先）。

### Q17 F-001 直连暴露 ✅（事故型）
- 【追问】服务端口直连可达，绕过网关怎么办？
- 【应答】网关侧有"信任过滤"剥离外部伪造的直连 JWT；F-001 曾因双 `StringRedisTemplate` 注入歧义（`getIfAvailable()` 抛 `NoUniqueBeanDefinitionException` 被吞）导致该逻辑**全线失效**——已用 `@Qualifier` 修复并 5 场景验证（覆盖生效/吊销拒绝 400+审计/内部调用/网关流量）。
- 【杀招】怎么发现的？还会不会有同类？
- 【兜底】靠演练（直连伪造 header）发现，不是靠读代码；同类风险用"注入歧义扫描 + 启动期 bean 断言"防复发；残余风险（端口暴露面）网络层收敛，已登记。

## 五、横向压力题

### Q18 仿真边界 ✅（诚实型）
- 【追问】这些数字都是单机仿真的，能代表生产吗？
- 【应答】不能完全代表。仿真的价值在**相对比较**（网关 vs 直连 10× 差距）、**瓶颈定位**（先崩哪层）、**机制验证**（故障注入/对抗）；生产还差真实流量分布、多租户噪声、长期稳定性。所有口径都标注"单机仿真值"。
- 【杀招】那面试官凭什么信？
- 【兜底】信方法不信绝对数：实测校准 + 可复现脚本 + 报告留档（`docs/reports/` 全部可查），任何数字能现场翻证据。

### Q19 单人开发 ✅（诚实型）
- 【追问】15 个服务一个人做，质量怎么保证？
- 【应答】六层测试矩阵（65 单测/契约、IT 6、E2E 12、评测 50、红队 8、压测 4 场景）+ 门禁脚本 + RV01~RV29 评审；用"红队 + 故障注入"替代外部评审视角。
- 【杀招】和真实团队开发的差距？
- 【兜底】认：缺跨人 code review 与长期演进；补偿是决策文档化（ADR/决策台账）+ 证据链可复现。面试讲"架构验证实践"，不冒充"团队生产系统"。

### Q20 如果重来 ✅（反思型加分）
- 【追问】哪些决策你会改？
- 【应答】三条：① 缓存一致性第一天就上 Canal（省掉延迟双删的心智负担）；② 分片第一天就用哈希（避免 75% 倾斜后的迁移）；③ 服务侧熔断/限流与网关规则同批上线（别等审计才发现缺口）。
- 【杀招】为什么当时没这么做？
- 【兜底】信息不足：Canal 的收益要在一致性事故后才显性；分片倾斜要真实数据分布才暴露；熔断优先级被"能跑通"压过——这正说明"实测驱动"的必要性。
