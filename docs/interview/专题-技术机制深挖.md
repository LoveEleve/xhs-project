# 专题：技术机制深挖（跨服务证据链版）

> 与 53 题的关系：单题讲"机制是什么"，本稿讲"**机制之间的连接**与**真实运行证据**"，重点是边界与易错点。
> 实测：2026-09-18；证据来源：E2E 链证据 JSON、MySQL 运行时表、代码位置。
> 关联题：04/05/06/07/15/18/21/27、45（Redisson）、47（Sentinel）。

## 机制一：事务消息全链（下单）

| 层 | 事实 | 证据 |
|---|---|---|
| 半消息 | 先发 half message，不投递 | `OrderService.java:231` |
| 本地事务 | INSERT t_order + t_order_item + t_local_message 同一 DB 事务 | `OrderTransactionListener.java:57-84` |
| 运行证据 | t_local_message：`ORD2026091823311662515370029, status=1, retry_count=0` | 实测库 |
| 消费预扣 | COMMIT 后消费者才去预扣库存 | Listener 注释 :27 |
| 回查 | Broker 60s 未裁定 → 查 t_local_message（与订单同事务，比查订单表索引更快） | Listener:103-134 |
| 防双投 | 本地事务成功后标记本地消息，30s 补发 Job 不再发 | `OrderService.java:255` |
| **易错点** | 预扣幂等键 = `fold-hash(orderNo)` 派生的 **pseudoOrderId**（负 Long，实测 `-8632101930510234040` 形态）；释放/回补必须用同一派生值，否则库存泄漏 | `OrderService.java:530-545`、t_inventory_prededuct_idem |

**3 连拷打**：① 回查为什么查本地消息表不查订单表？→ 同事务写入状态一致 + transactionId 索引。② 双投怎么防？→ markSuccess 标记 + 消费端幂等双保险。③ 消费端挂了呢？→ 消息重试 + LocalMessageRetryJob + 对账。

## 机制二：幂等体系分层（四个层次，各管一段）

| 层 | 位置 | 手段 | 证据 |
|---|---|---|---|
| L1 入口 | 下单 | `bizIdentifier + SET NX`（24h） | OrderService:112 |
| L2 消息 | 所有消费者 | `MessageIdempotentHelper`（msgId, 24h） | 06 题 |
| L3 资源 | 券/库存 | 乐观锁 `WHERE status=0`、预扣幂等表 | OrderService:264 |
| L4 回调 | 支付 | Redis SETNX + Redisson 锁 + DB 乐观锁 | PaymentService:134/157/285 |

> 边界：**锁是效率工具，幂等是正确性终线**（01 题口径）；四层任何一层都不假设上层可靠。

## 机制三：支付→订单的三级兜底（本稿最有料的一段）

```
Feign 同步 notifyPaySuccess（主）
  └─ 失败/503 → PAY_RESULT_TOPIC（order 侧 PayResultConsumer 兜底1）
       └─ 仍失败/未收敛 → XXL-Job paymentNotifyCompensateJob 扫 status=1 超窗重发（终兜底）
```

- 业务拒绝（如已退款）**不发 MQ**，避免退款后乱序误处理（`PaymentService.java:350-362`）。
- **发现的漂移**：代码注释写"PAY_RESULT_TOPIC 当前无消费端"，但 `PayResultConsumer` 实际存在——注释未随实现更新。面试可讲："文档/注释与实现漂移是常态，我们用对账和可观测兜住这类认知差"。
- 退款同构：Feign 同步 + `REFUND_RESULT_TOPIC`（`RefundResultConsumer`：已退款+释放库存+退券）。

**3 连拷打**：① 为什么不全走 MQ？→ 同步链路给用户及时反馈，MQ/Job 是补偿面。② 业务拒绝为什么要区分？→ 退款后重放支付成功会导致状态回退。③ 怎么证明兜底真的跑过？→ DLQ 指标 + 对账任务 + Job 执行记录。

## 机制四：TCC fence（资源侧三异常）

- 表证据：`t_tcc_fence`（xid/branch_id/action_name=tryDeductStock/status）、`t_tcc_freeze_detail`、`t_inventory_compensation`。
- 实测 fence 行：`test:1789727311404 / branch 1 / status 2`、`branch 2 / status 3`（空回滚/悬挂拦截状态）。
- 细节与 11 场景见 04 题；本稿只补"fence 与事务消息的接缝"：**事务消息管消息与本地库的原子，TCC fence 管跨服务资源的幂等**，两者中间靠"消费端预扣 + pseudoOrderId"衔接。

## 机制五：缓存 × 读写分离的可见性窗口（实测）

- 退款后 +2s：订单详情 API `status=3`（旧）；+3s：库存 API `75`（旧）；终态 master=5 / 库存=77，API 随后一致。
- 机制拆解：① 退款链路本身异步（Feign+MQ 兜底）；② 订单详情 SELECT 走从库（`ReadWriteRoutingInterceptor`，21 题），叠加复制延迟。
- 面试口径：**能够说出"窗口从哪里来、多大、谁来兜"** 比"强一致"更可信；对账任务（18 题）就是窗口的兜底。

## 机制六：通知事件管道（幂等 + 反自扰）

- 消费：`NotificationEventConsumer` → msgId 24h 幂等 + 聚合窗口 SETNX 防重复创建（通知表无天然唯一键）。
- 反自扰：`senderId == targetUserId` 直接跳过（自己评论自己不发通知）。
- 实测：跨用户评论 → 1 条 type=2「评论通知」✓。
- **订单域已接入**（2026-09-18 修复）：`OrderNotificationPublisher` 在支付/发货/退款三处埋点（MQ 异步不阻塞交易）；
  因 `uk_aggregate(user_id,type,target_id,notify_date)` 约束，同一订单当天聚合为一条并**刷新为最新状态**（标题"订单通知"，不再社交化"等 N 人"）。

## 机制七：traceId 全链路（HTTP/Feign/MQ/线程池/定时器，运行时证据）

- 六个 MQ Header 透传（`X-Trace-Id/User-Id/Gray-Tag/Api-Version/AB-Group/Pressure-Test`）；消费端 `restoreTraceContext` 恢复，线程池 `MdcAwareExecutorService` 快照传递。
- 实测：下单链 6 服务共享同一 trace（gateway→order→product→inventory→coupon→user）；**延时关单消息 30 分钟后消费仍带创建时的 trace**；`order-async` 42/42 行带 trace。
- 深挖修复的三处断链（2026-09-19）：
  1. 退款回调跑在 `@Scheduled` 线程 → 整链 trace=None → 新增 `TraceContextHolder.startNewTrace()` 逐单开链；
  2. `asyncSend` 回调（Netty 线程）日志丢 MDC → 捕获 traceId + `withTrace` 临时恢复；
  3. Feign/MQ 双通道并发退款 → 乐观锁异常 500 + 支付误补偿 → 幂等 catch（已退款返回 true）。
- 报告：`docs/reports/traceid-fullchain-evidence-20260919.md`。

## 机制组合矩阵（谁负责什么，别串岗）

| 问题 | 机制 | 不用的原因 |
|---|---|---|
| 消息与本地库原子 | 事务消息 + 本地消息表 | 普通消息会"订单成了消息没发" |
| 消费重复 | 幂等 helper + 资源乐观锁 | 依赖 MQ exactly-once 不现实 |
| 跨服务资源占用 | TCC + fence | 纯本地锁跨不了服务 |
| 支付结果可靠送达 | Feign→MQ→Job 三级 | 单通道都有单点 |
| 读到旧值 | 接受窗口 + 对账 | 强一致代价高、需求不要求 |
| 防重复通知 | msgId + 窗口锁 + 自扰跳过 | 通知表无唯一键 |
