# 面试故事卡 · 三个"假"

> 用途：面试官问"讲一个你排查过最难的问题 / 踩过什么坑"时用；也可在被追问"发布/配置/告警怎么做的"时展开。
> 共同主线：**以为做了 ≠ 真的做了——三件事的共同根因都是"缺少'真的生效'的验证机制"，根治方式都是"加一个能证伪的校验"。**
> 注意：本卡只用于面试口述，不写进简历。

---

## 卡 1 · 发布"假成功"

**30 秒版（先背这个）**
> 最值钱的一次是发布"假成功"：旧进程占着端口、新进程根本没起来，健康检查却打到了旧进程上，脚本报"发布成功"；还有 setsid 包装导致 `$!` 不是真实 java PID，PID 校验也形同虚设。后来改成：端口占用者精确清理、以实际监听者回写 PID、校验**监听 PID == 本次启动 PID**——发布才敢说真的成功了，回滚也必须走同样校验。

**追问链**
| 追问 | 应答 |
|---|---|
| 怎么发现的？ | 批次重启后核对：健康检查通过但版本行为没变；查端口占用者和进程 PID，发现旧手工进程还在服务、新进程压根没起来。 |
| 两类假成功分别是什么？ | ① 旧进程占端口 → 新进程起不来 → 健康检查打到旧进程；② `nohup setsid java &` 的 `$!` 是包装进程 PID（setsid 会 fork），PID 校验失效。 |
| 为什么健康检查不够？ | "看到活的" ≠ "看到新的"——回滚逻辑依赖"新版本是否真的在服务"，不校验 PID 的话回滚永远不会触发。 |
| 端口清理会不会误杀？ | 清理前校验占用者是不是本模块的 app.jar（防误杀其他服务），再 ensure_port_free。 |
| 多实例怎么处理？ | 多实例用最新构建 + 逐个回写真实监听 PID；发布包保留 3 版便于回滚。 |
| 回滚呢？ | 回滚也是发布——同样走健康校验 + PID 校验，否则"回滚成功"也可能是假的。 |

**证据**：`scripts/release-service.sh`（版本目录/软链/健康校验/回滚/PID 校验/端口清理/多实例/保留 3 版）；`interview/xhs/37-CICD与发布.md`；review 记录（0.55s 假恢复）。
**口径**：单机 27 容器环境；未做蓝绿（release 为停旧起新）。

## 卡 2 · 配置"假生效"（Nacos 死配置）

**30 秒版**
> 配置中心接入最经典的坑：15 个服务的 `shared-configs` 全是**死配置**——Spring Cloud 2020+ / SCA 2021+ 起 bootstrap 默认关闭，旧写法不再生效，服务其实一直靠本地 yml 在跑，"配置外置"只是写了没生效。排查从网关引用了一个 Nacos 里根本不存在的配置文件（404）开始，改成 `spring.config.import: optional:nacos:` 并补齐命名空间后，Nacos 侧请求从 code=300 变 200，15/15 服务出现 `Load config success`。

**追问链**
| 追问 | 应答 |
|---|---|
| 怎么发现的？ | 运维巡检发现网关引用的 common/gateway 配置在 Nacos 命名空间不存在（404）；再看部署包里 3 个待导入配置从未导入；深挖发现 14 个服务有依赖、有 shared-configs，但没有 bootstrap starter、没有 spring.config.import。 |
| 根因一句话？ | SCA 2023.0.1.2 用新式 config data 机制，bootstrap 上下文默认关闭，`shared-configs` 静默失效——**不报错，只是不生效**，所以一直没被发现。 |
| 为什么没早发现？ | 因为本地 yml 有兜底值，服务能正常跑；这正是最危险的地方——"写了没生效"没有任何报错。 |
| 修复为什么用 `optional:`？ | 保证 Nacos 不可用不阻塞启动（本地 fallback 仍在，回滚零风险）。 |
| 首次接线后为什么还失败？ | 14 个服务的 config 命名空间没配（只有 discovery 配了），默认落到 public → 查空 code=300；补 namespace 后才 200。 |
| 怎么证明真的生效了？ | 三层证据：Nacos 侧连续 15 次 get code=200 md5 一致；应用日志 15/15 `Load config success` + `Listening config`；15/15 服务 UP。 |
| 有没有行为变化？ | 零行为变化——导入的值与本地 fallback 一致，纯机制生效（切换可回滚、无风险）。 |

**证据**：`reports/nacos-config-externalization-20260918.md`；`scripts/nacos-import-configs.sh`；`interview/xhs/44-Nacos深度拷打.md`。
**口径**：Nacos standalone 无鉴权、密码明文为已知债；未做热更新演练（`refreshEnabled=true` 已开）。

## 卡 3 · 告警"假通知"（通知黑洞）

**30 秒版**
> 更险的一次：Prometheus 31 条规则全在跑，但 Alertmanager 的 receiver 是空的 `default-noop`——所有告警被静默丢弃，仓库里的 webhook 还是占位地址。**告警没通知等于没有告警**。后来做了本地落地器 alert-sink（落盘 jsonl + send_resolved），并用端到端演练验证：注入 `SELECT SLEEP(600)` → 规则 firing → Alertmanager active → sink 落盘 → 清理后收到 resolved。

**追问链**
| 追问 | 应答 |
|---|---|
| 怎么发现的？ | 做告警链路"端到端演练"时发现的——不是等出事，而是主动验证"告警发出后有没有人收到"。 |
| 为什么危险？ | 规则、指标、看板都是好的，只有最后一跳断了；出事时才会发现没人知道——最典型的"以为有监控"。 |
| 落地器怎么做的？ | Python 单文件 systemd 服务（:19099）→ `/data2/logs/alerts.jsonl` + 可读日志；接企微/飞书只需换 receiver（本地无凭据）。 |
| 怎么验证的？ | 注入慢查询 → 指标 >60s → 规则 firing → Alertmanager active → sink 落盘（22:34:25 [firing]）→ 清理后收到 resolved（受 `group_interval=5m` 影响延迟约 5 分钟）。 |
| 还有什么告警坑？ | 短命告警被 `group_wait` 吞掉 → 加 `keep_firing_for`；元监控 Watchdog；SLO 错误预算 43m12s/30 天 + Burn Ledger。 |
| 顺带补了什么？ | 4 条 MySQL 规则（连接使用率 >80% / 复制延迟 >30s / 长查询 >60s / 应用连接 >250）——就是当日 459/500 连接、177s 延迟、318 条挂 64 分钟的真实背景。 |

**证据**：`reports/alerting-e2e-20260917.md`；`ops/alert-runbook.md`；`interview/xhs/52-Prometheus监控栈深度拷打.md`。
**口径**：单机环境；IM 通知未接（落盘方案可平滑替换）；EsClusterNotGreen 长期 firing 属单节点副本问题（建议副本数 0）。

## 三卡共同话术（收尾用）

> "这三个故事其实是同一个问题：**'以为做了'和'真的做了'之间，差一个能证伪的验证**。发布要校验监听 PID、配置要校验 Load success、告警要端到端演练——我现在做任何机制接入，都会先想'我怎么知道它真的生效了'。"

## 使用建议

- **触发时机**：面试官问"最难的排查 / 踩过什么坑 / 怎么保证发布可靠 / 配置中心怎么用的 / 监控怎么做的"——直接抽对应卡。
- **节奏**：先给 30 秒版（只讲现象 + 根因 + 根治），等追问再展开表格里的细节。
- **别一次讲三个**：问哪个讲哪个，收尾时用共同话术带一句"这类'假生效'问题我踩过三个"，显体系化。
