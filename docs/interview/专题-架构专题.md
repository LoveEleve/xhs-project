# 专题：架构专题（容量 / 高可用 / 选型演进，基于实测）

> 用法：面向白板题与"系统怎么设计/怎么扛"类追问，所有数字均来自项目实测报告（文末索引），不引用简历口径之外的数。
> 关联题：14/18/19-26/35-38/40-53。

## 一、架构全景（15 服务 + 1 AI，边界与通道）

```
客户端 ── 19000 gateway（鉴权/HMAC/限流/灰度/版本，8 过滤器）
   ├─ 同步（Feign + LB）：user / product / search / cart / coupon / order / payment / inventory / content / home / notification / im / counter / analytics
   ├─ 异步（RocketMQ）：ORDER_TRANSACTION / PAY_RESULT / REFUND_RESULT / ORDER_CLOSE / ORDER_COMPENSATION / NOTIFICATION / 计数事件
   └─ 数据面：MySQL（order 4 库×4 表分片）+ 从库；Redis（业务 6379 + 缓存 16380 + 双主 6381 + Sentinel）；ES（业务 19200 / APM 19201）；Canal（MySQL→ES）
   xhs-ai（19020，独立栈）：AgentScope + 模型网关 + HITL + 评测，OTel→OAP
```

- **分层原则**：交易域（order/payment/inventory/coupon）强一致优先；内容/推荐域最终一致优先；通知/计数/分析可丢可重。
- **依赖方向**：交易域内 order 是编排者（Feign 调用库存/券/支付），其他域不回调 order；跨域一律事件化。

## 二、容量与性能（实测）

| 对象 | 实测 | 报告 |
|---|---|---|
| product 单接口 | **4,871 RPS** | `platform-loadtest-20260917.md` |
| comment 单接口 | **4,418 RPS** | 同上 |
| home 聚合接口 | **1,861 RPS**（分层聚合+降级） | 同上 |
| search（ES 调优后） | **508 → 1,448 RPS** | `comment-sql-tuning-20260917.md` |
| 同区优先收益（25ms netem，跨区 RTT +100ms） | 吞吐 **+34.1%**、P99 **-40.9%**、平均延迟 **-49.3%** | `zone-same-zone-benefit-20260918.md` |
| SkyWalking agent 开销 | ≈**5.4%**（7,439 vs 7,863 RPS） | `skywalking-overhead-20260918.md` |
| 压测隔离 | `ShadowTableInterceptor` + `X-Pressure-Test` 影子表 | xhs/22 |

- **瓶颈分析方法**（可口述）：固定资源 → 单接口跑满 → 找饱和度拐点（CPU/GC/连接池/锁）→ 逐项调优（SQL/索引/缓存/ES refresh）→ 影子表让压测数据不污染生产表。
- **容量模型口径**：按"实测单机 RPS × 实例数 × 安全系数"估算；下单等写链路受库存行锁/DB 写能力约束，不能按读接口线性放大。

## 四、一致性架构（分场景选择，不追求全局强一致）

| 场景 | 机制 | 兜底 |
|---|---|---|
| 订单落库 × 消息投递 | 事务消息 + 本地消息表 | 回查 + LocalMessageRetryJob |
| 跨服务资源 | TCC + fence | 补偿消息 + 对账 |
| 支付/退款结果 | Feign 同步 + MQ 兜底 | XXL-Job 扫描补偿 |
| 缓存 vs DB | 双删 + 逻辑过期 + 单飞 | Canal 回声保护、对账 |
| 分片/从库读取 | 接受秒级窗口 | 对账任务（6 个）+ 人工修复入口 |

> 面试主线：**"能强一致的只有单库单机事务；跨服务一律最终一致 + 对账；窗口大小要能报出来"**（本链实测秒级，见《业务全链路推演》4.2）。

## 五、选型与演进（为什么是这些组件）

| 决策 | 理由 | 代价/边界 |
|---|---|---|
| RocketMQ 而非 Kafka | 事务消息/延迟消息/重试队列开箱即用 | 社区生态小于 Kafka |
| Nacos（AP 注册 + 配置） | 注册配置一体、namespace 隔离 | 配置外置曾"假生效"，已修复并加巡检 |
| Redisson 只做合理场景 | 直连锁显式租期，未启用看门狗自动续期 | 不用 Redlock（1/14 题口径） |
| 不引入 Dubbo | 现有 Feign + LB 满足同步调用，多一套 RPC 治理成本不划算 | 长连接/多语言场景才会考虑 |
| ShardingSphere 4×4 | order 按 user_id 分片，容量线性扩展 | 跨片查询/聚合成本；无 rehash 方案 |
| SkyWalking + Prometheus + ELK | APM（trace）/指标/日志三件套职责分离 | agent 开销 5.4% 已实测可接受 |
| xhs-ai 独立栈 | 与交易域故障隔离，模型调用不影响主站 | 双栈运维成本（已用脚本化收敛） |

**实测校准锚点（2026-09-19）**：单库写 5,485 TPS（三表事务 1,898）；网关真实代理 2,375 RPS（直连 7,636 → 网关是首先被打爆的一层）；Redis 无 pipeline 28-29k ops/s（Lua 23-25k，P=16 上限 246k）。详见 `docs/reports/capacity-model-20260919.md` §八。

**"如果重来/扩容 10 倍"白板话术**（演算详见 `docs/reports/capacity-model-20260919.md`）：
1. **先算在途**：`在途 = RPS × P99`（product 244 / comment 309）→ 线程池与池化配置先对齐，否则扩实例也排队；
2. **扩应用**：`实例数 = 目标RPS / 单机实测 × 1.5`（product ≈15 实例、comment ≈14 实例）；
3. **定位数据面硬墙**：comment 10× 后需要 ~1,060 个 DB 连接 > 上限 500 → 必须先按 note_id 分片/读副本；ES 1,448/节点 → 10× 要 ≥10 节点；Redis 单主 ops ≈10× 目标 → 上 Cluster；
4. **写链路先拆物理库**：order 现在是 1 实例扛 4 个逻辑库，第一步拆 4 物理实例，再 4→8 分片；
5. 一致性窗口全部纳入对账 SLO；直连端口下线（只留网关入口）。
