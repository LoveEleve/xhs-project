# 第32题 | 购物车：三结构协同、CLEAR 屏障与匿名合并

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：Hash+Set+ZSet、hash tag、7 Lua、CLEAR 屏障、同毫秒序号、匿名合并、Redis 丢失恢复

## 问题
购物车怎么存？多结构怎么保证原子？清空和并发写冲突怎么办？Redis 丢了怎么办？

## 面试可讲版（五段式）

**① 业界背景**
购物车是典型的"高频写 + 多结构"场景：数量、选中态、排序是三种访问模式，Hash/Set/ZSet 各司其职；但多 key 操作在 Redis Cluster 下要保证同 slot（hash tag），原子性靠 Lua 或事务。难点：**清空与并发写**（CLEAR 与 ADD 竞态导致"清空后幽灵条目"）、**匿名转登录合并**（幂等）、**Redis 丢失恢复**（缓存当权威就要兜底）。

**② 项目选择**
- **三结构协同**：Hash（skuId→数量）+ Set（选中态）+ ZSet（加购时间排序），Key 用 `{userId}` hash tag 保证同 slot；
- **7 个 Lua 脚本**：加购（检查上限 50 品种/单 SKU 99 件 + HINCRBY + 截断 + SADD + ZADD 一次往返）、删除（HDEL+SREM+ZREM 三结构原子）、勾选/全选、改数量、清空、合并；
- **Redis 为权威 + MQ 异步落库**：事件流水（`CartSyncConsumer`/`CartEventSinkConsumer`）异步持久化 MySQL，防 Redis 故障丢数据；
- **CLEAR 屏障（C-05）**：清空时写 `cleared` 标记 + `clearBarrierTs`；并发 ADD 的事件若早于屏障 ts 会被落库侧跳过——**防止"清空后旧事件回灌"**；同毫秒用 **EVENT_SEQ 单调序号**（plusNanos）保证严格递增不被误判；
- **匿名合并**：登录时合并匿名车——**取 max 数量**（幂等，多次合并结果一致），且**校验 SKU 存在性**（幽灵条目不进车，G3-02-15）；匿名车前端清除（30 天过期）；
- **Redis 丢失恢复（P2-7）**：items 为空但有 `cleared` 标记 → 空车（用户真的清空了）；没有标记 → **从 MySQL 恢复并回写 Redis**；
- **对账**：`CartReconcileJob` 凌晨 4 点 Redis↔MySQL 以 Redis 为准。

**③ 坑**
- **清空竞态**：CLEAR 与 ADD 并发——没有屏障会出现"清空后条目又回来"或"落库顺序颠倒"；屏障 + 序号解决；
- **同毫秒事件**：毫秒时间戳相同，落库侧判"旧事件"误跳过——用单调序号补足纳秒精度；
- **匿名合并的重复**：合并请求重放会重复叠加——取 max 而非累加，天然幂等；
- **Redis 当权威的风险**：Redis 被驱逐/切主丢数据——必须有 DB 恢复 + 对账；本项目做了"无标记才恢复"的区分（避免把用户真实清空误恢复）；
- **Cluster 多 key**：不加 hash tag 直接 CROSSSLOT；三结构同用户必须同 slot。

**④ 兜底**
- Redis 丢失：有标记→空车；无标记→DB 恢复回写；
- 合并异常：幂等（max）+ SKU 校验；幽灵条目不进车；
- 落库失败：事件重试 + 对账收敛；
- 观测：事件 lag、恢复次数、对账差异。

**⑤ 话术**
> "购物车是 Hash 数量、Set 选中、ZSet 排序三结构，用 userId 做 hash tag 保证集群同 slot；加购、删除、清空这些多 key 操作都在 Lua 里原子完成，上限 50 种、单品 99 件。清空和并发写用 CLEAR 屏障加同毫秒单调序号解决，防止清空后旧事件回灌。Redis 是权威、MQ 异步落库，丢了先看有没有 cleared 标记——真清空就返回空车，否则从 MySQL 恢复回写。匿名合并取 max 保证幂等，还会校验 SKU 防止幽灵条目。"

## 追问与参考回答
**追问1：为什么用 Redis 当权威而不是 DB？** 购物车高频写、低价值、可容忍极小丢失；Redis 性能支撑，DB 作为持久化与恢复源；对账兜底。
**追问2：CLEAR 屏障具体怎么判？** 事件带 clearBarrierTs；落库侧比较事件 ts 与屏障——早于屏障的旧 ADD 事件跳过。
**追问3：匿名合并为什么不累加？** 用户可能反复触发合并（重试/多端）；累加会翻倍；max 语义符合"合并同一个车"的直觉且幂等。
**追问4：Redis 恢复会不会把用户清空的购物车又拉回来？** 有 cleared 标记保护——标记存在说明用户主动清空，返回空车；只有"无标记且 items 空"才判定为数据丢失并恢复。
**追问5：购物车需要缓存吗？** 它本身就是缓存形态（Redis 权威）；商品详情在展示时批量查 Product，失效商品标记出来。

## 发散追问地图（横向）
- Redis 结构设计：Hash/Set/ZSet 选型、大 key 拆分、hash tag。
- 原子性：Lua vs MULTI/EXEC vs Redisson、脚本复用（EVALSHA）。
- 一致性：异步落库/事件流水、CLEAR 屏障、对账。
- 缓存权威化：可容忍丢失的边界、恢复策略、降级。
- 电商语义：合并规则、失效商品、勾选金额计算、限购。

## 面试官评分点
**高级开发级**：能讲三结构与 Lua 原子；知道 hash tag。
**架构师加分**：CLEAR 屏障 + 同毫秒序号的竞态处理；"有标记才不恢复"的恢复判定；max 合并的幂等论证；Redis 权威的边界与兜底。
**危险信号**：多 key 操作不加原子保证；清空竞态没考虑；合并累加；Redis 丢失无恢复。
