# 第31题 | 优惠券：单 Lua 原子领券、Outbox 与退券语义

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：单 Lua 原子、hash tag slot、同步 MQ + 回滚、Outbox 补发、退券语义修正、限领防绕

## 问题
优惠券怎么防超发？领券和落库怎么一致？退券怎么处理？

## 面试可讲版（五段式）

**① 业界背景**
券系统的两个核心问题：**超发**（热点抢券，校验+扣减必须原子）和**一致性**（Redis 扣了、DB 没落）。原子性靠 Lua（单脚本多 key 操作）；一致性有两条路——同步落库（失败回滚）或异步 + Outbox 补偿。退券/核销是状态机语义问题，**口径错了会造超发敞口**。

**② 项目选择**
- **单 Lua 原子领券**：一个脚本里做完"查库存 → 查限领 → 扣库存 → 记领取次数"，**没有中间态**；Redis Key 用 `{templateId}` 做 **hash tag** 保证 Cluster 下同 slot（否则 CROSSSLOT 报错）；
- **同步 MQ 而不是异步**：领券成功后**同步**发 MQ 落库——异步失败会出现"Redis 已扣、MySQL 永远不落"；同步失败可以**立即回滚 Redis 库存**（`return_coupon.lua`）；~2ms 开销换一致性；
- **Outbox 兜底**：同步发失败不是终局——`claimNo`（UUID）先写 **Outbox 表**（唯一键幂等），`CouponOutboxSenderJob` 扫未发送记录补发（`markOutboxSent`）；
- **退券语义（RV30 修正）**：退券只把"用户券状态"恢复为未使用——**不回补模板 stock/remain**、不减少 claimed。原因：核销不扣 remain，若退券回补会形成 `remain+已发>total` 的**超发敞口**，且用户可"领→用→退→再领"绕过限领；
- **任务**：`CouponExpireJob`（过期）、`CouponOutboxSenderJob`（补发）、`CouponReconcileJob`（对账）；
- **幂等**：msgId 去重 + 唯一键（`uk_claim_no` 等）两层。

**③ 坑**
- **异步落库是坑**：最初也有人觉得"MQ 不会丢"——但发送失败=永久不一致；改同步 + 回滚后，极端失败还有 Outbox 兜底；
- **退券回补会造超发**：RV30 之前退券回补库存，`remain+claimed` 守恒被打破；修正后语义是"券归还未使用，库存不回补"；
- **限领绕过**：领→用→退→再领，如果退券减少 claimed，perUserLimit 形同虚设；所以 claimed 不回退；
- **Lua 多 key 跨 slot**：Cluster 下不加 hash tag 直接 CROSSSLOT；本项目的 `{templateId}` 是必须的不是优化；
- **Outbox 不是"发了就行"**：要标记已发送 + 补发任务 + 对账，否则 Outbox 表会无限增长/重复发。

**④ 兜底**
- 领券失败：Lua 原子拒绝（无中间态可回滚）；
- MQ 失败：立即回滚 Redis + Outbox 补发；
- 补发重复：唯一键/claimNo 幂等；
- 终线：`CouponReconcileJob` 对账（Redis vs DB）；
- 观测：领取/回滚/补发次数、Outbox 积压。

**⑤ 话术**
> "领券是一个 Lua 脚本原子完成查库存、限领、扣减、记次数；Key 用 templateId 做 hash tag 保证集群同 slot。落库用同步 MQ 不用异步——异步失败会 Redis 扣了 DB 不落；同步失败立即回滚 Redis，极端情况还有 Outbox 表加补发任务兜底。退券我们改过一次语义：不再回补库存、不减少已领次数，只恢复用户券状态——否则会出现 remain 加已发大于 total 的超发敞口，还能'领用退再领'绕过限领。"

## 追问与参考回答
**追问1：为什么同步 MQ 不担心性能？** 领券 ~2ms，Lua ~0.1ms；抢券场景 QPS 经限流控制，2ms 可接受；一致性优先。
**追问2：Outbox 和事务消息区别？** Outbox 是本地表 + 定时补发（自实现事务消息）；事务消息是 Broker 回查机制。目的相同：本地事务与消息发送原子化。
**追问3：退券为什么不回补 remain？** 核销本来就不扣 remain（核销=用户券状态变化），退券回补会双算；守恒口径按"total = remain + 已领取未使用 + 已使用 + 已退回（不可再发）"设计。
**追问4：热点券抢购怎么扛？** Lua 原子 + 库存预热 + 限流 + 领券结果同步返回；更极端可分段库存（类似库存分桶）。
**追问5：券过期怎么处理？** 定时任务扫描过期券（Redis + DB 双维度），过期券不可用；对账任务校验状态。

## 面试官评分点
**高级开发级**：能讲 Lua 原子领券与同步回滚；知道 hash tag。
**架构师加分**：退券语义修正的完整推导（超发敞口 + 绕限领）；Outbox 与同步发送的分层；Cluster slot 的实操认知。
**危险信号**：异步落库无兜底；退券回补库存；多 key Lua 不加 tag；限领可绕过。
