# 第09题 | IM 长连接跨实例路由

> 难度：★★★★☆｜频率：★★★☆☆｜区分度：高
> 关键词：WebSocket、Redis 路由表、Pub/Sub 广播、心跳续期、一致性哈希、离线消息

## 问题
问题：IM 长连接怎么支持多实例？用户在实例 A、消息发到实例 B 怎么办？

## 面试可讲版（五段式）

**① 业界背景**
长连接跨实例路由有三代方案：① 网关一致性哈希（同用户固定路由到同实例，但扩缩容会漂移）；② **在线路由表**（Redis 记录 userId→serverId，跨实例经 MQ/Pub-Sub 转发，业界主流）；③ 独立消息网关/代理层。核心问题：路由表的一致性与心跳过期（进程假死时条目必须能自愈）。

**② 项目选择**
组合方案：网关层用**一致性哈希**（`ImConsistentHashLoadBalancer`）把同用户连接尽量固定到同实例（减少跨实例），但**不依赖它保证正确性**；在线状态在 Redis 路由表 `im:online:{userId}`（值 serverId，90s TTL 心跳续期）；跨实例投递走 **Redis Pub/Sub**（`ImRouteSubscriber` 订阅独立 channel，仅本机持有连接的实例落地推送），消息先持久化再推送（离线可拉）。

**③ 坑**
- Pub/Sub 是"发后即忘"：订阅端重启窗口的消息会丢——所以推送只是尽力而为，**消息已先落库**，拉取兜底；
- 路由表条目依赖心跳续期，进程被 kill 后最多 90s 内仍显示"在线"，跨实例转发会失败 → 调用方 fallback 离线路径；
- 一致性哈希扩缩容有漂移，不能让"哈希正确"成为消息可达的前提。

**④ 兜底**
- Redis 订阅用独立连接（`RedisMessageListenerContainer` 与业务连接隔离，回调不占业务线程池）；
- ACK/未读数存 DB，重连后按游标拉取未收消息；
- 心跳 10s 级 + 90s TTL，进程重启自动重建路由。

**⑤ 话术**
> "长连接的可达性不靠哈希发誓：一致性哈希减少跨实例，路由表 + Pub/Sub 做转发，消息先落库保证最坏情况可拉回。路由表过期宁可多一次离线兜底，不赌心跳。"

## 追问与参考回答
**追问1：为什么不用 MQ 做跨实例转发？** Pub/Sub 延迟低、无堆积语义负担；用 MQ 也能做，但要处理消费组/堆积，且路由是广播语义，Pub/Sub 更贴。
**追问2：Pub/Sub 丢消息怎么办？** 推送失败/实例重启丢的那份，用户重连拉历史；在线位点由客户端 ACK 推进。
**追问3：多设备怎么处理？** 路由表值可扩展为多连接集合（当前单值口径），推送遍历本机连接；设备维度未做。
**追问4：为什么心跳 90s？** 抖动容忍与假死检测的折中：10s 心跳、9 次容错；更短会放大 Redis 写，更长会拉长误转发窗口。

## 面试官评分点
**高级开发级**：能讲清路由表 + 转发的完整链路；知道 Pub/Sub 不可靠与落库兜底；心跳/TTL 语义。
**架构师加分**：一致性哈希的漂移边界、假死自愈、多设备扩展、连接数与内存容量估算。
**危险信号**：认为哈希路由就万无一失；跨实例靠广播却无落库/兜底；心跳无 TTL。

## 本项目真实证据
- `im/handler/ImWebSocketHandler`、`ImHandshakeInterceptor`、`WebSocketConfig`；`im/loadbalancer/ImConsistentHashLoadBalancer`。
- `OnlineRouteService`：`im:online:{userId}` 路由键、90s TTL 心跳续期、Lua 脚本维护。
- `ImRouteSubscriber`：Redis Pub/Sub 独立连接、serverId 过滤、业务线程池隔离；`MessagePersistService`/`ChatMessage` 落库 + 离线拉取。
