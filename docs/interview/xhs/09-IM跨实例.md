# 第09题 | IM 长连接跨实例路由

> 难度：★★★★☆｜频率：★★★☆☆｜区分度：高
> 关键词：WebSocket、Redis 路由表、实例专属 Channel、PING/PONG 心跳、seqNo 有序、离线补发、Lua CAS 注销

## 问题
问题：IM 长连接怎么支持多实例？用户在实例 A、消息发到实例 B 怎么办？

## 面试可讲版（五段式）

**① 业界背景**
长连接跨实例路由有三代方案：① 网关一致性哈希（同用户固定路由到同实例，但扩缩容会漂移）；② **在线路由表**（Redis 记录 userId→serverId，跨实例经 MQ/Pub-Sub 转发，业界主流）；③ 独立消息网关/代理层。核心问题：路由表的一致性与假死自愈（进程挂掉后条目必须能过期），以及跨实例消息的有序与不丢。

**② 项目选择**
WebSocket + 路由表 + **定向 Pub/Sub**：
- 注册：`myxhs:im:online:{userId}`="1"（判在线）、`myxhs:im:route:{userId}`=serverId（定实例），TTL = 心跳间隔 30s × 3 = **90s**；客户端 **PING→PONG 续期**，注销用 **Lua CAS**（校验 serverId 再 DEL，防旧实例误删新路由）；
- 发送：会话内 `seqNo` 自增 → **先落库（事务）** → 查路由：本实例直推；他实例 publish 到**实例专属 Channel** `myxhs:im:route:{serverId}`（定向投递，无需广播过滤）；不在线/推失败存 `myxhs:im:offline:{userId}`，上线按 **seqNo 升序**补发；
- 项目里实现了 `ImConsistentHashLoadBalancer`（150 虚拟节点）作为可选优化，但**跨实例可达性不以它为前提**（仓内无启用接线；test-4 双实例 19014/19024 在网关分发下照常互通）。

**③ 坑**
- Pub/Sub 是"发后即忘"：订阅端重启窗口的消息会丢——推送只是尽力而为，**消息已先落库**，离线补发兜底；
- 路由依赖心跳续期：客户端 90s 无 PING 路由过期，跨实例转发会失败 → 走离线路径（宁可多一次兜底，不赌心跳）；
- **M8 离线乱序坑**：补发时 `selectBatchIds` 无排序 → 离线消息乱序；修复为按 `seqNo` 升序（`ChatService:340-344`）；
- ACK/TYPING（msgType 99/98）是瞬时信号，**推送失败不回放**（只有普通 CHAT 进离线重放）；
- 一致性哈希扩缩容有漂移，不能让"哈希正确"成为消息可达的前提（当前也未见启用）。

**④ 兜底**
- 离线存储 `myxhs:im:offline:{userId}` + 上线 seqNo 升序补发 + DB 未读数（`ChatUserRelation`）；
- 订阅用独立 `RedisMessageListenerContainer`（与业务连接隔离、回调不占业务线程池），跨实例透传 traceId（MDC）；
- Lua CAS 注销保证切换实例时路由不被旧连接误删；
- 实测：双实例跨实例送达 + ACK + 落库；离线 u2 上线补发 count=1。

**⑤ 话术**
> "长连接的可达性不靠哈希发誓：路由表 + 实例专属 Channel 定向转发，消息先落库、离线按 seqNo 补发。哈希只是减少跨实例的优化，路由过期宁可多一次离线兜底，不赌心跳。"

## 追问与参考回答
**追问1：为什么不用 MQ 做跨实例转发？** Pub/Sub 延迟低、无堆积语义负担；路由是"定向到某个实例"的语义，Pub/Sub 的 channel 天然匹配（我们还做了实例专属 channel，连过滤都省了）。
**追问2：Pub/Sub 丢消息怎么办？** 推送失败/实例重启丢的那份，发送端已落库且写了离线列表，用户重连按 seqNo 补发；读回执由客户端 ACK 推进。
**追问3：多设备怎么处理？** 当前路由是单值口径（一个用户一个实例），多设备需扩展为连接集合；设备维度未做，是明确边界。
**追问4：为什么 TTL 是心跳的 3 倍？** 30s 心跳、90s TTL = 容忍连续 2 次丢包；更短会放大 Redis 写并增加误离线，更长会拉长假死窗口（最多 90s 误判在线）。
**追问5：跨实例消息会乱序吗？** 不会依赖到达顺序：会话内 seqNo 由 Redis 自增分配，客户端/补发都按 seqNo 排序——离线补发乱序 bug（M8）就是这么修的。

## 面试官评分点
**高级开发级**：能讲清路由表 + 定向转发的完整链路；知道 Pub/Sub 不可靠与落库/离线兜底；心跳/TTL 语义。
**架构师加分**：假死自愈、多设备扩展、seqNo 有序设计、连接数容量估算、哈希亲和与路由表的取舍（以及"优化未接线"这种诚实的边界表述）。
**危险信号**：认为哈希路由万无一失；跨实例靠广播却无落库/兜底；心跳无 TTL；把未启用的组件说成已生效。

## 本项目真实证据
- `OnlineRouteService`：`myxhs:im:route:{userId}`/`myxhs:im:online:{userId}` 双键、TTL=`heartbeatInterval*3`（默认 30s×3=90s）、`UNREGISTER_LUA` 校验 serverId 原子注销、serverId=UUID8+pid。
- `ChatService`：`handleChat:97`（seq 自增:119 → 事务落库:124 → publish:161 → 离线:145/165）、`storeOfflineMessage:315`、`pushOfflineMessages:333`（seqNo 升序:340-344，M8 修复）、`handleAck:195`、`handleRead:210`。
- `ImRouteSubscriber:63-73`：实例专属 channel `myxhs:im:route:{serverId}`、MDC traceId 透传；push 失败降级离线(:140-150)。
- `ImWebSocketHandler`：PING→PONG+续期(:109,187-214)、ACK/TYPING 分发(:106-108)；`ImHandshakeInterceptor`/`WebSocketConfig` 握手鉴权。
- 实测：test-4 第六轮双实例跨实例路由+ACK+落库；离线补发 count=1。

## 发散追问地图（横向）
- 长连接选型：WebSocket/MQTT/QUIC/gRPC stream；握手鉴权（ticket/签名）。
- 路由方案：一致性哈希亲和 vs 路由表+定向转发 vs 网关代理层。
- 可靠性语义：ACK/重传/去重/seq 有序；至少一次与去重的组合。
- 多端与离线：多设备同步、会话游标、未读数分离（列表/未读缓存）。
- 群聊与扩散：写扩散规模、成员表、已读回执聚合。
- 推送兜底：厂商推送（APNs/FCM）与在线通道的双轨。
- 安全：鉴权、内容审核、防刷限流、连接数与内存容量。
