# 第59题 | 配置生效方式表：热更边界与"改了不生效"排查

> 难度：★★★★☆｜频率：★★★★｜区分度：高
> 关键词：Nacos、@RefreshScope、@Value、配置优先级、配置漂移、生效方式

## 问题
你们用 Nacos 做配置中心，改了配置为什么有的生效、有的要重启？配置没生效你怎么排查？

## 面试可讲版（五段式）

**① 业界背景**
"配置中心"解决的是**下发**，不解决**生效**。生效方式取决于三件事：① 配置怎么被读取（`@Value` 一次性注入 / `@ConfigurationProperties` 绑定 / Environment 动态查询）；② Bean 是否 `@RefreshScope`（重建才会拿到新值）；③ 配置源优先级（命令行 > 环境变量 > 配置中心 > 本地文件的次序因接入方式而异，要按你的框架版本实测，别背错）。

**② 项目选择**
- **唯一真热更**：`ChaosProperties`（`@RefreshScope + @ConfigurationProperties(prefix="chaos")`）——混沌故障注入开关，演练时动态开关；
- **Nacos 下发通道**是开着的：`spring.config.import: optional:nacos:my-xhs-common.yaml?group=DEFAULT_GROUP&refreshEnabled=true`（各服务 application.yml），但**业务参数全是 `@Value` 静态注入**，例如：
  - `inventory.bucket.default-count:2`、`hot-count:8`、`hot.detect-sample-rate:5`、`prededuct.expire-seconds:1800`（`InventoryService`）；
  - `order.close.delay-level:16`（`OrderService`）；
  - `myxhs.cart.reconcile.watermark-seconds:300`（`CartReconcileJob`）……
  改这些 = **滚动重启生效**；
- **配置源分布**：① Nacos 共享配置（仓库内两份副本：`config/nacos/`、部署包）；② 各服务 `application.yml`；③ order 的 `sharding-config.yaml`（分片/数据源）；④ 环境变量（`ADMIN_TOKEN`/`INTERNAL_TOKEN`/`JWT_SECRET`，未配时 fail-closed）。

**③ 坑**
- **最大误区**：`refreshEnabled=true` 只保证"配置能推送进来"，**`@Value` 字段不会变**——Bean 不重建，值永远是启动时那份；
- `@RefreshScope` 会给 Bean 加代理，**注意类型判断/`instanceof`/单例语义**（代理类 vs 原类）；
- **配置漂移**：Nacos 上的实际值与仓库副本（两份）不一致，测试环境被手改后没人知道；`sharding-config.yaml` 在三个配置源之外，容易被忽略；
- 敏感项（`JWT_SECRET`）改了必须全实例一致，否则新旧实例互相验不过 → 需要轮换方案（双密钥期）。

**④ 兜底（"改了不生效"五步排查链）**
1. **定位目标**：dataId / group / namespace 对不对（`my-xhs-common.yaml` + `DEFAULT_GROUP`）；
2. **查通道**：实例连的 Nacos 地址/命名空间对不对；`refreshEnabled` 是否开启；
3. **查覆盖**：本地 `application.yml` / 环境变量是否覆盖了配置中心的值（优先级问题）；
4. **查生效方式**：目标 Bean 是否 `@RefreshScope`？否 → 重启；
5. **查旧值持有**：Bean 重建了但内部**缓存/静态字段/构造时快照**还拿着旧值（需要对象级重建，如连接池参数）。
每步都能说出**证据**（actuator/env 里查、日志、Nacos 控制台版本对比）。

**⑤ 话术**
> "我们的配置中心通道是开的，但真正热更的只有混沌开关；业务参数因为都是 `@Value` 注入，属于'改配置→滚动重启生效'。所以内部有一张**配置生效方式表**：热更/重启/环境变量三类。排查'不生效'我按五步走：dataId-通道-覆盖-RefreshScope-旧值，每步都有查法。"

## 追问与参考回答
**追问1：为什么业务参数不都做成 @RefreshScope？** 收益低、风险高——热更不是免费的：Bean 重建时依赖它的对象可能拿到不一致的混合状态（一半新值一半旧值），连接池类参数还得重建连接池；我们只给"运行时开关类"配置开热更，其余走发布。
**追问2：Nacos 配置优先级和本地 yml 谁高？** 取决于接入方式：`spring.config.import` 模式下导入的配置源优先级**低于导入它的文件**（与 bootstrap 时代相反）；这条必须实测，是常见翻车点。
**追问3：配置里放什么不该放什么？** 环境相关的放配置中心（地址/开关/阈值）；**密钥类**要么走环境变量+密钥管理，要么走"双密钥轮换"流程；不要放会随实例不同而不同的东西（实例级参数）。
**追问4：怎么防止配置漂移？** 配置即代码：变更走发布单、仓库留副本、控制台只读化管理；定期 diff 仓库副本 vs Nacos 实际值。

## 发散追问地图（横向）
- Spring 侧：`@ConfigurationProperties` 校验（`@Validated`）、绑定时机、Environment 与 PropertySource 优先级链。
- Nacos 侧：2.x 长连接推送 + 本地缓存快照（`~/nacos/config`）、监听器机制、灰度配置。
- 运维侧：配置审计/回滚、多环境 namespace 隔离、金丝雀配置（先推 1 台）。

## 面试官评分点
**高级开发级**：能区分"下发"与"生效"；知道 `@Value` 与 `@RefreshScope` 的差异；能给排查链。
**架构级**：讲清热更的代价（对象重建一致性）、配置漂移治理与敏感配置轮换流程。
