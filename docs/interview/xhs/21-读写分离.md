# 第21题 | 读写分离与主从延迟

> 难度：★★★★☆｜频率：★★★☆☆｜区分度：高
> 关键词：AbstractRoutingDataSource、MyBatis 拦截器、readOnly 事务、主从延迟、强制走主库

## 问题
读写分离怎么实现？主从延迟怎么处理？什么情况必须走主库？

## 面试可讲版（五段式）

**① 业界背景**
读写分离解决读扩展：写主库、读从库。三种实现路径——① 中间件（ShardingSphere/MyCat）对应用透明；② 动态数据源（Spring `AbstractRoutingDataSource`）+ AOP/注解；③ ORM 拦截器按 SQL 路由。核心难点是**主从延迟**：写后立刻读从可能读不到；以及"事务内必须同连接"。

**② 项目选择**
- 实现：`ReadWriteRoutingDataSource` + **MyBatis Executor 拦截器**（`ReadWriteRoutingInterceptor`）：在 `Executor.query/update` 层拦（**不能在 StatementHandler 层**——那时连接已获取，路由无效）；
- 路由决策优先级：手动指定（`DataSourceContextHolder`）→ **@Transactional(readOnly=true) 自动走从** → SQL 前缀分析（SELECT/SHOW/DESC → SLAVE，写语句 → MASTER）；
- **事务安全**：活跃写事务中**不做 SQL 分析路由**（事务内所有语句必须同一连接，否则会破坏隔离性）——`isActualTransactionActive() && !readOnly` 直接放行；
- 从库不可用自动降级主库（30s 探测恢复），这属于可用性兜底；
- 结果：general log 实测 SELECT 落 slave（FINAL-HANDOFF 口径）。

**③ 坑**
- **延迟**：写后立即读从 → 读到旧值（用户"保存后看不到"）；解法：写后关键读**强制主库**（`DataSourceContextHolder.set(MASTER)` 或走主库的 hint）；本项目对状态敏感的读（下单后查订单）走主；
- **事务内不能切**：事务中 SELECT 也必须在主库同一连接（否则从库读不到未提交数据 + 连接不一致）；
- **Lazy 连接**：Spring 事务开启时不一定马上拿连接，路由 key 要在**获取连接前**设定（所以拦截器必须在 Executor 层）；
- **从库只读**：`setReadOnly(true)`，避免误写；写路由到从库会失败——这是设计而非 bug。

**④ 兜底**
- 复制延迟监控（Seconds_Behind_Source）；
- 从库故障降级主库 + 定期探测恢复（已实测：停从库读降级主库、恢复 ~40s 自动回切——zone 数据源改造后口径）；
- 强制主库开关（按方法/注解）；
- 强一致要求高的接口不走分离。

**⑤ 话术**
> "读写分离我们用动态数据源加 MyBatis Executor 拦截器：拦截点必须在拿连接之前，否则路由不生效。路由优先级是手动指定→readOnly 事务→SQL 前缀。最大的坑是主从延迟和事务一致性——写后马上读要强制走主库，写事务里的所有语句必须同连接，所以活跃写事务中我们不做路由切换。从库挂了自动降级主库，恢复后自动回切。"

## 追问与参考回答
**追问1：为什么拦截 Executor 而不是 StatementHandler？** MyBatis 执行顺序 Executor→getConnection→StatementHandler；在 StatementHandler 拦时连接已拿到，改路由无效。
**追问2：@Transactional(readOnly=true) 就够了吗？** 不够——只读事务走从库，但写事务里的 SELECT 要走主；还要处理"写后读"的场景强制主库。
**追问3：主从延迟多大？** 单机仿真下 ~0；生产异步复制通常毫秒~秒级，跨机房更差；关键读走主规避。
**追问4：半同步复制能解决吗？** 能降低丢失窗口但增加写延迟；"读己之写"更该用会话粘滞或强制主库。
**追问5：分库分表后读写分离怎么做？** 路由维度会变复杂（分片键+读从），中间件（ShardingSphere）更合适；本项目订单分片走 ShardingSphere，其他服务走轻量动态数据源。

## 发散追问地图（横向）
- 数据源：AbstractRoutingDataSource、多数据源事务（ChainedTransactionManager）、XA。
- 中间件：ShardingSphere 读写分离+分片、MyCat、ProxySQL。
- 延迟治理：半同步、读己之写（session sticky）、GTID 等待（WAIT_FOR_EXECUTED_GTID_SET）。
- 高可用：MHA/Orchestrator、Sentinel 从库故障切换、MGR。
- 观测：复制延迟指标、慢查询、连接池分池监控。

## 面试官评分点
**高级开发级**：能讲清拦截点选择；知道事务内不能切库。
**架构师加分**：路由优先级设计；写后读强制主库；从库故障降级与恢复；延迟监控与"读己之写"取舍。
**危险信号**：在 StatementHandler 拦截；事务内随意切从；不知道写后读延迟问题。

## 本项目真实证据
- `ReadWriteRoutingInterceptor:25`（写事务不路由）、`:49`（isActualTransactionActive 判断）、`:60`（SLAVE 设置）、拦截签名覆盖 Executor.query 两个重载 + update；
- `ReadWriteRoutingDataSourceConfig`：master/slave 池（20/10，slave readOnly）、`setInitializationFailTimeout(-1)`、从库恢复探测 30s（zone 改造后）；
- `DataSourceContextHolder` 手动指定优先级最高；
- FINAL-HANDOFF：general log 实证 SELECT→slave；MySQL 故障转移演练报告 `docs/reports/mysql-failover-drill-20260917.md`。
