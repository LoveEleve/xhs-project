# 第18题 | 对账体系与最终一致

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：最终一致、权威源、对账任务、XXL-Job 单调度、限速防雪崩、半成功修复

## 问题
你们的最终一致性怎么保证？对账任务怎么设计？以谁为准？

## 面试可讲版（五段式）

**① 业界背景**
分布式系统里"强一致做不到、最终一致必须兜底"是共识：核心思路是**每个数据有一条权威源 + 定期对账 + 幂等修复**。难点不在"比差异"而在：① 权威源怎么定（不同账本不同口径）；② 修复的幂等与限速（修复本身可能引发雪崩）；③ 调度只跑一个实例（否则重复修复）。

**② 项目选择**
- **6 个对账任务**（XXL-Job 调度）：`CartReconcileJob`（凌晨 4 点，Redis↔MySQL，**以 Redis 为准**）、`CounterReconcileJob`（凌晨 3 点，Redis 为准；但 **Redis=0 且 DB 有值时以 DB 为准**——防 Redis 丢数据被"修复"成 0）、`CouponReconcileJob`、`InventoryReconcileJob`、`UnreadReconcileJob`（限速防雪崩）、`PaymentReconcileJob`；
- **权威源按账本分**：购物车/计数走 Redis 权威（实时写入方）；券/库存走 DB 账本权威；这本身就是答"以谁为准"的加分点——不是统一答案，是**按业务选**；
- **调度保证单实例**：XXL-Job Admin 只调度一个 Executor 执行，**不需要 Redisson 分布式锁**——很多人第一反应是加锁，实际调度框架已保证；
- 配合 Outbox/本地消息表：对账是兜底，不是主路径。

**③ 坑**
- **修复动作本身要幂等**：对账是"每轮全量比 + 只修差异"，修完再比为 0 才算收敛；如果用"覆盖写"而不是"条件 UPDATE"，并发下会把新写入冲掉；
- **口径要写死在注释/代码**：counter 的"Redis=0 以 DB 为准"是实战经验（Redis 重启丢数据），否则对账会把真数据抹掉；
- **限速**：UnreadReconcileJob 对修复速度限流——一次性批量刷未读会把通知链路打爆（雪崩）；
- 对账不是实时：窗口内不一致是**正常态**，要能讲清"不一致窗口"与"收敛时间"。

**④ 兜底**
- 调度级：XXL-Job 单实例执行 + 失败重试 + 任务日志可审计；
- 数据级：修复用条件更新/幂等键；差异修复后再对账直至收敛；
- 窗口级：8 个对账/修复任务覆盖库存、券、购物车、未读、关注、本地消息补发、超时关单、订单映射补录；
- 观测：对账输出差异数/修复数指标与日志，异常趋势可告警。

**⑤ 话术**
> "最终一致我们是'权威源 + 对账 + 幂等修复'三段式。权威源按账本选：购物车和计数以 Redis 为准，券和库存以 DB 账本为准；计数还有个特例——Redis 值掉成 0 而 DB 有值时以 DB 为准，防止 Redis 丢数据被对账抹掉。调度用 XXL-Job 保证单实例，不需要额外分布式锁；修复限速防止把通知链路打爆。"

## 追问与参考回答
**追问1：对账频率多少？实时不一致怎么办？** 日级为主（凌晨跑），窗口内以业务兜底（用户操作走主路径）；对时间敏感的对账（未读）可调频率+限速。
**追问2：对账发现差异，修哪边？** 先定权威源（写路径确定真相），再幂等修复另一侧；修复后复对账确认收敛。
**追问3：怎么防止对账把并发新写覆盖？** 修复用条件更新/版本号；对账任务与业务写并发时，只修"稳定差异"（可加静默期/二次确认）。
**追问4：对账任务怎么保证只跑一个实例？** XXL-Job 路由策略保证 Admin 只调度一个 Executor；若换 Quartz/自研调度才需要分布式锁。
**追问5：怎么衡量对账体系有效性？** 差异数/修复数趋势 + 收敛率（修复后归零比例）+ 差异持续时间；长期差异=有未覆盖的写入路径。

## 发散追问地图（横向）
- 一致性模型：强一致/最终一致/线性一致、CAP、BASE。
- 对账 vs 补偿：对账是"发现+修复"，补偿是"反向操作"；事务消息/Outbox 与对账的关系。
- 调度：XXL-Job/Quartz/ElasticJob、单实例调度、分片广播、故障转移。
- 修复安全：幂等键、条件更新、静默期、二次确认、灰度修复。
- 观测：差异指标、对账报表、人工介入入口（工单/后台）。

## 面试官评分点
**高级开发级**：能说出对账三段式；知道权威源要按业务定。
**架构师加分**：调度单实例 vs 分布式锁的取舍；修复幂等与限速防雪崩；Redis=0 特例的实战价值；把对账放进"主路径+兜底"的整体一致性设计里讲。
**危险信号**：所有账本统一"以某侧为准"；对账加锁；修复直接覆盖写；把对账当实时一致方案。
