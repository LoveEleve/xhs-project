# 第27题 | 商品与 SPU 多级缓存（Bloom + 逻辑过期 + 空值 + 单飞）

> 难度：★★★★★｜频率：★★★★★｜区分度：高
> 关键词：缓存穿透/击穿/雪崩、布隆过滤器、逻辑过期异步刷新、空值缓存、冷 key 锁、afterCommit + MQ 失效

## 问题
商品详情缓存怎么设计？穿透/击穿/雪崩分别怎么防？缓存和 DB 怎么保持一致？

## 面试可讲版（五段式）

**① 业界背景**
缓存三难是一体三维：**穿透**（查不存在的数据，绕过缓存直打 DB）→ Bloom + 空值缓存；**击穿**（热点 key 失效瞬间并发打 DB）→ 逻辑过期 + 单飞（singleflight/互斥重建）；**雪崩**（大量 key 同时失效）→ 随机 TTL 或逻辑过期永不物理同时失效。一致性用 Cache Aside（更新 DB 后删缓存）+ 延迟双删 + MQ 兜底。经典坑：Bloom 的删除问题（布隆不能删）要用重建/计数布隆。

**② 项目选择**
- **两级缓存**：L2 Redis（SPU 详情）+ L3 MySQL；**没有 L1 本地缓存**（技术决策：多实例一致性 + 内存成本，Caffeine 试装后已移除）；
- **穿透两层**：`RBloomFilter`（100 万容量 / 1% 误判）前置拦截 + **空值缓存**（逻辑 2min / 物理 5min——短 TTL 防攻击者用海量不存在 ID 打爆 Redis 内存）；
- **击穿防法**：`RedisCacheData` 包装（**逻辑过期 30min + 物理 TTL 2h**）——逻辑过期后**返回旧值 + 异步刷新**（拿不到刷新锁就跳过，不阻塞请求）；冷 key miss 用**分布式锁单飞**（tryLock 1s，双重检查，只有拿锁线程查 DB 回填）；
- **雪崩**：逻辑过期本身让 key 不同时物理失效，**不需要随机 TTL**；
- **一致性**：写路径先更 DB → `afterCommit` 删缓存（防"未提交就删、读线程又回填旧值"）；删失败重试 3 次 + **延迟双删** + MQ 广播失效兜底（`CacheEvictConsumer` 消费重删）；
- **布隆过滤器工程化**：启动加载 `bloomFilterReady` 标志位——**加载期间/Redis 故障时降级跳过**（视为可能存在，放行到缓存/DB），避免启动期全量拦截；异步加载 + 状态可观测。

**③ 坑**
- **布隆不能删**：商品下架后 Bloom 仍有条目（假阳性），处理原则是"宁可多查一次缓存"而不是"漏拦"——下架商品靠 DB 状态字段兜底；
- **缓存空值的 TTL 要短**：正常数据 2h 兜底，空值只用 5min——否则新商品上架后持续返回 null；
- **逻辑过期返回旧值是有意为之**：一致性窗口（30min）是明确接受的；写路径 evict 会把窗口打断，读侧看到旧值的窗口实际远小于 30min；
- **"没有 L1"是主动决策**：曾试装 Caffeine 跑到 27,442 RPS，但多实例失效、内存膨胀、一致性复杂——移除后靠类加载锁修复也能 4,871，性能不是靠 L1 撑的；
- **回填竞争**：并发 miss 时无锁会多个线程同时查 DB 回填——所以有 load 锁 + 双重检查；锁超时短（1s）避免锁等待堆积。

**④ 兜底**
- Redis 不可用：Bloom 降级放行、缓存读写降级直查 DB（业务可用性优先）；
- 刷新失败：保留旧值（物理 TTL 2h 内可用），下次再触发刷新；
- 删缓存失败：重试 3 次 → 延迟双删 → MQ 广播重删三层；
- 观测：命中率、刷新次数、Bloom 拦截数、降级日志。

**⑤ 话术**
> "商品详情是 Redis+DB 两级、没有本地缓存。穿透两层：布隆过滤器加空值缓存，空值 TTL 只有 5 分钟；击穿用逻辑过期加异步刷新，返回旧值不阻塞；雪崩不用处理——逻辑过期本身不会同时失效。冷 key 并发 miss 用分布式锁单飞加双重检查。一致性是 afterCommit 删缓存，删失败重试加重试双删再加 MQ 广播兜底。布隆的坑是删不掉，下架商品靠 DB 状态兜底，宁可多查不能漏挡。"

## 追问与参考回答
**追问1：逻辑过期为什么不用随机 TTL？** 逻辑过期让"失效"变成应用层判断，物理 key 不集中失效；随机 TTL 只是扰动，热点 key 还是可能同时过期。
**追问2：布隆过滤器怎么处理商品下架？** 不能删（布隆不删）→ 假阳性方向是安全的（多查一次缓存），正确性由 DB 状态字段保证；量级大时可用计数布隆或定期重建。
**追问3：为什么空值缓存用这么短 TTL？** 防攻击：攻击者可用不存在 ID 打满内存；5min 足够挡正常穿透流量，又不长期占内存。
**追问4：afterCommit 删缓存还要延迟双删吗？** 要——并发读可能在删缓存后、事务提交前回填旧值；延迟双删覆盖这个窗口，MQ 广播是对跨实例/删失败的最后兜底。
**追问5：怎么证明缓存真的有效？** 压测对比（有缓存/无缓存）+ 命中率指标；商品详情 4,871 RPS/P99 50ms 是类加载锁修复后的实测值（缓存层兜底）。

## 发散追问地图（横向）
- 缓存模式：Cache Aside / Read-Through / Write-Behind；更新 DB+删缓存 vs 更新缓存。
- 布隆家族：计数布隆、Cuckoo Filter（支持删除）、分层布隆。
- 一致性：延迟双删的时间依据、binlog（Canal）订阅失效、版本号防旧值回填。
- 本地缓存回归：Caffeine vs Redis 权衡、多级缓存失效广播。
- 观测：命中率/穿透率/回源 QPS、大 key/热 key 治理。

## 面试官评分点
**高级开发级**：能区分穿透/击穿/雪崩并各自给方案；知道 Cache Aside。
**架构师加分**：空值 TTL 的安全视角；逻辑过期与写路径 evict 的窗口关系；布隆不可删的工程处理；"没有 L1"是量化决策（27,442 vs 4,871 的口径说明）；降级矩阵完整。
**危险信号**：用"缓存"一词掩盖三种场景；布隆加删除；空值长 TTL；删缓存无兜底。
