# 第29题 | 订单域：分片、状态机、事件溯源与关单兜底

> 难度：★★★★★｜频率：★★★★★｜区分度：高
> 关键词：ShardingSphere 4×4、user_id 分片、订单号映射表、状态机条件更新、事件溯源、延迟消息+XXL-Job 双保险

## 问题
订单表怎么分片？订单号不是分片键怎么查？订单状态怎么流转？超时关单怎么保证一定执行？

## 面试可讲版（五段式）

**① 业界背景**
订单是交易核心表：量大必须分片，但分片键选择是权衡——按 user_id 分查询亲和（用户查自己订单），但**订单号/商户维度查询会跨分片**；解法是**映射表（基因法/反查表）**。状态流转的正确性靠**状态机 + 条件 UPDATE**（不是"读出来判断再写"），跨服务一致靠事务消息/事件溯源；超时关单要**延迟消息 + 定时任务双保险**（延迟消息可能丢，定时扫描是终线）。

**② 项目选择**
- **分片**：ShardingSphere-JDBC **4 库 × 4 表 = 16 张逻辑表**，分片键 user_id：库 `user_id % 4`、表 `(user_id / 4) % 4`；同实例多 database 模拟分库，**生产改 jdbcUrl 即水平扩展**（配置化）；
- **订单号反查**：`order_mapping` 映射表（orderNo → userId → 路由分片）；写入与订单同流程（"同步执行但失败不阻塞主流程"），**失败由 `OrderMappingRepairJob` 补录**——彻底消除时间窗口永久遗漏；
- **状态机 + 事件溯源**：状态 0 待付款→1 已付款→2 已发货→3 已完成，4 已取消/5 已退款；流转走**条件 UPDATE**（`WHERE status=期望值`）；`OrderEventService.appendEvent` 落事件表（**event_seq 唯一键**防重 + 乐观锁收敛状态），事件类型→目标状态映射（含 T-110 修复：创建事件目标状态 -1，否则幂等检查恒真事件不落库）；
- **超时关单双保险**：下单发 **RocketMQ 延迟消息（delay-level 16）**；`OrderCloseJob`（XXL-Job）**每分钟扫描 30 分钟前待付款订单**兜底关单；
- **支付解耦**：支付表与订单映射表用**独立数据源（HikariCP + JdbcTemplate）绕过分片路由**，为支付域独立拆分预留；
- **本地消息表**：事务消息 + 本地消息表 + `LocalMessageRetryJob`（指数退避 30s×2^n、最大重试次数）补发。

**③ 坑**
- **"读状态再写"有并发窗口**：两个请求同时读到"待付款"，都去写"已取消"——必须条件 UPDATE 让数据库裁决；
- **T-110 事件链断**：创建事件目标状态=0 与订单初始状态相同，幂等检查恒真 → **创建事件从不落库**（事件链断）——目标状态改 -1 修复；教训：幂等判断要区分"状态流转"和"记录事件"；
- **映射表写入不能阻塞下单**：映射表是"查询辅助"不是核心数据——同步写但失败不抛错，靠补录任务收敛；
- **延迟消息不保证必达**：MQ 丢失/积压/消费失败都可能漏——定时扫描是终线（每分钟粒度）；
- **分片键设计没有 rehash**：扩容是明确短板（双写迁移/基因分片是正解，未落地）。

**④ 兜底**
- 关单：延迟消息（主）+ XXL-Job 扫描（兜底）+ 状态机条件更新（并发安全）；
- 映射：写入失败不阻塞 + 补录任务（扫描缺失）；
- 消息：本地消息表 + 重试 Job（退避）；
- 观测：关单任务执行日志、映射补录数、事件表状态收敛。

**⑤ 话术**
> "订单按 user_id 分 4 库 4 表共 16 张；订单号不是分片键，用映射表反查到 user_id 再路由，映射写入失败不阻塞主流程、由补录任务兜底。状态流转是条件 UPDATE 加事件溯源，事件表用序号唯一键防重。超时关单是延迟消息加每分钟定时扫描双保险。踩过的坑是创建事件因为幂等判断写错从不落库，事件链断了——修法是把创建事件的目标状态改成 -1，跟状态流转区分开。扩容没做 rehash，这是已知短板。"

## 追问与参考回答
**追问1：为什么按 user_id 而不是 order_no 分片？** 用户查"我的订单"是最高频查询，user_id 亲和；order_no 查询走映射表（低频）；商户维度另建索引/异步数仓。
**追问2：条件 UPDATE 失败怎么处理？** 影响行数 0 → 说明状态已变（幂等/冲突），按业务返回或查最新状态决定；不重试乱改。
**追问3：事件表和订单表怎么保证一致？** 同一个本地事务（事件与状态变更同库同事务）；跨服务用事务消息/对账。
**追问4：延迟消息 delay-level 16 是多久？** RocketMQ 固定档位 16 对应 30 分钟；选档位而非任意延迟是 MQ 能力边界（5.x 支持任意延迟但本项目用固定档）。
**追问5：地址为什么下单时要快照？** 用户随时可能改/删地址，历史订单必须保留**下单当时**的收货信息（对账/发货/纠纷取证）——所以创建订单时 `resolveAddressSnapshot(userId, addressId)` 把地址序列化存 `order.address_snapshot`，之后与用户地址表解耦；用户删地址也不影响历史单。
**追问6：映射表本身怎么防丢？** 写入与订单同流程（同步），失败降级不阻塞 + RepairJob 按订单扫描补录；映射表也可按 orderNo 分片/加唯一键。

## 发散追问地图（横向）
- 分片：ShardingSphere 内核、分片算法（hash/range/基因）、扩容迁移（双写/rehash）、分布式主键。
- 状态机：条件 UPDATE vs 悲观锁、Saga 状态机、事件溯源（ES/CQRS）。
- 超时治理：延迟消息/时间轮/定时扫描、幂等关单。
- 映射表：基因法（订单号带 user 后缀）、反查表、多维度索引（ES）。
- 消息：事务消息/本地消息表/Outbox、重试退避、DLQ。

## 面试官评分点
**高级开发级**：能讲分片键选择与反查；知道状态流转要条件 UPDATE。
**架构师加分**：映射表"不阻塞主流程 + 补录收敛"的分层设计；T-110 事件链断这类幂等陷阱；关单双保险（延迟消息不保证必达）；支付域独立数据源的拆分预留。
**危险信号**：读改写状态；映射失败阻塞下单；只靠延迟消息关单；分片无扩容方案却说"可扩展"。

## 本轮补充（2026-09-20 对抗测试 + 订单通知接入）
- 8 场景并发对抗全过：并发重复支付回调×5 幂等；取消vs支付=取消赢+**自动退款闭环**；重复退款回调幂等；确认收货vs退款无跳变；同 bizIdentifier 并发只 1 单。
- 部分退款：单笔部分退款订单/支付单保持已支付；**累计=全额**才置订单 5 + 支付单 3 + 库存回补。
- 订单→通知接入：`OrderNotificationPublisher`（支付/发货/退款三埋点、MQ 异步不阻塞交易）；聚合器刷新为最新状态（同订单当天一条，受 `uk_aggregate` 约束）。
- 机制口径：幂等事件（`INSERT IGNORE`+唯一键）＋乐观锁 `updateStatusWithLock`；失败路径删幂等键可安全重试。
