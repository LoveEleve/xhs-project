# 第58题 | 评论体系：楼中楼模型、游标分页与计数一致

> 难度：★★★★｜频率：★★★★☆｜区分度：中高
> 关键词：parent_id/reply_to_id、楼中楼、游标分页、MQ 计数事件、逻辑删除、热点评论

## 问题
评论和楼中楼怎么建模？列表为什么用游标分页？评论数怎么保证准？删除评论怎么处理计数？热点笔记评论怎么扛？

## 面试可讲版（五段式）

**① 业界背景**
评论是"读多写多 + 树形结构 + 计数敏感"的场景：数据模型要支持**两级树**（评论 → 回复，即楼中楼，一般不无限嵌套）；列表分页在深分页时 offset 会全表扫，**游标（keyset）分页**按 `id < lastId` 走索引更稳；评论数/点赞数属于**计数一致性**问题（见 11 题）；删除要幂等且计数要回退。

**② 项目选择**
- **模型**：`t_comment`（id/note_id/user_id/**parent_id**/**reply_to_id**/content/like_count/created_at/deleted）——`parent_id` 标识所属一级评论（楼中楼），`reply_to_id` 标识"回复了谁"；
- **两级树**：一级评论 + 其子评论（`getChildComments(parentId, lastId, pageSize)`），不做无限嵌套；
- **分页**：一级列表 `getCommentList(noteId, lastId, pageSize)` **游标分页**（按 id 倒序），另有 `getCommentPage` 供后台/兼容分页；
- **写入**：`createComment` 事务 + **`afterCommit` 发 MQ 事件**（计数/通知下游）；`deleteComment` 逻辑删除 + afterCommit（计数回退）；
- **计数**：`getCommentCount(noteId)` 读计数（Redis，见 11 题计数体系），DB 为兜底账本；
- **内容安全**：评论过 DFA 敏感词（33 题）；
- **点赞**：`like_count` 由计数体系维护（Set 去重 + 版本门）。

**③ 坑**
- **深分页**：`offset` 大时 MySQL 扫描丢弃严重 → 改游标 `id < lastId`（走主键索引，翻页稳定）；
- **楼中楼嵌套**：无限嵌套查询与渲染都复杂 → 固定两级，回复用 `reply_to_id` 表达"@谁"；
- **计数漂移**：MQ 事件重复/丢失 → 消费端幂等（msgId 去重）+ 对账 Job 兜底（11/18 题）；
- **删除的幂等**：重复删除要判重（`deleted` 标记），否则计数重复回退；
- **热点评论**：大 V 笔记评论写入集中 → 计数走 Redis 原子操作，DB 异步落库（Buffer 批量）。

**④ 兜底**
- 分页：游标兜底（无 lastId 时取最新）；
- 计数：Redis 权威 + DB 兜底 + 对账 Job（评论数、点赞数）；
- 删除：逻辑删除 + 幂等判重 + 计数回退事件；
- 内容：敏感词拦截 + 人工审核入口（内容合规）。

**⑤ 话术**
> "评论做两级：一级评论 + 楼中楼，`parent_id` 标识所属一级评论、`reply_to_id` 标识回复谁——不做无限嵌套，查询和渲染都简单。列表用**游标分页**（`id < lastId`）而不是 offset，深分页不退化。写评论是事务提交后发 MQ 事件给计数和通知，删除是逻辑删除 + 幂等判重 + 计数回退；评论数在 Redis 权威、DB 兜底，靠对账收敛——和点赞计数同一套体系。"

## 追问与参考回答
**追问1：为什么不做无限嵌套楼中楼？** 查询与渲染复杂度指数上升（要递归/闭包表），收益低；两级 + `reply_to_id` 已能表达"回复某人"的语义，行业主流（微博/小红书）也是两级。
**追问2：游标分页的坑？** 需要稳定排序键（id 单调）；翻页期间新评论插入不影响已翻页（不会重复/跳过），但无法跳页（业务可接受）；`lastId` 缺失时取最新。
**追问3：评论数怎么保证准？** 写评论发 MQ 事件 → 计数消费端幂等 +1；Redis 实时值、DB 异步落库；对账 Job 以 Redis 修 DB；重复投递靠 msgId 去重（11 题同源）。
**追问4：删评论计数怎么回退？** 逻辑删除 + 判重（已删不重复扣）+ 发回退事件；删除与计数是两件事，靠事件最终一致 + 对账兜底。
**追问5：热点笔记评论怎么扛？** 读：游标分页 + 计数走 Redis；写：计数原子操作 + Buffer 批量落库；评论正文写 DB（分片/索引 note_id）。

## 发散追问地图（横向）
- 评论模型：一级/楼中楼/回复/@/匿名；
- 分页：offset vs 游标 vs 滚动加载；
- 计数：Redis 计数/Set 去重/对账/防刷；
- 内容安全：DFA 敏感词/审核/举报；
- 通知：被评论/被回复通知（55 题）；
- 存储：评论表分片/冷热分离/大 V 笔记热点；
- 一致性：删除幂等/计数回退/消息重投。

## 面试官评分点
**高级开发级**：能讲清 parent_id/reply_to_id 两级模型；知道深分页要用游标。
**架构师加分**：游标分页的稳定性论证；评论数"Redis 权威 + DB 兜底 + 对账"的账本设计；删除幂等与计数回退；热点评论的写路径隔离。
**危险信号**：无限嵌套楼中楼；大 offset 分页；评论数直接 count(*)；删除不做幂等。
