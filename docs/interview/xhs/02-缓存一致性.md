# 第02题 | 缓存一致性：延迟双删、逻辑过期与 Canal

> 难度：★★★★☆｜频率：★★★★★｜区分度：高
> 关键词：Cache Aside、延迟双删、主从延迟、逻辑过期、布隆过滤器、空值占位、TTL 随机、CACHE_EVICT_TOPIC、Canal 失效

## 问题
问题：缓存和数据库怎么保持一致？为什么是"延迟双删 500ms"而不是先删缓存/先更库？Redis 挂了读请求怎么办？

## 30 秒简洁回答
结论：我们用 Cache Aside（读缓存、写库后删缓存），配三层兜底。① 写后**延迟双删**（第一次删在事务提交后立刻执行，500ms 再删一次）——500ms 不是随便拍的，是主从延迟约 200ms + 读线程耗时约 100ms + 余量推导出来的；② 第二次删失败发 MQ 广播 `CACHE_EVICT_TOPIC` 兜底；③ 最终一致靠对账与过期时间收敛。热点场景用**逻辑过期**（商品详情逻辑 30min/物理 120min，命中过期值时返回旧值并异步单飞刷新），避免击穿；防穿透用空值占位（NUL 包裹 + 2min）+ 布隆；防雪崩用 TTL 随机偏移。要强调的是：删缓存不是任何时候都绝对一致，读请求命中旧值是允许的窗口，但我们不接受"脏数据永久存在"。

## 展开回答（高级开发级）
**1）三种写策略对比。** ① 先更库再删缓存（我们的选择）：并发下最坏情况是短暂读旧值，无长期脏数据；② 先删缓存再更库：并发读会把旧值回填，脏数据持续到下次更新；③ 先更库再更缓存：写冲突时缓存可能被旧写覆盖。所以主流是 Cache Aside + 删除，而不是更新缓存。

**2）延迟双删的推导与实现。** 主从复制异步：写请求提交后，读请求可能落到从库读到旧值，然后回填缓存——如果只在提交时删一次，这轮回填就把旧值又写回来了。500ms = 主从延迟 ~200ms + 读请求耗时 ~100ms + 余量 ~200ms。实现上第一次删在事务提交后（`TransactionHook`），第二次删 500ms 后由守护 ScheduledExecutor 执行（不阻塞提交线程）；两次都失败则发 MQ 广播兜底。要诚实的是：500ms 是经验值，极端网络抖动下仍可能漏，所以最后还有对账。

**3）失效通道。** 缓存删除失败/需要跨服务失效时走 `CACHE_EVICT_TOPIC`（消息体含 key/source/retryCount），消费者按 key 删除，重试 3 次。库存缓存单独走 Canal：监听 binlog 变更 → `INVENTORY_CACHE_TOPIC`，用版本号 Lua 防乱序；**UPDATE 事件跳过**（这是回声保护：本服务自己的写会主动删，Canal 再删会打断读回填），DELETE 时 SCAN 删 bucket/total/count 三类 key。

**4）读路径的几种保护。** 防击穿：`tryLock(3s,10s)` + double check，抢不到锁的线程 sleep 100ms 重读或在逻辑过期场景直接返回旧值（单飞）；防穿透：空值缓存 + 布隆（100 万/1%）；防雪崩：TTL 加随机偏移（timeout/6）；Redis 整体不可用：直接降级查 DB 且**不回填**（避免 Redis 恢复后又被灌脏数据）。

**5）一致性级别。** 我们说的是"最终一致 + 窗口内可能读旧"：缓存-DB 差异窗口 <24h（对账兜底），强一致场景直接读库（支付、库存扣减），不用缓存。

## 进一步回答（架构师层级）
**为什么不用 Canal 作为唯一通道**：Canal 依赖 binlog 消费链路可用，本身有延迟与堆积风险；主路径必须是"业务代码主动删 + MQ 兜底"，Canal 只用于"外部直改 DB"与库存这类需要版本控制的场景。
**多级缓存与逻辑过期**：L2 逻辑过期解决的是"热点 key 到期瞬间大量请求打库"；代价是短暂读旧值。适合商品详情、笔记详情这类"允许秒级延迟"的数据；不适合价格、库存这类强一致数据。
**监控与治理**：缓存命中率、删除失败率、MQ 失效消费延迟、布隆误判与容量、空值占比、Redis 内存与淘汰速率都要有指标；大 key/热 key 探测（滑动窗口计数）触发逻辑过期与本地缓存。
**边界与风险**：主从延迟在切主/大事务时会放大到秒级；延迟双删的 500ms 是经验值；跨服务失效依赖 MQ 可靠投递，所以要有重试与死信处理；任何"缓存强一致"的说法都是伪命题，能说清窗口与兜底才是正确答案。

## 理解与复述提示（学习用，不要照念）
本质：缓存一致性 = 选择写策略（删优于更）+ 承认窗口 + 设计多层兜底。
顺序：① Cache Aside 与三种策略取舍 → ② 延迟双删 500ms 推导 → ③ MQ/Canal 失效通道 → ④ 穿透/击穿/雪崩三防 → ⑤ 一致性级别与对账 → ⑥ 边界（切主放大、500ms 经验值）。
记忆钩子："写库删缓存，双删补主从；删失败走 MQ，最终对账收。"

## 必须明确的边界
- 延迟双删不是强一致，只是把脏窗口压短；极端抖动仍可能漏，需要有对账/过期兜底。
- 500ms 是推导值不是协议：主从延迟、读耗时、网络都会变，要靠监控校准。
- 空值占位只能防"重复穿透"，布隆有误判（1%）且删除不清理（我们接受并监控容量）。
- Redis 不可用时选择降级查 DB 且不回填，是可用性优先的有意权衡。

## 常见错误
- 先删缓存再更库，导致并发回填长期脏数据。
- 只删一次、无兜底、无对账，还宣称强一致。
- 更新缓存代替删缓存；或在事务内删缓存（未提交就删，读回填脏值）。
- 不区分数据一致性要求，所有数据都上逻辑过期（价格/库存读到旧值）。

## 追问与参考回答
**追问1：为什么不是"先删缓存再更新 DB"？**
回答：并发读会在删除后、更新前把旧值查出来回填，脏数据会一直存在到下次写。先更库再删，最坏只是窗口内读到旧值，不会长期脏。

**追问2：双删的第二次删如果失败了呢？**
回答：重试 3 次（间隔 50ms）；仍失败发 `CACHE_EVICT_TOPIC` 广播，消费端重试 3 次；最后靠 TTL 与对账收敛。三层都失败的概率很低，但我们不假设为零。

**追问3：逻辑过期读到旧值，业务能接受吗？**
回答：按数据分级——商品/笔记详情接受秒级旧值；价格、库存、券这类强约束数据不走逻辑过期，直接读库或走 Lua 原子路径。

**追问4：Redis 挂了为什么降级查 DB 不回填？**
回答：Redis 故障期间 DB 可能已经被写过（也可能读到脏值），恢复瞬间如果把降级期间的值回填，就会把新值覆盖。降级期间只读不填，恢复后由正常读写重建缓存。

**追问5：Canal 和 MQ 广播冲突吗？**
回答：不冲突，职责不同。MQ 广播用于"本服务主动删失败"的兜底；Canal 用于"外部系统直改 DB"和库存这类需要 binlog 版本控制的场景。库存侧我们让 UPDATE 跳过（自己的写主动删过了），避免来回打架。

## 示例与使用说明
```java
// 写后：提交后删 + 延迟再删
transactionTemplate.executeWithoutResult(tx -> dao.update(entity));
cacheHelper.deleteAfterUpdate(key);            // 立即删（重试 3 次）
cacheHelper.delayDoubleDelete(key);            // 500ms 后再删，失败发 MQ

// 读：Cache Aside + 空值 + 随机 TTL
Obj v = cacheHelper.getWithCacheAside(key, () -> dao.select(id), 30, TimeUnit.MINUTES);
```
```lua
-- 库存失效版本控制（防乱序回填）
if redis.call('get', KEYS[1]) == false or tonumber(ARGV[1]) >= tonumber(redis.call('get', KEYS[1])) then
  redis.call('set', KEYS[1], ARGV[1]); -- 标记最新版本，再删缓存
end
```

## 面试官评分点
**高级开发级**：能讲清三种写策略的脏数据窗口；能给出双删推导与失效通道；三防齐全。
**架构师加分**：数据分级（哪些能容忍旧值）、Canal 与 MQ 的职责边界、缓存治理指标与大 key/热 key 处置、切主放大风险的兜底。
**危险信号**：宣称"缓存强一致"；只删一次无兜底；不区分数据一致性等级；把 500ms 当协议参数。
