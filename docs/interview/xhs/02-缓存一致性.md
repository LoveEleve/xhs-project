# 第02题 | 缓存一致性：先删缓存还是先更新 DB？

> 难度：★★★★☆｜频率：★★★★★｜区分度：高
> 关键词：Cache Aside、延迟双删、主从同步、Canal、singleflight、Bloom、CACHE_EVICT_TOPIC

## 问题
问题：缓存和数据库怎么保持一致？为什么是延迟双删？500ms 怎么来的？

## 面试可讲版（五段式）

**① 业界背景**
经典争论：先更库再删缓存（Cache Aside），还是先删缓存再更库？主流是前者——先删再更会在"删除后、更新前"被并发读回填旧值，脏数据长期存在；先更再删最坏只是窗口内读到旧值。Facebook 那篇 memcache 论文给出的解法是**延迟双删**（写后删一次、隔几百毫秒再删一次），本质是"赌主从同步完成"。更彻底的方案是订阅 binlog（Canal）异步删，把时间窗假设拿掉。

**② 项目选择**
先更新 DB → `deleteAfterUpdate` 删缓存（**重试 3 次×50ms**）→ 延迟 500ms 再删（`delayDoubleDelete`，失败发 `CACHE_EVICT_TOPIC`）→ 读路径 miss 用互斥回源（单飞）防击穿；商品详情用逻辑过期（30min 逻辑/120min 物理，命中过期值返回旧值+异步单飞刷新）。

**③ 坑（主动承认）**
- 500ms = 主从延迟 ~200ms + 读耗时 ~100ms + 余量 ~200ms，环境抖动就失效（切主/大事务时延迟会放大到秒级）。
- Bloom 启动时 DB 为空会导致**后插数据被拦**（踩过）；Bloom 容量只增不减，超容量误判率上升。
- 空值占位若忘记清（content 草稿曾缓存 NULL 占位 2min，发布时只清列表没清详情）→ 发布后详情 404 至占位过期。

**④ 兜底**
- **第一次删（`deleteAfterUpdate`）：重试 3 次、每次间隔 50ms**；Redis 不可用时"重试无意义"直接失败；3 次全失败记 ERROR 等 MQ 兜底（`:241-283`）；
- **第二次删（`delayDoubleDelete`，500ms 后）**：失败一律发 `CACHE_EVICT_TOPIC`（**Redis 不可用也发**，消费者等恢复后重试；`:304-352`）；
- 缓存 TTL 随机偏移（`timeout/6`，`:125,193`）+ 每日对账；
- Bloom 不可用降级放行（`bloomFilterReady=false` 跳过）、异步分段预热 100 万/1%；
- 库存缓存走 Canal 版本号 Lua：UPDATE 跳过（回声保护）、DELETE 物理清三类 key；
- Redis 整体不可用：降级查 DB **不回填**，恢复后由正常读写重建。

**⑤ 话术**
> "延迟双删是工程妥协，不是理论正确。所以我们用 MQ 广播和对账兜底；如果重做，我优先上 Canal 订阅，把时间窗假设去掉。"

## 追问与参考回答
**追问1：为什么不是"先删缓存再更新 DB"？** 并发读会在删除后、更新前把旧值回填，脏数据持续到下次写。先更再删最坏只是窗口内读旧值。
**追问2：第二次删失败怎么办？** 第二次删失败一律发 MQ 广播（Redis 不可用也发）；第一次删是 3×50ms 重试、Redis 不可用时快速失败靠第二次删补刀；最后 TTL + 对账收敛。
**追问3：逻辑过期读到旧值业务能接受吗？** 按数据分级：商品/笔记详情接受秒级旧值；价格/库存/券不走逻辑过期，直接读库或 Lua 原子路径。
**追问4：Redis 挂了为什么降级不回填？** 故障期间 DB 可能被写过，回填会把新值覆盖；只读不填，恢复后重建。
**追问5：Canal 和 MQ 广播冲突吗？** 不冲突：MQ 广播是"本服务删失败"的兜底；Canal 用于"外部直改 DB"和库存这类 binlog 版本控制场景。

## 面试官评分点
**高级开发级**：能讲三种写策略的脏数据窗口；双删推导 + 失效通道；穿透/击穿/雪崩三防。
**架构师加分**：数据分级（哪些容忍旧值）、Canal vs MQ 职责边界、缓存治理指标与大 key/热 key、切主放大风险。
**危险信号**：宣称"缓存强一致"；只删一次无兜底；所有数据都上逻辑过期。

## 本项目真实证据
- `CacheHelper`：`double-delete-delay-ms:500`(:57-58)、空值占位 `\u0000__CACHE_NULL__\u0000` + 2min(:46,128)、TTL 随机 `timeout/6`(:125,193)、`deleteAfterUpdate` 3×50ms 重试(:241-283)、`delayDoubleDelete` 500ms 二删 + MQ 兜底(:304-352)、500ms=200+100+200 推导注释(:306)。
- `SpuService`：`LOGIC_EXPIRE_MINUTES=30`(:130)、`PHYSICAL_TTL_MINUTES=120`(:414)、单飞刷新锁 `myxhs:product:lock:spu:{id}` tryLock(0,10s) 非阻塞(:648-656)、Bloom `tryInit(1_000_000, 0.01)`(:155) + 分段异步加载(:188-247)。
- `InventoryCacheEvictConsumer:84-99,174-189`：Canal→INVENTORY_CACHE_TOPIC、版本号防乱序、SCAN 删三类 key、UPDATE 跳过。
- 结果侧：商品详情 1020 RPS / P50 19.6ms / P99 60ms（Bloom + 逻辑过期）。

## 发散追问地图（横向）
- 缓存模式：Cache-Aside / Read-Through / Write-Through / Write-Behind 的取舍。
- 本地缓存：Caffeine（W-TinyLFU）、多级缓存 L1/L2 一致性（失效广播/版本号）。
- 热 key：本地副本+逻辑过期、key 打散、读写分离；大 key/热 key 探测（滑动窗口、采样）。
- Redis 部署形态：Cluster vs Sentinel vs Proxy；slot 迁移与多 key 限制。
- 淘汰策略：LRU/LFU/随机/TTL、maxmemory-policy 与容量规划。
- 击穿治理：单飞/互斥/异步刷新/预热；降级预案（只读、空值、直接 DB）。
- 一致性验证：影子读、对账、切主演练；"窗口+兜底"的表达范式。
