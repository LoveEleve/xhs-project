# 第54题 | 用户与认证域：双 token、吊销闭环与直连信任链

> 难度：★★★★｜频率：★★★★｜区分度：高
> 关键词：JWT 双 token、Redis 拉黑、改密吊销、验证码防刷、网关信任过滤、fail-closed

## 问题
登录态怎么设计？access token 过期怎么办？登出/改密怎么让旧 token 立刻失效？直连服务怎么防伪造身份？

## 面试可讲版（五段式）

**① 业界背景**
JWT 无状态好扩展，但**天然不可吊销**——要么短 TTL 忍窗口，要么引入黑名单/版本号变成有状态。双 token（access 短 + refresh 长）是折中：access 无状态验签，refresh 可控换发。吊销三选一：Redis 黑名单（本项目）、用户级 tokenVersion、token 表。

**② 项目选择**
- **双 token**：access（短）+ refresh（长）分层；刷新时旧 token 拉黑（防重放）；登出/改密触发**吊销闭环**（实测：改密后旧 access 立即失效并留审计）；
- **拉黑存储 Redis**：TTL 与 token 剩余有效期对齐，自动过期不膨胀；
- **验证码防刷**：一次性消费 + 频控；
- **网关信任链（F-001）**：网关只信自己的鉴权结果，外部伪造的直连 JWT/内部头一律剥离；**直连服务鉴权 fail-closed**（鉴权不可用→503 可重试，而不是 401 误登出）；
- **RBAC**：平台 JWT role claim → ADMIN/OPERATOR/VIEWER，管理端点收敛 ADMIN。

**③ 坑**
- **F-001（真事故）**：信任过滤依赖的 `StringRedisTemplate` 存在双 bean（业务 + cache），`getIfAvailable()` 抛 `NoUniqueBeanDefinitionException` 被吞 → **过滤逻辑全线失效**。修复：`@Qualifier("stringRedisTemplate")` + 5 场景验证（覆盖生效 / 吊销拒绝 400+审计 / 内部调用 / 网关流量）。教训：**被吞的异常 = 静默失效**，只有演练/启动期 bean 断言才能发现；
- **Redis 故障语义**：早期把"拉黑查询失败"当"已吊销"→ 全站 401 误登出；修复为 503 可重试（fail-closed 但语义正确）；
- **改密不吊销 = 旧 token 仍可用**：盗号场景下等于没改；改密必须触发全端吊销。

**④ 兜底**
拉黑 Redis 不可用：鉴权 fail-closed（拒绝但可重试）+ access 短 TTL 限制最坏窗口；直连端口残余暴露面登记为网络层收敛项。

**⑤ 架构师加分**
- 吊销是"有状态换安全"的权衡：黑名单 TTL 化避免存储膨胀；刷新/登出/改密三入口统一吊销路径；
- 信任链原则：**边界组件只信自己的判断**；与过滤器顺序协同（鉴权先于染色/限流，未认证流量不占业务预算）。

## 追问与参考回答
**追问1：为什么不用 tokenVersion？** 版本号要每请求查用户态；黑名单只查"是否被吊销"，命中率低 + TTL 自清理，读放大更小。
**追问2：多实例下吊销即时吗？** Redis 共享存储，跨实例即时；与 SSE/IM 路由表同一思路（中心态 + 本地缓存）。
**追问3：验证码怎么防重放？** 一次性消费 + 频控 + 失败计数；验证码与手机号绑定、校验即失效。
**追问4：F-001 为什么读代码发现不了？** 异常被 `catch` 吞掉 → 逻辑静默失效，静态看"逻辑是对的"；只有演练（伪造直连头）或启动期 bean 断言能发现——被吞的异常是最高危的一类 bug。
**追问5：JWT 无状态与吊销矛盾怎么权衡？** access 短 TTL 承担"不可吊销"的窗口，黑名单只覆盖主动吊销（登出/改密/刷新），两者叠加把风险窗口压到最小。

## 评分点
- 能讲清"无状态 vs 可吊销"的权衡；
- 有刷新/登出/改密三入口吊销闭环意识；
- 能主动讲 F-001 这类"被吞异常→静默失效"的事故模式与发现手段（演练）。

## 本项目真实证据
- `my-xhs-user`（双 token / 刷新 / 改密）、网关 `GatewayAuthFilter` + 信任过滤（`@Qualifier` 修复）、直连服务鉴权 fail-closed；
- 实测：改密吊销闭环、Redis 故障 503 语义（`docs/reports/redis-failure-semantics-20260920.md`）、F-001 5 场景验证（手册 ⑥）。
