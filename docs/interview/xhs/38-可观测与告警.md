# 第38题 | 可观测与告警：规则、链路与错误预算

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：40 条规则、分级 severity、通知链路、keep_firing_for、Watchdog、SLO 错误预算

## 问题
你们的监控告警怎么做的？告警为什么没第一时间被发现？SLO 怎么定？

## 面试可讲版（五段式）

**① 业界背景**
可观测三支柱：指标（Prometheus）、日志（ELK）、链路（traceId/SkyWalking）。告警工程的常见反模式：**规则一大堆但通知是黑洞**（receiver 空/占位地址）、**短命告警被吞**（group_wait 吃掉 firing→resolved）、**没有 Watchdog**（告警链路自己挂了没人知道）。SLO 落地要有**错误预算**与 Burn Ledger，不然 SLO 只是口号。

**② 项目选择**
- **指标与规则**：Prometheus 实测 **40 条规则 / 8+ 规则组**（应用 6、业务 8、黄金信号 7、MySQL 3+连接 4、节点 3、DLQ 1、Meta/Watchdog 等）；分 severity（critical/warning）；
- **验证式告警**（关键教训）：`MysqlLongRunningQueries` 用 `SELECT SLEEP(600)` 注入 → Prometheus firing → Alertmanager active → sink 落盘 `[firing]` → 清理后收到 `[resolved]`——**端到端实测过**；
- **通知链路**：Prometheus(19090) → Alertmanager(19093) → `alert-sink`（127.0.0.1:19099，Python systemd）→ `/data2/logs/alerts.jsonl`（+ 可读日志）；接企微/飞书只需换 receiver；
- **SLO 与错误预算**：`docs/slo/slo-and-degradation-matrix.md`——核心链路可用性 99.9%（错误预算 43m12s/30 天）/搜索 99.5%；实测基线（product 50ms@4,871、note 71ms@4,171 等）；**Burn Ledger 记账**（如发布脚本 bug 导致 home 停机 2-3 分钟 ≈ 7% 月度预算）；
- **Runbook**：每条关键告警带含义/排查 SQL/常见根因/处置/预防（如连接使用率告警对应僵尸连接事故）。

**③ 坑（真事故）**
- **通知黑洞**：规则 31 条但 Alertmanager receiver 是 `default-noop`，告警全被静默丢弃；仓库副本 webhook 还是占位地址——**告警没通知等于没有告警**；
- **短命告警被吞**：firing→resolved 间隔小于 `group_wait` 时可能只收到 resolved 甚至都收不到；用 `keep_firing_for`（如 `MysqlDown` 2m）+ 调整 group_wait（10s）处理；
- **没有 Watchdog**：告警链路自己挂了无人知晓——加 Watchdog 心跳（一直 firing，断了说明链路坏）；
- **规则堆积但无人响应**：总有长期 firing（EsClusterNotGreen yellow）会造成告警疲劳——正确姿势是**修根因**（单节点副本设 0）而不是忍着；
- **告警阈值没校准**：连接 459/500 的事故前没有连接率规则——事故后补 4 条 MySQL 规则（>80%、延迟>30s、长查询>60s、应用连接>250）。

**④ 兜底**
- 链路：Watchdog + sink 落盘（不依赖外部通道也能留痕）；
- 规则：按事故补规则（连接/延迟/长查询/连接数）；
- runbook：每条告警可操作（SQL/处置/预防）；
- SLO：错误预算 + Burn Ledger，发布/演练消耗可量化。

**⑤ 话术**
> "监控是 Prometheus 加 Alertmanager 加 Grafana 加 SkyWalking，规则实测 40 条、分为应用、业务、黄金信号、MySQL、节点、DLQ 等组。踩过最典型的坑是告警黑洞：规则 31 条但 Alertmanager 的 receiver 是空的，所有告警被静默丢弃；后来接了本地 sink，并且做端到端验证——注入慢查询，从 Prometheus firing、Alertmanager active 到落盘 firing/resolved 全链路走通。还有短命告警被 group_wait 吞、没有 Watchdog 的问题，用 keep_firing_for 加心跳解决。SLO 有错误预算和 Burn Ledger，发布事故停机 2 分钟会记成约 7% 月度预算。"

## 追问与参考回答
**追问1：告警分级怎么做？** severity=critical（服务不可用/资损）/warning（性能/容量）；路由可按 severity 分渠道；本项目默认落盘、可扩渠道。
**追问2：怎么避免告警疲劳？** 阈值校准 + 关联抑制 + 长期 firing 必须处理根因（EsClusterNotGreen → 副本 0）；只保留可行动的告警。
**追问3：SLO 怎么定和算？** 按核心链路定可用性/延迟目标；错误预算=1-SLO；Burn Ledger 记录每次事故消耗；未达标驱动优先级。
**追问4：Watchdog 是什么？** 一条永远 firing 的规则，Alertmanager 侧收到它说明链路正常；断收即告警链路故障——"监控监控自己"。
**追问5：指标基数怎么控？** 标签用有限枚举（服务/路由/状态），URI 归一化（≥10 位 ID → {id}），预注册空标签防系列被吞。

## 发散追问地图（横向）
- Prometheus：抓取/规则/告警状态机（inactive→pending→firing）、keep_firing_for、抑制/静默。
- 告警工程：分级/路由/值班/升级（PagerDuty）、SLO burn rate 多窗口。
- 日志链路：ELK、ILM、结构化字段。
- 链路追踪：SkyWalking/OTel、traceId 全链路。
- SLO：错误预算、Burn Ledger、发布门禁联动。

## 面试官评分点
**高级开发级**：能讲三支柱与告警链路；知道端到端验证告警。
**架构师加分**：告警黑洞这类"配了但没生效"的问题；keep_firing_for/短命告警；Watchdog 自监控；SLO 错误预算与 Burn Ledger 的工程化落地。
**危险信号**：规则数量当成绩；通知不验证；长期 firing 不管；SLO 只有口号。
