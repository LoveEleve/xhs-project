# 第11题 | 计数 Set 化与 Buffer 刷盘

> 难度：★★★☆☆｜频率：★★★★☆｜区分度：中
> 关键词：Redis INCR、Lua 原子去重、Set 化计数、双 Buffer 交换、攒批刷盘、对账修复、乱序虚增

## 问题
问题：点赞/收藏/粉丝这类计数怎么设计？高并发计数怎么落库？MQ 乱序/重复怎么保证不虚增？

## 面试可讲版（五段式）

**① 业界背景**
计数系统的三类经典问题：① 高频写怎么扛（Redis 实时 + DB 异步是共识）；② 重复/乱序消息怎么办（计数不是幂等操作，+1 两次就错）；③ 实时性与一致性怎么平衡（每次写都落库，DB 扛不住；只写 Redis，宕机丢数据）。业界方案：Redis 原子增减 + 幂等去重标记 + 批量刷盘 + 对账兜底。

**② 项目选择**
写链路：**Redis 原子增减（Lua 同一执行单元内"去重 + 增减"）** → `CounterBuffer` 攒批（`BATCH_SIZE=500`、`@Scheduled` 5s 触发、**双 Buffer 交换**：flush 时换出旧 buffer、立即建新 buffer 接收写入，避免 clear 丢数据）→ 批量刷盘 DB；一致性：Buffer 正常刷盘 + **失败重试 3 次 + 回写缓冲** + 每日凌晨对账修复；点赞/收藏用 **Set 化 Lua**（谁赞过记 Set），从根上解决"乱序 +1/-1 虚增"；另有**归零保护 Lua**（m11 修复）。

**③ 坑**
- **MQ 乱序虚增**（H2）：Like/Unlike 消息乱序到达，纯 INCR/DECR 会虚增 → 改 Set-based 原子 Lua：以"用户是否在集合里"判定状态迁移，重复/乱序消息自然幂等；
- **刷盘故障**（test-4 用 rename table 注入）：重试 3 次后回写缓冲，表恢复后自动补刷（DB=1 收敛）；
- Buffer 丢失窗口：进程被杀时内存中未 flush 的增量会丢——接受（计数可重建，对账修复），这是有意取舍；
- 冷热不均：热贴计数集中在一个 key → 分片计数与本地聚合是扩容方向（未做，边界）。

**④ 兜底**
- Redis 是实时权威，DB 是持久账本：对账 Job 以 Redis 全量重算修 DB；
- resetOffset 回放同一物理消息（同 offsetMsgId）被 Lua 去重拦截，计数不变（test-4）；
- 计数与业务解耦：业务只发事件，计数异步消费，主链路不受计数故障影响。

**⑤ 话术**
> "计数不是幂等操作，所以不能只靠重试——我们把'去重 + 状态迁移'塞进同一条 Lua，用 Set 化把乱序变无害；性能侧用双 Buffer 攒批，可靠性侧用重试+对账，接受'进程被杀丢最后一拍'这个有界损失。"

## 追问与参考回答
**追问1：为什么用 Set 不用位图/去重表？** Set 语义最直观（判断成员+状态迁移），单 key 规模可控；位图省内存但需要 userId 连续映射；去重表要落库，重了。
**追问2：双 Buffer 解决什么？** flush 期间新写入不能丢：交换后旧 buffer 刷盘、新 buffer 继续收；`volatile` + 锁保护交换。
**追问3：为什么不直接每次写 DB？** 点赞峰值 QPS 远高于 DB 承受，批量 upsert 把 N 次写合并成 1 次；500/5s 是压测校准过的批大小与延迟折中。
**追问4：计数丢了怎么办？** 两种丢法：进程被杀丢内存 buffer（对账重算）；Redis 丢（RDB/AOF 权衡）。计数不是资金，接受最终一致。
**追问5：大 V 粉丝数这种热点计数呢？** 分片计数（follower:{id}:{shard}）+ 读时聚合，或计数与列表分离（列表权威、计数缓存）；当前项目粉丝数走 ZSet ZCARD，未见分片（边界）。

## 发散追问地图（横向）
- UV 去重：HyperLogLog 误差 vs BitMap 精度 vs Set 精确（内存）；HLL 为何适合 UV 不适合计数。
- 分布式计数：CRDT（G-Counter/PN-Counter）思路；跨机房计数合并。
- Redis 持久化：RDB 快照丢窗口 vs AOF everysec 丢 1s；`WAIT` 命令与主从确认。
- 刷盘模式对比：定时批量 upsert vs binlog 订阅汇总 vs 流式（Flink）聚合。
- 幂等标记存储：Redis Set 过期策略、Bloom 误判对计数的影响。

## 面试官评分点
**高级开发级**：能说清"去重+增减"原子性的必要性；知道攒批与双 Buffer 的意义。
**架构师加分**：计数一致性级别选择（实时权威/最终持久）、热点分片、故障丢数界的界定与对账闭环。
**危险信号**：只答"用 Redis 计数"；重复消息靠重试不靠幂等；刷盘失败无重试无对账。
