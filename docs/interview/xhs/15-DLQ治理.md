# 第15题 | DLQ 治理与消费者韧性

> 难度：★★★★★｜频率：★★★★★｜区分度：高
> 关键词：maxReconsumeTimes、%DLQ%%group、DlqMetrics、指标恒 0 事故、三级治理、审批重投、核验

## 问题
问题：消息一直消费失败怎么办？死信队列怎么治理？重投谁来负责？

## 面试可讲版（五段式）

**① 业界背景**
消息队列的重试策略之争：**有限重试入 DLQ** vs **无限重试**（会堵死队列）vs 立即丢弃（丢数据）。共识是"有限重试 + 死信隔离 + 分级治理"：自动重试解决瞬时故障、补偿任务解决可修复状态、人工审批解决需要判断的变更。DLQ 监控的关键不是"有多少",而是**指标是否诚实**——很多团队的 DLQ 看板长期是 0，不是没积压，是指标写错了。

**② 项目选择**
- 消费端：`maxReconsumeTimes` 按组区分（**18 组 3 次 / 8 组 5 次**），耗尽进 `%DLQ%<group>`；不是所有失败都走 DLQ——业务侧另有补偿通道（Redis 待处理集合、本地消息表、Outbox）；
- 监控：`DlqMetrics` **自算 Gauge 采样 26 个消费组**（30s 间隔），没用 RocketMQ 原生指标；
- 重投**三级治理**：L1 自动重试（消费端退避）→ L2 补偿 Job（可自动修复的状态）→ **L3 死信重投必须人工审批**：xhs-ai 里由 Agent 发起（`dlq_list`/`dlq_detail` 诊断根因）、HITL 审批、执行后核验（`reentered_dlq`/`verified_consumed`）。

**③ 坑（都是真事故）**
- **指标恒为 0**（运行态 #21）：原实现用 `searchOffset(now)` 与 `maxOffset` 相减——两者恒等，指标永远是 0，整整一个监控盲区；直到做 AI 诊断时才发现。修复为 `minOffset/maxOffset` 差值（`DlqMetrics:137-141` 注释原话）；
- **`-1` 不是"没积压"**：它是"无 DLQ / 查询失败"的哨兵值，直接求和会把"查不到"混进"没积压"——必须区分处理；
- **22→26 组**：监控清单漏了 8 个组（扩容后新增消费组没登记），修复后重建 14 个服务；"监控覆盖不到 = 不存在"是 DLQ 治理最常见的系统性盲区；
- order 补偿消息进 DLQ 曾**没有重放通道**（只有进没有出）——后补"异常集合 + 对账 + 审批重投"链路；
- 死信里可能全是**毒丸消息**（反序列化失败）：重投必然再进 DLQ——核验器把这种情况识别为 `reentered_dlq` 而不是假装成功。

**④ 兜底**
- 消费端幂等（msgId+唯一键）让"重投/重复消费"无害；
- 死信重投全程审计（谁批、参数指纹、执行结果、核验结论）+ 队列级位点核验；
- 三组历史死信清账（存量治理）；DLQ 积压可观测（Gauge）+ 告警；
- 补偿通道分流：Redis 集合/本地消息/Outbox 承担"可自动修复"的那部分失败。

**⑤ 话术**
> "DLQ 治理我们踩过最典型的坑：指标恒为 0——不是没积压，是我们自己算错了。所以先说指标诚实（26 组全覆盖、区分 -1 哨兵），再谈重投：L1/L2 自动，L3 必须审批+核验，毒丸消息要能识别'重投无效'而不是死循环。"

## 追问与参考回答
**追问1：为什么不用 RocketMQ 原生指标？** 原生 DLQ 指标取数依赖运维接口且口径不稳；自算 Gauge 能精确覆盖"我们关心的 26 个组"，并与 Prometheus/告警打通。代价是要自己维护组清单（漏组就是这么来的）。
**追问2：为什么重投要人工审批？** 重投是生产变更：参数错/毒丸会造成风暴；审批保证"有人看过根因"。Agent 可以自动化诊断与提案，但执行必须过 HITL。
**追问3：毒丸消息怎么处理？** 核验器 detects `reentered_dlq` 即"重投无效"，人工改方案（修数据/跳过/丢弃），不能无限重投。
**追问4：DLQ 积压告警怎么设？** Gauge 持续 >0 或增长率阈值；注意监控本身要先验证（否则告警永远不响）。
**追问5：为什么有的组 3 次有的组 5 次？** 瞬时故障容忍度不同：回调类幂等且可重试（5 次），资源类失败往往需要人工（3 次尽快隔离）。

## 发散追问地图（横向）
- 重试策略：有限/无限/指数退避/死信；RocketMQ/Kafka/Pulsar 的 DLQ 机制对比。
- 指标工程：Gauge/SearchOffset 语义、-1 哨兵、告警阈值与增长率检测。
- 治理分级：自动补偿 vs 审批重投 vs 人工修复；SRE 变更管理与 Agent 自动化的边界。
- 毒丸与反序列化：schema 演进（Avro/Protobuf）、死信分类、跳过与隔离。
- 容量与成本：DLQ 存储（保留策略）、审计链存储、重投风暴保护（限速/熔断）。
- 演练：故障注入（消费端抛错/毒丸/ broker 抖动）、核验闭环与 MTTR 度量。

## 面试官评分点
**高级开发级**：能讲清有限重试与 DLQ 语义；知道三级治理；能把"指标恒 0"讲成自己的事故复盘。
**架构师加分**：监控覆盖治理（组清单/哨兵值）、重投的变更安全（审批+核验）、毒丸识别、补偿通道分流。
**危险信号**：认为 DLQ 指标不用验证；自动重投无审批；毒丸重投到成功。
