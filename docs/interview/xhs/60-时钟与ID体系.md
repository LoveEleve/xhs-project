# 第60题 | 时钟与 ID 体系：雪花、Redis 序列与墙钟的三套时间

> 难度：★★★★☆｜频率：★★★★｜区分度：高
> 关键词：雪花算法、时钟回拨、orderNo、事件版本、分片倾斜

## 问题
你们系统里主键、订单号和事件顺序分别怎么生成？时钟回拨会不会出问题？

## 面试可讲版（五段式）

**① 业界背景**
分布式 ID 的三个维度互相拉扯：**唯一性、趋势递增（B+树友好）、可读/可路由**。方案谱系：数据库自增（不可扩展）→ UUID（无序、索引不友好）→ 雪花（趋势递增、依赖时钟）→ 号段/Redis 序列（稳定、依赖存储）。**没有时钟完全免疫的方案**：雪花怕回拨，Redis 序列怕 Redis 抖，墙钟排序怕 NTP 偏移。

**② 项目选择（三种并存，各司其职）**
- **表主键 = 雪花**：MyBatis-Plus `ASSIGN_ID` + `IdGeneratorUtil`（内置 `IdWorker`）——趋势递增、B+树友好，不依赖 DB 自增；
- **订单号 = Redis 日序列**：`yyyyMMdd + 用户尾号(4位) + 当日 INCR 序号`，日 key 48h 过期；**Redis 故障降级为"时间戳+随机数"（概率碰撞，业务可用优先）**；
- **事件顺序** 两条路：order 域用 `t_order_event` 的**DB 自增序号**（唯一键防重）；inventory 域用**墙钟** `eventTime = System.currentTimeMillis()` 做事件版本（乱序防护的版本比较）。

**③ 坑（有一个真实事故）**
- **雪花 + 取模分片 = 分片倾斜（我们真踩了）**：Snowflake 增量 = `Δms<<22 + Δseq`，低 16 位在低流量时基本恒定 → `user_id mod 16` 恒定 → 16 个分片只有 2 个有数据（最大占比 75%）。**修复：取模改哈希取模 + 存量迁移 682 行 + 审计脚本**（详见分库分表专题）；
- **时钟回拨**：雪花依赖单调时钟，回拨会出重复/负数序列（经典面试题：回拨 2.3 秒生成 146 个重复 ID）；我们**未做过回拨演练，MP 内置实现的回拨行为要按版本核实**（诚实披露）；
- **墙钟做版本的风险**：跨节点时钟偏移（多实例多容器）会影响事件版本比较结果——单机部署掩盖了这个假设；
- **订单号可预测性**：日序列可枚举（含日期+用户尾号信息量），所以查询必须带**归属校验**（`isOrderOwner`），不能只靠"单号难猜"当安全边界。

**④ 兜底**
- 主键：DB 唯一索引兜底（雪花万一重复会插入失败而不是脏数据）；
- 订单号：生成失败降级可用性优先，但**碰撞由唯一索引挡**（失败可见可重试）；
- 事件顺序：order 用 DB 序号（不依赖时钟）；inventory 墙钟版本 + 对账（Redis 为 truth）做最终修复；
- 分片：哈希取模后分布审计脚本（阈值告警）常态化巡检。

**⑤ 话术**
> "我们的 ID 不是一种方案打天下。表主键用雪花（趋势递增、索引友好）；订单号用 Redis 日序列+用户尾号（可读、可路由），Redis 故障时降级时间戳+随机保可用，唯一性由唯一索引兜底；事件顺序尽量不用墙钟——order 用 DB 自增序号，只有 inventory 的事件版本用了时间戳，靠对账兜最终一致性。雪花我们踩过和分片交织的坑：低流量下 ID 低 16 位恒定导致取模分片倾斜 75%，后来改成哈希取模并迁移了存量。"

## 追问与参考回答
**追问1：雪花时钟回拨怎么防？** 三招：① 回拨检测（小于 lastTimestamp 时等待或告警）；② 切换 workerId/预留位；③ 业务侧唯一索引 + 幂等兜底。面试重点是**知道回拨会发生（NTP 校准/虚拟机暂停）而不是假设时钟永远向前**。
**追问2：为什么订单号不用雪花？** 可读性与可路由——客服/对账场景要"看到单号能定位日期"，雪花是纯数字无业务语义；且订单号要作为查询路由键（映射表 orderNo→userId）。
**追问3：Redis 序列为什么不怕时钟回拨？** 序列是存储端状态（INCR），与墙钟无关；怕的是 Redis 不可用（所以有降级路径）。
**追问4：为什么事件版本不用 DB 序号统一？** 成本与形态：inventory 事件是"跨 action 的乱序防护"，事件在 MQ 里传输，带时间戳最轻；order 有事件表落库，序号自然存在。若做重，可把"业务序号"放 payload 里传输，彻底摆脱墙钟依赖（改进方向）。
