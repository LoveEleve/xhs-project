# 第39题 | 公共组件：号段 ID、批量写入、ETag 与独立事务模板

> 难度：★★★☆☆｜频率：★★★☆☆｜区分度：中
> 关键词：号段模式、双 Buffer、批量写入（CPU×2/5000/ID 分片）、REQUIRES_NEW、ETag/304

## 问题
分布式 ID 怎么生成？批量写数据怎么优化？审计日志为什么用独立事务？ETag 做什么？

## 面试可讲版（五段式）

**① 业界背景**
公共组件的价值是"把重复问题的正确解法沉淀一次"。四个典型：**ID 生成**（UUID 无序/雪花依赖时钟/号段模式批量取号——库压力最小且趋势递增）；**批量写入**（单条 insert 的 RTT 浪费，批处理 + 并行 + 分片）；**审计事务**（业务回滚不能连审计一起回滚——REQUIRES_NEW）；**ETag**（读多写少接口用 304 省带宽）。

**② 项目选择**
- **号段模式 ID（`SegmentIdGenerator`）**：从 `t_id_segment` 批量取一段 ID 缓存在内存分配；**双 Buffer**（current/next）——当前号段用到 **70%** 就**异步加载**下一段，避免"用完才加载"的毛刺；DB 只承担批量取号（每段几百/几千），QPS 压力极低；
- **批量写入执行器（`BatchInsertExecutor`）**：线程数 **CPU×2**（IO 密集）、**JDBC Batch 每批 5000**、按 **ID 范围分片**（每个线程一段，互不冲突）；JDBC URL 必须 `rewriteBatchedStatements=true`（否则 batch 退化成逐条）；配套造数框架（`DataGenerator`/`RandomDataFactory`，规模倍数控制）；
- **审计独立事务（`AuditLogService`）**：`@Transactional(propagation = REQUIRES_NEW, timeout = 5)`——**业务回滚不影响审计落库**（审计是"发生过就必须记录"）；独立事务要短超时（5s）避免拖慢主链路；
- **ETag/304（`EtagResponseBodyAdvice`）**：对低频变更 GET 接口自动加 ETag，客户端带 `If-None-Match` 时返回 **304**（省带宽/降低服务端序列化开销）；ShallowEtagHeaderFilter 自动生成。

**③ 坑**
- **号段模式的主键趋势**：号段递增但多实例间有交叉——不是全局严格递增，但**趋势递增**对 B+ 树友好（比 UUID 的随机写强很多）；要严格递增得雪花/单点；
- **批量写入的坑**：不加 `rewriteBatchedStatements=true`，JDBC 假批处理（逐条发送）；批太大（如 5 万）事务超时——5000 是实测平衡点；
- **分片冲突**：多线程写同一段 ID 范围会锁冲突——按 ID 范围分片让每线程独立段；
- **REQUIRES_NEW 的代价**：挂起外层事务 + 新连接——滥用会耗尽连接池；审计这种"必须落"的场景才用；
- **ETag 的适用面**：动态/含用户态的接口不能乱加（缓存错数据）；只对低频变更的公开 GET 用。

**④ 兜底**
- 号段：双 Buffer 提前加载；DB 不可用时用尽当前段会阻塞（可接受，有监控）；
- 批量：失败重试 + 分批提交；
- 审计：独立事务失败只记日志不影响业务（但要有告警）；
- ETag：304 优化不影响正确性（客户端缓存校验）。

**⑤ 话术**
> "号段 ID 是双 Buffer：从库批量取号，当前段用到 70% 异步加载下一段，避免卡在边界；DB 只承担批量取号，压力极小。批量写入是 CPU×2 线程、每批 5000、按 ID 范围分片，JDBC 必须开 rewriteBatchedStatements，否则是假批处理。审计日志用 REQUIRES_NEW 独立事务，业务回滚了审计也要落——这是'发生过必须记录'。ETag 自动加 304，用在低频变更的 GET 上省带宽。"

## 追问与参考回答
**追问1：号段和雪花怎么选？** 雪花依赖时钟（回拨风险）且 workerId 分配麻烦；号段对时钟不敏感、批量取号、趋势递增——单库可撑高 QPS；超大规模用号段+雪花混合（美团 Leaf 思路）。
**追问2：双 Buffer 为什么 70% 触发？** 留 30% 缓冲给异步加载的时间窗（加载失败还有余量重试）；100% 才加载会卡请求。
**追问3：批量写入多大合适？** 和 DB/网络/事务大小有关；5000 是实测值；原则是"单批不超过事务超时，多批并行"。
**追问4：审计失败怎么办？** 独立事务失败不影响业务正确性，但要有告警；关键审计可加本地文件兜底（当前是日志告警）。
**追问5：ETag 和 Cache-Control 区别？** ETag 是内容协商（变了没），Cache-Control 是过期策略（多久内不用问）；配合使用。

## 发散追问地图（横向）
- 分布式 ID：UUID/雪花/号段/Leaf/Redis INCR、时钟回拨、workerId 分配。
- 批量处理：JDBC batch、rewriteBatchedStatements、MyBatis foreach、并行分片。
- 事务传播：REQUIRES_NEW/NESTED、事务挂起、连接池压力。
- HTTP 缓存：ETag/Last-Modified、304、CDN 缓存策略。
- 造数：数据工厂、规模倍数、压测数据隔离（影子表）。

## 面试官评分点
**高级开发级**：能讲号段/批量/独立事务/ETag 的用途。
**架构师加分**：双 Buffer 70% 阈值的缓冲逻辑；rewriteBatchedStatements 这类"假批处理"坑；REQUIRES_NEW 的连接池代价与适用边界；ETag 只用于低频变更接口的判断。
**危险信号**：UUID 当主键（随机写）；批量不开 rewrite；审计跟业务同事务或滥用 REQUIRES_NEW；动态接口乱加 ETag。
