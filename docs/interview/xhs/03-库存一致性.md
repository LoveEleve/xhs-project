# 第03题 | 库存一致性：Redis 预扣 + DB 条件更新

> 难度：★★★★☆｜频率：★★★★★｜区分度：高
> 关键词：分桶预扣、Lua 原子、条件 UPDATE、预扣幂等表、补偿 Job、对账、防超卖/防少卖

## 问题
问题：库存怎么防超卖？为什么预扣放 Redis、确认放 DB？Redis 挂了怎么办？

## 面试可讲版（五段式）

**① 业界背景**
库存扣减的经典争论有三组：① **扣减时机**——下单即扣（预扣）还是支付后扣？下单扣防超卖但会占用库存，支付后扣体验好但高峰期容易超卖；② **扣在哪**——DB 行锁 `SELECT ... FOR UPDATE` 稳但扛不住热点，Redis 原子扣减快但要处理一致性；③ **分段/分桶**——把单 SKU 库存拆成 N 桶以分散热点（阿里/美团实践）。共识方案：Redis 做高并发预扣，DB 做权威落账，最终一致收敛。

**② 项目选择**
下单时走 Redis **Lua 分桶预扣**（`preDeductScript`：校验 available≥qty 与扣减在同一脚本原子完成，同时记 `inventory:prededuct:{orderId}` hash 记录实际 bucket 号）；支付回调 `confirmDeduct` 在 DB 做**条件更新**（`available_stock = available_stock - qty AND available_stock >= qty`，影响 0 行即失败）；取消/超时走 `releaseStock`；DB 侧再加预扣幂等表，Canal 推缓存失效。

**③ 坑**
- **补偿释放必须按预扣时的真实 bucket**：F-037 发现早期按 bucket 0 兜底释放，若预扣落在别的桶会扣错账；修复为从 `inventory:prededuct:{orderId}` hash 读 `skuId:bucket`，无字段才回退 0（兼容旧数据）；
- **Redis 回填不能盲目**：N7 超卖防护之前用 MySQL `available_stock` 直接回填 Redis，忽略 locked 部分，导致可用量虚高——现在回填用 `total = available + locked` 口径并 SETNX 防并发重建；
- 分桶带来了"整体够、单桶不足"的少卖问题，靠桶间路由重试缓解（极端情况接受少卖，不超卖）。

**④ 兜底**
- 对账 Job：DB 权威源定期比对 Redis 桶合计，修差异；负库存修复有专门路径；
- 热 SKU 探测（`hotSkuDetector`）动态调桶数与本地缓存；
- 预扣幂等表 + 消息去重防重复扣；释放/确认都过 TCC fence（见 04 题）；
- SKU 异常集合 + DLQ：脏数据不再阻塞消费（RV33）。

**⑤ 话术**
> "正确性不靠单点：Redis Lua 扛并发，DB 条件更新做权威，预扣幂等表吃重复，对账收敛差异。允许少卖，绝不允许超卖。"

## 追问与参考回答
**追问1：为什么分桶？** 单 key 是热点，Lua 再原子也只能串行；分桶把 QPS 摊到 N 个 key，代价是桶间不均衡与少卖。
**追问2：预扣成功但下单失败？** 本地消息/补偿 Job 释放预扣（按真实 bucket），并幂等标记，不会重复释放。
**追问3：Redis 挂了还能下单吗？** 预扣路径不可用则拒绝下单（fail-closed），不能降级到 DB 硬扣——热点会打穿 DB。
**追问4：少卖怎么发现？** 桶合计 < DB available 且持续存在 → 对账告警；也可人工触发桶间重平衡。
**追问5：并发下"判断+扣减"怎么原子？** Lua 脚本内完成（Redis 单线程保证），DB 侧用 `WHERE available>=qty` 条件更新。

## 面试官评分点
**高级开发级**：能画出预扣→确认→释放三段；能解释 Lua 原子与条件 UPDATE 的关系；知道预扣幂等与补偿按真实 bucket。
**架构师加分**：分桶均衡/热点探测、少卖与超卖的取舍、对账与重建（total=available+locked）、故障注入验证。
**危险信号**：用 `SELECT FOR UPDATE` 硬扛热点；Redis/DB 双写无幂等；回填忽略 locked 造成虚库存。
