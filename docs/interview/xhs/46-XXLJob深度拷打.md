# 第46题 | 组件深度拷打：XXL-Job

> 难度：★★★★★｜频率：★★★★☆｜区分度：高
> 关键词：调度中心/执行器分离、misfire 策略、阻塞策略、分片广播、任务幂等、非法 cron

## 问题
定时任务怎么做的？任务重复执行怎么办？调度中心挂了会怎样？错过执行窗口怎么办？

## 面试可讲版（五段式）

**① 原理层**
- **架构**：调度中心（admin，管理/派发/日志/报表）+ 执行器（业务进程内，注册心跳、接收触发、回调结果）；执行器注册在 admin 的 `xxl_job_group`；
- **调度**：admin 用"时间轮 + DB 扫描"线程（每 5s 扫描 `trigger_next_time`）派发到快慢线程池；触发落 `xxl_job_log`（trigger_code 调度结果 / handle_code 执行结果）；
- **路由策略**：FIRST/轮询/一致性哈希/分片广播等；本项目统一 **FIRST**（配合任务内分布式锁，不用分片）；
- **阻塞策略**：SERIAL_EXECUTION（串行，本次未完则排队）、DISCARD_LATER、COVER_EARLY；本项目统一 SERIAL_EXECUTION；
- **misfire**：错过窗口的处理——`DO_NOTHING`（丢弃，默认）/ `FIRE_ONCE_NOW`（补跑一次）；
- **失败重试**：executor_fail_retry_count；本项目多为 0（失败交由下一轮任务/对账自愈）。

**② 项目用法（20 个任务，运行态审计）**
- admin **2.4.2**（18080），10 个执行器组（analytics/cart/counter/coupon/home/inventory/notification/order/payment/search），accessToken 鉴权；
- **任务分层**（全部 `@XxlJob` bean 模式，cron 配置在 admin）：
  - **对账自愈（小时级）**：库存/券/购物车/计数/未读/关注 + 死信扫描 + 推荐特征；
  - **高频补偿（秒/分钟级）**：本地消息重试（30s）、支付/退款超时（30s/60s）、通知补偿（2/3min）、关单（1min）、券过期（5min）、映射补录（5min）；
  - **每日离线（凌晨）**：Feed 清理（3:00）、ItemCF（2:00）、支付对账（3:00）；
- **多实例互斥**：**不用分片广播**（`getShardIndex` 使用数 = 0），任务内用 Redis `SETNX + 随机 token + Lua 比对删除`（RV30）保证同一时刻只有一个实例执行——"分片是把数据切开，锁是把执行串起来"，本项目任务量小、以对账为主，锁更简单直接。

**③ 真实事故（三段式，很能打）**
1. **非法 cron 导致任务"从未运行"**：`refundTimeoutCheckJob` 创建时 cron 写成 `0/60 * * * * ?`，**秒字段增量 60 越界**（必须 <60）→ admin 生成下次触发时间抛 `CronExpression.checkIncrementRange` 异常 → **调度器自动把任务置停用**（手动启用会被回写为 0）→ 零日志零执行；修复为 `0 * * * * ?` 后连续 `200/200`。排查链：状态被回写 → admin 异常栈 → cron 边界；
2. **每日任务静默丢弃**：`feedCleanup`（3:00）零执行、`recommendItemCF`/`paymentReconcile` 仅手动触发——环境每天凌晨关机，`misfire=DO_NOTHING` 把错过窗口直接丢弃（业务无感）；修复：三个每日任务改 `FIRE_ONCE_NOW`（恢复后补跑一次）；高频任务保持 DO_NOTHING（天然追平）；
3. **日报"633 失败"是口径陷阱**：拆解后绝大多数是 `trigger_code=500`（服务重启窗口执行器不在线）+ `handle_code=0`（任务体未显式上报），**真实业务失败仅 2 条**——看报表必须区分"调度失败/未上报/业务失败"。
- 历史事故：**P-D20**（19 任务仅 ~8 可调度——任务挂在 sample 组、地址 NULL；修复=建组+改 job_group+补任务），说明"部署后任务要审计"。

**④ 兜底**
- 任务内：Redis 锁（多实例互斥）+ 幂等/条件更新（重复执行安全）；
- 任务设计：对账扫描"差异可自愈"，补偿任务"失败下轮再来"；
- 运维：misfire 分级（每日任务 FIRE_ONCE_NOW）、执行器注册告警（admin 可见 registry 数）、日报拆解看板。

**⑤ 拷打追问**
1. **"调度中心挂了会怎样？"** 已排期的触发停止派发（所有定时任务暂停）；执行器与业务不受影响。admin 本项目单实例——**单点**，生产应双节点（配合 DB 行锁避免重复调度）。
2. **"执行器挂了会怎样？"** 触发记录 `trigger_code=500`（无可用地址/注册失败），等下一轮；服务重启期间高频任务会积累调度失败日志（口径拆解见上）。
3. **"SERIAL_EXECUTION 和 DISCARD_LATER 区别？"** 前者排队（本次未完，后续触发等待）；后者丢弃后续触发。长任务怕堆积用 DISCARD，对账类怕漏触发用 SERIAL。
4. **"为什么不用分片广播？"** 分片适合"大表按分片键并行"，本项目对账数据量小且要全局一致视图；加锁的"单实例跑全量"更简单，也避免分片下的半成功合并逻辑。
5. **"cron 有什么坑？"** 本项目实测：`0/60` 增量越界直接被禁用（不报错到业务，静默失效）；零点和星期字段、时区、`?` 用法都要复核——**上线前用 admin "下次执行时间"预览校验**。
6. **"任务重复执行怎么办？"** 前提是任务本身幂等：Redis 锁只保证"通常单实例"，锁失效/人工触发时靠幂等（唯一键、条件更新、按 msgId/业务键去重）。
7. **"怎么保证任务没漏跑？"** 日报 + 每任务 `trigger_last_time` 审计 + 关键任务告警；本次就是靠"零日志"发现的。
8. **"日志保留？"** admin 有清理任务（本项目未单独调），执行日志默认保留约 30 天（生产按合规调）。

**⑥ 话术**
> "XXL-Job 我们 20 个任务、10 个执行器组，对账/补偿/离线计算三层：高频的 30 秒级补偿、小时级对账、每天凌晨离线。多实例互斥不用分片广播，任务里用 Redis SETNX 加 token 比对删除——任务幂等才是底线。踩过两个典型坑：一个任务 cron 写成 `0/60`，秒字段增量越界，admin 直接把它自动禁用，于是'任务存在但从未运行'；还有每日任务在环境关机窗口被 DO_NOTHING 静默丢弃，改成 FIRE_ONCE_NOW 后恢复补跑。日报的失败数也要拆开看，633 条里真正业务失败只有 2 条。"

## 发散追问地图（横向）
- 调度原理：时间轮/DB 扫描、quorum、admin HA、分片广播实现。
- 任务治理：幂等设计、长任务拆分、慢任务告警、失败重试策略。
- 对比选型：Quartz、Elastic-Job、PowerJob、K8s CronJob、Temporal。
- 运维：执行器在线数、触发/执行指标、日志保留、灰度发布任务版本。

## 面试官评分点
**高级开发级**：能讲调度/执行分离、阻塞与 misfire 策略、任务幂等。
**架构师加分**：非法 cron 的完整排查链（状态回写→admin 栈）；"分片 vs 加锁"的选型理由；日报口径拆解；admin 单点与 HA 方案。
**危险信号**：任务不幂等只靠不重复触发；不知道 misfire；把调度失败当业务失败。
