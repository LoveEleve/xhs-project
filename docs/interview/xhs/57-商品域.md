# 第57题 | 商品域：SPU/SKU 模型、类目树、上下架与缓存

> 难度：★★★★｜频率：★★★★★｜区分度：中高
> 关键词：SPU/SKU 两级模型、类目树、上下架状态机、afterCommit 失效、Bloom/逻辑过期、双源库存

## 问题
商品怎么建模（SPU/SKU）？类目树怎么存和缓存？上下架怎么做、缓存怎么一致？商品读多写少怎么扛？

## 面试可讲版（五段式）

**① 业界背景**
商品域是典型的**读多写少 + 结构复杂**：SPU（标准化产品单元，如"连衣裙"）与 SKU（最小库存单元，如"红色-S"）两级模型是行业标准；类目是多叉树（父子+层级）；价格有列表价（original_price）与售价（price）；上下架是状态机。读侧 QPS 远高于写侧 → **缓存是主战场**（穿透/击穿/一致性三件事，见 27 题）。

**② 项目选择**
- **模型**：`t_spu`（name/brand_id/category_id/description/images/status）+ `t_sku`（spu_id/specs/price/original_price/stock/status）+ `t_category`（parent_id/level/icon/sort/status）；SPU 详情聚合其 SKU 列表（`listSkusBySpuId`）；
- **类目树**：`getCategoryTree()` 按 parent_id/level 构建；**Redis 全量缓存** `myxhs:product:category:tree`（TTL 2h）；
- **上下架**：`ProductStatus` 枚举 `ON_SHELF(1)/OFF_SHELF(0)`；`updateSpuStatus` 改状态 + **`afterCommit` 失效缓存**（事务提交后才失效，防回滚后缓存被误清）；
- **缓存**：SPU 详情两级（Redis + MySQL）+ **Bloom 防穿透 + 逻辑过期 + 空值缓存 + 单飞**（27 题详述）；`evictSpuCache` 统一失效入口；
- **浏览埋点**：`recordSpuViewAsync` 异步写行为表（不阻塞读）；
- **库存**：`t_sku.stock` 是**展示库存**，真实扣减在 inventory 服务（`t_inventory` 可用/锁定/冻结）——双源。

**③ 坑**
- **双源库存**：`sku.stock`（商品域展示）与 `t_inventory`（库存域权威）不一致 → 以 inventory 为准，展示字段只做近似（或定期同步）；
- **缓存失效时机**：事务内失效 → 回滚后缓存已被清（后续读回填旧值前有脏窗口）→ 改 `afterCommit`；
- **类目树全量缓存**：更新频率低但**全量对象**，重建时并发易击穿 → 加锁/单飞 + 空值兜底；
- **下架校验时机**：下架只改状态，购物车/订单仍可能持有旧商品引用 → 写路径（加购/下单）必须校验 `status=1`，不能只依赖读缓存；
- **SKU 级价格**：价格在 SKU 上，SPU 只展示"起售价"，改价要按 SKU 维度失效。

**④ 兜底**
- 读：Bloom（不存在直接拒）+ 空值缓存（防穿透）+ 逻辑过期（防击穿）+ 单飞（防击穿）；
- 写：afterCommit 失效 + 重试；下架在写路径二次校验；
- 类目树：Redis 挂了回源 DB 构建（`buildCategoryTree`）；
- 库存：展示字段异常时以库存服务为准。

**⑤ 话术**
> "商品用 SPU/SKU 两级：SPU 是标准化产品，SKU 是带规格和价格的最小单元，价格在 SKU 上。类目树是 parent_id+level 的多叉树，全量缓存在 Redis（2 小时 TTL），重建走单飞防击穿。上下架是 `ON_SHELF/OFF_SHELF` 状态机，改状态后在**事务提交后**失效缓存——事务内失效会在回滚时留下脏窗口。读侧是读多写少，所以缓存四件套（Bloom/空值/逻辑过期/单飞）都在，细节见缓存题。有个要点：SKU 上的 stock 只是展示，真实扣减在库存服务的独立账本，这是双源，我们以库存服务为准。"

## 追问与参考回答
**追问1：为什么 SPU/SKU 两级，不用单表？** 一个 SPU 下多规格 SKU（颜色/尺码），价格和库存都在 SKU 粒度；单表会把规格维度拍平导致冗余与更新异常。两级也是电商行业标准（商品详情聚合 SPU，加购/下单按 SKU）。
**追问2：类目树为什么全量缓存？怎么更新？** 类目变更极低频但被高频读取（导航/筛选），全量缓存最省事；更新走"改 DB → 删缓存 → 下次读重建"，重建加锁/单飞防并发击穿。
**追问3：上下架怎么保证缓存一致？** `updateSpuStatus` + `afterCommit` 失效；关键是**提交后**失效（避免回滚导致缓存被清而 DB 未变）；下架商品在加购/下单写路径二次校验，不信任读缓存。
**追问4：sku.stock 和库存服务什么关系？** 双源：商品域 stock 是展示用，库存域 `t_inventory`（可用/锁定/冻结）才是扣减权威。不一致时以库存服务为准，展示字段可异步校准——这是"账本要单一权威"的原则。
**追问5：商品读多写少，扩容先崩哪？** 缓存层：SPU 详情是热点，Redis 单主 ops 是瓶颈（见容量报告）；策略是热点隔离 + 本地无缓存（多实例一致性优先，Caffeine 试装后移除，27 题有取舍）。

## 面试官评分点
**高级开发级**：能讲清 SPU/SKU 两级模型与类目树缓存；知道上下架要失效缓存。
**架构师加分**：`afterCommit` 失效的时机论证；双源库存的"单一权威"原则；下架校验在写路径而非依赖缓存；读多写少的缓存四件套与本地缓存取舍。
**危险信号**：把展示库存当扣减权威；事务内失效缓存；下架只改状态不做写路径校验；说不出 SPU/SKU 区别。
