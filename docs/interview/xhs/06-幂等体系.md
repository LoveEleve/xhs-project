# 第06题 | 幂等体系：四层防线

> 难度：★★★★☆｜频率：★★★★★｜区分度：中
> 关键词：token 防重、msgId 去重、唯一键、状态机条件更新、预扣幂等表、对账兜底

## 问题
问题：重复下单/重复支付回调/重复消费，你们怎么保证幂等？

## 面试可讲版（五段式）

**① 业界背景**
幂等是分布式系统的基石。业界范式有四层：入口 **token 防重**（防用户连点）、消息层 **msgId 去重**、业务层 **唯一键/去重表**、状态层 **状态机条件更新**。常见争论：去重窗口设多长？token 先消费还是处理完再消费？共识是——**去重窗口只是成本优化，唯一约束才是终线**，因为任何窗口/缓存都可能失效。

**② 项目选择**
四层防线：① 入口——前端提交令牌 + 服务端参数指纹（一次性消费）；② 消息——消费切面按 `msgId` SETNX 去重（2h/24h 两档），配合 `@Order(1/10/50/100)` 的"消息幂等→限流→锁→业务幂等"固定顺序；③ 业务——唯一键（`uk_claim_no`、`uk_order_event_seq`、`uk_order_sku_action`、`uk_user_sku`）+ 状态机条件更新（`WHERE status=期望值`）+ 预扣幂等表；④ 收敛——对账 Job 修差异。

**③ 坑**
- 30s 本地消息补发未标已投递 → **同一个订单双投两条预扣消息**（修复：`markSuccessByTransactionId`）；这是"消费端幂等是终线"的实战证明；
- `msgId` 会因 `reconsumeTimes` 变化而变（RocketMQ 细节）→ 去重键要做归一化（OrderCompensationConsumer 用 SETNX 兜住）；
- SPU 新增早期"假幂等"（键不对）导致重试插入重复 → RV33 修为"幂等键 + userId"。

**④ 兜底**
- 唯一键永远在 DB（Redis 去重失效也拦得住）；
- 状态机天然幂等：支付/退款回调内部乐观锁，状态已流转直接返回（代码注释即此语义）；
- 预扣/券/点赞各自幂等表；AI 侧入口用 `X-Request-Id`（重复提交 409/回放）；
- 对账 Job 是最后兜底，允许"幂等失效但收敛回来"。

**⑤ 话术**
> "幂等不是一层，是从入口到对账的四层防线；去重窗口只是成本优化，唯一键才是终线。我们从不假设消息只来一次。"

## 追问与参考回答
**追问1：token 什么时候消费？** 处理前先用（防并发连点），失败是否退还看业务：下单失败要退还，否则用户无法重试；退还用原子脚本防双还。
**追问2：去重窗口 2h 够吗？** 看消息最大重投周期（死信扫描每小时 + 回查 75s 级），2h 覆盖正常路径，24h 档给慢路径；窗口外靠唯一键。
**追问3：为什么不全靠 MQ 的顺序/去重？** MQ 只保证 at-least-once 投递语义，消费失败/回查/补发都会重投；去重必须落在业务侧。
**追问4：唯一键冲突怎么处理（不是 bug）？** 捕获 `DuplicateKeyException` 当作"已处理成功"返回，记录指标即可，避免误报错误。
**追问5：AI 侧幂等和交易侧有何不同？** AI 侧操作是"提案+审批+执行"，幂等键要绑审批 ID 与参数指纹；重复批准不能重投两次（队列级位点核验）。

## 面试官评分点
**高级开发级**：能列出四层并说清各层失效后的后果；知道唯一键是终线；能解释状态机幂等。
**架构师加分**：幂等键设计（组合键/归一化/冲突语义）、切面顺序、去重窗口容量估算、对账与可观测（重复拦截计数）。
**危险信号**：只答"加个 Redis 去重"；把 token 消费放在处理完成后；不处理 DuplicateKey 语义。
