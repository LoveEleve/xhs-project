# 第56题 | 异地多活与单元化架构：谱系、单元设计与脑裂

> 难度：★★★★★｜频率：★★★★☆｜区分度：高
> 关键词：同城双活、异地多活、两地三中心、单元化 Set、GSLB、脑裂、LWW/CRDT、切流分级

## 问题
你们的多活只做了 zone？同城双活和异地多活有什么区别？单元化（Set）怎么设计？跨单元数据一致性怎么保证？GSLB 怎么切流？脑裂怎么办？

## 面试可讲版（五段式）

**① 业界背景**
多活按容灾级别与成本分谱系：
- **同城双活**：同城两机房（<50km），延迟 <2ms，可共享存储或双写，RPO≈0，容灾=机房级；
- **异地多活**：跨城（>1000km），延迟 20-50ms，每地可写 + 异步同步（RPO>0），容灾=城市级；
- **两地三中心**：生产 + 同城灾备 + 异地灾备，成本最高，RPO/RTO 分级；
- **单元化（Set 化）**：按用户/租户把流量与数据切成**自闭环单元**（每单元含完整服务集 + 分片数据），单元内请求闭环、跨单元只读或异步；故障时**单元级切流**（GSLB 摘除）。
核心矛盾：一致性 vs 可用性 vs 成本。数据面"双写必冲突"——要么单写多读（伪多活），要么异步双向同步 + LWW/CRDT（真多活但 RPO>0）。脑裂的本质是"两侧都认为自己对"，需要 quorum/仲裁或业务幂等兜底。

**② 项目选择**
我们做的是 **zone 级多活**（单机双实例仿真），共 7 条工作流：
1. **流量面**：SCLB 同 zone 优先（`ZonePreferenceFilter` + LB 子 context 正确接线）+ 网关 WebFlux 独立实现（12/12 同区命中；kill -9 后 **5.54s** 恢复）；
2. **JDBC 多活**：`DynamicDataSource`（402 行）按 zone 组装 master/独立只读副本，监听 `ZoneContext` 属性变更**热切换**，切换前等活跃连接归零（最长 30s）保护进行中 TCC 事务；content 试点热切后 slave 命中 **+206**（此前 master +207）；
3. **Redis 多活**：客户端 `ReadFrom.REPLICA_PREFERRED`（读本地写主）+ **服务端双主**（6379/6381 双向同步：DUMP/RESTORE 原子复制 + LWW + 30s 对账；单侧宕机不中断、**≤35s 追平**、dbsize 1871=1871）；
4. **MySQL**：zone 感知数据源（读本 zone、写主库、从库故障降级 + 30s 探测恢复）；
5. **Zone 传播**：X-Zone（Servlet Filter→ThreadLocal + Feign 出站自动带头，`myxhs_zone_propagation_total` 可观测）；
6. **动态化**：`ZoneAdminController` 热切端点（不重启、内部令牌保护、未认证 401）；
7. **演练数据**：RTO 1.31s/3.25s（kill）、4.79s（iptables 分区）；netem 跨区 25ms/向 → 同区优先吞吐 **+34%**、P99 **-41%**。
**没做的（诚实）**：异地多活/单元化 Set/GSLB——单机仿真，跨机房延迟与脑裂未模拟；动态数据源的 zone-b 指向只读副本（真多活应各 zone 独立主库）。

**③ 坑**
- **假切换**：进程 kill 后 0.55s"恢复"是假象（SIGTERM 优雅关闭仍在服务）→ 必须 `kill -9` 或等端口关闭；
- **列表快照误导**：Nacos 断连检测 ~3.3s，但 LB 本地列表缓存 TTL 默认 35s → 期间流量仍打死亡实例；改 liveness 健康检查后 RTO 6.16s→3.06s；
- **双主同步坑**：对账 tie-break 曾把单侧存在的 key 误判删除（修"存在优先"）；事件通道断开无重连会静默失效（已加重连）；
- **接线坑**：LB 配置必须在子 context（`@LoadBalancerClients`）；网关重复实现 bean 名冲突导致启动失败；鉴权白名单误区（HMAC 白名单 ≠ JWT 白名单）；
- **热切与事务并发**：等活跃连接归零（超时强切 + TCC Cancel 兜底）；
- **zone 参数没进进程**：Nacos 旧注册残留导致误判。

**④ 兜底**
- 流量面：健康检查摘除 + 同 zone 不足自动回退全局；
- 数据面：单侧宕机不中断 + 周期对账追平；MySQL 从库降级/恢复；
- 冲突：LWW（影子时间戳）+ 确定性 tie-break（存在优先/zone-a 优先）+ 防回环（值相等跳过）；
- 单元化（设计推演）：单元内自闭环、跨单元异步只读、**切流开关分级**（单元→机房→全局）、GSLB 健康检查 + TTL 收敛。

**⑤ 话术**
> "多活我分谱系和落地讲。谱系上：同城双活拼延迟和 RPO≈0，异地多活拼城市级容灾但 RPO>0，单元化是把用户切成自闭环的 Set——故障时切的是单元而不是单机。我们项目落地的是 **zone 级多活**，做了 7 条工作流：流量面 SCLB + 网关两套同区优先实现；JDBC 层 `DynamicDataSource` 热切换（等活跃连接归零保护 TCC）；Redis 客户端读本地写主 + 服务端双主 LWW 同步（单侧挂不中断、35 秒追平）；外加 zone 传播和热切端点。演练数据：进程故障 RTO 1.3-3.3 秒、网络分区 4.8 秒、跨区模拟下同区优先吞吐 +34%。**没做异地多活和单元化**，脑裂也没模拟——这是单机仿真的边界，生产级要上 GSLB + 单元化改造 + CRDT/仲裁。"

## 追问与参考回答
**追问1：同城双活和异地多活怎么选？** 看容灾目标与成本：机房级故障（断电/空调）→ 同城双活够（延迟低、可共享存储、RPO≈0）；城市级灾难（地震/洪水）→ 必须异地（代价是 20-50ms 延迟与 RPO>0 的异步同步）。多数公司分阶段：先同城双活，业务单元化后再异地。
**追问2：单元化（Set）按什么维度切？** 首选**用户/租户维度**（同一用户的所有数据落同一单元，天然避免跨单元事务）；次选商家/地区维度。关键约束：单元内**自闭环**（下单→支付→库存→履约全在一个单元完成），跨单元只做异步（对账/同步）；难点是"无法归属"的数据（全局配置、跨单元转账）要单独设计。
**追问3：跨单元数据一致性怎么保证？** 三层：① 单元内强一致（本地事务）；② 跨单元异步 + 幂等（消息/对账，接受最终一致）；③ 全局唯一性约束（如用户名）用中心服务或号段规避。不追求跨单元强一致——那是分布式事务的泥潭。
**追问4：GSLB 怎么做健康检查和切流？** DNS/HTTPDNS 按用户 ID 哈希解析到单元入口；健康检查分级（单元入口探活 → 单元内服务探活）；切流用**权重**（灰度降权 → 摘除），配合客户端 TTL（DNS 缓存收敛时间决定切流速度）；故障时先切新用户、再切存量（会话保持）。
**追问5：脑裂怎么处理？** 数据面双主脑裂 = 两侧都接受写 → 需要仲裁：① quorum（奇数节点投票，少数侧拒写）；② 单元化天然避免（单元只写自己的数据）；③ 业务兜底（幂等 + 对账 + 冲突合并）。我们项目用 LWW + 对账，但**没模拟脑裂**——这是诚实边界。
**追问6：你们的 zone 多活和真多活差多少？** 差三层：① 网络——同机仿真没有跨机房延迟/丢包/分区；② 数据——zone-b 是只读副本不是独立主库，没做单元级数据归属；③ 调度——没有 GSLB/DNS 层，切流靠 LB 健康检查。但**方法论是通的**：流量面同区优先、数据面同步+冲突解决、热切换保护事务——这三块换成真多活也是同样的问题。

## 面试官评分点
**高级开发级**：能区分同城/异地/单元化；知道数据面同步的取舍（RPO>0）。
**架构师加分**：单元化切分维度与自闭环设计；GSLB 切流分级与 TTL 收敛；脑裂仲裁思路；RPO/RTO 分级；能把项目的 zone 多活映射到谱系并**主动说边界**。
**危险信号**：把单写多读说成双活；双写无冲突策略；切流无分级；说不清 RPO；夸大成"异地多活"。
