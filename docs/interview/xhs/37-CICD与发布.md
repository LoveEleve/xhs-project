# 第37题 | CI/CD 与发布链路：门禁、版本化发布与"假成功"治理

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：Gitea Actions、act_runner、ci-gate、版本化发布、健康校验、PID 校验、假成功

## 问题
你们 CI/CD 怎么做的？发布怎么做回滚？怎么保证发布真的是新版本生效了？

## 面试可讲版（五段式）

**① 业界背景**
CI 的本质是**把质量判断自动化**（编译→单测→规范扫描→评测），CD 的本质是**把发布变成可重复、可回滚、可验证的动作**。两个最常见坑：① CI"绿灯"但没做真检查（跑了个空）；② 发布"成功"但流量还在旧进程上（假成功）——CD 的验证必须覆盖**"新版本真的在服务"**。

**② 项目选择**
- **CI（Gitea + act_runner）**：Gitea Actions 主仓镜像到本地仓库，act_runner（systemd + Docker 执行器）跑 `ci-gate.sh`：
  - 编译（common -am package）→ **单测**（`mvn test`）→ **规范扫描**（禁止 `printStackTrace()`/`System.out.println`/`@Disabled` 测试）→ 任一失败 exit 1；
  - 红/绿门禁都有实录归档（`ci-gate-red-*.txt`）；
- **CD（`release-service.sh` 版本化发布）**：
  - 每个版本落到 `/data2/releases/<module>/<时间戳>/app.jar` + `current` 软链切换；
  - 流程：停旧（**先按 pid 文件，pid 失效则按端口占用者精确清理**）→ 起新 → **健康校验** → 失败**自动回滚上一版**；
  - **健康校验必须命中"本次启动的进程"**（监听 PID == 启动 PID）——这是对"假成功"的根治；
  - 按模块 JVM 参数（512m/1024m）、保留最近 3 版；
- **多实例支持**：`INSTANCE_ID`/`PORT_OVERRIDE` 起第二实例（多活演练用），跑当前版本的独立目录、pid 独立管理；
- **"假成功"治理（血泪教训）**：早期发布存在两类假成功——① 旧手工进程占端口，新进程起不来，健康检查打到旧进程；② `nohup setsid java &` 的 `$!` 不等于真实 java PID（setsid 会 fork），PID 校验失效。修复：**端口占用者精确清理 + 以实际监听者回写 PID + 校验监听 PID==启动 PID**。

**③ 坑**
- **健康检查"看到活的"不等于"看到新的"**：必须校验 PID；否则回滚逻辑永远不触发；
- **`$!` 不可信**：setsid 包装（甚至 npm exec 多级进程链）后 `$!` 是包装进程；要回写真实 PID（监听者）；
- **端口清理只按进程名会误杀**：多实例场景按模块名 pkill 会连第二实例一起杀；按端口占用者 + 校验 jar 路径；
- **CI 在本地跑无隔离**：act_runner 的 docker 执行器要挂载 m2 缓存（加速）但不能挂源码写权限（污染）；
- **回滚也是发布**：回滚要同样走健康校验 + PID 校验，否则"回滚成功"也可能是假的。

**④ 兜底**
- 发布失败：自动回滚上一版（同样校验）；
- 无上一版：明确报错不装成功；
- CI 失败：分支红 + 阻断合并（门禁）；
- 版本管理：保留 3 版 + 磁盘治理；发布日志在 `/data2/logs/release-*.log`。

**⑤ 话术**
> "CI 用 Gitea 加 act_runner，门禁脚本做编译、单测、规范扫描（禁 printStackTrace、System.out、@Disabled），红绿都有实录。CD 是版本化发布：每版独立目录加 current 软链，停旧起新、健康校验、失败自动回滚。最值钱的一次治理是'假成功'——旧进程占端口、新进程没起来，健康检查却打到了旧进程，报发布成功；还有 setsid 导致 $! 不是真实 PID，PID 校验也形同虚设。后来改成：端口占用者精确清理、以实际监听者回写 PID、校验监听 PID 必须等于本次启动 PID，发布才敢说真的成功了。"

## 追问与参考回答
**追问1：为什么不用 Jenkins/GitLab CI？** 环境已有 Gitea（代码托管）+ act_runner 轻量可嵌入；Gitea Actions 兼容 GitHub Actions 语法，迁移成本低。
**追问2：发布为什么不做蓝绿？** 单机资源有限，做了版本化 + 回滚的"近似蓝绿"；真蓝绿需要双实例 + 流量切换（多活演练里验证过双实例启动能力，但 release 脚本本身还是停旧起新）。
**追问3：健康检查怎么定义健康？** `/actuator/health` 200 + PID 校验（本次启动）；更严格可加业务探针（接口冒烟）。
**追问4：回滚怎么保证不丢配置？** 版本目录只含 jar；配置来自 Nacos + JVM 参数（发布时传入），回滚复用同一套参数。
**追问5：CI 门禁够吗？** 门禁是底线（编译/单测/规范）；更深的质量靠评测/审计/演练（AI 项目有 eval-gate；平台有测试审计）。

## 发散追问地图（横向）
- CI：GitHub Actions/Gitea Actions/Jenkins、runner 隔离、缓存策略、矩阵构建。
- CD：蓝绿/金丝雀/滚动、版本化、回滚策略、发布审批。
- 验证：健康探针、PID 校验、冒烟测试、发布后指标观察。
- 供应链：制品仓库、依赖锁定、镜像签名。
- 事故：假成功/静默失败、发布窗口与监控联动。

## 面试官评分点
**高级开发级**：能讲门禁三件套（编译/单测/规范）与版本化发布。
**架构师加分**：**PID 校验根治假成功**；setsid/进程链的 $! 坑；多实例端口清理的精确性；回滚同样要校验；CI 与生产发布的分层。
**危险信号**：健康检查不校验进程；发布无回滚；回滚无验证；CI 只跑编译。
