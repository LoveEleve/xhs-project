# 第33题 | 内容与社交：DFA 敏感词、图片上传与关系模型

> 难度：★★★★☆｜频率：★★★★☆｜区分度：中
> 关键词：DFA/Trie、动态词库广播、魔数校验、Set/ZSet 关系模型、拆侧 Lua、24h 版本窗口

## 问题
笔记发布做了哪些校验？敏感词怎么过滤和更新？点赞/收藏/关注怎么建模？

## 面试可讲版（五段式）

**① 业界背景**
内容安全的核心是**过滤算法 + 词库运维**：正则/SQL LIKE 在 10 万词库下不可用，**DFA（Trie 树）** 一次遍历 O(n)；词库要能**热更新**（多实例同步）。社交关系是"高频幂等写 + 多维查询"：点赞用 Set（天然幂等）、时间序关系用 ZSet、互查关系用 Set/DB；难点是**半成功**（Redis 更新成功、落库失败）与**乱序回放**（旧事件覆盖新状态）。

**② 项目选择**
- **DFA 敏感词**：Trie 树启动加载（静态 classpath + 动态 Redis 词库），匹配前**文本预处理**（去空格/特殊字符/全角转半角）防绕过；运营改动通过 **Redis Pub/Sub 广播**（`sensitive-word:reload`）让所有实例重建 Trie——词库热更新无重启；
- **发布原子性**：`@Transactional` 内做 DFA 检测 + 落库；当前策略是"DFA 通过即自动发布"（无人工审核队列，诚实边界）；
- **图片上传**：大小限制 5MB（**先于** getBytes 校验防 OOM）→ **文件头魔数校验**（只读前 12 字节，防 Content-Type 伪造）→ 日期目录 + UUID 命名；本地存储可切 MinIO；
- **点赞**：Redis **Set**（`myxhs:like:note:{noteId}`，SADD 天然幂等）+ 用户反向索引 Set；双层幂等（`@Idempotent` 5s 窗口 + SADD）；
- **收藏**：ZSet（按收藏时间）或关系表；**关注**：ZSet（score=关注时间），**拆侧 Lua**（`follow_self.lua`/`follow_target.lua`：当前用户侧与目标用户侧各自原子更新）；
- **乱序防护**：点赞/收藏/关注的取消事件带 **24h 版本窗口**（`VERSION_TTL_HOURS=24`）——窗口内旧版本丢弃，防"取消事件延迟到达把新点赞抹掉"；
- **评论**：两级（一级 parent_id=0，楼中楼 parent_id=一级 ID），游标分页 + 一级评论预加载前 3 条子评论。

**③ 坑**
- **敏感词绕过**：用户在敏感词中插空格/特殊符号——预处理必须做（本项目明确）；全角半角也要归一；
- **词库更新不一致**：多实例各自持有 Trie，不广播会出现"A 实例拦、B 实例不拦"——Pub/Sub 广播重建；
- **魔数校验顺序**：先查大小再读字节（防大文件 OOM）；只读头部 12 字节（WebP 头部最长）不要全量读；
- **关系半成功**：Redis 更新成功但漏落库——对账任务修复（关注半成功可修复）；幂等去重让重放无害；
- **共同关注 OOM**：大 V 关注列表几万条，取交集前**限制条数**（防内存爆）；
- **发布无审核队列**：DFA 通过即发布是当前实现——要主动说清（不是"有完整内容审核体系"）。

**④ 兜底**
- 词库：静态 + 动态 + 广播；加载失败降级（空 Trie 不影响发布，但会打告警）；
- 上传：大小/魔数/类型三重校验；存储可切；
- 关系：SADD/ZADD 幂等 + 版本窗口 + 对账修复；
- 观测：敏感词命中数、审核拒绝数、关系对账差异。

**⑤ 话术**
> "发布链路的校验是 DFA 敏感词——Trie 树 O(n)，匹配前做空格/特殊字符/全角预处理防绕过；词库支持动态更新，运营改动通过 Redis 广播让所有实例重建 Trie。图片上传大小、魔数、类型三重校验，魔数只读头部防伪造。社交关系：点赞用 Set 天然幂等，关注用 ZSet 带时间序，拆侧 Lua 原子更新两侧；取关这类事件带 24 小时版本窗口防乱序回放。要说明的是当前是 DFA 通过即发布，没有人工审核队列。"

## 追问与参考回答
**追问1：DFA 和 AC 自动机区别？** DFA/Trie 是单模式串匹配的多词匹配；AC 自动机加失败指针，适合超大规模词库的线性匹配；10 万级词库两者都可用，DFA 实现简单。
**追问2：词库热更新怎么做？** 运营写入 Redis 词库 + PUBLISH 通知；各实例收到消息重建 Trie（volatile 引用原子替换，读请求无锁）。
**追问3：点赞为什么用 Set 不用计数器？** Set 记录"谁点了"，天然幂等（重复 SADD 无害），还能查状态；计数由计数服务单独维护（Set 人数=计数权威）。
**追问4：24h 版本窗口解决什么？** MQ 消息乱序/延迟：取消点赞的旧事件晚到，若无版本判断会覆盖掉"重新点赞"的新状态；窗口内按版本拒绝旧事件。
**追问5：拆侧 Lua 为什么拆两个脚本？** 关注要同时更新"我的关注列表"和"对方的粉丝列表"，两个 key 的原子操作在不同用户维度；拆侧后各自原子 + 事件驱动最终一致，避免跨用户大事务。

## 发散追问地图（横向）
- 内容安全：DFA/AC 自动机、敏感词变体（拼音/谐音/拆字）、机审+人审、审核队列。
- 上传存储：本地/MinIO/S3、分片上传、秒传（hash 去重）、CDN。
- 关系模型：Set/ZSet/关系表、大 V 优化（分页/缓存）、共同关注。
- 幂等与乱序：SADD 幂等、版本窗口、事件重放。
- 评论系统：两级/无限级、游标分页、热评排序、楼中楼折叠。

## 面试官评分点
**高级开发级**：能讲 DFA 原理与热更新；知道三种关系的存储选型。
**架构师加分**：预处理防绕过；广播重建的无锁实现（volatile 替换）；拆侧 Lua 的原子边界；24h 版本窗口；"无审核队列"的诚实边界。
**危险信号**：正则/ LIKE 做敏感词；词库多实例不一致；魔数校验顺序错；关系无幂等/对账。
