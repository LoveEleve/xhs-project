# 第61题 | 端到端超时预算：HTTP × MQ 全链路视角

> 难度：★★★★★｜频率：★★★★☆｜区分度：高
> 关键词：超时预算、deadline 传播、重试放大、消费链、层叠超时

## 问题
一次请求跨多个服务、还经过 MQ 异步消费，超时总预算怎么设计？哪里最容易放大？

## 面试可讲版（五段式）

**① 业界背景**
超时的本质是**预算分配**：上游给的总时限，必须 >= 下游各层超时之和 × 重试倍数，否则出现"子层还在等、全局已超时"的白等。进阶做法：deadline 传播（每层把"剩余预算"传下去，如 gRPC deadline、HTTP `X-Deadline` 头），子层超时 = min(自身超时, 剩余预算)。**重试是预算的乘数**：超时 1s + 重试 3 次 = 最坏 3s，必须显式记账。

**② 项目选择（现状盘点）**
- **HTTP 侧（Feign 统一默认配置，各服务数值不一）**：
  | 服务 | connect / read (ms) |
  |---|---|
  | order / payment / cart | 3000 / 5000 |
  | home / search | 3000 / 3000 |
  | inventory | 500 / 3000 |
  | notification / im / user / product / analytics / coupon / counter | 500 / 2000 |
- **聚合服务分层超时（唯一显式预算的地方）**：home 聚合第 1 层 800ms + 第 2 层 2s < 全局 4s，内层独立线程池（`batchFeignPool`），超时给默认值部分降级（详见第 20 题）；
- **MQ 侧**：producer `send-message-timeout: 3000`；**Producer 重试已显式固定为 2 次**（2026-09-27：此前为隐式默认；sync 最坏 3×3s=9s 阻塞；"发送超时≠失败"，靠消费者幂等/对账兜底）；消费者 `maxReconsumeTimes 3/5`（总处理 4/6 次后进 DLQ）；**消费内可再发起 Feign 调用**（home→analytics、search→product 已确认）；
- **熔断/降级**：Sentinel degrade 规则 JSON 仅 5 个服务（cart/payment/home/content + 网关流控），Feign 挂 Sentinel FallbackFactory；
- **Redis**：超时→fail-closed→503（宁可失败不给脏数据）；**Feign 无重试配置**（不放大 ✓）；`MqTraceHelper` 只传 traceId，**不传剩余预算**。

**③ 坑**
- **数值不统一**：500ms~5s 各服务自定义，没有基线表——同类调用（都打 inventory）在不同调用方超时不一样，故障时表现不一致；
- **消费链最坏时长无上限文档**：单条消息最坏 = 消费内 Feign（最多 5s）× 本地重试 + MQ 重试次数×退避；积压时"重试 × 超时"叠加放大（第 15 题 DLQ、第 20 题慢下游的交叉地带）；
- **无 deadline 传播**：上游 2s 已耗尽，下游还在跑 5s；线程/连接被白占；
- **超时位置错配**：连接超时（网络不通）与读超时（下游慢）语义不同，数值配反（连接 5s 读 2s）会放大故障感知延迟。

**④ 兜底**
- 分层聚合已有完整闭环（800ms/2s/4s + 独立池 + 部分降级 + 拒绝策略）；
- 消费者重试有界（3/5 次）→ DLQ → alert；
- Redis fail-closed + 503（不返回脏数据）；
- 排障靠 traceId 串联 + P99 分解（SkyWalking/Prometheus）。

**⑤ 话术（承认缺口 + 讲清方向）**
> "我们的超时是分服务配置的，聚合链路有真正的分层预算：800ms+2s 小于全局 4s，内层独立线程池。要说缺口：**没有全链路 deadline 传播**——traceId 传了，剩余预算没传；MQ 消费链的最坏时长也没有一张账。如果让我改：① 统一 Feign 基线（按下游能力分档）；② 关键入口带 deadline 头逐层递减；③ 把'重试 × 超时'写进预算表，禁止预算外重试。"

## 追问与参考回答
**追问1：deadline 怎么传？** 入口（网关/控制器）计算绝对截止时间，放请求头（`X-Request-Deadline`）注入 Feign 拦截器；每层取 `min(配置超时, deadline - now)`；过期直接拒绝（fail-fast），不再发起下游调用。
**追问2：重试怎么不放大？** 三个前提：① 明确可重试语义（幂等接口/只读）；② 预算内重试（剩余预算 ≥ 单次超时 × 次数）；③ 退避+抖动+熔断（下游持续失败就别再打）。我们目前 Feign 层**不重试**，重试只发生在 MQ 消费侧（有界），这是保守但安全的选择。
**追问3：MQ 消费链怎么设预算？** 消费是"拉取-处理-ACK"模型：处理超时 → 消费位点不退（重试）；所以要给单条处理设上限（本地 future.get 超时）、给消费线程池设隔离（不与 HTTP 池共用）、给积压设监控（Lag）+ 回放限速。
**追问4：怎么验证预算是对的？** 混沌注入：给下游加固定延迟（如 6s），观察上游在承诺时间内返回降级结果、线程池不堆积、无重试风暴（第 20 题的验证方法）。

## 发散追问地图（横向）
- 协议层：gRPC deadline/取消传播、HTTP/2 RST_STREAM、TCP 层超时与重试的交互。
- 治理层：Sentinel 流控/熔断/隔离、Resilience4j TimeLimiter、bulkhead。
- 容量层：Little's Law（并发 = QPS × 时延）、线程池与连接池尺寸推导、排队论拐点（第 22 题）。
- 异步层：MQ 消费的背压/限流、批量消费、影子组回放限速（第 15 题）。

## 面试官评分点
**高级开发级**：能盘点自己系统的超时现状（数值、边界）；知道"重试 × 超时"的放大关系。
**架构级**：能设计 deadline 传播与预算表；能把 HTTP 与 MQ 两条链的超时统一到一个预算模型里讲。
