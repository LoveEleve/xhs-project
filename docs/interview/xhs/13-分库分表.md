# 第13题 | 分库分表与扩容短板

> 难度：★★★★☆｜频率：★★★★☆｜区分度：高
> 关键词：ShardingSphere-JDBC、分片键、user_id % 4、4×4、订单号映射表、跨分片查询、无 rehash

## 问题
问题：订单怎么分库分表？分片键怎么选？用订单号查订单怎么办？扩容怎么做？

## 面试可讲版（五段式）

**① 业界背景**
分库分表三个方向：① 中间件代理（MyCat/ShardingSphere-Proxy，运维集中但多一跳）；② 客户端分片（ShardingSphere-JDBC，无额外部署、侵入应用）；③ 自研路由。核心设计点：**分片键选择**（高基数、分布均匀、尽量覆盖查询）、跨分片查询方案（映射表/冗余/ES）、扩容（rehash/双写迁移/一致性哈希）。共识：分片键选错，后面全是债。

**② 项目选择**
ShardingSphere-JDBC（手动 `YamlShardingSphereDataSourceFactory` 建数据源，`jdbc:shardingsphere:` 协议），订单域 **4 库 × 4 表 = 16 张逻辑表**，分片键 **user_id**：库路由 `user_id % 4` → ds0~ds3；表路由 `(user_id / 4) % 4` → t_xxx_0~3；开发环境同一 MySQL 实例的多 database 模拟分库，生产只改 jdbcUrl 指到不同实例。**订单号映射表** `t_order_no_mapping` 放公共库，解决"用订单号查订单"无法定位分片的问题（订单号补录 Job 兜底）。

**③ 坑（主动承认）**
- **无 rehash/扩容方案未落地**：4×4 是固定取模，扩分片必须双写迁移（当前是已知短板，不是设计完成品）；
- **支付表不分片**（有意拆分）：查询维度是 order_id/payment_no，不适合 user_id 分片，且未来拆独立支付服务——用独立数据源 + JdbcTemplate 绕开分片路由；
- **跨分片查询**是天花板：非 user_id 维度查询全靠映射表/ES 冗余（订单号→映射表；商品/搜索→ES）；
- 分片键倾斜：大卖家/大客户会热点分片（当前无拆分，监控兜底）。

**④ 兜底**
- 订单号映射表 + `orderMappingRepairJob` 补录，保证映射最终完整；
- 对账 Job + 事件序号唯一键保证分片内一致性；
- 影子表压测（SQL 自动改写 `_shadow` 表）在分片结构上做容量验证；
- 分片路由由中间件统一，业务代码不感知，后续换扩容方案可控。

**⑤ 话术**
> "分片键选 user_id 覆盖交易主路径；不是 user_id 的查询走映射表/ES，代价是冗余与补录；4×4 无 rehash 是明确短板——扩容方案（双写迁移）我可以说清思路，但还没落地，不假装它完成。"

## 追问与参考回答
**追问1：为什么用 user_id 而不是 order_id？** 用户查自己的订单是主路径（user_id 维度）；order_id 天然唯一但分布随机，走它会让"我的订单列表"变广播查询。
**追问2：用订单号查订单怎么定位分片？** 映射表：order_no → user_id（分片键），先查公共库再路由；写入时同步落映射，失败由补录 Job 兜底。
**追问3：扩容怎么做？** 方案：① 双倍扩容 + 双写迁移（新老分片同写，全量迁移后切读）；② 一致性哈希减少迁移量（但需业务评估）；③ 逻辑分片数 > 物理实例数预留余量（我们是固定 16，没预留，所以是短板）。
**追问4：跨分片分页/聚合怎么做？** 中间件对无分片键查询会广播+内存合并（LIMIT 越界性能差）；正确姿势是冗余到 ES 或建映射表做二次索引。
**追问5：分片后事务怎么办？** 单分片内仍是本地事务；跨分片避免强一致（按 user_id 分片天然把用户订单收在一个分片），跨域用消息+对账。

## 发散追问地图（横向）
- 全局 ID：雪花（时钟回拨）、Leaf/号段、UUIDv7、Redis INCR——分片下唯一性方案对比。
- 分片算法：取模 vs 范围 vs 一致性哈希 vs 目录（查表）路由的迁移成本对比。
- 中间件对比：ShardingSphere-JDBC/Proxy、MyCat、Vitess、业务自研路由的取舍。
- 读写分离与影子题库：主从路由（本项目 ReadWriteRoutingInterceptor）、影子表压测改写。
- 数据迁移：双写、停机迁移、DTS/binlog 回放、灰度切换与回滚。

## 面试官评分点
**高级开发级**：能画出分片路由（库/表两级取模）；知道映射表解决什么；承认扩容短板。
**架构师加分**：分片键决策依据、扩容与迁移方案、跨分片查询体系（映射/冗余/ES）、倾斜与热点治理。
**危险信号**：分片键拍脑袋；不认扩容问题；跨分片查询无方案硬广播。

## 本项目真实证据
- `sharding-config.yaml`：4 database × 4 表=16 逻辑表、分片键 user_id、库 `% 4`/表 `(/4) % 4`、同实例多库模拟、生产只改 jdbcUrl（文件头注释）。
- `ShardingSphereDataSourceConfig:41-49`：手写 YAML 建数据源；`PaymentDataSourceConfig:19-23`（支付不分片三理由）；`MappingDataSourceConfig:15`（`t_order_no_mapping` 在公共库，独立数据源）。
- `orderMappingRepairJob`（20 个 @XxlJob 之一）补录映射；影子表压测改写 `_shadow`。
