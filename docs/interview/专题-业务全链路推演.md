## 一、链路总览（单用户真实走过）

```
注册/登录 → 商品浏览(多级缓存) → 搜索(ES) → 加购(Redis) → 领券 → 下单(事务消息+预扣)
→ 支付(回调幂等) → 库存确认 → 发货 → 收货 → 发笔记/评论 → 退款(回补库存+退券)
```

## 二、逐跳机制（代码级）

### 跳1 登录 → 网关 8 过滤器
captcha 落 Redis（`myxhs:user:captcha:*`）→ 登录签发 HS512 JWT（含 jti/type=access/role）→ 后续请求带 `Authorization + X-Timestamp/Nonce/Signature`（HMAC per-session secret，见 17 题）。

### 跳2 下单：事务消息（链1 的核心）
`OrderService.createOrder`（`OrderService.java:112` 起）：

1. **幂等**：`bizIdentifier + Redis SET NX`（24h）防重复提交（:46/:112）
2. **防御纵深**：下单层再校验 SPU 上架状态（:160）、前置库存校验（:173-186，避免"订单已建但预扣失败进 DLQ"）
3. **算钱**：真实 SKU 价 + 券折扣；`payAmount = total - discount`（:188-195）
4. **半消息**：`sendMessageInTransaction(ORDER_TRANSACTION_TOPIC, ...)`（:231）
5. **本地事务**（`OrderTransactionListener.java:57`）：`INSERT t_order + t_order_item + t_local_message` 同一 DB 事务 → COMMIT/ROLLBACK
6. **消费者预扣库存**：OrderTransactionConsumer 消费后调库存预扣（注释 :27「消费者消费：Inventory 预扣库存」）
7. **防双投**：本地事务成功后 `markSuccessByTransactionId`（:255-261），LocalMessageRetryJob 30s 不再补发
8. **回查**（`OrderTransactionListener.java:103`）：Broker 60s 未收到裁定 → 查 `t_local_message`（与订单同事务写入，状态一致；有 orderNo 索引）

> 库存预扣幂等键是 `fold-hash(orderNo)` 派生的 **pseudoOrderId**（半消息阶段无真实 orderId）；释放/回补必须用同一派生值，否则记录找不到 → 库存永久泄漏（`OrderService.java:530-545`）。这是"分片+事务消息"叠加后的易错点。

### 跳3 用券：同步核销 + 失败取消订单
订单提交后同步 `couponFeignClient.useCoupon`（`OrderService.java:263-299`）：
- 券侧 `markUsed` 乐观锁 `WHERE status=0`（天然幂等+归属校验）
- 核销失败 → `cancelOrder` 释放库存，保证"打了折扣的订单必有已核销的券"
- N-7 观测：`useCoupon` 返回折扣 vs 下单折扣不一致 → WARN（模板被改，金额以 `getCouponDiscount` 为权威）

### 跳4 支付：回调双幂等 + 通知订单双通道
`PaymentService`：
- 幂等三层：Redis SETNX（:134）+ Redisson 锁（:157）+ DB 乐观锁 `WHERE status=待支付`（:285/:301）
- **支付成功 → 订单**：
  - 主通道：Feign 同步 `notifyPaySuccess`（OrderController:184）
  - 兜底1：`PAY_RESULT_TOPIC`（order 侧 `PayResultConsumer`，仅在 Feign 失败/503 时收敛）
  - 兜底2：XXL-Job `paymentNotifyCompensateJob`（扫描 status=1 超窗未收敛支付单重发，:357-359）
  - 业务拒绝（如退款后）不发 MQ，避免乱序误处理

### 跳5 库存确认 / 取消释放 / 退款回补
- 支付成功：`confirmDeduct`（`OrderService.java:802`）
- 取消/关单：`releaseStock`（:538）+ `ORDER_COMPENSATION_TOPIC` 补偿重试
- 退款：`refundRestore`（:872）——本次实测 77→75→**77 恢复**

### 跳6 退款：同步 + MQ 兜底
渠道回调 `REFUND_SUCCESS` → t_refund(status=1) → `orderFeignClient` 同步 onRefundSuccess，失败走 `REFUND_RESULT_TOPIC`（`RefundResultConsumer`：已退款+释放库存+退券）。乐观锁 `WHERE status=已支付` 幂等。

### 跳7 内容与通知
发笔记 → 评论（DFA 敏感词前置）→ 评论事件发 `NOTIFICATION_TOPIC` → `NotificationEventConsumer`：
- 两级幂等：msgId 24h + 聚合窗口 SETNX
- 跳过"自己通知自己"（`:20-24`）
- 实测跨用户：B 评论 A 的笔记 → A 收到 1 条 type=2「评论通知」✓

## 四、实测发现的两个业务边界（诚实披露，面试加分项）

### 4.1 订单域未接入通知系统（真缺口）
- **代码证据**：order 模块全量 grep `Notification` = 0；order 只发 `ORDER_CLOSE / ORDER_COMPENSATION / ORDER_TRANSACTION / PAY_RESULT / REFUND_RESULT` 五个 topic，**无 NOTIFICATION_TOPIC 生产者**。
- **运行证据**：全生命周期（创建/支付/发货/收货/退款）后 `t_notification` = 0；而同一时间跨用户评论 → 1 条通知，证明通知管道本身可用。
- **影响**：用户收不到"支付成功/已发货/退款到账"站内通知；通知域已有模板（t_push_template）、失败重试（t_push_task_fail），缺的是订单域接入。
- **面试口径**：主动说"通知能力在、订单域未接入，这是已知缺口"→ 就是 ai/18 那种"主动披露"的加分项。

### 4.2 退款后的收敛窗口（异步 + 读写分离叠加）
- **实测**：退款回调 +2s 读订单详情 status=3（旧）、+3s 读库存 75（旧）；稍后复查 master=5、库存=77，API 也=5/77。
- **机制**：退款是"Feign 同步 + MQ 兜底"异步链（ORDER_REFUNDED 事件落 t_order_event）；订单详情 SELECT 走从库（21 题读写分离 `ReadWriteRoutingInterceptor`），叠加复制延迟。
- **定性**：最终一致，秒级窗口；由对账/补偿兜底（18 题）。**不要把它说成强一致**。
- **话术**："退款链路异步收敛+从库读取，秒级窗口内可能读到旧状态；我们靠事件兜底+对账保证终态，这个窗口是对账设计的输入之一。"

## 五、2 分钟口述稿（可直接背）

"用户从挑商品到退款到账，我们这条链路是这么走的：详情读多级缓存，搜索走 Canal 同步的 ES；加购在 Redis 里用三套结构；下单用 RocketMQ 事务消息保证'订单落库'和'预扣消息'原子——本地事务写订单+明细+本地消息表，消费者再去预扣库存，预扣的幂等键是订单号派生的 pseudoOrderId；用券是同步核销+乐观锁，核销失败就取消订单释放库存；支付回调三层幂等，支付成功通知订单是 Feign 同步为主、MQ 兜底、XXL-Job 终兜底；退款同理，回补库存、退回券、订单置为已退款。整条链的失败路径都有对应兜底。实测时我发现两个边界：一是订单域还没接通知，用户收不到交易通知；二是退款是异步收敛+从库读取，秒级窗口内可能读到旧状态——这两个我都会主动讲，说明我知道系统的真实边界在哪里。"
