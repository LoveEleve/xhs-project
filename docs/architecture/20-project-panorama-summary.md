## 一、项目概述

### 1.1 项目定位

**my-xhs** 是一个对标小红书的社交+电商高并发微服务项目，覆盖内容社区、社交互动、电商交易三大核心业务线。

### 1.2 业务蓝图

```
┌─────────────────────────────────────────────────────────┐
│                    my-xhs 业务全景图                      │
├──────────────┬──────────────┬───────────────────────────┤
│  内容社区     │  社交互动     │  电商交易                  │
├──────────────┼──────────────┼───────────────────────────┤
│ • 笔记发布    │ • 关注/取关   │ • 商品SPU/SKU             │
│ • 笔记详情    │ • 粉丝列表   │ • 购物车                   │
│ • 评论系统    │ • 点赞/收藏   │ • 库存扣减                 │
│ • 内容审核    │ • Feed流     │ • 优惠券                   │
│ • 搜索/建议   │ • 计数服务   │ • 订单（下单/取消/支付）     │
│ • 热搜榜     │ • 通知推送   │ • 支付（模拟/抽象接口）      │
│ • 话题/标签   │ • IM即时通讯  │ • 分库分表                 │
└──────────────┴──────────────┴───────────────────────────┘
```

## 三、各模块架构设计及亮点

### 3.1 模块总览

| 模块 | 核心亮点 | 技术挑战 | vs 华仔差异 |
|------|---------|---------|------------|
| **用户服务** | 双Token机制（Access 30min + Refresh 7d） | 高并发注册唯一性 | 华仔单Token 7天 |
| **笔记服务** | DFA敏感词过滤（10万词库毫秒级） | 评论排序（时间+热度双ZSet） | 华仔无敏感词、仅一级评论 |
| **社交服务** | 推拉结合Feed流 + Lua原子操作 | 大V关注热点处理 | 华仔仅推模式、用List |
| **计数服务** | Buffer-Trigger批量写 + 对账修复 | 10万QPS计数不丢失 | 华仔耦合在social、直接写 |
| **商品服务** | 多级缓存（Caffeine+Redis）+ HotKey探测 | 亿级流量详情页 | 华仔无HotKey探测 |
| **搜索服务** | 独立服务 + 双索引（商品+建议） | 千万级全量同步ES | 华仔耦合在product |
| **购物车** | 3种Redis结构协同 + 匿名购物车合并 | Redis故障不丢购物车 | 华仔无匿名合并 |
| **库存服务** | 分桶预扣减 + 桶间自动均衡 | 秒杀10万QPS不超卖 | 华仔无桶间均衡 |
| **优惠券** | Lua原子领券 + 推送引擎任务分片 | 千万用户发券 | 华仔领券分两步 |
| **订单服务** | 状态机 + 事务消息 + 本地消息表兜底 | 分布式事务一致性 | 华仔无本地消息表 |
| **通知中心** | Bitmap已读状态 + SSE实时推送 | 100亿级通知存储 | 华仔无通知中心 |
| **网关** | HMAC签名 + 灰度路由 + API版本路由 | 统一鉴权+安全防护 | 华仔无HMAC/灰度 |

### 3.2 核心技术亮点（26个）

```
缓存层（6个）：
  ① 多级缓存（Caffeine+Redis+MySQL）
  ② HotKey探测自动升级本地缓存
  ③ 逻辑过期防缓存击穿
  ④ Cache Aside + 延迟双删 + Canal兜底
  ⑤ 分桶缓存（库存/计数）
  ⑥ Bitmap已读状态（空间节省99%）

消息层（5个）：
  ⑦ RocketMQ事务消息（下单）
  ⑧ 本地消息表兜底
  ⑨ 死信队列处理
  ⑩ 顺序消息（评论）
  ⑪ Buffer-Trigger批量写（计数）

数据层（5个）：
  ⑫ ShardingSphere分库分表（订单/优惠券）
  ⑬ Canal + MQ增量同步ES
  ⑭ 全量重建（断点续传+零停机别名切换）
  ⑮ 增量对账修复
  ⑯ Flyway数据库变更管理

安全层（4个）：
  ⑰ JWT双Token机制
  ⑱ HMAC签名验证（防篡改+防重放）
  ⑲ @RateLimit注解防暴力破解
  ⑳ DFA敏感词过滤

架构层（6个）：
  ㉑ 推拉结合Feed流
  ㉒ BFF聚合层（CompletableFuture并行）
  ㉓ 状态机配置化（订单）
  ㉔ 灰度路由（Nacos元数据）
  ㉕ 全链路流量染色
  ㉖ 服务降级预案（P0-P3分级）

深度技术点（11个，华仔项目未涉及）：
  ㉗ 请求级超时预算（Timeout Budget，Google SRE实践）
  ㉘ 自动降级决策引擎（多指标综合→自动L0-L3降级→半开恢复）
  ㉙ 数据倾斜检测与自动再均衡（分片监控+在线扩分片）
  ㉚ 幂等性增强：返回上次成功结果（而非报错"重复请求"）
  ㉛ 慢查询自动发现与治理闭环（slow_log→ES→Grafana→自动EXPLAIN→周报）
  ㉜ 数据生命周期自动化管理（XXL-Job分批归档+ES ILM Policy）
  ㉝ JVM调优参数模板（G1 GC科学计算+GC日志分析）
  ㉞ 连接池参数科学计算（HikariCP/Lettuce/RocketMQ公式推导）
  ㉟ API版本兼容性矩阵（版本生命周期管理+废弃通知机制）
  ㊱ Service Mesh预留设计（Spring Cloud→Istio演进路径）
  ㊲ 事件溯源（订单事件表+快照表互补，完整审计轨迹）
```

## 四、技术挑战量化

| 挑战 | 量化指标 | 解决方案 |
|------|---------|---------|
| 高并发读 | 首页Feed QPS 139 | 多级缓存 + BFF并行聚合 |
| 高并发写 | 点赞/计数 QPS 10万+ | Buffer-Trigger + Redis Lua |
| 数据一致性 | 缓存与DB不一致 | 延迟双删 + Canal兜底 + 对账修复 |
| 分布式事务 | 下单涉及6个服务 | 事务消息 + 本地消息表 |
| 热点Key | 大V/爆款商品 | HotKey探测 + 本地缓存升级 |
| 海量存储 | 订单10亿/关注10亿 | ShardingSphere分库分表 |
| 秒杀超卖 | 10万人抢1个SKU | 分桶预扣减 + Lua原子操作 |
| 搜索性能 | 千万级文档搜索 | ES 3节点集群 + 双索引 |
| 系统可用性 | 99.95% | 降级预案 + 混沌工程 + 监控告警 |
| 超时级联 | 6服务串行最坏18秒 | 请求级超时预算（Timeout Budget） |
| 人工降级滞后 | 凌晨故障无人值班 | 自动降级决策引擎（L0-L3+半开恢复） |
| 数据倾斜 | 分片数据量差10倍 | 倾斜检测 + 在线扩分片 |
| 幂等体验差 | 重复请求返回错误 | 幂等增强：返回上次成功结果 |
| 慢查询治理 | 慢查询发现靠人工 | 自动发现→EXPLAIN→周报闭环 |
| JVM调优 | GC停顿影响RT | G1科学参数 + GC日志分析 |

## 六、与华仔项目的差异总结

### 6.1 my-xhs 优于华仔的地方

| 维度 | my-xhs | 华仔 | 优势说明 |
|------|--------|------|---------|
| Token机制 | 双Token（Access+Refresh） | 单Token 7天 | 更安全，Token泄露影响范围小 |
| 网关安全 | HMAC签名+灰度路由+API版本 | 基础路由 | 防篡改+防重放+灰度发布 |
| 评论系统 | 楼中楼+DFA敏感词+双ZSet排序 | 一级评论 | 更完整的评论体系 |
| 社交Feed | 推拉结合 | 仅推模式 | 大V场景不会写扩散爆炸 |
| 计数服务 | 独立服务+Buffer-Trigger+对账 | 耦合在social | 解耦+高性能+数据可靠 |
| 通知中心 | 完整通知+Bitmap+SSE | 无 | 完整的通知体系 |
| 库存 | 分桶+桶间均衡+预扣超时回退 | 分桶 | 更完善的库存方案 |
| 订单 | 状态机+事务消息+本地消息表 | 事务消息 | 多一层兜底保障 |

### 6.2 华仔优于 my-xhs 的地方（已采纳补充）

| 维度 | 华仔 | my-xhs 原状 | 采纳措施 |
|------|------|-----------|---------|
| 亿级数据生成 | 有完整方案 | ❌ 缺失 | ✅ 已补充 `massive-data-generation.md` |
| 全链路压测 | GoReplay实战 | 仅JMeter单接口 | ✅ 已补充 GoReplay 章节 |
| 流量漏斗模型 | 有科学推算 | 拍脑袋 | ✅ 已补充流量漏斗推算 |
| 监控体系 | 5篇详细实战 | 骨架文档 | ⏳ 后续增强 |
| 简历写法 | 有具体模板 | 空规划 | ⏳ 后续增强 |

### 6.3 华仔方案不采纳的地方

| 华仔方案 | 不采纳原因 |
|---------|----------|
| Nginx mirror 流量镜像 | mirror子请求阻塞nginx、reload影响线上，GoReplay更优 |
| JVM-Sandbox-Repeater | 挂载瞬间占资源可能导致服务夯住，功能不完善需二次开发 |
| TcpCopy | 需部署intercept辅助服务器，不支持应用层协议解析 |
| Rancher 2.x | 已过时，K8s原生方案更通用 |
| 布隆过滤器注册查重 | 有误判率，注册是强一致场景，分布式锁+唯一索引更可靠 |
| ES 7.9.3 | 版本过旧，my-xhs 用 ES 8.x |
| 前端 Vue 管理后台 | my-xhs 定位后端项目，前端不是重点 |

## 七、面试考察点

### Q1: 介绍一下你的项目（1分钟版本）

> "我做的是一个对标小红书的社交+电商微服务项目，覆盖内容社区、社交互动、电商交易三大业务线。技术上用 Spring Cloud 微服务架构，12个核心服务，设计目标100万DAU。核心亮点包括：多级缓存+HotKey探测扛高并发读、Buffer-Trigger+Lua原子操作扛高并发写、推拉结合Feed流、事务消息+本地消息表保证分布式事务、ShardingSphere分库分表支撑10亿级数据。"

### Q2: 项目最大的技术挑战是什么？

> "最大的挑战是数据一致性。系统中有多处'写MySQL+写Redis+写ES'的场景，任何一步失败都会导致数据不一致。我的方案是三层保障：第一层延迟双删（毫秒级）、第二层Canal监听binlog异步补偿（秒级）、第三层定时对账修复（分钟级）。三层叠加后，数据不一致的窗口从'可能永久'缩小到'最多几分钟自动修复'。"

### Q3: 你的项目和网上的教程项目有什么区别？

> "三个核心区别：第一，数据量真实——我造了1000万用户、5000万笔记、10亿关注关系的测试数据，不是空库跑demo；第二，方案有取舍——每个技术选型都有多方案对比和选型理由，不是拿来就用；第三，有生产级考量——降级预案、监控告警、混沌工程、全链路压测都有规划，不是'能跑就行'。"
