## 三、调用层级定义

> 第N层只能调用第N+1层及以下的服务，**禁止反向调用**（防止循环依赖）

```
Layer 0: Gateway（入口层）
   ↓
Layer 1: Home（聚合层，只聚合不对外提供服务）
   ↓
Layer 2: 业务服务层（Note, Social, Product, Search, Cart, Order, IM）
   ↓
Layer 3: 基础服务层（User, Counter, Inventory, Coupon, Push）
   ↓
Layer 4: 基础设施层（MySQL, Redis, MQ, ES）
```

### 层级规则

| 规则 | 说明 | 原因 |
|------|------|------|
| 禁止同层循环调用 | Social → Note → Social ❌ | 死循环、无限重试 |
| 禁止反向调用 | Counter → Social ❌ | 基础服务不能依赖业务服务 |
| 允许跨层调用 | Order → User ✅（跳过Layer2） | 减少不必要的中转 |
| 允许同层单向调用 | Note → Counter ✅（Layer2→Layer3） | 业务需要计数 |

## 四、核心调用链路详解

### 4.1 下单链路（最复杂，涉及6个服务）

```
Gateway → Order → Inventory（扣库存）
                → Coupon（扣券）
                → Cart（清购物车）
                → User（获取地址/扣积分）
                → Product（获取商品信息/快照）
                → Push（发送订单通知）
                → Search（同步订单到ES，异步）
```

**调用方式**：
- 同步调用（Feign）：Inventory、Coupon、Cart、User、Product
- 异步调用（MQ）：Push、Search（Canal同步）
- 事务保障：RocketMQ事务消息 + 本地消息表

### 4.2 Feed流链路（读聚合）

```
Gateway → Home → Social（获取关注列表/关注状态）
               → Note（获取笔记内容）
               → Counter（获取点赞/收藏/评论数）
               → User（获取用户信息）
               → Search（获取推荐内容，发现流）
               → Push（获取通知数）
```

**调用方式**：全部同步调用（CompletableFuture并行编排）

### 4.3 笔记发布链路

```
Gateway → Note → Counter（初始化计数）
               → Push（通知粉丝，异步）
               → User（校验用户状态）
               → Search（同步笔记到ES，异步，Canal）
```

### 4.4 社交互动链路（点赞/评论/关注）

```
Gateway → Social → Note（校验笔记是否存在）
                 → Counter（更新计数）
                 → User（获取用户信息）
                 → Push（发送互动通知，异步）
```

## 五、循环依赖检测与预防

### 5.1 已识别的风险点

| 风险调用 | 场景 | 是否允许 | 解决方案 |
|----------|------|---------|---------|
| Social ↔ Note | Social需要笔记信息，Note需要社交状态 | ❌ 禁止双向 | Social→Note单向，Note通过MQ异步获取关注状态 |
| Order ↔ Inventory | 下单扣库存，库存回退调订单 | ❌ 禁止双向 | Order→Inventory单向，库存回退通过MQ通知Order |
| Counter ← 任何服务 | 计数是基础服务 | ✅ 允许 | Counter不反向调用任何业务服务 |
| Push ← 任何服务 | 通知是基础服务 | ✅ 允许 | Push不反向调用任何业务服务 |

### 5.2 防止循环依赖的架构原则

```
原则1：基础服务（Counter/Push）不反向调用业务服务
原则2：业务服务间需要双向数据时，用MQ异步解耦
原则3：聚合服务（Home）只读不写，不对外提供服务接口
原则4：数据查询走ES宽表，不走跨服务实时查询
```

## 六、Feign Client 定义规范

### 6.1 每个 Feign Client 必须标注层级

```java
// ✅ 正确：标注层级，便于检测
@FeignClient(name = "my-xhs-counter", contextId = "counterClient")
@Layer(level = 3, description = "基础服务-计数")
public interface CounterClient {
    @GetMapping("/api/counter/get")
    CounterDTO getCounter(@RequestParam String bizType, @RequestParam Long bizId);
}

// ❌ 错误：基础服务反向调用业务服务
@FeignClient(name = "my-xhs-social")  // Counter不应该调用Social
@Layer(level = 3)  // Layer3禁止调用Layer2
public interface SocialClient { ... }
```

### 6.2 调用方式选择矩阵

| 场景 | 同步(Feign) | 异步(MQ) | 说明 |
|------|-----------|---------|------|
| 需要立即获取结果 | ✅ | ❌ | 查用户信息、查库存 |
| 结果可以延迟处理 | ❌ | ✅ | 发通知、同步ES、更新计数 |
| 需要事务保障 | ✅ 事务消息 | ✅ | 下单=事务消息，通知=普通消息 |
| 可能失败但可重试 | ❌ | ✅ | 通知推送、ES同步 |
| 服务不可用时的兜底 | ❌ | ✅ | MQ堆积可恢复，Feign调用失败立即返回错误 |

## 七、服务间数据共享策略

| 策略 | 使用场景 | 示例 |
|------|---------|------|
| Feign实时调用 | 需要最新数据，低频调用 | 下单时查用户地址 |
| ES宽表冗余 | 高频查询，允许短暂延迟 | 订单搜索=订单+商品信息宽表 |
| MQ事件广播 | 数据变更通知 | 笔记发布→通知Search同步ES |
| 数据库共享(❌禁止) | — | 不同服务绝不共享数据库 |

## 八、生产决策与表达

### Q: 服务间调用会不会形成循环依赖？

> "我们定义了严格的4层调用架构：Gateway→聚合层→业务层→基础层。基础服务（Counter/Push）不反向调用任何业务服务。业务服务间需要双向数据时，用MQ异步解耦。同时CI流水线中有依赖检测工具，自动扫描Feign Client构建依赖图，有环则构建失败。"

### Q: 下单链路调了6个服务，RT会不会很长？

> "同步调用的关键路径是：Order→Inventory(5ms)→Coupon(5ms)，Cart清空异步不阻塞。CompletableFuture并行编排把User查询和Product快照查询并行化。整个链路P99控制在500ms以内。非关键路径（Push通知、ES同步）全部走MQ异步，不阻塞主流程。"

### Q: 如果一个基础服务挂了，会影响多少业务？

> "Counter挂了：点赞/收藏数不显示，但点赞/收藏操作正常（Redis直写）；Push挂了：通知延迟，不影响核心链路；User挂了：无法登录，属于P0故障。所以User服务实例数>=3，Counter/Push实例数>=2。"
