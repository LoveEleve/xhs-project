## 二、核心设计决策详细溯源

### 2.1 计数服务 — Buffer-Trigger 方案

**my-xhs 设计**：点赞/收藏/评论数不直接写DB，而是先写Redis缓冲区，攒批100条或1秒后批量写入DB。

**知识来源**：《亿级流量系统架构设计与实战》第3章

```
书中原文：
"微博计数器方案：写请求→Redis INCR→本地缓冲→定时合并→批量持久化"

核心思想：
1. 写请求先落Redis（毫秒级响应）
2. 本地缓冲区攒批（减少DB写入次数）
3. 相同Key的增减合并（+1, -1, +1 = +1，一次写入）
4. 批量INSERT ON DUPLICATE KEY UPDATE（DB压力降100倍）
```

**my-xhs 实现对照**：

| 书中方案 | my-xhs 实现 |
|----------|-------------|
| Redis INCR | ✅ `counter:{bizType}:{bizId}` |
| 本地缓冲 | ✅ Caffeine本地缓存 |
| 定时合并 | ✅ 100条/1秒触发 |
| 批量持久化 | ✅ `INSERT ... ON DUPLICATE KEY UPDATE` |
| 对账修复 | ✅ XXL-Job定时扫描Redis↔DB差异 |

### 2.2 Feed流 — 推拉结合方案

**my-xhs 设计**：普通用户发笔记用推模式（写扩散到粉丝收件箱），大V用拉模式（读时聚合）。

**知识来源**：《亿级流量系统架构设计与实战》第4章

```
书中原文：
"微信朋友圈Feed流：
- 普通用户发动态 → 推送到所有好友的收件箱（写扩散）
- 大V发动态 → 不推送，读取时再聚合（读扩散）
- 判断标准：粉丝数 > 10万 则为大V"

核心权衡：
- 推模式：写放大，但读极快
- 拉模式：读放大，但写极快
- 推拉结合：两全其美
```

**my-xhs 实现对照**：

| 书中方案 | my-xhs 实现 |
|----------|-------------|
| 推模式写扩散 | ✅ 发笔记→查粉丝列表→遍历写收件箱ZSet |
| 拉模式读扩散 | ✅ 读Feed时合并关注的大V动态 |
| 大V判断 | ✅ 粉丝数>10万标记为大V |
| 粉丝分桶 | ✅ 大V粉丝按ID分桶，异步推送 |

### 2.3 分布式事务 — 事务消息+本地消息表

**my-xhs 设计**：下单同时扣库存、扣优惠券，用RocketMQ事务消息+本地消息表双保险。

**知识来源**：《深入理解分布式事务》第6章 + 《凤凰架构》第3章

```
《深入理解分布式事务》：
"可靠消息最终一致性方案：
1. 发送Half消息（不可消费）
2. 执行本地事务
3. 成功则Commit，失败则Rollback
4. RocketMQ回查机制兜底"

《凤凰架构》补充：
"本地消息表是最后的兜底：
1. 本地事务中同时写业务表和消息表
2. 定时任务扫描消息表，投递到MQ
3. 投递成功后标记已处理"
```

**my-xhs 实现对照**：

| 书中方案 | my-xhs 实现 |
|----------|-------------|
| 事务消息Half | ✅ `TransactionMQProducer` |
| 本地事务执行 | ✅ 创建订单+扣库存+扣券 |
| Commit/Rollback | ✅ 根据本地事务结果 |
| 本地消息表 | ✅ `t_local_message`表兜底 |
| 定时扫描补偿 | ✅ XXL-Job每分钟扫描未投递消息 |

### 2.4 缓存一致性 — Cache Aside + 延迟双删 + Canal

**my-xhs 设计**：写操作先更新DB→删Redis→延迟双删，Canal监听binlog异步兜底。

**知识来源**：《分布式缓存：原理、架构及Go语言实现》第5章

```
书中原文：
"缓存一致性三层保障：
1. 同步删缓存（先更新DB，后删缓存）
2. 延迟双删（解决并发读写问题，延迟500ms再删一次）
3. 异步监听binlog（最终一致性兜底）"

为什么不先删缓存后更新DB？
"线程A删缓存→线程B读DB旧值写缓存→线程A更新DB
结果：缓存是旧值，DB是新值，不一致！"
```

**my-xhs 实现对照**：

| 书中方案 | my-xhs 实现 |
|----------|-------------|
| Cache Aside | ✅ 读先查缓存，写先更新DB |
| 延迟双删 | ✅ `@CacheEvict` + 500ms后异步再删 |
| binlog监听 | ✅ Canal → MQ → 删缓存 |

### 2.5 高并发库存 — 分桶预扣方案

**my-xhs 设计**：库存按SKU拆分N个桶，用户按userId路由到固定桶，单桶失败尝试其他桶。

**知识来源**：《超大流量分布式系统架构解决方案》第7章

```
书中原文：
"秒杀库存分桶方案：
1. 1000库存 → 拆成10个桶，每桶100
2. 用户按userId % 10 路由到固定桶
3. 单桶扣减失败 → 遍历其他桶尝试
4. 桶间自动均衡（监控各桶余量，低于阈值从其他桶借）"

核心思想：
"热点Key分桶，本质是把N个请求对1个Key的竞争，分散成对N个Key的竞争"
```

**my-xhs 实现对照**：

| 书中方案 | my-xhs 实现 |
|----------|-------------|
| 库存分桶 | ✅ `inventory:bucket:{skuId}:{bucketId}` |
| 用户路由 | ✅ `userId % bucketNum` |
| 桶间漫游 | ✅ 单桶失败→尝试下一个桶 |
| 自动均衡 | ✅ XXL-Job定时检测+借调 |
| Lua原子扣减 | ✅ EVAL脚本保证原子性 |

### 2.7 性能优化 — 全链路思维

**my-xhs 设计**：性能基线（QPS/RT/成功率）+ 容量水位 + 压测报告。

**知识来源**：《性能之道：分布式系统全栈性能优化》+ 《大型网站性能优化实战》

```
《性能之道》四维模型：
"点：单个接口/SQL优化
 线：调用链路整体优化
 面：单服务全面优化
 体：全系统整体优化"

《大型网站性能优化实战》公式：
"单线程QPS = 1000ms / RT
 最佳线程数 = (RT / CPU时间) × CPU核数
 
 例：RT=100ms，CPU时间=10ms，4核
 最佳线程数 = (100/10) × 4 = 40"
```

**my-xhs 实现对照**：

|----------|-------------|

| 压测报告 | ✅ JMeter+GoReplay |

### 2.8 高可用 — 五大核心要素

**my-xhs 设计**：性能、可用性、可伸缩、可扩展、安全。

**知识来源**：《大型网站技术架构：核心原理与案例分析》（李智慧）

```
书中原文：
"大型网站架构5大核心要素：
1. 性能：响应时间、吞吐量、并发数
2. 可用性：7×24小时不间断，99.99%
3. 可伸缩：加机器能加性能
4. 可扩展：新功能不影响旧功能
5. 安全性：防攻击、防泄露"

可用性计算：
"99.9% = 年宕机8.76小时
 99.99% = 年宕机52.56分钟
 99.999% = 年宕机5.26分钟"
```
