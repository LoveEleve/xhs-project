# my-xhs 架构决策分析：设计完整 vs 实现分阶段

> 设计上考虑亿级场景不是过度设计，是架构深度。真正要区分的是"设计"和"实现节奏"。
> 架构师的价值不在于"只做够用的"，而在于"知道什么场景用什么方案，并设计好演进路径"。

---

## 一、核心观点

```
设计完整 ≠ 过度设计
实现分阶段 ≠ 偷懒减配

设计层面：完整保留所有方案（15个服务、4版演进、推拉结合、分桶……）
实现层面：按阶段演进（V1先跑通核心链路，按需演进到完整版）
```

**面试官更想听的是**：
> "库存扣减我设计了4版演进——V1 DB直接扣QPS 500就扛不住，V2 Redis预扣但单Key热点，
>  V3 分桶但不均匀，V4 分桶+自动均衡。我的系统当前用的是V4，因为架构上保证了扩展性。"

而不是：
> "我用了Redis预扣，够用了。"

---

## 二、设计完整性论证

### 2.1 为什么设计要完整

| 设计决策 | 只做够用的 | 设计完整 |
|----------|-----------|---------|
| Feed流 | 纯推模式 | 推拉结合+大V处理+粉丝分桶 |
| 库存扣减 | Redis预扣 | 4版演进+分桶+自动均衡 |
| 计数服务 | 直接写DB | Buffer-Trigger+对账 |
| 服务数量 | 8个合并 | 15个独立服务 |
| 分库分表 | 单库单表 | 分片策略+读写分离 |

**设计完整的理由**：

1. **展示架构深度**：面试官看到你考虑了亿级场景的设计，比"我只做了MVP"更有说服力
2. **演进路径清晰**：4版演进不是4个独立方案，而是一条有逻辑的演进路线——说明你理解每一步为什么要升级
3. **扩展性保障**：架构上保证了可扩展，需要演进时不需要重构
4. **学习深度**：只学1种方案和学4种方案及演进路径，理解深度完全不同

### 2.2 真正的过度设计

| 真正的过度设计 | 说明 | my-xhs有没有 |
|---------------|------|-------------|
| 为不存在的场景写代码 | 实现了群聊但不需要 | ❌ 没有 |
| 引入不需要的中间件 | Flink流计算但无实时需求 | ❌ 没有 |
| 复杂度超过收益 | 10行代码用3个设计模式 | ❌ 没有 |
| 数据量未到就分片 | 1000行就分库分表 | ❌ 没有（设计预留，实现按需） |

## 三、实现节奏规划

### 3.1 三阶段实现

```
Phase 1（跑通核心链路）：
  实现最少代码让系统跑起来
  - 8个服务（部分合并为模块化单体）
  - Redis预扣库存（V2）
  - 纯推模式Feed流
  - 事务消息下单（本地消息表预留接口）
  - 单库单表（分片配置预留）

Phase 2（补齐生产级方案）：
  按需演进到设计文档中的完整方案
  - 拆分到15个服务
  - 库存分桶（V4）
  - 推拉结合Feed流
  - 双保险分布式事务
  - 分库分表

Phase 3（独立领域深入）：
  在完整版基础上，对6个独立领域做深入学习
  - 搜索（ES调优、向量搜索）
  - Feed流（推荐算法、内容去重）
  - IM（群聊、消息漫游）
  - 通知（多端同步、推送A/B测试）
  - 交易（TCC、支付集成）
  - 库存（秒杀排队、防刷策略）
```

### 3.2 Phase 1 实现优先级

| 优先级 | 模块 | 核心功能 | 理由 |
|--------|------|----------|------|
| P0 | common | R、@Idempotent、@DistributedLock、@RateLimit、RedisOperator | 所有服务的基础 |
| P0 | gateway | 路由+JWT鉴权+限流 | 没网关跑不起来 |
| P0 | user | 注册/登录/Token | 没用户什么也做不了 |
| P0 | note | 笔记CRUD+评论 | 小红书核心内容形态 |
| P0 | social | 关注/点赞/Feed(纯推) | 社交是核心差异化 |
| P0 | counter | Buffer-Trigger计数 | 点赞/收藏数展示 |
| P0 | product | SPU/SKU | 电商基础 |
| P0 | trade | 购物车+库存(V2)+优惠券+订单 | 交易链路（Phase 1合并为1个服务，内部模块化） |
| P0 | search | ES搜索+建议 | 内容/商品发现 |
| P1 | push | MQ异步+SSE推送 | 社交体验闭环 |
| P2 | home | 首页聚合 | 调用已有服务即可 |
| P2 | im | WebSocket私信 | 独立系统 |
| P2 | admin | 后台管理 | 内部工具 |

### 3.3 Phase 1 中的模块化单体

```
my-xhs-trade（Phase 1 合并服务，内部模块化）
├── com.myxhs.trade.cart      # 购物车模块
├── com.myxhs.trade.inventory  # 库存模块
├── com.myxhs.trade.coupon     # 优惠券模块
├── com.myxhs.trade.order      # 订单模块
└── com.myxhs.trade.config     # 共享配置
```

**合并理由**：交易链路4个服务紧密耦合（下单要同时调4个），合并后：
- 服务间调用变成本地方法调用，RT从200ms降到50ms
- 不需要分布式事务（同一个Spring事务）
- 运维成本降低（4个Docker镜像→1个）

**拆分条件**：当某个模块的QPS远超其他模块时拆出。例如秒杀场景库存QPS是订单10倍，库存独立扩容。

## 四、每项设计决策的完整定位

| 设计决策 | 设计文档 | Phase 1实现 | 完整版实现 | 拆分/演进条件 |
|----------|----------|------------|-----------|-------------|
| Buffer-Trigger | 攒批100条/1秒 | **攒批10条/5秒** | 动态调整 | 计数QPS>1万时调整 |
| Feed流 | 推拉结合 | **纯推模式** | 推拉结合 | 出现粉丝>5万KOL时 |
| 库存扣减 | 4版分桶 | **V2 Redis预扣** | V4 分桶+均衡 | 秒杀QPS>5万时 |
| 分布式事务 | 事务消息+本地消息表 | **事务消息(本地消息表预留)** | 双保险 | 生产稳定性要求高时 |
| 微服务 | 15个服务 | **8个(模块化)** | 15个 | 单模块QPS超集群50%时拆分 |
| 分库分表 | 4库8表 | **单库单表(预留分片)** | 分库分表 | 单表>1000万行时 |
| 商品缓存 | refreshAfterWrite | **分字段策略** | 同左 | — |
| 通知推送 | SSE集群 | **SSE单实例** | SSE+Redis Pub/Sub | 多实例部署时 |
| 支付 | 接口抽象 | **MockPayService** | AlipayPayService | 上线时 |

## 五、独立判断总结

### 我同意书中方案的（正确且必要）

| 决策 | 书中方案 | 我同意的理由 |
|------|----------|-------------|
| Buffer-Trigger计数 | ✅ | 高频写攒批是正确思路 |
| Cache Aside+延迟双删+Canal | ✅ | 三层保障各有分工，没有冗余 |
| 事务消息下单 | ✅ | 电商场景最佳实践 |
| Redisson分布式锁 | ✅ | 看门狗续期解决业务未完成锁过期的问题 |
| Sentinel限流熔断 | ✅ | 网关层统一容错是正确架构 |
| SSE替代WebSocket推送 | ✅ | 通知是单向推送，这是我的独立判断 |

### 我补充书中没有的（独立设计）

| 决策 | 我的补充 | 理由 |
|------|---------|------|
| 模拟支付 | PayService接口+MockPayService | 链路完整跑通，不依赖第三方 |
| 分字段缓存策略 | 基础信息+价格分开缓存 | 价格不能缓存旧值，订单争议 |
| 模块化单体→微服务 | Phase 1合并交易链路 | 降低运维复杂度，按需拆分 |
| 购物车3种Redis结构 | Hash+Set+ZSet | 1个Key搞不定，3种结构各取所长 |

### 我质疑但最终保留的（设计完整，实现分阶段）

| 决策 | 质疑 | 最终判断 |
|------|------|---------|
| 15个服务 | 2-3人维护15个服务？ | **设计15个，实现先8个** |
| 库存分桶 | 1万QPS不需要分桶？ | **设计4版演进，实现先V2** |
| 推拉结合 | 100万DAU没有大V？ | **设计推拉结合，实现先纯推** |
| 本地消息表 | 事务消息回查99.99%够用？ | **设计双保险，实现先事务消息** |

> **核心理念**：架构师的价值不是"只做够用的"，而是"知道什么场景用什么方案，并设计好演进路径"。
> 设计要完整（展示深度），实现要分阶段（务实落地），两者不矛盾。
