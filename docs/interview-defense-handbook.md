# xhs 平台面试防御手册（29 个主题速查 + 8 个高危问题 + 23 篇深挖长文）

> 用法：每个主题按 **设计 → 争议/备选 → 已知坑 → 兜底 → 话术** 五段掌握。
> 原则：**坑要主动承认，兜底要能说清边界**——面试官最反感"我们没问题"，最喜欢"我们知道这里有问题，所以这样兜"。

## A. 分布式锁与并发控制

- **设计**：Redisson RLock 直连锁 + 显式租期（10s~7200s：支付/用户/缓存单飞 10s、库存 30s、SPU 300s、索引重建 7200s、Job 4~50s），解锁统一 `isHeldByCurrentThread()`。注解切面（@Order(50)/watchdog/fail-open）为框架件未接入；消息幂等用 helper 显式 SETNX 去重。
- **争议**：RedLock（多节点多数派）vs Redisson+DB 兜底 vs ZK+fencing。项目注释明确放弃 RedLock（运维复杂 + Kleppmann 已论证其局限）。
- **坑**：
  - Redis 异常时加锁直接失败（fail-closed，拒绝/跳过）；切主丢锁窗口只影响效率；
  - 10s 锁在多 Feign 串行下可能过期，同用户出现两单；
  - 释放失败仅告警。
- **兜底**：DB 乐观锁/唯一键是最终防线；Sentinel 切主 `retryAttempts=5×1000ms`；抢锁失败直接拒绝（支付）/跳过（Job）。
- **话术**：
  > “我们把锁定位成效率工具而不是正确性保证。加锁点都在关键路径直连 Redisson、显式租期：抢锁失败就拒绝或跳过，Redis 挂了加锁直接失败（fail-closed）——宁可暂时不可用也不冒险重复执行。真正防重靠 DB 唯一键和状态机条件更新。Sentinel 切主确实有丢锁窗口，所以没上 RedLock，也没把 fencing 责任交给锁本身。”

## B. 缓存穿透/击穿/雪崩与一致性

- **设计**：CacheHelper 三件套——更新 DB 后删缓存重试 3 次、延迟双删 500ms、失败发 `CACHE_EVICT_TOPIC`；读 miss 用分布式锁 singleflight；空值占位 2 分钟；TTL 加 1/6 随机；商品侧补 Bloom + 逻辑过期异步刷新。
- **争议**：延迟双删（时间窗假设）vs 订阅 binlog/Canal 删缓存；空值缓存 vs 布隆过滤器（两层互补）。
- **坑**：
  - 500ms = 主从 200ms + 读 100ms + 余量，环境变慢就失效；
  - Bloom 启动时 DB 为空会导致后插数据被拦（运行态 #11，需重启重建）；
  - 缓存 Redis 与业务 Redis 已拆实例（allkeys-lru vs noeviction），但部分 cache 模板无业务引用。
- **兜底**：预热失败不阻塞启动；Bloom 不可用降级放行 + 空值兜底；Redis 故障直查 DB 不回填；逻辑过期防击穿。
- **话术**：
  > “延迟双删本质是赌时间窗，我们承认；所以配了三层保险：删缓存重试、MQ 广播失效、每日对账。如果重来一次，我会优先上 Canal 订阅，把时间窗假设拿掉。”

## C. 库存分桶 + Lua + DB 一致性

- **设计**：`inventory:{skuId}:total/bucket:N` 同 hash tag；`prededuct.lua` 原子做幂等检查→路由桶→不足遍历他桶→写预扣 Hash/ZSet；Java 侧 `floorMod` 路由（避免 Lua 双精度对大 ID 取模失真）；MySQL 预扣幂等表兜底；MQ 失败回滚 Redis。
- **争议**：单 Key DECR（简单、热点集中）vs 分桶（并发分散、需桶遍历）；Redis 权威 vs DB 直接扣。
- **坑**：reinit/resize 没有统一暂停屏障；幂等占位无 processing/sent 状态，崩溃会卡单；SKU 不存在时直接 ACK 可能出现“订单提交了库存没扣”。
- **兜底**：超时 Job 按 ZSet 60s 释放 + Outbox 补发 + 对账以 Redis 修 MySQL；canal 误删后自愈重建桶；20 并发/超量实测不超卖。
- **话术**：
  > “Redis 和 MySQL 之间没有事务，我们用的是‘Redis 先扣 + 幂等占位 + Outbox + 超时回补 + 对账’的最终一致。Lua 只保证单次 Redis 原子，跨存储的一致性靠补偿和对账，不装成强一致。”

## D. TCC fence（空回滚/悬挂）

- **设计**：仿 Seata TCC Fence：`t_tcc_fence` 唯一键插入 + 状态机 1(Try)→2(Confirm)/3(Cancel)；Try 遇 3 判悬挂拒绝；Confirm/Cancel 用 `UPDATE ... AND status=1` 幂等。
- **争议**：Seata AT/TCC/Saga vs 裸 TCC+Fence；Fence 独立表 vs 复用业务行状态；超时取消按 xid 明细 vs 按 SKU 聚合（旧实现已淘汰）。
- **坑**：Confirm/Cancel 对影响行数与库存状态校验不足；**TCC 与普通分桶是两本账**，对账 Job 有可能覆盖 TCC 状态。
- **兜底**：迟到 Confirm 被 fence 拒；并发双 Cancel 只有一次执行；超时 Job 先写 fence 再解冻；**11 场景（幂等/空回滚/悬挂拒绝/超量拒绝/fence 状态机 1→2/3）直接调用实测通过**（test-4 运行态对账报告第六轮），另有 FINAL-HANDOFF 五场景与 test-3 G5-02-06/07 佐证。
- **话术**：
  > “TCC 只用在专项链路，和普通分桶库存确实是两本账，文档里也标了风险。面试里我会主动说这是已知边界：混用场景必须靠对账隔离，而不是假装统一。”

## E. 事务消息 + 本地消息表 + 回查

- **设计**：半消息 → `executeLocalTransaction` 同事务写订单/明细/本地消息 → COMMIT；Broker 回查 `checkLocalTransaction` 查本地消息表决定 COMMIT/ROLLBACK/UNKNOWN。
- **争议**：事务消息 vs 纯本地消息表 vs Outbox 双写；回查查本地消息表（同事务、有索引）vs 查订单表；补发是 at-least-once 不是 exactly-once。
- **坑**：本地消息不标已投递时，30s 补发 Job 会**双投**；无 user_id 的补发走广播，分片下 LIMIT 截断可能乱序；MQ 全挂时下单 500 fail-closed。
- **兜底**：`markSuccessByTransactionId` 消除双投；补发指数退避 30s~480s×5 → 死信 status=3 + 每小时死信扫描重投；消费端幂等；75s 回查延迟注入实测库存只扣一次。
- **话术**：
  > “我们说的是最终一致，不是恰好一次。回查负责把半消息收敛，补发负责 Broker 挂了也能兜，重复投递由消费端幂等吃掉——每一层都有兜底，但每层都不是‘绝不出错’。”

## F. 幂等体系（四层）

- **设计**：① Redis SETNX（注解式 + 消息去重 Helper + 业务键）② DB 唯一键（`uk_msg_id`/`uk_claim_no`/`uk_order_event_seq`/预扣幂等表）③ 状态机条件 UPDATE ④ Set 结构天然幂等。
- **争议**：Redis 去重（快、TTL）vs DB 唯一键（强、可回滚）vs 状态机（终态收敛）；Helper 注释明说“强幂等必须 DB 唯一索引兜底”。
- **坑**：Redis 不可用时幂等 fail-open；通知表无天然唯一键只能靠 24h Redis 幂等；幂等键释放策略要对（事务提交前失败才释放）。
- **兜底**：所有关键写路径都有唯一键；状态机收敛重复事件；异常分类决定是否删标记。
- **话术**：
  > “幂等不是一把锁能解决的，是 Redis 去重 + 唯一键 + 状态机三层同时上。Redis 只挡第一波，最终防重靠数据库约束。”

## G. 消息乱序与版本控制

- **设计**：业务版本号——库存 `eventTime` Lua 原子比较；社交 `actionTime` + 24h 窗口；购物车 CLEAR 屏障 + DB `updatedAt` 比较；ES 用 Canal `ts` 作 external version + tombstone；首页已删标记 5 分钟拦晚到推送。
- **争议**：单队列顺序消费/分区有序 vs 业务时间戳版本；时间戳 vs binlog offset；最终态交对账 vs 严格因果序。
- **坑**：同毫秒版本相等会**互相跳过**；`eventTime=null` 不拦截；跨 action 共用版本 key 会让早到的 PRE_DEDUCT 被跳过；ES 同毫秒同版本写入被拒。
- **兜底**：购物车 catch 二次校验防 TOCTOU；计数用 Set 天然抗乱序；search 实测 001→000→002 拒绝低版本；相等场景靠对账收敛。
- **话术**：
  > “时间戳版本不是严格因果序，同毫秒会打架，我们承认。所以关键链路要么用天然幂等的结构（Set），要么加屏障（CLEAR），最后再加对账兜底。”

## H. Feed 推拉结合

- **设计**：普通作者写扩散（粉丝 Pipeline 批量 ZADD，500/批 + Redis 进度断点）；大 V（阈值 10w 粉，`home.feed.big-v-threshold=100000`）写发件箱走拉模式；读侧合并收件箱 + 大 V 发件箱。
- **争议**：纯推（读快写慢）vs 纯拉（大 V 友好）vs 推拉结合；阈值取多少。
- **坑**：进度 key TTL 只有 1h；已删标记只 5min，晚到推送可能写回；收件箱膨胀靠异步裁剪。
- **兜底**：ZADD 幂等可重推；content 侧 30s 本地消息补发 + 60s 推送未完成补偿（MySQL `push_status` 兜底）；断点续推实测可跳过已推粉丝。
- **话术**：
  > “推拉结合是为了控制写扩散成本。大 V 一条动态如果推给十万粉丝，写放大不可接受，所以大 V 走拉、普通用户走推，失败用本地消息和状态位兜。”

## I. IM 长连接跨实例

- **设计**：本机 session Map + Redis 路由 `im:route:{u:userId}`（90s TTL 心跳续期；hash tag 使 route/online 同 slot，续期与注销单脚本原子）+ 每实例专属 Pub/Sub channel；一致性哈希 LB（150 虚拟节点）**组件就绪含单测、未切换网关默认（设计项）**，当前靠 Redis 路由表精准寻址；跨实例踢线（新实例接管路由后定向通知旧实例关闭旧连接）；离线 ZSet 补发。
- **争议**：旧方案 MQ 广播（每实例都收再过滤，N-1 无效）→ 改为 Redis Pub/Sub 精准投递；一致性哈希 vs 轮询。
- **坑**：Pub/Sub 无持久化，订阅者离线即丢；路由 TTL 依赖心跳，GC/分区时本地有 session 但路由没了；取不到 userId 退化为轮询；单机 5w 连接上限。
- **兜底**：先落库再推送，失败转离线（1000 条/7 天）；路由删除用 Lua 比对 serverId，防旧实例误删新路由；双实例实测通过。
- **话术**：
  > “有状态长连接的难点是跨实例寻址。我们用一致性哈希减少重定向，用 Redis 路由表做寻址，Pub/Sub 只负责送达，消息持久化在 DB，所以订阅者掉线不会丢消息。”

## J. SSE 跨实例

- **设计**：本机 SseEmitter map（30min 超时）+ Redis 路由 30s TTL + 10s 心跳续期 + Pub/Sub 跨实例推送；ticket 一次性两步鉴权。
- **争议**：SSE vs WebSocket vs 轮询；Pub/Sub 广播 vs 点对点 MQ；在线推送 vs 拉列表兜底。
- **坑**：用户不在线通知直接丢（靠列表 API 兜底）；序列化把 Long 变 Integer（已改 raw JSON）；路由 TTL 依赖心跳。
- **兜底**：`remove(key,value)` 双参数防旧连接回调误删新连接；心跳失败清理；未读数有 DB 对账；双实例实测通过。
- **话术**：
  > “SSE 我们只当实时通道，不当可靠通道。可靠性和已读状态在 DB 和未读对账里，连接丢了下次拉列表也能补齐。”

## K. 计数 Set / Buffer

- **设计**：写路径 Redis INCR/DECR（去重标记 + 增减同一 Lua）；点赞用 Set（SADD/SREM/SCARD）覆盖写计数；`CounterBuffer` 双缓冲 5s/500 条批量 upsert；读 Redis→MySQL 两级；对账修 DB。
- **争议**：delta 计数 vs Set 去重（乱序下 delta 会虚增，Set 天然幂等）；攒批 vs 实时写。
- **坑**：对账只以 DB 已有行为基准，“DB 无行但 Redis 有值”不覆盖，曾导致刷盘失败增量**永久丢**（运行态 #20）；dedup TTL 2h 与 count key 30 天不一致；EXPIRE 必须在 INCRBY 后。
- **兜底**：刷盘重试 3 次 → 失败回写 Buffer 下周期重刷；懒迁移从权威 Set 同步；归零保护。
- **话术**：
  > “计数是最终一致里最容易丢的一类。我们吃过刷盘失败的亏，所以失败会回写缓冲、下个周期补刷，而不是只靠对账——对账覆盖不到‘DB 还没有行’的场景。”

## L. 限流（Sentinel vs Lua 滑动窗口）

- **设计**：网关 Sentinel 路由级滑动窗口（LeapArray），Nacos 规则优先 + 本地兜底；服务内 `@RateLimit` 用 Redis ZSet + Lua 滑动窗口，支持按用户。
- **争议**：Sentinel vs 手写 Lua；令牌桶/漏桶（允许突发）vs 滑动窗口（严格）；单机 vs 集群限流（Token Server）。
- **坑**：Sentinel 是**单机**限流不是全局；Redis 挂时 Lua 限流 fail-open；Nacos 规则覆盖顺序曾踩坑（已用 ApplicationReadyEvent 规避）。
- **兜底**：统一返回 429/40202；压测后按实测容量校准（写路由保持严格）；同用户第 6 次实测精确拦截。
- **话术**：
  > “限流按容量校准，不是拍脑袋填 QPS。网关是单机维度限流，集群精确限流要 Token Server，我们评估后认为当前规模不需要，用余量 40% 来兜。”

## M. 分库分表

- **设计**：ShardingSphere 4 库 × 4 表，`user_id % 4` 定库、`(user_id/4) % 4` 定表；bindingTables 防笛卡尔积；Snowflake 主键；订单号走公共库映射表反查。
- **争议**：按 user_id 分片（用户维度聚合）vs 按 order_id（点查友好）；映射表 vs 基因法；Snowflake vs 号段。
- **坑**：非分片键查询全分片广播；补录 Job 每 5 分钟全表扫描，数据量上来会线性变慢；**固定 4×4 没有扩容 rehash 方案**；映射写失败有窗口。
- **兜底**：映射补录 Job 消除遗漏；worker-id 环境变量优先、IP 兜底防多实例冲突；补录只更新指定列。
- **话术**：
  > “分片键选 user_id 是业务查询决定的，代价是非分片键要广播。扩容目前是已知短板——4×4 没有 rehash 工具，正确做法是双写迁移或基因分片，这是我们下一步要补的。”

## N. Redis 部署

- **设计**：Sentinel 主从（Redisson/Spring 都支持自动切主）；业务 Redis（noeviction）与缓存 Redis（allkeys-lru）分实例；多 key Lua 用 hash tag 同 slot。
- **争议**：Sentinel vs Cluster vs RedLock；单实例多 DB vs 多实例（业务/缓存隔离）。
- **坑**：Sentinel 切主窗口内锁可能没同步；`prededuct.lua` 里预扣记录与索引未全加 `{skuId}` tag，**Cluster 下会 CROSSSLOT**（当前只支持 Sentinel）；主从延迟影响延迟双删。
- **兜底**：`retryAttempts=5` + watchdog 15s + DB 乐观锁兜底；T-124 修了 bucket hash tag；coupon 用 `{templateId}` 同 slot。
- **话术**：
  > “我们选 Sentinel 是够用且简单，但代码里还留着 Cluster 不兼容的点（Lua 多 key 的 hash tag 没打全），这是明确的升级前置工作，不会说‘随时可切 Cluster’。”

## O. DLQ 治理与消费者韧性

- **设计**：消费者 `maxReconsumeTimes`（18 个组 3 次 / 8 个组 5 次）→ `%DLQ%<group>`；DlqMetrics 对 26 个消费组采样出 Gauge（RV18 对齐：补 8 缺失组、移除 5 陈旧组）；业务侧另有补偿通道（Redis 集合/本地消息/Outbox）。
- **争议**：有限重试入 DLQ vs 无限重试；自动重投 vs 人工审批；原生指标 vs 自算。
- **坑**：DLQ 指标曾**恒为 0**（`searchOffset(now)` 与 maxOffset 恒等，运行态 #21）；`-1` 是“无 DLQ/查询失败”的哨兵不是真实积压；order 补偿进 DLQ 曾没有重放通道。
- **兜底**：积压改为 `maxOffset-minOffset`；订单补偿近上限写 Redis 待处理集合、由 Job 每分钟重放；L3 死信重投需人工审批。
- **话术**：
  > “DLQ 指标我们踩过‘恒为 0’的坑，根因是指标算法自己写错了，不是没积压。修完以后按消费组可见。死信重投走审批，避免脚本误操作。”

## P. traceId 跨服务/MQ/长连接

- **设计**：网关生成 32 位 traceId → MDC + Header + SkyWalking sw8；Feign 拦截器透传；MQ header wrap/restore；IM 消息内 traceId 优先，Pub/Sub 跨实例显式携带。
- **争议**：SkyWalking 自动埋点 vs 业务可读 traceId（最后把两边映射打通）；ThreadLocal vs 显式传参。
- **坑**：消费端不 clear 会随线程池**串号**；MQ 消费无 HTTP 请求只能靠 ThreadLocal；定时任务无 Context 只能 MDC 兜底。
- **兜底**：入口必生成；Feign/MQ/WS 三条通道各自兜底；实测 order→MQ→inventory 同 trace、双 IM 实例两端同 trace。
- **话术**：
  > “traceId 的难点在跨线程和跨协议。HTTP 有 header，MQ 要自己包，WebSocket 要放在消息体里；线程池复用必须 finally clear，否则串号，这个坑我们踩过。”

## Q. 网关过滤器顺序与 HMAC 防重放

- **设计**：BodyCache(0) → 日志(+100) → 鉴权(+1000) → 染色(+1200) → HMAC(+1500) → 限流(+2500) → 灰度(+3000) → 版本(+3100)；签名串 `method|path|query|ts|nonce|bodyHash`，±5min 窗口 + nonce SETNX 5min。
- **争议**：GlobalFilter+Order vs 路由级；对称 HMAC vs 非对称签名；HMAC 默认关闭（按需增强）。
- **坑**：nonce 校验 Redis 异常时 **fail-open**（保留重放窗口），而密钥读取异常 **fail-closed**——不一致是有意权衡；body 限 1MB，multipart 跳过；时间戳依赖客户端时钟。
- **兜底**：`MessageDigest.isEqual` 防时序攻击；黑名单查询 fail-closed；实测合法 200 / 缺签 403 / 篡改 403 / 重放 403 / 过期 403。
- **话术**：
  > “过滤器顺序就是安全模型的顺序：BodyCache 必须最先（HMAC 要 bodyHash），鉴权必须在染色和限流之前，灰度和版本放最后做属性注入。fail-open/fail-closed 我们是分开设计的：nonce 缓存挂了宁可放行，密钥读不到宁可拒绝。”

## R. 对账 Job 体系与最终一致

- **设计**：库存对账（凌晨 3 点，Redis 权威修 MySQL + 分桶原子校验）、券对账（2 点，Redis 修 remain_count）、购物车对账（4 点）、未读对账（5min，DB 修 Redis）、关注对账（1h）、本地消息补发（30s）、超时关单（1min）、订单映射补录（5min）。
- **争议**：对账修复 vs 双向同步 vs 事件重放；权威源按账本选（库存/券/购物车=Redis，未读=DB，关注=ZSet），**不是全局统一**。
- **坑**：对账与在线写没有统一屏障，库存对账遇 MQ 积压可能多扣（下次自愈）；counter 对账不覆盖“DB 无行”；购物车对账在 key 不存在时跳过删除（防 Redis 故障误删）；未读对账游标曾跳切割边界。
- **兜底**：分桶校验用原子 Lua 防盲 SET 覆盖在途预扣；刷盘失败回写 Buffer；XXL-Job 单 Executor 调度所以多数 Job 不加锁。
- **话术**：
  > “对账是最后一道防线不是第一道。它的权威源按业务选，而且和在线写之间没有屏障，所以只能收敛历史差异，不能保证实时一致——这是设计边界。”

## S. Zone 多活（路由/数据面/容灾）

- **设计**：流量面=实例 zone 标 + LB 同 zone 优先（不足回退全局）+ 健康检查摘除（liveness/3s）；网关 WebFlux 独立反应式 zone LB；数据面=MySQL 读本 zone/写主库/从库故障降级恢复；Redis 客户端读副本写主库 + **服务端双主**（DUMP/RESTORE + LWW + 30s 对账）；支持运行时热切 zone（ZoneContext 事件，不重启）。
- **数字**：进程 kill RTO **1.31s/3.25s**、网络分区 **4.79s**、回切 <5s；网关就近 12/12、切换 5.5s；Redis 双主单侧宕机不中断、恢复 ≤35s 追平；240/240 同 zone 命中。
- **坑**：① 供应商 Bean 放 default context 不生效（必须进 LB 子 context）；② SIGTERM 优雅关闭造成"0.55s 假恢复"；③ LB 列表缓存 35s 掩盖切换（改 liveness 后 3.06s）；④ 双主对账 tie-break 曾误删单侧数据（改"存在优先"）；⑤ zone 参数没进进程时 Nacos 会显示旧注册残留。
- **兜底**：同 zone 不足回退全局；从库故障降级 + 30s 探测恢复；双主 LWW + 防回环（值相等跳过）+ 周期对账；发布链路 PID 校验防"旧进程假成功"。
- **话术**：
  > "多活分两层：流量面优先同 zone、健康检查摘除，RTO 1.3~4.8 秒；数据面本 zone 读、主库写，Redis 还做了双主双向同步——DUMP/RESTORE 原子复制加 LWW 加对账兜底，单侧挂了不中断、35 秒内追平。边界明说：单机仿真，跨机房延迟和脑裂没有模拟。"

## V. 订单号生成与分布式 ID（订单域）

- **两个号分工**：业务单号 `orderNo`（对外：客服/渠道回传/对账，可读可检索）+ 主键 `id`（Snowflake，内部分片/关联用）。
- **orderNo 组成**：`ORD + yyyyMMddHHmmssSSS(17) + userId%10000(4) + Redis 日序列%10000(4)`；`t_order_no_mapping.uk_order_no` 唯一键兜底；Redis 不可用时降级随机序列（碰撞概率上升，唯一键仍是最后防线）。
- **Snowflake workerId 三级优先级**：`WORKER_ID` env → `-Dworker.id` → `(ip 后两段×31 + serverPort) mod 1024`。
- **实测坑 1（重号）**：只按 IP 派生 → 同机多实例（容器/多活演练）取同一 workerId（实测两实例均 257）→ 同毫秒同序列会生成相同 ID → **加入端口维度**后 354 vs 454。
- **实测坑 2（ID 生成器缺陷外溢到存储层）**：低流量下 Snowflake 增量低位恒定（`Δms<<22` 恒被 16 整除、Δseq=0）→ 按 `id mod 16` 分片时 131 单 75% 落 2/16 片 → 改**哈希取模** + 迁移存量 682 行 → 16/16 均匀。
- **反查**：orderNo 非分片键 → 映射表（order_no → user_id）定位分片；写失败窗口由 5 分钟补录 Job 修复；`/by-order-no/{orderNo}` 强制归属校验（非本人 403）。
- **时钟回拨**：ShardingSphere 5.5 内置容忍窗（`max-tolerate-time-difference-milliseconds`），超限拒绝生成；**我们没做回拨监控/告警（已知缺口）**。
- **追问预判**：UUID（无序→页分裂）？DB 自增（分表不全局）？号段模式（有实现未接业务）？单号可枚举（归属校验兜底）？seq%10000 回绕（同毫秒+同用户尾号+同 seq 余数才碰撞，唯一键兜底）。
- **深挖提示**：见附录 V′（两个真实事故的完整复盘，这是 P7-P8 的"鉴别题"）。

## W. 支付域一致性（资金链路）

- **双状态机**：支付单 0 待支付 → 1 成功 / 2 失败 / 3 已退款；退款单独立状态机。所有流转都是**条件 UPDATE**（`WHERE status=当前值`），并发只有一个赢家。
- **回调三态解析**（本轮修复）：成功 / 明确失败 / **无法判定**；无法判定回 "fail" 让渠道重试、**不改状态**；渠道中间态（`WAIT_BUYER_PAY`/`NOTPAY`/`USERPAYING`）不再被误判为失败。
- **重复回调**：状态守卫天然幂等（status!=0 直接返回，"重复回调不改状态"）；**迟到成功**（超时已置 2 → 渠道终态成功到达）条件翻转 2→1 + 走完整 `afterPaySuccess`（7 项副作用），订单已取消则由"业务拒绝自动退款"闭环兜底。
- **金额防线**：`pay()` 回查订单 `/pay-amount` 比对（fail-closed，不等即拒）；**零元单**（全额券抵扣）跳过渠道直接记账成功（渠道 API 不接受 0 元）。
- **退款语义**："累计退款 = 支付金额"驱动库存回补与退券，回传退款单号唯一归属；售后域三层护栏（同 SKU 跨类型累计 + 订单实付 + 支付域可退）。
- **补偿与对账**：支付 30min / 退款 15 天超时检测（扫 DB + 乐观锁，非 Redis 扫描）；通知补偿 5 分钟窗口 / 最多 10 次 / 批量 100；结算域按 T-1 渠道账单做**三方对账**（差异挂账 + 自动收敛）。
- **诚实边界（必背）**：三渠道为**文本 Mock**（无真实渠道对接）；**回调验签不存在**（仅 `X-Internal-Call` 内部可达）；渠道 `queryPayStatus` 定义了但 **0 调用**、无关单 API；手续费单档。
- **上生产我会补的三件事（加分回答）**：① **渠道验签 SPI**（Alipay RSA2 / WeChat V3，fail-closed，Mock 实现仅测试用）；② **超时前置渠道查询**（置失败前先 `queryPayStatus`，防"本地失败渠道已收钱"——现有迟到成功是事后兜底，这是事前防线）；③ **回调端点公网暴露时的 IP 白名单 + 限流 + 原始报文留存**（对账举证）。
- **追问预判**：为什么用双通道（同步 pay + 异步回调）？重复回调/乱序回调怎么办？超时失败但用户已付？退款并发累计？金额用分还是元？（见附录 W′）

## X. 订单状态机与事件溯源（订单域）

- **状态**：0 待付款 → 1 已付款 → 2 已发货 → 3 已完成；旁路 4 已取消 / 5 已退款。事件→目标状态映射集中在 `EVENT_STATUS_MAP`（`ORDER_CREATED` 的 to=**-1**：创建不是状态流转）。
- **双写顺序**：每次流转 **先追加事件**（`t_order_event`，`uk_order_event_seq(order_id,event_seq)` 唯一键，先于 MySQL 8 分区）**再条件 UPDATE 状态**（`WHERE status=前置值`，乐观锁单一赢家）。
- **序号冲突的正确语义（考点）**：`INSERT IGNORE` 返回 0 ⇒ 另一事务也在为同一订单追加 ⇒ 本事务状态更新必失败 ⇒ **整体回滚让调用方重试**；重试时幂等检查看到状态已是目标值 → 跳过，不会无限失败。**反面设计已排除**：冲突处加锁重算 seq 会形成"事件锁→订单锁"与调用方"订单锁→事件锁"的反向锁序 → 死锁面。
- **幂等 + 收敛**：重复事件但状态不一致（人工重置/补偿重放）→ 不重复插事件、用乐观锁把状态**收敛**回目标值（T-123 实证：事件在但状态回退会永久不一致）。
- **回放校准**：`POST /api/order/internal/reconcile/{orderId}`（X-Internal-Call）——dry-run 默认只报告；repair 才条件更新并补齐里程碑时间；**终态差异只报告不覆盖**（方向保护）。
- **竞态闭环**：关单与支付成功同用 `WHERE status=0` 守卫 → 只有一个赢家；支付成功但订单已取消 → 自动退款闭环。
- **诚实边界**：状态机是**隐式**的（转移合法性靠各调用点守卫，无显式转移表）；事件表**只增不清理**；校准只有手动端点（无自动调度）。
- **上生产我会补的三件事**：① 显式转移表 + 单一 `transition()` 入口（不引框架，防非法流转）；② 事件按月归档（冷表 + 查询路由）；③ 校准自动化：筛"状态长期停滞"的订单做 dry-run + 差异告警。

## Y. 优惠券：超发防线与"券=钱"的语义

- **四层防超发**：① 单 Lua 原子（查库存 + 查限领 + 扣库存 + 记次数，键带 `{templateId}` hash tag 同 slot）；② Outbox 事务发件 + **发送失败 = 回滚 Redis + 作废 Outbox（status=2）**；③ 双层幂等（msgId 消费侧 + `uk_claim_no` DB 唯一键）；④ 对账（stock 对账 + claimed 计数对账 + 卡住 Outbox 告警）。
- **关键坑（本公司真修过）**：发送失败只回滚 Redis 不动作废 Outbox → 补发任务稍后投递 → 用户"领失败却拿到券"且计数已回滚可再领 = **超发**。回滚与作废必须成对。
- **-3 自愈**：库存键未初始化（Redis 重启）→ 从 MySQL 实时初始化 + 重试一次；重试结果按语义分派（-2 限领返回 30013 而不是 30014 售罄，T-121）。
- **退券 ≠ 退库存（语义必背）**：核销不扣 remain，退券只把用户券恢复"未使用"，**不回补 stock/remain、不减 claimed**——否则会出现 `remain+已发>total` 超发敞口，且可"领→用→退→再领"绕限领。
- **对账权威源**：stock 以 Redis 为准修 MySQL（Redis 是实时扣减权威）；claimed 以 DB 已发券数为准（计数可能丢）；在途±1 窗口日切低峰可接受。
- **已删除的雷（面试可讲）**：历史遗留的"退券 Redis 补偿链"（生产者零调用）按旧语义 INCR stock/DECR claimed，与现行 RV30 语义直接冲突 → 整链删除（消费者/Job 重放/常量）。
- **上生产我会补**：热门券 stock 单键 → **分桶**（与库存同款：N 桶 + 邻桶借用）；claimed 键无 TTL 的内存上限评估。

## Z. 购物车：Redis 权威 + 顺序语义 + CLEAR 屏障

- **三结构**：`items` Hash（skuId→数量）+ `checked` Set（勾选）+ `sort` ZSet（加购时间排序）；三结构由 **7 个 Lua 原子维护**，键带 `{userId}` hash tag 同 slot。
- **为什么 Redis 是权威**：购物车读写比高、结构多、并发写多；MySQL 只是异步镜像（流水 `t_cart_event` + `t_cart_item`），用于 Redis 丢失后恢复与对账。
- **TOCTOU 修复**：`check_item/update_quantity` 原为"hasKey→SADD/HSET"两步（并发 remove 会造幽灵条目）→ 改单 Lua 原子检查+写。
- **T-107 标志位（细节考点）**：Lua 对"新商品"返回 `数量+10000`——调用方据此发 ADD 事件（checked=1）；已存在商品加购发 UPDATE（checked=null），否则会把用户取消勾选的商品强制改回勾选（Redis/MySQL 不一致）。
- **顺序三层防线**：① 事件按 userId 分区 + **ORDERLY 消费**（主保障）；② 实例内自增序号 + 时间戳 CAS（乱序兜底）；③ **CLEAR 屏障**（清空与并发写乱序，有界：24h 淘汰 + 50k 上限）。
- **merge 语义**：已有商品取 `max(现有, 合并量)`（防"匿名车少量覆盖登录车大量"），新商品查品种上限；两条路径都只在需要时动 checked。
- **对账**：Redis 空 + MySQL 有 → 反向重建；**但 itemsKey 不存在疑似 Redis 故障时只跳过不删**（防摧毁 MySQL 兜底）——"双份全丢"的教训。
- **诚实边界**：角标用 `HLEN`（含下架/失效条目，与列表口径不一致，属取舍）；其它变更脚本的 TTL 靠 Java 侧 3 次 EXPIRE 刷新（非原子，仅影响"延长"）；事件流水 30 天保留（本轮补清理+索引）。

## AA. 搜索与索引治理（MySQL → ES 双通道同步）

- **双通道**：Canal（binlog 实时）+ MQ 补偿（失败重放），消费端按事件类型 index/delete；**外部版本号（毫秒 ts）拒绝陈旧写**——乱序/重投都不会把新文档写旧。
- **tombstone**：删除事件先写"墓碑"再删 ES 文档，防"旧消息晚到复活已删数据"。
- **全量重建**：id 游标断点续传（每批 500）；**写入带外部版本（与增量同域）**，版本冲突按"已最新"跳过而非批次失败；完成后**清零断点**（否则次日"全量"退化成增量）；尾部**清理源表已删死文档**（含建议索引）。
- **查询**：search_after 深分页（按 sort 值游标，避开 from+size 的深翻页开销）；`size+1` 判断 hasMore（尾页误报修复）；IK 分词的 index(max_word)/search(smart) 双 analyzer。
- **热搜**：分钟桶 ZSet 滑窗打分（λ 衰减）+ 单 Lua 完成"屏蔽词检查 + IP 限频 + 用户限频 + 写桶"；快照榜 + 置顶/屏蔽管理。
- **建议/历史**：completion suggester（weight 用互动数 log10 缩放）+ 前缀缓存；历史 ZSet/List 去重 + trim + TTL。
- **诚实边界**：单节点 ES（replicas=0，生产需 ≥1）；重建期间用默认 refresh（生产可调 refresh_interval 摊薄写放大）；suggest 只随全量重建刷新（无增量）；GEO 召回依赖 `geo_hash` 但无写入方（策略恒空）；推荐精排是规则不是 ML。

## AC. 通知：聚合窗口 + 未读对账 + SSE 送达三件套

- **聚合**：按"自然日 + (用户,类型,目标)"收敛为一条（`uk_aggregate` 唯一键）；窗口内后续事件只 `aggregate_count+1` 不增未读；订单类通知（type=5）命中同一聚合键时**定向刷新内容**（支付成功→已发货→退款到账必须显示最新状态）。
- **未读计数**：INCR/HINCRBY 双键同 slot（`{u:userId}`）单 Lua 原子 + 30 天 TTL；DECR 安全脚本（不为负）；**已读走 DB 条件更新（`WHERE is_read=0`）再减计数**——DB 是门控，Redis 只是缓存。
- **对账**：全量累计所有批次后按用户修正（防"跨批部分计数覆盖"）+ SCAN 清理"Redis 有残留而 DB 无未读"的键；卡住 Outbox 类异常打指标。
- **SSE 送达**：ticket 一次性两步握手（GETDEL，防 URL 日志重放）；实例级定向 Channel（路由值 = host:port#pid，唯一可区分）；心跳 10s 续期 + 失败清理死连接；30 分钟强制断连由客户端自动重连。
- **可靠性的分工**：SSE 只是"实时加速"（best-effort），**列表 API 才是权威**——推送失败/离线都不影响用户"最终能看到"。
- **诚实边界**：markAllRead 的 DB→Redis 归零可吞并发 +1（对账 10 分钟内收敛）；聚合窗口用应用时区与 DB 的 `notify_date` 在跨日边界有理论偏差；`Last-Event-ID` 断线回放为设计项；通知表无保留策略（建议 180~365 天）。

## AD. 内容域：发布原子性 + DFA 审核 + 计数事件

- **发布 = Outbox**：`t_note` 与 `t_local_message` **同事务**落库 → 事务后发 `FEED_TOPIC`；发送失败由 `FeedMessageRetryJob` 指数退避补发（最多 5 次 → 死信）。草稿/编辑/软删同一套。
- **DFA 敏感词**：词与文本**同一套预处理**（去空格/全角转半角/小写——原实现只预处理文本，含大写/空格的词永不命中）；trie **copy-on-write 重建**（新 trie 构建完再 volatile 发布，读侧永远看到完整结构）；动态词写 Redis + Pub/Sub 广播全实例热更新；管理端点 X-Admin-Call。
- **计数事件**：COMMENT/UNCOMMENT/SHARE/VIEW 经 MQ → counter 域（msgId 去重 + 5 秒攒批 + 对账收敛）；**content 侧即发即忘无补偿**（丢事件的兜底是 counter 的对账，不是重试）。
- **评论**：楼中楼（parent_id/reply_to_id）+ `batchCountByParentIds` 批量精确计数；通知发往"回复者或笔记作者"（排除自评）；被回复评论并发删除时空值防御（原 NPE 500）。
- **删除联动**：写 tombstone（7 天）+ SCAN 清理 `following:latest`（限速）；Feed 的 DLB 推送终态（重投上限 → push_status=3 + 指标告警）。
- **诚实边界**：`auditStatus` 无审核工作流端点（状态字段靠管理端/DB，审核流为设计项）；计数事件的即发即忘丢失只靠对账收敛；SHARE/VIEW 无补偿生产。

## AE. 售后分摊与结算：钱怎么退才不超退

- **分摊（最大余数法）**：整单优惠按明细金额比例分摊到每件商品，**分为单位整数运算**：逐项下整 → 取整差额按"小数余数从大到小"补分 → **平局按明细 ID 升序**（同一订单任何时候重算结果一致）。不变量：Σ 分摊 == min(优惠, 商品总额)、每项分摊 ≤ 该项金额；**纯函数不落库**，售后时按订单快照重算。
- **应退金额**：整件可退 = 明细金额 − 分摊优惠；**部分数量按比例向下取整**（永不超退）；**"本次退满"时用"整件可退 − 已占用"补齐差额**——否则每次取整会让用户累计少拿几分，与对账口径也对不上。
- **三层护栏**：① 同 SKU 跨售后类型的累计上限（"已占用"= 退款中 + 已完成，**在途也占额度**，防不同类型并发双退）② 累计退款 ≤ 订单实付 ③ 支付域可退上限。
- **状态机**：0 待审核 → 1 已同意 → 3 退款中 → 4 已完成（2 拒绝 / 5 取消 / 6 退款失败）；全部条件更新；唯一键 `(order_id, sku_id, type)` 防同类型重复申请；**审核时按最新占用复核**（并发双类型申请自动驳回）。
- **退款事实核对**：退款失败/卡住的恢复任务**先向支付域核对事实**（金额 + 类型 + 时间窗 + **退款单号归属**）再决策——已成功→补库存并置完成；无记录→退避重试（上限 3 次）。退款单号回传实现"一笔成功退款只归属一张售后单"。
- **库存回补**：按 `(orderId, skuId)` **累计正增量**只放行正增量（重复调用/分次退货不漏补不重补）+ 失败落补偿表 + `restock_status` 跨服务兜底重试。
- **结算**：T-1 日切账单（`(账单日,渠道)` 唯一键 + 条件更新幂等重跑）；三方对账三类差异（本地有渠道无 / 渠道有本地无 / 金额不一致）挂账，**人工已处理不被覆盖、消失自动收敛、重现自动复位**；对账单未到按标记跳过（防假差异）；按 (日期,渠道) 锁串行。
- **诚实边界**：手续费单档（未做渠道×品类分级）；分摊不落库（算法变更会影响历史重算口径）；支付三渠道为 Mock。

## AF. 首页聚合：4 秒预算内的多路并发

- **分层聚合**：入口 → 第一层并行（笔记详情/商品/用户等短超时调用，`layer1=800ms`）→ 第二层并行（依赖第一层结果：作者/关注/热门评论等）→ 组装。**两轮都从同一个全局预算（4s）里扣**：第二层用 `max(500, 4000 - 已耗时)`，保证"总延迟有上界"，而不是每层各 3s 叠加。
- **双池隔离（A3 修复的线程池饥饿）**：外层 `aggregatorPool`（20/50/200）与内层 `batchFeignPool`（30/80/500）分离——若内层任务提交到外层池，外层请求把核心线程占满 + 队列不扩容 → 内层饿死到超时。两池均 `CallerRunsPolicy`（降级为调用线程执行，不丢任务）。
- **单路降级 vs 硬失败**：默认**单路失败仅降级**（空 map/0，绝不 500）——每个 future 体内 try/catch；唯一例外是购物车页：购物车服务 503 → 抛 `DownstreamUnavailableException` → 整体 503（没有购物车的购物车页没有意义）。
- **空页收敛**：下游全超时/降级导致 `cards` 为空时，`hasMore=false` + `nextCursor=null`（否则前端无限翻空页）。
- **Feed 的推拉结合**（与 H 主题互链）：大V走发件箱拉模式、普通用户按粉丝批量写收件箱；cursor 断点续推。
- **诚实边界**：用户主页"获赞+收藏"统计有 1000 条笔记上限；推模式断点用 ZSet 下标（取关左移会漏推，拉模式覆盖）；大V路径不写 `following:latest`（拉模式覆盖，设计取舍）。

## 8 个最容易被问倒的问题（速答）

1. **Redis 挂了锁/幂等/限流全 fail-open，凭什么不超卖不重复？**
   → 锁/幂等只是第一道防线；最终防线是 `WHERE available>=qty`、状态机条件 UPDATE、唯一索引。鉴权是 fail-closed，MQ 丢失靠对账/重放收敛。实测 Redis 阻断下无幽灵数据。
2. **延迟双删 500ms 凭什么够？**
   → 不够，所以配了删缓存重试 3 次 + MQ 广播失效 + 对账兜底；承认 Canal 方案更优，是下一步。
3. **有事务消息为什么还要本地消息表？补发不会双投？**
   → 本地消息表是回查锚点 + Broker 全挂兜底；补发是 at-least-once，用 `markSuccessByTransactionId` + 消费端幂等消重。
4. **TCC 和分桶是不是两本账？**
   → 是。TCC 走独立冻结账本，文档明确混用有覆盖风险，当前只用于专项链路，靠对账隔离——主动承认而非掩饰。
5. **同毫秒两条事件版本相等怎么办？**
   → 会互相跳过；购物车加 CLEAR 屏障 + DB 时间戳二次校验，计数用 Set 天然幂等，最终靠对账。
6. **Sentinel 切主可能丢锁，为什么不用 RedLock/ZK？**
   → RedLock 运维复杂且 Kleppmann 质疑其安全假设；用 retryAttempts + watchdog + DB 乐观锁换简单性。fencing token 未实现，但 DB 版本列承担等效终线。
7. **对账万能吗？刷盘失败为什么差点永久丢增量？**
   → 不万能。对账只覆盖“DB 已有行”；所以刷盘失败必须回写 Buffer。教训：有兜底也要实测，不能假设。
8. **按订单号怎么查？将来扩容怎么办？**
   → 订单号走映射表反查 user_id；扩容没有 rehash 方案，是已知短板，正解是双写迁移/基因分片。

# 附录 · P0 长文展开（2026-09-14）

## D′. TCC fence：空回滚、悬挂与"两本账"的诚实边界

**① 业界背景。** TCC 的概念来自 Pat Helland 2007 年 "Life beyond Distributed Transactions"，核心是把分布式事务拆成 Try（预留）/Confirm（确认）/Cancel（回滚）三段，用业务补偿代替数据库回滚。Seata 把它工程化，并补齐了三个经典异常：**空回滚**（Try 未到 Cancel 先到）、**悬挂**（Cancel 后迟到的 Try 又执行）、**幂等**（Confirm/Cancel 重试）。对标的三种方案：Seata AT 用全局锁 + undo log，侵入小但热点行全局锁竞争大；Saga 长事务补偿无隔离，中间态对外可见；裸 TCC 业务侵入最大、但可控性最强。Fence 的本质是一张**唯一键表**，把"分支事务有没有发生过 Cancel"变成数据库可见的事实。

**② 项目选型与理由。** 库存预扣链路自研 TCC + 独立 `t_tcc_fence` 表（`TccFenceService`）：Try 插 fence（主键冲突=幂等命中，必须跳过业务，否则双冻结）；Cancel 先插 fence（状态=CANCELLED，Try 没执行过则插成功但什么都不做=空回滚）；Try 时查 fence 见 3 直接拒绝（悬挂）。为什么不用 Seata：多一个 TC 集群的部署与存储成本，且我们只有一个专项链路用 TCC（其余走事务消息/本地消息表），框架收益不抵复杂度。为什么 fence 独立表而不是复用业务行状态：Cancel 可能先于 Try 到达，"业务行还没建"这种状态业务表表达不了。超时取消也从"按 SKU 聚合 freezing_stock + updated_at"改成"按 xid 冻结明细"——旧实现有三宗罪：一刀切回退该 SKU 全部冻结（含别单刚冻的）、热 SKU 的 updated_at 被任何冻结刷新导致超时永远不可达、回退不写 fence 导致迟到 Confirm 把已回退库存再 confirm（超卖）。

**③ 已知坑（主动承认）。** 第一，**TCC 与普通分桶库存是两本账**：TCC 走独立冻结账本，普通链路走 Redis 分桶+DB，混用场景对账 Job 有可能覆盖 TCC 状态——文档里明确标了风险，靠对账隔离而不是假装统一。第二，Confirm/Cancel 如果只写 fence 不校验业务行数与库存状态，异常路径会静默漏处理。第三，这个机制没有"绝不出错"的保证：它保证的是 Try/Cancel 的**相对顺序语义**，不是跨系统的因果序。

**④ 兜底手段。** 状态机条件 UPDATE（`UPDATE ... WHERE status=1`）保证并发双 Cancel 只有一次真正执行；超时 Job（`TccTimeoutJob`，60s 一轮）扫描 status=1 明细逐条 cancelFence(1→3) 再解冻；迟到 Confirm 被 fence 拒绝（status=3）；**11 场景（幂等/空回滚/悬挂拒绝/超量拒绝/fence 状态机 1→2/3）直接调用实测通过**（test-4 运行态对账报告），并有 FINAL-HANDOFF §6 与 test-3 G5-02-06/07 佐证；Redisson 锁保证多实例只有一个 Job 实例执行。

**⑤ 话术（30 秒版）。** "TCC 只用在库存专项链路，因为我们没有引入 Seata，fence 表解决空回滚/悬挂/幂等三件事。它最大的边界是和普通分桶库存两本账，文档里明确标了，靠对账隔离——面试我会主动说这个，而不是等追问。如果重来，要么全线 Seata，要么把冻结账本和分桶库存做成互斥使用。"

## G′. 消息乱序与版本控制：时间戳是妥协，不是银弹

**① 业界背景。** MQ 只保证**分区内有序**：RocketMQ 顺序消息靠单队列串行（吞吐换顺序），跨 consumer group 完全不保证顺序——我们真的踩过：点赞/取消点赞拆了两个 group，取消先到、点赞后到，最终 DB 显示"已点赞"但用户实际取消了。业界解决乱序四大流派：单分区顺序消费、业务版本号（last-write-wins）、事件溯源+状态机收敛、幂等数据结构（Set/位图）。

**② 项目选型与理由。** 我们按链路特征混用：库存用 `eventTime` 在 Lua 里原子比较（脚本内比较+写入，避免 check-then-act）；社交点赞/收藏用 `actionTime` 版本号 + 24h 窗口（Redis 记录最后版本，旧事件跳过），并把 LIKE/UNLIKE 合并成一个 consumer group（`LikeUnlikeConsumer`）——这是"先消灭乱序源，再谈版本"的顺序；购物车用 CLEAR 屏障（清空动作先把操作序列"抬到"最新）+ DB `updatedAt` 二次比较；ES 搜索用 Canal 的 `ts` 做 external version + tombstone（删除标记），让 ES 自己拒绝旧版本写；Feed 的已删标记 5 分钟内拦截晚到的推送。为什么不全部顺序消费：写扩散和计数是吞吐敏感链路，单队列串行的代价远大于版本号的复杂度。

**③ 已知坑（主动承认）。** 同毫秒两条事件版本相等会**互相跳过**（时间戳精度不够）；`eventTime=null` 的事件不参与比较、直接放行；跨 action 共用版本 key 时，早到的 PRE_DEDUCT 会被当作旧事件跳过；ES 同毫秒同版本写入会被拒（版本严格递增假设）；超过 24h 窗口的迟到事件不再拦截。这些都是时间戳版本的固有边界，不是实现对错。

**④ 兜底手段。** 计数用 Redis Set 做"用户维度去重"，天然抗乱序（重复/乱序都不改变集合）；购物车在 catch 分支做二次校验防 TOCTOU；搜索侧实测 001→000→002 的低版本被拒；相等/超窗的残余场景交给对账 Job 收敛。

**⑤ 话术（30 秒版）。** "时间戳版本不是严格因果序，同毫秒会打架，我们承认。所以关键链路要么用天然幂等的结构（Set），要么加屏障（CLEAR），最后靠对账兜底。如果重来，我会考虑用 binlog offset/序列号替代时间戳，或者对强顺序链路直接做分区顺序消费。"

## R′. 对账 Job 体系：选对权威源，承认无屏障

**① 业界背景。** 对账是金融行业处理"最终一致"的标准答案（银行/支付宝 T+1 对账）。工程上有两条路线：一是"在线强一致（TCC/事务消息）+ 对账兜底"，金融系主流；二是"事件溯源/CDC 流式一致"，互联网新架构偏好。对账的核心从来不是"跑个 Job"，而是**谁是权威源**以及**差异如何有方向地修复**。

**② 项目选型与理由。** 8 个对账/修复 Job 覆盖全链路：库存（凌晨 3 点）、券（2 点）、购物车（4 点）、未读（5 分钟）、关注/粉丝（1 小时）、本地消息补发（30 秒）、超时关单（1 分钟）、订单映射补录（5 分钟）。权威源**按账本选，不统一**：库存/券/购物车以 Redis 为准（用户操作直接写 Redis，MySQL 只是异步持久化的兜底存储）；未读以 DB 为准；关注关系统以 Redis ZSet 为准（ZCARD 覆盖 counter）。调度用 XXL-Job，Admin 只调度一个 Executor 实例，所以多数 Job 不额外加分布式锁。

**③ 已知坑（主动承认）。** 第一，**对账与在线写之间没有屏障**：库存对账撞上 MQ 积压时可能"多扣"，只能靠下一次对账自愈——这是设计边界，不是 bug。第二，counter 对账只覆盖"DB 已有行"，DB 缺行时对账看不见。第三，购物车对账在 Redis key 不存在时跳过删除（防止 Redis 故障被误判为"用户删了全部购物车"）。第四，未读对账游标曾经跳切割边界。第五，最疼的教训：计数 Buffer 刷盘失败如果只依赖对账，对账覆盖不到"DB 无行"的场景，会永久丢增量——后来改成刷盘失败必须回写 Buffer（#20 复盘）。

**④ 兜底手段。** 库存对账对分桶做原子 Lua 校验，避免盲 SET 覆盖在途预扣；修复动作以权威源为准且幂等（可重复执行）；本地消息补发配合 `markSuccessByTransactionId` 消除双投；所有 Job 都保留执行日志与修复计数，便于回溯。

**⑤ 话术（30 秒版）。** "对账是最后一道防线，不是第一道。它的权威源按业务选，而且和在线写之间没有屏障，所以只能收敛历史差异，不能保证实时一致——这是我们文档里写明的边界。如果重来，我会给对账加水位线/版本屏障，或者把关键账本换成 CDC 流式同步。"

## M′. 分库分表：分片键就是查询模型，扩容要提前设计

**① 业界背景。** 分库分表的核心矛盾是"分片键只能优化一类查询"：按 user_id 分对"我的订单列表"友好，按 order_id 分对"订单详情"友好。业界三种解法：**基因法**（把 user_id 的二进制位编码进 order_id 末位，单键路由）、**映射表**（订单号→user_id 独立存储反查）、**ES 二级索引**（查询与存储解耦）。扩容是另一个经典难题：取模分片没有 rehash 工具，主流方案是双写迁移（新老规则并行写、旧数据后台搬）或一致性哈希/基因分片从设计期规避。

**② 项目选型与理由。** ShardingSphere 4 库 × 4 表：`user_id % 4` 定库、`(user_id/4) % 4` 定表；bindingTables 绑定订单/明细/本地消息，避免 join 笛卡尔积；主键用 Snowflake（`ShardingSphereDataSourceConfig` 里 worker-id 动态计算：环境变量优先、IP 兜底，防多实例冲突）。为什么不用基因法：订单号还承担对账/回调的外部语义，改结构风险大；映射表（`t_order_no_mapping`）改动可控，配合 `MappingRepairJob` 每 5 分钟补录消除写失败窗口。查询分工：用户维度走分片键；客服/风控按订单号先查映射表拿 user_id 再路由。

**③ 已知坑（主动承认）。** 非分片键查询（订单号、时间范围、状态）只能**全分片广播**，数据量上来线性变慢；补录 Job 全表扫描同样随量线性劣化；**固定 4×4 没有 rehash 方案**，扩容是明确短板；映射写失败到补录之间有查询不到的窗口。

**④ 兜底手段。** 映射表 + 5 分钟补录 Job 收敛遗漏；Snowflake worker-id 冲突有环境变量与 IP 双保险；补录只更新指定列避免覆盖业务字段；SQL 层用 Explain/慢查询监控广播比例，超阈值就考虑把高频非分片查询投影到 ES。

**⑤ 话术（30 秒版）。** "分片键选 user_id 是业务查询决定的，代价是非分片键要广播，我们监控广播比例。扩容目前是已知短板——4×4 没有 rehash 工具，正确做法是双写迁移或基因分片，这是我们下一步要补的。"

## I′+J′. IM 与 SSE 跨实例：有状态连接的寻址与送达分离

**① 业界背景。** 长连接（WebSocket/SSE）是**有状态**的，接入层无状态化后必须解决"用户连在哪个实例"。业界路线：广播（每个实例都收再过滤，N 个实例 N-1 次无效投递）、一致性哈希路由（同用户固定实例，但要处理实例上下线和重定向）、集中式 session 注册中心（Redis 路由表/etcd）、网关前缀路由（如 MQTT broker）。送达侧又有 Pub/Sub（无持久化）vs 持久订阅/MQ（可靠但重）。

**② 项目选型与理由。** **Redis 路由表**做精准寻址——IM 用 `im:route:{u:userId}`（90s TTL 心跳续期；hash tag 让 route/online 同 slot，续期/注销走单脚本原子），SSE 用 30s TTL + 10s 心跳续期；每实例一个专属 Pub/Sub channel，路由查到实例后**点对点投递**，并支持**跨实例踢线**（新实例接管路由后定向通知旧实例关连接）。入口一致性哈希（150 虚拟节点）为**组件就绪未接线**的设计项（当前不依赖它减少跨实例投递）。旧方案 MQ 广播被替换（延迟与无效投递不可接受）。SSE 另加 ticket 一次性两步鉴权（限制在 URL 里的 token 泄露面）。

**③ 已知坑（主动承认）。** Pub/Sub 无持久化，订阅者离线即丢——所以"实时通道"不承担可靠性；路由 TTL 依赖心跳，GC 停顿/网络分区时会出现"本地有 session 但路由已过期"；取不到 userId 时退化为轮询；单机连接数有上限（约 5w 量级）。

**④ 兜底手段。** 消息**先落库再推送**，推送失败转离线（1000 条/7 天）或靠列表 API/未读对账补齐；路由删除用 Lua 比对 serverId，防旧实例误删新实例路由；SSE 的 `remove(key,value)` 双参数防旧连接回调误删新连接；心跳失败主动清理；双实例实测通过。

**⑤ 话术（30 秒版）。** "有状态连接的难点是跨实例寻址。我们用一致性哈希减少重定向、Redis 路由表做寻址、Pub/Sub 只负责送达；可靠性放在 DB 和离线消息里，所以订阅者掉线不会丢消息——实时通道和可靠通道是两回事。"

## K′. 计数 Buffer：Set 管正确性，Buffer 管性能

**① 业界背景。** 计数系统两条路线：**delta 计数**（INCR/DECR，性能好但依赖消息不重不漏）和**去重结构**（Set/Bitmap/HyperLogLog，天然幂等但有内存成本）。点赞这类"用户-目标"关系天然适合 Set：SADD 幂等，乱序/重投都不改变集合，SCARD 就是权威值。攒批（Buffer）则是把高频 DB 写合并，代价是丢增量风险。

**② 项目选型与理由。** 写路径：Redis INCR/DECR 做实时值，**同一 Lua 里先做去重标记（`myxhs:counter:dedup:{msgId}`）再增减**，保证 MQ 重投不重复计数；点赞/收藏类用 Set（SADD/SREM/SCARD）覆盖写计数，把"最终值"交给集合而不是算术。`CounterBuffer` 双缓冲（5s 或 500 条触发）批量 upsert DB；读路径 Redis → MySQL 两级；不用 Caffeine 本地缓存——多实例下各节点会看到不同计数值，Redis 亚毫秒延迟不值得换分布式不一致。对账 Job 以 Redis 权威修 DB。

**③ 已知坑（主动承认）。** 对账只以 **DB 已有行**为基准，"DB 无行但 Redis 有值"覆盖不到——刷盘失败曾导致增量**永久丢**（运行态 #20 复盘）；dedup TTL 2h 与 count key 30 天不一致，超窗重投可能重复计数（窗口内幂等，窗口外交对账）；EXPIRE 必须在 INCRBY 之后，否则 key 会被提前重置。

**④ 兜底手段。** 刷盘失败重试 3 次 → 仍失败**回写 Buffer 下周期重刷**（而不是只靠对账）；懒迁移从权威 Set 同步到 DB；归零保护防止负数；对账 Job 每小时/每天收敛历史差异。

**⑤ 话术（30 秒版）。** "计数是最终一致里最容易丢的一类。我们吃过刷盘失败的亏：对账覆盖不到'DB 还没有行'的场景，所以失败必须回写缓冲、下个周期补刷。delta 计数只用在有去重的路径上，点赞这类关系值用 Set 兜正确性。"

## L′. 限流：按容量校准，而不是拍脑袋填 QPS

**① 业界背景。** 限流的两条轴：**算法**（计数器/滑动窗口/令牌桶/漏桶——突发流量允许度不同）与**范围**（单机 vs 集群）。单机限流便宜但总量=N×阈值；集群精确限流需要 Token Server（集中发令牌）或 Redis+Lua 全局限流（每次请求一次 Redis 往返）。Sentinel 是单机 LeapArray 滑动窗口的代表，规则可动态下发。

**② 项目选型与理由。** 网关用 Sentinel 路由级滑动窗口（Nacos 规则优先 + 本地兜底，ApplicationReadyEvent 保证规则加载顺序），服务内精细场景用 `@RateLimit`（Redis ZSet + Lua 滑动窗口，支持按用户维度）。为什么不全用 Redis：网关是流量入口，每请求一次 Lua 的网络开销换全局精确不划算；为什么保留 Lua 版：同用户第 6 次这种"按用户精确拦截"Sentinel 单机做不到。

**③ 已知坑（主动承认）。** Sentinel 是**单机**限流，集群总量是 N 倍阈值；Redis 挂时 Lua 限流 fail-open（宁放行不阻断交易）；Nacos 规则与本地规则覆盖顺序踩过坑（已规避）；阈值必须按实测容量校准，不是配置数字游戏。

**④ 兜底手段。** 压测后按容量设限（写路由保持严格、读路由留余量），统一 429/40202 响应；关键写路径在限流之外还有 DB 约束兜底；同用户第 6 次实测精确拦截。

**⑤ 话术（30 秒版）。** "限流按容量校准，不是拍脑袋。网关是单机维度，集群精确限流要 Token Server，我们认为当前规模不需要，用约 40% 余量兜；Redis 崩溃时 Lua 限流 fail-open，因为限流挂了不该阻断交易。"

## Q′. 网关 HMAC 防重放：fail-open 与 fail-closed 是分开设计的

**① 业界背景。** 防重放三件套：时间戳窗口（拒绝过期请求）、nonce 去重（拒绝重复请求）、签名（防篡改）。对称 HMAC 简单快；非对称签名（RSA/Ed25519）能分离签发与验签权限但重。典型争议是"nonce 存储挂了怎么办"——安全与可用性的直接冲突。

**② 项目选型与理由。** GlobalFilter 链固定顺序：BodyCache(0) → 日志(+100) → 鉴权(+1000) → 染色(+1200) → HMAC(+1500) → 限流(+2500) → 灰度(+3000) → 版本(+3100)。顺序即安全模型：BodyCache 必须最先（HMAC 要对 bodyHash 验签），鉴权先于染色与限流（未认证流量不进入业务计数）。签名串 `method|path|query|ts|nonce|bodyHash`，±5min 时间窗 + nonce SETNX 5min；默认按需开启（内网调用不需要额外链路开销）。

**③ 已知坑（主动承认）。** nonce 校验遇 Redis 异常 **fail-open**（保留重放窗口），而密钥读取异常 **fail-closed**——这个不一致是**有意权衡**，不是疏漏；body 限 1MB、multipart 跳过；时间戳校验依赖客户端时钟，时钟漂移大的客户端会被误拒。

**④ 兜底手段。** `MessageDigest.isEqual` 防时序攻击；下发的密钥任何异常都 fail-closed；黑名单查询 fail-closed；实测矩阵：合法 200 / 缺签 403 / 篡改 403 / 重放 403 / 过期 403。

**⑤ 话术（30 秒版）。** "过滤器顺序就是安全模型的顺序。fail-open/fail-closed 我们是分开设计的：nonce 缓存挂了宁可放行，密钥读不到宁可拒绝——因为前者只损失防重放窗口，后者损失的是信任根。"

## O′. DLQ 治理：先让指标诚实，再谈自动重投

**① 业界背景。** 死信治理的路线之争：**无限重试**（可能毒消息拖垮消费者）vs **有限重试入 DLQ**（需配套处置闭环）；**自动重投**（快但可能循环）vs **人工审批重投**（稳但慢）。无论选哪条，前提都是**指标可信**——DLQ 积压看不见，治理就是空谈。

**② 项目选型与理由。** 消费者 `maxReconsumeTimes`（18 组 3 次 / 8 组 5 次）→ `%DLQ%<group>`；监控用自算 Gauge 采样 26 个消费组；业务侧另有补偿通道（Redis 待处理集合/本地消息表/Outbox），不是所有失败都走 DLQ。重投走三级治理：L1 自动重试、L2 补偿 Job、**L3 死信重投必须人工审批**（xhs-ai 里由 Agent 发起、HITL 审批、执行后核验再入 DLQ）。

**③ 已知坑（主动承认）。** DLQ 指标曾**恒为 0**——`searchOffset(now)` 与 `maxOffset` 恒等，算法写错把真实积压藏了（运行态 #21）；`-1` 哨兵表示"无 DLQ/查询失败"不是真实积压；监控清单硬编码 22 组与实际 26 组有 8 组盲区（cart 死信事件后修复）；order 补偿进 DLQ 一度没有重放通道；跨 group 顺序不保证（Like/Unlike 拆组事故）。

**④ 兜底手段。** 积压算法改 `maxOffset-minOffset`；26 组清单与代码对齐并加维护注释；订单补偿近上限先写 Redis 待处理集合、Job 每分钟重放；死信重投审批 + 执行后**队列级位点核验**（不是"发送成功=成功"）；消费者做失败分类（可重试 vs 确定性失败）。

**⑤ 话术（30 秒版）。** "DLQ 治理第一件事不是重投，而是让指标诚实——我们踩过指标恒为 0 的坑，根因是算法自己写错。修完后按消费组可见、清单与实际对齐；重投走人工审批，执行后还要核验位点，不做'发送成功就算成功'。"

## P′. traceId 跨协议：跨线程和跨协议是两个坑

**① 业界背景。** 分布式追踪两条路线：APM 自动埋点（SkyWalking/Jaeger，框架级）与业务可读 traceId（MDC/日志串联）。两者痛点不同：APM 全但业务日志里不好查；业务 traceId 灵活但要自己跨线程、跨协议透传。

**② 项目选型与理由。** 网关生成 32 位 traceId → MDC + Header + SkyWalking sw8（双轨映射打通）；Feign 拦截器透传 HTTP；MQ 用 header wrap/restore；IM 消息体里显式携带 traceId（WebSocket 没有 header 语义）；Pub/Sub 跨实例也显式带。定时任务无请求上下文，用 MDC 兜底生成。

**③ 已知坑（主动承认）。** 消费端不 `clear` 会随线程池**串号**（A 请求的 traceId 出现在 B 请求日志里）；MQ 消费没有 HTTP 请求，ThreadLocal 只能靠消息头回填；跨实例 Pub/Sub 消息不带 trace 就断链；SkyWalking 的 sw8 与业务 traceId 不是同一个 ID，必须做映射。

**④ 兜底手段。** 入口必生成；Feign/MQ/WS 三条通道各自透传；线程池包装器 finish 时 finally clear；实测 order→MQ→inventory 同一 trace、双 IM 实例两端同 trace。

**⑤ 话术（30 秒版）。** "traceId 的难点在跨线程和跨协议：HTTP 有 header，MQ 要自己包，WebSocket 要放消息体里；线程池复用必须 finally clear，否则串号——这个坑我们踩过，现在三条通道都有兜底和实测。"

## T′. LLM 工具设计：给模型的接口不是给程序员的接口

**① 业界背景。** Function Calling / MCP 生态里，工具 schema 直接决定模型的选择准确率与调用成功率。Anthropic/OpenAI 的工具设计指南反复强调：参数少而扁平、命名语义化、描述里写"何时用/何时不用"、示例优于解释。业界另一个趋势是**渐进加载**（tool_search / 懒加载技能），因为工具数量膨胀会同时抬高 token 成本与误选率——我们 32 个工具虽未到阈值，但已在 Agent 侧设了软 32/硬 40 的预算护栏。

**② 项目选型与理由。** 我们最初把数据源原样暴露：ES 的 `search` 要 `index` + 完整 DSL，Prometheus 的 `query` 要手写 PromQL。实测 qwen3.8-flash 在嵌套 schema 上**连续 3 次缺参**（`required property 'index' not found`）、P95 聚合**答非所问**（98s）。于是把查询组装收回到服务端，向模型暴露**业务级工具**：`log_top_services(level,minutes,topN)`、`log_search(service,level,keyword,minutes,size)`、`metric_top(metric,service?,topN)`、`metric_trend(metric,service,minutes)`、`consumer_lag_top(topN)`。模型只填业务语义参数，DSL/PromQL 由 `LogQueryBuilder`/`MetricQueryBuilder` 白名单生成。同题对比：5xx 63s→52s，P95 98s(答偏)→50s，趋势从"做不到"到 33s 且能区分冷启动与平台期。

**③ 已知坑（主动承认）。** 工具**注册成功 ≠ 可用**：ES 工具因框架权限默认 ASK 挂起过（`MCP client not initialized`/空答复）；子进程被 kill 后需进程级自愈；工具数量到 32 已触及软预算，再涨必须先做 token 预算与 tool_search；业务级工具覆盖面有限（复杂聚合仍要回退裸 query）；模型偶发不按"只查一次"的约束执行，靠 prompt + 工具内部超时兜。

**④ 兜底手段。** 参数 clamp（minutes≤1440/size≤100/topN≤50）+ 服务名校验正则；白名单指标目录（非法 metric 直接报错给模型纠错）；只读工具 + 审计留痕；每个工具有单测（当前 40/40）；工具总数指标 `ai_agent_tools_total` + 软硬预算；裸查询工具保留作兜底并在 prompt 里标明适用边界。

**⑤ 话术（30 秒版）。** "给 LLM 的工具接口要按任务设计，不是按数据源。我们踩过模型填不对 ES DSL 的坑，所以把 DSL/PromQL 收回服务端，只暴露业务参数——P95 查询从 98 秒答偏变成 50 秒答对。工具不是越多越好，32 个已到软预算，下一步是 tool_search 渐进加载。如果重来，我会从第一天就用业务级工具目录 + 单测守着。"

## U′. 去 MCP 化与 RBAC：生产化收口的两条依赖治理

**① 业界背景。** Agent 生产化绕不开两类"依赖治理"：**权限依赖**（谁能调用危险能力）与**工具运行时依赖**（工具进程挂了怎么办）。前者对应 OWASP LLM Top10 的"过度授权（Excessive Agency）"——最小权限、危险操作强制人工确认；后者是 MCP 生态的现实问题：协议标准只规定"怎么连"，没规定"进程崩了怎么无感热替换"。框架（我们用的 AgentScope）支持运行时注册/摘除工具，但实测**重挂后已注册工具不重绑**（调用报 `MCP client not initialized`）。

**② 项目选型与理由。** 两条依赖分别用"接平台能力"和"砍依赖面"解决：
- **RBAC**：不重建账号体系，直接消费平台 JWT 的 `role` claim（实测带 `OPERATOR`），加管理/内部令牌视为 ADMIN，默认 VIEWER；`reindex`/评测/诊断/MCP 直连全部收敛到 ADMIN，普通用户走会话所有权校验（自己的审批自己批）。对照 OWASP 最小权限：VIEWER 只能对话与查自己的数据，危险/全局能力一步收口。
- **去 MCP 化**：既然框架不能热替换，就不把 MCP 放进 Agent 的**关键路径**——20 个工具（运维16+业务4）全部自研（REST 直连 ES/Prometheus/RocketMQ Admin/MySQL），MCP 20 个工具保留给运维经管理端点直连。框架限制从"可能导致 Agent 瘫痪的缺陷"降级为"不使用的功能"。

**③ 已知坑（主动承认）。** 自研工具放弃了 MCP 生态的复用（新数据源接入要自己写）；MCP 里少用的复杂能力（如 ES 的 get_shards、Prom 的 config/flags）需要时得回管理端点；RBAC 目前只有三级且依赖平台 claim 合规（平台若给普通用户发 OPERATOR 就等同于放权）；没有细粒度资源级鉴权（如"只能重投 A 服务的死信"）。

**④ 兜底手段。** 自研工具全部带参数校验/白名单/只读标记/审计；`es_search` 索引前缀白名单防越权检索；去 MCP 后 MCP 已旁路（Agent 不依赖）；MCP 直连死进程修复为 15.1s 快速失败 + 1.2s 按需重建（2026-09-20 复核，旧 19s/39s 口径作废）；RBAC 实测矩阵（OPERATOR JWT→403、admin 令牌→200）；管理/内部令牌走常量时间比较防时序攻击。

**⑤ 话术（30 秒版）。** "MCP 协议没有定义进程级热替换，框架也不支持，硬修不如不依赖——我们把 20 个工具全自研，MCP 只留给运维直连，于是'工具进程挂了 Agent 就瘫'这个风险从架构上消失了。权限同理：不重建账号体系，消费平台 JWT 的角色声明，管理端点全部收口到 ADMIN，危险操作永远走人工审批。如果重来，我会在选型第一周就做这两件事，而不是等到生产化清单。"

## V′. 订单号生成：两个号的分工、两个真实事故与三条追问链

**① 它到底干了什么。** 一次下单会产生两个"号"：用户/客服看到的业务单号 `ORD2026092315301212345678`（可读、可按天检索），和数据库主键 `1859932140379344897`（Snowflake，18-19 位，用于分片路由与表关联）。两者不是一回事：**业务号给人用，主键给系统用**——这是本题的第一层答案，答不出这一层，后面全是背课文。

**② 为什么需要两个号。** 业务号要满足：可读（客服报单号就能定位）、可按天分段（对账/归档/日志检索）、长度可控（短信/渠道回传）；主键要满足：全局唯一（16 张分片表无法协商自增）、趋势递增（B+ 树顺序插入，避免页分裂）、无外部依赖（不靠中心发号）。

**③ 怎么做 + 两个真实坑。**
- orderNo = `ORD` + 毫秒时间戳(17 位) + `userId % 10000`(4 位) + **Redis 日序列** `INCR order:seq:yyyyMMdd` 取 `%10000`(4 位)，48h TTL 自动跨天换 Key；唯一约束落在 `t_order_no_mapping.uk_order_no`（本地消息表重试导致"同一逻辑订单跑两次"时，靠它兜住只成一单）。
- **坑 1（重号，实测）**：Snowflake workerId 原实现只用 IP 派生 → 同机多实例（容器/多活演练）取到同一个值（两实例均 257）→ 同毫秒+同序列直接产出相同 ID。修复：加入 `serverPort` 维度（354 vs 454），并保留 env `WORKER_ID` 显式钉住能力。
- **坑 2（ID 生成器缺陷外溢到存储层，最有含量）**：分片初期按 `id mod 16` 预判分布，实测 131 单 **75% 落在 2/16 片**——根因是低流量下 Snowflake 的时间增量恒为 1024ms 级、序列增量恒 0，`(Δms<<22 + Δseq)` **恒定被 16 整除** → `id mod 16` 几乎是常量。修复：改 `user_id` 哈希取模（`hashCode & 0x7fffffff`），并迁移存量 682 行（迁移脚本 + 路由抽查全命中）。**这条的面试价值**：它证明"发号器的低位不是随机的"，能把它和分片倾斜联系起来的人不多。

**④ 三条追问链（准备到第 3 层）。**
- *为什么不用 UUID？* 无序 → 聚簇索引随机插入页分裂 + 写放大；36 字符存储与索引膨胀；没有时间语义（分区/归档要额外字段）。*那为什么不用自增？* 单表自增无法全局唯一（16 表各发各的），加全局前缀又要中心协调（DB 号段/Redis INCR 都引入依赖）；号段模式（DB 段号 + 双 Buffer 预加载）我们有实现与单测但**未接业务**——诚实说"评估后先沿用 Snowflake"比硬吹好。
- *时钟回拨怎么办？* 标准四级：回拨小（< 容忍窗）按旧时间继续发；回拨大则拒绝/换 workerId/告警。我们的实现是 ShardingSphere 5.5 内置（`max-tolerate-time-difference-milliseconds` 容忍窗、超限拒绝生成），**但没有专门的回拨监控与告警**——这是已知缺口，改进路径：记录 lastTimestamp + 回拨指标 + 告警。
- *单号能被枚举/伪造吗？* 组成全是可预测部分（时间戳 + 用户尾号 + 日序列），**能被猜**；防线在服务端：`/by-order-no/{orderNo}` 先查映射表再比对 `userId`（非本人 403），下单幂等键与限流另挡一层。这条要主动说"单号不是凭证"，比被问穿好。

**⑤ 诚实边界与一句话收尾。** 当前 orderNo 的 `%10000` 序列在单日超过 1 万单后会回绕（碰撞需"同毫秒 + 同用户尾号 + 同回绕余数"三者同现，唯一键兜底），改进方向是把序列位数与日期解耦（更长序列或 base62）。**一句话**：订单号这题的分水岭不在"背 41 位怎么分配"，而在能不能讲出"对外号 vs 对内主键的分工"和"发号器特性如何影响存储层"——前者是 P6，后者才是 P7-P8。

## W′. 支付域：状态机怎么兜住渠道的"不可信"

**① 它到底干了什么。** 用户在收银台点支付 → 我们本地生成支付单（0 待支付）→ 调渠道拿到 tradeNo → 渠道异步回调"成功" → 我们把支付单置 1 并通知订单"已支付"。**关键认知：支付系统不信任渠道回调的到达时机，也不信任它只来一次**——所有设计都围绕"回调可能重复、可能乱序、可能不来、可能来晚了"展开。

**② 为什么这么设计。** 渠道回调是**外部不可控事件**：网络会让你收不到（要主动查/对账）、渠道会重发（要幂等）、通知会先失败后成功（迟到成功）、用户会在超时和成功之间的缝隙里付款（钱和状态错位）。所以本地必须有一份**权威状态机**，渠道回调只是"驱动状态迁移的信号"，不是状态本身。

**③ 怎么做 + 坑。**
- 状态迁移全部条件 UPDATE：重复回调 → `WHERE status=0` 不命中 → 直接返回（天然幂等）；并发回调只有一个赢家。
- 回调结果三态：**明确失败才置 2**；"解析不出来"必须回 "fail" 让渠道重试——这条是本轮的真实修复：原实现把"格式不符"当失败，会把一个成功回调标记成失败并触发订单取消（资损/客诉）。
- **迟到成功**：超时任务已把单置 2，渠道终态成功才到 → 条件翻转 2→1 + 重跑全部成功副作用（通知订单/MQ/事件/自动退款判断）——注意这里不能再走 `WHERE status=0` 的旧入口，否则守卫失败直接 return，"用户已付却既没记账也没退款"。
- **零元单**：全额券抵扣 payAmount=0，渠道 API 不接受 0 元 → 直接本地记账成功（tradeNo=ZERO_AMOUNT），否则用户只能等 30 分钟关单。
- **金额防线**：发起支付前回查订单 `/pay-amount` 比对（不一致直接拒，fail-closed）；退款按"累计退款=支付金额"校验，三层护栏（SKU 跨类型/订单实付/支付域可退）。

**④ 三条追问链（答到第 3 层）。**
- *重复回调怎么办？* → 状态守卫幂等。*那渠道重发但本地已发起退款呢？* → 退款单独立状态机 + 只认累计额度，重复退款请求被额度校验拒绝。*钱和状态不一致怎么发现？* → T-1 渠道账单三方对账（差异挂账：本地有渠道无 / 渠道有本地无 / 金额不一致）。
- *超时置失败后用户付了钱？* → ① 迟到成功翻转（事后兜底，已实现）② 生产应补**超时前置渠道查询**（事前防线，`queryPayStatus` 有定义未接线）。*那订单已经取消了？* → 走"业务拒绝自动退款"闭环：钱退回去，订单保持取消，用户无感知损失。
- *金额用什么类型？* → DB `DECIMAL(10,2)`、Java `BigDecimal`；分摊算法用**分**为单位整数运算 + 最大余数法（浮点会在多次部分退款后累积误差）。*渠道金额单位呢？* → 支付宝/微信是"分"，Mock 是元——**接入真实渠道时必须做单位映射**，这是接入清单里的第一条。

**⑤ 诚实边界 + 上生产我会补的三件事。** 当前三渠道全是文本 Mock、**没有验签**（仅内部可达）、`queryPayStatus` 未接线、无关单 API、手续费单档——这些在简历与文档里都要明说"Mock 渠道 + 回调模拟器，真实接入留 SPI"。若让我主导上生产：① **验签 SPI**（RSA2/V3 + 平台公钥轮换 + fail-closed）；② **超时前置查询 + 关单**；③ **回调端点公网化配套**（IP 白名单/限流/原始报文留存 90 天，用于对账举证与纠纷）。**一句话**：支付域的分水岭是"把渠道当不可信输入"——幂等、三态、迟到处理、对账四个词能自洽讲完，就是 P7 水平。

## X′. 订单状态机：状态表给查询，事件表给真相

**① 它到底干了什么。** 支付成功那一刻，代码做两件事：向 `t_order_event` 追加一条事件（`PAID, 0→1, seq=N`），再用条件 UPDATE 把订单状态置 1（`WHERE status=0`）。**状态表是给查询用的物化视图，事件表才是状态变迁的唯一事实来源**——这句话是本题的第一层答案。

**② 为什么需要双写。** 只改状态：没有审计（谁在什么时候把它改成 2 的？）、没有回放（对不上账时无依据）、并发下容易互相覆盖。只写事件：每次查询都要重放（性能不可接受）。双写 = 可查 + 可审计 + 可校准，代价是必须保证两者同事务、同胜负。

**③ 怎么做 + 三个真坑。**
- **条件 UPDATE 收敛并发**：所有流转都带前置状态条件，并发只有一个赢家；输家拿 0 行受影响，走各自的补退逻辑。
- **坑 1（锁序死锁，我们踩过并排除）**：最早为防序号冲突用了 `FOR UPDATE` 锁定读——结果 `appendEvent` 的锁序是"事件锁→订单锁"，而调用方（支付成功/取消）是"订单锁→事件锁"，**反向锁序**。改为无锁快路径：冲突时 `INSERT IGNORE` 返回 0 → **直接回滚**让调用方重试（重试时幂等检查会幂等跳过）。理由：冲突 ⇒ 对方也在追加 ⇒ 状态乐观锁必有一个输家 ⇒ 本事务本就该失败，回滚是正确语义而非妥协。
- **坑 2（创建事件从不落库，T-110）**：`ORDER_CREATED` 的目标状态原设 0，而创建时订单 status 也是 0 → 快速幂等检查 `current==target` 恒真 → **创建事件永远不写**，事件链从第一条就断了。修复：`ORDER_CREATED` 的 to 设为 **-1**（表示"非状态流转"）。
- **坑 3（事件在、状态退，T-123）**：人工重置状态或补偿重放后，事件表里已有 `REFUNDED`，但订单状态被改回 1 → 原实现"事件已存在即跳过" → **永久不一致**。修复：不重复插事件，但用乐观锁把状态**收敛**到事件的目标值。

**④ 三条追问链。**
- *为什么不用 Spring StateMachine 之类的框架？* → 我们缺的是"转移表 + 单一入口"，不是状态机引擎；引框架会把业务守卫（发货限管理端、取消需未支付）塞进配置，排障更远。**改进方向：自研显式转移表 + 单一 `transition()`，把非法流转挡在入口。**
- *事件表会不会无限增长？* → 会。当前只增不清理，按月归档是生产必需（冷表 + 查询路由），否则几年后单表十亿行扫不动。*那归档后怎么回放？* → 回放按 `order_id` 走归档路由，且回放本身只对单订单做（全量回放不是在线服务该干的事）。
- *校准为什么不自动跑？* → 全量扫代价高且会误伤"正在流转中"的订单。生产做法：**按"状态长期停滞"筛候选**（如 `updated_at` 超过业务最长流转时长），再 dry-run 出差异告警——注意校准永远只报告，不做自动覆盖（终态方向保护）。

**⑤ 关单链路：三条路径 + 补偿三件（必背的完整闭环）。**
- **三条路径**：用户主动取消 / RocketMQ 延时消息（`OrderCloseConsumer`）/ XXL-Job 兜底扫描（`OrderCloseJob`，防延时消息丢失）→ 最终都收敛到同一个 `closeTimeoutOrder`（状态守卫幂等）。
- **关单补偿三件**：`RELEASE_STOCK`（释放库存，用 `pseudoOrderId = fold-hash(orderNo)` 定位预扣记录——**半消息阶段订单还没入库，只能用 orderNo 派生幂等键**，释放必须用同一个派生值否则库存永久泄漏）/ `RETURN_COUPON`（退券，幂等靠券状态机）/ `CLOSE_ORDER`（关单）。三条动作**都不依赖订单状态**（P1-2 修复：旧实现一律调关单，对已取消订单直接跳过 → 库存/券泄漏）。
- **补偿落点**：Feign 失败/异常 → 消费 `ORDER_COMPENSATION_TOPIC` 重试（maxReconsume=3）→ 接近上限时写 Redis 兜底集合 → `OrderCloseJob` 每分钟重放（本轮加了 24h TTL + 每轮 20 条上限，防坏成员永久刷日志）。
- **TOCTOU 与收敛**：`cancelOrder/deliverOrder` 都是"先 select 判状态、再流转"——并发窗口由 `appendEvent` 的条件 UPDATE（乐观锁）兜住；输家以前抛 500，本轮改为业务异常（"订单状态已变化，请刷新"）→ 4xx 语义。
- **诚实边界**：状态机是隐式的、事件表无归档、校准无自动调度（三条在接入清单）；`checkLocalTransaction` 在缺 userId header 时退化为 `order_no` 全库扫描（生产链路由生产者必带 header，兜底路径已保留）；`*_at` 里程碑时间在事件事务之外补写（崩溃窗口由校准的"补齐里程碑时间"自愈）。
- **一句话**：订单状态机这道题，"先事件后状态 + 条件 UPDATE 单一赢家"是 P6 答案；能讲清"冲突为什么宁可回滚不抢锁""事件在状态退怎么收敛""关单三条路径与补偿三件怎么闭环"，才是 P7-P8。

## Y′. 优惠券：把"券"当钱管——四层防线和一个跟语义打架的补偿链

**① 它到底干了什么。** 一条券的生命周期四步：**领**（Lua 原子扣库存+记限领）→ **持有**（t_user_coupon 落库，异步）→ **用**（绑定订单，乐观锁单向流转）→ **退**（订单取消/退款时恢复"未使用"）。任何一步做错都会"多出券"——券就是钱，超发就是资损。

**② 为什么需要四层防线。** 领券是"Redis 快路径 + DB 落库"的双写：Redis 挂了会丢、MQ 会重投、DB 会失败。单一手段都挡不住超发，必须四层各管一段：**Lua 管并发原子性、Outbox 管发送可靠性、幂等键管重投、对账管长期漂移**。

**③ 怎么做 + 两个真坑。**
- **坑 1（回滚与作废必须成对）**：发送 MQ 失败时，我们回滚 Redis（stock+1、claimed-1）**并且把 Outbox 作废（status=2）**。只回滚不作废 → 补发 Job 稍后把消息发出去 → 用户"领券失败却拿到券"，而 Redis 计数已回滚、还能再领一次 → 超发。这个坑的教训是：**补偿任务与回滚路径必须共享同一个"事实"**（Outbox 状态）。
- **坑 2（一个跟现行语义打架的旧补偿链）**：代码里曾残留"退券 Redis 补偿链"（消费者在、生产者零调用），它会对 stock+1/claimed-1；但现行语义（RV30）明确"退券只恢复用户券状态，不动 stock/claimed"——因为**核销不扣 remain**，退券若回补就会出现 `remain + 已发 > total` 的超发敞口，且用户可"领→用→退→再领"绕限领。两条规则互相打架，一旦有人手工投递消息或误接线就直接超发。处置：**整链删除**（不是修——它服务的是被推翻的语义）。
- **-3 自愈**：Redis 重启丢 stock 键 → Lua 返回 -3 → 从 MySQL 初始化 + 重试；重试的错误码按语义分派（限领撞上限要返回"已达限领"而不是"已领完"）。

**④ 三条追问链。**
- *怎么防超发？* → 再背一遍四层（Lua/Outbox/幂等/对账）。*双写不一致怎么发现？* → stock 对账（Redis 为准修 DB）+ claimed 对账（DB 为准修计数）+ 卡住 Outbox 告警（用户被扣了却没拿到券必须可见）。*为什么两个对账方向相反？* → 因为实时权威不同：**发放走 Redis 权威，存量走 DB 权威**——谁在关键路径上扣减，谁是实时权威。
- *Redis 挂了能领券吗？* → 不能（Lua 失败 → fail-closed），这和库存预扣一样：**钱的事宁可不服务，不能超发**。恢复后从 DB 补齐。
- *热点券（秒杀）怎么办？* → 单 stock 键会成为 Redis 热点（单键 ~10w QPS 上限）；生产做法是**分桶**（N 个桶各挂库存，不足时邻桶借用，与库存域同款设计）。当前模板量级不需要，列为设计项。
- *退券为什么退给用户而不是回池子？* → 语义选择：券已发出，退回的是"用户的使用权"；回池会让`remain+已发`暴涨。要复用就等它过期（ExpireJob 批量 UPDATE 1000/批）。

**⑤ 诚实边界。** claimed 键无 TTL（以已发券为准的对账兜底）；claimed 对账是 per-key 查询（日切低峰可接受，量大改按模板聚合）；热点券未分桶。**一句话**：优惠券这题的分水岭是"把券当钱"——四层防线能背是 P6，能讲清"回滚与作废为什么必须成对"和"为什么退券不回补库存"，才是 P7-P8。

## Z′. 购物车：为什么"Redis 为权威"不是偷懒，是分工

**① 它到底干了什么。** 用户点一次"加入购物车"，Redis 上三个结构同时变：`items`（数量）、`checked`（勾选）、`sort`（排序）；一次 Lua 完成，键同 slot。MySQL 那边只有一条异步流水 + 一份镜像，供恢复与对账。

**② 为什么这么分工。** 购物车是"高频、多结构、弱一致"的场景：写入 QPS 高、结构有 3 个、用户对"刚加的没显示"容忍度远低于"丢一单"。把权威放 Redis 是拿**可恢复性**换性能：Redis 丢了能从 MySQL 镜像 + 事件流恢复；反过来（DB 权威）则每次操作都要写 DB，购物车会先把数据库压垮。

**③ 怎么做 + 三个真坑。**
- **坑 1（三结构各自为政）**：Hash 删了 Set 还在 = 勾选了一个不存在的商品；ZSet 还在 = 排序列表里的幽灵条目。所有多结构操作必须单 Lua（7 个脚本就是这么来的）。
- **坑 2（TOCTOU）**：`check_item` 原来"hasKey → SADD"两步，并发 `remove` 插在中间 → SADD 把已删商品重新"勾选"进来。改单脚本原子检查+写。
- **坑 3（清空与并发写）**：用户点清空的同时另一个标签页加购——清空的 DEL 与加购的 HSET 交错会留下"半个购物车"。防线是三层：事件按 userId 顺序消费（主）+ 实例内序号/时间戳 CAS（兜底）+ CLEAR 屏障（把清空时间记下来，晚于清空时间戳的事件丢弃）。屏障本身要有界——我们给过 24h 淘汰 + 50k 上限（无界 map 是内存泄漏的经典形态）。

**④ 三条追问链。**
- *Redis 丢了购物车会怎样？* → MySQL 镜像 + 事件流恢复；对账三分支：Redis 有 MySQL 无 → 补 MySQL；Redis 无 MySQL 有 → **要判断"是真删了还是 Redis 故障"**——itemsKey 不存在时只跳过不删，否则 Redis 一挂就把 MySQL 兜底一起删了（双份全丢）。
- *加购时校验库存吗？* → 不校验（校验要打库存服务，购物车是高频写；且购物车≠订单，库存应在下单时锁）。列表展示时用 SKU/SPU 状态标 valid，失效条目不参与结算。这是"可用性优先 + 下单兜底"的分工。
- *为什么不用一个 Hash 存所有信息（数量+勾选+时间）？* → 勾选要按成员查询/全选（Set 语义）、排序要按时间（ZSet 语义）；塞进一个 Hash 会让"全选"变成 O(n) 遍历。**结构选型跟着访问模式走**。

**⑤ 诚实边界。** 角标 `HLEN` 含失效条目（要精确就得逐个校验商品状态，代价不划算，取舍已注明）；TTL 刷新非原子；事件流水原先无保留策略（本轮补了 30 天清理 + created_at 索引）。**一句话**：购物车这道题的分水岭是"为什么敢让 Redis 当权威"——能讲清"可恢复性换性能 + 结构跟着访问模式 + 对账防双份全丢"，就到位了。

## AA′. 搜索：把"派生数据"当一场永不结束的对账

**① 它到底干了什么。** 用户搜"连衣裙"，请求打到 ES——但**权威数据在 MySQL**。ES 里的每一篇文档都是 MySQL 的派生副本，由两条通道搬运：Canal 解析 binlog 实时同步（毫秒级），MQ 补偿补漏（最终一致）；每天凌晨再全量重建做"兜底对账"。

**② 为什么需要两条通道 + 全量重建。** 单通道都会漏：Canal 会丢位点、MQ 会重投乱序、进程会宕机。设计上把"同步"当成**持续对账**：实时通道负责时效，全量重建负责兜底，外部版本号负责让两者打架时"新写赢"。

**③ 怎么做 + 三个真坑。**
- **坑 1（乱序写旧文档）**：Canal 的 binlog 事件可能乱序/重投，如果按到达顺序写，旧文档会覆盖新文档。修复：所有写带**外部版本号**（毫秒时间戳，`ExternalGte`），ES 自己拒绝"版本更低"的写。
- **坑 2（删了又活）**：删除事件先删文档，但一个更早的 update 事件晚到 → 已删文档"复活"。修复：删除写 tombstone（带 TTL），增量写前检查墓碑。
- **坑 3（全量重建的自我退化）**：重建完成后**必须清零断点**——原实现保留 lastId，次日"全量"从末尾继续，等于只做了增量，历史漏同步永远修不回来。另外重建写入也要带外部版本，否则重建中的"陈旧读"会覆盖并发的增量新写；版本冲突要当"已最新"跳过，否则整个重建批次报失败。

**④ 三条追问链。**
- *ES 和 MySQL 不一致怎么发现？* → 全量重建是"对账"：扫描 MySQL 全量 upsert 到 ES（带版本），并**清理源表已删的死文档**（否则已删内容一直能被搜到）。*为什么不删掉 ES 重建？* → 索引不能停服务；断点续传 + 版本序保证重建期间增量不丢。
- *深分页怎么做？* → search_after（用上一页最后一条的 sort 值当游标），避免 from+size 在深页时"每页重排全量"。*那 hasMore 呢？* → 多取 1 条（size+1），取满且多出 1 条才算有下一页。
- *热搜为什么用分钟桶而不是计数器？* → 热度要"随时间衰减"（Σ count×e^(-λΔt)），分钟桶 + 重算天然带时间维度；反作弊（IP/用户限频、屏蔽词）与写入放同一个 Lua，防刷与计数原子。

**⑤ 诚实边界。** 单节点 ES（副本 0）；suggest 只随全量重建刷新；GEO 召回无数据源；精排是规则；热搜快照 30 天保留（分钟级快照量大）；所有"临时键→RENAME"路径必须带 hash tag（ItemCF/热搜榜/热门池三处，否则 Cluster 下 RENAME 必失败）。**一句话**：搜索域的分水岭是"承认 ES 只是派生数据"——能讲清双通道 + 版本号 + tombstone + 重建对账这四件套怎么咬合，就到位了。

## AC′. 通知系统：把"实时"和"可靠"拆成两条路

**① 它到底干了什么。** 用户点赞了你的笔记 → 一条 MQ 事件到达通知服务 → ① 按"(用户,类型,目标,当天)"聚合（同一笔记当天第 5 个赞不再是 5 条通知，而是一条"等 5 人赞了你"）② 未读 +1（Redis 原子）③ 如果用户在线，SSE 推一条实时提醒。用户打开 App 时，看到的列表来自 MySQL——**推送来没来，不影响列表里有没有**。

**② 为什么这么拆。** 通知是"低频价值、瞬时价值"：用户在线的几秒内看到最有价值，但"最终一定能看到"才是底线。所以把可靠通道（列表 API + DB + 未读对账）和实时通道（SSE best-effort）分开设计——实时通道可以丢、可以重、可以降级，可靠通道必须准。

**③ 怎么做 + 三个真坑。**
- **坑 1（聚合把未读算错）**：聚合更新主通知时如果再 +1 未读，用户会看到"1 条通知 5 个未读"。规则：**只有新建通知才 +1**，聚合更新不增未读（红点已代表过它）。
- **坑 2（对账自己造错）**：未读对账按通知表分页扫描，原实现"每批各自汇总再回写"——用户未读跨批时，后一批的**部分计数**覆盖前一批的完整计数。修复：**全局累计所有批次后再统一修正**。
- **坑 3（订单通知的状态滞后）**：type=5 的通知命中同一聚合键（同一订单），若不刷新内容，用户会一直停在"待发货"（支付成功后那条）。修复：订单类命中聚合时定向 `UPDATE content`，不参与"等 N 人"的社交化标题。

**④ 三条追问链。**
- *SSE 推送失败/用户离线怎么办？* → 不重试（best-effort），列表 API 兜底。*那"实时"的意义？* → 在线时体感；离线的未读靠对账保证红点准确。*为什么不用 MQ 做推送？* → 推送是广播语义、量大、无消费确认需求；SSE 实例级定向 Channel 更轻（跨实例走 Pub/Sub 定向投递）。
- *未读为什么会不准？* → 三个来源：Redis 丢数据（对账重建）、并发归零吞 +1（窗口内收敛）、聚合逻辑错（坑 1）。每个都有对应防线。
- *聚合键为什么要带日期？* → 对齐 DB 唯一键（`user_id,type,target_id,notify_date`），让"当天聚合"在 DB 层也有强约束——Redis 窗口锁丢了也不会产生重复主通知。

**⑤ 诚实边界。** 归零吞 +1、跨时区边界、无断线回放、无保留策略——都已登记（含触发条件）。**一句话**：通知域的分水岭是"实时与可靠分开"——能讲清"推送只是加速、列表才是权威"，以及聚合为什么不能动未读，就到位了。

## AD′. 内容域：一篇笔记发布，背后有四件要善后的事

**① 它到底干了什么。** 用户点"发布"，服务端做四件事：① 笔记落库（`t_note`）② DFA 敏感词过滤 ③ 推 Feed（`FEED_TOPIC`）④ 计数/搜索/通知的后续联动。四件事分布在不同服务——**本地数据库只能保证第一件的原子性，其余三件都得靠"补偿设计"**。

**② 为什么用 Outbox 而不是"发完 DB 直接发 MQ"。** 直接发 MQ：DB 提交成功、MQ 发送失败 → 笔记存在但没人看到（Feed 没推）。Outbox：先与业务数据**同事务**写一条本地消息，提交后再发 MQ；发送失败由补偿任务重发（幂等）。**关键点在"同事务"**——本地消息与业务数据同生共死，补偿任务只补"发"，不判断业务。

**③ 怎么做 + 三个真坑。**
- **坑 1（DFA 词库与文本不同源）**：单词表里的词如果不做和正文一样的预处理（去空格、全角转半角、小写），含大写/空格的敏感词**永远不会命中**——词库形同虚设还不报错。修复：构建 trie 时对词做同一套 `preprocess`。
- **坑 2（热更新打碎 trie）**：动态词增删要重建 trie，如果在原结构上边删边加，读侧会看到"半个词库"。修复：**copy-on-write**——构建新 trie，完成后 volatile 发布引用；读侧要么全旧要么全新。
- **坑 3（Feed 重投死循环）**：发布事件的补偿重投，如果"已删笔记/大V路径"不标记完成，补偿任务会每 60s 重投同一条直到上限。修复：所有提前 return 的分支都要 `markPushCompleted`（或置终态），配 `push_status=3` 终态 + 指标。

**④ 三条追问链。**
- *计数事件丢了怎么办？* → counter 域的对账任务以 Redis 为准修 DB、以行为/权威集合重建（content 侧不重试正是为避免双写不确定性）；**承认"即发即忘"是设计，不是漏洞**。
- *审核流程呢？* → `auditStatus` 字段在，但**没有审核工作流**（无审核端点/任务队列）——状态由管理端/DB 驱动，审核流列为设计项（面试要主动说，别被问穿）。
- *评论删除与计数？* → 评论数缓存 `COMMENT_COUNT` 在评论增删时延迟双删（原实现删笔记时不失效它 → 删除后红点数最长 5 分钟不降）。

**⑤ 诚实边界。** 审核无工作流；计数事件无补偿；DFA 是词表级（无语义/变体识别）。**一句话**：内容域的分水岭是"承认跨服务没有本地事务"——能讲清 Outbox 补的是"发"不是"业务"、DFA 的两个坑（预处理同源/热更新），就到位了。

## AE′. 售后：一张优惠券怎么分、一分钱怎么退

**① 它到底干了什么。** 订单 ¥300、用了 ¥50 券、三件商品（¥100/¥120/¥80）。用户退第二件，该退多少？**不能退 ¥120**（券要按比例扣），也不能把 ¥50 全扣在它头上。答案：¥50 按 100:120:80 分摊 → 第二件分摊 = 50×120/300 = ¥20 → 应退 ¥100。

**② 为什么用"最大余数法"而不是简单四舍五入。** 三件分摊 16.67/20.00/13.33（四舍五入）→ 和 = ¥50.00 恰好；但换成 33.33/33.33/33.34 这类组合，逐项四舍五入的和常常不等于总额（差 1~2 分）。**最大余数法保证"Σ 分摊 == 优惠总额"**（先下整，余分给小数部分最大者），并且**永不把某件商品分摊超过它的金额**；平局按明细 ID —— 保证**确定性**：同一订单任何时间重算，结果逐分一致。

**③ 怎么做 + 三个真坑。**
- **坑 1（退款少几分）**：部分数量退款按比例下整（10 分退 1/3 = 3 分），三次各退 1 件累计 9 分 ≠ 一次退 3 件的 10 分。修复：**"本次退满"时用"整件可退 − 已占用"补齐差额**——多次退款累计严格等于整件可退。方向永远是"宁可少退，最后补齐"，不产生任何超退。
- **坑 2（不同类型并发双退）**：同一 SKU 可同时存在"仅退款"和"退货退款"两种申请（唯一键不同）。修复：额度校验的"已占用"包含**退款中**的单子（`status IN (3,4)`），第二单必然超额被拒。
- **坑 3（退款张冠李戴）**：按订单维度退款时，渠道回传的金额 + 时间可能对应多张售后单。修复：支付域**回传退款单号**，售后域按单号归属判定 + 恢复任务先核对事实（金额 + 类型 + 时间窗 + 单号）再决定"置完成/重试/失败"。

**④ 三条追问链。**
- *分摊结果为什么不落库？* → 纯函数 + 订单快照，任何时点可重算且确定性；落库反而引入"算法变更后历史数据口径不一致"。*那算法变更怎么办？* → 变更要评估历史重算的口径影响（边界已注明）。
- *退款和结算怎么对上？* → 结算按 T-1 渠道账单三方对账，差异分三类挂账；人工处理过的差异不被对账覆盖（尊重人工结论），消失的自动收敛。
- *手续费呢？* → 单档按收款毛额计提，跨日退款会让单日净额为负（口径一致）；分级费率是接入项。

**⑤ 诚实边界。** 手续费单档、分摊不落库、渠道是 Mock。**一句话**：售后资金的分水岭是"用整数运算把'不超退'做成可证明的不变量"——能讲清最大余数法 + 退满补差 + 在途占额度 + 退款单号归属，就到位了。

## AF′. 首页聚合：把"6 个服务"变成"1 次请求"的两个纪律

**① 它到底干了什么。** 打开首页 = 一次请求要拼齐：推荐流 + 每篇笔记的详情/计数/作者/是否点赞。这些数据分布在 6+ 个服务。聚合层用两轮 `CompletableFuture` 并行取数，任一路慢/挂都不能把整页拖死。

**② 为什么要"预算制"而不是"每层固定超时"。** 每层各给 3s，两层就是 6s——用户早就走了。正确做法是**全局预算**：总延迟 4s；第一层给 800ms 拿"主干数据"，第二层拿"剩余预算（≥500ms）"拿"装饰数据"。**装饰数据晚到不如不要**——降级成空值，页面主体先出来。

**③ 怎么做 + 三个真坑。**
- **坑 1（线程池饥饿）**：外层请求占了 `aggregatorPool` 的核心线程，内层的 future 又提交到同一个池 → 队列不扩容、核心线程不释放 → 内层任务饿死直到超时（表现为"偶发整页超时"）。修复：**内外两层用两个池**（外层 20/50/200，内层 30/80/500），内层只做 Feign 调用。
- **坑 2（一路挂拖垮全页）**：future 体内不捕获异常，异常完成的 future 在 `getNow()` 时抛 `CompletionException` → 整页 500。修复：**每个 future 体内 try/catch 降级**（返回空 map/0），`getNow(默认值)` 只在"超时未完成"时兜底。
- **坑 3（降级导致无限翻页）**：下游全挂时 `cards` 为空但 `hasMore=true` → 前端一直翻空页。修复：**空页时 `hasMore=false` + `nextCursor=null`**（宁可"到底了"，不可"永远有下一页"）。

**④ 三条追问链。**
- *为什么购物车页反而要硬失败？* → 降级的方向要按"页面语义"定：首页少几个卡片可接受；购物车页没有购物车就没有意义——**硬失败（503）比一张空壳页面诚实**。
- *CallerRunsPolicy 不会拖慢请求线程吗？* → 会（队列满时由请求线程执行下游调用，受 Feign 超时约束）；但相比"丢弃任务"，在聚合场景"降级执行"更符合可用性优先；拒绝策略的选择本身是取舍。
- *为什么不用响应式（WebFlux）？* → 这套聚合是阻塞 Feign + 线程池编排；换响应式是另一套成本模型（全链路非阻塞），当前规模用线程池 + 预算制更简单可控。

**⑤ 诚实边界。** 获赞统计 1000 条上限、推模式 cursor 用 ZSet 下标（取关左移漏推）、大V不写 following:latest——三条都已登记（拉模式覆盖）。**一句话**：聚合层的分水岭是"预算制 + 双池 + 按页面语义决定降级方向"——能讲清"装饰数据可丢、主干数据要快、购物车要硬失败"，就到位了。
