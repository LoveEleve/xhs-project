# vol-ai 写作与分析方法论

> 适用范围：`my-xhs-ai/docs/vol-ai/` 全部模块文档与后续重写任务。
> 目标：把 `my-xhs-ai` 从“功能清单 / 项目总结”写成一卷**可阅读、可验证、可交接、可面试复述**的 AI 系统深度解剖文档。

---

## 一、先定组织原则：按系统模块组织，不按抽象技术主题组织

`vol-ai` 不能按“Memory 篇 / Langfuse 篇 / Temporal 篇 / 测试篇”这种纯技术主题来平铺。

原因和 `vol-xhs` 一样：

读者真正想弄懂的不是“你用了哪些技术词”，而是：

- 这个 AI 项目到底是什么，不是什么
- 控制面在哪里，工具面在哪里，事实边界在哪里
- 为什么系统中心不是模型，而是 Harness
- 为什么这里需要审批、记忆、trace、PoC
- 哪些是真做完了，哪些还只是实验

所以本卷统一采用：

- **横轴：系统模块 / 能力分层**
- **纵轴：四个分析视角**

也就是：

- 目录按系统模块划分：`00-overview-architecture` 到 `06-temporal-durable-poc`
- 每个模块内部，再从四个视角解剖：
  1. 业务价值视角
  2. 执行控制视角
  3. 系统工程视角
  4. 平台边界视角

注意：

这四个视角不是四套独立目录，而是每篇文章、每个模块都必须有意识覆盖的四组问题。

---

## 二、四个视角分别回答什么

### 1. 业务价值视角

回答的是：

- 这个模块到底在帮谁解决什么问题？
- 它服务的是运营、运维、研发，还是终端用户？
- 它为什么值得存在？
- 如果没有它，真实业务会卡在哪里？

例如：

- `Intent Router` 不是路由炫技，而是在决定什么问题不该交给 Agent
- `HITL` 不是审批按钮，而是在把高危动作锁进人机协作边界
- `Memory` 不是“更聪明”，而是在帮助研发诊断用户记住上次排查过什么

这里必须先讲清**角色、问题、价值**，不能先讲类名和字段。

### 2. 执行控制视角

回答的是：

- 模型到底被怎样约束？
- 为什么这里不能让模型自由发挥？
- 它的行动边界在哪里？
- 结构化输出、工具调用、审批、恢复如何组成一套执行控制链？

重点包括：

- Intent Router
- Agent Harness
- ToolRegistry
- PolicyGuard
- HITL
- RunStore / checkpoint / resume

这是 `vol-ai` 区别于普通 AI 项目的核心视角。

### 3. 系统工程视角

回答的是：

- 这套系统为什么能跑起来？
- 为什么 trace、评测、记忆、PoC 不是点缀，而是工程基座？
- 哪些问题是配置问题，哪些是运行态问题，哪些是环境问题？

重点包括：

- API / SSE
- Langfuse trace
- E2E 测试
- Memory embedding
- Temporal PoC
- 运行脚本 / demo 脚本

这里必须讲**真实运行证据**，不能只讲设计图。

### 4. 平台边界视角

回答的是：

- 哪些能力已经真实做完了？
- 哪些能力只是 PoC？
- 哪些能力不能夸大？
- 当前为什么可以收官，收官口径该怎么讲？

重点包括：

- 已完成 vs PoC vs 未完成
- demo 级 vs 平台级
- 真实 E2E 证据
- 评测规模边界
- 多 Agent 的真实状态

这是 `vol-ai` 很重要的一层，因为这个项目已经进入**作品集 / 面试交付**阶段，不再只是代码记录。

## 三、模块文章的固定组织方式

每个模块都要遵守下面的主顺序：

1. **先写读者困惑**
2. **再给一句话答案**
3. **再建立最小心智模型**
4. **再推演一个直觉但失败的方案**
5. **再回到真实实现和源码证据**
6. **最后收束边界、代价与桥接**

推荐顺序：

1. 读者困惑
2. 一句话答案
3. 最小心智模型
4. 直觉方案为什么不够
5. 角色与时序 / 数据流 / 状态机
6. 主链路拆解
7. 源码证据
8. 工程落地问题
9. 边界、失败与代价
10. 当前状态（已完成 / PoC / 未完成）
11. 篇末桥接

注意：

- 不能按源码文件顺序写
- 不能按“我都做了什么”流水账写
- 不能先摆结论再补证据
- 不能把 PoC 写成已完成

## 四、`vol-ai` 的三步分离怎么落地

本卷继续遵守总方法论的三步分离：

1. 素材提取
2. 理解路径设计
3. 叙事写作

但在 AI 系统场景里，素材提取要额外补四类证据。

### 第一步：素材提取

每篇写作前，至少提取这些卡片：

- 核心入口：API / Controller / worker / signal / demo script
- 核心控制器：Router / Harness / PolicyGuard / ToolRegistry
- 下游依赖：MySQL / MCP / Prometheus / RocketMQ Dashboard / Langfuse / Embedding / Temporal
- 状态机：Run / WAITING_APPROVAL / Conversation / Memory / WorkflowState
- 关键配置：application.yml / env vars / trace 配置 / tool 白名单
- 失败路径：工具不可用、审批未通过、Langfuse trace 缺失、Temporal restart 卡住等
- 运行态证据：真实 trace、真实 E2E、真实 demo、数据库状态、Temporal 实验结果
- 已知边界：PoC、误报、未实现能力、未覆盖项

### 第二步：理解路径设计

先离开代码，回答：

- 读者在这个模块最容易困惑什么？
- 应该先讲“业务价值”还是先讲“控制边界”？
- 哪些实现细节现在讲会打断主线？
- 哪个失败方案最能逼出设计动机？
- 哪个问题适合放到下一篇展开？

如果这些问题答不出来，不允许直接写正文。

### 第三步：叙事写作

按理解路径写，不按代码文件顺序写。

优先顺序永远是：

- 问题
- 冲突
- 失败方案
- 设计顿悟
- 机制拆解
- 代码证据
- 运行证据
- 边界
- 桥接

## 五、证据分级：代码、语义、运行态三层证据

`vol-ai` 不能只靠“代码看起来像这样”下结论。

统一用三层证据法：

### L0：代码静态证据

能证明：

- 类、方法、配置、接口、状态、依赖真实存在
- 调用链、边界、状态流转在代码层面成立

典型材料：
- 文件路径
- `file:line`
- 关键代码片段
- 配置片段
- schema / tool spec / workflow interface

### L1：框架/语义证据

能证明：

- 某个框架行为到底如何解释
- 某个注解/中间件语义是否符合直觉
- 某个 trace / workflow / embedding / signal 语义是不是这样

典型材料：
- LangChain4j / Temporal / OTel / Spring / MCP 的框架语义
- SDK 行为
- CLI 语义
- 测试环境和真实环境的差异说明

### L2：运行态证据

能证明：

- 这个机制在真实环境里真的生效了
- 这次 trace / E2E / PoC 真跑通过
- 这次修复不是纸面修复，而是运行态验证过

典型材料：
- Langfuse trace 链接
- `CR_SUCCESS`
- demo 输出
- Temporal restart 脚本结果
- E2E 评测报告
- 日志与数据库状态

### 三层证据的使用规则

- 重要结论至少要有 L0
- 平台能力 / 可观测 / durable execution / 高危动作，优先要求到 L2
- 没有 L2 时，要明确写“PoC / 设计 / 预期”，不能冒充已闭环

## 六、`vol-ai` 特有的边界纪律

### 1. 状态分离铁律
`vol-ai` 里最容易写乱的，不是模块关系，而是状态层次。

后续所有文章都必须显式区分至少这五类状态：

1. **业务事实**：订单、支付、库存、日志、MQ、Prometheus 指标
2. **Run 状态**：step、budget、termination、approval、checkpoint
3. **Conversation 状态**：多轮消息、摘要、当前会话上下文
4. **Long-term Memory**：研发用户的历史诊断记忆（embedding + 语义检索）
5. **PoC 状态**：Temporal / Langfuse / 其他实验性能力的运行态

禁止把这些状态混成一个“大状态系统”来讲。

### 2. 能力分级铁律
`vol-ai` 里的所有能力，必须在文中显式标注属于哪一层：

- **已完成**：有代码 + 有测试或真实运行结果
- **PoC**：有代码 / 实验 / 单场景验证，但不是主线量产能力
- **未完成**：只有设计、部分实现或待补环境

例如：
- `dlq.redeliver` 真 E2E = 已完成
- Temporal restart = PoC
- 真正多 Agent 协作 = 未完成

不允许把 PoC 写成已完成，也不允许把已完成写得像平台全成熟。

### 3. 角色铁律
本卷必须始终写清楚“谁在使用系统”。

这里至少有两类用户：
- **研发 / 运维 / 运营诊断人员**：AI 诊断台的真实使用者
- **业务终端用户**：电商平台里的消费者/普通用户

`my-xhs-ai` 主要服务的是**前者**，不是后者。

所以：
- Memory 记住的是“研发上次查过什么”
- Demo 展示的是“研发如何排障”
- Trace 挂的是“诊断任务”而不是消费者行为

这条角色边界必须反复强调，不能混写成“用户画像系统”。

### 4. 证据优先级铁律
对 AI 项目来说，某些能力没有 L2 运行态证据就不能算硬证据。

下列主题，优先要求给出 L2：
- Langfuse trace
- DLQ 重投
- HITL 审批
- Memory 语义命中
- Temporal restart 恢复

如果只有：
- 代码
- 配置
- 单测

那最多算 L0/L1，不算“真实能力已落地”。

### 5. 禁止夸大铁律
下列写法一律禁止：

- 把 `BUSINESS/OPS/FULL` profile 分流写成“真正多 Agent 协作”
- 把基础 embedding memory 写成“MemoryOS 级长期记忆系统”
- 把 Temporal PoC 写成“主线已全面 durable”
- 把 5 条 E2E 写成“系统性全量验证”
- 把 Langfuse trace 接通写成“完整可观测平台”
- 把 `service.restart/order.refund` 这类未落地能力写成已开放

本卷宁可写得克制，也不允许写得虚高。

### 6. 不把 mock / test 当真链路
只有真实对外依赖跑通过，才算 L2 运行态证据。

### 7. 不把“接入大模型”当作核心成就
真正的核心成就是：
- 模型被约束了什么
- 工具边界怎么形成
- 审批怎么生效
- trace 怎么落地
- durable execution 怎么证明

## 七、卷内推荐顺序

当前建议：

1. `00-overview-architecture/`
2. `01-intent-router-harness/`
3. `02-tool-mcp-policy/`
4. `03-memory-conversation-rag/`
5. `04-hitl-dlq-observability/`
6. `05-eval-quality-release/`
7. `06-temporal-durable-poc/`

顺序原则：
- 先立住“这是什么系统”
- 再立住“模型怎么被控制”
- 再立住“工具和状态怎么协同”
- 最后再讲 trace / 测试 / PoC / 收官

### 卷内依赖图（先粗定）

- `00-overview-architecture`：全卷硬前置
- `01-intent-router-harness`：`02`、`04`、`05` 的硬前置
- `02-tool-mcp-policy`：`04`、`05` 的硬前置
- `03-memory-conversation-rag`：依赖 `00`，对 `04`/`05` 为软依赖
- `04-hitl-dlq-observability`：依赖 `01` + `02`，对 `06` 为软前置
- `05-eval-quality-release`：依赖 `01` + `02` + `04`
- `06-temporal-durable-poc`：依赖 `00` + `01`，但定位为收官后置篇

规则：
- 硬依赖没立住，不写后文
- 软依赖可局部解释
- 导航依赖只做桥接，不把后文结论当前提

## 八、写作完成后的深审

### 第一轮：事实审
- 文件、方法、路径、配置、数值是否真实

### 第二轮：口径审
- 已完成 / PoC / 未完成 是否分清
- 有没有夸大

### 第三轮：结构审
- 是否按理解路径，而不是按文件顺序
- 是否存在失败方案推演

### 第四轮：证据审
- 关键结论有没有真实证据支撑
- trace / demo / E2E / PoC 是否引用到位

## 九、`vol-ai` 的最终目标

本卷最终不是写成“AI 项目总结”，而是写成：

> **一套围绕企业级诊断 Agent 的深度系统解剖。**

它要让读者最终能回答：

- 这个项目到底是什么，不是什么
- 它为什么不只是“接了个大模型”
- 系统真正的中心为什么是 Harness
- 为什么 ToolRegistry / HITL / Memory / Langfuse / Temporal 各自有不可替代的角色
- 哪些是真做完了，哪些还不能夸大

这就是 `vol-ai` 的写作任务。
