# 为什么真正把这套系统和普通 AI Demo 拉开差距的，不只是模型会不会答，而是它能不能在高风险动作前停下来

> 对应目录：`vol-ai/04-hitl-dlq-observability/`
> 目标问题：很多 AI 项目都会讲“我们也接了工具、也能查数据、也能返回答案”，那 `my-xhs-ai` 和普通 demo 真正拉开差距的地方到底在哪？为什么这里最值钱的一层，不只是 `dlq.redeliver` 跑通了，而是系统能在高风险动作前停下来、给人看、留下证据、再继续执行？

## 一句话困惑

如果只从能力清单看，`my-xhs-ai` 已经有很多显眼的东西：

- 会查订单量
- 会查 5xx
- 会查 DLQ
- 会做 Memory
- 会做 Langfuse trace
- 甚至还能重投死信

从结果表面看，很多人会自然得出一个结论：

> 系统越厉害，应该越自动；既然模型都能查到 `ORIGIN_MESSAGE_ID` 了，为什么不直接把消息重投掉？为什么还要专门停下来进入审批？

这个问题非常重要。因为它会直接暴露 `my-xhs-ai` 和大量 AI Demo 之间真正的分界线：

- 普通 Demo 追求“模型会不会做出动作”
- 企业级系统必须回答“模型有没有资格直接做这个动作”

而 `HITL + DLQ + Langfuse` 正是这一层分界线最集中的体现。

## 一句话答案

`my-xhs-ai` 真正拉开和普通 AI Demo 差距的地方，不是它能不能回答问题，而是它把高风险动作做成了一条**可调查、可挂起、可审批、可恢复、可追踪**的链路；`dlq.redeliver` 只是其中最典型的例子，HITL 才是这套系统真正进入企业级语境的地方。

## 先建立最小心智模型

先把这一层最容易混掉的三件事分开：

```text
诊断
  = 查清问题发生了什么

执行
  = 真的去改变某个外部世界状态

审批
  = 在执行前，把控制权从模型收回给人
```

在很多 AI Demo 里，这三件事会糊成一条线：

```text
查到问题 -> 模型决定 -> 直接执行
```

而在 `my-xhs-ai` 里，真正的高危链路应该是：

```text
查到问题
  -> 形成候选动作
  -> 进入 WAITING_APPROVAL
  -> 人工 approve/reject
  -> resume 执行
  -> 留下证据与 trace
```

也就是说：
- 模型可以调查
- 模型可以提出执行意图
- 但模型不能天然拥有最终执行权

这条线如果不立住，前面已经建立起来的：
- Harness 边界
- 工具边界
- 记忆边界

都会在高风险动作这里被重新击穿。

## 先推演第一个最直觉、也最容易误导人的失败方案：查到 `ORIGIN_MESSAGE_ID` 就直接重投

这是绝大多数人第一次看到 DLQ 场景时的直觉方案。

### 为什么这个方案看起来合理

因为从业务流程上看，好像已经没有模糊空间了：

1. 先查到某条 DLQ 消息
2. 提取 `ORIGIN_MESSAGE_ID`
3. 知道 `retryTopic`
4. 再调用 `dlq.redeliver`

如果这一切都已经查清楚，看起来系统只差最后一步：

> 模型顺手帮你执行一下，不就完了吗？

这个思路在 demo 场景里非常诱人，因为它会让系统显得“更自动”“更 Agent”。

### 它会先坏在哪里

它会先坏在：**查清楚不等于应该立刻执行。**

`dlq.redeliver` 并不是一个“无副作用确认键”，它会把一条之前已经失败过的消息重新推回下游。只要重投错了，就可能导致：

- 错误消息再次污染下游
- 非目标订单被重新消费
- 库存 / 优惠券 / 补偿链再次被触发
- 本来已经处理完的异常被重新放大

也就是说，这里真正的问题从来不是“模型会不会找到 msgId”，而是：

> **谁来承担这次重投的最终责任？**

如果是模型直接执行，这个责任边界就是模糊的。

### 它第二次坏在哪里

它会坏在：**系统无法区分“调查能力”和“执行能力”。**

`mqDlqQuery` 和 `dlq.redeliver` 在形式上看起来都像工具调用，但语义完全不同：

- 前者是在读世界
- 后者是在改世界

如果没有一条显式的审批边界，系统很容易退化成：
- 只要模型能查到，就默认模型也能执行

一旦这条逻辑成立，后面别的高危动作也会自然滑坡：
- restart
- refund
- inventory compensate

所以这不是一个“单点动作”问题，而是一条**系统级滑坡路径**。

### 它第三次坏在哪里

它会坏在：**事后无法解释为什么执行了。**

在企业系统里，最危险的并不只是执行本身，而是执行之后没人说得清：

- 是谁触发的
- 当时看到了哪些证据
- 有没有人批准
- 为什么这条消息会被重投
- 如果出了事故，证据链在哪里

如果系统里没有挂起、审批、resume 和 trace，这种动作在事后会非常难解释。

所以“查到 `ORIGIN_MESSAGE_ID` 就直接重投”这个方案，不是更高效，而是会在三层同时失效：

1. 风险决策层失效
2. 执行边界层失效
3. 事后追责层失效

## 再推演第二个看起来更稳的失败方案：模型先征求一句确认，然后直接执行

有些人会觉得，上一个方案太激进了，那就温和一点：

> 模型先输出“请确认是否重投”，用户说一句“确认”，然后系统就直接执行。

这个方案比第一个更像“有人在回路里”，看起来也更安全。

### 为什么这个方案看起来合理

因为它似乎满足了最基本的人机协作：
- 模型没直接执行
- 人也说了“同意”
- 系统就继续走

在很多产品场景里，这已经会被当作“有审批”了。

### 它为什么还是站不住

因为这不是系统审批，而只是会话层确认。

也就是说，它只满足：
- 人说了一句“可以”

但不满足：
- 系统进入显式状态 `WAITING_APPROVAL`
- 审批信息被结构化记录
- 可以 reject
- 可以 resume
- 审批前任务可以停在一个稳定点
- 审批后任务可以继续完成
- 整个过程可以被 trace 和 run store 回放

这说明“会话确认”与“系统审批”完全不是一回事。

### 它第二次坏在哪里

它会坏在：**会话确认不是 durable state。**

这是这一层最关键、也最容易被忽略的失败点。

如果只是模型问一句、人回一句，然后系统继续执行，那么在这中间任何地方出问题：

- 进程挂了
- worker 重启了
- 页面关了
- 网络断了

系统都很难回答：
- 当前到底算批准了没有？
- 该不该继续？
- 继续时依据是什么？

也就是说，这种“会话式审批”没有 durable state。

而 `my-xhs-ai` 当前最值钱的地方之一，就是已经把这种“人确认一下”上升成了：
- `WAITING_APPROVAL`
- `approve/reject`
- `resume`
- Temporal PoC 下的 restart 恢复验证

### 它第三次坏在哪里

它会坏在：**审批不再是系统能力，只是交互话术。**

这会让整个项目退化成：
- 模型会先问一句
- 但系统层没有真正的审批状态机

如果是这样，后面你再接：
- Langfuse
- RunStore
- Temporal

其实都失去了意义，因为审批从头到尾只是 prompt 行为，而不是系统行为。

所以“会话确认就算审批”这条路也站不住。

## 真正的源码证明链：HITL 怎样从“问一句”变成系统能力

到这里必须把“高危动作必须停下来给人看”压成一条清楚的代码证明链。

### 第一级：Tool 层先定义风险等级
见：
- `my-xhs-ai-tools/src/main/java/com/myxhs/ai/tools/AgentToolCatalog.java`

这里已经把工具做了风险分级：
- L1
- L2
- L3

最关键的是：
- `mqDlqQuery` 属于 L2
- `dlq.redeliver` 属于 L3

这意味着系统在工具层就已经明确：

> 查可以是普通动作，重投不是。

### 第二级：`PolicyGuard` 决定它不是普通工具调用，而是审批动作
见：
- `my-xhs-ai-app/src/main/java/com/myxhs/ai/app/service/agent/harness/PolicyGuard.java:63-88`

这里最重要的判断链是：

- L3 且无执行器 → deny
- L3 且有执行器 → `requiresApproval`

也就是说，系统不是“知道它危险”而已，而是明确把它推向一个不同状态：
- 不是直接执行
- 也不是普通 deny
- 而是**审批门**

### 第三级：Harness 把审批门做成状态
见：
- `my-xhs-ai-app/src/main/java/com/myxhs/ai/app/service/agent/harness/AgentHarness.java:393-399`
- `:438-449`

这里发生的不是“模型说等等”，而是：
- `suspendForApproval(...)`
- 记录 `policyDenied` step
- `flagWaitingApproval`
- 生成 `approval_json`
- 持久化状态

这一步非常关键，因为它把审批从“交互语句”变成了**系统状态**。

### 第四级：`RunController` 把审批做成显式系统接口
见：
- `my-xhs-ai-app/src/main/java/com/myxhs/ai/app/controller/RunController.java:91-107`

这里必须明确分清两个入口：

- 普通诊断入口：`POST /api/runs`
- 审批语义入口：`POST /api/runs/{id}/approve`

这意味着审批不是聊天继续的一部分，而是**系统接口的一部分**。

返回值也不是“模型继续说话”，而是：
- `APPROVED_RUNNING`
- `REJECTED_CANCELLED`

所以 `RunController` 在这里证明的是：

> 审批语义已经从交互层提升到了系统 API 层。

### 第五级：`RunManager` / `RunStore` / Temporal PoC 共同证明“挂起后还能恢复”
这里分两层：

#### 主线系统
- `RunStore`
- `WAITING_APPROVAL`
- `resumeEntry`

证明：主线系统已经不是“问一句就算”，而是有挂起/恢复语义。

#### Temporal PoC
- `WAITING_APPROVAL`
- kill worker
- restart worker
- approve
- `COMPLETED`

这一步必须再钉一条边界：

> 这证明的是**审批型长任务具备 durable execution 的可行性**，不是证明主线已经全面迁移到 Temporal。

也就是说，Temporal 这里是**PoC 级别的能力证明**，不是主线架构切换事实。

### 整条证明链收束成一句话

所以真正完整的链，不是：

```text
模型发现问题 -> 用户确认 -> 执行
```

而是：

```text
风险分级
  -> PolicyGuard 裁决
  -> Harness 挂起
  -> 系统审批接口
  -> RunStore / Temporal 恢复
  -> 执行
```

这条链，才是 `my-xhs-ai` 真正的企业执行边界。

## 再补一层运行态证据：这不是纸上审批

### 运行态证据 1：DLQ 真链路已经跑到 `CR_SUCCESS`
这一条最值钱：

- Agent 先查 `mqDlqQuery`
- 提取 `ORIGIN_MESSAGE_ID`
- 进入 `WAITING_APPROVAL`
- approve
- 调 `dlq.redeliver`
- **返回 `CR_SUCCESS`**

也就是说，这套审批机制不是“理想上的守门人”，而是在真实高危动作上已经生效。

### 运行态证据 2：Langfuse trace 把审批前后都记录了下来
当前 Langfuse 里已经能看到：
- run trace
- generation
- tool
- answer
- userId / sessionId / model / tokens / cost

这意味着“停下来给人看”不只是产品语义，也已经进入了可观测语义。

### 运行态证据 3：Temporal PoC 已完成真实 restart 闭环
真实 PoC 已经证明：
- 启动 workflow
- 进入 `WAITING_APPROVAL`
- kill worker
- restart worker
- approve
- `COMPLETED`

这说明审批这件事，在当前项目里不是“方便时做一下”，而是已经被设计成一个可以承受中断的严肃执行边界。

## 普通 AI Demo vs 当前系统

| 维度 | 普通 AI Demo | `my-xhs-ai` |
|---|---|---|
| 工具调用 | 模型直接调 | 经过分级、注册、裁决 |
| 高危动作 | 直接执行或会话确认 | `WAITING_APPROVAL` + approve/reject |
| 审批状态 | 话术级 | 系统状态级 |
| 恢复能力 | 通常没有 | 主线 resume + Temporal PoC |
| 可观测 | 最多日志 | Langfuse trace |
| 责任边界 | 模糊 | 明确收回给人 |

这张表才真正解释了：
为什么这套系统和普通 AI Demo 的差距，不在“模型答得更聪明”，而在“系统敢不敢在该停的时候停下来”。

## 这层设计的代价

如果说 `HITL + DLQ + Observability` 是企业级边界，那代价也必须讲清楚。

### 1. 自动化程度被主动压低
当前系统不是在追求“模型最省人”，而是在追求“系统最可控”。

也就是说，它主动放弃了：
- 一键全自动执行高危动作
- 模型自由推进所有补偿逻辑

换来的是：
- 审计
- 可解释
- 可恢复
- 人在回路中

### 2. 链路复杂度明显上升
为了让一次 `dlq.redeliver` 安全成立，系统要串起来：
- tool level
- policy level
- harness state
- API
- store
- trace
- PoC

这显然比“直接调一下接口”复杂得多。

### 3. 但这个复杂度是必须的
因为一旦是高危动作，系统真正要优化的不是“最快做完”，而是：

> **最小化错误动作被自动执行的概率。**

这就是这层复杂度成立的根本理由。

## 收束结论

现在可以把开头的问题彻底收回来了。

真正把 `my-xhs-ai` 和普通 AI Demo 拉开差距的，不是模型更聪明，也不是工具更多，而是：

- 它会在高危动作前停下来
- 它会把控制权收回给人
- 它会把这次暂停、审批、恢复、执行全都纳入系统状态和 trace

所以这里最重要的结论是：

> **企业级 Agent 的分水岭，不是会不会调工具，而是敢不敢在该停的时候停下来。**

而 `my-xhs-ai` 已经在 `HITL + DLQ + Langfuse + Temporal PoC` 这条链上，把这件事做成了真实系统能力。
