# Agent 框架还是自研控制面：一个 Java 企业诊断系统的取舍

> 系列：T13 专题长文 | 版本：v1 | 日期：2026-08-18
> 配套：`theory-agent-v1.md`、`theory-enterprise-agent-engineering-v1.md`、`theory-evaluation-v1.md`
> 案例系统：`my-xhs-ai` 电商运营/运维诊断 Agent

---

## 一、先给结论

本项目没有因为“自研”本身更高级，就拒绝 LangGraph、CrewAI 或其他 Agent 框架；也没有因为框架流行，就把核心执行语义交给黑盒。

最终选择是：

> **复用成熟库解决模型调用、结构化输出和协议接入；自研最需要业务精确控制的 Agent 执行状态机。**

自研的对象不是整个 Agent 生态，而是一个有限范围的 Harness：

- Run/Step 状态；
- 工具调用循环；
- 证据登记与存在性校验；
- 预算与循环检测；
- checkpoint/resume；
- HITL 挂起与审批；
- SSE 事件；
- 评测指标。

这是一种**边界清晰的自研**，不是重复造轮子。

---

## 二、先区分“框架能力”和“业务执行语义”

成熟 Agent 框架通常可以帮助开发者完成：

- 模型客户端封装；
- Prompt/Message 管理；
- Function Calling；
- 基础 ReAct 循环；
- 工具注册；
- 多 Agent 编排；
- 状态图或节点编排。

但企业项目真正难以直接复用的，往往是业务执行语义：

- 哪个状态可以恢复；
- 哪个步骤不能重跑；
- 哪个工具需要审批；
- 哪类证据必须持久化；
- 哪些数字可以进入答案；
- 哪种拒答算成功；
- 哪种失败应该回流评测集。

这些语义不是框架名称能够自动决定的，必须根据系统自己的数据、权限和审计要求定义。

## 三、为什么本项目没有直接把核心交给框架

### 3.1 现有系统是 Java/Spring Cloud 电商平台

`my-xhs-ai` 需要直接接入既有 Java 体系：

- Spring Boot；
- Spring Cloud 服务；
- MySQL 分片；
- Prometheus；
- 日志与审计；
- 现有认证和配置体系。

Java 侧并非没有 Agent 能力，但成熟度、版本兼容和业务整合方式与 Python 生态不同。项目优先选择能直接嵌入现有系统的 LangChain4j + 自研 Harness，而不是为了追随某个 Python 框架重新拆出一套服务。

### 3.2 Durable 语义是项目核心，而不是附加功能

本项目不是短流程问答，而是包含：

- 多步工具调查；
- 状态持久化；
- checkpoint；
- 取消；
- 崩溃恢复；
- HITL 挂起；
- 审批后 resume。

本项目没有完成 LangGraph/CrewAI 的同场景 PoC，因此不宣称它们无法实现这些能力。真正需要评估的是：框架状态与项目 Run/Step Store、证据链和审批记录之间，是否存在清晰的映射、事实源和一致性策略。

如果没有明确映射就直接把框架状态当作业务状态，可能出现：

- 双写；
- 状态漂移；
- 恢复语义不一致；
- 审计记录缺失。

一套系统里最多只能有一个执行事实源；其他状态必须明确是投影、缓存或派生视图，不能两边都可写却没有冲突策略。

这时真正需要回答的不是“哪个框架更流行”，而是：

> **框架状态如何映射到业务事实模型，映射成本是否低于当前受控范围内自研？**

### 3.3 安全边界不能隐藏在 Prompt 或黑盒循环里

本项目的安全红线是：

- 不执行任意 SQL；
- 不执行任意 Shell；
- 不执行任意 PromQL；
- 工具 deny-by-default；
- 参数白名单；
- L3 工具必须 HITL。

因此每个工具调用都必须经过：

```text
模型决策
  → ToolRegistry
  → schema/参数校验
  → profile 工具子集
  → access level
  → HITL（如 L3）
  → 实际执行
```

如果安全检查主要依赖 Prompt，或者封装在项目团队没有显式控制和测试的中间层里，就很难审计，也很难证明“注入不能绕过权限”。问题是控制权和测试可见性，而不是某个框架天然不安全。

### 3.4 证据链是领域语义，不是通用日志

通用框架可以记录 tool call，但本项目还要求：

- 每次调用生成 evidenceId；
- 最终答案的 `evidenceRefs` 必须命中本轮真实调用；
- 证据需要包含来源、窗口、反证和不确定性；
- Run 结束后可追溯。

这不是简单的“保存一段工具输出”，而是业务诊断的事实约束。因此 `ToolResultRegistry`、`EvidenceChain` 和 `EvalAsserter` 必须与业务状态一起设计。

## 四、自研 Harness 到底自研了什么

### 4.1 不是自研模型调用

模型调用使用 LangChain4j 的 OpenAI-compatible ChatModel。项目没有重新实现：

- HTTP 模型协议；
- Tokenizer；
- 模型推理；
- JSON 解析基础库。

### 4.2 自研的是执行控制面

这里的“自研 Harness”不是指一个类包揽全部能力，而是指围绕 Agent 执行控制面的协作组件：

| 组件 | 责任 |
|---|---|
| `AgentHarness` | 决策循环、handler、预算、证据校验 |
| `RunManager` | 异步调度、会话锁、恢复、取消、SSE |
| `JdbcRunStore` | Run/Step/checkpoint 持久化 |
| `ToolRegistry/PolicyGuard` | 工具元数据、权限、参数校验 |
| `EvalRunner/EvalGate` | 评测执行、指标与门禁 |

`AgentHarness` 负责：

```text
读取 Run 状态
  → 构造上下文
  → 调用模型
  → 解析结构化决策
  → Policy/Tool 校验
  → 调用工具
  → 登记证据
  → 写 checkpoint
  → 继续、挂起或终止
```

每个环节都有明确终止原因和预算语义。

### 4.3 为什么状态机适合这个项目

状态机的优点不是“代码更简单”，而是状态转换显式：

```text
RUNNING
  ├─ TOOL_CALL → RUNNING
  ├─ ANSWER → SUCCEEDED
  ├─ DECLINE → SUCCEEDED/明确拒答
  ├─ L3 工具 → WAITING_APPROVAL
  ├─ CANCEL → CANCELLED
  ├─ 超时/预算 → PARTIAL 或 FAILED
  └─ 恢复 → RUNNING
```

显式状态让以下问题可以被测试：

- 什么情况下释放会话锁；
- 什么情况下 SSE 发送终态；
- 什么情况下允许 approve；
- 什么情况下禁止重复 resume；
- 什么状态可以被恢复 worker 认领。

### 4.4 自研范围必须控制

如果自研范围不断扩大，就会变成危险的“平台幻想”。本项目刻意不自研：

- 通用模型推理框架；
- 通用向量数据库；
- 通用消息队列；
- 通用分布式工作流平台；
- 通用观测平台。

只在业务约束无法由现成组件直接表达的地方自研。

换句话说：不属于业务差异化的能力交给成熟组件，业务约束最强的控制面保留在自有代码中。

### 4.5 当前自研与 Temporal 的位置

| 维度 | 当前自研控制面 | Temporal 类平台 |
|---|---|---|
| 状态持久化 | 直接使用项目 Run/Step Store | 平台提供通用持久化/重放语义 |
| 失败恢复/重放 | 围绕本项目 checkpoint 与状态认领定制 | 原生工作流重试/回放能力更强，但需映射业务状态 |
| HITL | 直接按业务审批模型定制 | 可以建模，但需要适配业务状态 |
| 部署复杂度 | 单服务、较低 | 需要额外平台组件与运维能力 |
| 通用性 | 面向当前诊断场景 | 更强，适合多类长流程 |
| 当前阶段 | 足够验证业务闭环 | 可能过重，后续可做对照 PoC |

这不是“Temporal 不好”，而是当前需求规模下先选择较小的控制面；如果并发、长任务、跨服务工作流和可靠性要求继续增长，应重新评估 Temporal 等 Durable 平台。

### 4.6 为什么不是简单地在框架外包一层

“框架负责循环，外层负责审计”看起来简单，但需要确认边界是否足够深入：

- checkpoint/resume 需要进入执行循环的恢复点；
- HITL 挂起需要暂停并恢复同一份上下文；
- 证据登记必须覆盖每次真实工具调用；
- 终止原因必须和状态转换保持一致；
- 预算、循环检测和工具权限需要在执行前阻断。

如果这些能力只在外层观察，可能出现“外层以为已记录、内层已经继续执行”或“外层恢复了 Run、框架内部上下文却不同步”。因此本项目选择让最小控制面掌握这些核心边界，而不是把它们做成事后监听器。

这也不意味着框架不能被包裹；如果框架能提供清晰的状态钩子、恢复语义和事实源映射，外层适配仍然是可行方案。

## 五、先评估框架，再决定是否自研

正确流程不是“框架不好，所以自研”，而是：

```text
定义业务状态/安全约束
  → 成熟框架最小 PoC
  → 对照状态、恢复、审批、证据、观测映射
  → 评估迁移/运行/维护成本
  → 决定采用、包裹或自研最小控制面
```

本项目在 D1-D4 已通过 LangChain4j 验证模型、结构化输出和工具调用；后续围绕真实电商诊断场景扩展 Run Store、HITL、证据和评测控制面。LangGraph/CrewAI 的同场景 PoC 尚未完成，因此它们属于待验证替代方案，而不是已被实验否定的方案。

## 六、什么时候应该使用成熟框架

自研不是默认答案。以下场景更适合直接使用成熟框架：

### 5.1 快速验证产品想法

如果目标是验证：

- 模型是否能调用工具；
- 某个 Prompt 是否有效；
- 某个 RAG 流程是否有价值；

优先用成熟框架，避免过早建设状态机。

### 5.2 业务状态很简单

如果任务：

- 一次请求内完成；
- 没有审批；
- 没有副作用；
- 不需要崩溃恢复；
- 不需要复杂审计；

那么框架默认循环通常已经足够。

### 5.3 团队需要 Python 生态能力

如果团队主要使用 Python，且岗位/项目依赖：

- LangGraph；
- AutoGen；
- CrewAI；
- Eino；
- 现有 Python 工具链；

直接采用对应生态通常比 Java 自研更高效。

## 七、什么时候值得自研

建议同时满足几个条件再自研：

1. 状态和恢复是核心业务语义；
2. 权限和审批不能交给黑盒；
3. 需要与现有 Java/微服务体系深度集成；
4. 需要精确控制证据和审计；
5. 有足够测试能力维护自研状态机；
6. 已经通过原型证明需求真实存在。

`my-xhs-ai` 的选择正是这个交集：它不是先写一个通用 Agent 平台，而是先围绕真实电商诊断场景验证了状态、证据、安全和评测需求。

---

## 八、自研与框架的真实代价

自研 Harness 也带来成本：

- 需要自己处理状态竞态；
- 需要自己补恢复测试；
- 需要自己维护模型适配；
- 需要自己设计评测；
- 需要自己跟踪框架/模型升级；
- 需要自己解释每个终止状态。

项目实际 review 中已经发现过：

- Router Bean 不一致导致两入口行为分裂（`architecture-review-v1.md` P0-1）；
- 会话锁释放时机问题（`review-m11-impl.md`）；
- 状态枚举变化遗漏终态判断点（`review-m11-impl.md`）；
- 评测器把列表序号误判为业务数字（`EvalAsserterTest`、`review-m14-impl.md`）；
- 复杂归因触发 `BUDGET_STEPS`（nightly 质量摘要）。

所以“自研”不是少依赖，而是把复杂度从框架外显地搬到了自己的代码和测试里。

## 九、如何做出正确的技术决策

可以用下面的决策表：

| 问题 | 如果答案是“是” | 建议 |
|------|----------------|------|
| 是否需要多次恢复和重放？ | 状态是核心语义 | 评估 Durable 框架或自研子集 |
| 是否有高风险副作用？ | 需要审批与审计 | 权限/审批必须由代码控制 |
| 是否已有稳定 Java 业务体系？ | 集成成本高 | 优先 Java 生态，避免无谓拆服务 |
| 是否只是验证想法？ | 需求未确定 | 先用成熟框架 |
| 是否需要跨 Agent、跨系统通信？ | 单进程不够 | 评估 A2A/消息协议 |
| 是否有能力维护自研状态机？ | 没有测试/维护资源 | 不要自研 |

### 9.1 保留可替换边界

即使当前自研，也不应把系统锁死。应保持以下稳定接口：

- `ToolSpec` 与工具参数契约；
- `Evidence`/证据模型；
- `RunStatus`/终止原因；
- 评测用例与报告格式；
- `PolicyGuard`；
- 业务工具接口。

未来可替换的部分包括：

- Agent loop；
- checkpoint engine；
- worker scheduler；
- model provider adapter。

如果重新开始，且目标只是验证模型能否调用工具，我不会先写 Harness，而会先用成熟框架做最小 PoC；当前自研选择成立，是因为项目已经进入状态持久化、HITL、证据审计和 nightly 评测阶段。这个选择仍应保留复盘入口：若未来某个成熟框架能以更低成本覆盖这些语义，就应重新评估，而不是把自研当成终点。

技术选型不是“哪个框架最先进”，而是：

> **哪个方案能以最低复杂度满足当前最重要的业务约束，同时保留未来替换边界。**

## 十、面试表达模板

如果面试官问“为什么不用 LangGraph”，可以这样回答：

> 我不是因为 LangGraph 不好才不用，而是因为这个项目的核心问题不是普通的工具循环，而是 Java 电商体系里的 Run/Step 持久化、证据引用、权限、HITL 和恢复语义。成熟框架可以解决模型调用和基础编排，我仍然复用了 LangChain4j；但如果把业务状态和框架状态强行混在一起，会产生状态漂移和审计困难。因此我只自研最小 Harness 控制面，而没有重新实现模型调用、协议或数据库。这个取舍的代价是自己承担状态竞态和测试维护，所以我用 review、单测、真模型门禁和 nightly 评测来约束它。

---

## 十一、本文要点

1. 自研不是目标，业务执行语义才是目标。
2. 框架解决通用编排，自研解决无法直接表达的业务约束。
3. 状态、权限、证据和审批不能被黑盒化。
4. 自研范围应限制在控制面，不要重复实现整个 Agent 生态。
5. 原型期优先成熟框架，需求确定且状态语义复杂后再考虑自研。
6. 自研的复杂度不会消失，只会转移到代码、测试和维护中。
7. 最好的架构往往是“成熟库 + 小范围自研”，而不是全盘自研或全盘依赖。
