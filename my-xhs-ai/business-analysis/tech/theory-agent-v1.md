# 什么是企业级 Agent：从 Chatbot、Workflow 到受限诊断 Agent

> 系列：T9 理论讲解 | 版本：v1 | 日期：2026-08-18
> 配套：`retrospective-v1.md`、`pitch-3tier-v1.md`、`nine-questions-v1.md`
> 案例系统：`my-xhs-ai` 电商运营/运维诊断 Agent

---

## 一、先给结论

**会调用大模型的程序，不一定是 Agent；真正接近 Agent 的，是能基于目标、当前状态与环境反馈，动态决定下一步行动的系统。**

但在企业场景里，真正有价值的不是让 Agent 更自由，而是让它在明确边界内完成任务：

- 能根据问题选择下一步行动；
- 能调用外部工具获取事实；
- 能根据工具结果调整后续计划；
- 能在证据不足时停止或拒答；
- 能受到预算、权限、审计和评测约束。

因此，本文采用一个工程定义：

> **企业级 Agent = 受约束的模型决策循环 + 确定性工具 + 状态管理 + 权限治理 + 质量评测。**

模型只是决策循环中的一个组件，不是整个系统。

### Agent 不等于完全自治

企业系统真正交给模型的，不是"任何事情都让它自己决定"，而是**可验证、可撤销、可审计**的一部分决策权；不可逆、高风险动作必须交还给代码约束或人工审批。

## 二、Chatbot、Workflow、Agent 的区别

### 2.1 Chatbot：生成回答

Chatbot 的基本流程是：

```text
用户输入 → 模型生成文本 → 返回文本
```

它适合：

- 问答
- 改写
- 总结
- 简单知识库问答

仅以文本生成为中心的 Chatbot，通常不会把以下能力作为核心执行模型：

- 多步任务状态；
- 工具执行顺序；
- 失败恢复；
- 权限审批；
- 结果可审计。

这不是产品名称的绝对区分；一个 Chatbot 也可以逐步增加工具、会话和审计能力。关键在于任务状态与动态决策是否成为系统的一等公民。

### 2.2 Workflow：代码决定路径

Workflow 的路径由代码预先定义：

```text
输入订单查询
  → 计算时间窗口
  → 查询订单量
  → 格式化结果
  → 返回
```

Workflow 的优势是：

- 可重复；
- 可测试；
- 可预测；
- 成本稳定。

它的局限是：面对开放问题时，所有可能路径都需要提前编码。

### 2.3 Agent：模型参与下一步决策

Agent 的典型循环是：

```text
读取问题/状态
  → 模型决定下一步
  → 调用工具或生成答案
  → 读取工具结果
  → 再决定下一步
```

关键差异不是“用了函数调用”，而是：

> **下一步做什么，不完全由代码固定，而是会根据当前状态和工具结果动态决定。**

例如：

```text
用户：为什么订单量下降了？

Agent：
1. 查当前订单量
2. 查基线订单量
3. 查漏斗转化
4. 发现支付正常，再查订单服务错误
5. 根据证据定位断点
```

如果步骤 3 发现支付失败率异常，后续路径可能转向支付失败码；如果发现指标数据为空，后续路径可能转向数据采集链路。

### 2.4 一张表看懂三者区别

| 维度 | Chatbot | Workflow | Agent |
|---|---|---|---|
| 下一步决策 | 模型生成文本 | 代码固定 | 模型基于状态决定 |
| 工具调用 | 可选 | 固定 | 动态 |
| 状态恢复 | 通常非核心 | 可编码 | 通常必须显式设计 |
| 权限治理 | 依产品实现 | 代码控制 | 必须限制模型动作 |
| 评测重点 | 文本质量 | 结果正确性 | 决策、工具、证据、完成率 |

## 三、为什么企业系统不能只做“自由 Agent”

自由 Agent 看起来灵活，但企业系统会立刻遇到五类风险。

### 3.1 事实风险：模型会编造

模型可以生成一个看似合理的数字，但这个数字可能没有来自任何数据源。

在业务诊断中，“订单下降 23%”和“订单下降 18%”不是语言风格差异，而是两个不同的经营结论。

### 3.2 权限风险：模型可能调用不该调用的能力

如果模型能自由生成 SQL、Shell 或 PromQL，就无法通过 prompt 保证它永远不越权。

企业系统必须把“模型想做什么”和“系统允许做什么”分开：

```text
模型提出动作
  → PolicyGuard 校验
  → 工具注册表校验
  → 参数白名单校验
  → 高风险动作进入人工审批
```

### 3.3 稳定性风险：Agent 可能循环或发散

Agent 可能：

- 反复查询同一指标；
- 不断切换时间窗口；
- 工具结果已经足够却继续探索；
- 在预算耗尽前无法收束。

因此必须有步骤、Token、成本和循环检测边界。

### 3.4 恢复风险：长任务不是一次 HTTP 请求

一次 Agent 调查可能持续几十秒甚至更久，中间包含多轮模型调用和工具调用。

如果进程在第 8 步崩溃，系统必须知道：

- 前 7 步是否完成；
- 哪些工具已经调用；
- 当前证据有哪些；
- 从哪里恢复；
- 是否会重复执行有副作用的动作。

### 3.5 质量风险：回答一次正确不等于系统稳定

模型输出具有随机性。一次 demo 成功不能证明下一次 prompt、模型版本或数据窗口变化后仍然正确。

企业 Agent 需要把质量转成指标：

- 任务通过率；
- 完成率；
- 幻觉率；
- 证据数量；
- 工具调用准确性；
- 时延；
- Token 与成本；
- 发散率。

## 四、企业级 Agent 的最小组成

本文把企业级 Agent 拆成六个组件。

### 4.1 决策循环

负责根据当前问题、历史状态和工具结果决定下一步。

在 `my-xhs-ai` 中，它由 `AgentHarness` 执行，模型输出结构化决策：

- `TOOL_CALL`：调用工具；
- `ANSWER`：生成最终答案；
- `DECLINE`：明确拒答或说明超出能力范围。

### 4.2 工具层

工具不是给模型一个 Shell，而是给模型一组受控能力：

- `order.query_volume`
- `payment.success_rate`
- `funnel.conversion`
- `service.http_errors`
- `mq.consumer_lag`
- `mysql.replication_lag`
- `log.search`

每个工具都有描述、参数 schema、权限级别和执行器。

### 4.3 状态层

状态至少包括：

- 当前 Run 的执行状态；
- 已完成步骤；
- 工具结果和证据；
- 消息上下文；
- 预算消耗；
- 最终答案。

`my-xhs-ai` 用 Run/Step Store 和 checkpoint 保存这些状态。

### 4.4 治理层

治理层决定 Agent 能不能做某件事：

- deny-by-default；
- 工具注册表；
- 参数白名单；
- L1/L2/L3 权限；
- HITL 审批；
- 审计日志。

### 4.5 观测层

当前观测层实现的是 run 级指标、步骤记录、工具审计和成本估算：

- 模型调用记录；
- 工具调用；
- 步骤耗时；
- Token；
- 成本估算；
- 终止原因；
- 失败和 bad case。

完整的 LLM 全链路 Trace、可视化平台和供应商账单级成本治理仍属于后续增强项。

### 4.6 评测层

评测层不是上线后的附属品，而是 Agent 的安全网：

- YAML 用例；
- 硬断言；
- 数字一致性；
- LLM-as-judge；
- bad case 回流；
- smoke/regression/nightly 分层。

## 五、为什么 `my-xhs-ai` 采用 Workflow + Agent 分层

系统没有让所有请求都进入 Agent，而是先判断问题类型。

### 5.1 确定性问题走 Workflow

例如：

```text
2026-08-01 到 2026-08-07 的下单量
```

这类问题有明确的：

- 时间窗口；
- 业务口径；
- 数据工具；
- 结果格式。

直接调用确定性工具更可靠，也更便宜。

### 5.2 归因问题走 Agent

例如：

```text
为什么订单量下降了？定位漏斗断点
```

这类问题没有固定的单一查询路径，可能需要：

- 当前/基线订单量；
- 浏览、加购、下单、支付漏斗；
- 支付失败事件；
- HTTP 5xx；
- 数据采集异常；
- 业务口径核对。

这时 Agent 的动态调查能力才有价值。

### 5.3 这种分层的三个收益

1. **减少不必要的模型调用**：固定查询不消耗 Agent 预算。
2. **提高结果可重复性**：确定性指标不受模型随机性影响。
3. **缩小评测范围**：模型只在真正需要推理的场景中承担不确定性。

这也是企业系统中“最简单可行架构优先”的体现。

## 六、为什么“能调用工具”还不够

很多 Demo 具备 Function Calling，就把自己称为 Agent。但工具调用只是能力基础，不是企业级完成标准。

### 6.1 工具调用不等于证据可信

模型调用了工具，不代表最终答案一定引用了工具结果。

`my-xhs-ai` 的运行时约束是：

```text
真实工具调用 → ToolResultRegistry
最终答案 evidenceRefs → 必须命中 Registry
```

### 6.2 工具调用不等于权限正确

模型可能调用一个真实存在、但当前角色不允许使用的工具。

因此工具注册表同时保存 access level，PolicyGuard 在执行前再次校验。

### 6.3 工具调用不等于任务完成

模型可能调用了很多工具，却没有形成结论；也可能形成结论却没有说明不确定性。

所以评测必须同时检查：

- 是否完成；
- 是否有证据；
- 是否引用真实结果；
- 是否违反边界；
- 是否在预算内收束。

## 七、什么才算“企业级”

“企业级”不是用了多少框架，也不是模型参数有多大，而是系统能否在不确定性下保持可控。

### 最低标准

- 工具受控；
- 权限明确；
- 证据可追溯；
- 状态可恢复；
- 失败可解释；
- 质量可回归；
- 成本可估算、可封顶、可追踪；完整账单级成本治理仍需供应商账单或运行平台支持。

### `my-xhs-ai` 当前的实证

在 `mimo-v2.5-pro` 下，nightly 100 条全量结果为：

- 通过率：100%；
- 完成率：96%；
- 幻觉率：0%；
- 平均耗时：23.3 秒/条；
- 平均 Token：10,324/条。

这里需要准确解释：

- 100% 通过表示样本满足当前断言；
- 96% 完成表示 100 条中 96 条以 `SUCCEEDED` 结束；其余少量样本以允许的 `PARTIAL/BUDGET_STEPS` 终止，但仍满足当前用例断言，因此通过率仍为 100%；
- 0% 幻觉表示本轮没有发现未匹配的业务数字；
- 这些是当前数据、当前模型和当前评测集下的实测结果，不等同于所有生产流量下的永久保证。

## 八、常见误区

### 误区 1：Agent 越自由越高级

企业系统恰恰相反。自由度越高，权限、审计、恢复和评测成本越高。真正的能力是知道哪里应该自由，哪里必须固定。

### 误区 2：多 Agent 一定优于单 Agent

多 Agent 增加了分派、上下文、通信和评测复杂度。`my-xhs-ai` 先做单 Agent 地基，再用 BUSINESS/OPS PoC 对比评测，而不是默认堆多 Agent。

### 误区 3：Prompt 写得好就不会幻觉

Prompt 可以改善行为，但不能替代运行时校验。证据引用、权限边界和评测门禁必须由系统确定性执行。

### 误区 4：一次 Demo 成功就是完成

Demo 只能说明一个样本成功。企业系统需要 smoke、regression、nightly 和 bad case 回流。

### 误区 5：失败就是模型差

失败可能来自：

- 模型未收束；
- 工具不可用；
- 数据缺口；
- 评测断言错误；
- 预算过紧；
- 权限边界生效。

工程化 Agent 的重要能力，是把这些原因区分开。

## 九、面试表达模板

如果面试官问“你做的 Agent 和普通聊天机器人有什么区别”，可以这样回答：

> 普通聊天机器人主要解决文本生成，而我的系统解决的是受约束的多步调查。它先把确定性查询走 Workflow，把复杂归因交给受限 Agent；Agent 只能调用注册工具，所有数字必须关联真实证据，执行型工具需要人工审批，长任务有 checkpoint 和恢复，最终还要经过完成率、幻觉率、时延和成本评测。我们在 `mimo-v2.5-pro` 下跑过 100 条 nightly，结果是 100% 通过、96% 完成、0% 幻觉。这个结果不是对模型永远正确的承诺，而是对当前系统约束和评测闭环有效性的实证。

---

## 十、本文要点

1. Agent 的本质是动态决策循环，不是简单 Function Calling。
2. 企业 Agent 的核心不是自由，而是受控的自由。
3. Workflow 与 Agent 应按问题确定性分层。
4. 工具、状态、权限、评测和观测必须一起设计。
5. 运行时证据校验比 prompt 口头承诺更可靠。
6. 评测集和评测器本身也需要测试。
7. 通过率、完成率、幻觉率必须分开理解。
8. “企业级”首先意味着可控、可解释、可回归。
