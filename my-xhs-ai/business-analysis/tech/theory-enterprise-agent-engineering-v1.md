# 企业级 Agent 的核心工程原理：状态、恢复、安全与评测

> 系列：T10 理论讲解 | 版本：v1 | 日期：2026-08-18
> 配套：`theory-agent-v1.md`、`retrospective-v1.md`、`nine-questions-v1.md`
> 案例系统：`my-xhs-ai` 电商运营/运维诊断 Agent

---

## 一、本文要回答什么

上一篇解释了 Agent 与 Chatbot、Workflow 的区别，本文进一步回答一个更工程化的问题：

> **一个 Agent 怎样才能从“能调用工具”变成“可以在企业系统里被管理”？**

答案不是再加一个模型，而是建立五个工程边界：

1. 状态边界：一次执行到底保存什么；
2. 语义边界：会话、知识和长期记忆如何区分；
3. 恢复边界：进程崩溃后从哪里继续；
4. 权限边界：模型可以提出什么动作，系统允许执行什么动作；
5. 质量边界：如何证明模型没有持续变差。

---

## 二、四类状态为什么必须分离

企业 Agent 最容易出现的架构问题，是把所有上下文都叫“Memory”。实际上，至少要区分 Run、Conversation、RAG 和 Memory。

### 2.1 Run：一次执行的状态

Run 描述一次具体任务：

- 用户问题；
- 当前状态；
- 已执行步骤；
- 工具结果；
- 证据引用；
- Token 与成本；
- 终止原因；
- 最终答案。

Run 的生命周期通常是：

```text
RECEIVED → RUNNING → SUCCEEDED
                    → PARTIAL
                    → FAILED
                    → CANCELLED
                    → WAITING_APPROVAL → RUNNING
```

Run 关注的是“这一次任务执行到哪里了”，不是用户长期偏好。

### 2.2 Conversation：多轮对话关系

Conversation 描述用户与系统之间的多轮关系：

```text
conversation
  ├── message（用户问题）
  ├── message（Agent 回答）
  ├── message（用户追问）
  └── runId 关联
```

Conversation 解决的是：

- 这次追问属于哪次会话；
- 上一轮结论是什么；
- 当前问题是否承接上文；
- 会话列表和审计如何组织。

它不等于执行状态，也不等于长期用户记忆。

### 2.3 RAG：外部知识与业务口径

RAG 保存的是系统外部知识：

- 指标定义；
- 业务口径；
- 故障手册；
- 运维文档；
- 版本说明。

RAG 的典型流程是：

```text
文档 → 解析 → 分段 → Embedding → 索引
查询 → BM25/向量检索 → 融合 → 上下文
```

RAG 回答“系统知道什么”，Run 回答“这次查到了什么”。二者不能混淆。

### 2.4 Memory：跨会话长期事实

Memory 保存可能跨越多个 Conversation 的信息：

- 用户偏好；
- 常查指标；
- 历史确认过的业务约束；
- 案例记忆；
- 长期画像。

Memory 必须有自己的：

- 所有权；
- 更新策略；
- TTL；
- 权限；
- 删除机制；
- 冲突解决规则。

`my-xhs-ai` 当前已实现 Run、Conversation、RAG，以及 Conversation 内的规则摘要；独立用户级长期 Memory Store 尚未实现。这种边界必须明确，不能把摘要注入包装成完整长期记忆。

### 2.5 状态 ownership 表

| 状态 | 主要回答 | 主要写入者 | 主要读取者 |
|------|---------|-----------|-----------|
| Run | 这次执行到哪里 | RunManager/Harness | 状态查询/SSE |
| Conversation | 用户前后文是什么 | ConversationService | 下一轮上下文 |
| RAG | 系统口径和知识是什么 | Ingest 管道 | 检索/回答 |
| Memory | 用户长期事实是什么 | Memory 策略 | 跨会话 Agent |

ownership 清晰后，TTL、权限、更新和删除策略才能分别设计；否则所有数据都塞进“上下文”会导致生命周期和权限混乱。

### 2.6 状态一致性与最终一致性

多种状态并存后，问题不再只是“有没有数据”，还包括写入顺序和失败补偿：

- Run 已完成，但 Conversation 消息写入失败；
- SSE 已发送，但 Run Store 尚未更新；
- checkpoint 已写入，但指标尚未更新；
- 审批记录已写入，但 resume 请求重复到达。

工程上不能假设所有存储和网络操作同时成功，必须明确：

1. 哪个状态是事实源；
2. 哪些更新需要事务；
3. 哪些事件允许异步最终一致；
4. 失败后如何重试、补偿或向用户显式报告。

`my-xhs-ai` 的设计重点是 Run Store 的状态与 checkpoint 可恢复、SSE 事件有明确顺序、审批状态转换具备条件控制；完整跨系统事务仍不等同于分布式强一致。

## 三、为什么不能把上一轮工具结果直接塞进下一轮

假设用户第一轮问：

```text
为什么订单量下降了？
```

Agent 查到某个窗口订单量为 5 单。第二轮用户问：

```text
那支付呢？
```

如果系统直接把第一轮工具原文当成永久事实，就会有三个问题：

1. 旧窗口可能已经不是当前窗口；
2. 旧数据可能被清理或更新；
3. 旧证据可能与第二轮问题的时间范围不一致。

因此更安全的策略是：

```text
跨轮保留：问题、结论、摘要、会话关系
跨轮不直接保留：旧工具原文作为当前事实
需要新数字：重新调用工具查询
```

这是一条重要原则：

> **Conversation 可以承接语义，不能替代当前事实查询。**

## 四、Durable Execution 到底解决什么

### 4.1 MQ 只能传任务

消息队列可以告诉消费者“有一个任务要处理”，但它通常不能完整表达 Agent 的内部执行状态：

- 模型已经决策了几次；
- 哪些工具已经调用；
- 哪条证据已经登记；
- 当前消息上下文是什么；
- 当前预算消耗多少；
- 是否正等待人工审批。

因此：

> **MQ 是传输机制，Durable Runtime 是执行语义。**

### 4.2 Durable 的最小数据模型

`my-xhs-ai` 的核心模型可以抽象为：

```text
ai_run
  run_id
  user_id
  session_id
  query
  status
  termination_reason
  budget_json
  versions_json
  started_at
  ended_at

ai_step
  run_id
  step_no
  state
  decision_json
  tool_result
  evidence_id
  messages_snapshot
  created_at
```

其中 `messages_snapshot` 是恢复的关键：它让系统能够重建模型下一步所需的上下文。恢复时不重跑已经完成的模型决策和工具步骤，而是从最后一个未完成边界继续。

**成熟度说明**：Run/Step 持久化、checkpoint/resume 已实现并有测试；真实 `kill -9` 故障注入演示尚未完成，不能把代码测试等同于生产故障演练。

### 4.3 Checkpoint 的含义

Checkpoint 不是简单保存一个“当前步骤数字”，而是保存恢复所需的最小完整状态：

- 已完成的步骤；
- 模型决策；
- 工具结果；
- 证据登记；
- 消息上下文；
- 预算消耗；
- 当前画像或策略版本。

如果只保存 step number，而不保存上下文，恢复时仍然无法知道模型应该基于什么继续。

### 4.4 状态 CAS 与原子认领

恢复任务时不能让两个线程同时接管同一个 Run。可以把它理解成概念伪代码：

```text
扫描到超时 RUNNING
  → 以“当前状态 + 最后活动时间”为条件做原子认领
  → 只有认领成功的 worker 才能 resume
```

只有成功更新的线程才获得恢复权。这样可以避免：

- 两个 worker 同时恢复；
- 同一工具被重复调用；
- 两份最终答案互相覆盖。

### 4.5 幂等不是所有工具都天然具备

只读查询通常天然幂等：重复查一次不会改变业务状态。

执行型工具则不同：

```text
审批通过 → 执行动作 → 记录 EXECUTED
```

恢复时必须先检查执行记录，避免重复副作用。

所以 Durable 的完整问题不是“能不能恢复”，而是：

> **恢复后能不能在不重复副作用的前提下继续。**

## 五、HITL：为什么人工审批不是简单确认框

### 5.1 高风险动作的两阶段模型

执行型 Agent 不应该直接从模型决策跳到副作用操作：

```text
模型提出动作
  → WAITING_APPROVAL
  → 人工查看工具、参数、理由
  → APPROVED / REJECTED
  → resume 或终止
```

从设计目标看，审批界面应让人看到：

- 哪个工具；
- 哪些参数；
- 为什么需要执行；
- 相关证据；
- 操作人；
- 审批时间；
- 审批理由。

当前项目已实现 `WAITING_APPROVAL`、approve/reject、审计和 resume，并由自动化测试验证；真实 DLQ 重投仍受上游 `ORIGIN_MESSAGE_ID` 查询接口异常影响。

### 5.2 为什么挂起要释放线程

错误实现是：

```java
while (!approved) {
    Thread.sleep(...);
}
```

这会占用 worker，并在并发增加时快速耗尽线程池。

正确语义是：

```text
RUNNING → WAITING_APPROVAL（线程结束）
审批事件 → 从 checkpoint resume（重新获得执行线程）
```

因此 `WAITING_APPROVAL` 是一个持久化状态，不是某个线程的临时状态。

### 5.3 审批拒绝也是完整结果

拒绝不能简单返回 HTTP 403 就结束。系统还需要：

- Run 进入明确终态；
- 保存 approver、时间、理由；
- SSE 推送审批结果；
- 后续查询能看到审计记录；
- 恢复逻辑不能再次执行被拒绝动作。

### 5.4 审批本身也需要幂等

审批请求可能因为客户端重试、网络重传或并发操作重复到达。因此审批接口也要做状态条件控制：

```text
只有 WAITING_APPROVAL
  → approve/reject 才生效
非挂起状态
  → 返回冲突，不重复 resume
并发 approve/reject
  → 只有一个状态转换成功
```

这和执行型工具的副作用防重是两层问题：前者防止重复恢复，后者防止重复业务动作。

### 5.5 `my-xhs-ai` 的真实边界

当前 HITL 状态机、挂起、审批、resume 和 fake 测试链路已经实现并验证；`dlq.redeliver` 的真实 RocketMQ 端到端仍受上游 `ORIGIN_MESSAGE_ID` 查询接口 NPE 影响。因此应区分：

- **HITL 控制流已实现并测试**；
- **真实死信重投链路尚未完全闭环**。

## 六、PolicyGuard：安全不能只靠模型听话

### 6.1 Prompt 约束不是权限控制

Prompt 可以告诉模型“不要删除数据库”，但不能成为最后一道安全边界。模型可能：

- 误解任务；
- 输出错误工具名；
- 被间接注入影响；
- 构造异常参数。

因此权限必须在模型之外确定性执行。

### 6.2 Deny-by-default

Deny-by-default 的含义是：

```text
没有明确注册、明确权限、明确参数规则
→ 默认拒绝
```

而不是：

```text
先允许所有工具，再依赖模型自觉
```

### 6.3 三层控制

`my-xhs-ai` 的工具治理按执行顺序可以拆成四层：

1. **注册控制**：工具是否存在于 ToolRegistry；
2. **参数控制**：参数是否符合 schema 和白名单；
3. **画像/权限控制**：当前 Agent profile 和角色是否允许访问该工具与 access level；
4. **人工控制**：L3 工具是否经过 HITL 审批。

其中 profile 工具子集解决“这个 Agent 能不能看到/调用这类工具”，access level/HITL 解决“这个动作是否需要额外授权”，两者不是同一层。

### 6.4 Prompt Injection 的正确防法

Prompt Injection 无法被可靠地完全识别，但可以限制其影响范围：

- 它不能注册新工具；
- 不能突破参数白名单；
- 不能绕过 L3 审批；
- 不能获得任意 SQL/Shell/代码执行权。

这不等于所有信息泄露风险都已经解决。提示词泄露、PII 脱敏、恶意 RAG 内容和输出安全仍需要数据最小化、权限过滤与红队测试。

## 七、评测闭环为什么是一等公民

### 7.1 评测不是最后才加的测试

普通软件通常把输入、输出和错误状态定义得比较明确；Agent 的答案是开放文本，不能简单全文比较。

因此需要分层：

| 层级 | 检查内容 | 作用 |
|------|---------|------|
| 硬断言 | 状态、证据数量、关键词、禁用模式 | 确定性正确性 |
| 数字一致性 | 答案数字与证据数字 | 明显幻觉信号 |
| 工具分析 | 调用次数、参数、发散 | 行为质量 |
| LLM-as-judge | 结论质量、不确定性 | 主观质量补充 |
| 人工分析 | bad case 归因 | 评测集进化 |

### 7.2 通过率和完成率不是一回事

本次 nightly 100 条结果（当前数据、`mimo-v2.5-pro` 和当前评测断言规则下）：

- 通过率 100%；
- 完成率 96%；
- 幻觉率 0%。

这表示：少量复杂归因用例以允许的 `PARTIAL/BUDGET_STEPS` 终止，但仍满足当前用例的状态、证据和其他断言。也就是说：

```text
pass = 是否满足用例断言
completion = 是否以 SUCCEEDED 终止
```

两者不能混成一个指标。

### 7.3 评测器也可能有 Bug

本项目曾真实发现并修复多类评测误报：

- `1) 2) 3)` 列表序号被当业务数字；
- 零证据拒答仍被送入数字一致性检查；
- `0.553s` 与 `553ms` 单位换算被误判；
- Markdown 表格排名数字被当业务数字。

这说明：

> **评测代码本身也必须拥有单测和边界样本。**

### 7.4 如何解释发散率

nightly 摘要中综合发散率约 35%。它表示部分 Run 出现同工具多窗口/多参数探索，不等于 35% 失败。

需要同时观察：

- 发散后是否最终完成；
- 发散是否触发预算；
- 发散带来的额外 Token；
- 哪些工具描述容易让模型反复尝试。

因此发散率是优化信号，不应直接当成门禁失败率。

## 八、把这些原理串成一条执行链

一个企业 Agent 的完整执行链可以表示为：

```text
用户问题
  ↓
Workflow / Agent 路由
  ↓
读取 Conversation 摘要与当前 Run 状态
  ↓
模型提出结构化决策
  ↓
ToolRegistry + PolicyGuard 校验
  ↓
工具调用 / HITL 挂起 / 拒答
  ↓
记录 Step、Evidence、Checkpoint
  ↓
根据环境反馈继续或结束
  ↓
答案存在性校验与质量评测
  ↓
Run 终态 + 审计 + 指标
```

这条链里每一层都回答一个问题：

- Router：该不该用 Agent？
- Conversation：这是不是同一个对话？
- Run：这次执行到哪里？
- ToolRegistry：能调用什么？
- PolicyGuard：当前允许调用吗？
- HITL：高风险动作是否获批？
- Checkpoint：崩溃后从哪里恢复？
- Evidence：答案依据是什么？
- Eval：这次行为是否满足质量标准？

## 九、面试表达模板

如果面试官问“企业级 Agent 最难的地方是什么”，可以这样回答：

> 最难的不是让模型调用一个工具，而是把不确定的模型决策放进一个可管理的执行系统。我会把问题拆成五个边界：Run 保存执行状态，Conversation 保存多轮关系，RAG 保存外部知识，Memory 负责长期事实；checkpoint 和状态认领解决恢复与幂等；PolicyGuard 和 HITL 解决越权与高风险操作；最后用分层断言、数字一致性和 nightly 评测把非确定性转成可观察指标。以 `my-xhs-ai` 为例，MiMo V2.5 Pro 下 100 条 nightly 全量通过率为 100%、完成率 96%、幻觉率 0%，但我仍把少量 `PARTIAL/BUDGET_STEPS` 视为收敛效率观察点，而不是把通过率包装成永久正确性。

## 十、本文要点

1. Run、Conversation、RAG、Memory 是不同状态，不应统称为 Memory。
2. Conversation 可以承接语义，不能替代当前事实查询。
3. Durable 的核心是 checkpoint、状态认领和幂等恢复。
4. HITL 是持久化状态流转，不是线程阻塞等待。
5. PolicyGuard 必须在模型之外确定性执行。
6. Prompt Injection 的正确防法是限制影响范围，而不是幻想完全识别。
7. 通过率与完成率必须分开解释。
8. 评测器本身也需要测试。
9. 发散率是优化信号，不等于失败率。
10. 企业 Agent 的核心是把模型决策纳入可管理的执行系统。
