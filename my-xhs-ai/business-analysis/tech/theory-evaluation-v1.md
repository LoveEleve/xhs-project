# Agent 评测与质量闭环：从“回答像不像”到可回归工程指标

> 系列：T11 理论讲解 | 版本：v1 | 日期：2026-08-18
> 配套：`theory-agent-v1.md`、`theory-enterprise-agent-engineering-v1.md`、`retrospective-v1.md`
> 案例系统：`my-xhs-ai` 电商运营/运维诊断 Agent

---

## 一、为什么 Agent 必须被评测

传统接口通常有明确的输入、输出和错误码，可以用精确断言验证：

```text
输入 A → 输出 B
```

Agent 的输出却包含开放文本、动态工具路径和非确定性决策：

```text
输入 A → 多轮决策 → 多个工具 → 开放式结论
```

因此，Agent 评测不能只问：

> “这段回答听起来像不像正确答案？”

而要拆成几个可观察问题：

1. 是否选择了合理的执行路径？
2. 是否调用了允许的工具？
3. 工具参数是否正确？
4. 是否真的完成了任务？
5. 结论数字是否来自证据？
6. 是否在预算内收束？
7. 时延、Token 和成本是否可接受？
8. 面对数据不足或越权请求，是否诚实拒答？

这就是 Agent 质量闭环的起点：**把开放式行为拆成可观测证据和统计指标。**

---

## 二、评测的四个层次

### 2.1 单元层：验证确定性机制

单元测试不负责证明模型“聪明”，而是证明系统边界不会失效：

- JSON 决策解析；
- 工具参数白名单；
- 证据引用存在性；
- 循环检测；
- 预算触发；
- 状态转换；
- 数字抽取和单位换算；
- 拒答路径。

`EvalAsserterTest` 的价值就在这里：它发现并修复了列表序号、窗口数字、Markdown 排名、秒/毫秒等评测器自身误报。

### 2.2 契约/集成层：验证工具和数据口径

工具测试验证：

- 工具名和参数 schema；
- 返回 JSON 结构；
- 时间窗口解释；
- 分片扫描口径；
- 哨兵值处理；
- MCP 请求/认证/审计契约。

这一层解决的是“模型调用到的工具是否可信”，而不是模型是否会规划。

### 2.3 真模型门禁层：验证关键用例

`EvalGateRunTest` 只选最关键的锚点：

- 业务归因；
- 技术排障；
- 诚实拒答。

门禁适合 PR 或小范围回归，重点是快速发现严重退化，而不是覆盖所有自然语言变体。

### 2.4 Nightly 全量层：观察分布和长尾

Nightly 负责跑完整评测集，观察：

- 业务问题的不同表达；
- 运维问题的不同组合；
- 安全/拒答边界；
- 多轮和边缘输入；
- 发散、预算和时延长尾。

`my-xhs-ai` 当前使用：

- smoke：20 条；
- regression：80 条；
- 合计：100 条。

## 三、为什么不能只用一个“准确率”

Agent 的质量至少需要分成以下指标。

### 3.1 通过率 Pass Rate

```text
通过率 = 满足当前用例全部断言的样本数 / 总样本数
```

它回答：

> 这个样本的硬断言、证据要求和软质量检查是否全部通过？

通过率不是模型事实正确率，因为它依赖当前用例和断言设计。

### 3.2 完成率 Completion Rate

```text
完成率 = 以 SUCCEEDED 终止的样本数 / 总样本数
```

它回答：

> Agent 是否真正完成了任务，而不是在 PARTIAL 或预算终止状态下结束？

这和通过率不同：一个 `PARTIAL` 样本可能被用例允许，因此通过，但不代表完全完成。

本次 nightly 的结果就是一个典型例子：

- 通过率：100%；
- 完成率：96%；
- 幻觉率：0%。

准确解释是：少量复杂归因样本触发了允许的 `PARTIAL/BUDGET_STEPS`，但仍满足当前断言。

### 3.3 幻觉率 Hallucination Rate

在本项目中，幻觉率是一个确定性启发式信号：

```text
答案中未能与真实工具证据匹配的业务数字样本数 / 参与检查的样本数
```

它依赖两层机制：

1. **运行时存在性校验**：`evidenceRefs` 必须命中本轮真实工具调用；
2. **评测数字一致性**：答案数字与工具结果数字做容差/单位语义比对。

注意：数字一致性不是完整自然语言事实验证，不能证明所有文本结论都正确。

### 3.4 工具调用质量

不能只看最终答案，还要看 Agent 是否正确使用工具：

- 是否选对工具；
- 参数是否合理；
- 是否反复改变无关窗口；
- 是否调用了当前 profile 不允许的工具；
- 是否在证据足够后继续探索。

`ToolUsageAnalyzer` 的 divergence 信号，就是对行为路径的补充观察。

### 3.5 时延、Token 和成本

至少记录：

- 每次 Run 时延；
- 每步耗时；
- 输入/输出 Token；
- 成本估算；
- budget 触发；
- 重试次数。

本轮 nightly 的基础观测：

| 指标 | smoke 20 | regression 80 | 合计 100 |
|------|:--:|:--:|:--:|
| 平均耗时 | 26.1s/条 | 22.6s/条 | 23.3s/条 |
| 平均 Token | 11,122.5 | 10,124.8 | 10,324.3 |
| 平均步骤 | 10.0 | 9.0 | 9.2 |
| 平均证据 | 4.0 | 3.5 | 3.6 |
| 发散率 | 40.0% | 33.8% | 35.0% |

这些是本轮观测值，不等同于供应商账单、月度成本或生产容量保证。

## 四、断言应该如何分层

### 4.1 硬断言：确定性边界

适合检查：

- 状态是否在允许集合；
- 证据数量是否达到最低要求；
- 必须出现的关键词；
- 禁止出现的泄漏/执行语义；
- 禁止匹配的 PII 或危险模式。

硬断言应该少而明确，不能用大量关键词把模型答案锁死。

### 4.2 软断言：质量信号

数字一致性、工具调用分析和发散率属于软断言或质量信号：

- 它们可以发现明显异常；
- 它们不应被包装成完整语义证明；
- 它们需要容忍单位换算、日期、列表序号和派生数字。

### 4.3 LLM-as-judge：主观质量补充

Judge 适合评价代码断言难以表达的内容：

- 结论是否回答问题；
- 不确定性是否说明充分；
- 证据与结论是否相关；
- 建议是否具有可执行性。

但 Judge 也不是事实真相：

- Judge 自身也会犯错；
- 必须保留原始答案、证据和评分理由；
- 不能用 Judge 替代权限和存在性校验。

### 4.4 人工分析：评测集的进化入口

bad case 不应该只记录“失败”，而要分类：

- 模型规划问题；
- 工具描述问题；
- 参数 schema 问题；
- 数据口径问题；
- 评测断言问题；
- 预算/时延问题；
- 合理拒答但用例设计错误。

分类之后，才能决定是改 prompt、改工具、改评测，还是接受边界。

## 五、为什么评测器本身也要被评测

本项目 nightly 前后真实暴露过多类评测器问题：

### 5.1 列表序号误报

模型回答使用 `1)`、`2、` 或 Markdown 表格排名时，数字抽取器不能把这些序号当成业务数字。

### 5.2 时间窗口误报

“最近 7 天”“最长 31 天”“2025 年 1 月”是查询上下文，不是业务指标结果。

### 5.3 单位换算误报

`0.553s` 与 `553ms` 是同一个事实的不同单位表示。

### 5.4 零证据拒答误报

`DECLINE` 是明确的零证据路径。没有工具证据时，不应该把拒答文本中的年份、时间范围数字拿去做业务数字一致性检查。

这些问题说明：

> **评测器不是上帝视角，它也是需要边界样本、回归测试和版本管理的软件。**

## 六、如何处理评测失败

遇到失败，第一步不是调高阈值或修改 prompt，而是先分类。

### 类型 A：模型未完成

表现：

- `BUDGET_STEPS`；
- `PARTIAL`；
- 证据已收集但未形成结论。

处理：

- 查看是否集中在复杂问题；
- 分析步骤和 Token；
- 检查是否反复换窗口；
- 再决定优化 prompt、工具描述或预算。

### 类型 B：工具/数据问题

表现：

- MCP 超时；
- 数据源为空；
- 业务事件表缺失；
- 真实接口断链。

处理：

- 不把基础设施错误归因给模型；
- 把数据 partial/空结果传给答案；
- 对用户说明不确定性。

### 类型 C：评测器问题

表现：

- 模型回答合理但断言失败；
- 单位、日期、排名或列表序号误报；
- 拒答用例要求了不应有的证据。

处理：

- 先修断言逻辑；
- 补边界单测；
- 重新跑受影响集合；
- 不为了让数字好看而放宽所有断言。

### 类型 D：合理边界

表现：

- 模型明确拒绝当前不支持的退款数据；
- 日志白名单不包含目标服务；
- 用户前提与当前观测相反。

处理：

- 用例应该允许诚实拒答；
- 记录能力边界；
- 不强迫模型调用无关工具来“凑证据”。

## 七、Nightly 的质量闭环

完整闭环不是“跑一次测试”，而是：

```text
评测集
  → Agent 执行
  → 原始报告
  → 指标汇总
  → bad case 分类
  → 修复代码/工具/断言/数据
  → 受影响集合回归
  → 更新评测集与报告
```

本轮 `my-xhs-ai` 已经完成：

- smoke 20 条全量；
- regression 80 条全量；
- MiMo V2.5 Pro 关键门禁；
- 评测器多类误报修复；
- nightly 质量与成本摘要。

当前剩余的重点不是“有没有评测”，而是：

- 发散样本如何减少；
- 复杂归因如何更快收束；
- Token/时延如何继续降低；
- bad case 如何稳定回流；
- 评测集如何防止过拟合当前模型。

## 八、面试表达模板

如果面试官问“你怎么评测 Agent”，可以这样回答：

> 我不会只看答案像不像，而是分层评测。单元层验证状态机、权限和评测器边界；工具契约层验证 MCP、参数和数据口径；真模型门禁验证关键业务/排障/拒答用例；nightly 再观察 100 条样本的分布和长尾。指标上把通过率、完成率、幻觉率、工具调用、时延、Token 和发散率分开。`my-xhs-ai` 在 `mimo-v2.5-pro` 下跑过 100 条 nightly，当前断言下通过率 100%、完成率 96%、幻觉率 0%，平均 23.3 秒/条；其中完成率低于通过率，是因为少量复杂归因允许以 `PARTIAL/BUDGET_STEPS` 结束。我还专门给评测器补了列表序号、日期窗口、单位换算和零证据拒答的边界测试，因为评测器本身也可能产生误报。

---

## 九、本文要点

1. Agent 质量不是一个准确率，而是一组互补指标。
2. 通过率、完成率和幻觉率必须分开解释。
3. 工具调用路径是质量的一部分，不能只看最终文本。
4. 硬断言适合边界，软断言适合异常信号，Judge 适合主观补充。
5. 评测器本身也必须有边界测试。
6. bad case 先分类，再决定改模型、工具、断言还是数据。
7. 合理拒答不是失败，错误强迫证据才是评测设计问题。
8. Nightly 的价值在于观察分布、长尾和收敛效率。
9. 真实评测结果必须带数据、模型、断言规则和报告路径。
