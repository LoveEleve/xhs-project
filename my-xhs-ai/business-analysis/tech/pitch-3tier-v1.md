# 项目总述三档讲稿（my-xhs-ai）

> 日期：2026-08-17 | 定位：面试/作品集母稿 | 配套：`retrospective-v1.md`（总复盘）、`jd-hit-matrix-v1.md`（JD 命中）、`docs/reports/eval-gate-report-20260817.md`（评测证据）
> 用法：30 秒版用于开场/电梯；3 分钟版用于自我介绍；10 分钟版用于深聊。三档共用同一套事实，不互相矛盾。

---

## 一、30 秒版

我做的是一个面向电商运营和运维场景的企业级诊断 Agent，核心不是聊天，而是让 Agent 能够基于真实数据完成可追溯调查。系统采用"确定性查询优先、复杂归因进入受限 Agent"的架构，通过 MCP 工具、证据链、存在性校验、HITL 审批和 eval-gate，重点解决三个问题：**不编造、不越权、可评测**。目前已完成会话记忆、工具注册表、审批闭环、多智能体和评测闭环，真库真模型门禁与抽样回归均已跑绿。

---

## 二、3 分钟版

我做这个项目，是因为普通聊天机器人或简单 RAG 很难满足企业场景：它可能回答得很流畅，但不能证明数字来源，也不能安全执行操作，更不能稳定回归。

所以我把系统设计成两条路径：

- "订单量是多少"这类确定性问题，直接走工具；
- "为什么订单量下降了"这类跨指标、跨时间窗口的归因问题，才进入受限 Agent。

Agent 不是直接执行任意代码或 SQL，而是通过 MCP 调用注册工具，访问订单分片、支付、内容事件、Prometheus、日志和 RAG 数据。它每一步都受预算、循环检测、工具权限和结构化输出约束。

项目最核心的设计是三道防线：

1. **不编造**：工具结果进入本轮证据登记簿，最终答案的 `evidenceRefs` 必须命中真实调用记录；数字还要做一致性校验。
2. **不越权**：工具采用 deny-by-default 和参数白名单，执行型 L3 工具必须进入 HITL 审批，审批后才能 resume 执行。
3. **可评测**：通过 eval-gate 评估完成率、幻觉率、证据数量、时延和成本，而不是只看回答是否自然。

在此基础上，我又补齐了会话与摘要记忆、ToolRegistry、多 Agent 分流、HITL 审批和 bad case 回流。最近一次真库真模型验证中，`EvalGateRunTest` 和 `SampledRegressionTest` 均通过；期间还修复了评测器把答案中的 `1) 2) 3)` 误判为业务数字的问题。

所以这个项目的核心价值不是"接入了一个大模型"，而是把大模型约束成一个**能够调查、引用证据、声明不确定性，并在权限边界内运行的诊断系统**。

## 三、10 分钟版

### 1. 项目问题

项目面向电商平台的运营和运维诊断，覆盖订单、支付、内容互动，以及 MQ、HTTP、数据库等场景。

企业场景与普通 Agent Demo 的区别在于：

- 数字必须可追溯；
- 结论必须能够解释；
- 工具调用必须受权限控制；
- 执行中断后需要恢复；
- 模型升级或 prompt 变化后必须可回归；
- 成本和时延必须可观测。

因此，我没有把目标定义成"让模型更会聊天"，而是定义成：**让 Agent 在真实业务边界内完成可验证调查**。

### 2. 核心架构取舍

第一层是 Workflow 和 Agent 分离。

固定指标查询由确定性工具完成，保证结果可重复；复杂归因才进入 Agent。这样既减少模型调用，也避免让模型参与本来不需要推理的问题。

第二层是受限 Harness。

Harness 是一个状态机，不是无限 ReAct 循环。它负责：

- 结构化决策解析；
- 工具调用调度；
- 步骤、Token、成本预算；
- 循环和无进展检测；
- 证据登记；
- 取消、checkpoint 和恢复；
- SSE 事件输出；
- 最终答案校验。

第三层是 ToolRegistry 和 MCP。

工具元数据、参数 schema、权限级别和执行器统一注册，PolicyGuard 根据注册表校验权限，MCP 从同一事实源导出工具目录。这样新增工具不需要在 Harness 里继续堆硬编码分支，也为业务 Agent 和运维 Agent 的工具子集隔离提供基础。

### 3. 如何保证不编造

只靠 prompt 约束不够，所以我做了确定性存在性校验。

每次真实工具调用都会进入本轮 registry。模型最终答案中的证据引用必须命中 registry，否则答案会被拒绝并要求重新生成；如果持续无法提供真实证据，就明确失败或拒答。

数字一致性是第二层检查：答案中的业务数字要能在工具证据中找到对应值。最近评测时发现，模型用"1) 2) 3)"列举原因，评测器却把列表序号当成业务数字，导致幻觉率误报。这个问题通过修正数字提取逻辑并补单测解决了。

这说明评测系统也必须像业务代码一样被测试，不能把评测结果当成绝对真理。

### 4. 如何保证不越权

工具权限采用 deny-by-default：

- L1/L2 工具主要是只读查询；
- 未注册工具不能调用；
- 参数必须经过白名单校验；
- L3 执行工具不能直接执行；
- 必须进入 `WAITING_APPROVAL`；
- 审批通过后从 checkpoint resume；
- 拒绝则终止并留下审计记录。

例如 `dlq.redeliver` 不会因为模型说"请重投"就直接执行，而是先挂起，审批人确认后才恢复执行。

这里的关键不是"让模型识别恶意请求"，而是即使模型被 prompt injection 影响，也无法突破确定性的权限和工具边界。

### 5. 会话、记忆和状态分离

我把 Agent 的状态拆成四类：

- **Run**：一次执行的状态、步骤、证据和终止原因；
- **Conversation**：用户多轮会话和消息关系；
- **RAG**：外部知识库和口径文档；
- **Memory**：长期偏好或历史摘要。

跨轮只注入摘要和历史结论，不直接复用旧工具原文。需要新的业务数字时必须重新查询，避免把过期证据当成当前事实。

### 6. 多智能体为什么没有一开始就做

多智能体不是默认更好。最初先用单 Agent 验证工具、证据和评测基础，之后才做 BUSINESS/OPS/FULL 双 Agent PoC。

分流主要依据问题领域：

- 订单、支付、内容进入业务 Agent；
- MQ、HTTP、日志、数据库排障进入运维 Agent；
- 共享同一个 Harness，但使用不同 prompt、工具集和预算。

最终通过对比评测决定是否全量采用，而不是因为"多 Agent"听起来先进就直接堆复杂度。

### 7. 评测如何闭环

评测包括：

- YAML 用例集；
- 硬断言：状态、证据数量、关键词；
- 数字一致性：检测潜在幻觉；
- 完成率、通过率、幻觉率；
- 时延、Token、成本；
- LLM-as-judge；
- bad case 回流。

最近真实验证中：

- `EvalGateRunTest` 7 条关键用例通过；
- completion rate 为 100%；
- 修复评测器误报后 hallucination rate 为 0；
- `SampledRegressionTest` 通过。

这里的原则是：**Agent 的非确定性不能靠人工感觉管理，必须转化成可重复的质量指标。**

### 8. 关键业务价值

项目不是抽象问答，而是面向具体业务问题：

- 订单下降：浏览、加购、下单、支付和基线窗口联合分析；
- 支付下降：成功率与失败结构结合；
- 内容互动下降：数据不足时明确声明，不编造趋势；
- MQ/HTTP/DB 排障：通过指标、日志和复制延迟逐步缩小范围；
- 高风险操作：进入审批闭环，而不是直接执行。

### 9. 技术取舍

- **Java**：复用现有 Spring Cloud、电商微服务和数据基础设施，降低业务接入成本；
- **自研 Harness**：Java 侧需要精确控制状态、checkpoint、权限和持久化，通用 Agent 框架不能直接替代这些业务约束；
- **单一已验证模型**：当前为 `mimo-v2.5-pro`，通过 eval-gate 关键门禁后作为默认模型；切模型必须重跑评测，避免变量膨胀；
- **薄前端**：前端只消费 API、SSE、证据和审批状态，不承载推理逻辑；
- **不采用 CodeAct**：企业诊断场景优先安全边界和可审计性，不允许模型获得任意代码或 SQL 执行能力。

### 10. 总结句

这个项目不是把大模型接进电商系统，而是围绕企业 Agent 的核心矛盾做了一套工程化约束：

- 需要推理，但不能失控；
- 需要灵活，但不能越权；
- 需要自然语言，但数字必须有证据；
- 需要快速迭代，但质量必须可回归。

最终形成的是一个面向真实业务的、**受限、可审计、可评测、可恢复的诊断 Agent**。
