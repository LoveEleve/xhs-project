# 如何降低 Agent 编造风险：存在性校验、证据链与数字一致性

> 系列：T13 专题长文 | 版本：v1 | 日期：2026-08-18
> 配套：`theory-agent-v1.md`、`theory-enterprise-agent-engineering-v1.md`、`theory-evaluation-v1.md`
> 案例系统：`my-xhs-ai` 电商运营/运维诊断 Agent

---

## 一、问题不是“模型会不会撒谎”

讨论 Agent 幻觉时，很多方案会先想到：

- 写更长的 system prompt；
- 要求模型“不要编造”；
- 在回答末尾加一句“如有不确定请说明”；
- 换一个更强的模型。

这些方法可以改善行为，但都不是确定性安全边界。

企业诊断真正要解决的问题是：

> **模型最终说出的数字和结论，是否能追溯到本轮真实观察到的证据？**

“订单量下降 23%”这句话的问题，不是它听起来像不像人话，而是：

- 这个数字来自哪个工具？
- 工具是否真的被调用？
- 调用时使用了什么时间窗口？
- 工具返回的原始结果是什么？
- 模型是否把另一个窗口的数字拿来回答当前问题？

因此，本项目不把“不编造”定义成 prompt 风格，而是定义成一条**可验证的证据约束**。

## 二、三种“看起来有证据”但其实不可信的回答

### 2.1 模型声称调用过工具，但实际上没有调用

```text
模型：我查询了订单数据库，当前订单量是 12000 单。
```

如果模型没有实际发起工具调用，这个数字就没有来源。

### 2.2 调用了工具，但引用了错误窗口

```text
工具 A：当前窗口订单量 = 5
工具 B：基线窗口订单量 = 6
模型：当前订单量为 6，比基线下降。
```

模型确实调用了工具，但答案引用错了数字。

### 2.3 工具结果真实，但模型推导出无证据数字

```text
工具：成功 4，失败 0
模型：支付稳定性提升了 37%。
```

工具结果可能支持“当前成功率 100%”，但不一定支持“提升 37%”。这类派生数字必须有清晰计算依据，否则仍然是风险信号。

---

## 三、第一道防线：证据存在性校验

### 3.1 每次真实工具调用生成证据

Agent 调用工具后，系统记录：

```text
Tool Call
  tool = order.query_volume
  args = {window: 2026-08-11~2026-08-17}
  result = {value: 5, ...}
  evidenceId = ev_xxx
```

这条记录进入本轮 `ToolResultRegistry` / `EvidenceChain`。

两者职责不同：`ToolResultRegistry` 是运行时证据引用校验的事实源；`EvidenceChain` 是 Run 对外呈现和持久化的证据视图。它们相关，但不是同一个对象。

### 3.2 最终答案必须引用证据

模型输出最终答案时，不只需要 `conclusion`，还需要 `evidenceRefs`：

```json
{
  "action": "ANSWER",
  "conclusion": "当前订单量低于基线",
  "evidenceRefs": ["ev_xxx"],
  "counterEvidence": "支付失败事件为 0",
  "uncertainty": "样本量较小"
}
```

系统执行确定性校验：

```text
for ref in answer.evidenceRefs:
    if ref 不在本轮 ToolResultRegistry:
        拒绝答案 → 要求模型重想
```

### 3.3 为什么这比 prompt 更可靠

Prompt 只能告诉模型“应该引用证据”，但不能阻止它输出一个不存在的 evidenceId。

Registry 校验则直接检查事实：

- 工具是否真的调用过；
- evidenceId 是否属于本轮；
- 答案是否引用了真实记录。

所以它把“请你诚实”变成了“系统不接受无法验证的答案”。

### 3.4 存在性校验能保证什么，不能保证什么

它能保证：

- 引用的 evidenceId 真实存在；
- 证据来自本轮真实工具调用；
- 模型不能凭空伪造调用记录。

它不能单独保证：

- 模型正确理解了证据；
- 引用的证据真的支持结论；
- 自然语言建议没有逻辑错误；
- 工具本身的数据口径一定正确。

所以存在性校验是第一道防线，不是全部答案。

还要区分“调用事实”和“数据口径”：证据链保证调用事实可追踪，不自动保证数据源口径正确。订单查询的 16 节点分片扫描、浏览漏斗读取 `t_product_behavior` 而非聚合表 `t_counter`，都需要工具契约、数据说明和业务校验共同保证。

### 3.5 四层反幻觉模型

1. **能力层**：只提供受控工具，不给任意 SQL、Shell 或代码执行。
2. **事实层**：`evidenceRefs` 必须命中本轮真实调用记录。
3. **表达层**：结构化答案包含结论、证据、反证和不确定性。
4. **评测层**：数字一致性、硬断言、Judge 和人工 bad case 共同发现质量问题。

四层分别限制“能做什么”“依据是什么”“如何表达”和“长期是否退化”，不能用其中一层替代其他层。

## 四、第二道防线：数字一致性

### 4.1 为什么要单独检查数字

企业诊断中，数字是最容易验证、也最容易造成业务伤害的部分。

本项目的统计单位是“评测用例”而不是单个数字：

```text
幻觉嫌疑率 = 存在未匹配数字的评测用例数 / 评测用例总数
```

只有符合评测条件的 `SUCCEEDED` 用例参与数字检查；`DECLINE` 的零证据路径不应被强行纳入数字比对。

可以先把模型答案和工具证据都抽取成数字集合：

```text
答案：订单量从 6 降到 5，降幅约 16.7%
证据：current=5, baseline=6
```

然后检查答案中的数字是否能在证据中找到合理对应。但要区分两个层次：

```text
数字匹配 ≠ 数字归属正确
```

一个数字出现在某条工具结果里，不代表它一定属于当前结论；窗口、字段、计算关系和业务口径仍需要工具契约与语义分析共同确认。

### 4.2 数字一致性不是简单字符串相等

以下表达在语义上可能相同：

```text
工具：0.553 秒
模型：553ms
```

以下表达也可能只是展示差异：

```text
工具：67.0
模型：67
```

因此检查器需要考虑：

- 数值近似；
- 小数和整数；
- 秒与毫秒；
- 百分比；
- 派生值；
- 日期和时间；
- traceId 和证据 ID；
- 列表序号和 Markdown 表格排名。

### 4.3 为什么数字一致性只能是启发式信号

假设工具返回：

```json
{"success": 4, "fail": 0}
```

模型回答：

```text
成功率为 100%，比上周提升 20 个百分点。
```

“100%”可以由证据计算得到，但“提升 20 个百分点”需要基线证据。纯数字匹配无法完整理解这个语义关系。

另一方面，模型可能说：

```text
当前问题较严重，但具体原因还需要更多数据。
```

这句话没有数字，但不代表它一定正确或错误。

因此数字一致性检查应该被定义成：

> **发现明显无证据数字和数量级跳变的启发式质量信号。**

它不能取代业务语义判断，也不能取代 LLM-as-judge 或人工分析。

## 五、评测器本身也会产生幻觉误报

这是本项目最有价值的工程经验之一。

### 5.1 列表序号误报

模型使用：

```text
1) 积压可能是瞬时高水位
2) 采集是五分钟快照
3) 生产消费速率短时失衡
```

如果数字抽取器只看 `\d+`，就会把 1、2、3 当成业务数字。

修复方式：排除：

- `1)`；
- `2）`；
- `3、`；
- `4. `；
- Markdown 表格排名。

### 5.2 时间窗口误报

以下数字通常不是业务指标：

```text
最近 7 天
最长 31 天
2025 年 1 月
```

它们描述的是查询范围或日期上下文，不应该拿去和工具业务结果做一致性匹配。

### 5.3 单位换算误报

```text
工具：0.553s
答案：553ms
```

如果不做单位换算，会把正确答案判成幻觉。

### 5.4 零证据拒答误报

`DECLINE` 是一个合法的零证据路径：

```text
用户要求查询系统不支持的历史数据
→ Agent 明确说明范围限制
→ 不调用无关工具
→ 不伪造证据
```

如果评测器仍然强制对这段文字做数字一致性检查，就会把“2025 年 1 月”“最近 31 天”之类的拒答说明误判成幻觉。

| 场景 | 是否需要工具证据 | 正确行为 |
|---|:--:|---|
| 可查询的业务归因 | 是 | 调工具并引用证据 |
| 超范围问题 | 否 | `DECLINE` + 能力边界 |
| 当前观测否定用户前提 | 通常是 | 调工具后诚实反驳 |
| 高风险操作 | 是 | 证据 + HITL 审批 |

### 5.5 评测器修复的单测原则

每次发现误报，都应该补成稳定单测：

- 正常业务数字保留；
- 日期和时间跳过；
- 百分比按规则处理；
- 序号跳过；
- 单位换算成立；
- 零证据拒答不触发数字检查。

这体现了一个重要原则：

> **评测系统不是上帝视角，它本身也是需要被测试的软件。**

评测器版本变化会影响历史结果的可比性。修改断言器后，必须同时记录：

- 模型版本；
- 评测集版本；
- 断言器/策略版本；
- 工具与数据口径版本。

受影响的集合需要重新跑，不能只修改规则后直接宣布质量提升。

## 六、证据链还需要反证和不确定性

只给支持结论的证据还不够，企业诊断还需要明确：

- 有没有反证；
- 当前结论覆盖什么范围；
- 哪些数据缺失；
- 哪些只是瞬时观测；
- 下一步应该补什么信息。

例如用户问“为什么 MQ 有积压”，工具返回当前 `totalLag=0`，正确回答不是强行解释“积压原因”，而是：

```text
当前没有证据支持存在消费积压。
可能积压已经恢复，或用户观察的是其他时间点。
当前结果是五分钟采集快照，不代表历史累计情况。
```

这不是“模型没回答”，而是 Agent 正确识别了问题前提和当前证据不一致。

---

## 七、从运行时约束到评测门禁

“不编造”需要两层闭环：

### 运行时

```text
工具调用
  → EvidenceChain
  → evidenceRefs 存在性校验
  → 无效答案重想/拒绝
```

### 离线评测

```text
评测用例
  → Agent 执行
  → 硬断言
  → 数字一致性
  → 通过率/完成率/幻觉率
  → bad case 分类
```

运行时解决单次请求能不能接受，离线评测解决系统长期是否退化。

这两个层次不能互相替代：

- 只有运行时校验，没有 nightly，无法发现模型版本变化；
- 只有 nightly，没有运行时校验，线上单次请求仍可能编造。

## 八、真实结果：不是宣传数字，而是条件化证据

本次 `mimo-v2.5-pro` nightly 100 条全量结果：

- 通过率：100%；
- 完成率：96%；
- 幻觉率：0%；
- 平均耗时：23.3 秒/条；
- 平均 Token：10,324/条。

这些数字的正确解释是：

- 当前 100 条用例满足当前断言；
- 少量复杂归因以允许的 `PARTIAL/BUDGET_STEPS` 终止；
- 本轮没有发现未匹配的业务数字；
- 结果依赖当前模型、数据、工具口径和评测规则；
- 不能推导成“生产环境永久 100% 正确”。

这正是工程评测和营销数字的区别：**结果必须携带条件。**

## 九、面试表达模板

如果面试官问“你怎么保证 Agent 不编造”，可以这样回答：

> 我不会只靠 prompt 说“请不要幻觉”。运行时，每次真实工具调用都会登记到 ToolResultRegistry，最终答案的 evidenceRefs 必须命中本轮真实调用，否则拒绝并重想；EvidenceChain 负责对外呈现和持久化；评测层再做数字一致性检查，识别明显的无证据数字和数量级跳变。数字检查只是启发式信号，不替代自然语言语义判断。我们还给评测器本身补了列表序号、日期窗口、单位换算和零证据拒答的边界测试。最终在 MiMo V2.5 Pro 下跑 100 条 nightly，当前断言下通过率 100%、完成率 96%、幻觉率 0%。

---

## 十、本文要点

1. “不编造”不能只靠 prompt，必须有运行时证据约束。
2. EvidenceRefs 存在性校验是事实来源约束，不是语义正确性证明。
3. 数字一致性是启发式幻觉信号，不是完整事实验证。
4. 反证和不确定性是诊断答案的一等字段。
5. 合法拒答不应该被评测器误判成失败。
6. 评测器本身也需要边界测试和版本管理。
7. 运行时约束与离线 nightly 评测缺一不可。
8. 评测数字必须带模型、数据、断言规则和报告路径等条件。
