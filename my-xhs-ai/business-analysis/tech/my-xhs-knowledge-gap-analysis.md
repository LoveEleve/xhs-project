# `my-xhs` 知识层缺口分析（2026-08-20，第一阶段已完成，主路径已接通）

> 目标：明确 `my-xhs-ai` 当前在“理解 `my-xhs` 系统本体”上的结构性缺口，并给出下一阶段建设路线。

---

## 一、问题定义

当前 `my-xhs-ai` 已经比较强的能力是：
- 运行态诊断
- 指标查询
- 日志检索
- DLQ 调查与重投
- Langfuse trace
- HITL 审批
- 向量语义记忆
- Temporal PoC

这些能力足以让它成为一个强的**运行态诊断 Agent**。

但如果问题换成：
- `my-xhs` 的整体架构是什么？
- 订单 / 库存 / 支付主链是怎样协作的？
- 为什么 inventory 比 product 更复杂？
- 为什么要事务消息 + 本地消息表 + 补偿任务？
- `gateway` / `home` / `order` / `inventory` 的职责边界是什么？
- 某个 5xx 最终对应哪段源码 / 哪层架构设计？

那么当前 `my-xhs-ai` 大概率答不好，或者只能答得浅。

这说明：

> 当前项目的主要短板，不在运行态能力，而在**系统知识层**。

---

## 二、最准确的现状判断

### 2.1 当前项目擅长什么
当前 `my-xhs-ai` 真正擅长的是：

- 基于工具的运行态调查
- 基于日志和指标的排障
- 基于审批边界的高危动作执行
- 基于 trace 的过程追踪

也就是说，它更像：

> **运行态诊断 Agent**

### 2.2 当前项目不擅长什么
它当前不一定擅长：

- 讲 `my-xhs` 的全局架构
- 讲主交易链路的设计取舍
- 讲模块边界和同步/异步协作
- 把运行态异常映射回系统设计层
- 做“架构知识问答”而不是“运行态诊断”

也就是说，它还不够像：

> **理解 `my-xhs` 本体的系统知识 Agent**

### 2.3 这不是模型问题，而是知识层问题
根因不在：
- 模型太弱
- trace 不够
- Memory 不够花哨

真正根因在：

> **`my-xhs` 的系统级知识还没有被组织成一层可检索、可解释、可导航的公共知识底座。**

---

## 三、缺口地图：当前答不好的问题有哪些

可以把当前答不好的问题分成 4 类。

## 3.1 全局架构类
典型问题：
- `my-xhs` 的整体架构是什么？
- 哪些服务是核心交易服务，哪些是聚合层？
- 哪些链路是同步 Feign，哪些是异步 RocketMQ？
- `gateway`、`home`、`order`、`inventory` 各自边界是什么？

### 当前为什么答不好
因为这些问题依赖：
- 系统总图
- 服务分组
- 主链路解释
- 架构边界文档

而当前 Agent 的主路径主要依赖：
- 指标工具
- 运行态日志
- DLQ / MySQL / Prometheus

也就是说，它能看“现象”，但不一定理解“全景结构”。

## 3.2 主交易链设计类
典型问题：
- 为什么订单服务是编排中心？
- 为什么库存要三级扣减？
- 为什么事务消息是交易主链的核心绑定器？
- 为什么需要本地消息表和补偿任务？

### 当前为什么答不好
因为这些问题本质是：
- 设计取舍问题
- 分布式一致性问题
- 失败方案为什么不行的问题

而不是单纯的数据查询问题。

换句话说，当前 Agent 擅长回答：
- “订单量是多少”

但不一定能稳稳回答：
- “为什么这里不能只靠普通消息 / 同步调用来保证一致性？”

## 3.3 模块职责与代码边界类
典型问题：
- `OrderTransactionConsumer` 属于哪一层能力？
- `CouponFeignClient` 为什么是补偿链上的高风险点？
- 某个 5xx 到底对应 Controller / Service / Feign / MQ 哪一层？

### 当前为什么答不好
因为这类问题需要：
- 对源码结构有导航能力
- 对服务职责有抽象理解
- 对调用链有分层解释能力

当前系统还没有把：
- Controller
- Service
- Feign client
- MQ producer/consumer
- 状态枚举
- 配置边界

抽成一层系统性的源码知识地图。

## 3.4 故障经验与系统经验类
典型问题：
- 这个问题以前出现过吗？
- 这是配置问题、运行态问题，还是设计问题？
- 历史修复经验是什么？

### 当前为什么答不好
因为这些信息虽然存在于：
- handoff
- review
- failure docs
- 测试记录

但还没有形成：
- 可复用的 failure knowledge
- 面向 Agent 的问题-根因-修复结构

## 五、为什么现有资料还不能直接喂给 Agent

## 5.1 文档粒度太粗
比如 `vol-xhs` 的文章是给人读的：
- 长文
- 叙事化
- 包含很多铺垫和失败方案推演

这对人很好，但直接喂给 Agent 会有问题：
- 检索粒度太粗
- 容易命中过大上下文
- 很难稳定回答单点问题

## 5.2 知识类型混在一起
现在同一批文档里混着：
- 架构知识
- 业务规则
- 故障复盘
- 测试执行过程
- handoff 细节

如果不先分层，Agent 很容易：
- 用测试记录回答架构问题
- 用故障复盘回答业务规则
- 用临时 handoff 口径当成稳定系统设计

## 5.3 缺少“源码导航层”
现在文档很强，但源码知识还没抽象成可导航层。

所以一旦问题需要：
- 架构 → 源码
- 现象 → 调用链
- 设计 → 类/方法

Agent 仍然会缺一层桥。

## 5.4 缺少专门的“系统知识问答路径”
当前主路径更偏：
- 查数
- 查日志
- 查 DLQ
- 跑审批

它没有一条明确路径专门处理：
- 架构讲解
- 主链路解释
- 模块职责说明
- 设计取舍问答

所以不是“知识不存在”，而是：
> **这些知识还没有被组织成一条可稳定服务 Agent 的系统知识路径。**

## 六、下一阶段应该怎么建设

这里不是一句“做 RAG”就够了。

应该分 4 步走。

## Phase 1：知识缺口清单化
目标：
- 把当前答不好的问题按类型列完整
- 先定义问题，再做知识层

产物：
- 本文档（第一版）

## Phase 2：文档知识分层
把 `my-xhs` 文档拆成三类知识卡：

### A. Architecture cards
回答：
- 服务拓扑
- 边界
- 同步/异步链路
- 核心状态流转

### B. Business cards
回答：
- 订单规则
- 库存规则
- 支付规则
- 优惠券规则
- 指标口径

### C. Failure cards
回答：
- 症状
- 真实根因
- 修复经验
- 恢复建议

## Phase 3：源码结构层
把源码抽成导航层，而不是全文索引：
- service map
- call-chain map
- mq map
- feign map
- state map

## Phase 4：系统知识问答路径
在 Agent 里新增一种明确路由：
- 架构问答
- 业务规则问答
- 设计取舍问答
- 源码结构问答

而不是把所有问题都塞到运行态调查路径里。

---

## 七、如果补完之后，项目会怎么变

补完这层之后，`my-xhs-ai` 会从：

> 运行态诊断 Agent

升级成：

> 系统知识 + 运行诊断一体化 Agent

这会是非常大的提升。

因为它不仅能回答：
- 现在出什么问题了

还会回答：
- 这个系统为什么会这样设计
- 这个异常在系统主链里意味着什么
- 哪层边界在这里断了

这才是真正“懂系统”的 Agent。

---

## 八、最重要的结论

当前 `my-xhs-ai` 最大的结构性缺口之一，不是模型、不是真 trace、不是真审批，而是：

> **还没有把 `my-xhs` 那一侧的文档知识和源码结构，系统性沉淀成一个可检索、可解释、可导航的知识层。**

这件事如果不补，系统会一直停在：
- 会查运行态
- 但不一定会讲系统本体

而一旦补上，它的层次会明显再上一个台阶。
