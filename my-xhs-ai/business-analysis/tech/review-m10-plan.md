# 深度 Review：M10 设计 + 规划 + 五项目借鉴（写码前审查）

> 日期：2026-08-15 | 对象：design-m10-conversation.md / roadmap-m10-m14.md / deep-plan-v2.md / five-agents-insights.md
> 视角：批判性——**场景适配优先**（我们是诊断 Agent：短会话/读为主/实时反馈；五项目是 coding Agent：长会话/写为主/异步）
> 结论：**2 个 P0 设计缺陷、1 个顺序错误、1 个借鉴克制原则、若干补强**——全部修订后动工

## P0-1：跨轮证据引用与存在性校验冲突（M10 设计的真实缺陷）

**问题链**：
1. `ToolResultRegistry` 是 **AgentRun 级的**（run 结束即丢，registry 在 AgentRun 内）
2. M10 设计"注入历史消息（含上轮 tool result 文本）"——模型可见上轮工具结果
3. 模型引用上轮证据（"如前所述 ev_xxx"）→ 本轮 `validateAnswer` 在**本轮 registry** 查 ev_xxx → 不存在 → **拒绝重想** → 反复失败甚至 EVIDENCE_INVALID
4. 设计里"上轮结论引用不强制校验（文档说明）"——这是**把缺陷丢给模型自觉**，违背项目红线（不靠模型自觉）

**根因**：把"展示用的历史消息"和"校验用的 registry"混在一起注入，没区分"上下文可见"与"证据可校验"。

**修复决策（3 选 1）**：
| 方案 | 做法 | 代价 |
|------|------|------|
| A. 历史注入只带结论不带工具结果 | 注入 user/assistant 消息（finalAnswer），**过滤** tool result 文本；模型无法引用上轮 ev_xxx（看不到）| 丢失上轮调查细节，Q3 要重查 |
| B. 跨轮 registry 合并 | 会话级 registry：上轮 evidenceId 注册到会话 store，本轮校验可查 | 会话级状态引入；证据可能过期（数据已变）|
| C. 历史注入带工具结果 + 校验豁免声明 | 明确"历史中的 ev_xxx 不可引用"写进 prompt | 模型可能仍犯错（不可靠）|

**推荐 A**（V1）：历史注入 = user/assistant 消息（结论+证据 ID 列表，无工具原文）；模型想引用上轮证据时**重新调用工具**（正确语义：数据可能已变化）。成本低、语义正确、保持校验严格。**反证**：诊断场景数据随时间变化，跨轮引用旧证据本来就是错的——A 反而是对的语义。

## P0-2：checkpoint 快照与会话消息的职责冲突（双写不一致风险）

**问题**：`ai_step.messages_snapshot`（崩溃恢复用，每步全量快照）vs 新增 `ai_message`（会话注入/展示用）——同一份对话两份存储，**谁为准**？

**修复决策**：
- **checkpoint 快照 = 恢复专用**（内部一致性，含系统提示/工具结果，不对外）
- **ai_message = 会话专用**（user/assistant 结论 + 证据引用，供注入/展示/追溯）
- 职责分离 + 单向流：run 终态 → 写 ai_message；checkpoint 不反向读会话表
- 明确**不合并**：checkpoint 是执行态，会话是交互态（四态分离原则的落地）

## P0-3（顺序错误）：M12 工具注册表应在 M11 之前

**问题**：M11 HITL 需要"工具权限级（L1/L2/L3）+ 审批挂点（pre-execute 缝）"——权限元数据是**注册表的职责**。现在顺序 M11→M12 是"先建权限再建载体"，本末倒置。

**修订**：**M10 → M12（注册表，含 accessLevel 元数据）→ M11（HITL，挂注册表）→ M13 → M14**
（或 M12 拆两半：schema 注册先行，权限策略随 M11）

## P0-4（前置债）：eval-gate 未跑绿就开工 M10

**问题**：所有里程碑验收都靠评测，而 eval-gate 上次 7/7 失败从未追查——评测地基是塌的。

**修订**：**M10 动工前置 = eval-gate 跑绿**（修 7 个失败用例，门槛真实通过）；M10 的多轮用例加进评测集。

## 场景适配：借鉴克制原则（防膨胀）

五项目是 coding agent（100+ 轮会话/写为主），我们是诊断 agent（2-5 轮/读为主/实时）。逐条适配：

| 借鉴模式 | coding 场景动机 | 诊断场景 | 结论 |
|---------|--------------|---------|:--:|
| 收件箱双游标（admitted/promoted）| 用户边跑边输入，防并发覆盖 | 用户提问→等待→回答，无并发输入 | **V1 不做**（等真实需求）|
| 三段式压缩状态机（防 thrash/提交栅栏）| 100+ 轮上下文管理 | 会话 2-5 轮，消息上限 20 轮截断即可 | **简化**：上限截断 + 规则摘要 |
| Context Epoch 不可变基线 | 保 prompt cache（长会话高频）| 系统提示稳定，本轮即可固化 | **采纳**（低成本）|
| TaskSpec×evidence_ids | 无人值守任务验收 | **与我们证据链天然契合** | **采纳**（M14 强化）|
| 五事件工具管线 | 复杂工具副作用管理 | dlq.redeliver 等执行工具需要 | **采纳**（M11 简化版：pre-execute 门）|
| Capability Seams 三角色 | 多产品可替换 | 工具注册表理念 | **采纳**（M12）|
| 审查 fork 多 Agent | coding 质量 | 诊断结论复核有价值 | **采纳**（M13 PoC 起点）|
| 权限继承/防递归 | 子 agent 嵌套 | 同 | **采纳**（M13）|
| profile-bundle 版本化 | 插件生态 | 诊断模板/话术分层 | **暂缓**（V1 常量够，膨胀后再说）|

**原则**：只加"诊断场景可验证收益"的复杂度；coding agent 的工程是为长会话/并发/写操作服务的，诊断场景直接照搬就是过度设计（Anthropic Simplicity 原则的落实）。

## M10 设计补强清单（修订后）

1. **历史注入**：user/assistant 结论消息（P0-1 方案 A）——不含工具原文，含证据 ID 列表（展示用途）
2. **消息上限**：20 轮截断 + 规则摘要（不引入压缩状态机）
3. **职责分离**：ai_message 会话专用，checkpoint 恢复专用（P0-2）
4. **并发限制**：同会话同一时间仅一个活跃 run（V1 串行，409 语义复用）
5. **验收用例补**：多轮归因（Q2 引用 Q1 结论且**重新调用工具**而非引用旧 ev）——防模型"抄上轮答案不验证"
6. **前置**：eval-gate 跑绿

---

## 结论

- **M10 有 2 个 P0 设计缺陷**（跨轮证据校验冲突、双写职责）——好在写码前发现
- **顺序修正**：M12 提前到 M11 前；eval-gate 跑绿为 M10 前置
- **借鉴克制**：诊断场景适配后保留 7 条、简化 2 条、暂缓 2 条（收件箱双游标/压缩状态机 V1 不做）
- 修订后 M10 设计可开工（见 design-m10 修订版）
