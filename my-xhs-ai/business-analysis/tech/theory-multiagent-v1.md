# 多智能体一定更好吗：M13 双 Agent PoC 与评测复盘

> 系列：T13 专题长文 | 版本：v1 | 日期：2026-08-18
> 配套：`theory-agent-v1.md`、`theory-enterprise-agent-engineering-v1.md`、`theory-evaluation-v1.md`
> 案例系统：`my-xhs-ai` 电商运营/运维诊断 Agent

---

## 一、先给结论

**多智能体不是 Agent 系统的默认升级路径。**

它只有在以下问题确实存在时才值得引入：

- 单个 Agent 的工具空间过大；
- 不同领域需要明显不同的提示词和策略；
- 任务可以自然拆成相对独立的角色；
- 分工带来的质量提升超过了通信和编排成本。

`my-xhs-ai` 的 M13 采用了一个克制的决策流程：

```text
单 Agent 打基础
  → 双 Agent 分流 PoC
  → 同一评测集对比
  → 数据决定是否默认启用
```

最终结果支持当前默认启用领域分流，但这个结论来自评测数据，不来自“多 Agent 听起来更先进”。

---

## 二、单 Agent 的问题是什么

单 Agent 的优势很明显：

- 架构简单；
- 上下文只有一份；
- 工具调用路径容易追踪；
- 成本和时延变量少；
- 评测更容易解释。

但随着工具增加，单 Agent 会遇到几个问题。

### 2.1 工具空间变大

业务诊断可能需要：

- 订单；
- 支付；
- 内容；
- 漏斗；
- 基线；
- RAG。

运维排障又需要：

- HTTP 错误；
- HTTP 延迟；
- MQ lag；
- DLQ backlog；
- MySQL 复制延迟；
- MySQL deadlock；
- 日志检索。

全部工具放进一个 Agent，会增加：

- 工具选择困难；
- Prompt 变长；
- 错误调用机会；
- 评测分支；
- 权限治理复杂度。

### 2.2 领域策略不同

“为什么订单量下降”与“为什么 MQ 有积压”虽然都需要多步调查，但推理方式不同：

- 业务 Agent 关注漏斗、窗口、转化和经营结论；
- 运维 Agent 关注服务、指标、日志、错误率和故障边界。

如果所有问题使用一份 Prompt，领域规则容易互相干扰。

### 2.3 工具权限边界不同

业务 Agent 通常需要订单/支付/内容工具；运维 Agent 需要观测和日志工具。按领域缩小工具子集，可以减少误用和越权机会。

---

## 三、多智能体增加了什么成本

多 Agent 不是免费抽象，它会增加新的系统问题。

### 3.1 分派错误

如果问题被分派到错误 Agent，后续所有工具和 Prompt 都可能不合适。

### 3.2 上下文传递

如果未来演进到 Agent A 执行一半、再把任务交给 Agent B 的串联式协作，就需要明确传递：

- 用户问题；
- 已有证据；
- 当前窗口；
- 中间结论；
- 失败原因；
- 权限上下文。

如果上下文传递不完整，协作反而会比单 Agent 更差。当前项目暂未实现这种 Agent-to-Agent handoff，而是先分派 profile 后由共享 Harness 独立执行。

### 3.3 评测复杂度增加

需要分别验证：

- 分派是否正确；
- 每个 Agent 是否使用正确工具；
- Agent 间上下文是否丢失；
- 最终答案是否仍引用真实证据；
- 总成本和时延是否上升。

### 3.4 观测和恢复复杂度增加

单 Agent 只需要追踪一个 Harness；多 Agent 还要追踪：

- dispatcher；
- profile；
- 子 Agent；
- 跨 Agent 证据；
- 失败重试；
- resume 时的原始画像。

因此，多 Agent 的收益必须通过对比评测证明。

---

## 四、M13 的设计：共享引擎，隔离画像

`my-xhs-ai` 没有为每个 Agent 复制一套执行引擎，而是采用分派式画像：

```text
AgentDispatcher
  ├── BUSINESS profile  ← 业务分工 Agent
  └── OPS profile       ← 运维分工 Agent
        ↓
共享 AgentHarness

FULL profile：全量工具视图，主要用于基线/回退，不属于 Agent 间协作角色。
```

当前实现是**分派式多 Agent**：一个问题先选择 profile，再由该 profile 独立完成一次 Run；不是 Agent A 执行一半后把上下文接力给 Agent B 的串联式协作。

每个 profile 主要定义：

- Prompt 领域变体；
- 工具子集；
- 预算参数；
- 领域描述；
- 分派规则。

共享 Harness 保留统一的：

- 结构化决策格式；
- 证据存在性校验；
- PolicyGuard；
- checkpoint/resume；
- HITL；
- 终止原因；
- 评测格式。

这样做的好处是：

- 领域知识可以隔离；
- 核心安全机制不复制；
- 工具证据格式统一；
- 单 Agent 与多 Agent 的结果可比较；
- 新增 profile 不需要复制状态机。

---

## 五、如何决定是否默认启用

### 5.1 必须使用同一评测集

如果单 Agent 和多 Agent 使用不同问题集，结果无法比较。

对比时至少固定：

- query；
- 数据窗口；
- 工具版本；
- 模型；
- 评测断言；
- 预算范围；
- 结果统计口径。

### 5.2 不能只看通过率

多 Agent 可能通过率提升，但成本翻倍、时延变长、分派错误增加。因此至少比较：

| 指标 | 作用 |
|---|---|
| 通过率 | 质量结果 |
| 完成率 | 是否收束 |
| 幻觉率 | 证据/数字风险 |
| 工具误用率 | 路径质量 |
| 平均步骤 | 编排复杂度 |
| Token | 成本代理 |
| 时延 | 用户体验 |
| 分派准确率 | 多 Agent 理想指标；当前未单独产出报表，主要通过最终结果间接验证 |

### 5.3 M13 的真实结果

M13 在同一组 7 条锚点评测上比较单 Agent 与双 Agent：

| 方案 | 通过率 | 幻觉率 |
|---|:--:|:--:|
| 单 Agent | 85.7% | 14.3% |
| 双 Agent | 100% | 0% |

这次结果支持在当前项目中把领域分流作为当前默认方案，但它证明的是“当前 PoC 成立”，不是“多 Agent 在所有任务上都更优”。结论必须限定为：

- 当前评测集；
- 当前模型；
- 当前工具描述和数据口径；
- 当前 profile 分派规则。

它不能推出“多 Agent 永远优于单 Agent”。

## 六、为什么不是 Agent 之间自由聊天

“多 Agent”不等于让多个模型互相聊天。

自由聊天会增加：

- 无法预测的通信轮数；
- 上下文膨胀；
- 证据来源混乱；
- 成本和时延；
- 责任边界模糊。

`my-xhs-ai` 的选择是**领域分派**，不是开放式群聊：

```text
用户问题
  → AgentDispatcher
  → 选择 profile
  → 共享 Harness 执行
  → 统一证据/权限/评测
```

当前并不需要 Agent A 和 Agent B 自由协商。自由聊天式协作不只会增加成本和上下文，还会让责任归属变模糊：哪个 Agent 对错误结论负责、哪条证据是谁引入的、哪个步骤越权，都更难追踪。

问题领域可以由规则和少量语义信号稳定识别时，显式分派更简单、更可审计。当前也不需要 A2A：多个 profile 在同一应用内共享 Harness，没有跨进程/跨系统 Agent 通信；如果未来改成串联式或跨系统协商，再评估 A2A。

---

## 七、多 Agent 的安全边界

多 Agent 不能因为“内部协作”就绕过现有安全机制。

每个 profile 仍必须经过：

- 工具注册表；
- 工具子集过滤；
- access level；
- 参数白名单；
- HITL 审批；
- 证据登记；
- 统一终止状态。

尤其要避免：

```text
业务 Agent 无权限
  → 请求运维 Agent 代为执行
  → 绕过原本的权限边界
```

正确做法是：权限跟随用户、Run 和工具调用上下文，而不是只跟随某个 Agent 名称。

### 7.1 M13 暴露过的真实失败类型

多 Agent PoC 并不是一次写完就稳定。review 曾发现：

- 纯 traceId 信号被错误分派到 BUSINESS，破坏日志排障闭环；
- resume 路径丢失原始 profile，恢复后可能使用错误工具集。

这些问题分别通过分派规则修正和恢复时保留画像修复。它们说明：多 Agent 新增的不只是分工收益，还新增了**分派信号和恢复上下文**两类状态。

出处：`review-m13-impl.md`。

## 八、什么时候应该从单 Agent 升级

可以把以下信号作为升级门槛：

| 信号 | 建议 |
|---|---|
| 单 Agent 工具空间过大且误用明显 | 考虑多 Agent |
| 业务/运维推理模式明显分离 | 考虑领域分派 |
| 单 Agent 评测已出现稳定性瓶颈 | 先做对比 PoC |
| 只是为了显得先进 | 不做 |
| 评测集不稳定 | 先补评测 |
| 工具/数据口径还没清楚 | 先修工具和数据 |

## 九、什么时候不应该做多 Agent

以下情况优先保持单 Agent：

1. 工具数量少；
2. 领域边界不清；
3. 任务路径短；
4. 单 Agent 质量已经足够；
5. 团队还没有稳定评测集；
6. 多 Agent 只能增加通信，没有明确质量收益；
7. 需要先解决数据和工具口径问题。

多 Agent 不应成为“功能数量”的 KPI。

## 十、面试表达模板

如果面试官问“为什么做多 Agent”，可以这样回答：

> 我没有把多 Agent 当成默认升级，而是先用单 Agent 把工具、证据、权限和评测地基做稳。随着业务诊断和运维排障的工具空间变大，我做了 BUSINESS/OPS 双 Agent 分流 PoC，共享同一个 Harness，只隔离 Prompt、工具子集和预算。用同一组 7 条锚点评测对比后，单 Agent 通过率 85.7%、幻觉率 14.3%，双 Agent 通过率 100%、幻觉率 0%，所以当前选择领域分流。但这个结论限定在当前数据和评测集，未来如果工具规模、通信和恢复复杂度继续增加，还要重新评估多 Agent 的成本收益。

---

## 十一、本文要点

1. 多 Agent 是复杂度选择，不是默认升级。
2. 引入多 Agent 的前提是存在清晰领域边界和可测质量收益。
3. 共享 Harness、隔离 profile 比复制多套执行引擎更稳。
4. 多 Agent 对比必须使用同一评测集和同一统计口径。
5. 通过率提升不够，还要看成本、时延、分派和上下文损失。
6. 领域分派不等于 Agent 自由群聊。
7. 权限和证据边界必须跨 Agent 保持一致。
8. 单 Agent 仍然是很多场景下更简单、更可靠的选择。
