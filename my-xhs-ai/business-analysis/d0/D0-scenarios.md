## 能力面 A —— 业务诊断

### A1. 订单量下降归因（漏斗断点定位）
- **问题**：某时段订单量明显下降，Agent 需定位漏斗断点并给出最可能原因。
- **漏斗定义（⚠️ 领域错配修正）**：电商漏斗应为 **商品浏览(sku) → 加购 → 下单 → 支付**。
  - **`t_user_behavior` 的"浏览"是 note_id 维度的笔记浏览（内容域），不能用于电商漏斗**——内容浏览与电商交易是两条不同用户旅程。
  - 真正缺的是 **sku 维度的"商品浏览"事件**（现状无此事件）。
  - **加购缺事件时间序列**：`t_cart_item` 只有当前状态（updated_at 为最后变更），无法还原历史时段加购量，需"加购事件流"。
  - 下单 = `t_order`(created_at)、支付 = `t_payment` 可直接聚合。
- **数据依赖**：商品浏览事件(sku，需补) + 加购事件流(需补) + t_order + t_payment。
- **就绪度**：❌ 需补——缺商品浏览事件 + 缺加购事件流（审计 A5 修正）。
- **验收标准**：
  - [ ] 能定位下降发生在漏斗哪一环（或明确"无商品浏览/加购事件无法定位断点"）
  - [ ] 关键数字（下单量/支付量/各环节量）与确定性工具逐字段一致
  - [ ] 结论带证据链 + 来源引用 + 不确定性声明

### A2. 支付成功率下降归因
- **问题**：支付成功率下降，Agent 需归因（哪个渠道/阶段/失败原因）。
- **数据依赖**：t_payment + 支付渠道。
- **就绪度**：❌ 缺失败码——Payment 仅 status+payType，**无 failCode/failStage/channelResp**（审计 A1）。
  - ⚠️ **口径默认（[待确认] 指标字典定）**：支付成功率 = **成功数 / (成功数 + 失败数)**（分母排除 0 待支付、3 退款——待支付是未完成的尝试、退款是售后非支付失败）。
  - ⚠️ **渠道为 Mock**（payType 1-支付宝/2-微信，`sql/mysql-order-init.sql:24`）——"渠道归因"是模拟渠道，非真实三方，文档/答案须注明。
- **验收标准**：
  - [ ] 能归因到渠道/阶段/失败原因（或明确"无失败码无法归因"）
  - [ ] 支付成功率按**已定义口径**计算，且与工具结果一致
  - [ ] 不把渠道差异当根因（区分相关与因果）

### A3. 内容互动骤降归因
- **问题**：内容互动（赞/藏/评/分享）骤降，Agent 需区分"内容质量变差" vs "分发/曝光减少"。
- **数据依赖**：**互动时间序列来源 = `t_user_behavior` 逐事件（赞/藏/评/分享 + created_at）**，而非 `t_counter`。
  - ✅ `t_user_behavior` **行为链路已修复（P1，2026-08-13）**：表迁至 content 库（7 值枚举注释）、上报端点 `/api/recommend/behavior`、运行态验证落库成功 → **互动事件可用**（原 ⚠️ 转 ✅）。
  - ⚠️ `t_counter` 是**时点聚合值**（`sql/mysql-content-init.sql:67`，原地更新、无历史时间序列），不能用于"骤降"趋势——须用行为事件算每日新增互动。
  - ⚠️ 曝光/Feed 分发数据**缺失**（审计 A6，关注流曝光需自建；推荐流可复用 behavior_type=1），区分质量 vs 分发仍受限。
  - ⚠️ 缺 `published_at/audited_at`（审计 A2），发布/审核时点分析受限。
- **就绪度**：🟡 互动事件 ✅（已修复）；曝光（关注流）+ published_at 仍缺。
- **验收标准**：
  - [ ] 基于行为事件给出互动时间序列，判断骤降时段（非 t_counter 时点值）
  - [ ] 能给出"质量端 vs 分发端"判断方向（或明确"缺关注流曝光数据无法区分"）
  - [ ] 互动数字与工具一致，带证据链 + 不确定性声明

## 能力面 B —— 技术排障

### B1. MySQL 死锁 / 慢查询根因（trace + 指标交叉）
- **问题**：MySQL 死锁 / 慢查询，Agent 需用 trace + 指标交叉归因根因。
- **数据依赖**：error log / slow_query + SkyWalking。
- **就绪度**：⚠️ 需补管道——**无 mysql-exporter**（B1）+ **无 slow_query_log 管道**（B2）。
- **验收标准**：
  - [ ] 能交叉 trace + 指标给出根因（或明确"数据未采集无法归因"）
  - [ ] 慢查询/死锁证据来自确定性工具
  - [ ] 不把现象当根因（区分相关与因果）

### B2. RocketMQ 消费积压 / 死信归因
- **问题**：MQ 消费积压 / 死信，Agent 需归因。
- **数据依赖**：consumer offset / DLQ / outbox。
- **就绪度**：✅ 已有；DLQ 有基类但**无实际消费者**（B4，排查重投需补）。
- **验收标准**：
  - [ ] 能归因积压/死信原因（消费者卡住/消息格式/业务异常等）
  - [ ] 积压量/offset 来自确定性工具
  - [ ] 死信重投属 L3，一律人工审批（HITL）

### B3. 服务 5xx / 慢端点归因（跨服务链路）
- **问题**：服务 5xx / 慢端点，Agent 需跨服务链路归因。
- **数据依赖**：Prometheus + SkyWalking trace。
- **就绪度**：✅ 已有。
- **验收标准**：
  - [ ] 能跨服务定位根因服务/环节
  - [ ] 5xx 率/延迟来自确定性工具 + trace 交叉
  - [ ] 结论带证据链 + 不确定性声明

### B4. MySQL 主从复制延迟归因（新增）
- **问题**：主从复制延迟高 / 读到旧数据，Agent 需归因（大事务/从库慢查询/网络/relay log）。
- **数据依赖**：`SHOW SLAVE STATUS`（Seconds_Behind_Master / Io_Running / Sql_Running）+ slow_query + 大事务。
- **就绪度**：❌ 需补 **B6 复制延迟指标**（mysql-exporter）+ **B2 慢查询管道**（见 `D0-distributed-diagnosis.md`）。
- **验收标准**：
  - [ ] 能报出复制延迟量（Seconds_Behind_Master）并归因方向（或明确"未采集无法归因"）
  - [ ] 延迟数字来自确定性工具（非模型编造）
  - [ ] 区分复制延迟与真实数据不一致（相关 vs 因果），带证据链
