# 12. 计数域（my-xhs-counter）业务逻辑

> 端口 19004 | 3 端点 | Redis 缓冲 + 批量落库 + 对账

## 一、业务定位
**全平台计数的权威读取层**：点赞/收藏/评论/分享/浏览/粉丝/关注等计数的实时读写与对账。支撑内容展示的互动数字。

## 二、核心业务逻辑
1. **写入路径**：CounterEventConsumer 消费 10 类事件 → Redis INCR 实时 → Set 24h 去重 → Buffer 攒批百条 → batchUpdate MySQL t_counter。
2. **查询路径（CacheAside）**：Redis GET → 未命中查 MySQL 回填。
3. **对账路径**：游标扫描 t_counter → 对比 Redis → 不一致以 MySQL 为准修正 Redis。
4. **计数类型**：1点赞/2收藏/3评论/4分享/5浏览/6粉丝/7关注；targetType 1笔记/2用户。

## 三、异常路径
- Redis 与 MySQL 计数漂移 → 对账修正（以 MySQL 为准）。
- Buffer 批量写失败 → 计数丢失风险（需去重 + 重试）。
- MQ 消费者失败 → removeMark 后重试，防重试窗口归零。

## 四、对 AI 项目（指标/诊断）的价值
| 指标 | 来源 | 就绪度 |
|------|------|:---:|
| 互动计数（赞/藏/评/分享/浏览） | t_counter | ✅ |
| 计数漂移/对账差异 | 对账 | ⚠️ 需观测 |
| 粉丝/关注数 | t_counter(6/7) | ⚠️ 净增长需事件流水 |

> **全平台互动指标的聚合源**，是"互动率/内容热度/粉丝增长"等业务指标的关键数据底座，数据就绪度好。内容支柱诊断离不开它。
