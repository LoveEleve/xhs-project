# 06. 订单与支付域（my-xhs-order + my-xhs-payment）业务逻辑

> order 19005/19011 | payment 19009 | 19 端点 | 分库分表 + 事务消息 + EventSourcing + 双通道支付 | **全链路最复杂**

## 一、业务定位
**电商交易闭环的核心**：订单创建（全链路最复杂）、支付、退款、超时关单，贯穿商品/库存/优惠券/支付多个服务，是 GMV 的载体。

## 二、订单状态机
```
0待付款 ──支付──→ 1已付款 ──发货──→ 2已发货 ──确认──→ 3已完成
   │取消               │退款
   ↘                   ↘
  4已取消             5已退款
```

## 三、关键业务逻辑 / 不变量
1. **创建订单（事务消息）**：幂等锁(SETNX) → 取SKU/库存/算券 → 本地事务(INSERT order+item+local_message) → 半消息 → 库存预扣 Consumer；回查机制兜底。
2. **分库分表**：`user_id % 4` 分库 + `(user_id/4)%4` 分表；`t_order_no_mapping` 全局表做订单号反查路由。
3. **库存联动**：创建预扣(pseudoOrderId) → 支付成功确认 → 取消/关单释放；pseudoOrderId 幂等防重复扣减。
4. **支付双通道**：Mock(90%成功/10%失败) 或 Remote(Feign→PaymentService→回调)。
5. **补偿与对账**：本地消息表 CompensationJob 补发；延时关单 ORDER_CLOSE_TOPIC；对账游标扫描。
6. **EventSourcing**：每次状态流转 INSERT t_order_event（from→to），可回溯。

## 四、异常路径（重要）
- 支付失败(10%/真实) → onPaymentFailed 自动取消 + 释放库存 + 退券。
- 超时未支付 → 延时关单 → 同上。
- 并发支付/取消 → 乐观锁保证单方向成功。
- 退款：remote 双通道回调；refund-fail 需补偿。

## 五、⚠️ 数据缺口（已核实）
| 缺口 | 现状 | 影响 |
|------|------|------|
| **支付失败原因** | `Payment` 仅 status，无 failCode/failStage/渠道摘要 | 「为什么支付失败」答不出原因，只能答状态/渠道 |
| 退款商品级明细 | t_refund 有 reason，无商品明细 | 商品退款率算不准 |
| 漏斗归因 | 需浏览→加购→下单→支付链路 | 需关联 user_behavior + cart |

## 六、对 AI 项目（指标/诊断）的价值
| 指标 | 来源 | 就绪度 |
|------|------|:---:|
| 订单量/状态分布/客单价 | t_order | ⚠️ 分片需汇总投影 |
| 支付成功率/渠道分布 | t_payment | ✅（原因字段缺失） |
| 超时关闭数/退款率 | t_order | ✅ |
| 死信/本地消息表积压 | t_local_message | ✅ |

> **PLAN 三个 V1 场景的所在地**，工程复杂度最高、业务价值也高，但**数据缺口最严重**——不先补支付失败码，场景 B 无法回答"为什么"。
