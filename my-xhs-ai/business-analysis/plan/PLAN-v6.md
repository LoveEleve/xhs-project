## 1. 定位与目标

### 1.1 产品定位
交付一个与 my-xhs **真实业务与基础设施深度结合**的 **运营 + 运维智能助手**：

> 面向运营与技术支持，对**业务异常**（订单/支付/库存/内容/增长/搜索）进行受限、可恢复、可审计的多步调查；同时能对**技术排障**（死锁/慢查询/MQ积压/5xx/链路）给出证据链归因；全程不越权、不泄漏、可追溯。

它不是万能聊天机器人，也不是让 LLM 直连数据库的 NL-BI。

### 1.2 三大能力面（本版核心）
```
能力面A 业务诊断    —— 回答"业务为什么异常"（内容/交易/增长/搜索）
能力面B 技术排障    —— 回答"系统为什么异常"（死锁/慢查询/积压/5xx/链路）
能力面C AI 安全    —— 全程横切的护栏（注入/越权/PII/供应链/幻觉）
```

### 1.3 服务对象（第一用户）
| 用户 | 主要能力面 | 支撑的决策 |
|------|-----------|-----------|
| 运营/数据分析 | A（为主）+ C | 内容/交易/增长运营决策 |
| 技术支持/SRE | B（为主）+ C | 排障、恢复、容量 |

### 1.4 V1 范围声明（防范围膨胀）
- **主线 = 能力面 A（业务诊断）+ 能力面 B（O&M 排障）**。
- **能力面 C（AI 安全）是全程横切护栏**，不单列为独立里程碑/独立交付面——安全能力随 A/B 的每个阶段落地并深化（D0 基线 → D6 攻防深化），但**不额外加周期**。
- 若 A/B 任一能力面在某阶段评估为风险过高或价值不明，允许**先做精简版**（如只做 B1/B2 排障、A1 单场景）并明确降级，不牺牲质量门禁。

### 1.4 成功标准（证据导向，不数概念）
- ≥3 个真实业务诊断场景 + ≥3 个真实技术排障场景端到端运行。
- 所有业务数字由确定性工具产生，带口径/时间窗/数据时间/来源。
- Agent 只能调授权固定工具；**不能生成任意 SQL/PromQL/ES DSL**；V1 无写工具。
- 长任务支持超时/取消/重试/恢复/部分结果/人工介入。
- 每次运行可追溯 model/prompt/tool/retrieval/policy 版本。
- 版本化评测集 + PR 回归 + 故障注入 + 红队 + 发布门禁。
- 具备 trace/指标/成本/审计/告警/灰度/回滚。
- 提供可公开讲解的架构/ADR/评测/故障报告/演示。

### 1.5 V1 具体场景清单（全项目验收锚点，D0 前固化）

> 成功标准里的"三个业务 + 三个排障"以本清单为准；评测集、验收、里程碑均以这 6 个场景为锚点。

**能力面 A —— 业务诊断（3 个）**
| # | 场景 | 数据依赖 | 就绪度 |
|:--:|------|---------|:---:|
| A1 | 订单量下降归因（漏斗断点：浏览→加购→下单→支付） | 行为+购物车+订单 | ⚠️ 缺漏斗粒度 |
| A2 | 支付成功率下降归因 | t_payment + 渠道 | ❌ 缺失败码 |
| A3 | 内容互动骤降归因（赞/藏/评/分享/Feed） | t_counter + 行为 | ⚠️ 缺 published_at |

**能力面 B —— 技术排障（3 个）**
| # | 场景 | 数据依赖 | 就绪度 |
|:--:|------|---------|:---:|
| B1 | MySQL 死锁 / 慢查询根因（trace+指标交叉） | error log / slow_query + SkyWalking | ⚠️ 需补管道 |
| B2 | RocketMQ 消费积压 / 死信归因 | consumer offset / DLQ / outbox | ✅ |
| B3 | 服务 5xx / 慢端点归因（跨服务链路） | Prometheus + SkyWalking trace | ✅ |

> 这些场景的**数据就绪度**正是 §8 缺口清单要补齐的对象。D0 完成后 6 场景必须都有事实数据 + 人工基线。

## 2. 先确定什么需要 Agent（沿用并强化 v5 标准）

**判断标准：下一步动作需要根据上一步观察结果动态决定，才优先考虑 Agent。**

| 业务请求 | 默认实现 | 原因 |
|---------|---------|------|
| "今天订单量？" | 指标工具 | 路径确定，要求数字可重复 |
| "支付成功率按渠道？" | 指标工具 | 固定聚合 |
| "每周运营报表" | Durable Workflow | 流程固定 |
| "退款口径是什么？" | RAG | 答案来自文档/指标字典 |
| "为什么今天订单降？" | 受限 Agent | 调查路径依赖中间证据 |
| "MySQL 最近有死锁吗？" | 观测指标工具 | 确定性查询 |
| "这个慢查询是根因吗？" | 受限 Agent(排障) | 需 trace+指标交叉归因 |
| "重启 order 服务" | **拒绝/人工审批** | V1 无运维写动作 |

> 补充 v5：**O&M 面同样遵循**——能确定查询的(死锁/积压/5xx)走工具，需要多步交叉归因的才走 Agent。

## 3. 系统架构

### 3.1 逻辑架构
```
运营 / 技术支持 / Prometheus 告警
             ↓
my-xhs-gateway（认证、角色、限流、request context）
             ↓
my-xhs-ai
├── Intent Router
│   ├── 业务指标查询 ──→ Deterministic(业务工具 L1)
│   ├── 观测指标查询 ──→ Deterministic(观测工具 L2)
│   ├── 业务知识问答 ──→ RAG（指标字典/Runbook/Schema）
│   ├── 固定报告 ─────→ Durable Workflow
│   └── 开放调查(业务/排障) → Bounded Agent
├── Agent Harness（plan/act/observe、budget、loop检测、HITL、证据链）
├── Run API + SSE
└── Run/Conversation State
             ↓
工具层（按能力面分层授权）
├── business-mcp   L1 业务只读工具（领域 API + 指标语义层）
├── observability-mcp L2 观测只读工具（PromQL/ES日志/诊断SQL/trace/DLQ）
└── knowledge-rag  指标字典/Runbook/Schema/业务文档

横切（从 D0 贯穿）：Policy / Guardrails / Eval / OTel / Audit / Cost / Model Gateway
```

### 3.2 部署边界
V1 只新增两个服务（沿用 v5）：
| 服务 | 端口 | 职责 |
|------|:--:|------|
| `my-xhs-ai` | 19020 | API、Router、Agent、RAG、Run、SSE |
| `my-xhs-ai-mcp` | 19021 | 受控只读工具（业务+观测） |
| `my-xhs-ai-ui` | 19022 | 轻量 Web 前端（SSE 流式，UI 薄壳） |

> **逻辑组 vs 物理服务**：§3.1 的 `business-mcp` / `observability-mcp` / `knowledge-rag` 是**逻辑工具分组**（对应 L1/L2/知识库），不是三个物理服务。V1 只部署**一个** `my-xhs-ai-mcp`，内部按逻辑组区分工具与授权；仅在出现数据安全边界/独立所有权/独立扩缩容/故障隔离等证据后才拆物理服务，**不为每个库建一个服务**。

> **UI 层定位（v6.1 补入，参考 opencode/pi 的交互范式）**：`my-xhs-ai-ui` 是**轻量 Web 薄壳**，只消费 `my-xhs-ai` 的 API+SSE，不承载核心逻辑。用途：流式展示 Agent 思考/工具调用过程、证据链/来源可点回原文、HITL 审批按钮、权限/审计可见性。**核心仍是后端 API/SSE**，UI 只是让运营/技术支持能直接用（参考 `../09-reference/pi-reference.md`）。前端只在 D2 给最小聊天壳、D7 完整试点界面，不提前投入。

### 3.3 工具权限分级（本版关键设计）
```
L1 业务工具（只读领域 API + 指标语义层）—— 运营权限
L2 观测工具（PromQL / ES DSL / 诊断SQL / trace / DLQ）—— 排障权限，更敏感，审计更严
L3 运维动作（重启 / 重投 / 回滚 / 改配置）—— V1 默认拒绝，需人工审批
```
- 安全护栏（注入检测/内容过滤/PII脱敏/权限守卫/审计）作为**横切层叠加在每级之上**。
- L1/L2 是 V1 开放范围；L3 一律走人工，不开放给 Agent。

### 3.4 数据与状态分离（沿用 v5，四类状态必须分开）
| 状态 | 权威存储 |
|------|---------|
| 业务事实 | 原业务服务/数据库 |
| Durable Run State | Workflow History / Run Store |
| Conversation State | Redis + 持久会话表 |
| Long-term Memory | 独立 Memory Store（按需引入） |

### 3.5 运行状态机（沿用 v5）
```
RECEIVED → AUTHORIZED → PLANNED → RUNNING
                |-> WAITING_TOOL / WAITING_RETRY / WAITING_APPROVAL
                `-> SUCCEEDED / PARTIAL / FAILED / CANCELLED / EXPIRED
```

## 4. 技术选型（⚠️ 暂定，待 D0 核验后锁定）

> **现状：技术选型尚未开始/未定死。** 下表继承 v5 原则，所有版本在 D0/D1 真正引入时**重新核验、锁定、保存兼容性报告**，不盲信旧版本号。

| 能力 | 默认主线 | 挑战者/实验 | 决策 |
|------|---------|-----------|------|
| Java LLM/Agent | LangChain4j Core | AgentScope Java 2.0、Spring AI | 同一场景 PoC 后只保留一个 |
| MCP | 官方 MCP Java SDK | 框架内置适配 | 协议层不自研 |
| Durable Workflow | Temporal Java SDK | AgentScope persistence、Restate | 故障恢复实验后决策 |
| 模型访问 | OpenAI-compatible client | LiteLLM | 多 Provider/配额需求成立时引入 |
| RAG | LangChain4j + ES | 独立向量库 | 先做容量/质量基线 |
| Trace | OTel + 现有 SkyWalking | OpenInference | 统一 traceId/runId/stepId |
| LLM 可观测 | Langfuse | 自研 | OTLP/HTTP 集成，避免 SDK 锁定 |
| CI 评测 | JUnit + Promptfoo | DeepEval/RAGAS/Inspect | 只做限时对比 |
| 策略 | Java deny-by-default allowlist | OPA | 复杂后引入 OPA |
| PII | Java 确定性脱敏 | Presidio | 中文 PoC 达标后采用 |
| 本地推理 | 不作 V1 前置 | vLLM | 数据主权/规模成立时引入 |

**D0 技术核验动作**：
- 确认**模型接入现状**：项目是否有可用模型 key / 网关 / Provider（D1 卡点，必须先回答）。
- 锁定 MCP/框架/模型接入版本，跑 conformance + 兼容性报告，产出第一批 ADR。

## 5. 交付阶段（v6 重排，业务 + O&M + 安全三线）

### D0：基线、缺口与安全地基（2-3 周）
- 定义第一用户 + 支撑的业务决策；固化 §1.5 六个场景。
- 指标字典：口径/维度/时区/延迟/Owner/版本。
- **业务数据缺口补齐**（见 §8.1，含**动现有服务的工程治理**：归属/回归门禁/事件流水演进）。
- **观测缺口补齐**（见 §8.2）：mysql/redis exporter、slow_query_log 管道、DLQ 消费者。
- 威胁模型 + 固定只读工具 + deny-by-default + 审计分离落地。
- 技术选型核验（含**模型接入现状**）+ 首批 ADR + 30 条基线评测。
- **Gate**：§1.5 六场景都有事实数据+人工基线；指标正确性可被普通 Java 测试独立验证；观测管道就绪。

### D1：最小纵向切片（3 周）
- `my-xhs-ai` Maven 骨架 + gateway 路由 + 健康检查。
- 模型 Provider 抽象、超时/重试/结构化输出/SSE。
- 一个业务指标工具（如 `order.query_volume`）+ 一个观测工具（如 `mysql.slow_query`）。
- 意图→工具→结果→来源引用闭环 + JUnit 契约 + 最小 trace + token/cost。
- **⚠️ 依赖**：D1 的 `mysql.slow_query` 工具必须等 **D0 的 slow_query_log 管道**（§8.2）就绪后才能真正取数；若 D0 未完成，先做 mock/契约测试，不阻塞骨架。
- **Gate**：关键数字与工具逐字段一致；模型不可用返回明确降级；trace 无密钥/PII。

### D2：可信工具层与 MCP（4 周）
- `my-xhs-ai-mcp` + 官方 MCP Java SDK。
- 业务三组（订单/支付/库存）+ 观测三组（MySQL/Redis/MQ）固定只读工具。
- **⚠️ 依赖**：观测三组依赖 **D0 的 exporter（mysql/redis）+ slow_query_log 管道 + DLQ 消费者**（§8.2）就绪；未就绪的观测工具同样先做契约测试。
- 工具 schema、分页、窗口上限、deadline、错误分类、数据新鲜度。
- 只读账号、字段白名单、角色授权(L1/L2)、审计。
- **`my-xhs-ai-ui` 最小聊天壳**：SSE 流式展示工具调用与结果（只接 API，不实现业务逻辑），先能演示闭环。
- **Gate**：LLM 无法提交任意 SQL/PromQL/ES DSL；非授权调用 100% 拒绝并审计；工具输出可被非 LLM 测试验证。

### D3：RAG 与上下文（3-4 周）
- 指标字典/Runbook/Schema/故障手册知识库。
- 清洗/chunk/embedding/混合检索/rerank/引用 + ACL-aware。
- **Gate**：口径可点击回原文；检索不到可信内容时拒答/声明不确定。

### D4：受限诊断 Agent（业务+排障，4-5 周）
- Intent Router 区分 指标/观测/RAG/Workflow/Agent。
- 业务归因 Agent + 排障证据链 Agent（trace+指标交叉）。
- 循环检测、证据/反证、部分结果、不确定性。
- 三个业务 + 三个排障场景端到端。
- 框架对照 PoC（LangChain4j vs AgentScope Java）+ ADR。
- **Gate**：固定问题优先走确定性路径；预算达到即停；不把相关当因果。

### D5：Durable Execution 与记忆（4 周）
- Run/Step 状态机、checkpoint、取消、重试、退避、HITL。
- Worker kill/重启/重复消息/工具超时故障测试。
- Temporal PoC（若触发条件成立）。
- **Gate**：工具成功但 Worker 崩溃不产生不可接受重复副作用；旧 Workflow 可 replay。

### D6：评测、安全与 AgentOps 深化（4-5 周）
- PR/nightly/release 三层评测；300+ 分层用例（正常/边界/拒答/权限/故障/多轮/攻击/注入）。
- **效果评估指标固化为一等公民（JD18 校准）**：任务完成率、工具调用准确率、幻觉率（数字与确定性结果一致性）、响应时延、Token/成本——进 Dashboard 并设阈值（见 §7.1）。
- JUnit 确定性 + Promptfoo 黑盒 + **红队（注入/越权/PII）**。
- Langfuse + OTel 的 run/step/model/tool/retrieval trace + Dashboard；**Phoenix 列入评测工具备选调研**（JD18 加分项）。
- **Gate**：确定性权限/schema/密钥扫描/关键契约全绿；注入 ASR、越权拦截率、PII 泄漏=0；质量/成本/延迟不过阈值。

### D7：部署、试点与作品集（3-4 周）
- Compose + K8s 清单；Secret/NetworkPolicy/只读文件系统/限额/PDB/健康。
- 容量/压测/备份恢复/RTO/RPO/灰度/回滚演练。
- Shadow→Canary→Pilot。
- **`my-xhs-ai-ui` 完整试点界面**：Agent 思考过程流式、证据链可点、HITL 审批、Dashboard 入口。
- 手册 + 演示视频 + 面试材料。
- **Gate**：release bundle 一键回滚；故障演练覆盖模型限流/MCP 超时/Worker 崩溃/中间件不可用；SLO 基于真实负载校准。

## 6. 贯穿式 DoD（每个能力都满足）
- 业务 Spec/输入输出/权限/失败行为/验收已定义。
- 代码/模型/Prompt/数据集/工具/索引/策略版本可追溯。
- 确定性单测/契约/权限测试通过。
- 新能力已加入版本化评测集 + 机器可读结果。
- 所有 LLM 调用有 trace/延迟/token/错误状态。
- trace/日志/评测无密钥与未脱敏 PII。
- timeout/retry/cancel/fallback/partial 已定义。
- 质量/延迟/成本不越回归阈值。
- ADR 记录采用/拒绝/替代/退出条件。
- 文档/Dashboard/Runbook 已同步。

### 6.1 工程失败模式与韧性清单（横切检查项，v6.1 收敛）
> 把散落在 D1/D4/D5/D6 的韧性机制收敛为一张总表：每个失败模式 → 处理机制 → 归属阶段。**任何 Agent/工具进入评测前都按此清单过一遍。**

| # | 失败模式 | 处理机制 | 归属 |
|:--:|---------|---------|:--:|
| 1 | 工具/推理死循环 | Harness loop 检测（连续同工具/同状态上限）+ **预算达到即停** | D4 |
| 2 | 步骤数/Token 超预算 | 预算(budget)上限：步骤数、Token、成本三重封顶 | D4 |
| 3 | 模型超时/不可用 | Provider 超时 + 明确降级（返回"暂不可用"而非瞎编） | D1 |
| 4 | 工具调用超时 | 每工具 deadline，超时标记为失败并重试/放弃 | D2 |
| 5 | 工具重试/退避 | 可重试错误 + 指数退避；不可重试错误直接失败 | D1/D5 |
| 6 | 用户取消 | Run 状态机 cancel，允许中途取消 | D5 |
| 7 | 重复消息/重复执行 | 幂等键 + 去重；Worker 重复消息故障测试 | D5 |
| 8 | Worker 崩溃 | checkpoint 落盘 + 状态机 replay 恢复，不重跑已完成步骤 | D5 |
| 9 | 部分成功 | 返回部分结果 + 明确哪些未完成，不假装全成 | D1 |
| 10 | 高危动作(重启/重投/写) | L3 一律 HITL 人工审批，Agent 不能自决 | D0-D5 |
| 11 | 成本失控 | 场景预算 + 月度上限 + 成本分布测 | D6 |
| 12 | 不确定结论 | 声明不确定性 + 证据/反证，不把相关当因果 | D4 |
| 13 | 中间件/MCP 不可用 | 故障演练 + 降级；release 一键回滚 | D7 |
| 14 | 越权/注入/PII 泄漏 | deny-by-default + 权限守卫 + 脱敏 + 审计（能力面 C） | D0-D6 |

> 配套：评测集按此清单设"故障/恢复"分层用例（§7 数据集分层：故障注入）；SLO 见 §7.1（超时/成本/恢复有阈值）。

## 8. D0 门禁：数据与观测缺口清单（本版明确化）

### 8.1 业务数据缺口（必须补齐，否则 Agent 只能答"现象"）
> ⚠️ **这些补齐会改动现有 16 服务**（表结构/代码/事件），不是 AI 侧的事。工作量 + 归属 + 回归必须明确（见下）。

| 缺口 | 影响 | 方案 | 归属服务 |
|------|------|------|---------|
| 支付失败原因 | 场景 A2 无法归因 | 补支付失败事件(失败码+阶段+渠道摘要) | my-xhs-payment |
| note.published_at/audited_at | 内容发布/审核分析受限(A3) | 补两个时间字段或事件流水 | my-xhs-content |
| 关注事件流水 | 净粉丝增长/流失分析难 | 关注/取关改事件流水或历史表 | my-xhs-analytics/content |
| 退款商品级明细 | 商品退款率算不准 | t_refund 补商品明细 | my-xhs-payment |
| 转化漏斗粒度 | "订单降"难归因断点(A1) | 确认/补 浏览→加购→下单→支付 行为粒度 | my-xhs-analytics/home |

**数据补齐的工程治理（D0 内单独立项）**
- **归属**：由对应服务 Owner 承担，AI 项目只提需求与验收，不代改现有服务。
- **回归门禁**：每项补齐后必须重跑受影响链路的 full-chain-test（复用现有 7 链测试），确保不破坏既有 46 项 P0 修复。
- **演进**：优先用**事件流水**（append-only、不破坏既有表）而非改既有表字段，降低回归风险。
- **验收**：补齐后 6 场景（§1.5）必须有可查询事实数据 + 人工基线，才允许进入 D1。

### 8.2 观测缺口（O&M 工具数据基础）
| 缺口 | 影响 | 方案 |
|------|------|------|
| 无 mysql-exporter | 死锁/慢查询/锁等待不可采集 | 部署 exporter |

## 9. 安全与治理基线（能力面 C）
- **deny-by-default**：只允许显式注册的角色/工具/参数/字段；V1 无写工具。
- **权限分级** L1/L2/L3（见 §3.3）；审计与可观测分离。
- **Prompt 注入**：检测只是信号，确定性权限才是兜底；间接注入(检索/工具结果)不可信。
- **数据最小化**：只返回聚合不返回用户明细；PII 脱敏进上下文前完成。
- **供应链/模型治理**：Provider 数据保留/地域/密钥入 ADR；版本锁定+SBOM+密钥扫描。
- **发布门禁**：model+prompt+tool+index+policy 捆绑可回滚 bundle。
- **合规**：EU AI Act 按部署地区/角色/风险分类评估，不默认高风险。
