# 对 PLAN.md（v5）的批判性再判断

> 依据：`business-reality.md` 的真实业务分析。目标不是「捧」也不是「踩」，而是判断：**这份 AI 规划是否真的服务于 my-xhs 的业务**，以及哪里偏离了。
> 立场：不盲从旧规划；基于业务现实指出取舍问题。

---

## 一、总判断

**PLAN.md 的「工程/方法/治理」部分质量很高，但「业务取舍」部分偏科，没有以业务优先。**
一句话：**它把「工程上最难的系统」当成了「业务上最重要的事」，选错了 V1 的主战场。**

---

## 二、成立的部分（应保留，不重复否定）

- **架构主线正确**：确定性系统管数字/权限/副作用，LLM 管理解/调查/解释；V1 只读 + 默认拒绝授权。✅
- **四类状态分离**（业务事实 / Durable Run / Conversation / Long-term Memory）✅
- **评测、安全、可观测、成本从 D0 贯穿**，不是最后补课 ✅
- **学习双轨 + 论文四步法**，兼顾交付与成长 ✅
- **克制**：不默认多 Agent、不默认十个 MCP 微服务 ✅

这些是整个规划的骨架，是对的，不用推翻。

---

## 三、偏离业务的部分（需要修正）

### 3.1 ⚠️ V1 三个场景全部集中在「电商交易 + 工程侧」

| PLAN V1 场景 | 所属支柱 | 是否工程最复杂 |
|-------------|---------|:---:|
| A 订单下降诊断 | 电商 | 是（分库分表+事务消息+EventSourcing） |
| B 支付成功率下降 | 电商 | 是（双通道+分布式事务） |
| C 库存预扣失败 | 电商 | 是（TCC+独立实例隔离） |

**问题**：三个场景选的全是分布式事务最复杂的系统。而对「内容+社交+电商」平台而言，**内容互动 / 增长 / 搜索分析**的业务价值并不低于甚至可能高于这三者。场景选择看起来更像「拿最难的工程系统当作品集亮点」，而不是「先解决运营最痛的问题」。

> 依据 business-reality.md：全平台运营问题里，内容增长、用户成长、热搜/无结果率等占很大比例，V1 一个都没覆盖。

### 3.2 ⚠️ 把「Agent 诊断」当主菜，本末倒置

业务现实：Top-20 运营问题里 **绝大多数是确定性指标查询**（订单量、热搜、互动率、支付成功率……），只有极少数是「多步调查归因」的 Agent 诊断。

PLAN 却把「受限诊断 Agent」设为 D4 的核心交付和主卖点。
**更符合业务的顺序应该是：先交付「业务指标助手」（D1-D3 就能用、价值立现、风险低），再把 Agent 诊断作为增强层。** 一上来主攻诊断，会让前 4 个月交付的东西反而离日常运营最远。

### 3.3 ⚠️ 自我矛盾：LLM 能否碰数据库

`PLAN.md` 明说「不让 LLM 直连数据库」，但同项目 `business-domain.md` 给了「所有 t_* 表 SELECT」的直连清单。
→ 必须拍板统一（推荐：固定 MCP 只读工具，符合 PLAN 安全原则）。这在动工前是阻塞项。

### 3.4 ⚠️ 没有定义「第一用户」和「支撑的业务决策」

PLAN 大量谈技术，但没说清：**谁是 AI 的第一用户（运营？技术支持？），AI 输出的诊断要支撑运营的什么决策**。没有这个，评测集和验收标准没有锚点。

---

## 四、缺失的部分（PLAN 没覆盖但业务需要）

1. **跨全平台的业务价值优先级排序**——不是按工程复杂度，而是按运营决策影响排序。V1 应从「内容/交易/增长」整体里挑最高价值切片。
2. **转化漏斗归因能力**——「订单为什么降」的真正答案是漏斗断点（浏览→加购→下单→支付哪一步掉），需要确认 t_user_behavior 漏斗粒度，PLAN 未提。
3. **内容支柱的指标**——互动率、审核通过率、草稿转化、优质内容增长，V1 缺位。
4. **明确的数据缺口补齐计划**——PLAN §2.2 列了清单，但应作为 D0 硬门禁 + 专人专项，而非「尽量补」。

---

## 五、重大补充：O&M 技术排障维度（本会话新增）

**PLAN 最大的整体遗漏：只设计了"业务诊断"，几乎没设计"技术运维/排障"。**

用户指出关键点：一个面向运营+运维的 Agent，除了"订单为什么降"，还必须能答"**MySQL 为什么死锁/慢查询、负载为什么高、MQ 为什么积压、服务为什么 5xx**"——后者是分布式系统的日常痛。

### 5.1 PLAN 低估了 O&M（有资产、无设计）
- my-xhs 的**观测资产其实很全**：SkyWalking 全链路 + Prometheus + ELK + XXL-Job + 故障 SOP（见 `../../docs/test-2/engineering-docs/monitoring-pipeline.md` / `failover-scenarios.md`）。
- 但 PLAN 只把"observability-mcp"一句话带过（Prometheus/ES 日志/trace/DLQ），**没有把它当作与业务诊断并列的一等能力面**，也没有设计 O&M 工具的分级授权与审计。

### 5.2 O&M 排障场景（详见 pillar-3-ops/）
| 域 | 典型场景 |
|----|---------|
| MySQL | 死锁 / 慢查询 / 负载 / 主从延迟 / 连接池耗尽 / 分片路由 |
| Redis | 内存淘汰 / OOM / Sentinel 切换 / 热点大key / 缓存脏读 |
| RocketMQ | 消费积压 / 死信 DLQ / Outbox 积压 / 事务消息失败 |
| ES | 索引健康 / 同步延迟 / 重建失败 |
| JVM/服务 | OOM / GC / 5xx / 慢端点 / 跨服务链路(trace) |
| 定时任务/事务 | XXL-Job 失败 / TCC 悬挂 / 本地消息表积压 / 对账差异 |

### 5.3 O&M 给 AI 项目带来的设计增量
1. **工具权限分级**：业务工具(L1) < 观测工具(L2: PromQL/ES/诊断SQL/trace) < 运维动作(L3: 重启/重投/回滚)。V1 只做 L1+L2 只读，L3 默认拒绝需审批。
2. **业务↔技术联动**：业务异常(订单降)的技术根因(慢查询/死信/中间件)要靠 trace+指标交叉定位——Agent 证据链需跨 pillar-1/2 与 pillar-3 取证。
3. **O&M 观测缺口补全**：mysql/redis exporter 缺失、slow_query_log 无管道、无 DLQ 消费者、VM 未接线——应纳入 D0 观测就绪门禁。
4. **审计分离**：观测工具访问更敏感，与业务查询分开记录。

## 六、重大补充：AI 自身安全（Guardrails）维度（本会话新增）

**用户指出第三大遗漏：大模型/Agent 安全。** PLAN §9 有安全基线、phase-11 有安全设计，但**没有在新规划里把它固化为与业务/O&M 并列的一等能力面**，且分散在多个阶段（D0/D6/D7）。

### 6.1 AI 安全 ≠ O&M
- O&M(支柱三)：管好系统不宕机（死锁/慢查询/积压）。
- AI 安全(支柱四)：防住针对 LLM/Agent 本身的攻击——**提示注入(直接/间接)、过度代理、数据泄漏/PII、供应链、幻觉、合规**。

### 6.2 本系统天然有利的安全基础（可复用）
- **V1 只读 + 固定工具 + deny-by-default** → 即便提示注入成功，也没有写工具可调用 → 无业务写副作用。
- 业务 VO 已脱敏（receiverPhone→`138****1234`）。
- 鉴权四层 + 观测/审计概念已有。

### 6.3 需固化的安全增量
1. **威胁模型**：OWASP LLM Top 10 映射到本系统（直接/间接注入、工具结果注入、过度代理、PII、供应链、幻觉）。
2. **安全原则**：确定性安全兜底不依赖 LLM 自辨；数据最小化；权限最小化；审计与可观测分离。
3. **工具权限分级已定**：L1业务 < L2观测 < L3运维(默认拒绝需审批)，安全层叠加在每一级之上。
4. **红队/评测**：注入 ASR、越权拦截率、PII 泄漏=0、幻觉率，纳入 release 评测门禁。
5. **发布 bundle**：模型+Prompt+工具+索引+策略捆绑可回滚。

### 6.4 与工具权限的衔接（关键设计）
安全护栏（注入检测、内容过滤、PII 脱敏、权限守卫、审计）作为**横切层**叠加在 L1/L2/L3 之上，而非独立阶段——从 D0 就开始，不是最后补课。

---

## 七、修正后的建议（业务 + O&M + AI 安全 三能力面）

```
D0 硬门禁（不跳过）：
  ① 拍板「MCP 固定工具 vs LLM 直连」矛盾  → 推荐 MCP 固定只读工具
  ② 定义第一用户（运营 + 技术支持）+ AI 支撑的业务决策
  ③ 数据缺口补齐（支付失败码 / note.published_at / 关注事件流水 / 退款商品级 / 漏斗粒度）
  ④ 观测缺口补齐（mysql/redis exporter、slow_query_log 管道、DLQ 消费者）
  ⑤ 安全基线落地（威胁模型、固定只读工具、deny-by-default、审计分离）

新 V1 主线（三能力面，从易到难）：
  S1 业务指标助手（确定性：内容/交易/增长/搜索）→ 当天运营价值，风险最低
  S2 观测指标助手（确定性：慢查询/死锁/MQ积压/JVM/5xx）→ 运维价值，L2 只读
  S3 异常检测与告警（业务+系统双维度，规则+阈值）
  S4 受限诊断 Agent（业务归因 + 技术排障证据链，跨支柱取证）
      → PLAN 的 D4 作为增强层，而非唯一主菜
  横切：安全护栏(注入/越权/PII/审计)从 S1 即接入，随 S1-S4 全程加固
```

> 一句话总结：**PLAN 的方法和架构合格，但有三处偏科/遗漏——(a) V1 业务取舍只盯电商交易、(b) 遗漏 O&M 技术排障维度、(c) AI 自身安全未固化为一等能力面。修正方向：业务 + O&M + AI 安全三能力面并重，「指标助手打底 → 观测助手 → 异常检测 → 诊断 Agent 作增强」，安全护栏全程横切——这才叫既服务于业务、又服务于运维、且自身安全可控。**
