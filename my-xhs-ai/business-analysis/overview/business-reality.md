# my-xhs 业务现实分析（AI 项目的前置业务理解）

> 目的：在评价/设计任何 AI 项目前，先真实、独立地搞清 my-xhs 到底是什么业务、为谁服务、靠什么产生价值。
> 说明：本文档刻意不先入为主地接受 PLAN.md 的结论，而是从源码和现有业务文档反推业务现实。
> ⚠️ **本文档是"第一版业务概览"**，偏宏观；按业务支柱细化的最新分析见 `pillar-1-content/`、`pillar-2-commerce/`、`pillar-3-ops/`、`pillar-4-ai-security/`（本文件不再逐一更新）。
> 依据：15 个微服务源码（gateway/user/content/analytics/counter/product/order/inventory/cart/coupon/search/home/im/notification/payment）+ `docs/test-2/business-docs/`。

## 1. my-xhs 本质是什么

**一句话：my-xhs 是一个「内容 + 社交 + 电商」一体化平台，产品形态对标小红书。**

它不是纯电商，也不是纯社交，而是**两个业务支柱并存**，互相导流：

| 支柱 | 覆盖服务 | 用户行为 | 产生价值的方式 |
|------|---------|---------|--------------|
| **内容与社交** | content-social、home、search、analytics、im、notification、user | 发布笔记、评论、点赞、收藏、关注、搜索、Feed 浏览、私信 | 内容资产、社交关系、用户粘性与增长 |
| **电商交易** | product、cart、coupon、order、payment、inventory | 浏览商品、加购、领券、下单、支付、退款、收货 | GMV、交易、履约 |

两条支柱通过「笔记种草 → 商品转化」的路径衔接（home BFF 同时聚合笔记详情与商品详情，Feed 内容与商品混排）。

## 2. 用户角色（AI 服务的对象）

| 角色 | 关注什么 | 对应 AI 价值 |
|------|---------|-------------|
| **普通用户 / 内容消费者** | 找内容、找商品、体验 | （C 端产品功能，非本 AI 范围） |
| **内容创作者 / KOC** | 曝光、互动、粉丝增长、笔记数据 | 内容运营分析 |
| **运营 / 数据分析** | 平台健康度、增长、转化、营销效果 | **指标助手 + 异常诊断** |
| **技术支持 / SRE** | 订单/支付/库存/中间件异常、死信 | 异常诊断 + 系统排障 |
| **商家 / 管理员** | 商品、库存、券、审核 | 交易/库存运营 |

> ⚠️ PLAN.md 没有明确「谁是 AI 的第一用户、AI 支撑哪些具体业务决策」——这是需要补齐的。

## 3. 两条业务主链路（AI 必须理解的真流程）

### 3.1 内容与社交闭环
```
创作者发布笔记(NC01) → 审核(DFA) → 上架
  → 粉丝收件箱递送(FEED_TOPIC) → Feed 曝光(home H01)
  → 用户互动：点赞/收藏/评论/分享(内容社交34端点)
  → 异步计数(CounterEventConsumer 10事件) + 通知(notification)
  → 搜索发现(search) / 推荐(ItemCF) / 热搜
```
业务健康度 = 发布量、审核通过率、互动率、粉丝增长、内容分发效率。

### 3.2 电商交易闭环
```
浏览商品 → 加购(cart) → 领券(coupon) → 下单(order D01)
  → 库存预扣(inventory TCC) → 支付(payment) → 发货 → 确认收货 → 完成
  → 异常路径：取消、退款、超时关单、预扣失败、对账
```
业务健康度 = 订单量、转化漏斗、支付成功率、退款率、库存水位、核销率。

## 4. 关键业务指标（按业务域，AI 真正要回答的）

来自现有业务文档 Top-20 运营问题，按业务价值重组：

| 业务域 | 关键问题 | 数据来源 |
|--------|---------|---------|
| 内容增长 | 日发布量、审核通过率、草稿转化率、优质内容数 | t_note |
| 内容互动 | 互动率（赞/藏/评/分享）、热门话题 | t_note、t_counter、Redis |
| 用户成长 | 日注册、活跃度、粉丝增长 Top | t_user、t_follow |
| 搜索/推荐 | 热搜 Top20、无结果率、推荐 CTR | ES、Redis、t_user_behavior |
| 交易 | 订单量、转化漏斗、客单价 | t_order、t_order_item |
| 支付 | 支付成功率、渠道分布、**失败原因** | t_payment |
| 退款 | 退款率、商品级退款明细 | t_refund、t_order_item |
| 库存 | 预扣成功率、库存水位、冻结占比 | t_inventory、t_tcc_fence |
| 营销 | 领券/用券/核销率、到期预警 | t_coupon_template、t_user_coupon |
| 基础设施异常 | MQ 死信、推送失败、本地消息表积压 | t_local_message、t_push_task_fail |

## 5. 数据就绪度（业务现实 vs AI 需求，独立核实）

**已核实的事实**（不是照抄 PLAN，是读代码确认）：

| 数据 | 现状 | 对 AI 的影响 |
|------|------|-------------|
| 支付失败原因 | `Payment.java` **只有 status(0/1/2/3)，无失败码/失败阶段/渠道摘要** | 「支付为什么失败」只能答「哪个渠道/什么状态」，答不了「为什么」 |
| 笔记时间字段 | t_note 有 created_at，**无独立 published_at/audited_at** | 发布/审核时间分析受限制 |
| 关注/点赞/收藏 | 存 Redis ZSet/Set，**非持久化事件流水** | 净粉丝增长、取关分析难做 |
| 转化漏斗 | t_user_behavior 有 browse/like/fav/comment/share/search，**但缺「加购→下单」漏斗关键环节粒度** | 「订单为什么降」难归因到漏斗断点 |
| 退款明细 | t_refund 有 reason，**无商品级明细** | 商品退款率算不准 |
| 订单分片 | t_order 4 分片 | 聚合分析需汇总投影，避免跨分片在线扫描 |

> 结论：**数据缺口是真实且业务关键的，不是工程洁癖。** 这些不补，Agent 的诊断结论会停留在「现象」，给不出「原因」。

## 6. 一个必须重视的自我矛盾（AI 项目自己的文档打架）

对比同一 AI 项目自己的两份文档：

| 文档 | 说法 |
|------|------|
| `../../docs/PLAN.md` §2.3「明确不做」 | **不让 LLM 直连数据库或生成任意查询语言**；Agent 只能调用授权固定工具 |
| `../../docs/reference/business-domain.md`「AI Agent 查询能力」表 | MySQL(13306/07/08/09) 只读 **所有 t_* 表 SELECT**；Redis **myxhs:* 前缀**；ES 只读 |

**这两者直接矛盾**：一份说 LLM 不能碰数据库，另一份列了一张「所有表 SELECT」的直连清单。

> 这暴露了业务理解与工程约束没有对齐。在动工前必须拍板：是「MCP 固定只读工具（推荐）」还是「LLM 直连只读库」——前者符合 PLAN 的安全原则，后者与它冲突。

## 7. 给 AI 项目的业务判断（结论）

1. my-xhs 是**双支柱平台**，不是单纯的电商或内容。AI 项目不能只服务其中一个支柱。
2. 全平台真正高频、高价值的运营问题，**绝大多数是确定性指标查询**（订单量、热搜、互动率、支付成功率……），只有少数是「需要多步调查归因」的 Agent 诊断（订单/支付/库存为何异常）。
3. 因此**最高价值、最低风险的 AI 服务，应该是一层「业务指标助手」**，覆盖全平台；Agent 异常诊断只是其中一小块增强，而不是唯一主菜。
