# ADR-005：自研 UI/平台，不采用 opencode/pi 作底座

- **状态**：✅ 已接受
- **决策**：my-xhs-ai 的**后端（Java/LangChain4j，安全内建）+ 前端（自研薄 Web UI）全部自研**。opencode / pi（及同类编码 Agent 工具）**只作 UI 交互与模块划分的参考，不作运行时底座、不替换我们的实现**。

## 背景
用户提出是否"直接用 opencode/pi 的界面、调 opencode/pi 来操作"。两者都是 **TypeScript 编码 Agent 工具**（统一 LLM API + Agent 运行时 + TUI/Web 界面）。

## 为什么不自研（拒绝采用作为底座）
1. **定位不符**：opencode/pi 是**编码 Agent**（操作文件/跑命令），我们是**业务诊断 Agent**（查订单/支付/慢查询、逐步归因），业务上不匹配。
2. **安全模型根本冲突（最关键）**：pi 明确"**无内置权限系统，靠沙箱/容器隔离**"。我们面对真实业务数据 + 运维观测数据，必须 **deny-by-default + L1/L2/L3 + HITL + 审计内建在工具层**，不能外包给"不设防"的通用编码工具。
3. **技术栈不符**：我们是 Java + LangChain4j；它们是 TypeScript 编码工具，硬接会丢失确定性工具契约、评测、成本控制。

## 决策内容
- **后端**：自研 `my-xhs-ai`（Java/LangChain4j）+ `my-xhs-ai-mcp`（受控只读工具），安全/权限/评估/可观测内建（见 §3、§6.1、§7）。
- **前端**：自研 `my-xhs-ai-ui` 薄壳（API+SSE 流式），**模仿** opencode/pi 的交互范式（流式思考、工具调用展示、HITL 审批、证据链可点），不采用其代码。

## 借鉴（不采用）什么
| 面 | 借鉴 |
|----|------|
| UI 交互 | 流式输出 / 工具展示 / HITL 按钮 / 差分渲染思路 |
| 模块划分 | LLM 接入 / Agent 运行时 / telemetry / UI 分离 |
| 可观测 | 厂商中立 telemetry 契约 + 一致性测试思路（印证 OTel + 契约测试）|

> 详细参考：`../09-reference/pi-reference.md`。

## 替代方案（已拒绝）
- **用 opencode/pi 当 UI + 靠 MCP 接我们的工具**：安全模型冲突（无内建权限）+ 技术栈不符 + 定位不符。
- **零 UI、只给 API**：运营/技术支持无法直接使用，业务落不了地（不满足 §1 目标）。

## 后果
- 优点：安全可控、贴合业务、可评测、可审计、技术栈统一（Java）。
- 代价：UI 需自研（薄壳，工作量可控，仅 D2 壳 + D7 完整界面），不直接复用 opencode/pi 的成熟界面。
