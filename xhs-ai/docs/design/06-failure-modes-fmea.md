# D06 · 失败模式与影响分析（FMEA）

> 面试/评审视角：不仅要"能跑"，还要回答"挂了会怎样、怎么发现、怎么降级、怎么恢复、怎么验证"
> 每个失败模式必须给出：检测 → 影响面 → 用户可见行为 → 降级 → 恢复 → 演练/验证

## 2. 关键设计回应（会被追问的点）

1. **为什么 Redis 挂了是 fail-closed 而不是本地内存兜底？** 本地兜底会造成多副本状态分叉，恢复后冲突不可判定；宁可短暂不可用 + 明确提示。
2. **F5 与 F11 的关系**：审批登记必须在**写库成功之后**才对模型可见（状态只在提交点发布）；写库失败→动作不进入可审批状态，杜绝"审批了但没记录"。
3. **F7 的会话重建边界**：只重建"对话文本历史"（`ai_message`），不重建工具调用中间态；重建后明确告知"上下文已降级"。
4. **F1 的只读检索模式**：不是简单报错，而是把可用工具（ES/Prom/MySQL）结果结构化返回并附引用——**模型挂了仍可当检索工具用**。
5. **F15 的隔离机制**：每个数据源独立线程池/信号量（bulkhead）+ 独立超时/熔断；会话并发上限保护。
6. **F11 的幂等键**：变更动作重放安全（见 D02 三段式），崩溃后由 settlement 核验，不需要人工对账。

## 3. 演练计划（Chaos/故障注入清单）

| 演练 | 方法 | 期望 |
|------|------|------|
| LLM 故障 | iptables 阻断出网 / mock 502 | F1 降级链生效，无挂起 |
| Redis failover | Sentinel `failover` 命令 | ≤30s 恢复，会话无错乱 |
| Redis 清空 | FLUSHDB（隔离） | F7 重建成功，审计完整 |
| ES 停止 | `docker stop my-xhs-elasticsearch` | 日志类工具受控失败，其余可用 |
| jdtls kill | kill -9 | JGit 降级 + 自动重启 |
| xhs-ai 滚动重启 | kill + 拉起 | 会话恢复；pending 审批可继续 |
| 磁盘/预算 | 占位注入 | fail-fast + 告警 |
| 注入红队 | 构造含指令日志/知识 | 不触发高危工具；审计留痕 |
