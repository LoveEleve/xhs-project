# 工程结构规范

> **作用域**: 定义本项目的目录组织、模块划分、依赖方向。本规范由 ArchUnit 机械化守护。
> **状态**: 强制 · 违反即阻断 CI

---

## 1. 顶层目录结构（Java / Maven 项目）

```
<project-root>/
├── CLAUDE.md                  # AI 协作入口（地图模式，~100 行）
├── README.md
├── .gitignore
├── pom.xml                    # Maven 根 POM（版本统一管理）
├── .editorconfig
│
├── .harness/                  # 🔗 Harness 约束体系（真相来源）
│   ├── agents/                #   Agent 定义（owner.md …）
│   ├── rules/                 #   规则约束
│   ├── skills/                #   开发技能
│   ├── wiki/                  #   领域知识
│   └── changes/               #   变更追踪
│
├── <module>-common/           # 公共模块（model / dto / exception / util）
├── <module>-service-*/        # 业务服务模块
├── <module>-server/           # Spring Boot Web 服务
├── <module>-web/              # 前端（可选）
└── <module>-tests/            # E2E + 集成 + 架构约束测试
```

## 2. 模块职责与依赖方向

| 模块 | 职责 | 允许依赖 |
|------|------|---------|
| `*-common` | model / dto / enums / exception / util / constant | 无（仅 JDK + 基础库） |
| `*-service-*` | 业务服务、核心逻辑 | common, 框架 |
| `*-server` | Web 服务、门面、配置 | common, service, 框架 |
| `*-tests` | E2E / 集成 / 架构约束 | 全部（仅测试作用域） |

**依赖方向（单向，不可逆）**:

```
common  ←  service  ←  server  ←  tests
   ↑_________↑_________↑
      （上游永不依赖下游）
```

### 2.1 模块设计原则
1. **单一职责** —— 一个模块只做一件事
2. **显式通信** —— 模块间只通过接口/契约交互，禁直接内部方法调用
3. **可观测性** —— 每个模块暴露健康检查 + 关键指标
4. **无状态** —— 业务服务无状态，状态存于缓存/数据库

### 2.2 Server 层边界
- `*-server` 负责 REST 入口、Facade、会话协调、结果装配，不承载具体业务决策。
- `Controller` 只能依赖 `Facade / Application Service`，不得直接依赖具体业务实现类。
- `server` 层若出现业务规则复制/拼装，视为分层漂移，必须拆回 service 层。

## 3. 架构铁律（ArchUnit 守护）

| 规则 | 描述 |
|------|------|
| R1 | **Service 之间禁止直接依赖内部实现** —— 只能通过接口/契约通信 |
| R2 | **Common 禁止依赖任何业务模块** —— 它是最底层基座 |
| R3 | **Controller 禁止直接调用 Service 实现类** —— 必须经接口访问 |
| R4 | **Server 禁止复制业务规则** —— 仅做入口/门面/编排 |

```java
@AnalyzeClasses(packages = "com.<project>")
public class ArchitectureConstraints {
    @ArchTest
    static final ArchRule services_must_not_depend_on_each_other =
        classes().that().resideInAPackage("..service..")
            .should().onlyDependOnClassesThat()
            .resideInAnyPackage("..common..", "java..", "org.springframework..");

    @ArchTest
    static final ArchRule controller_must_not_call_services_directly =
        noClasses().that().resideInAPackage("..controller..")
            .should().dependOnClassesThat().resideInAPackage("..service..impl..");
}
```

## 4. 包结构规范（模块内部）

```
com.<project>.<module>/
├── config/                # Spring 配置
├── service/               # 业务服务
├── repository/            # 数据访问（缓存/数据库）
├── model/                 # 模块私有模型（公共模型放 common）
├── dto/                   # 数据传输对象
└── ...
```

**命名约定**:
- 包名全小写，单数
- Service 以 `Service` 结尾

---

## 5. 文件组织约束

| 约束 | 规则 | 守护手段 |
|------|------|---------|
| 文件长度 | ≤ 500 行 | Checkstyle FileLength |
| 方法长度 | ≤ 50 行 | Checkstyle MethodLength |
| 圈复杂度 | ≤ 10 | Checkstyle CyclomaticComplexity |
| 一个文件一个 public 类 | 强制 | Checkstyle OuterTypeNumber |
| 禁止 SNAPSHOT 依赖 | 强制 | Maven Enforcer |

---

## 6. 新增模块/feature 的目录约定

- 新 Service → 新建 `*-service-<name>/`，并在根 POM `<modules>` 注册
- 新需求 → 在 `.harness/changes/<id>/` 建档（见开发流程规范）
- 新架构决策 → 追加 ADR 到 `.harness/wiki/`
## 7. 架构审查关注点（arch-review 引用的语言特有检查项）

- **Maven 3.9+（离线 -o） 模块间依赖方向** — 是否有反向依赖？
- **ArchUnit（待接入） 约束** — 是否有被绕过的架构规则？
- **Spring Bean 注入** — 是否有循环依赖？
- **Service 层** — 是否有瘦 service + 胖 controller 的反模式？
