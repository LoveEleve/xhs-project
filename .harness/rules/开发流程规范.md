# 开发流程规范

> **作用域**: 定义本项目从需求到上线的开发流水线、技能调度顺序、阶段门禁、变更追踪。
> **理念**: 人类设计约束 → AI 沿流水线生产 → 机器验证每一步。
> **执行者**: `.harness/agents/owner.md`（Owner Agent）

---

## 1. 流水线总览

```
                                   ┌──────────── 每一步都对照 .harness/rules/ 校验 ────────────┐
                                   │                                                          │
   人类意图                         ▼                                                          │
      │   ① harnessing  ──▶ ② coding-skill ──▶ ③ unit-test-write ──▶ ④ expert-reviewer ──▶ ⑤ unit-test-ci ──▶ ⑥ deploy-verify ──▶ 交付
      │   规格构建                 测试先行实现       测试完善              专家评审             CI 门禁            部署验证
      ▼
   .harness/changes/<id>/   （全程留档，状态机驱动）
```

每个阶段对应 `.harness/skills/` 下一个技能，**严格按序，不可跳步**。

---

## 1.1 三层结构：协议 / 能力 / 门禁

项目 Harness 资产分三层维护，各司其职、互不耦合：

| 层 | 载体 | 内容 | 变更频率 |
|----|------|------|---------|
| **协议** | `AGENTS.md` / 本仓库 `rules/` + `owner.md` | 事实源、研发阶段、人工决策点、授权边界、完成条件 | 低，需人工审批 |
| **能力** | `.harness/skills/` | 领域 Skill（PRD/方案/测试/排障/归档）+ 跨语言通用技能 | 中 |
| **门禁** | `.harness/scripts/` | 确定性执行脚本（工作区校验/同步/发布门禁） | 低 |

> 公共能力通过 `.harness/skill-dependencies.json` **声明依赖**（来源 + 兼容版本），而非复制进每个项目；
> 项目 Skill 只保留业务编排，便于公共能力统一升级。

## 2. 阶段定义与门禁

| 阶段 | 技能 | 输入 | 产出 | 出口门禁（Gate） |
|------|------|------|------|-----------------|
| ① 需求分析 | `harnessing` | 一句话意图 | 规格卡 + 验收标准 + 设计约束 + 测试策略 | 规格明确、AC 可测试、≥3 边界情况、测试策略清晰 |
| ② 编码实现 | `coding-skill` | 已确认的规格卡 | 失败测试 + 最小实现 | 失败测试先存在并转绿、构建/lint 通过 + 符合编码规范 |
| ③ 单测编写 | `unit-test-write` | 实现代码 | 边界/降级/回归测试 | 测试通过 + 核心覆盖率 ≥80% + 关键降级路径已覆盖 |
| ④ 专家评审 | `expert-reviewer` | 代码 + 测试 | 评审报告 | 0 个 🔴 严重问题 |
| ⑤ CI 门禁 | `unit-test-ci` | 完整变更 | CI 报告 | 静态分析 + 架构约束 + 全量测试 全绿 |
| ⑥ 部署验证 | `deploy-verify` | 通过 CI 的构建 | 验证报告 | 冒烟 + 健康检查通过，有回滚预案 |

> **门禁原则**: 任一 Gate 不通过 → 退回修复或请示人类，**禁止进入下一阶段**。
>
> **跨阶段上下文资产**（6 阶段共用的知识底座，非某一阶段私有）：
> - `.harness/wiki/*` 业务规则 → ① ② ④ 消费；`.harness/tech/*` 技术链路 → ② ④ 消费
> - `.harness/动态事实来源.md` → ⑥ 消费（环境/日志/工作项实时查询）
> - `.harness/CONTEXT.md` 术语 → ② ③ ④ 消费
> - `iterations/` 机器可读协议（可选增强）→ 见 §2.2，① 产 REQ/AC、② 产任务、③ 产 TC、④ 对账

## 2.1 TDD 小循环（默认适用于核心业务逻辑）

在 ②~③ 阶段内部，核心业务逻辑默认遵循：

```
Red      先写失败测试（基于 AC / 边界 / 降级路径）
Green    写最小实现让测试通过
Refactor 在测试保护下重构
```

适用范围：
- 核心业务逻辑
- 业务规则判断
- 降级 / fallback 路径

非强制范围：
- 纯 DTO / 配置类 / 一次性脚手架

禁止事项：
- 先写完整实现再回头补核心业务测试
- 用覆盖率代替测试先行

## 2.2 机器可读迭代协议（iterations/，可选增强）

> 复杂需求可将单文件 `change.md` 扩展为**多文件迭代协议**，使阶段产物可被机器对账：
> `prd.md`（REQ/AC）→ `solution.md`（REQ→任务/观测点）→ `test/design.md` / `test/cases.md`（TC）→ `test/report.md`（证据）。
> 归档与知识回流统一落在 `.harness/changes/<id>/archive.md`（见 §3），不随迭代协议拆分。

**与 change.md 的关系（关键）**：迭代协议**不替代** `change.md`。`change.md` 始终存在并驱动 6 阶段状态机；选用迭代协议时，在 `change.md` frontmatter 增加 `iteration: <ITER-ID>` 字段指向 `.harness/iterations/<ITER-ID>/`，二者并行。`harness-status` / `harness-retro` 仍只扫 `.harness/changes/*/change.md`，不受影响。

**实例化（谁创建 <ITER-ID> 目录）**：需求阶段（`harnessing`）判定"复杂需求"后，把 `.harness/iterations/_TEMPLATE/` 复制为 `.harness/iterations/<ITER-ID>/`（ITER-ID 建议用 change 的 slug 或独立递增号），再填 `prd.md`。模板骨架由 apply-harness 生成，实例目录由 harnessing 在需求确认时创建。

**编号体系**：

- `REQ` — 需求（prd.md 定义，solution 与 test 反向引用）
- `AC` — 验收条件（归属某条 REQ，可测试）
- `TC` — 测试用例（归属某条 AC，供 flow→test 对账）

**阶段间接口门禁（上游变更，下游必须同步）**：

| 上游（已确认） | 下游 | 强制检查 |
|----------------|------|---------|
| `prd.md` 的 REQ/AC 变更 | `solution.md` | 每条 REQ 有任务承接、每条 AC 有观测点 |
| `solution.md` 未确认 | `coding` | **禁止进入编码** |
| `test/design.md` 未确认 | `coding` | **禁止进入编码** |
| `test/report.md` 无真实证据 | 发布准备 | **禁止进入发布** |
| 上游 AC 变更 | `test/cases.md` | 每条 AC 至少 1 个 TC，无孤立 TC |

> 原则：REQ 编号一旦确认不可变；改需求 = 改 REQ = 同步下游，禁止悄悄改下游产物绕过对账。

## 3. 变更追踪（.harness/changes/）

每个需求 = 一个变更，分配唯一 ID `C-NNN`，目录结构：

```
.harness/changes/C-NNN-<slug>/
├── change.md          # 变更卡（需求 + 验收标准 + 影响面 + 状态）
├── review.md          # 专家评审记录（④ 阶段产出）
├── verify.md          # 部署验证记录（⑥ 阶段产出，可选）
└── archive.md         # 归档 + 知识回流清单（done 后产出，harness-retro 统计知识回流率）
```

**变更状态机**:

```
draft → analyzing → coding → testing → reviewing → ci → verifying → done
                                                  └─(打回)─┘
```

- 状态写在 `change.md` frontmatter 的 `status:` 字段。
- 状态变更即更新文件 → 天然支持**断点续传**（Owner Agent 读 status 定位当前阶段继续）。
- 走迭代协议时（见 §2.2），`change.md` 仍驱动本状态机，仅额外以 `iteration:` 字段关联 `iterations/<ITER-ID>/` 多文件产物。
- **多变更并存时**：每个消费 change 的技能按 `.harness/rules/变更定位规则.md` 定位目标 change——显式指定 `<id>` 优先；否则按当前阶段匹配的 status 过滤；多候选时**停下列出清单请人类选择**，禁止擅自默认取第一个。

## 4. 人机协同协议

### 4.1 人类职责（意图指挥官）
- 定义需求、做架构决策、确定优先级、最终验收（👍/👎）
- 审批 ① 需求卡、④ 评审报告中的关键决策
- 不写实现代码、不写单元测试（除非 AI 无法完成）

### 4.2 Owner Agent 职责（实现执行者）
- 编排技能、编写代码与测试、更新文档、自审计、根因诊断
- 不做架构决策（只给建议）、不改变需求范围

### 4.3 必须暂停请示的触发点
1. 需求模糊到无法确定实现方式
2. 设计方案在实现时被证伪
3. 需要新增依赖 / 改 public API / 改架构
4. 发现安全风险
5. 触碰生产配置或密钥

## 5. 特殊场景流程裁剪

| 场景 | 裁剪规则 |
|------|---------|
| **Hotfix（紧急修复）** | 可简化 ①，但必须最小化变更卡（修复描述 + AC），修复后补全；④⑤ 不可省 |
| **Spike（技术探索）** | 可跳过完整 ①②③，但探索结论必须沉淀为 ADR 或 wiki 更新 |
| **棕地修改（改已有功能）** | 先更新对应 wiki/changes，再走 ②~⑥ |
| **纯文档变更** | 仅走 ① + ④（评审），无需 ③⑤⑥ |

## 5.1 状态流转责任

| 场景 | 责任人 | 动作 |
|------|--------|------|
| 新建变更 | Owner Agent | 创建目录与 `change.md`，状态置为 `analyzing` |
| 需求卡完成待审批 | Owner Agent | 明确提示"请审批"，不擅自进入 `coding` |
| 需求审批通过 | 人类（或经明确授权的 Owner Agent） | 将状态从 `analyzing → coding` |
| 编码完成 | Owner Agent | `coding → testing` |
| 测试完成 | Owner Agent | `testing → reviewing` |
| 评审通过 | Owner Agent | `reviewing → ci` |
| CI 全绿 | Owner Agent | `ci → verifying` |
| 验证通过 | Owner Agent | `verifying → done` |
| 阶段切换时 | Owner Agent | 生成 `.harness/changes/<id>/handoff.md` 交接文档，供下一个对话续接 |
| 评审/CI/验证打回 | Owner Agent | 按问题性质回退到对应上游状态，并在相关文件记录原因 |

默认规则：没有人类审批，不得从 `analyzing` 进入 `coding`。

## 6. 迭代节奏

```
单次协作周期（一个变更）:
  ① 读上下文（rules + wiki + change）
  ② 小步实现（每步编译通过）
  ③ 自审计（对照 AC 与 rules）
  ④ 修复 → 报告 → 人审 → 提交 → 更新 change 状态

每日:  完成的变更已提交，change 状态已更新
每周:  熵管理 —— 扫描代码异味、架构漂移、登记技术债
```

---

## 6.1 战争迷雾与决策地图（大项目规划）

对于大型项目，不要在开始时试图规划所有细节——你最多只能看到当前几步的决策，随着前面的决策逐步完成，后面的决策才会逐渐清晰。

### 决策地图（分层可见）

```
当前层（可见）     → 本次迭代需决策的事项
下一层（模糊可见）  → 了解大致方向，但不做细节规划
再下一层（迷雾）    → 知道存在，但不做任何假设
```

### 工作方式

1. **只规划当前层** — 当前迭代的变更卡，写清楚 AC、边界、设计约束
2. **下一层做标记** — 在 `.harness/changes/` 中创建占位变更卡，状态为 `draft`，只写标题和一句话目标
3. **迷雾层不碰** — 不做假设、不写代码、不预留抽象接口
4. **每完成一个当前层决策，迷雾层前移** — 将下一层的某个占位卡提升为 `analyzing`

### 冲突处理

- 当实现当前层时发现下一层的假设不成立 → 更新下一层占位卡，不修改当前层代码
- 当迷雾层突然清晰（如需求变更） → 创建新变更卡，状态为 `analyzing`，独立评估影响

### 禁止

- ❌ 为"未来可能的需求"提前写代码或预留抽象接口（YAGNI）
- ❌ 在第一个迭代就画完整架构图并承诺不变
- ❌ 因为"迷雾层的某个担忧"而在当前层过度设计

## 7. 质量博弈（防偷懒 / 防过度设计）

| 信号 | 应对 |
|------|------|
| "差不多了" | 逐条对齐 change.md 中的每个 AC |
| "基本实现了" | 追问：边界情况、错误处理、日志、注释呢？ |
| "先把代码写出来再补测试" | 退回 ②，要求先基于 AC / 边界写失败测试 |
| 残留 TODO/FIXME | 转为 `.harness/changes/` 任务条目 |
| 引入不必要抽象 | YAGNI —— 要求解释"现在"的价值 |
| 为未来需求写代码 | 砍掉，转为新变更登记 |

## 8. 流程合规检查清单（每个变更收口）

- [ ] 走完 ①~⑥ 六个阶段，每个 Gate 通过
- [ ] `.harness/changes/<id>/change.md` 状态 = `done`
- [ ] commit message 含变更 ID
- [ ] 涉及的 `.harness/wiki/` 文档已同步
- [ ] 无残留 TODO/FIXME，无被绕过的约束

## 9. 技术债管理（熵管理）

```
登记位置: .harness/changes/ 中专设技术债条目，或汇总于 .harness/changes/TECH-DEBT.md
优先级:
  P0  影响系统稳定性/安全性 —— 一周内修复
  P1  影响开发效率         —— 本月内修复
  P2  代码异味             —— 下个迭代修复
规则: 每个迭代至少处理 1 个 P1+ 技术债
```

**熵检测信号**: 模块间循环依赖 · 架构约束测试被注释/绕过 · 超长文件或超长函数 · 超 3 个月未解决的 P1+ 技术债。

**周期任务**: 每周扫描异味 · 每月架构漂移分析 + 依赖升级评估 · 每季度全面架构审查 + 规则修订。

## 10. 版本策略（语义化版本）

```
MAJOR.MINOR.PATCH
  MAJOR  架构变更 / 破坏性 API 变更
  MINOR  新功能
  PATCH  Bug 修复 / 性能优化 / 文档更新
```

规则文档（`.harness/rules/`）变更需在 commit message 注明，重大约束调整需人类审批。
