# PRD: 支付模块生产化改造

> 机器可读的迭代协议产物之一。本文件定义**业务需求与验收标准**，是 solution 的唯一事实来源。

## 背景与目标

支付域现状（证据：`06-支付联动` §七/§八、`模块对照/04-支付` §7）：

- **单次尝试支付模型**：30 分钟内在途拦截（`statusKey` 存在即拒），放弃/换渠道后无法重试；且只拦"商户侧新建"，渠道侧旧交易仍活（prepay_id 有效期内可付）→ 双活窗口；
- **退款域无出金幂等键**：`refundByOrder` 无 out 键防重（订单侧以"重试前查支付事实"缓解；支付域内仍留"部分退款+响应丢失"理论窗口）；
- **超时处置不达生产标准**：到点直接置失败——不查渠道（29 分付款会被误标失败）、置失败无核实证据、渠道交易不关闭（GAP-1/2/3/4）。

本迭代把支付模块升级到**生产形态**：支付单复用（一订单最多一条活支付单）、退款出金幂等、超时处置按渠道真相；使"学习即最终形态"，资金安全链路达标。

## 非目标（Out of Scope）

- 真渠道 SDK 接入与回调验签（无 HTTP 回调端点，模拟器直调 service——接真渠道时补；记录）
- 结算域改造（已达标）；对账体系扩展（11 已记录）

## 需求（REQ）

| ID | 需求描述 | 优先级 |
|----|---------|--------|
| REQ-1 | **支付单复用**：一个订单最多一条"活着的"（status=0）支付单——同渠道再次发起=**复用**（返回同 paymentNo，补记 REUSE 事件）；换渠道=**关旧交易 + 旧单置已关闭(status=4) + 新开一单**；并发发起由**唯一索引兜底**（DuplicateKey → 重查复用）；旧拦截键（`statusKey`/`payingKey` 的拦新读点）清理 | P0 |
| REQ-2 | **退款出金幂等**：`refundByOrder` 接受业务幂等键（`outRefundNo`，订单侧以售后单号/补偿重试同键传入）；`t_refund` 增唯一索引；同键重复请求**返回既有 refundNo**（不重复出金）；无键调用兼容现行为（记日志） | P0 |
| REQ-3 | **超时处置按渠道真相**（GAP-1/2/3/4）：① 置失败前**查渠道**（`queryPayStatus`）：渠道=成功 → 本地**收敛为成功**（补记 + 通知订单）；渠道=明确未支付 → 置失败；渠道**不可达 → 不处置、留下一轮**（"不知道"≠"没付"）；② 置失败前**关闭渠道交易**（`strategy.close`）；③ 置失败**记录核实证据**（1=渠道已确认未支付 / 2=超时未核实）；④ **对账核查分支**：未核实失败单日终重查渠道，已付 → 收敛成功（GAP-4） | P0 |
| REQ-4 | **订单终结咬合**：订单未支付终结（04B 链路）后，该订单的 pending 支付单被**关闭**（status=4 + 渠道 close），终结后不可再支付 | P0 |
| REQ-5 | **清理批次**（模块对照/04 §7 收口）：死配置接线（`pay.timeout.ms`/`refund.timeout.days` 生效）；注释漂移修正（T-077 等）；模拟器参数配置化（成功率/延迟）；`checkPaymentTimeout` 锁 TTL 与周期对齐；结算差异"自动收敛为已忽略"语义复核（结论+注释） | P1 |
| REQ-6 | **可靠性不降级**：既有幂等（乐观锁/Redis 标记）、通知四层兜底（Feign/MQ/补偿 Job/对账）、结算域全部保持；全模块测试基线（251+）全绿 + 新增用例 | P0 |

## 边界情况

- 当并发发起支付时：唯一索引 DuplicateKey → 重查 → 复用（不抛用户可见错误）
- 当渠道不可达时：超时处置**不动作**（下一轮再查；绝不"查不到就置失败"）
- 当调用方未传 `outRefundNo` 时：兼容现行为（按无幂等键路径执行 + 日志）
- 当订单终结与支付回调竞态时：沿用既有 false 业务拒绝 + 自动退款语义（06 §4.3）
- 当复用请求遇到已支付/已关闭支付单时：按现状返回（幂等语义保持）

## 人工决策点（已由 Owner 决策，2026-10-16）

- **决策 1（复用/换渠道语义）** = 采用 06 §七 既定方案：同渠道复用（阶段 1）、换渠道 close+新开（阶段 2）。理由：主流生产做法 A+B；保留"支付单=渠道凭证"锚点。
- **决策 2（退款幂等键）** = 订单侧传入业务键（售后单号/补偿重试同键），支付域唯一索引兜底；无键调用兼容。理由：出金动作幂等是硬要求；兼容期防破坏存量调用方。
- **决策 3（超时处置矩阵）** = 渠道成功→收敛成功；明确未付→失败+close+证据；不可达→不处置；**并补对账核查分支**（GAP-4：未核实失败单日终重查渠道，已付→收敛）。理由：生产标准"按渠道真相处置"；GAP-1/4 修复。
- **决策 4（订单终结咬合）** = 终结链路后通知支付侧关闭 pending（复用既有 Feign/消息链路，不新建通道）。理由：消灭"关单后仍可付"窗口。
- **决策 5（占位消费者/验签）** = 占位消费者保留（文档化占位，不动）；验签不做（无回调端点，记录待真渠道接入）。理由：控制范围，避免为 mock 场景造无主端点。
