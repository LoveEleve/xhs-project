# ADR 格式规范

> 架构决策记录（Architecture Decision Record）。ADR 仅当同时满足三个条件才创建，不泛滥。

---

## 三个必要条件（缺一不可）

| 条件 | 说明 |
|------|------|
| **难逆转** | 改主意成本高，不是轻易能翻盘的 |
| **脱离上下文会惊讶** | 未来读者看代码会想"为什么这么搞" |
| **真实权衡** | 有过真正替代方案，你因特定理由选了其中一个 |

只要三条缺一，**跳过 ADR**。轻松可逆的决定不用记——反正你会翻盘；不让人惊讶的决定不会有人追问；没有真正替代方案的决定，记"我们做了显而易见的事"毫无意义。

---

## 格式

ADR 放在 `docs/adr/`，按序号命名：`0001-xxx.md`、`0002-xxx.md`。

`docs/adr/` 目录惰性创建——仅在第一个 ADR 需要时建立。

**模板**：

```md
# {简洁标题}

{1-3 句话：上下文是什么、做了什么决定、为什么。}
```

**一个 ADR 可以只有一段话。** 价值在于记录了"做了决定"和"为什么"，不在于填满章节。

### 可选字段（仅当真有价值时加，大多数 ADR 不需要）

- **Status** frontmatter：`proposed | accepted | deprecated | superseded by ADR-NNNN`
- **Considered Options**：被否决的替代方案值得记住时才写
- **Consequences**：有非显而易见的连锁影响时才标注

---

## 什么值得写 ADR

| 类别 | 示例 |
|------|------|
| **架构形状** | 单体 vs 微服务、monorepo 结构 |
| **上下文间集成模式** | 领域事件异步 vs HTTP 同步 |
| **有锁定成本的技术选型** | 数据库、消息队列、认证提供方、部署目标 |
| **边界和范围划定** | "Customer 数据由 Customer 上下文拥有，其他上下文只引用 ID" |
| **与常规做法的刻意偏离** | "不用 ORM 而是手工 SQL，因为 X" |
| **代码中不可见的约束** | "不能用 AWS，因为合规要求" |
| **被否决的替代方案** | 考虑过 GraphQL 选了 REST，原因微妙 → 记下来，否则半年后有人会再提 |

---

## 编号

扫描 `docs/adr/` 找最大序号，递增一位。
