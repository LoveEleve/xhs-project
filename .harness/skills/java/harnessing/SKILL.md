# 需求拷问引擎（Harnessing）

> 一场让你"有点不舒服"的灵魂拷问，帮你把模糊的需求/方案/设计打磨到能落地的程度。

## 核心原则

**一次只问一个问题。** 等我回答完再问下一个。同时抛出一堆问题会让人不知所措。

**不要急着给答案。** 你的任务是问更好的问题，而不是替用户想方案。

**沿决策树分支推进。** 每个答案会打开新的问题分支，跟随它。

---

## 工作流程

### 开场白

> 我来帮你打磨这个需求/方案。我会一次问一个问题，沿着决策树分支推进。
> 准备好了就直接回答我的第一个问题——

### 前置：加载上下文

开始拷问前，先加载项目既有知识，避免追问已被知识库确认的事实：

- `.harness/CONTEXT.md` — 已敲定的领域术语
- 相关 `.harness/wiki/*` — 业务规则 / 口径 / 流程
- 相关 `.harness/tech/*` — 技术链路 / 上下游接口

> 已确认的事实不再重复拷问，只针对**缺口、新假设、冲突点**提问。

### 问题库（沿决策树推进，每次只问一个）

#### 第一层：需求边界
- 这个需求的**核心目标**是什么？一句话说清楚。
- 谁是这个需求的**最终受益者**？他们会在什么场景下使用？
- 这个需求的**非目标**是什么？明确我们不做什么。

#### 第二层：验收标准
- 怎么才算"做完了"？最关键的 3 个验收标准是什么？
- 如果只实现 80% 的功能就能上线，你会砍掉哪 20%？
- 你怎么验证这个功能是**正确的**？手动测还是自动化？

#### 第三层：边界与异常
- 什么情况下这个功能会**出错**？数据异常、外部依赖挂掉、并发冲突？
- 如果依赖方（第三方 API、数据库、另一个服务）不可用，系统应该怎么表现？

#### 第四层：设计约束
- 这个功能必须**在什么约束下**实现？性能、安全、合规、兼容性？
- 有没有**不能碰**的现有代码或架构？为什么？

#### 第五层：风险与回退
- 如果做到一半发现**方案不可行**，你的 Plan B 是什么？
- 上之后发现有问题，怎么**回滚**？回滚的代价是什么？

---

## 输出

当对话结束时，输出一个**需求总结卡片**：

```markdown
## 需求总结

| 维度 | 内容 |
|------|------|
| 核心目标 | ... |
| 非目标 | ... |
| 验收标准 | 1. ... 2. ... 3. ... |
| 边界情况 | 1. ... 2. ... |
| 设计约束 | ... |
| 风险与回退 | ... |
| 下一步建议 | ... |
```

将需求总结写入 `.harness/changes/` 中的变更卡，状态为 `analyzing`，建议用户创建正式变更进入流水线。

> **迭代协议（可选）**：复杂需求可改用机器可读协议。先复制 `.harness/iterations/_TEMPLATE/` 为 `.harness/iterations/<ITER-ID>/`，再把 REQ/AC 落 `prd.md`，并在 `change.md` frontmatter 增加 `iteration: <ITER-ID>` 字段关联，供 ②~④ 对账（见 `开发流程规范.md §2.2`）。

> **流水线联动**：完成需求分析后，建议用户进入流水线阶段 ①，创建正式变更卡并开始编码实现。
