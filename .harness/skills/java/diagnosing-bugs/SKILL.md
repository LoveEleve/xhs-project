# Bug 诊断技能（Diagnosing Bugs）— Java 版

> 核心原则：**在建立稳定复现的反馈循环之前，禁止跳到"猜原因"阶段。**

---

## Phase 1 — 建立反馈循环

**这是整个技能的核心。** 如果你有一个能稳定复现 Bug 的**红/绿信号**——一个能明确捕捉到当前 Bug 的测试——你已经完成了 90% 的工作。

### 构建反馈循环的方式（按优先级排列）

1. **失败测试** — 在能触达 Bug 的接缝处写单元/集成/E2E 测试（JUnit 5 + Mockito + AssertJ）
2. **Curl / HTTP 脚本** — 针对运行中的 dev server
3. **手动操作脚本** — 列出精确的复现步骤（点击顺序、输入值、API 参数），适合 UI/交互类 Bug
4. **浏览器 DevTools / 调试器** — 捕获 Network/XHR、Console 错误、状态检查（调试器 / jdb）
5. **CLI 调用** — 带 fixture 输入，比对 stdout 与已知正确快照
6. **Playwright 无头浏览器脚本** — 驱动 UI，断言 DOM/console/network
7. **重放录制的 trace** — 保存真实请求/事件日志到磁盘，隔离重放
8. **临时测试桩** — 启动最小子系统（一个服务 + Mock 依赖），单函数调用跑 Bug 路径
9. **二分法测试桩** — 如果 Bug 在两个已知状态之间出现，自动化"启动状态 X → 检查 → 重复"以便 `git bisect run`
10. **对比测试** — 同一输入跑旧版 vs 新版，对比输出

### 构建反馈循环的核心原则

- **要有侵略性，要有创造力，拒绝放弃。** 花不成比例的时间在这里。
- **收紧循环**：让它更快（缓存 setup，跳过无关初始化）、信号更清晰（断言具体症状，不是"没崩溃"）、更确定（固定时间，随机种子，隔离文件系统）
- **非确定性 Bug**：目标不是干净的复现，而是**更高的复现率**。循环跑 100 次，并行化，加压力，缩小时间窗口。50% 的 flake 是可调试的，1% 不是。

### 如果实在无法建立反馈循环

停下来，明确说出你尝试了什么。向用户请求：
(a) 能复现的环境访问权限
(b) 保存的 artifact（HAR 文件、日志 dump、core dump、带时间戳的录屏）
(c) 在线上加临时探针的权限

**禁止在没有反馈循环的情况下进入 Phase 2。**

### Phase 1 完成条件

- [ ] 有一个**可复现**的命令——脚本路径、测试调用、curl——你已**至少执行过一次**并看到输出
- [ ] 这个命令能**捕捉用户报告的具体症状**（不是附近的另一个错误）
- [ ] 它是**确定性**的（非确定 Bug：有足够高的复现率）
- [ ] 它是**快速**的（秒级，不是分钟级）
- [ ] 它是**可自动化运行**的

---

## Phase 2 — 复现 + 最小化

运行反馈循环，确认 Bug 出现。然后将复现条件缩小到**最小场景**：逐个削减输入、调用方、配置、数据、步骤，每次削减后重新运行，只保留对 Bug 必需的要素。

**完成条件：** 移除任何一个剩余要素都会让 Bug 消失。

---

## Phase 3 — 假设

在测试任何假设之前，生成 **3-5 个排序的假设**。单一假设会让你锚定第一个合理的想法。

每个假设必须是**可证伪的**：说明它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 将让 Bug 消失 / <改变 Z> 将让 Bug 更严重。"

**向用户展示排序列表，再开始测试。** 用户通常有领域知识可以快速重排。

---

## Phase 4 — 探测

每个探测必须对应 Phase 3 的特定预测。**一次只改一个变量。**

工具偏好：调试器 / jdb 调试器/REPL 检查 > 定向日志 > "全量日志再 grep"

**每个调试日志打唯一标签**，如 `[DEBUG-a4f2]`，结束时一次性清理。

---

## Phase 5 — 修复 + 回归测试

**先写回归测试，再修复。** 但前提是有**正确的接缝**——测试能模拟真实 Bug 模式的接缝。

如果找不到正确的接缝，**这本身就是发现**——代码架构阻止了 Bug 被锁定。

有正确接缝时：
1. 将最小化复现转为失败测试
2. 看它失败
3. 应用修复
4. 看它通过
5. 用原始（未最小化的）场景重新运行 Phase 1 反馈循环

---

## Phase 6 — 清理 + 事后分析

- [ ] 原始场景不再复现（重新运行 Phase 1 循环）
- [ ] 回归测试通过（或记录找不到正确接缝）
- [ ] 所有 `[DEBUG-...]` 探针已移除
- [ ] 一次性原型已删除
- [ ] 正确的假设写入 commit message

**然后问：什么能阻止这个 Bug？** 如果答案是架构变更（没有好的测试接缝、耦合过深），交给 `/arch-review` 技能处理。
