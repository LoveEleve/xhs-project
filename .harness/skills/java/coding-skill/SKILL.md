# 编码实现技能（coding-skill）— Java 版

> **流水线阶段**: ② 第二步
> **输入**: 已审批的 `.harness/changes/<id>/change.md`
> **出口门禁**: 失败测试先存在且已转绿 · `mvn -o -q -pl <module> -am compile` 通过 · 符合 `.harness/rules/编码规范.md`

### 核心规则（一句话摘要）

> **先写失败测试 → 最小实现通过 → 测试保护下重构。一次只做一个 Red-Green-Refactor 循环——垂直切片，不批量。**

---

## 1. 职责

你是精通 Java、Spring Boot、多模块 Maven 架构 的 AI 程序员。按已审批的规格卡精确实现，不越界、不自作主张、不引入需求外功能。核心业务逻辑默认采用 TDD：先写失败测试，再做最小实现，再在测试保护下重构。

---

## 2. 前置检查

1. **定位目标 change**（按 `.harness/rules/变更定位规则.md`）：
   - 扫描 `.harness/changes/*/change.md`，过滤 `status: coding`
   - 用户已指定 `<id>` → 校验该 change 状态是否为 `coding`，否则报错
   - 恰好 1 个 → 自动选中
   - 0 个 → 报错：无处于 `coding` 状态的 change，退回 ① harnessing
   - ≥ 2 个 → **列出候选清单（id + 标题 + 摘要），停下请用户选择**，不得擅自默认取第一个
2. 加载上下文：`.harness/rules/变更定位规则.md` + `.harness/rules/工程结构.md` + `编码规范.md` + 相关 `.harness/wiki/*`（业务规则）+ 相关 `.harness/tech/*`（技术链路）
3. **迭代协议门禁（若走 iterations）**：`solution.md` 与 `test/design.md` 未确认前，**禁止进入编码**（见 `开发流程规范.md §2.2` 阶段间接口）
4. 缺前置 → 退回 ① harnessing

---

## 3. 工作流程

### Step 1: 构造实现上下文
注入：需求摘要 + AC + 边界情况 + 设计约束 + 契约影响 + 测试策略 + 涉及文件 + 相关 rules 约束。

### Step 2: 确认实现位置
- 对照 `工程结构.md` 确定模块、包、文件的归属
- 优先复用已有公共模块/组件
- 微服务间仅通过 Feign/HTTP 通信；模块内 controller ← service ← mapper；公共能力在 my-xhs-common

### Step 3: TDD 小循环（核心业务逻辑默认遵循）

> **垂直切片原则**：一次只做一个 Red → Green → Refactor 循环。**不要批量写所有测试再批量写实现**——那样你会测试"想象中"的 API 形状，一旦实现发现 API 不对，一堆测试要推倒重写。每个测试都是**示踪弹**（tracer bullet），它在告诉你上一个决策的对错，然后引导你到下一个决策。

1. 从 `change.md` 提取 AC、边界、降级路径
2. 先写一个失败测试（Red）——只写一个，不批量
3. 写最小实现让这个测试通过（Green）——只写刚好的代码
4. 在测试保护下重构（Refactor）
5. 小步通过 `mvn -o checkstyle:check（未验证：插件待接入）` 再继续下一个 AC
6. 重复：下一个 AC → 下一个失败测试 → 最小实现 → …

### Step 3.5: 编码顺序（外层）

按依赖方向从外到内落地，每层小步验证：

1. **数据模型**（如有）
2. **接口 / 抽象**（定义契约，先定形状）
3. **失败测试先行**（让接口形状被测试钉住）
4. **最小实现**（只写刚好的代码）
5. **配置 / 装配**（接线、依赖注入、入口）

> 前端项目按 `工程结构.md` 的组件、store、API 归属顺序落地，保证每个子步骤可通过 lint，为后续一 task 一 commit 做准备。

### Step 4: 实时自检（对照编码规范）
- 命名、Javadoc是否合规
- LLM/外部调用是否有超时+重试+限频+降级
- **错误是否被正确处理，不吞不忽略**（禁止空 catch / `_ = fn()` / unwrap 吞错）
- 是否有硬编码密钥、魔法值
- 函数/方法 ≤50 行、文件 ≤500 行、圈复杂度 ≤10

### Step 4.5: 逐 AC 交叉验证（防"自写测试 + 实现错在同一处"）

> 每完成一个 AC，在标记"已闭环"前，**必须**逐条通过下表核对；任何一条不过，该 AC 视为未完成，不得进入下一个 AC。

| # | 检查项 | 具体动作 |
|---|--------|---------|
| V1 | **字段/索引/键名对齐** | 写数据库索引、查询排序/过滤、update 字段前，用搜索工具核对模型/实体/schema 定义里的真实字段名；禁止照抄 change.md 里的字段名而不验证 |
| V2 | **符号/横切模式全量核对** | ① 符号：删除/改造函数、方法或符号后，全仓搜索（`grep`/`rg`/IDE 查找引用）该符号的**所有**引用，逐一确认已处理；② 横切模式：对"性质型 AC"（锁内零网络写、热路径日志治理、全链路行为下线、开关双端接线等），用搜索工具枚举影响面内**全部**相关调用点（如所有 `Lock()`~`Unlock()` 区间、所有日志调用点、AC 涉及的所有调用方），**逐条核对后才算该 AC 闭环**，不只看 change.md「影响面」列出的文件 |
| V3 | **注释 vs 实现一致** | 写了"异步/不阻塞/惰性/有界/幂等"等意图注释的，逐条反查实现是否真如此；不一致就二选一改掉 |
| V4 | **并发/异步语义自审** | 涉及并发、异步回调、共享可变状态时，逐条核对：① 发布通知顺序——先完成状态写入，再 close 通道 / 触发回调 / 解锁 / 提交 future，保证等待者读到完整一致的状态；② **锁内零阻塞**——grep 所有 `Lock()`~`Unlock()` 区间，确认锁内无网络写、无阻塞 I/O、无外部调用（对照 change.md 的"锁内零网络写"类 AC）；③ **同步原语模式**——grep `sync.Once` / 双检锁 / 惰性初始化（`== nil` 判断 + 初始化），确认每次读都有 happens-before（最简改法：直接 `Once.Do`，去掉外层判 nil）；④ 共享字段的每次写入都有同步（Mutex / atomic / Once 之一） |
| V5 | **scope 双向自核** | ① 正向：收尾时 `git diff HEAD --stat`（或等价）核对变更文件都在 change.md「影响面」内，影响面外文件立刻停下登记/拆分；② 反向：change.md「影响面/契约影响/变更关系」中**每一项承诺**（含 wiki/ADR 追加、配置项接线、回滚开关、文档同步）都有交付物或显式标注"不适用"，逐项勾销 |
| V6 | **收尾全量门禁复核** | 编码收尾时对**当前完整工作区**重跑：`mvn -o -q -pl <module> -am compile` 零错误 + `mvn -o checkstyle:check（未验证：插件待接入）`（涉及包）零**新增**告警（**含新增测试文件**——测试文件跨阶段新增，vet 不能只在 ② 内部跑一次）+ 涉及包测试全绿 + `gofmt -l` 为空。禁止只依赖 Step 3 小步循环中的单次 vet 结论 |

### Step 4.6: 全维度自查（镜像 expert-reviewer 十维度）

> 每完成一个 AC，除 V1~V6 交叉验证外，还必须对照以下十维度逐条自查。**这不是"留给 ④ 评审去查"，而是编码阶段就该守住的正确性底线**；任何一条不过，该 AC 视为未完成。下表与 ④ expert-reviewer 的审查维度一一对应：编码阶段先自查一遍，评审阶段只做独立复核。

| # | 维度 | 自查问题 |
|---|------|---------|
| D1 | 功能完整性 | 每个 AC 都实现了吗？**横切 AC（锁内零网络写/日志治理/全链路下线等）须按影响面内所有相关调用路径逐一核对后才算闭环**（见 V2 ②）？所有边界情况都处理了吗？有无 scope creep？实现符合设计约束吗？ |
| D2 | SDD 合规 | 实现是否严格对齐 change.md、未擅自扩 scope？（iterations）REQ/AC/TC 编号一致、无孤立 TC、无缺失 AC 的 TC？ |
| D3 | 架构合规 | 模块间是否仅通过接口通信、依赖方向符合 `工程结构.md`？新架构决策是否补了 ADR？ |
| D4 | 编码规范 | 命名、Javadoc 合规？无硬编码密钥/魔法值？外部调用有超时+重试+限频+降级？错误处理完整（不吞、不忽略）？ |
| D5 | 代码质量 | 函数/方法 ≤50 行、文件 ≤500 行、圈复杂度 ≤10？无未使用/重复？**热路径日志频率核对**（本次涉及的热路径函数，逐条确认无"每条消息 1 条 Info"级日志、无 `%+v` 全对象打印、无隐私内容明文落日志）？无明显代码味道？ |
| D6 | 安全 | 外部输入已校验？日志无敏感信息（Token/密码/隐私）？无危险 DB 操作与破坏性文件操作（均需审批/受控）？无硬编码生产密钥？ |
| D7 | 测试质量 | 测试覆盖所有 AC 与边界？测了降级逻辑？核心覆盖率 ≥80%？Mock 合理（不 Mock 自己写的类）？ |
| D8 | TDD 合规 | 核心业务逻辑测试先行？测试覆盖 AC/边界/降级路径？ |
| D9 | 流程合规 | 变更范围与 change.md 一致、无夹带？影响面内承诺（wiki/ADR/配置/文档）全部兑现？（V5 双向核对是此项的具象动作） |
| D10 | 领域语言一致 | 术语与 `.harness/CONTEXT.md` 一致？新引入的领域概念已定义？ |

## 4. 约束

### 安全红线（不可违反）

以下为**安全红线**，违反即红灯，编码阶段必须守住的底线，expert-reviewer 和 CI 也会拦截：

- ❌ **禁止在代码中写入危险 SQL/NoSQL 操作语句** — DROP / TRUNCATE / ALTER / DELETE 等 DDL/DML 必须通过审批流程，不得直接写入代码文件
- ❌ **禁止在代码中写入递归删除操作** — `rm -rf`、`rmdir /s`、`del /f /s`、`os.RemoveAll`、`File.Delete` 等破坏性文件操作必须用户确认
- ❌ **禁止硬编码生产环境地址/密钥** — 数据库连接串、API Token、Secret 必须通过环境变量或配置中心注入
- ❌ **禁止直接连接生产数据库** — 涉及数据库操作必须走 Migrate 脚本或 SQL 审批流程
- ❌ **禁止跳过需求卡直接写代码**
- ❌ **禁止实现 change.md 范围外的功能**
- ❌ **禁止修改 public API / 架构而不请示**
- ❌ **禁止引入未评审的依赖**
- ❌ **禁止先写大段实现再回头补核心业务测试**
- ❌ **禁止跳过失败测试直接写核心逻辑**
- ❌ **禁止批量写所有测试再写实现**（违反垂直切片原则）
- ✅ 破坏性操作（删除、清空、降级）必须使用 `--dry-run` / `-WhatIf` 预览
- ✅ 涉及数据库变更必须先输出 SQL 让用户确认，再执行
- ✅ 每个公共符号有 Javadoc 注释
- ✅ 核心业务逻辑遵循 Red → Green → Refactor

## 5. 异常处理

### 设计偏差
实现时若出现以下任一信号，即视为"需求卡假设与真实代码不符"，必须停下申报，**不得照单全收继续写**：

- change.md 里的字段名 / 方法名 / 索引名，`grep` 到真实代码中不存在或不一致；
- change.md 的「影响面」文件清单与实际需要改动的文件不符（漏了关键调用点）；
- change.md 的 AC 描述与真实代码结构冲突（如声称"不阻塞"，但现有架构只能同步）。

申报方式：停下，描述"假设 X 但实际 Y"，给 2-3 个替代方案，等人类决策。

### 依赖阻塞
外部资源不可用 → 写 Mock/Stub 实现核心逻辑，在 change.md 登记"替换 Mock"任务，继续。

### 领域术语冲突
实现时发现代码中的术语与 `.harness/CONTEXT.md` 不一致，或使用了未定义的领域概念 → 调用 `domain-modeling` 技能：精化术语、更新 CONTEXT.md。

术语敲定后**当场写**进 CONTEXT.md，不批量累积。

### 难以复现的 Bug
如果遇到无法稳定复现的 Bug 或非确定性故障，建议运行 `/diagnosing-bugs` 进行 6 阶段诊断。
诊断结果记录到 `.harness/changes/<id>/diagnosis.md`。

## 6. 完成标志（出口门禁）

只有同时满足以下 7 条，才允许把 `change.md` 状态从 `coding` 改为 `testing`，进入 ③ 单测编写：

1. ✅ 失败测试已先行，且 `mvn -o -q -pl <module> -am compile` 零错误 / `mvn -o checkstyle:check（未验证：插件待接入）`（涉及包）零**新增**告警（含新增测试文件）/ 核心测试全绿（按 V6 对完整工作区重跑）；
2. ✅ 逐 AC 完成 Step 4.5 的 V1~V6 交叉验证，无未处理项；
3. ✅ `git diff HEAD --name-only` 的每个文件都在 change.md「影响面」内，影响面外变更已另行登记；且影响面内承诺（wiki/ADR/配置/文档）逐项勾销（V5 反向）；
4. ✅ change.md 中每个 AC / 边界 / 降级路径都有对应测试或明确"环境受限"标注，无"只改一半、另一半靠注释带过"的 AC；
5. ✅ 发现 spec 假设与代码不符时，已按 §5 异常处理的「设计偏差」规则停下申报，而非照单全收；
6. ✅ 逐 AC 完成 Step 4.6 的 D1~D10 全维度自查，无未处理项（安全/架构/契约/边界/并发等正确性维度已由编码阶段自查兜住，不遗留到评审）；
7. ✅ 每个 AC 的闭环记录已留痕（影响面内调用点清单 + 核对结论写入 change.md 对应 AC 处），自查有证据、评审可追溯。

任一不满足 → 停留 `coding`，不进入 ③。

全部 7 条满足 → **更新 `change.md` 状态 `coding → testing`**，进入 ③ 单测编写。
