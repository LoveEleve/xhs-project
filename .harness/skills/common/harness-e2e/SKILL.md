# Harness E2E — 端到端测试

基于 `.harness/changes/<id>/change.md` 的验收标准，生成或执行**端到端用例**——从用户入口出发，穿过真实接口/服务/存储，验证整条业务链路。

> **定位**: 与 `unit-test-write`（单测）互补。单测验证"模块内正确"，E2E 验证"跨模块/跨服务串起来正确"。`harness-quality` 的 flow→test 映射矩阵里，关键业务流的直接测试可由 E2E 承担。

---

## 1. 何时使用

- change 的 AC 涉及跨模块/跨服务链路（如"下单 → 扣库存 → 发消息 → 出账单"）
- `harness-quality` 映射矩阵发现某条业务流无端到端覆盖
- 回归前验证核心主链路（冒烟级 E2E）

## 2. 前置

1. 按 `.harness/rules/变更定位规则.md` 定位目标 change（`status: verifying` 或 `done` 均可用）。
2. 确认服务可运行：从语言包 `deploy-verify` 技能的命令段读取启动命令（apply-harness 渲染该技能时已填充实际命令值），启动 dev 环境（或已有测试环境）。
3. 加载 `.harness/wiki/接口协议.md` + `数据模型.md`，理解链路中的契约。

## 3. 执行流程

### Step 1: 提取链路
从 change.md 的 AC + 影响面，列出需要验证的**主链路**与**降级链路**（每条链路一个入口动作 → 关键中间步骤 → 期望终态）。

### Step 2: 生成用例（写 `.harness/changes/<id>/e2e.md`）

对每条链路输出用例卡：

```markdown
## 用例 E2E-<n>: <链路名>
- 前置: <数据/服务状态准备>
- 步骤:
  1. <入口动作（接口/UI/消息）>
  2. <中间步骤>
  3. <中间步骤>
- 期望终态:
  - <结果 1（响应/数据落库/消息发出）>
  - <结果 2>
- 验证方式: <真实调用 / 自动化脚本>
```

### Step 3: 执行
- **优先自动化**：写成可执行脚本/测试（用语言包 `unit-test-write` 技能里已渲染的测试框架与工具，或 curl/HTTP 脚本），真跑并记录**真实退出码与输出**。
- 无法自动化的步骤：列出精确手动操作步骤（点击顺序、输入值、API 参数），标注待人工执行。
- 执行后逐条核对期望终态，产出结果表：

| 用例 | 结果 | 证据（输出/退出码） |
|------|------|-------------------|
| E2E-1 主链路 | 🟢 / 🔴 | <真实输出摘要> |
| E2E-2 降级链路 | 🟢 / 🔴 | <真实输出摘要> |

### Step 4: 结论
- 全 🟢 → 更新 `change.md` 状态（`verifying → done`，若部署验证通过）。
- 有 🔴 → 如实记录失败点与复现信息，退回对应阶段（编码/集成），**不得按通过处理**。

## 4. 铁律

- **真跑才算数**：E2E 用例必须真实执行并留证据，禁止"我看了一下应该没问题"替代。
- **主链路必测**：每次 change 影响的主链路必须有 E2E 用例（或已有用例覆盖），不因"改动小"而跳过。
- **失败如实报**：E2E 失败就是红灯，退回修复，不降低标准放行。

## 5. 与相邻技能

| 场景 | 归属 |
|------|------|
| 单测 | `/unit-test-write` |
| 部署冒烟/健康检查 | `/deploy-verify` |
| 质量判定 + flow→test 对账 | `/harness-quality` |
| E2E 用例生成/执行 | **本技能**（`/harness-e2e`） |

## 完成标志

- 用例卡已落盘 `.harness/changes/<id>/e2e.md`
- 用例已执行并留真实证据（退出码/输出），结果表已产出
- 主链路与降级链路均 🟢（或 🔴 已如实记录并退回）
