# Domain Modeling — 领域语言维护

**主动**构建和打磨项目的领域模型。这是"主动的纪律"——挑战术语、发明边界场景、在术语/决策成型的**当下**写进 CONTEXT.md 和 ADR。仅仅"读 CONTEXT.md 取词"不算本技能——那是任何技能都能做的一行习惯。**本技能用于"改变模型"，不是"消费模型"。**

---

## 文件结构

多数项目是单上下文：

```
.harness/
├── CONTEXT.md          ← 领域语言（活词典）
├── CONTEXT-FORMAT.md   ← 编写规范
└── wiki/
    ├── 架构决策.md      ← ADR 列表入口
    └── ADR-FORMAT.md   ← ADR 编写规范
```

若根目录存在 `CONTEXT-MAP.md`，则是多上下文项目，映射各上下文所在位置与关系。

**惰性创建**：只有有内容可写时才建文件。首个术语敲定时才建 CONTEXT.md；第一个 ADR 需要时才建对应条目。

## 会话中的主动动作

### 对照词表挑战术语

当用户使用的术语与 `CONTEXT.md` 已有语言冲突时，**立即指出**：
> "你的词表定义 'cancellation' 为 X，但你似乎指的是 Y——到底是哪个？"

### 精化模糊语言

当用户用了含糊或过载的词，提出一个精确的规范词：
> "你说 'account'——你指的是 Customer 还是 User？两者是不同的东西。"

### 用具体场景压测领域关系

当讨论领域关系时，用具体场景做压力测试。编造能触及边界的场景，逼用户在概念边界上精确。

### 与代码交叉验证

当用户描述某机制如何工作时，检查代码是否同意。发现矛盾就表面化：
> "你的代码取消整个 Order，但你刚说支持部分取消——哪个是对的？"

### 当场更新 CONTEXT.md

术语敲定后**当场**写进 CONTEXT.md，不批量累积。遵循 `CONTEXT-FORMAT.md` 的规范。

CONTEXT.md 应**完全不含实现细节**。不要把它当规格、草稿或实现决策仓库。它只是术语表，仅此而已。

### 克制地提供 ADR

只有当三个条件**全都满足**才建议创建 ADR：

1. **难逆转** — 改主意成本高
2. **脱离上下文会惊讶** — 未来读者会疑惑"为什么这么搞"
3. **真实权衡** — 有真正替代方案，你选了其中一个有特定理由

任一缺失，跳过 ADR。遵循 `ADR-FORMAT.md` 的规范。

## 与流水线技能的联动

| 触发场景 | 动作 |
|---------|------|
| `harnessing` 遇到模糊术语 | 调用本技能精化并写 CONTEXT.md |
| `coding-skill` 发现代码与 CONTEXT.md 矛盾 | 调用本技能修正术语 |
| 做出满足 ADR 条件的设计决策 | 调用本技能写 ADR |
| `expert-reviewer` 发现代码与领域语言不一致 | 标注为问题项 |

## 完成标志

- 术语敲定后 CONTEXT.md 已更新（当场，不批量）
- 满足条件的架构决策已补 ADR
- 代码与领域语言无矛盾
