# Harness Quality — 质量闸门与报告

跑真实 check → 对照质量目标 → 出可核对的报告 → **人签字放行**。

> **定位**: 与 `/unit-test-ci` 的分工——`unit-test-ci` 是**机械化执行**全量门禁（编译/静态分析/架构约束/测试/安全），本技能在其之上做**客观判定 + 可追溯 + 人签字**：一切判定来自真实数据，AI 只整理报告，**放行由人**。

---

## 立身之本

**一切判定来自客观数据**：覆盖率数字来自覆盖率工具、E2E 覆盖来自 flow→test 映射 + 真跑结果、lint 来自退出码。

**AI 只负责把这些数据整理成报告，不参与"达标与否"的判定**，放行由人。

> ⛔ 绝不允许出现的行为：
> - 用"我看了一下代码，测试挺全的"这类判断替代真实数据
> - 用上一次的结果冒充本次
> - 命令没跑通却按通过处理
> - 覆盖率没测量却写一个数字
> - **量不到就如实写"未测量"**——这与"无命令可跑 → 该项不判定"是同一条纪律

## 1. 前置：两份真源

| 文件 | 作用 | 缺失时 |
|------|------|--------|
| `.harness/rules/开发流程规范.md` + 语言包 `unit-test-ci` 技能内的命令段 | **怎么量**（命令：TEST_CMD / COV_CMD / LINT_CMD / ARCH_TEST_CMD / SECURITY_CMD 等，已按语言渲染） | 中止，提示先跑 `/apply-harness` 或 `/unit-test-ci` 确认命令可用 |
| `.harness/quality-targets.yml` | **目标值**（覆盖率阈值、lint 阈值、flow→test 覆盖要求） | 提示创建（见 §2），或使用默认目标 |

### quality-targets.yml 模板

```yaml
# .harness/quality-targets.yml
core_coverage: 0.80        # 核心逻辑覆盖率阈值
total_coverage: 0.60       # 全量覆盖率阈值（可选）
lint_violations: 0         # lint 违规数上限
flow_test_required: true   # 每条业务流必须有对应测试
danger_ddl_dml: 0          # 危险 DDL/DML 命中数上限（必须为 0）
hardcoded_secrets: 0       # 硬编码凭据命中数上限（必须为 0）
```

首次运行本技能且该文件不存在 → 用上表默认值创建，并提示人类确认目标（目标调整属人类决策，AI 不得自行放宽）。

## 2. 执行流程

### Step 1: 锁定范围
- 按 `.harness/rules/变更定位规则.md` 定位目标 change（`status: ci` 或人工指定任意 change）。
- 若为全项目质量体检 → 使用 `git diff` 或指定版本区间作为范围，报告开头标注范围。

### Step 2: 跑真实 check（机械执行）
逐条运行 `unit-test-ci` 命令段中的命令（或直接调用 `/unit-test-ci <id>` 收集其输出），**记录每条的真实退出码与原始输出**：
- 编译 / 静态分析 / 竞态 / 架构约束 / 单测 / 覆盖率 / 安全扫描
- 覆盖率用覆盖率工具真实测量（`COV_CMD`），**不读文档、不估算**

### Step 3: flow→test 映射矩阵（核对业务流覆盖）
对 `change.md` 的**每条验收标准 AC** 建立映射：

| 业务流 / AC | 触发入口 | 对应测试（文件:用例） | 状态 |
|-------------|---------|---------------------|------|
| AC-1: <描述> | <接口/入口> | <测试文件>:<用例名> | 🟢 已覆盖 / 🔴 无测试 / ⚠️ 仅间接覆盖 |

- **判定**: 每条 AC 必须有**直接对应的测试**（单元/集成/E2E 均可）。AC 存在但无测试 → 🔴 红灯。
- **对账**: 把 `change.md` 的 AC 清单与测试文件列表逐条对账，**漂移即红灯**——实现里的行为在 AC 中没有、或 AC 中的行为没有测试，都算漂移。

### Step 4: 出报告
产出 `.harness/changes/<id>/quality-report.md`：

```markdown
# 质量报告: C-NNN

## 范围
<变更范围 / 版本区间>

## 客观数据
| 检查项 | 真实结果 | 目标 | 判定 |
|--------|---------|------|------|
| 编译 | 0 error | 0 | 🟢 |
| 覆盖率（核心） | 82% (工具: <COV_TOOL>) | ≥80% | 🟢 |
| lint | 3 违规 | 0 | 🔴 |
| flow→test 映射 | 4/5 AC 有直接测试 | 全覆盖 | 🔴 |
| 硬编码凭据 | 0 | 0 | 🟢 |
| 未测量项 | — | — | ⚪ 未测量（如实标注） |

## 达标判定
- 是否全部达标：✅ / ❌
- 未达标项清单 + 差距数据（不写"感觉不够好"这类主观话）

## 放行签字
- [ ] 我（人类）确认以上数据属实，允许进入下一步（/unit-test-ci 全绿后 /deploy-verify）
- [ ] 我（人类）拒绝放行，理由: <…>
```

### Step 5: 人签字放行
- 把报告呈现给人类，**请其明确签字**（同意放行 / 拒绝并给理由）。
- AI **不得**代替人类勾选放行。未获签字 → 状态保持在 `ci`，不进入 `verifying`。
- 人类拒绝 → 按理由退回对应阶段（编码/补测试/改目标），并记录到报告。

## 3. 与相邻技能边界

| 场景 | 归属 |
|------|------|
| 机械化跑全量门禁 | `/unit-test-ci` |
| 代码双轴评审（Spec/Standards） | `/expert-reviewer` |
| 质量判定 + 报告 + 人签字 | **本技能**（`/harness-quality`） |
| 测试地基（命令真跑验证） | `/harness-test-setup` 纪律（apply-harness 已内置） |

## 完成标志

- 报告已落盘 `.harness/changes/<id>/quality-report.md`，全部数据来自真实运行
- flow→test 映射已逐条对账，漂移已红灯
- 已获得人类签字（放行或拒绝），未代签
