# Harness API Mock — API Mock 数据生成

按 `.harness/wiki/接口协议.md`（或 change.md 的「契约影响 · REST」）生成 **mock 数据与 mock 服务**，使前后端可并行开发、联调不阻塞。

> **定位**: 服务于联调与测试——后端接口未实现时，用 mock 把契约固定下来，让前端可先行开发，让测试可先跑通。mock 数据必须**忠于接口协议**（字段名/类型/枚举/错误码一致），否则联调时假数据反而误导。

---

## 1. 何时使用

- 前后端并行开发，后端接口未就绪
- change 定义新接口，需要先行验证前端/链路
- E2E/集成测试需要稳定的测试数据（脱离真实下游依赖）

## 2. 前置

1. 定位接口来源：`.harness/wiki/接口协议.md`（首选）或 change.md 的「契约影响 · REST」。
2. 确认接口清单：路径、方法、请求/响应结构、错误码、鉴权方式。

## 3. 执行流程

### Step 1: 提取契约
列出需要 mock 的接口，对每个接口记录：
- 路径 + 方法
- 请求参数（query/path/body）与校验规则
- 响应结构（成功/失败/异常分支）+ 状态码
- 依赖的外部调用（是否需 mock 下游）

### Step 2: 生成 mock 数据
对每个接口生成**多种形态**的 mock 响应：

| 分支 | 示例数据 | 用途 |
|------|---------|------|
| 正常成功 | <符合契约的完整响应> | 主流程 |
| 空数据 | <空列表/空对象> | 空态 UI |
| 边界值 | <最大/最小/超长/特殊字符> | 边界校验 |
| 错误分支 | <业务错误码 + 错误信息> | 错误处理 |
| 鉴权失败 | <401/403 响应> | 权限拦截 |

**纪律**：
- mock 字段名、类型、枚举值**逐字对照接口协议**，不自由发挥
- 响应必须包含真实接口会返回的字段（含 `code`/`message`/`data` 包裹结构，按项目约定）
- 随机数据使用固定的种子（seed），保证可复现

### Step 3: 落地 mock 服务
按项目可用能力选择方式（参考语言包已渲染技能中的 mock 工具——即 apply-harness 参数表 `HTTP_MOCK_UTIL` 所对应的实际工具）：
1. **内嵌 mock server**：轻量脚本/服务（如 mock 框架），按契约文件返回数据
2. **mock 数据文件**：JSON/fixture 文件，供前端直接 import 或测试加载
3. **网关/代理层 mock**：在开发网关配置 mock 路由

产出 `.harness/changes/<id>/api-mock.md`：接口→mock 数据文件的映射表 + 启动方式。

### Step 4: 校验
- mock 响应能通过契约校验（字段/类型/枚举）
- 启动 mock 服务后，至少一个真实请求能打到并返回预期数据（**真跑一次**）
- 更新「契约影响 · REST」或接口协议文档，标注接口 mock 状态（`mock` / `real`）

## 4. 纪律

- **忠于契约**：mock 数据不得与接口协议矛盾，否则联调必踩坑
- **分支齐全**：不只 mock 成功分支，错误/边界分支也要覆盖（前端才测得到）
- **可复现**：随机数据带种子，测试不 flaky
- **标注状态**：mock 与 real 接口在文档中明确区分，防止误以为接口已实现

| 场景 | 归属 |
|------|------|
| API mock 数据生成 | **本技能**（`/harness-api-mock`） |
| 接口协议维护 | `domain-modeling` / wiki |

## 完成标志

- 契约接口均已生成 mock 数据（含成功/空/边界/错误/鉴权分支）
- mock 服务可启动，至少一个真实请求验证通过
- `api-mock.md` 已落盘，接口 mock 状态已标注
