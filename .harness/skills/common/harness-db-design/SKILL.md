# Harness DB Design — 数据库设计

从 `.harness/changes/<id>/change.md` 的需求与验收标准，产出**数据模型设计**：实体 → 表结构 → 索引 → 约束 → 迁移脚本，并把设计沉淀到 `.harness/wiki/数据模型.md` 与迁移文件。

> **定位**: 与 `database-migration-toolkit` 分工——本技能负责**设计**（表结构/关系/索引该长什么样），`database-migration-toolkit` 负责**执行**（把设计落地为可回滚的迁移脚本并执行）。两者配合：本技能产出设计后，迁移脚本通常也一并生成（或交给 toolkit 落地）。

---

## 1. 何时使用

- change 新增/修改业务实体、关联关系、状态流转、字段
- 涉及索引、唯一约束、外键、级联策略
- 需要评估存量表迁移（加字段/改类型/拆表/归档）

## 2. 前置

1. 按 `.harness/rules/变更定位规则.md` 定位目标 change（`status: analyzing` 或 `coding`）。
2. 加载 `.harness/wiki/数据模型.md`（若存在）——理解**存量模型**，新设计必须与之兼容。
3. 读取 `change.md` 的「验收标准」「边界情况」「契约影响 · 数据模型」。

## 3. 执行流程

### Step 1: 识别实体
从 AC 与用户故事提取实体（名词），确定实体间关系（1:1 / 1:N / M:N）与基数。

### Step 2: 表结构设计
对每个实体输出：

| 字段 | 类型 | 约束（PK/FK/UNIQUE/NOT NULL） | 默认 | 说明 |
|------|------|-------------------------------|------|------|
| id | <DB 主键类型> | PK | auto | 主键 |
| <字段> | <类型> | <约束> | <默认> | <说明> |

设计要点：
- **主键**：优先自增/雪花/UUID（按项目约定，见 `编码规范.md`），禁止用业务字段做主键
- **索引**：查询条件列加索引；组合索引遵循最左前缀；禁止无索引的全表扫（除非表极小）
- **约束**：业务不变式用 CHECK/UNIQUE 表达；外键按项目约定（如 MyBatis-Plus/JPA 生态常约定逻辑外键 + 应用层校验）
- **软删除**：如项目约定 `deleted` 字段，全表统一
- **时间字段**：`created_at` / `updated_at` 统一命名与默认值

### Step 3: 变更评估（对存量表）
若改动存量表，列出**兼容性清单**：

| 存量表 | 变更类型（加字段/改类型/拆表/归档） | 是否破坏性 | 迁移策略 |
|--------|----------------------------------|-----------|---------|
| <表> | <变更> | 🟢 兼容 / 🔴 破坏 | <先加字段后回填 / 新表+切换+删旧> |

**铁律**：破坏性变更（删列/改类型/改约束）必须先评审、可回滚、避开高峰，禁止直接 `DROP`。

### Step 4: 落盘
1. 更新 `.harness/wiki/数据模型.md`：实体关系图（Mermaid erDiagram）+ 表结构 + 变更记录。
2. 生成迁移脚本（或调用 `database-migration-toolkit` 落地）：命名含版本号与变更 ID（如 `V<c>__C-0NN_<desc>.sql`），含 `up` 与 `down`（回滚）。
3. 在 `change.md` 的「契约影响 · 数据模型」补充本次模型变更摘要。

## 4. 自检清单

- [ ] 每个实体有明确主键，索引覆盖查询路径
- [ ] 无破坏性变更未标注/未评审
- [ ] 迁移脚本含回滚（down）
- [ ] `数据模型.md` 已同步，无"代码改完了文档还是旧的"

## 5. 与相邻技能

| 场景 | 归属 |
|------|------|

## 完成标志

- 表结构/索引/约束已设计并自检通过
- `数据模型.md` 已更新（含 erDiagram 与变更记录）
- 迁移脚本已生成（含回滚），或已交 `database-migration-toolkit` 落地
