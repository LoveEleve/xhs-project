> **完成记录（2026-10-16）**：四阶段全部落地（分摊落库 → 售后挂行 → 拆单 → 履约下沉）。

> 运行时验证（真实 Redis/MySQL/MQ）按项目规则后置。

## 用户故事

作为订单域开发者，我想要把单层订单升级为"父单/子单/行三层 + 行级售后 + 分摊落库"，以便系统能正确表达"一次支付 = 多份履约"（多商家）、支持行级退款与结算，且不降低现有可靠性内核。

## 非目标（Out of Scope）

- 换货售后；商家结算/分账；前端展示改造（记录）；自动确认收货/售后时效；排队削峰

## 验收标准

- AC-1 ~ AC-10 见 `.harness/iterations/ITER-001-订单拆单与行级售后/prd.md`（本变更走迭代协议，AC 以 prd.md 为准）

## 边界情况

- 同 SKU 两行下单 → 拒绝（保持现有规则）
- 支付回调 vs 关单竞态 → false 业务拒绝 + 自动退款（06 §4.3 保持）
- status=2 全退 → 收敛到 5（修复 08 §5.2 缺口，方式见决策点 1）
- 聚合重算并发 → CAS + 重试，最终收敛

## 非功能需求

| 维度 | 指标 |
|------|------|
| 性能 | 详情 ≤ 3 次批量查询；无 N+1；下单拆单 O(行数) |
| 可靠性 | 幂等/竞态/补偿/对账全链路保持；聚合最终收敛 |
| 安全 | 归属校验与服务端金额重算保持 |

## 设计约束

- 四阶段实施（分摊落库 → 售后挂行 → 拆单 → 履约下沉），禁止 big bang
- 生产标准：业务/工程/分布式/微服务/性能全维度；业务流程与结果正确优先
- 不改文章正文（只记录修订清单：`docs/学习/订单-改造/02-改造后文章修订记录.md`）

## 契约影响

- REST: `/api/order/deliver`、`/confirm` 改子单维度；订单详情/列表响应增子单/行；售后 apply 改 item 维度
- 模块间通信: 终结事务消息扩展为"全子单取消"；支付回调/退款收敛契约保持
- 数据模型: t_sub_order（新）、t_order_item（+sub_order_id/seller_id/discount_share）、t_aftersale（+item_id）、t_sku（+seller_id）
