# C-002 支付模块生产化改造

## 用户故事

作为支付域开发者，我想要把支付模块从"mock 可用"升级到"生产形态"（支付单复用 / 退款出金幂等 / 超时处置按渠道真相），以便学习的是最终形态、不再二次返工，且资金安全链路达到生产标准。

## 非目标（Out of Scope）

- 真渠道 SDK 接入与回调验签（无 HTTP 回调端点；模拟器直调 service——接入真渠道时补，记录）
- 结算域改造（已达标：日切/三方对账/差异挂账）
- 对账体系扩展（11 已记录）

## 验收标准

- AC-1 ~ AC-8 见 `.harness/iterations/ITER-002-支付模块生产化改造/prd.md`（本变更走迭代协议）

## 边界情况

- 并发发起支付 → 唯一索引兜底（DuplicateKey → 重查复用）
- 渠道不可达 → 不处置、留下一轮（"不知道"≠"没付"）
- 无幂等键的历史调用方 → 兼容现行为（记日志）
- 订单终结与支付回调竞态 → 沿用既有 false 语义

## 非功能需求

| 维度 | 指标 |
|------|------|
| 性能 | 复用路径不新增 DB 往返；超时扫描保持游标批处理 |
| 可靠性 | 幂等（唯一索引 + 乐观锁 + out 键）；渠道真相优先；可靠性不降级 |
| 安全 | 归属校验保持；出金幂等强化 |

## 设计约束

- 分阶段实施（复用 → 换渠道 → 退款幂等 → 超时生产化 → 咬合与清理），禁止 big bang
- 生产标准：业务/工程/分布式/性能全维度；资金安全正确优先
- 不改文章正文（修订清单更新至 `docs/学习/订单-改造/02`）

## 契约影响

- REST: `/api/payment/pay`（复用语义）；`/api/payment/refund-by-order`（+幂等键）
- 模块间通信: 支付侧**订阅既有 `ORDER_TERMINATION_TOPIC`**（新增消费者，订单侧零改动）关闭 pending；支付回调/退款通知契约不变
- 数据模型: `t_payment`（+`uk_order_pending` 函数索引、+`verify_method`、+status=4 已关闭）；`t_refund`（+`out_refund_no` 唯一索引）

## 影响面

- 模块/服务: my-xhs-payment（主）、my-xhs-order（仅验证，零改动）、my-xhs-common（无）
- wiki: 数据模型（归档时回流）

## 测试策略

- 先写失败测试：复用/唯一索引兜底/幂等退款/超时处置矩阵
- 边界测试：并发发起、渠道不可达、无幂等键兼容
- 回归：全模块基线保持（251+ 全绿）
