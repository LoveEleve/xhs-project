## 用户故事

作为库存域开发者，我想要把库存链路从"近似幂等 + 名不副实的键模型"升级到"**逻辑事件幂等闭环 + 集群正确的单键模型**"，
并补齐 DLQ 兜底/对账 CAS/指标/注释，以便学习的是最终形态，且与订单/支付/商品/购物车/优惠券的改造水准对齐。

## 非目标（Out of Scope）

- **不做"真分片形态"**（桶粒度 tag + 跨节点 + 放弃跨 key 原子）——无集群环境验证、收益无法证明，属演进方向；
- TCC 冻结（判定层/资源层/超时 Job）——项目口径：独立接口能力、未接线，不讲不扩；
- 重型一致方案（CDC 增量对账/水位线）——CAS 条件更新已够（克制）；
- 权限/管理面细节。

## 验收标准

- AC-1 ~ AC-8 见 `.harness/iterations/ITER-008-库存模块生产化改造/prd.md`（本变更走迭代协议）

## 边界情况

- 补发/重试消息（新 msgId）→ **逻辑事件键幂等拦截**（orderId:skuId:action）；未处理过的事件正常处理
- 消费进程崩溃 → 重投 → L1 靠 Lua 逐 SKU 幂等补扣；L2 靠事务内幂等不丢不重；退款回补靠同槽原子脚本不双补
- confirm 时部分 SKU 记录缺失（预扣迟到）→ **写确认标记**（超时任务改判补确认，不释放）
- DLQ 重放 × 重投 → attempt≤3 防循环；超限仅告警（对账兜底）
- 旧键残留（bucket:* 等）→ 部署说明一次性清理（无真实环境）

## 非功能需求

| 维度 | 指标 |
|------|------|
| 性能 | 去桶后预扣路径命令数下降（total+bucket 双写 → 单键单写）；超时 Job SCAN 键数≈在途 SKU 数（有界） |
| 可靠性 | 逻辑事件幂等闭环（补发/重试/崩溃三场景）；零"已付款货被放回"窗口（F12）；零超卖向量 |
| 安全 | 无 |
| 可观测 | 指标补齐（confirm/release/refund/outbox/补偿/对账/DLQ）；注释与部署基准一致 |

## 设计约束

- 产品语义锚定：**允许少卖，绝不允许超卖**；不确定一律向安全方向；
- 集群正确性 = 每个 Lua 脚本全部 KEYS 同 tag（静态可验证，单测断言）；
- 原子性保留：预扣"校验+扣减+记账"单脚本原子、04B 墓碑原子语义不回归；
- 生产标准：业务/工程/分布式/微服务/性能/可观测全维度；不改文章正文（走修订记录）。

## 契约影响

- REST: `ConfirmDeductRequest`/`ReleaseStockRequest` 增 `items[{skuId,quantity}]`（order 侧 Feign Map 载荷同扩）；`StockVO`/`InitRequest` 删 `bucketCount`（product 侧 DTO 同步）
- MQ: 新增 DLQ 重放消费者（3 个 `%DLQ%` 消费组）；无新业务 topic
- 数据模型: 新增 `t_inventory_l2_event`（L2 事务内幂等表）；无其他 DDL
