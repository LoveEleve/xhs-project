# 第04题 | 验证完整性与"假绿"：exitCode=0 不等于通过

> 难度：★★★★★｜频率：★★★★｜区分度：高
> 关键词：假绿、fail-closed、可证伪判定、surefire 汇总、testsRun>0、对抗式自审

## 问题

问题：你的门禁怎么判定通过？为什么"只看 exitCode"是危险的？

## 面试可讲版（五段式）

**① 业界背景**
质量门禁的失效模式里最隐蔽的是**假绿（false green）**：流程显示通过，但实际什么都没验证。典型来源：测试被跳过（`-DskipTests`）、一个测试都没有（surefire 打 "No tests to run" 但 exit 0）、命令写错但恰巧成功、覆盖率报告缺失被忽略。业界原则是 **fail-closed + 可证伪断言**：不能证明"验证发生了"，就不许标成功。

**② 项目选择**
TEST 门禁的判定被设计成三段式：
1. 命令退出码（必要不充分）；
2. **必须解析到 surefire 汇总**（`Tests run: X, Failures: Y, Errors: Z, Skipped: W`）——解析不到 = 测试证据缺失 = 红；
3. **`testsRun > 0`**——0 个测试 = 红。
失败时 reason 带证据（`exitCode=1（testsRun=94, failures=1, errors=0）`），红绿都可复核。COVERAGE 门禁同理解析报告文件，报告不存在/无法解析/无行数据都算红。

**③ 坑**
- **这个规则是我自己 review 时抓出来的**：最初的实现是 `passed = exitCode == 0`，然后我意识到 `mvn test` 在"没有测试"时也是 0；修完补了"无汇总/0 测试"两个用例；
- `mvn -q` 会吞掉 surefire 摘要 → 命令模板明确不用 `-q`（用 `-B -ntp`）；
- 输出截断必须**保尾部**，否则汇总行被截掉会误红；
- 多模块 reactor 的汇总取"最后一段"（单模块精确，多模块是已知局限，见追问）。

**④ 兜底**
- 更深的"假绿"（测试自己造假断言、覆盖率作弊）无法靠 exitCode 层防御，需要评审阶段（双轴评审）和"AC↔测试映射"门禁来兜——后者是设计；
- 判定语义写死在代码并全覆盖测试，不靠人记。

**⑤ 话术**
> "门禁的敌人不是失败，是**假通过**。我的 TEST 门禁不信 exitCode 单独说了算：必须解析到测试汇总，而且测试数大于 0，否则直接红——这就是 fail-closed。"

## 追问与参考回答

**追问1：怎么发现这个问题的？** 对抗式自审：假设"我要让它假绿，最小代价怎么做"，答案就是"让它什么都没跑"。修复后加了反例测试。
**追问2：解析摘要和解析退出码哪个更可靠？** 两者互补：退出码是权威的"本次命令结果"，摘要是"验证发生的证据"；缺一不可。
**追问3：多模块 Reactor 怎么汇总？** 当前取最后一段汇总（单模块精确）；正确做法是解析 surefire XML 报告目录做聚合（设计）。已明确标注局限，不吹精确。
**追问4：跳过测试的显式场景（如编译门禁）怎么办？** 门禁类型不同：COMPILE 门禁只判退出码（它本来就不该跑测试）；TEST 门禁才要求测试证据——**判定规则按门禁类型拆分**。
**追问5：红的时候为什么不直接抛异常？** 失败是门禁的正常输出：要落证据（日志/指标/reason）、要进状态机（FAILED + 可重试），不是异常路径。

## 面试官评分点

**高级开发级**：能说出至少两种假绿来源；判定不只看 exitCode；红时保留证据。
**架构师加分**：fail-closed 原则、判定规则按门禁类型拆分、AC↔测试映射的设计思路、自审方法（对抗式）。
**危险信号**：`exitCode==0` 一刀切；解析失败静默放行；跳过测试的 CI 配置不检查。
