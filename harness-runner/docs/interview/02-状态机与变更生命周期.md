# 第02题 | 状态机与变更生命周期：重入、重试、断点恢复

> 难度：★★★★★｜频率：★★★★★｜区分度：高
> 关键词：自研 FSM、转移表、StageRun 唯一键、attempt 重试、rehydrate、乐观锁、幂等

## 问题

问题：用户点了两次"推进"、进程被杀重启、阶段失败重试——你的变更状态怎么保证不错乱？

## 面试可讲版（五段式）

**① 业界背景**
工作流引擎两条路线：通用 FSM 框架（Spring StateMachine、Temporal）与自研转移表。桥水/SRE 的经验是"**状态机要小、要显式、要可测试**"；AI 流水线还有个特殊要求：**阶段必须有 attempt 语义**（同阶段失败重试要留历史，才能对比分析），这是通用框架不直接给的。

**② 项目选择**
两个对象：`Change`（6 个阶段的生命周期：CREATED → IN_PROGRESS ⇄ PAUSED/FAILED → DONE/CANCELLED，转移表 20 行，唯一事实源）和 `StageRun`（一次阶段执行，唯一键 `(changeId, stage, attempt)`）。
关键设计：
- **重试 = attempt+1**，旧记录保留（可对比红/绿两次的证据）；
- **断点恢复**：持久化 `status + currentStage + version`，重启后从 currentStage 续跑，PASSED 阶段不重复执行；
- **重入幂等**：产物按 `(changeId, type, version)` 递增版本，命令天然可重跑，LLM 调用按 callId 留证；
- **乐观锁**（设计）：`version` 随每次转移自增，写库带 `WHERE version=?`，并发推进时后写者失败。

**③ 坑**
- 非法转移**不许改状态也不许碰 version**——边界测试专门锁这条：异常抛出后 version 与 currentStage 必须原样（否则恢复语义就乱了）；
- `rehydrate`（从持久化恢复）要校验状态一致性：CREATED 不许有阶段、IN_PROGRESS/PAUSED/FAILED 必须有阶段——防脏数据把状态机带偏；
- FAILED 重试必须**回到同一阶段**而不是下一阶段——这个在引擎测试里锁死（尝试 2 从 TEST_WRITE 继续）。

**④ 兜底**
- 并发控制当前只有设计：文件仓储是单写者语义，未实现乐观锁/锁文件；多实例需 DB 适配器；
- 崩溃恢复有专门测试：换引擎实例接着推（`continuesAfterRestart`）；
- 状态与演示：CLI `status` 能看到每次尝试的结果与时间。

**⑤ 话术**
> "状态机我故意只做确定性 FSM：6 个阶段 + 转移表 + attempt 语义，因为它的核心价值是**可恢复、可追责**——每次失败重试都留一代记录，红绿两次可以并排看。"

## 追问与参考回答

**追问1：为什么 Stage 用枚举而不是动态流程？** 6 阶段是产品定义（对应技能包流水线），固定顺序是特性不是缺陷；动态流程会把门禁映射和断点恢复复杂化。
**追问2：怎么防"重复执行已通过的阶段"？** `currentStage` 只前移不回退；恢复时从 currentStage 开始；若显式重跑需要新的 force 语义（未实现，设计里）。
**追问3：为什么不用事件溯源（ES）？** ES 的收益是审计与时间旅行，成本是投影复杂度。我用"状态快照 + 事件流"混合：状态是权威（change.json），事件是审计（events.jsonl）——轻量版 ES。
**追问4：attempt 的上限？** 没有硬上限（人工控制），但每次重试都有记录与证据，可用于统计"哪些门禁最容易反复失败"。
**追问5：PAUSED 语义怎么用？** 人工介入/等外部条件；`advance` 会自动 resume（CLI 里避免"卡死"），状态机层面允许显式 suspend/resume。

## 面试官评分点

**高级开发级**：说清转移表、attempt 唯一键、重试回同阶段；知道非法转移不能动 version。
**架构师加分**：可恢复语义（快照 + 事件）、恢复一致性校验、乐观锁的设计与未实现边界。
**危险信号**：状态用字符串散落各处；重试直接跳到下一阶段；恢复不校验一致性。
