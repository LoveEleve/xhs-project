# 第01题 | 项目定位与架构：为什么把 Markdown 流水线做成 Java 引擎

> 难度：★★★★｜频率：★★★★★｜区分度：高
> 关键词：Harness Engineering、方法论资产 vs 运行时、六模块划分、端口与适配器、CLI 先行

## 问题

问题：面试官看完简历："你这套 harness 体系到底解决什么问题？为什么是 Java 引擎，不是一堆提示词？"

## 面试可讲版（五段式）

**① 业界背景**
AI 写代码之后，瓶颈从"写"变成"信"：业界共识是"生成便宜、验证昂贵"（verification is the bottleneck）。工具生态分两派：提示词/技能包派（Claude Skills、spec-kit、BMAD）解决"怎么约束 AI"；运行时派（CI、Agent 平台）解决"怎么执行与验证"。**缺口在两者之间**：约束是 Markdown，执行是重型 CI，中间没有"可编排、可验证、可追溯"的轻量运行时。

**② 项目选择**
我把它做成两层：**方法论层**（harness 技能包：6 阶段流水线、SDD-TDD、30+ 技能、6 语言参数化）+ **运行时层**（Java 引擎，把 Markdown 流程变成可执行系统）。引擎六个模块：`domain`（状态机，纯 Java）、`assets`（技能资产解析）、`llm`（LLM 编排）、`gate`（门禁执行器）、`engine`（编排 + 证据）、`app`（CLI）。依赖单向：`app → engine → {domain, assets, llm, gate}`。存储走端口（Repository/EventLog/ArtifactStore/LlmCallStore），运行时是文件实现，H2 适配器留口。

**③ 坑**
- 模块边界是硬约束：LLM 概念不许渗进 domain（domain 零依赖），否则单测跑不动、替换供应商伤筋动骨；
- CLI 先行不是偷懒：先证明"一条命令跑完全流程"，服务化（REST/H2）是 stretch——**能演示 > 能吹牛**；
- 门禁是"跑任意命令"，所以绝不能把需求文本拼进命令行——模板来自配置、argv 用 list 形式。

**④ 兜底**
- 当前边界：单机、单语言（Java/Maven）、无多租户；REST/H2 为设计；
- LLM ② 编码闭环、知识库注入、降级/预算未实现；
- 价值证明走真实工程（xhs 15 微服务）而非自造 demo。

**⑤ 话术**
> "我做的是 AI 研发流水线的运行时：把'需求→编码→测试→评审→CI→部署验证'从文档变成可执行的状态机 + 门禁 + 证据链。技能包解决'让 AI 守规矩'，引擎解决'规矩被真的执行并且留下证据'。"

## 追问与参考回答

**追问1：为什么不是 IDE 插件 / GitHub App / SaaS？** 形态取决于验证方式的最佳位置：门禁本质是跑本地工具链（mvn/npm），本地进程隔离最真实（真实退出码、真日志）；SaaS 反而要拉远构建。CLI 是薄壳，REST 是 stretch，核心引擎不变。
**追问2：六个模块是不是过度设计？** 四个模块有独立可测性理由：domain 零依赖（32 单测）、gate 处理进程细节、llm 可 mock、assets 纯解析；合并会让测试金字塔塌掉。app 确实薄，这是有意的（便于换 REST）。
**追问3：为什么存储要抽象成端口？** 三个用途：测试注入（内存/临时目录）、演进（H2/MySQL）、形态切换（CLI/服务）。代价是接口多一层，收益是不改引擎换存储。
**追问4：这项目最大的技术挑战是什么？** 不是状态机也不是 LLM，是**门禁执行器的进程语义**（假死/超时/进程树）和**验证完整性**（假绿）——这两个回答"为什么可信"。
**追问5：和 xhs 项目什么关系？** xhs 是被服务的第一个工程，也是证据来源：真实 93 个测试、真实覆盖率、红→绿演练；不是玩具 demo。

## 面试官评分点

**高级开发级**：能分清"方法论资产"和"运行时"；说清单向依赖与端口含义；知道 CLI 先行是策略。
**架构师加分**：把"验证昂贵"作为架构出发点；模块划分能说出测试/演进收益；主动划边界（未实现列清楚不遮掩）。
**危险信号**：把技能包说成"我发明的框架"却讲不出机制；架构图背不出来；把设计说成已实现。
