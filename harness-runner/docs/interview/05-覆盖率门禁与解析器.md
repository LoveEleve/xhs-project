# 第05题 | 覆盖率门禁与解析器：JaCoCo XML 与 DTD 坑

> 难度：★★★★｜频率：★★★★｜区分度：高
> 关键词：JaCoCo、行/分支覆盖、XML 报告、外部 DTD、XXE、报告级聚合、避免重复跑测试

## 问题

问题：覆盖率门禁怎么判定？为什么解析报告文件而不是控制台输出？

## 面试可讲版（五段式）

**① 业界背景**
覆盖率门禁的两个流派：**解析控制台文本**（快但格式易漂移：mvn 版本/语言/插件都能改输出）与**解析结构化报告**（稳，JaCoCo XML/CSV、Cobertura XML）。另外覆盖率本身有争议：全量阈值对存量项目不公平，业界演进方向是**增量覆盖率**（只卡新代码）。

**② 项目选择**
- **解析 JaCoCo XML**：取报告级 `<counter type="LINE">` 聚合算 `covered/(covered+missed)`，与阈值（0~1）比较；无 BRANCH 计数时不输出 `branchPercent`，避免 `0.0` 误导；报告不存在、无法解析、无行数据三种情况分别给出不同 reason。
- **一条命令拿全证据**：覆盖率命令 = `jacoco:prepare-agent` → `test` → `jacoco:report`，同一份输出顺带解析测试数；CI 阶段用 `COMPILE + COVERAGE` 组合而**不额外跑 TEST 门禁**，避免测试跑两遍（review 时发现的浪费）。

**③ 坑（真踩）**
- **外部 DTD 被拦**：JaCoCo XML 头部有 `<!DOCTYPE report PUBLIC "-//JACOCO//DTD Report 1.1//EN" "report.dtd">`，JDK 安全解析默认禁止读取外部 DTD，直接 `SAXParseException`——表现为"报告明明存在却解析失败"。修法：关 `load-external-dtd`，同时保留 `external-general-entities=false` 等 XXE 防护（安全与可用的平衡）。
- **报告缺失 vs 解析失败**要分开报（前者是配置问题，后者可能是格式/格式版本问题）；
- **产物 createdAt 一致性**：save 返回文件 mtime（而不是 `Instant.now()`），否则"保存的元数据"和"列表读出的元数据"对不上（测试抓出来的）。

**④ 兜底**
- 增量覆盖率、按包/类过滤"核心逻辑"是设计；当前是全局行覆盖率；
- 多模块报告聚合（各模块 jacoco.xml）未做——演示项目按单模块定位；
- 阈值怎么定是项目约定：xhs 实测 22%，我定 20% 作为演示阈值（**不假吹 80%**）。

**⑤ 话术**
> "覆盖率门禁我只认报告文件，不认控制台文本；而且判定有三种红——报告没了、解析不了、没有行数据。踩过最有意思的坑是 JaCoCo 的外部 DTD 被 JDK 安全策略拦掉，报告存在却解析失败——修的时候要同时保住 XXE 防护。"

## 追问与参考回答

**追问1：为什么是行覆盖率不是分支覆盖率？** 行覆盖率对开发者更直观；分支数据能解析出来就带在 metrics 里（有则输出、无则省略），阈值目前卡行覆盖。
**追问2：阈值定多少合理？** 因项目而异：存量项目定"不倒退阈值"（如当前 22% 定 20%），新项目可以卡 80%；业界更优解是增量覆盖率，我列进了设计。
**追问3：为什么用 0.8.12 这种固定插件版本？** 门禁要可复现：插件版本是命令模板常量（`JACOCO_PLUGIN`），不依赖项目是否配置了 JaCoCo；这样"无侵入"给任意工程加覆盖率门禁。
**追问4：项目自己配了 JaCoCo 会冲突吗？** 有风险：重复 prepare-agent 会产生两个 -javaagent。当前命令走 CLI 插件坐标，项目若已绑定 prepare-agent 需换 `report`-only 命令（设计里备注）；xhs 工程未配 JaCoCo，所以直接可用。
**追问5：报告解析失败会不会把好构建判红？** 会（fail-closed）：无法证明覆盖率达标就不许过。这是门禁语义的一致选择。

## 面试官评分点

**高级开发级**：能分清控制台解析 vs 报告解析的取舍；知道 JaCoCo 报告结构；能给出阈值策略。
**架构师加分**：DTD/XXE 的安全与可用平衡；命令组合避免重复执行；增量覆盖率演进思路；不假吹覆盖率数字。
**危险信号**：用正则解析控制台覆盖率；报告缺失静默通过；阈值和实际数据对不上被追问翻车。
