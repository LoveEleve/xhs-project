## 一、验证的边界（最锋利的区）

### 拷打 1 · "假绿"你防住了，那"假测试"呢？ ❗️P1
- 【直球】TEST 门禁要求 surefire 汇总 + testsRun>0，这算严了吗？
- 【应答】防住的是"没跑测试"这类假绿：`mvn test -DskipTests`、空测试集、解析失败——都红。
- 【锥子】那 AI 生成的测试全是 `assertTrue(true)` 呢？测试跑了、数量够、exitCode=0、覆盖率还涨了——你的门禁全绿，但什么都没验证。你这套"验证基础设施"验证了个寂寞。
- 【反杀/认账】**认账。** 机器可判定的边界是"验证发生了"，不是"验证有效"。当前能给的增量：① 技能包 `unit-test-write` 规范（不测 happy path、每 AC 一个测试）——但这是**提示词层约束，不是机器门禁**；② 机器可做的启发式：断言数量下限、AC↔测试命名映射校验（缺映射红）——**设计，未实现**；③ 真正的答案：**变异测试**（PIT）——把变异杀伤率当门禁，AI 写假测试直接暴露，代价是构建时间 ×3~10。结论：这是"验证有效性"的开放问题，我有路线，不吹已解决。
- 【发散】变异测试（PIT/mutation coverage）/ 断言质量分析 / 测试作弊模式库 / LLM-judge 评测的偏差 / AC↔TC 映射协议
- 【证据】`GateRunner.judgeTest()`；技能包 `unit-test-write` SKILL.md；xhs 演练红色数据（`evidence/d4-xhs/`）

### 拷打 2 · 覆盖率 22% + 阈值 20%，不是自欺欺人吗？ ❗️P1
- 【直球】你的覆盖率门禁是怎么定的阈值？
- 【应答】xhs 实测行覆盖 22.0%，演示阈值定 20.0%（"不倒退"口径）。
- 【锥子】按现状倒推阈值 2 个点，这叫**指标粉饰**。而且 Goodhart 定律：一旦覆盖率是门禁，就会被博弈——只测 getter/setter、加排除项、阈值永不上调。你的门禁可能正在教人"刷指标"。
- 【反杀/认账】**部分认账。** 20% 的诚实定位是"演示可跑的软闸门"（存量债只减不增），不是质量目标；但说"防博弈"我做不到。演进设计：① **增量覆盖率**（只卡 diff 涉及的新代码，业界正解）；② 覆盖率**趋势看板**而非单点阈值；③ 阈值分档（新模块 80%，存量模块不倒退）。当前是全局单点阈值——**明说局限**。
- 【发散】diff-cover / 增量覆盖实现（jacoco + git diff 行映射）/ 软闸门与质量趋势 / 指标设计（Goodhart、虚荣指标）/ 技术债治理节奏
- 【证据】`MavenGateCommandFactory`；`evidence/d4-xhs/.../test_report/v1-test_report.md`（22.0% ≥ 20.0%）

### 拷打 3 · "机器验证"的前提是规格正确——但你的规格是 LLM 写的 ❗️P0
- 【直球】AC（验收条件）由 LLM 生成，之后所有门禁都以它为靶子？
- 【应答】① 阶段生成 AC 草案，`AcValidator` 只做形式校验（非空/唯一/可测形式），产物与 prompt/响应全留证。
- 【锥子】这是**循环论证**：用不可信的模型产出"规格"，再用机器验证"实现符合规格"。规格若错，后面全绿也是错（garbage in, garbage out）。你引以为豪的"验证体系"在选择忽略了一个事实：**验证者不能同时是规格的作者**。
- 【反杀/认账】**认账，且认为这是全项目最重要的缺口。** 现状：runner 里 ① 阶段之后**没有人工确认点**——技能包方法论里 ①→② 本来就有"已审批的 change.md"（HITL 是设计的一部分），但运行时没实现审批命令/状态。修复设计（明确）：① 阶段产物状态为 `DRAFT`，新增 `approve` 命令（人打开产物 → 确认/编辑 AC → approve）才允许推进到 ②；未审批推进 = 拒绝。② 长期：双轴评审的 Spec 轴 + AC↔代码映射校验。③ 形式化规格（TLA+/Alloy）不现实，不做但要能讲清为什么不现实。
- 【发散】需求工程（EARS/用例/BDD）/ HITL 审批闭环（xhs 的 Agent 项目里有同类设计）/ 形式化验证适用边界 / GIGO 与"验证的前提"哲学 / 责任归属（谁签字）
- 【证据】`HarnessingTask`、`AcValidator`；技能包 `harnessing`/`coding-skill`（"已审批的 change.md"）；runner 无 approve 命令（**确认缺口**）

## 二、一致性与并发

### 拷打 4 · 状态与证据跨文件——崩溃在中间怎么办？ ❗️P2（当前顺序自洽）
- 【直球】状态变更和产物写入不是同一事务吧？
- 【应答】单文件原子（tmp+ATOMIC_MOVE），跨文件无事务。
- 【锥子】崩溃在"门禁绿 → 写证据 → 改状态"之间，会出现"证据有了、状态没动"或"状态动了、证据没写"——你能接受一个**可追溯性有洞**的变更系统？
- 【反杀/自证】当前顺序是 **write-ahead evidence**：`StageExecutor` 先写 stage-runs/产物/事件，返回后才由 `ChangeEngine` 改状态。崩溃点矩阵：① 阶段执行中崩 → 状态未推进 → 重跑 attempt+1，证据递增不丢；② 写证据时崩 → 状态未推进 → 同上；③ 状态写崩 → 文件要么旧要么新（原子写）→ 旧则重跑、新则继续。**唯一残留窗口**：状态推进后 `CHANGE_DONE` 事件写失败 → 状态 DONE、事件缺一条（可检测、不影响推进正确性）。结论：顺序是有意设计，可正面回答；残留窗口如实说。
- 【发散】单文件原子 vs 跨文件一致（write-ahead log/outbox）/ Temporal 的持久化执行模型 / 崩溃一致性测试（故障注入 kill -9 各阶段）/ 幂等重入设计
- 【证据】`StageExecutor.execute()` 顺序；`ChangeEngine.advance()`；`AtomicFiles`

### 拷打 5 · 两个人同时 advance，你的乐观锁呢？ ❗️P0
- 【直球】你说的乐观锁写在哪？
- 【应答】决策卡里有设计：`UPDATE ... WHERE version=?`；文件实现是单写者假设。
- 【锥子】那就是**没有**。两个 CLI 同时 `advance`：都读到 version=3，都推进一步写回 version=4——丢一次推进；如果一个是 FAILED 重试一个是正常推进，状态直接串线。你连文件锁都没加。
- 【反杀/认账】**认账：乐观锁仅设计未实现。** 可 15 行修的方案：`FileChangeRepository.save` 先读现有 `change.json` 的 version，与待写对象的"期望前驱 version"比较，不一致抛 `ConcurrentModificationException`（等价于文件版 CAS）；再加 `FileLock` 可选。为什么没做：单机 CLI 场景 + 优先把验证链跑通。**列为 P0**（面试被追问时这是最容易被抓的点，要么修要么用"单写者语义"话术兜住）。
- 【发散】文件锁/OS advisory lock / SQLite WAL / 数据库 CAS / 分布式锁与 fencing token / 幂等命令设计（advance 带 expectedVersion）
- 【证据】`FileChangeRepository.save()` 无版本检查（确认）；`docs/03` 决策卡 D2 并发答法

## 三、进程与信任模型

### 拷打 6 · 你的执行器"忠实地"执行任何命令——包括恶意命令 ❗️P1
- 【直球】进程执行器处理了假死/超时/进程树，安全吗？
- 【应答】命令来自配置模板；argv 用 list 形式不过 shell；需求文本不进命令。
- 【锥子】信任模型呢？门禁本质是"跑任意命令"。未来 LLM ② 生成构建/修复命令；即便现在，对一个不受信仓库跑 `mvn test` 就会执行它的 pom 插件（**构建脚本即代码**）。你的执行器没有沙箱、没有用户隔离、没有网络限制、没有资源上限——还事无巨细地给它留全量日志。这不是"执行器"，是"特洛伊木马快递员"。
- 【反杀/认账】**认账，且这是所有 CI 的共性问题，不是本项目独有。** 当前信任边界明确：命令来自操作者/配置（等价于操作者自己敲命令）；对不受信代码跑门禁的风险 = 本地跑 mvn 的风险。设计防线（分层）：① 命令白名单（mvn 的固定 goal 集合）；② 资源限制（cgroup/ulimit：CPU/内存/进程数）；③ 网络隔离（禁网跑测试）；④ 最小权限用户 + 只读挂载；⑤ 容器化 runner（长期）。**不做"安全"的吹嘘，只讲"信任边界 + 路线"。**
- 【发散】沙箱（seccomp/nsjail/bubblewrap/firejail）/ 容器隔离与 gVisor / 构建供应链攻击（postinstall、Maven 插件、依赖投毒）/ SLSA 与可复现构建 / 企业隔离 runner
- 【证据】`ProcessExecutor`（无沙箱）；`GateCommand` / `MavenGateCommandFactory`（模板来源）

### 拷打 7 · 路径穿越修了，那 `--project / --workspace` 呢？ ❗️P2
- 【直球】路径安全你做了什么？
- 【应答】changeId 白名单（`[A-Za-z0-9_-]{1,64}`），探针实测过 `../../evil` 越界并修复。
- 【锥子】白名单只挡 ID；`--workspace /etc` 就往系统目录写，`--project` 指向任何目录都行；artifact 路径由 `type` 枚举决定所以安全，但**操作者输入的两个根路径没有任何校验**。
- 【反杀/认账】CLI 形态下这是**操作者信任模型**（与"自己 cd 到目录跑命令"等价），不构成漏洞；但服务化（REST/H2）时必须变：workspace 由服务端配置、project 走白名单注册、路径规范化 + 前缀校验。**当前不修，但服务化前必须修**——写进缺口。
- 【发散】路径规范化（realpath 前缀校验）/ 符号链接攻击 / zip-slip / 多租户目录隔离 / 服务化权限模型
- 【证据】`Workspace.changeDir()` 白名单；D3 探针记录

## 四、LLM 治理

### 拷打 8 · "不重试直接红"是保守还是懒？ ❗️P1
- 【直球】LLM 解析失败为什么不重试？
- 【应答】证据优先：先留原文，防止无限重试烧钱；重试是设计（错误回填）。
- 【锥子】生产模型抖动/限流 3~5% 很常见。你的流水线会**天天红**，然后团队开始无视红灯——可靠性工程常识：误报率高的门禁会被绕过，你的整个门禁体系被一个 LLM 阶段拖成摆设。
- 【反杀/认账】**认账：错误的失败分类。** 正确设计：**传输类错误**（超时/429/5xx）指数退避重试 ≤2 次；**语义类错误**（解析失败/校验不过）不重试（重试大概率复现），标红 + 人工。重试要幂等（callId + attempt 记录，不重复副作用）。**当前一律不重试是 MVP 口径**，列为 P1。
- 【发散】重试预算/退避/抖动、熔断与半开、误报率（false positive rate）作为门禁指标、告警疲劳、SLO 错误预算、幂等重试
- 【证据】`AcGenerator` / `HarnessingTask`（不重试）；`docs/03` D 节（重试为设计）

### 拷打 9 · 留证了 prompt 和响应，但它们也是不可信数据 ❗️P2
- 【直球】LLM 留证有哪些？
- 【应答】prompt 原文 + 响应原文 + 调用索引（模型/耗时/字符数/状态）。
- 【锥子】留证不等于隔离。响应里的内容会进产物、进后续 prompt（未来的 ②③ 阶段上下文）——**prompt 注入的传播链**：需求文本里写"忽略指令"就可能污染下游；而且原文里可能有敏感信息（代码/密钥）落盘无脱敏。
- 【反杀/认账】**认账两个点**：① 注入防护未做（缓解：AC 只是草案 + 机器判定不信任 LLM；但"传播链"未建模）；② 敏感信息脱敏未做（留证 vs 隐私的权衡：证据要真，但密钥不该落盘）。设计：prompt 注入检测（规则/分类器）、上下文隔离（不可信内容标记）、留证脱敏（pattern 扫描 + 报告而非删除）。
- 【发散】间接 prompt 注入 / OWASP LLM Top10 / 数据脱敏与 DLP / 留证与隐私合规（GDPR/个保法）/ PII 检测
- 【证据】`LlmCall` / `FileLlmCallStore`；`evidence/d4-xhs/.../llm/`

## 五、证据与审计

### 拷打 10 · 你的证据可以随便改——"可追溯"≠"防篡改" ❗️P1
- 【直球】证据链怎么保证不被改？
- 【应答】产物有 sha256；事件流 append-only。
- 【锥子】sha256 是**自己算自己存**——改文件的人顺手改哈希就完事了，等于自己批自己的卷子。你说审计哈希链是设计——那"可追溯"到底追什么？出事故要上法庭/合规审计时，你的证据包一文不值。
- 【反杀/认账】精确区分并认账：现在是 **traceable（可追溯）不是 tamper-evident（防篡改）**。演进三级：① 事件行链式哈希（每行含前一行 hash，本地可检测篡改）——纯本地、成本低，**最容易补**；② 关键产物摘要外送（SCM 提交 / 对象存储 WORM / 时间戳服务），把"自证"变成"他证"；③ 签名（GPG/Sigstore）+ 密钥管理（更大工程）。**讲清"自证性证据的内在局限"本身就是加分点。**
- 【后续（2026-09-25）】① 已落地：SHA-256 链式哈希 + `verify` 命令（篡改定位到行，exit 1，见 `evidence/d5-hashchain/`）；②③（外锚/签名）仍为边界。
- 【发散】哈希链/默克尔树 / 时间戳（TSA）/ WORM / Sigstore 与 SLSA / in-toto / 取证与合规
- 【证据】`FileArtifactStore.sha256`；`FileEventLog`（无链式哈希，确认缺口）

### 拷打 12 · LLM ② 编码闭环为什么不做？ ❗️P2
- 【直球】不做编码闭环，"AI 写代码"的价值就少一半吧？
- 【应答】时间盒取舍：先把**验证侧**做深（这是我的差异化），编码闭环列为设计。
- 【锥子】没有闭环 = 你只审稿不写作，演示冲击力大打折扣；而且"验证"这件事，只有配上"生产"才有说服力——否则像考了驾照没开过车。
