## 一、追问清单（按模块）

### A. 状态机与变更生命周期

| 追问 | 答案 |
|---|---|
| 为什么状态机自研，不用 Spring StateMachine？ | 6 个阶段固定、转移简单；核心诉求是"持久化恢复 + 门禁关卡"，Spring StateMachine 的层次/并行/事件能力用不上，且持久化要自己写 StateMachinePersister，收益不匹配。自研转移表是唯一事实源，单测直接覆盖。 |
| 两个请求同时推进同一个变更？ | 已实现（D5）：per-change 锁（跨进程 `FileLock` + 同进程 `Semaphore`），`advance/approve` 全程持锁；`save` 再加版本前置条件（文件版 CAS，版本未前进即拒）。锁是单机 advisory，多实例需 DB 锁/分布式锁（设计）。 |
| ① 阶段 LLM 生成的规格怎么保证靠谱？ | HITL（已实现 D5）：① 阶段通过后状态置 `AWAITING_APPROVAL`，必须 `approve` 才能进 ②；未审批的 advance 被拒（exit 3）。approve 会校验"待审批产物存在"（产物被删则拒绝）；人工审阅产物（AC 草案 + 门禁证据）。审阅签名/产物 diff 校验为设计。 |
| 服务重启后怎么恢复？ | 状态在 H2；启动时扫描 IN_PROGRESS 的变更，其中 RUNNING 的 StageRun 视为"中断"→ 标记 FAILED（可重试）；PASSED 阶段不重复执行。 |
| 重试会不会重复副作用（重复写文件/重复调 LLM）？ | 产物按 `(changeId, type, version)` 幂等覆盖；LLM 调用按 attempt 记录；命令天然可重跑；每次重试 attempt+1，历史保留可对比。 |
| 阶段"通过"的标准？ | 该阶段所有门禁 PASS（结果落 `gate_result`）；引擎只在门禁全绿时调 `advance()`。 |
| 非法转移怎么处理？ | 转移表校验，非法直接抛 `IllegalStateTransitionException`；所有状态变更必须走聚合根方法（不暴露 setter）。 |

### B. 门禁执行器（最值钱的坑）

| 追问 | 答案 |
|---|---|
| 子进程卡死怎么办？ | 两个机制：① **stdout/stderr 并发读**——不读会因管道缓冲区满导致子进程阻塞（最常见的"命令假死"）；② `waitFor(timeout)` 超时后 `destroyForcibly` + 进程树清理（`ProcessHandle.descendants()`）。 |
| 为什么不用 Maven Invoker API？ | 通用性（未来要跑 npm/go test/自定义脚本）+ 进程隔离（Maven 崩了不影响引擎）+ 真实退出码；代价是流/超时/进程树要自己处理——这些坑也是价值。 |
| 命令注入怎么防？ | 命令模板来自配置（非用户输入）；需求文本只进 LLM prompt，不拼进命令；参数用 ProcessBuilder list 形式（不经过 shell 解析）。路径注入同理：changeId 白名单校验（`[A-Za-z0-9_-]{1,64}`），防 `../` 越界（review 时探针实测可利用，已修）。 |
| 输出几 MB 怎么办？ | 完整日志落文件（`outputRef` 存路径）；内存里用上限截断；解析只扫关键行（BUILD SUCCESS / 覆盖率百分比）。 |
| 覆盖率门禁怎么判定？ | 解析 JaCoCo **XML/CSV 报告**（不解析控制台文本，避免格式漂移）；按包/类过滤"核心逻辑"再比对阈值。**坑（已踩）**：JaCoCo XML 带外部 DTD，JDK 安全解析默认禁止读取外部 DTD 导致解析失败——需关掉 `load-external-dtd`（或自定义 EntityResolver）。 |
| 门禁失败后阶段还能推进吗？ | 不能——门禁全绿是 `advance()` 的前置条件；失败置 FAILED，可重试（attempt+1）。 |
| 测试门禁怎么防"假绿"？ | 不只信 exitCode：必须解析到 surefire 汇总且 `testsRun>0`，无汇总 / 0 测试直接红；红时 reason 带 testsRun/failures/errors 证据；**全部测试被跳过（`testsRun - skipped <= 0`）也判红**（基准实测）。 |
| 门禁的有效性怎么量化？ | 故障注入基准：7 类故障场景真实跑 mvn——6 类应拦截全部检出（100%）、4 项基线无假阳性；报告与全量日志在 `evidence/benchmark/`。 |
| "假测试"（assertTrue(true)）怎么防？ | TEST 门禁只能验证"测试发生"（设计边界）；**变异门禁（PIT）**用变异得分 `KILLED/(KILLED+SURVIVED+NO_COVERAGE)` 判定——基准里假测试在 TEST 门禁绿、在 MUTATION 门禁红（0%，4 个 NO_COVERAGE）。前提：项目声明 `pitest-maven` + `pitest-junit5-plugin`。 |
| 存量项目覆盖率阈值怎么不被博弈/不误伤？ | **增量覆盖率（D5.8）**：只卡 diff 变更行——基准对照：新增未测 10 行 → 0% < 80% 红；新增已测方法 → 100% ≥ 80% 绿；变更无可执行行则跳过阈值。治 Goodhart 与存量债；前提 git 仓库 + base ref，测试行不计入。 |
| 覆盖率门禁跑两次 `mvn test` 浪费怎么办？ | COVERAGE 门禁命令内置 `prepare-agent → test → report`，同一输出顺带解析测试数；D4 编排用 COMPILE + COVERAGE 两条门禁即可拿到编译 + 测试 + 覆盖率三类证据。 |

### C. 产物与对账

| 追问 | 答案 |
|---|---|
| 产物版本怎么管？ | 每阶段成功写新 version（自增）+ sha256 完整性校验；旧版本保留可对比。 |
| 怎么证明"每条 AC 都被测试覆盖"？ | 迭代协议 AC/TC 编号映射（AC-1 → TC-1..n）；门禁校验映射完整性，无映射的 AC 直接红。 |
| 事件日志干什么用？ | 状态流转全记录（审计、问题回放、统计阶段耗时/拦截次数）。append-only JSONL：读取容忍截断行（崩溃半写不毒化后续读取），追加前检测残缺尾巴先补换行（防止"粘行"吞掉下一条事件）。 |
| 证据怎么防篡改？ | 事件链式哈希（已实现 D5.7）：每条事件含 `prevHash/hash`（SHA-256，链首 GENESIS），`verify` 命令逐条复算，篡改定位到行（exit 1）。**诚实边界**：防的是局部篡改；整链重写需外锚（SCM/WORM/TSA/签名）——"自己算自己存"不能自证。 |
| 为什么引擎用文件仓储而不是直接上 H2？ | 单机零依赖，一个 change 目录自包含（change.json / stage-runs.json / events.jsonl / artifacts），可直接当证据包拷走；仓储全走端口，H2 适配器后补即可。 |
| CLI 和引擎的边界？ | CLI 只做参数解析与展示；状态推进、门禁执行、产物落盘全部在 engine；CLI 换 REST 时 engine 不动。 |

### D. LLM 编排（① 已实现；降级/预算/知识库为设计）

| 追问 | 答案 |
|---|---|
| 结构化输出怎么保证？ | ① 阶段已实现：prompt 约束 JSON 格式 + `response_format=json_object` + 解析后做可测性校验（AC 非空/id 唯一/描述非空）；解析失败不重试，直接红并把原始输出与 prompt 全量留档（`llm/` 目录）。重试 ≤2 次与错误回填是设计（② 阶段一起做）。 |
| 演示为什么是 fake provider？有没有真跑过？ | 演示机无 API Key，按设计走 fallback，但 prompt/响应全留档；OpenAI 兼容客户端是真实实现并有单测（本地 HttpServer 验证请求体/鉴权/响应解析/500 与缺 content 的错误路径），配 `HARNESS_LLM_API_KEY` 即切换。 |
| 模型不稳定/超时？ | 降级链：主 → 备用 → 轻量；仅传输类错误重试（已出流不重放，防重复副作用）；熔断半开探测。**设计**，未实现。 |
| 成本怎么控？ | Token 预算三段：真实计量 → 软限 80% 切轻量 → 硬限 429；工具 schema 也计入预算。**设计**；当前只记录 promptChars/outputChars 与 tokens 字段。 |
| Prompt 怎么组装？ | ① 阶段已实现：模板（`prompts/harnessing-ac.md`）+ 占位符注入（项目/需求）；技能 SKILL.md 提取 + 上下文预算截断（rules/CONTEXT/产物摘要）是设计。 |

## 二、决策卡（8 个设计决策）

| # | 决策 | 为什么 | 备选与取舍 |
|---|---|---|---|
| D1 | 服务形态（而非纯 CLI 库） | 要状态持久化、多项目、可观测、可查询 | 纯 CLI：轻，但无法多项目/历史查询 |
| D2 | 状态机自研 | 阶段固定 + 门禁关卡 + 断点恢复；转移表=唯一事实源、可单测 | Spring StateMachine：抽象重、持久化要自接 |
| D3 | 门禁走子进程 | 通用（任意命令）+ 进程隔离 + 真实退出码 | Maven Invoker：只支持 Maven、同 JVM 风险 |
| D4 | LLM 独立模块 | 路由/降级/预算/计量是横切关注点，各阶段共用；便于 mock 单测 | 内联各阶段：重复代码、难统一治理 |
| D5 | v1 只做 Java/Maven | 门禁命令与工程结构强绑定语言；先做深再扩宽 | 一开始多语言：广而浅，解析全要重做 |
| D6 | 阶段产物 + 门禁（非一口气做完） | 每阶段可校验/可重入/可追责；失败可定位 | 一口气：失败无法定位、无证据、不可重入 |
| D7 | 存储默认 H2 文件（MySQL 可选） | 单机资源受限；零安装、单文件；schema 同构可切 | MySQL：更生产但需服务；纯内存：不能断点续跑 |
| D8 | 目标项目可配置（不绑定 xhs） | 门禁/部署命令参数化；引擎通用 | 硬编码：只能服务一个项目 |

### 重点展开 · D2 状态机自研

- **需求本质**：6 个阶段、顺序推进、门禁关卡、失败重试、可暂停、可恢复——是一个**确定性的有限状态机**，不需要层次/并行/复杂事件。
- **关键约束**：状态必须持久化（服务重启可恢复）→ 状态机与存储强耦合，框架的 `StateMachinePersister` 要自己实现，省不了多少事。
- **收益**：转移表 20 行代码 + 单测全覆盖，行为完全可控可解释。
- **代价**：没有可视化/复杂事件支持——但本项目用不到。

### 重点展开 · D3 门禁走子进程

- **需求本质**：门禁要跑"任意命令"（mvn/脚本/未来 npm/go），且要**真实退出码**与**进程隔离**。
- **踩坑点（真做过才答得出）**：`ProcessBuilder` 的 stdout/stderr 管道有缓冲区，**不并发读会阻塞子进程**（表现为命令永远不结束）；超时后要清理**整棵进程树**（Maven 会 fork JVM），否则僵尸进程占资源。
- **备选 Maven Invoker**：只支持 Maven 且跑在同 JVM，插件/类加载冲突风险，退出码语义也不如进程真实。
